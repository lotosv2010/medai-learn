# 从 Token 到上下文窗口：模型眼里的文字长什么样

> 128K 的窗口，真正好用的可能只有一半——而且中文比英文贵。

## 🎯 这篇文章解决什么问题

上一篇结尾留了个尾巴：你只发了 20 来个汉字，账单算你 28 个 token。

这个「为什么」背后，是整篇文章。

对大部分刚上手的人来说，大模型是一个黑箱：prompt 进去，文字出来，账单按月扣。中间发生了什么，一概不知。而这层黑箱恰恰是所有成本优化、长文档处理、上下文设计的地基——你不理解 token，就只能拍脑袋估钱；不理解窗口，就只能靠「塞进去试试」；不理解注意力稀释，就会把「模型漏看了」误判成「模型不够聪明」。

这篇文章要解决四件事：

- Token 到底是怎么来的，为什么中文比英文贵——以及贵多少
- 一张账单怎么算出来的，为什么输出比输入贵好几倍
- 上下文窗口为什么是硬上限，增大它的真实代价是什么
- 为什么「整本说明书塞进去」，它偏偏漏了中间那条

每一段照旧配「面试官会怎么问」，以及标准答案和加分答案。读完你不只是懂了，是能答了。

## 🔍 一份说明书，塞得进去却读不出来

先看一个真实会发生的事。

做一个用药咨询助手，用户问：「这个药的禁忌人群有哪些？」

开发的做法很自然：说明书 PDF 解析成文本，大约 6 万 token，直接整份塞进 prompt，后面附一句「请根据以上说明书回答」。

模型的回答很漂亮。列了五条禁忌，格式规范，语气专业。

但你回头核原文，第 3 章明确写着：**重度肝功能不全者禁用。**

它没提。

于是有两种解释：

- **它没看到。** 但 6 万 token 明明远在 128K 窗口之内，物理上就在那里。
- **它看到了，但没「用上」。** 这才是真相。

这两件事的区别，就是这篇文章的全部。

我们习惯用一个直觉理解上下文窗口：**窗口是一块地方，东西放进去，模型就能读到。** 这个直觉在短 prompt 上完全成立——你问一句，它答一句，从不出错。但在长文本上，它开始崩。

要拆掉的其实是三个直觉：

| 你以为 | 实际 |
|---|---|
| 塞得进去就能读到 | 有效注意力远小于标称窗口 |
| 窗口越大越好用 | 代价是显存、并发、延迟和钱 |
| 成本按字数估 | 按 token 算，而且中文更贵 |

三个直觉，对应下面五节原理。我们一个一个拆。

## ⚙️ 原理讲透：Token、窗口与注意力

### Tokenizer 的本质：文本 → 子词 → 整数 ID

模型不认识字。它只认识数字。

中间那一步转换，叫 **tokenizer（分词器）**。流程是三段：**原始文本 → 切成若干 token（子词）→ 查表映射为整数 ID → 送进模型**。

以「阿莫西林」为例，它会被切成 `["阿", "莫", "西林"]` 三个子词，再查表变成 `[23_478, 9_931, 118_204]` 这样的整数序列。模型全程只碰这三个数字，从未见过那几个汉字。

![每个 token 查表得到一个向量：模型真正处理的是这些数字，文字只是给你看的](https://jalammar.github.io/images/gpt2/gpt2-token-embeddings-wte-2.png)

模型的词表通常在 5 万到 20 万之间——这是它能「认识」的全部符号集合。

那为什么不直接把每个汉字当一个 token？或者把每个英文单词当一个 token？

两种极端各有致命问题：

- **按整词切**：词表会爆炸到几百万（还要覆盖各种变形、专有名词、新词），而且遇到词表里没有的词就彻底没法处理。
- **按单字（字符）切**：序列会变得极长。一个英文单词要占 8-10 个位置，而注意力的计算量随长度平方增长——直接算不动。

**子词（subword）** 是这两者之间的折中：常见的高频组合整块保留成一个 token，罕见的词拆成几段有意义的片段。这样词表规模可控，序列长度也可控。

具体怎么决定「什么算高频组合」？主流做法叫 **BPE（Byte Pair Encoding）**，直觉只有四步：

- 从最细粒度的单元开始（字节 / 字符），此时每个单元只是一个碎片
- 统计语料里相邻两段一起出现的频率
- 把频率最高的那一对合并成一个新单元
- 把「统计频率 → 合并最高频」这两步重复几万次

跑完几万轮，你就得到了一份「哪些组合被合并成了一个 token」的规则表。所以：

**token 不是「字」，不是「词」，是从语料统计里长出来的高频片段。**

这解释了一个容易困惑的现象：同一个词在不同上下文里，切法可能不一样。因为 BPE 合并是按序列局部做的贪心决策，前后文不同，贪心路径就可能不同。

> 💬 **面试官**：Token 是什么？和字符、单词有什么区别？
>
> ✅ **标准答案**：Token 是 tokenizer 切分出来的子词单元，是模型真正处理的单位，也是计费单位。它既不是字符也不是单词——常见词可能一个词只占 1 个 token，罕见词会被拆成好几段。
>
> 🎁 **加分答案**：所以「字数」和「token 数」之间没有固定换算率。更重要的是——**不同厂商的 tokenizer 完全不同**，同一段文本在 A 家和 B 家算出来的 token 数不一样。做成本估算必须用目标模型自己的 tokenizer 去算，拿别家的数字套会系统性偏差。工程上这一点经常被忽略。

🔧 **真实场景**：给业务方报成本时，如果按「字数 ÷ 2」粗估，在中文场景会低估接近一半。安全的做法是跑一遍真实 tokenizer，把「每条请求平均 token 数」做成一个可观测指标。

### 为什么中文更贵

回到 BPE 的合并规则——它是**从语料里统计出来的**。

而主流 tokenizer 的训练语料，英文占绝对大头。结果就是：

- 英文的高频组合被充分合并。`information`、`treatment`、`capsule` 这类词，1 个 token 就够了。
- 汉字在语料里出现的绝对次数少得多，很多字根本没被合并成独立 token，停留在「字节级」。

一个汉字在 UTF-8 里占 3 个字节。如果这个字没被合并成一个 token，它就会被拆成 2-3 个字节级 token。

下面这张图是这个现象的直观对照：同一段语义，英文和西班牙语基本是「一个词一个色块」（一个 token），而最下面那行日语假名，每个字符都被拆成了两个色块：

![同一句话的三种语言：英文和西语一个词就占一个 token，日语假名每个字符被拆成两个 token](https://static.simonwillison.net/static/2023/gpt-token-encoder-decoder.jpg)

中文的处境和那行假名是一样的——不是中文「不紧凑」，是分词器没见过足够多的中文。

于是就有了这个反差：

- **英文**：一个常用单词 = 1 个 token
- **中文**：一个汉字 = 1 到 3 个 token

同样表达一个意思，中文的 token 数常常是英文的 1.5-2 倍。这个比例在不同厂商的分词器上会有差异（下文实验会给出示意数字），但「中文更贵」这个方向是普遍的。

注意这里有个反直觉的地方：中文的表达非常紧凑，字符数往往只有英文的 1/4；但 token 数反而更多。**你眼睛看到的信息密度，和模型实际处理的单位密度，是两套账。**

> 💬 **面试官**：中文和英文表达同一个意思，token 数一样吗？
>
> ✅ **标准答案**：不一样，中文通常更贵。因为 BPE 的合并规则是按语料频率学出来的，主流分词器训练语料以英文为主，汉字常被拆成 2-3 个字节级 token，而常见英文单词只占 1 个。同语义下中文 token 数常是英文的 1.5-2 倍。
>
> 🎁 **加分答案**：要说清这不是「语言缺陷」，而是**分词器训练数据分布**的结果。国产模型（通义、DeepSeek、Qwen 等）在中文语料上训练更充分，中文 token 效率通常明显更好。所以中文场景选国产模型，不只是合规和价格问题，也是 token 效率问题——这一条在选型讨论里很少有人提，提出来就是加分点。

🔧 **真实场景**：同一套 prompt 模板，中文版和英文版在英文优先的分词器上成本可能差一倍。但**不要**因此就把中文任务改成英文 prompt——prompt 语言会显著影响输出质量，省的是输入那几毛钱，赔的可能是一整轮效果。正确的方向是换中文效率更好的模型，而不是硬改 prompt 语言。

### 计费公式：输入便宜，输出贵

账单的算法只有一行：

```text
成本 = 输入 token 数 × 输入单价 + 输出 token 数 × 输出单价
```

看似平淡，但有个关键不等式：**输出单价通常是输入的 3-5 倍。**

为什么？从上一篇的生成机制就能推出来：

```text
输入（prefill）：整段一次性读入，可以高度并行 → 单位成本低
输出（decode）  ：一个一个往外吐，每吐一个都要完整跑一次前向 → 单位成本高
```

输入是「一口气读完」，输出是「一个字一个字写」。后者天然贵。

这个不等式直接决定了成本优化的优先级：

| 输出长度 | 相对成本 | 典型场景 |
|---|---|---|
| 20 token | 1x | 抽取、分类、日期 |
| 200 token | 约 10x | 摘要、一段回答 |
| 2000 token | 约 100x | 长文生成、报告 |

（这里只比输出，把输入视为固定背景。）

所以「让它少说废话」不是风格偏好，是**唯一不需要任何技术改造就能省下来的钱**。

> 💬 **面试官**：输入 token 和输出 token 哪个贵？这对产品设计有什么影响？
>
> ✅ **标准答案**：输出更贵，常见是输入的 3-5 倍。因为输出是逐 token 自回归生成的，每生成一个都要完整跑一次前向计算；输入是并行 prefill，能一次读完且可缓存复用。
>
> 🎁 **加分答案**：由此推出的成本优化顺序是**反直觉的**——第一优先级不是「换便宜模型」，而是「控制输出长度」。产品上的具体手段：默认给简短回答、要求结构化输出（JSON 比散文省）、把长篇解释放到可展开的次要区域、在 prompt 里加约束词（「只回答」「不要解释」「用不超过 50 字」）。这些改动零技术成本。第二优先级才是压缩输入（历史裁剪、摘要、前缀缓存）。

🔧 **真实场景**：把「请详细说明」改成「请用不超过 50 字回答」，输出 token 直接掉一个量级。同一个模型、同一个功能，成本差 5-10 倍，效果在大多数场景下没差别——因为用户根本不读那 500 字。

### 上下文窗口：一次调用的硬上限

**上下文窗口 = 一次 API 调用里，输入 token + 输出 token 加起来的上限。**

「加起来」这三个字是重点。128K 窗口不是「能塞 128K 输入，然后还能再答 128K」，而是两者共享这 128K。

超过会怎样？两种结局：直接报错拒绝，或者被截断（截哪一端由厂商决定，通常砍最早的对话历史）。

那为什么窗口不能做成无限大？三个真实约束，一个比一个硬：

**第一，注意力计算量是平方级的。** 标准注意力里，每个 token 要和它前面的所有 token 算相关性。序列长度翻倍，注意力部分的计算量约翻 4 倍。

![注意力在做什么：每个位置的输出，都是对前面所有位置的加权汇总——所以序列一长，要算的配对数量就爆炸](https://jalammar.github.io/images/gpt2/gpt2-self-attention-example-2.png)

**第二，显存被 KV Cache 吃掉。** 生成每个 token 都要复用前面所有 token 的中间结果（Key/Value），这段缓存随序列长度线性增长。更致命的是——**每个并发请求独占一份**。所以窗口从 8K 涨到 128K，单请求显存涨 16 倍，能同时服务的用户数掉一个数量级。

**第三，训练语料里长文本本来就稀缺。** 位置编码在超出训练长度的区间上泛化能力会衰减，这是「标称支持但实际变差」的根源之一。

把两个增长关系写在一起：注意力计算量约 **O(n²)**，KV Cache 显存约 **O(n)** 且每并发独占。序列长度 n 放大 16 倍，计算量放大 256 倍，显存放大 16 倍。

所以上下文窗口是一个**被算力和显存定价出来的商品**，不是模型能力的自然刻度。这句话值得记住。

> 💬 **面试官**：为什么上下文窗口有限？扩大窗口的代价是什么？
>
> ✅ **标准答案**：三重代价——注意力计算量随长度平方增长；KV Cache 显存随长度线性增长且每个并发请求独占一份；训练数据里长文本稀缺导致超长区间效果衰减。
>
> 🎁 **加分答案**：由此得到一个反直觉的工程结论：**长文本处理往往不是「用大窗口模型一次塞完」最划算。** 大窗口意味着显存被吃、并发被压、单位 token 反而更贵，且效果还受注意力稀释影响。「切分 + 检索 + 只喂相关片段」在成本和准确率上常常双赢——这就是 RAG 存在的经济动因，不只是「知识不在参数里」这一个理由。

🔧 **真实场景**：日均 1000 次问诊，每次都塞 6 万 token 的完整说明书，光输入成本就是「只喂 2 千 token 相关片段」的 30 倍。一年多出来的钱，够养一套检索系统了。

### 注意力稀释：Lost in the Middle

这是本篇最重要的一段，请慢读。

2023 年有一篇论文做了个很干净的实验。思路极简：

把一条关键信息（「答案是 XXX」）埋进一段长文本里，**只改变它的位置**——开头、中间、结尾，然后问模型同一个问题。其他所有条件不变。

结果画出来是一条 **U 形曲线**：两头命中率高，中间直接塌下去。

更狠的对照是：论文还测了「闭卷」（不给文档，看模型自己记不记得）和「开卷」（给文档）。在长文档场景下，**「开卷但把资料放在中间」的表现，甚至不如闭卷。**

也就是说：把资料塞进去，不但没帮上忙，还起了反作用。

为什么？这里只做现象层解释，不推公式（这一阶段的原则就是「原理够用即止」）：

- **关注预算被摊薄。** Transformer 的注意力本质上是在序列上分配「看哪里」的权重。序列越长，每个位置分到的平均关注越少。
- **训练数据里的重点在两头。** 人写的文本，重要信息倾向于出现在开头（标题、结论先行）和结尾（总结、重申）。模型在这样的数据上训练，自然学成了「重点看两头」。
- **位置编码在超长区间上定位变模糊。** 越靠中间，模型对「这是第几个位置」的感知越弱。

合起来就是一句话：**模型不是没看到中间那段，是「看到了，但没给它足够的权重」。**

这种位置敏感性在「大海捞针」测试里看得最直观。图里横轴是文档长度，纵轴是针被埋进文档的位置（越往下越靠近文档末尾），每个格子的颜色代表「这个位置答对了没有」：

![大海捞针测试的经典热力图：横轴是文档长度、纵轴是针的埋入位置，拿它对照读，能直接看出失败是否集中在某个位置区间](https://raw.githubusercontent.com/gkamradt/needle-in-a-haystack/main/img/GPT_4_testing.png)

读这张图的正确方式，不是看「整体准确率多高」，而是看**颜色是不是随纵轴均匀变化**。如果失败只集中在某一段纵坐标上，那就是位置效应；如果失败随横轴整体变多，那就是长度效应。两种效应叠在一起，就是你亲眼看得到的「有效上下文小于标称窗口」。

工程推论（阶段一先给方向，具体编排策略留到阶段三）：

- **关键约束、关键事实放开头。** 系统指令、禁忌、剂量上限，优先占开头的位置。
- **重要指令可以在结尾重复一次。** 首尾双重保险在长 prompt 上收益明显。
- **长文档不要「整份塞」。** 先切分、先检索，只喂相关片段——既省钱，又避开中段塌陷。
- **让模型「先引用、再回答」。** 强制它去原文定位，能显著降低跳读概率。

> 💬 **面试官**：什么是 Lost in the Middle？工程上怎么规避？
>
> ✅ **标准答案**：模型在长上下文里，对中间位置信息的利用率显著低于开头和结尾，呈现 U 形的位置敏感性。规避手段是把关键信息前置、必要时在结尾重复、把长文档切分后只喂相关部分、要求模型先引用原文再作答。
>
> 🎁 **加分答案**：要强调这是**系统性偏差，不是能力不足**。它由注意力机制和训练数据分布共同决定，所以换个更强的模型只会减弱、不会消失——指望「模型升级了这问题就没了」是错误的工程预期。进一步：评估一个模型的长上下文能力，必须做**位置分层测试**，只看整体准确率会把中间塌陷完全掩盖掉。

🔧 **真实场景**：回到开头那个漏掉「重度肝功能不全者禁用」的案例。这条禁忌在说明书第 3 章，整份 6 万 token 塞进去，它正好落在中段。正确做法是：按章节切分 → 检索出「禁忌」那一段（可能只有 800 token）→ 放在 prompt 开头 → 再问。同一份资料，同一个模型，准确率天差地别。

## 🧪 动手实验：两次量化

> **说明**：下面这段是脚本的**运行形态示意**，其中的 token 数字与命中结果均为示意值，真实数值以你本机运行为准。脚本已就绪：`labs/phase1-cognition/01-token-window/`，一条命令即可跑通。

两个实验，一个测「贵不贵」，一个测「读不读得到」。

```bash
# 在仓库根目录
pnpm install
cp .env.local.example .env.local    # 实验 B 需要 DEEPSEEK_API_KEY

```

实验 A 是纯本地计算，**零成本**，配不配 key 都能跑。实验 B 要真实调用，约 ¥2-4，脚本启动会先打印预估。

### 实验 A：同一句话，三种写法的 token 消耗

选一段医学语义完全等价的内容，分别写成中文、英文、代码：

```typescript
const SAME_MEANING = {
  中文: '阿莫西林胶囊适用于敏感菌所致的上呼吸道感染，成人常用量为每次零点五克，每六至八小时一次。',
  英文: 'Amoxicillin capsules are indicated for upper respiratory tract infections caused by susceptible bacteria. The usual adult dose is 0.5 g every 6 to 8 hours.',
  代码: "const dose = { adult: 0.5, unit: 'g', intervalHours: 8 }",
}

const rows = Object.entries(SAME_MEANING).map(([label, text]) => {
  const tokens = countTokens(text)
  return [label, String(text.length), String(tokens), (tokens / text.length).toFixed(2)]
})
```

用 `gpt-tokenizer`（tiktoken 的 JS 实现）数 token。示意输出：

```text
写法   字符数   token 数   token/字符
中文   44       50         1.14
英文   163      30         0.18
代码   54       20         0.37
```

三条读数：

**第一，中文 token 数比英文多，尽管字符数只有英文的 1/4。** 44 个字符换来 50 个 token，163 个字符只有 30 个 token。这就是「中文更贵」的量化形态。

**第二，中文的 token/字符接近 1.14。** 意味着平均每个汉字要花超过一个 token——这正是「汉字没有被充分合并成单 token、常被拆成字节级」的直接体现。

**第三，英文的 token/字符只有 0.18。** 平均一个 token 覆盖五个多字符，因为常见词被合并成了整块。

代码那一行值得单独说：它字符密度不如中文，但 token 数并不比同长度的英文更省——变量名、标点、空格各占一块，`intervalHours` 这种驼峰词还会被拆开。**读一段代码，往往比读同等字数的英文更吃 token。**

脚本还会打印一行提示：这里用的是 GPT 的分词器，各家不同、绝对数值有差异，但「中文更贵」的方向是普遍的。

### 实验 B：needle-in-a-haystack

这是一个被广泛使用的长上下文压力测试，思路直白得像它的名字：在一大堆干草里藏一根针，看你能不能找出来。

三个变量，控制到只剩两个：

- **填充长度**：5k / 20k / 80k token
- **针的位置**：开头 / 中间 / 结尾
- 组合起来 = **3 × 3 = 9 次调用**

针是一条唯一事实：

```typescript
const NEEDLE_FACT = '本批号药品的召回截止日是 2027 年 3 月 15 日。'
const QUESTION = '请问本批号药品的召回截止日是哪一天？只回答日期，不要解释。'
```

填充文本用一段药学部规范说明反复重复，凑够目标 token 数。然后把针插到指定位置：

```typescript
function placeNeedle(haystack: string, position: 'head' | 'middle' | 'tail'): string {
  if (position === 'head') return NEEDLE_FACT + '\n\n' + haystack
  if (position === 'tail') return haystack + '\n\n' + NEEDLE_FACT
  const mid = Math.floor(haystack.length / 2)
  return haystack.slice(0, mid) + '\n\n' + NEEDLE_FACT + '\n\n' + haystack.slice(mid)
}
```

判定命中就三件事：答里有年份、月份、日期。`temperature: 0`，问题固定说「只回答日期，不要解释」——把所有非实验变量压死。

示意命中矩阵：

| 长度 | 开头 | 中间 | 结尾 |
|---|---|---|---|
| 5k | ✅ | ✅ | ✅ |
| 20k | ✅ | ❌ | ✅ |
| 80k | ✅ | ❌ | ❌ |

三条读数：

**位置效应。** 中间列 3 次里只中 1 次，两头 6 次里中 5 次。50k 以内完全看不出差别，一过 20k 中段就开始失守。

**长度效应。** 20k 时中间已经失败，80k 时连结尾也保不住。越长的上下文，整体可靠性越低。

**短上下文里位置几乎无影响。** 5k 那行全绿——这就是为什么日常短 prompt 从来不暴露这个问题，也是为什么很多人第一次遇到长文档漏读时会懵。

这张表就是你亲手复现的 Lost in the Middle。

> 💬 **面试官**：你怎么证明「长上下文不是免费的」？
>
> ✅ **标准答案**：做位置分层的压力测试。固定一条关键事实，只改它在输入中的位置和整体长度，看命中率怎么变化。整体准确率会掩盖位置偏差，必须分层看。
>
> 🎁 **加分答案**：这个实验本身的设计思路就是考点——**控制变量**。只让「位置」和「长度」两个变量动，其余全部固定：同一模型、temperature 0、同一问题、同一判定规则。这比「我拿说明书试了试，感觉不太行」有说服力得多，而且它就是评估集设计的雏形（这一套方法到阶段九会正式展开）。

🔧 **真实场景**：这就是为什么长文档功能上线前必须做位置分层评估，而不是「找一份说明书试试看」。试一份、碰巧通过了，只证明那一份的那条信息碰巧不在中段。

## 🚧 结论与边界

本篇的结论可以压成一句话：

> **Token 是计量单位，窗口是硬上限，而有效注意力远小于标称窗口。**

三条推论：

- 成本是「token 数 × 单价」算出来的，不是「调用次数」算出来的。而且输出比输入贵得多，所以控制输出是第一省钱手段。
- 窗口越大不等于越好用。它同时被注意力计算的平方级增长、KV Cache 的显存占用、训练语料的长度分布三重定价。
- 「塞进去」和「读到」是两件事，中间隔着注意力稀释。这个偏差是结构性的，换模型只会减弱。

有意识地留到后面四件事：

- **内容怎么编排、配额怎么分、前缀缓存怎么配** → 阶段三（上下文工程）
- **用检索替代长上下文，RAG 为什么存在** → 阶段四
- **幻觉与知识截止** → 第 02 篇
- **怎么量化「改完之后到底有没有变好」** → 阶段九（评估体系）

## 🎤 面试追问链

单个问题答对只能拿及格分。真正的区分度在追问——面试官会顺着你的答案往下挖，看你有没有真正的体系。

**追问一：「窗口标称 128K，为什么我塞 100K 就报错了？」**

因为窗口是输入 + 输出共享的。你塞 100K，留给输出的只剩 28K；如果你的 `max_tokens` 设得比这大，或者厂商按「必须为输出预留空间」来校验，就会直接拒绝。要按「输入 + 预期输出 + 安全余量」来算可用空间，而不是拿标称窗口直接用。

**追问二：「那把 max_tokens 设小不就行了？」**

可以，但这是权衡，不是免费操作。`max_tokens` 是输出的硬上限，设太小会把回答截断在半句话上——用户看到的是残缺文本，体验比报错更糟。正确做法是**先算预算**：窗口 − 预期输出 − 余量 = 可用输入空间；再按这个空间去决定是压缩历史、切分文档，还是换成更大窗口的模型。

**追问三：「中文更贵，那我用英文写 prompt 是不是更省钱？」**

只对「固定部分的输入」成立，而且有代价。prompt 语言会显著影响输出质量，中文任务用英文 prompt 可能让模型回答得生硬、偏离中文语境，甚至效果下降。省的是输入的几分钱，赔的是整轮效果。相对稳妥的方向是：中文场景优先选中文 token 效率更好的国产模型，而不是硬改 prompt 语言。

**追问四：「Lost in the Middle 换个更强的模型就没了吧？」**

会减弱，不会消失。它是注意力机制和训练语料分布共同导致的系统性偏差，属于「结构性」问题而不是「能力不足」。所以工程上的解法永远是编排（关键信息前置、往返重复、切分检索），不能指望升级模型解决。判断某个模型的长上下文能力好不好，也必须做位置分层测试，看整体准确率会被骗。
