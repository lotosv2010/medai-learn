## 🧩 场景切入：从归并排序到深比较两棵处方树

分治这个词听着抽象，但它其实藏在你写过的很多代码里。先看三个真实场景，把直觉建起来。

### 归并排序：分治最直观的教科书案例

归并排序就是分治本身。它做三件事：

```
分：把数组从中间一分为二
解：递归地对两个子数组进行归并排序
合：合并两个有序子数组
```

画成图，就是一棵「先往下拆、再往上合」的树：

```
              [38, 27, 43, 3, 9, 82, 10]          ← 原始数组
                    /            \
        分        [38,27,43,3]      [9,82,10]      ← 一分为二
                 /      \          /      \
              [38,27]  [43,3]   [9,82]   [10]     ← 继续拆
              /   \    /   \    /   \      |
            [38] [27] [43] [3] [9] [82]  [10]     ← 拆到单元素（不再拆）
              \   /    \   /    \   /      |      ← 开始「合」
              [27,38]  [3,43]   [9,82]   [10]     ← 两两合并成有序
                 \      /          \      /
                [3,27,38,43]      [9,10,82]       ← 继续合并
                    \                 /
              [3, 9, 10, 27, 38, 43, 82]          ← 全部有序
```

左边那半「往下拆」是**分解**，右边那半「往上合」是**合并**。注意一个关键点：**「合」这一步才是让结果变有序的地方**。单元素子数组天然有序（不需要排），真正的排序工作全部发生在「把两个有序数组合并成一个更长的有序数组」这个动作里。

![归并排序的「拆分 → 合并」递归树（发布前请自行转存素材库）](https://cdn.jsdelivr.net/gh/krahets/hello-algo@main/docs/chapter_divide_and_conquer/divide_and_conquer.assets/divide_and_conquer_merge_sort.png)

上面这张图（来自开源算法教程《Hello 算法》的分治章节）把「先自顶向下拆成单元素、再自底向上两两合并」的完整过程画了出来——上半部分是分解，下半部分是合并。（推荐搜索关键词：「归并排序 递归树 拆分合并 示意图」）

💡 顺带回忆一下第 10 篇《排序》讲过的：归并排序是**稳定排序**，因为合并两个有序数组时，遇到相等元素我们总是**先取左边**的，不会打乱原本的先后顺序。这跟快速排序不同——快排会在分区时把相等元素乱甩，所以不稳定。

关于归并排序的完整手写实现和三路分区、TimSort 的细节，第 10 篇已经讲透了，本篇聚焦的是它背后那个「分治」的骨架。

### 深比较两棵处方对象树：树结构天然适合分治

🔧 **真实场景**：在药品电商的「处方审核」页面，医生修改了处方后，前端要判断「新处方和旧处方到底哪里变了」，才能决定是整体重渲染、还是只更新变化的字段。处方对象是一棵嵌套的树：

```typescript
interface Prescription {
  id: string;
  patient: { name: string; age: number };
  drugs: Array<{ code: string; dosage: string; frequency: string }>;
}
```

要判断两棵这样的对象树是否「深度相等」，最直白的做法是**递归分治**：

```
分：把「比较两棵树」拆成「比较根节点的每个字段」
解：对每个字段，如果是对象/数组，递归地深度比较
合：所有字段都相等，两棵树才相等
```

这跟「相同的树」（下面高频题会讲到）是同一个套路。**树这种递归定义的数据结构，天然就适合分治**——因为「比较一棵树」可以完全由「比较它的每棵子树」组合出来。

> 💬 **面试官**：判断两个对象是否深度相等，你会怎么写？为什么不用 `JSON.stringify` 比较？
>
> ✅ 标准答案：用递归分治——先比类型，再比字段，字段是对象/数组就递归比下去。**不用 `JSON.stringify` 的三个原因**：① 它不保证 key 的顺序，`{a:1,b:2}` 和 `{b:2,a:1}` 逻辑相等但字符串不同；② 它无法处理循环引用（直接抛 `Converting circular structure to JSON`）；③ 它会把 `undefined`、函数、`Symbol` 等类型丢掉，`{a: undefined}` 会被序列化成 `{}`，导致误判相等。
>
> 🎁 加分答案：能补一句——工程上比较对象树，还有一种思路是**只比较变化的子树**：给树的每个节点算一个哈希（子树哈希），下次比较时先比根哈希，哈希相同就整棵子树跳过。这正是 **Merkle 树**的思想，Git 的版本管理、以及一些前端状态库（如 immutable 结构）都用它把「全树比较」降成「只比变化路径」。

### 分片处理大数据：外排序里的分治

🔧 **真实场景**：运营要导出「全平台 1000 万条用药记录」，按销量排序后给分析师。如果一次性把 1000 万条读进内存排序，浏览器标签页直接内存溢出崩溃。真实做法是**分治 + 分片**：

- **分**：把 1000 万条切成 20 个 50 万条的分片
- **解**：每个分片单独在内存里排好序
- **合**：把 20 个「各自有序」的分片归并成一个全局有序序列

这就是**外排序（external sorting）**的核心思想——当数据大到内存装不下时，利用「归并只需要顺序读取两个有序序列」的特性，把大问题拆成能装进内存的小问题。数据库的 `ORDER BY` 超大结果集、Hadoop 的 MapReduce，底层都是这个套路。

⚠️ 顺便说一句：这也解释了为什么「有序」这么值钱——**两个有序序列合并是 O(n) 的线性操作**（两路归并只从头扫一遍），但两个无序序列合并排序是 O(n log n)。先把问题拆到「天然有序」（单个元素），再用廉价的合并逐步拼回来，这就是分治便宜的地方。

## 📌 分而治之到底是什么

三个场景看完，可以下定义了。

**分而治之（Divide and Conquer）**，是**算法设计**中的一种方法。它将一个问题**分**解成多个和原问题相似的小问题，**递归解决**小问题，再将结果**合**并以解决原来的问题。

拆开这句话，有三个不可省略的动作，对应三个英文单词：

| 动作 | 英文 | 含义 |
|------|------|------|
| 分 | Divide | 把大问题拆成同类的小问题 |
| 治 | Conquer | 递归求解这些小问题 |
| 合 | Combine | 把小问题的解组装成大问题的解 |

**关键认知：分治是一种「算法设计范式」，不是某一种具体算法。** 归并排序是它、快速排序是它、二分搜索是它、快速幂也是它——它们长得不一样，但骨架完全一致：**拆 → 递归 → 合**。

很多人会把它和「递归」混为一谈。区别在于：**递归是「函数怎么调用自己」的机制，分治是「先拆、再解、后合」的完整套路**。递归是分治的实现手段，分治是递归的应用目的——你完全可以写出一个递归函数，但它根本不是分治（比如递归遍历一棵树打印所有节点，它就没有「合并子问题结果」这一步）。

## ⚙️ 分治三步骤：分解 → 解决 → 合并

把上面那个范式拆细，就是标准的**三步**。这三步是面试里问得最多的地方，先记住名字，再看每步具体在干什么。

### 分解（Divide）

**把大问题拆成规模更小的同类子问题。** 注意「同类」两个字——拆出来的子问题，必须和原问题是**同一种问题**，只是规模更小。正是因为「同类」，才能用递归解决它。

- 归并排序里：把数组从中间一分为二，得到两个「需要排序的数组」——和原问题同类
- 二分搜索里：把搜索区间砍成一半，得到「在更小区间里找目标」——同类
- 快速幂里：把 `x^n` 拆成 `x^(n/2)` ——同类

### 解决（Conquer）

**递归求解子问题。** 如果子问题足够小（到了 base case），就直接给出答案；否则继续拆。

- 归并排序里：子数组长度 ≤ 1 时，它天然有序，直接返回
- 二分搜索里：区间为空时说明没找到
- 快速幂里：`n === 0` 时返回 1

### 合并（Combine）

**把子问题的解组合成原问题的解。** 这一步是分治最容易被忽视、却最关键的环节。

- 归并排序里：把两个有序子数组合并成一个有序数组（两路归并）
- 二分搜索里：**没有合并步**——因为在某个子区间里找到了答案，直接返回即可
- 快速幂里：`x^n = (x^(n/2))²`，把子问题的结果平方

> 💬 **面试官**：分治的三步骤是什么？「合并」步为什么是关键？
>
> ✅ 标准答案：三步是**分解（Divide）、解决（Conquer）、合并（Combine）**。**合并步是关键，因为它才是分治区别于普通递归的分水岭**——普通递归只是「自己调用自己」，而分治必须能把「子问题的解」组装回「原问题的解」。没有合并步，就只是把问题拆散了，问题并没有被解决。比如二分搜索只是「每次丢掉一半」，丢了之后剩下的区间自己就是答案，所以它不需要合并步；而归并排序必须把两个有序数组真正合并起来，结果才有意义。
>
> 🎁 加分答案：能进一步说——**「合并」的代价直接决定了分治的复杂度**。主定理 `T(n) = aT(n/b) + f(n)` 里的 `f(n)`，就是这一步的成本。归并排序的合并是 O(n)（要扫一遍两个子数组），所以最终是 O(n log n)；如果某个分治算法的合并能优化到 O(1)，复杂度就会大幅下降。能意识到「合并步成本影响整体复杂度」，说明你真的理解了三步骤的分量，而不是背下来的。

**用归并排序把三步串一遍**（这是回答「举例说明分治」的标准素材）：

```
mergeSort(nums):
  ① 分解：mid = n / 2，拆成 nums[0..mid] 和 nums[mid..n]
  ② 解决：递归 mergeSort(左半) 和 mergeSort(右半)
        —— 直到子数组长度为 1（天然有序）
  ③ 合并：把两个有序的子数组，两路归并成一个有序数组
```

## 🆚 分治 vs 递归 vs 动态规划

这是本篇**最重要的一节**，也是很多人学完分治和 DP 后依然分不清的地方。我们用一张表把三者的关系彻底理清。

### 分治一定是递归，但递归不一定是分治

先厘清「递归」和「分治」的关系：

- **递归是机制**：函数调用自身。—— 它是实现分治的**手段**
- **分治是范式**：拆 → 递归解 → 合并。—— 它必须满足「子问题独立 + 有合并步」

所以：**凡是分治，一定用到了递归；但用递归的代码，不一定构成分治。** 判断标准就是两个：

1. 子问题是否**相互独立**（各算各的，互不依赖）
2. 是否有明确的**合并步**（要把子结果组装回来）

### 核心分野：独立 vs 重叠

分治和动态规划的真正区别，藏在一个词里：**子问题是否重叠**。

- **分治的子问题相互独立**：归并排序把数组拆成两半，左半和右半的排序过程**各算各的，互不干扰**，没有任何一个子问题被算两次。所以**不需要记忆化**。
- **DP 的子问题相互重叠**：求斐波那契 `fib(5)`，需要 `fib(4)` 和 `fib(3)`；求 `fib(4)` 又需要 `fib(3)` 和 `fib(2)`——注意 **`fib(3)` 被算了两次**。这些重复的子问题，正是 DP 要缓存下来（记忆化）的东西。

一句话总结：

> **子问题独立 → 分治；子问题重叠 → 动态规划。**

这就是为什么**归并排序不需要记忆化，而斐波那契需要**。归并排序的子问题（各半区间的排序）天然不重复，缓存毫无意义；斐波那契的朴素递归子问题大面积重复，不缓存就是指数级爆炸。

### 三者对比表

| 维度 | 普通递归 | 分治 | 动态规划 |
|------|---------|------|---------|
| 是否自己调用自己 | ✅ 是 | ✅ 是 | ✅ 是（或改写为迭代） |
| 子问题是否独立 | 不限 | ✅ **相互独立** | ❌ **相互重叠** |
| 是否有合并步 | 不一定 | ✅ **必须有** | 不需要（取最优即可） |
| 是否需要记忆化 | 不需要 | ❌ 不需要（子问题不重复） | ✅ **必须**（避免重复计算） |
| 典型代表 | 树遍历、阶乘 | 归并排序、快排、二分、快速幂 | 斐波那契、编辑距离、背包 |

### 怎么判断该用分治还是 DP

给一个递归问题，按这个顺序判断：

- **第一步：子问题会不会被重复计算？**
  - 不会重复 → 往**分治**想（归并排序、快排、二分、树的递归）
  - 会重复 → 往**DP** 想（斐波那契、编辑距离、最短路径、背包）
- **第二步：有没有「合并步」？**
  - 有 → 更确定是分治
  - 没有，只是「取所有子问题里的最优」→ 更确定是 DP（DP 是取 min/max/最优，不是组装）

> 💬 **面试官**：分治和动态规划的本质区别是什么？如何判断一个递归问题该用分治还是 DP？
>
> ✅ 标准答案：**本质区别在「子问题是否重叠」**。分治的子问题相互独立、互不依赖，各算一次就够了，所以不需要缓存；动态规划的子问题**相互重叠**、会被反复用到，所以必须用记忆化（或 DP 表）把结果存下来，否则就是指数级重复计算。判断方法：先问「同一个子问题会不会被算很多次」——不会重复就是分治，会重复就是 DP。
>
> 🎁 加分答案：能再补两层——① 从**结果形态**上分：分治是「把子问题的**解合并**成原问题的解」（归并排序合并两个有序数组）；DP 是「在子问题的解里**取最优**」（最短路径取 min、背包取 max）。② 从**方向**上分：DP 有自顶向下（记忆化递归）和自底向上（DP 表）两种写法，而分治基本只有自顶向下一种（因为你没法「自底向上」地把数组拆开）。能说出这两条，就把两者的区别讲到了骨子里。

## 📐 主定理（Master Theorem）：分治复杂度的尺子

讲完了分治是什么、怎么用，现在来回答最难的那一问：**怎么算分治的复杂度？**

面试官问「归并排序为什么是 O(n log n)」，如果你只会说「因为分成两半、每层合并 O(n)、一共 log n 层」——这是**递归树**的直觉解释，能用，但不够严谨。想答得漂亮，得掌握**主定理**这把「尺子」。

### 分治的递归式长什么样

所有分治算法的复杂度，都能写成一个统一的形式：

```
T(n) = a·T(n/b) + f(n)
```

三个参数的含义：

- **`a`**：每个问题被拆成几个子问题（比如归并排序拆成 2 个）
- **`n/b`**：每个子问题的规模（比如归并排序每个规模是 n/2）
- **`f(n)`**：分解 + 合并这一步的额外开销（比如归并排序的合并是 O(n)）

把这个式子翻译成「递归树」的直觉：

```
                     f(n)                    ← 顶层：合并代价 f(n)
                    /    \
              f(n/b)      f(n/b)             ← 第 1 层：a 个子问题，各贡献 f(n/b)
             /    \      /    \
          ...    ...   ...    ...            ← 往下每层规模缩小 b 倍
        /  \    /  \   /  \   /  \
              ...                             ← 叶子：规模缩到 1，共 a^(log_b n) = n^(log_b a) 个

  总树高：log_b n 层（每层规模除以 b，除以 log_b n 次后到 1）
  叶子总数：a^(log_b n) = n^(log_b(a))
```

整棵树的代价 = **每一层的代价** × **层数**，而哪一层最「贵」，决定了总复杂度。

![分治递归树：每层拆成 a 个子问题、规模缩小 b 倍（发布前请自行转存素材库）](https://cdn.jsdelivr.net/gh/krahets/hello-algo@main/docs/chapter_computational_complexity/iteration_and_recursion.assets/recursion_tree.png)

这张递归树图（来自开源教程《Hello 算法》的递归章节）直观展示了主定理的推理基础：**每往下一层，问题规模缩小 b 倍，节点数乘以 a**——比较「每一层的合并代价」和「叶子层的总代价」谁更大，就是主定理三个 case 的本质。（推荐搜索关键词：「master theorem recursion tree 递归树」）

### 三种 case：比谁更「贵」

主定理比较两个量：**叶子层总量 `n^(log_b a)`** 和 **合并/分解代价 `f(n)`**。谁大，谁的复杂度就占主导：

| 情况 | 条件 | 结果 | 直觉 |
|------|------|------|------|
| **Case 1** | `f(n)` 比 `n^(log_b a)` 小 | `Θ(n^(log_b a))` | **叶子**太贵了，合并开销可忽略——代价集中在「拆出的海量小问题」上 |
| **Case 2** | 两者**同阶** | `Θ(n^(log_b a) · log n)` | **每层一样贵**——每层代价都是 `n^c`，共 log n 层 |
| **Case 3** | `f(n)` 比 `n^(log_b a)` 大 | `Θ(f(n))` | **顶层**太贵了，递归子问题开销可忽略——代价集中在「第一次分解/合并」上 |

（严谨表述下 Case 1 还要求 `f(n) = O(n^(log_b a − ε))`，Case 3 还要求正则条件 `a·f(n/b) ≤ c·f(n)`，面试说清「谁大听谁的」这个直觉就足够，不必背 ε 和正则条件。）

### 用主定理推归并排序

归并排序的递归式：

```
T(n) = 2·T(n/2) + O(n)
       ↑    ↑       ↑
       2 个子问题，每个规模 n/2，合并代价 O(n)
```

代入：`a = 2`，`b = 2`，`f(n) = O(n)`。

先算叶子层总量：`n^(log_b a) = n^(log_2 2) = n^1 = n`。

现在比较 `f(n) = O(n)` 和 `n^(log_b a) = O(n)`——**两者同阶！** 命中 **Case 2**：

```
T(n) = Θ(n^(log_b a) · log n) = Θ(n · log n)
```

**结论：归并排序是 O(n log n)。** 这就是用主定理推导的标准过程。

> 💬 **面试官**：主定理怎么用？归并排序的复杂度如何用主定理推出？
>
> ✅ 标准答案：把分治算法的复杂度写成 `T(n) = aT(n/b) + f(n)` 的递归式，然后比较 **`n^(log_b a)`（所有叶子节点的总代价）** 和 **`f(n)`（分解合并代价）**。归并排序是 `T(n) = 2T(n/2) + O(n)`，其中 `n^(log_2 2) = n`，和 `f(n) = O(n)` 同阶，命中 **Case 2**，结果乘上一个 log n 层数，得到 **O(n log n)**。
>
> 🎁 加分答案：能顺手用主定理解释**为什么快排会退化**——快排平均时 `T(n) = 2T(n/2) + O(n)`，也是 O(n log n)；但如果每次选的基准都是极值（比如已排序数组选首元素当基准），递归式退化成 `T(n) = T(n−1) + O(n)`，这是一条**链**而不是树（只有一个子问题），`a = 1`，展开得到 O(n²)。核心差异在于**「分解步是否均衡」**：均衡 → 树形递归 → O(n log n)；不均衡 → 链形递归 → O(n²)。能讲清「快排的复杂度取决于分解的均衡程度」，比单纯背「快排最坏 O(n²)」高一个层次。

### 经典分治算法复杂度清单

把常见分治算法全部套进主定理，得到这张表，建议直接记住递归式：

| 算法 | 递归式 | 命中 Case | 复杂度 | 说明 |
|------|--------|-----------|--------|------|
| 归并排序 | `T(n) = 2T(n/2) + O(n)` | Case 2 | O(n log n) | 分解绝对均衡 |
| 快速排序（平均） | `T(n) = 2T(n/2) + O(n)` | Case 2 | O(n log n) | 平均基准把数组分得比较均匀 |
| 快速排序（最坏） | `T(n) = T(n−1) + O(n)` | — | O(n²) | 基准取极值，退化成链 |
| 二分搜索 | `T(n) = T(n/2) + O(1)` | 只有一支 | O(log n) | 每次**只解一个**子问题，无合并步 |
| 归并 K 个升序链表 | `T(k) = 2T(k/2) + O(k·n)` | Case 2 | O(k·n log k) | 每层合并总代价 O(k·n) |
| 快速幂 | `T(n) = T(n/2) + O(1)` | 只有一支 | O(log n) | 指数每次减半 |

注意表格里**二分搜索和快速幂**的特殊性：它们的递归式是 `T(n) = T(n/2) + ...`，即 `a = 1`——**每次只处理一个子问题**（另一半直接丢弃）。这是分治的**退化形态**：连「合并」都不需要，因为答案就在那唯一被保留的子问题里。

> 💡 记住一句话区分：**「每次扔掉一半，只留一个子问题」→ 单支递归 → O(log n)（二分、快速幂）；「拆成两个子问题都要算」→ 双支递归 → O(n log n)（归并、快排平均）。**

### 树的分治：翻转 / 比较 / 对称

二叉树是**天然的分治结构**——因为「一棵树的问题」可以完全由「它的左右子树的问题」组合出来。下面三道题，是树分治最经典的模板，笔记里的完整代码全部保留。

**226 翻转二叉树**

思路：先翻转左右子树，再把子树换个位置——符合「分、解、合」的特性。

- **分**：获取左右子树
- **解**：递归翻转左右子树
- **合**：把翻转后的左右子树交换位置放到根节点上

```typescript
// 翻转二叉树
export class TreeNode {
  val: number
  left: TreeNode | null
  right: TreeNode | null
  constructor(val?: number, left?: TreeNode | null, right?: TreeNode | null) {
    this.val = (val===undefined ? 0 : val)
    this.left = (left===undefined ? null : left)
    this.right = (right===undefined ? null : right)
  }
}

export function invertTree(root: TreeNode | null): TreeNode | null {
  if(!root) return null;                      // 👈 base case：空节点直接返回
  return new TreeNode(
    root.val,
    invertTree(root.right),                   // 👈 解：翻转右子树，放到左边
    invertTree(root.left)                     // 👈 解：翻转左子树，放到右边
  );                                          // 合：构造新节点即完成交换
};
```

**100 相同的树**

思路：两棵树相同 ⟺ **根节点的值相同 + 左子树相同 + 右子树相同**——完美的分治。

- **分**：获取两个树的左子树和右子树
- **解**：递归判断两个树的左子树是否相同、右子树是否相同
- **合**：将上述结果合并，如果根节点的值也相同，树就相同

```typescript
// 相同的树
export class TreeNode {
  val: number
  left: TreeNode | null
  right: TreeNode | null
  constructor(val?: number, left?: TreeNode | null, right?: TreeNode | null) {
    this.val = (val===undefined ? 0 : val)
    this.left = (left===undefined ? null : left)
    this.right = (right===undefined ? null : right)
  }
}

export function isSameTree(p: TreeNode | null, q: TreeNode | null): boolean {
  if(!p && !q) return true;                   // 👈 都为空，相同
  if(
    p && q && // p 和 q 同时存在
    p?.val === q?.val && // 根节点相同
    isSameTree(p.left, q.left) && // 左子树相同
    isSameTree(p.right, q.right) // 右子树相同
  ) {
    return true;
  }
  return false;
};
```

**101 对称二叉树**

思路：转化为「左右子树是否互为镜像」。

- **分**：获取两个树的左子树和右子树
- **解**：递归地判断「树1的左子树和树2的右子树是否镜像」「树1的右子树和树2的左子树是否镜像」
- **合**：如果上述都成立，且根节点值也相同，两棵树就镜像

注意这道题的关键转换：**对称不是「左子树 == 左子树」，而是「左子树和右子树互为镜像」**，所以递归时要把参数交错传（`rec(l.left, r.right)` 和 `rec(l.right, r.left)`）。

```typescript
// 对称二叉树
export class TreeNode {
  val: number
  left: TreeNode | null
  right: TreeNode | null
  constructor(val?: number, left?: TreeNode | null, right?: TreeNode | null) {
    this.val = (val===undefined ? 0 : val)
    this.left = (left===undefined ? null : left)
    this.right = (right===undefined ? null : right)
  }
}

export function isSymmetric(root: TreeNode | null): boolean {
  if(!root) return true;                      // 👈 空树是对称的
  const rec = (l: TreeNode | null, r: TreeNode | null): boolean => {
    if(!l && !r) return true; // 递归结束条件：两边都空
    if(
      l && r &&
      l.val === r.val &&
      rec(l.left, r.right) &&                 // 👈 左的左 vs 右的右
      rec(l.right, r.left)                    // 👈 左的右 vs 右的左（交错）
    ) {
      return true;
    }
    return false;
  }
  return rec(root.left, root.right);
};
```

**三题归一：树的分治模板**

这三道题看着不同，代码骨架完全一样，抽出模板就是：

```
树分治(root1, root2):
  ① base case：处理空节点（都空 → 返回一个「相同/成功」的值）
  ② 分：拿到需要递归的子树对
  ③ 解：递归解决子树对（注意对称题要交错传参）
  ④ 合：把「根节点的处理结果」和「子树的递归结果」合并（通常是逻辑与 &&）
```

这就是「树天然适合分治」的具象体现——**对根做的处理（合）+ 对子树做的递归（分解与解决）**，正好就是分治三步骤。

### 二分搜索：分治的退化形态

笔记里的「猜数字大小」（LeetCode 374）是二分搜索的经典应用，也是**单支递归**分治的代表。

- **分**：计算中间元素 `middle`，看看目标在左边还是右边
- **解**：递归地在较大或较小的子数组里继续搜索
- **合**：**不需要此步**——因为在子数组中搜到就直接返回了

```typescript
// 猜数字大小
/** 
 * Forward declaration of guess API.
 * @param {number} num   your guess
 * @return 	            -1 if num is lower than the guess number
 *			             1 if num is higher than the guess number
 *                       otherwise return 0
 * var guess = function(num) {}
 */

function guess(n: number, pick: number) {
  return pick > n ? 1 : pick < n ? -1 : 0;
}

export function guessNumber(n: number, pick: number): any {
  console.time('猜数字大小');
  const rec: any = (start: number, end: number) => {
    if(start> end) return; // 递归结束
    let middle = Math.floor((start + end) / 2);
    const res = guess(middle, pick);
    if(res === 0) {
      console.timeEnd('猜数字大小');
      return middle
    } else if (res === 1) {
      return rec(middle + 1, end);            // 👈 只往右半边递归
    } else if(res === -1) {
      return rec(start, middle - 1)           // 👈 只往左半边递归
    }
  }
  return rec(0, n);
};
```

- 空间复杂度：O(log n)，递归是堆栈调用，空间复杂度和递归的层次有关

**为什么说二分是「分治的退化形态」？** 看它的递归式：`T(n) = T(n/2) + O(1)`——`a = 1`，即**每次只解一个子问题**（另一半直接扔掉）。所以：

- 它没有「合并步」（答案在留下的那一支里，直接返回）
- 复杂度是 O(log n) 而不是 O(n log n)（没有树形展开，只有一条链）

这也解释了本文档反复强调的那句：**分治的「分」如果只分出一支（另一半不用管），就退化成二分。**

### 快速幂：50 Pow(x, n)

快速幂是**分治在数值计算上的经典应用**，面试出现频率很高。朴素地算 `x^n` 要乘 n 次，是 O(n)；快速幂利用「指数拆半」把它降到 O(log n)。

核心观察是两个恒等式：

```
当 n 为偶数：x^n = (x^(n/2))²          ← 拆一半，平方回来
当 n 为奇数：x^n = (x^(n/2))² · x       ← 多出来的一个 x 单独乘
```

比如 `x^8 = (x^4)² = ((x^2)²)² = (((x)²)²)²`——指数每次除以 2，8 → 4 → 2 → 1，只需 3 步而不是 8 步：

```
   分：把 x^8 拆成 (x^4)²             ← 分解
   解：递归求 x^4                      ← 解决
   合：把结果平方                       ← 合并
```

迭代展开看，指数的递归树是一条「每次减半」的链，深度只有 log n：

```
   x^8
    └─ (x^4)²
         └─ ((x^2)²)²
              └─ (((x)²)²)²
                   └─ base case: x^1
   递归深度 = log₂8 = 3  ← 对比朴素循环要乘 8 次
```

```typescript
type Pow = (x: number, n: number) => number;

export const myPow: Pow = (x, n) => {
  // 处理负指数：x^(-n) = 1 / x^n
  if (n < 0) {
    return 1 / myPow(x, -n);                  // 👈 负指数取倒数
  }

  const fastPow = (base: number, exp: number): number => {
    if (exp === 0) return 1;                  // 👈 base case：任意数的 0 次方是 1
    const half = fastPow(base, Math.floor(exp / 2));  // 解：先算出 x^(n/2)
    return exp % 2 === 0
      ? half * half                           // 合：偶数 → 平方回来
      : half * half * base;                   // 合：奇数 → 平方后再乘一个 x
  };

  return fastPow(x, Math.abs(n));
};
```

> 💬 **面试官**：快速幂为什么是 O(log n)？它跟朴素循环有什么本质区别？
>
> ✅ 标准答案：朴素做法是循环乘 n 次，O(n)。快速幂把指数 n **每次折半**——`x^n = (x^(n/2))²`，只需递归 log n 层，每层做常数次乘法，所以是 **O(log n)**。本质区别在于：朴素是「**一个个乘**」，快速幂是「**把已经算好的结果平方复用**」——这是「分治 + 结果复用」带来的指数级加速。
>
> 🎁 加分答案：能补两点——① 快速幂还有一个**迭代（二进制）版本**：把 n 看成二进制，例如 `n = 13 = 1101₂`，则 `x^13 = x^8 · x^4 · x^1`，从低位往高位算出 `x^(2^k)` 并以「是否乘入」决定是否累乘，全程 O(log n) 且不占递归栈，工程上更常用。② 快速幂的思想不止用于幂运算，**矩阵快速幂**是求「第 n 项斐波那契数」O(log n) 解法的核心（把递推写成矩阵乘），这是 DP 和分治的结合点，能提出来是强加分。

### 多数元素：169 分治求众数

**多数元素**（LeetCode 169）：找数组中出现次数大于 ⌊n/2⌋ 的元素。有哈希表、摩尔投票、分治三种解法，这里讲**分治版**，因为它最贴合本篇主题。

分治的洞见是：**如果元素 `a` 是整个数组的众数，那它必然是「左半数组的众数」或「右半数组的众数」中的某一个**。注意是「或」不是「且」——这是分治法的关键推理。

- **分**：把数组从中点切成左右两半
- **解**：递归求左半的众数 `left` 和右半的众数 `right`
- **合**：如果 `left === right`，众数就是它；否则在**整个区间内**分别数 `left` 和 `right` 的出现次数，谁多谁是众数

```typescript
type MajorityElement = (nums: number[]) => number;

export const majorityElement: MajorityElement = (nums) => {
  // 合并步：在 [lo, hi] 区间内统计 target 出现次数
  const countInRange = (lo: number, hi: number, target: number): number => {
    let count = 0;
    for (let i = lo; i <= hi; i++) {
      if (nums[i] === target) count++;
    }
    return count;
  };

  const divide = (lo: number, hi: number): number => {
    if (lo === hi) return nums[lo];           // 👈 base case：只剩一个元素

    const mid = Math.floor((lo + hi) / 2);
    const left = divide(lo, mid);             // 解：左半众数
    const right = divide(mid + 1, hi);        // 解：右半众数

    if (left === right) return left;          // 合：两半众数相同，直接返回

    // 合：不同则在当前区间内比较两者出现次数
    const leftCount = countInRange(lo, hi, left);
    const rightCount = countInRange(lo, hi, right);
    return leftCount > rightCount ? left : right;
  };

  return divide(0, nums.length - 1);
};
```

- 空间复杂度：O(log n)，递归栈深度

> 💬 **面试官**：求多数元素，分治、哈希表、摩尔投票三种解法你选哪个？
>
> ✅ 标准答案：如果只求答案、不在意空间，**摩尔投票（Boyer-Moore）最优**——O(n) 时间、O(1) 空间，因为它利用了「众数超过一半，抵消其他元素后必然剩下」的性质。分治是 O(n log n)、哈希表是 O(n) 时间 O(n) 空间。
>
> 🎁 加分答案：能补一句——**分治版虽然不如摩尔投票快，但它的推理很漂亮，而且可扩展到「求出现次数超过 ⌊n/k⌋ 的元素」的 generalized Boyer-Moore**。分治版的核心洞见是「全局众数必是某一半的众数」，这个「把全局性质归约到子问题」的思路，是分治解题的通用心法。

### 合并 K 个升序链表：23

这是分治最「有区分度」的一道题，也是**分治 vs 顺序合并复杂度差异**的经典教学案例。

问题是：给你 k 个升序链表，合并成一个升序链表。有两种思路：

**思路一：顺序合并（一对一串）** —— 把链表 1 和 2 合并成 `m1`，再把 `m1` 和链表 3 合并，依次类推：

```
   L1 ──▶ merge ──▶ m1 ──▶ merge ──▶ m2 ──▶ merge ──▶ ... 
         (L1+L2)          (+L3)          (+L4)
```

问题在于：**越到后面，参与合并的链表越长**。第 i 次合并时，前 i 个链表的总长度约为 i·n（假设每个链表平均长度 n），要扫一遍是 O(i·n)。k 次累加起来：

```
  O(n) + O(2n) + O(3n) + ... + O(k·n) = O(k²·n)
```

**思路二：分治两两合并** —— 像归并排序那样，把 k 个链表两两配对合并，合并后的结果再两两配对：

```
        分：k 个链表 → 两两配对
   ┌─────┬─────┬─────┬─────┐
   L1    L2    L3    L4   ...        ← 第 1 层：k/2 对合并
    └──┬──┘     └──┬──┘
      m1           m2      ...       ← 第 2 层：k/4 对合并
       └─────┬─────┘
             ...
       最终一个有序链表
```

这样**每层的总合并代价都是 O(k·n)**（k 个链表总共 k·n 个节点，每层都要扫一遍），而层数是 log k（k 每次减半）。所以：

```
   T(k) = 2T(k/2) + O(k·n)     ← 每层合并总代价 O(k·n)
        命中主定理 Case 2
   → O(k·n·log k)
```

**复杂度对比**：

| 方案 | 递归式/累加 | 复杂度 |
|------|------------|--------|
| 顺序合并 | `O(n) + O(2n) + ... + O(k·n)` | **O(k²·n)** |
| 分治两两合并 | `T(k) = 2T(k/2) + O(k·n)` | **O(k·n·log k)** |

分治合并把 k² 降成了 k·log k。以 k=1000 为例，k² = 100 万，而 k·log k ≈ 1000 × 10 = 1 万——**相差两个数量级**。

实现上，需要一个「合并两个有序链表」的单元函数（就是第 05 篇讲过的 LeetCode 21），分治版复用 k−1 次：

```typescript
export class ListNode {
  val: number;
  next: ListNode | null;
  constructor(val?: number, next?: ListNode | null) {
    this.val = val === undefined ? 0 : val;
    this.next = next === undefined ? null : next;
  }
}

// 合并两个有序链表：分治的「合并单元」
export function mergeTwoLists(
  l1: ListNode | null,
  l2: ListNode | null
): ListNode | null {
  const dummy = new ListNode(0);              // 👈 哑节点，统一边界
  let cur = dummy;
  while (l1 && l2) {
    if (l1.val <= l2.val) {                   // 👈 <= 保证稳定
      cur.next = l1;
      l1 = l1.next;
    } else {
      cur.next = l2;
      l2 = l2.next;
    }
    cur = cur.next;
  }
  cur.next = l1 ?? l2;                        // 接上剩余部分
  return dummy.next;
}

// 分治合并 K 个链表
export function mergeKLists(lists: Array<ListNode | null>): ListNode | null {
  const divide = (lo: number, hi: number): ListNode | null => {
    if (lo === hi) return lists[lo];          // 👈 base case：只剩一个链表
    if (lo > hi) return null;                 // 空区间
    const mid = Math.floor((lo + hi) / 2);
    const left = divide(lo, mid);             // 解：合并左半
    const right = divide(mid + 1, hi);        // 解：合并右半
    return mergeTwoLists(left, right);        // 合：合并两个结果
  };
  return divide(0, lists.length - 1);
}
```

```typescript

const build = (vals: number[]): ListNode | null => {

```

复杂度：

- 时间复杂度：**O(k·n·log k)**，k 是链表个数，n 是每个链表平均长度
- 空间复杂度：O(log k)，递归栈深度（不含输出链表本身）

> 💬 **面试官**：合并 K 个升序链表，为什么用分治而不是顺序合并？两者复杂度差多少？
>
> ✅ 标准答案：**顺序合并是 O(k²·n)，分治两两合并是 O(k·n·log k)**。差异的根源在于：顺序合并时「越到后面参与合并的链表越长」，第 i 次合并要扫 i·n 个节点，累加起来是平方级；而分治两两合并**每一层的总合并代价都是 O(k·n)**（所有链表每层各扫一遍），总共 log k 层，所以是 k·n·log k。当 k 很大时（比如 1000 个链表），相差近两个数量级。
>
> 🎁 加分答案：能补两点——① 这题还有**第三个解法：用最小堆**。把 k 个链表的头节点放进最小堆，每次取堆顶（最小）接到结果上，再把它的 next 放回堆。复杂度 **O(k·n·log k)**，和分治同阶，但代码用堆会更「数据流」一些，工程上更通用（比如 K 个有序日志流合并）。② 分治和堆的取舍：分治**不占额外堆空间**（原地递归），堆方案需要 O(k) 的堆空间；但堆方案**天然支持「流式」输入**（链表不断到来时也能续接），分治必须先拿到全部 k 个链表。能对比到这一层，说明你不是背答案，是真懂。

## 🔧 前端工程落地

分治不只是刷题的思想，它在你每天用的框架和引擎里到处跑。这一节把本篇的几个分治算法，对上三处真实的前端工程实现。

### V8 TimSort 的归并步

第 10 篇《排序》里我们讲过，V8 的 `Array.prototype.sort` 用的是 **TimSort**——一个归并排序 + 插入排序的混合体。它的归并部分，正是分治：

- **分解**：扫描数组，识别出「已经有序的连续片段」（叫 run），每个 run 就是天然有序的子问题
- **解决**：短的 run（< 64）用插入排序补成有序
- **合并**：按 TimSort 的 `mergeCollapse` 策略，把相邻 run 两两归并成更长的 run，直到整个数组有序

TimSort 比朴素的归并排序聪明的地方在于：**它对「现实世界大量部分有序的数据」做了优化**——不需要每次都傻乎乎地从中间劈开，而是先利用数据里已有的有序性。但它的**骨架依然是分治的「拆成 run → 归并合并」**。

> 💡 这就是分治思想的工程价值：**同一个范式，套上不同的「分解策略」（怎么切）和「合并策略」（怎么合），就能适配不同的数据特征**。归并排序从中间切、TimSort 从有序 run 切、外排序从内存上限切——分解方式千变万化，但「拆 → 递归 → 合」的骨架不变。

### React reconcile 树 diff

导读篇里我们讲过 React 的虚拟 DOM diff。现在有了分治的视角，可以把它看得更透。

React 的 reconcile 算法本质是一个**分治递归**：

- **分解**：要 diff 整棵树，先处理当前节点，然后把问题拆成「diff 每个子节点」的子问题
- **解决**：递归 diff 每个子节点（`reconcileChildFibers`）
- **合并**：把子节点的 diff 结果收集起来，决定真实 DOM 的增删改

而 React 又进一步把「子节点的 diff」拆成了**两个独立子问题**：

- **单节点 diff**（`reconcileSingleElement`）：新的 children 只有**一个**元素时的处理
- **多节点 diff**（`reconcileChildrenArray`）：新的 children 是**多个**元素时的处理

这两个子问题**相互独立**——正因如此，React 可以在代码里用 `if` 直接判断该走哪个分支，而不需要担心它们之间的互相干扰。**这就是分治的「子问题独立」特性在工程代码里的直接体现**：独立，所以可以放心拆开、分别优化。

再看顶层：React 的整个 diff 之所以能做分治，关键在于导读篇讲的「**只做同层对比**」这个约束——它把原本需要跨层比较的 O(n³) 问题，强行约束成「每层独立的同层比较」，也就是把一个问题拆成了**若干个互不干扰的「同层子问题」**。这个约束，本质上是「为了让分治成立（子问题独立）而做的工程妥协」。

### Webpack tree-shaking 可达性分析

第 09 篇《图》讲过，Webpack 的模块依赖是一张有向图。**tree-shaking（摇树优化）的本质，是这张图上的可达性分析**——从入口模块出发，能走到的模块就是「活的」，走不到的就是「死的」，死代码可以被删掉。

这个分析用分治的视角看也很清楚：

- **分解**：从入口出发，把「分析整个依赖图」拆成「分析入口的每个依赖子图」
- **解决**：对每个 import 出去的依赖，递归地分析它自己的依赖子图
- **合并**：把所有子图的可达结论合并起来，得到每个模块「是否可达入口」

⚠️ 不过这里跟纯分治有一点区别，正好可以点出来：**模块依赖图可能有环**（循环依赖），而纯分治假设子问题相互独立、不会绕回来。所以 Webpack 分析时必须维护一个「已访问集合」来打断环——这正是第 09 篇讲的「图的环检测」。**当分治的「子问题独立」假设被打破（出现环/重叠）时，就必须引入额外的机制（访问标记 / 记忆化）**——注意，这与「分治 vs DP」的分野（独立 vs 重叠）是同一个道理，只是换了个场景。

> 💬 **面试官**：分治这个思想，在前端工程里你能举出哪些真实例子？
>
> ✅ 标准答案：至少能举三个——① **V8 TimSort**：识别有序 run 后用归并合并，是归并排序（分治）的工程优化版；② **React reconcile**：把整棵树的 diff 拆成「单节点 diff」和「多节点 diff」两个独立子问题递归处理，是分治的典型；③ **Webpack tree-shaking**：从入口递归分析每个依赖子图的可达性再合并结论。
>
> 🎁 加分答案：能点出「分治的适用边界」——**上面这些工程场景里，凡是子问题可能重叠的（如模块图有环），实现时都必须加「访问标记」或「记忆化」来打断重复**。这恰恰印证了分治与 DP 的分野：子问题独立才能纯分治，一旦出现重叠（环、重复子问题），就得引入缓存机制，那时候它就已经带上了 DP 的味道。能意识到「工程实现总是在纯分治和 DP 之间权衡」，说明你对这两个思想是真理解，而不是分开背的。

## 🎓 面试高频问（汇总标准答案）

把本篇四个核心面试问集中在这里，方便复习速查。

**问 1：分治的三步骤是什么？「合并」步为什么是关键？**

✅ 三步骤是**分解（Divide）、解决（Conquer）、合并（Combine）**。合并步是关键，因为它才是**分治区别于普通递归的分水岭**——普通递归只是自己调自己，而分治必须能把「子问题的解」组装回「原问题的解」。没有合并步，问题只是被拆散了，并没有被解决。二分搜索之所以不需要合并步，是因为答案就在保留下来的那个子区间里，直接返回即可。

**问 2：分治和动态规划的本质区别是什么？如何判断该用分治还是 DP？**

✅ 本质区别在**子问题是否重叠**。分治的子问题相互独立、各算一次就够了，所以不需要缓存；DP 的子问题相互重叠、会被反复用到，必须用记忆化或 DP 表把结果存下来，否则就是指数级重复计算。判断方法：先问「同一个子问题会不会被算很多次」——不会重复就是分治，会重复就是 DP。补充：分治是「把子问题的解**合并**成原问题的解」，DP 是「在子问题的解里**取最优**」。

**问 3：主定理怎么用？归并排序的复杂度如何用主定理推出？**

✅ 把分治的复杂度写成 `T(n) = aT(n/b) + f(n)`，然后比较 **`n^(log_b a)`（所有叶子的总代价）** 和 **`f(n)`（分解合并代价）**：`f(n)` 小 → Case 1，取 `n^(log_b a)`；两者同阶 → Case 2，多乘一个 log n；`f(n)` 大 → Case 3，取 `f(n)`。归并排序 `T(n) = 2T(n/2) + O(n)`，`n^(log_2 2) = n` 与 `f(n) = O(n)` 同阶，命中 Case 2，得 **O(n log n)**。

**问 4：合并 K 个升序链表为什么用分治而不是顺序合并？两者复杂度差多少？**

✅ **顺序合并是 O(k²·n)，分治两两合并是 O(k·n·log k)**。顺序合并时越到后面参与合并的链表越长，第 i 次合并要扫 i·n 个节点，累加就是平方级；分治两两合并每层总合并代价都是 O(k·n)，共 log k 层，所以是 k·n·log k。k 很大时（如 1000），两者相差近两个数量级。

| 分治 vs DP | 子问题独立 → 分治；子问题重叠 → DP | ⭐⭐⭐ 必考 |
| 主定理 | 比较 `n^(log_b a)` 与 `f(n)`，谁大听谁的 | ⭐⭐⭐ 必考 |
| 归并排序复杂度 | `T(n)=2T(n/2)+O(n)` → Case 2 → O(n log n) | ⭐⭐⭐ 必考 |
| 二分搜索 | `T(n)=T(n/2)+O(1)`，单支递归，退化形态 | ⭐⭐ 高频 |
| 快速幂 | 指数拆半，O(n) → O(log n) | ⭐⭐ 高频 |
| 合并 K 链表 | 分治 O(kn log k) vs 顺序 O(k²n) | ⭐⭐ 高频 |
| 树的分治 | 根处理 + 递归子树 + 合并结果（翻转/比较/对称） | ⭐⭐ 高频 |
| 工程落地 | TimSort / React diff / tree-shaking 都是分治 | ⭐ 中频 |

> 💡 记住这条主线：**分治 = 分解（拆）→ 解决（递归）→ 合并（组装）**。它和动态规划的唯一分野是**子问题是否重叠**——独立就是分治（归并、快排、二分、快速幂），重叠就是 DP（斐波那契、编辑距离、背包）。而主定理 `T(n) = aT(n/b) + f(n)` 是分治的「复杂度计算器」，比较叶子总量 `n^(log_b a)` 和合并代价 `f(n)`，谁大听谁的。把这三点刻进脑子，分治这一章就通关了。
