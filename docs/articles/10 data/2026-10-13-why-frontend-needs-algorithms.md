## 一、你写的代码里，处处是数据结构

先说结论，再逐个拆解：**你以为前端不用数据结构，其实你每天都在用它，只是它被 React、V8、浏览器这些框架和引擎「藏」起来了**。

下面这四个场景，任何一个前端都写过、都遇到过，但它们底层的数据结构选型逻辑，大多数人从没认真想过。

### React Fiber：用链表做到「暂停和恢复」

React 16 之前，组件树是一棵真正的**树**——父组件递归渲染子组件，子组件递归渲染孙组件，一层层调下去。这种「递归树」的问题在于：**一旦开始渲染，就必须一口气渲染完整棵树，中间停不下来**。一棵复杂的组件树渲染 100ms，主线程就被锁死 100ms，用户点个按钮都没反应——这就是「掉帧」。

React 16 引入 Fiber 架构，核心改动就是**把组件树改造成了「树 + 链表」的混合结构**。每个组件对应一个 Fiber 节点，节点上有三个指针：

```
┌─────────────────────────────────────────────────┐
│                FiberNode 的三个指针               │
│                                                   │
│   parent ──────► child ──────► child              │
│     │              │             │                │
│     │  return      │ return      │ return         │
│     │              │             │                │
│     └── sibling ──►│── sibling ──►│                │
│                    │             │                │
│  child  ：指向第一个子节点（往下钻）               │
│  sibling：指向下一个兄弟节点（横向走）             │
│  return ：指向父节点（回溯用）                     │
└─────────────────────────────────────────────────┘
```

`child` 指针往下钻到子节点，`sibling` 指针横向走到兄弟节点，`return` 指针回溯到父节点。三个指针一组合，整棵组件树就被编码成了一张**可以任意游走、可以随时暂停和恢复**的链表结构。

**为什么不用普通数组、也不用纯树？** 因为链表最大的特性是——**遍历到任意节点，都可以停下手头的活，记住当前位置，之后从这个位置继续**。React 利用这一点实现了「时间分片」：每次只处理一部分 Fiber 节点，时间片用完了就暂停，把主线程让给用户交互，下一帧再接着上次的位置继续。这正是递归树做不到的——递归树依赖调用栈，栈一旦压进去，不弹完就回不来，没法「暂停在中间」。

> 💬 **面试官**：React Fiber 为什么用链表，而不是普通的树？
>
> ✅ 标准答案：Fiber 通过 `child`、`sibling`、`return` 三个指针，把组件树改造成「树 + 链表」的混合结构。链表的核心价值是**可以在任意节点暂停遍历、记住当前位置、之后恢复**——这是 React 时间分片（Time Slicing）的基础。普通的递归树依赖调用栈，一旦开始渲染就必须一口气走完，无法中途暂停让出主线程，长任务会阻塞用户交互导致掉帧。
>
> 🎁 加分答案：能点出**「可中断」是 Fiber 架构的灵魂**——时间分片、Concurrent Mode 的优先级调度，都建立在这个「能暂停恢复」的链表结构之上。还可以补一句：`return` 指针额外承担了「出错时沿链回溯组件栈」的能力，React ErrorBoundary 抓错误时就是沿 `fiber.return` 链一层层找到父组件边界。链表在这里解决的，本质是「把不可控的深递归，变成可控的、可分片的迭代遍历」。

### 虚拟 DOM diff：为什么只做同层对比

React 的 reconcile（调和）算法，本质是在新旧两棵虚拟 DOM 树之间，找出最小的变化并应用到真实 DOM。这个过程用到的数据结构操作，是**树的层序遍历 + 双指针对比同层子节点列表**。

最关键的一个设计约束是：**diff 只做「同层对比」，不做跨层对比**。

```
旧树            新树            diff 策略
  A              A
 / \            / \
B   C          B   C          ✅ 同层对比：A 的 children
/ \   \       / \   \             [B,C] 对比 [B,C]
D  E   F     D   E   F        ✅ 同层对比：B 的 children
                               [D,E] 对比 [D,E]
                               ❌ 不做：D 是否移动到了 F 的位置
                               （跨层移动直接被当作「删除 + 新建」处理）
```

**为什么只做同层对比？** 因为如果允许跨层移动，算法要把任意一个节点和任意其他节点做两两比较，找出最优的「移动方案」——这本质上是一个树编辑距离问题，最朴素的算法复杂度是 **O(n³)**。而真实前端场景里，跨层移动 DOM 节点是**极低频**的操作，为了这个极低频场景付出 O(n³) 的代价，完全不划算。于是 React 做了一个工程妥协：**只对比同层，跨层移动一律当作「删除旧节点 + 新建新节点」处理**。这个妥协把复杂度从 O(n³) 直接降到了 **O(n)**。

这就是「数据结构选型」最生动的例子——**不是选一个「更聪明」的数据结构，而是选一个「复杂度更低、够用」的策略，哪怕它牺牲了某些边缘能力**。

> 💬 **面试官**：虚拟 DOM diff 为什么只做同层对比？这个限制带来了什么代价？
>
> ✅ 标准答案：跨层对比要找出任意节点间的最优移动方案，本质上是一个树编辑距离问题，复杂度高达 O(n³)。而真实前端场景里跨层移动 DOM 是极低频操作，React 为了这个低频场景付 O(n³) 不值得，于是只做同层对比，把复杂度降到 O(n)。代价是：**跨层移动 DOM 会被当作「删除 + 新建」处理**，性能不是最优——比如把一个节点从一棵子树平移到另一棵子树，React 会直接卸载重建而不是移动。
>
> 🎁 加分答案：能补两点——① 这个 O(n³) 是有出处的，经典的树 diff 算法（如 1979 年提出的算法）就是三次方复杂度，React 通过「同层对比 + 类型不同直接替换 + key 复用」三条启发式规则把它降到了 O(n)，这是「用启发式假设换性能」的典型；② 能提到 `key` 的作用——同层对比里，`key` 让 React 能在列表里快速识别「哪些节点可复用、哪些是新增/删除」，没有稳定的 `key` 时列表 diff 会退化为「全删重建」，这解释了为什么 React 强烈要求列表项带唯一 `key`。

### 浏览器事件循环：两个不同优先级的队列

你有没有想过，为什么 `Promise.then` 的回调永远比 `setTimeout(fn, 0)` 先执行？

```javascript
console.log('1');

setTimeout(() => {
  console.log('2');   // macrotask 队列
}, 0);

Promise.resolve().then(() => {
  console.log('3');   // microtask 队列
});

console.log('4');

// 输出顺序：1 → 4 → 3 → 2
// 为什么 3 在 2 前面？因为两个回调被塞进了两个不同优先级的队列
```

答案藏在浏览器事件循环里。事件循环维护了**至少两条任务队列**：

```
┌────────────────────────────────────────────────────┐
│                   一次事件循环（tick）                 │
│                                                      │
│  ① 执行一个 macrotask（宏任务）                       │
│     └─ setTimeout / setInterval / I/O / 事件回调       │
│                                                      │
│  ② 清空整个 microtask 队列（微任务）                  │
│     └─ Promise.then / MutationObserver / queueMicrotask │
│                                                      │
│  ③ 渲染（如果需要）                                   │
│                                                      │
│  ④ 回到 ①，取下一个 macrotask                         │
└────────────────────────────────────────────────────┘
```

这两条队列都是 **FIFO（先进先出）队列**——先入队的任务先执行。区别在于**优先级和调度时机**：macrotask 队列每次事件循环只取出**一个**执行；而 microtask 队列一旦开始清空，就**一口气把当前队列里所有微任务全部执行完**，期间新产生的微任务也会被插队到本轮继续执行。

所以上面的代码：`setTimeout` 的回调进了 macrotask 队列，`Promise.then` 的回调进了 microtask 队列。同步代码跑完（打印 1、4）后，事件循环先看 microtask 队列——里面有个打印 3 的任务，清空它；然后再取下一个 macrotask，才轮到打印 2。

**这件事的本质，就是两个不同优先级的 FIFO 队列在调度任务**。你每天都在用 `Promise` 和 `setTimeout`，但它们的执行顺序，完全是「队列 + 优先级」这个数据结构概念决定的。

> 💬 **面试官**：microtask 和 macrotask 的调度顺序是怎样的？为什么 Promise 比 setTimeout 先执行？
>
> ✅ 标准答案：浏览器事件循环维护两条任务队列，都是 FIFO 队列。每轮循环先执行一个 macrotask（如 `setTimeout` 回调），然后**清空整个 microtask 队列**（如 `Promise.then` 回调），清空期间新产生的微任务也会本轮执行，最后才是渲染、再进入下一轮取下一个 macrotask。所以 `Promise.then` 的回调进了优先级更高的 microtask 队列，永远比下一轮的 `setTimeout` 先执行。
>
> 🎁 加分答案：能点出几个高频易错细节——① microtask 是在**当前 macrotask 结束后、渲染之前**被清空的，所以微任务里改 DOM 会在本次渲染前生效，而 macrotask 里的改动要等下一轮；② microtask 队列是「清空为止」，如果在微任务里不断 `queueMicrotask` 会产生微任务风暴、阻塞渲染，这是 `Promise.then` 无限链式调用的隐患；③ 还能提到 `MutationObserver`、`queueMicrotask`、`process.nextTick`（Node 里优先级更高）都属于微任务家族，能列举这些说明你对事件循环不是死记硬背。

### V8 数组优化：JS 数组根本不是真正的数组

最后一个场景，最能颠覆直觉：**JS 的数组，底层根本不是 C 语言里那种「连续内存、随机访问」的真数组**。

V8 为了优化性能，会根据数组的**实际内容**，把数组归类为不同的内部类型（Elements Kind），不同种类之间访问速度差距巨大。核心几类：

| 内部类型 | 含义 | 性能 |
|---------|------|------|
| `PACKED_SMI_ELEMENTS` | 紧凑的小整数数组 | 最快 |
| `PACKED_DOUBLE_ELEMENTS` | 紧凑的双精度浮点数组 | 快 |
| `PACKED_ELEMENTS` | 紧凑的混合类型数组 | 较快 |
| `HOLEY_SMI_ELEMENTS` | 含空洞的小整数数组 | 慢 |
| `HOLEY_ELEMENTS` | 含空洞的混合类型数组 | 最慢 |

关键在于「**紧凑（PACKED）**」和「**空洞（HOLEY）**」的区分：

```javascript
const packed = [1, 2, 3, 4];        // PACKED_SMI_ELEMENTS —— 紧凑，无空洞
packed[4] = 5;                       // 仍是 PACKED，空洞被补上了

const holey = [1, 2, , 4];          // HOLEY —— 中间有个空洞（empty）
holey[10] = 5;                       // 空洞更多了

// 一旦从 PACKED 变成 HOLEY，就再也回不去了
// 访问 HOLEY 数组，V8 每次都要额外检查「这个位置是不是空洞」
```

**为什么打空洞会变慢？** 紧凑数组的每个位置都有值，V8 可以放心地直接访问；一旦数组里有空洞，V8 每次访问元素都得多走一步「这个下标是不是空洞」的检查，走的是更慢的通用访问路径。实测下来，**访问性能差距可以达到 5 倍甚至更多**。

更「反直觉」的一点是：**一旦数组从紧凑退化成含空洞，它就不会再自动变回紧凑**。这意味着你对一个数组打一次空洞，它之后的访问性能就永久性地降档了。所以高性能代码里，要尽量避免给数组制造空洞——比如用 `push` 追加而不是直接 `arr[100] = x` 跳着赋值。

> 💬 **面试官**：JS 数组的底层实现是真正的数组吗？打空洞会发生什么？
>
> ✅ 标准答案：不是。JS 数组底层由 V8 按内容归类为多种内部类型（Elements Kind），分「紧凑（PACKED）」和「含空洞（HOLEY）」两大类。紧凑数组访问最快；一旦打空洞（如跳着赋值、`delete` 元素），数组就降级为 HOLEY 类型，每次访问都要额外检查「该位置是否为空洞」，走更慢的访问路径，性能差距可达 5 倍以上，而且**降级后不会自动恢复**。
>
> 🎁 加分答案：能讲清「为什么」和「怎么避免」——① 为什么 JS 数组不是真数组：因为 JS 数组元素可以是任意类型、长度可动态变，无法像 C 那样固定连续内存，V8 用「隐藏类 + 分档优化」来逼近真数组性能；② 怎么避免性能降档：用 `push`/`pop` 而不是 `arr[n] = x` 跳着赋值、不要 `delete arr[i]`（用 `splice` 或置为 `undefined` 更可控）、尽量保持数组元素类型一致。能提到「V8 还会做字典模式（dictionary mode）回退」说明你真的看过底层。

## 二、数据结构与算法到底是什么

看完上面四个场景，你已经有了一个直觉：数据结构不是课本里抽象的「链表、树、图」，而是**真实工程里每天都在做的「选型决策」**。那回到最基础的问题——它到底是什么。

### 一句话定义：组织数据的方式 + 操作数据的步骤

用最朴素的话讲：

- **数据结构**：计算机**存储、组织数据的方式**——就好比厨房里的锅碗瓢盆，不同的器具有不同的摆放和用途
- **算法**：**一系列解决问题的清晰指令**——就好比食谱，告诉你一步步怎么做出一道菜

这两者共同决定了一段代码的**时间成本（跑多快）**和**空间成本（占多少内存）**。数据结构是为算法服务的，算法围绕数据结构来操作，所以经典说法是：

> **程序 = 数据结构 + 算法**

### 逻辑结构 vs 存储结构

理解数据结构，可以从两个维度拆开看：**逻辑结构**和**存储结构**。

**逻辑结构**，指的是数据元素之间的**关系**，大体分两类：

- **线性结构**：数据元素之间是一对一关系，除了首尾元素，每个元素都「首尾相接」。常见的有栈、队列、链表、线性表
- **非线性结构**：数据元素不再保持在一个线性序列里，每个元素可能与零个或多个元素发生联系。常见的有二维数组、树、图

**存储结构**，则是逻辑结构在计算机里的**具体实现**，常见四种：

- **顺序存储**：内存位置连续，如数组——靠「物理相邻」表达逻辑相邻
- **链式存储**：内存位置不一定连续，靠指针主动建立关联，如链表
- **索引存储**：额外建立索引表来定位元素
- **散列存储**：通过哈希函数算出元素位置，如哈希表

这里有个关键认知：**逻辑结构是「想怎么组织」，存储结构是「实际怎么存」**。同一种逻辑结构（比如「线性表」）既可以用顺序存储（数组）实现，也可以用链式存储（链表）实现——这正是下一节「抽象数据类型」的核心。

### 抽象数据类型（ADT）：接口与实现分离

上面那个「同一种逻辑结构，可以有多种存储实现」的思想，抽象出来就是**抽象数据类型（Abstract Data Type，ADT）**。

ADT 的核心是：**把「接口」（提供什么操作）和「实现」（底层怎么存储）分离开**。你只需要关心「这个数据结构支持哪些操作、各自什么复杂度」，而不必关心它内部是数组还是链表。

一个最经典的例子是**队列**：

- 队列的接口是固定的：入队（enqueue）、出队（dequeue）、查看队头（peek）
- 但实现可以是数组（顺序存储），也可以是链表（链式存储）
- 两种实现的**接口一模一样**，但**性能特征不同**——比如用数组实现的队列，如果靠 `shift` 出队是 O(n)（因为要搬移后续元素），而用链表实现出队是 O(1)

所以「选数据结构」这件事，本质是：**先明确你需要什么操作（接口），再根据这些操作的复杂度要求，选一个合适的存储实现**。这就是 Fiber 为什么选链表、diff 为什么只做同层对比背后的统一逻辑。

### 常见的数据结构与算法全景

最后给一张全景表，把本系列要覆盖的内容先铺开：

| 分类 | 数据结构 | 对应算法 |
|------|---------|---------|
| 线性结构 | 栈、队列、链表 | 遍历、增删节点 |
| 集合与映射 | 集合、字典、散列表 | 去重、判存、哈希查找 |
| 非线性结构 | 树、堆、图 | 深度/广度优先遍历、Top-K、最短路径 |
| 算法基础 | —— | 排序（冒泡/选择/插入/归并/快排）、搜索（顺序/二分）、递归 |
| 设计思想 | —— | 分治、动态规划、贪心、回溯 |

这张表，就是后面 15 篇文章的骨架。现在你对「要学什么」有了全貌，接下来解决「为什么前端尤其要学」。

## 三、前端为什么尤其需要

可能你会说：「你说的这些，后端不也一样要学吗？为什么前端『尤其』需要？」

答案是：**因为前端的运行环境，给数据结构选型加上了几个后端没有的硬约束**。

### 单线程 + 16.6ms/frame + 内存受限

服务端程序跑在服务器上，多核、内存大、不直接面向用户感知。而前端代码跑在浏览器里，有三个独特的约束：

- **主线程是单线程的**：JS 执行、DOM 操作、事件处理、渲染，全都挤在一条主线程上。一个长任务（比如一段 O(n²) 的循环）卡住主线程，整个页面就「冻结」，按钮点不动、动画卡住
- **执行时间直接影响帧率**：要保证 60fps 流畅，每一帧只有约 **16.6ms** 的预算。你的 JS 一旦超过这个时间，就会掉帧——这在后端是完全不存在的压力
- **内存受限**：浏览器标签页的内存是有上限的，移动端尤其紧张。深克隆一个巨大的对象树、缓存策略不当，都可能让页面被浏览器直接杀掉

这三个约束，让「数据结构选型的权衡」在前端和后端**完全不同**。同样一个问题，后端可能「多开几个线程、多占点内存」就解决了，前端却必须精打细算——因为主线程就一条、帧预算就 16.6ms、内存就那么多。

回想第一节的四个例子：Fiber 用链表是为了「16.6ms 的帧预算下能暂停让出主线程」；diff 只做同层是为了「别让主线程花 O(n³) 去干一件低频的事」；事件循环分优先级是为了「让用户交互尽快响应」；V8 数组分档优化是为了「省内存 + 加速访问」。**每一个数据结构决策，背后都是前端特有的性能约束在起作用。**

### 数据结构「藏得深」，不是「用得少」

很多人觉得「前端用不上数据结构」，真相是：**前端不是用得少，而是数据结构被框架和引擎「封装」起来了，藏得深**。

你随便翻一翻前端的日常：

- **DOM 树、虚拟 DOM 树**——是「树」
- **事件循环的任务队列**——是「队列」
- **函数调用、递归、ErrorBoundary 的组件栈**——是「栈」
- **React Fiber、JS 原型链**——是「链表」
- **路由表、缓存、权限码映射**——是「散列表 / 字典」
- **Webpack 模块依赖、npm 包依赖**——是「图」
- **JS 数组、Set、Map**——是「线性表 / 集合 / 映射」

栈、队列、链表、树、图、散列表——**经典数据结构一个不落，全在前端里**。区别只在于：后端工程师要自己手写这些结构，所以「看得见」；前端工程师大多直接调用框架提供的封装，所以「看不见」。

学数据结构的意义正在于此：**当你把这些藏起来的结构认出来，你就不再是「会用 API 的人」，而是「能看懂框架为什么这样设计的人」**。这也是后面 15 篇里，每篇都会专门写一节「前端工程落地」的原因——让你把抽象的数据结构和真实的 React/V8/浏览器源码对上号。

## 四、本系列怎么学

认知的问题解决了，接下来是方法。这一节把整个系列的学习路径和刷题方法一次讲清楚。

### 16 篇学习地图：一条主线贯穿到底

整个系列 16 篇，遵循一条清晰的认知主线：

```
导读（本篇）
  → 复杂度分析（第 02 篇）
  → 线性结构：栈（03）→ 队列（04）→ 链表（05）→ 集合与散列表（06）
  → 非线性结构：树（07）→ 堆（08）→ 图（09）
  → 算法基础：排序（10）→ 搜索（11）→ 递归（12）
  → 设计思想：动态规划（13）→ 分治（14）→ 回溯（15）→ 贪心（16）
```

为什么是这个顺序？它遵循了「**先认识结构，再掌握算法，最后上升到思想**」的递进逻辑：

- **先学复杂度分析**（第 02 篇）：因为它是衡量一切的尺子，没有它，后面所有「O(n) 比 O(n²) 好」的判断都无从谈起
- **再学具体结构**（第 03-09 篇）：按「线性 → 非线性」由易到难，每个结构讲透「是什么、怎么实现、什么复杂度、前端怎么用、面试怎么考」
- **然后学算法基础**（第 10-12 篇）：排序、搜索、递归，是数据结构之上最基础的操作
- **最后上升到设计思想**（第 13-16 篇）：动态规划、分治、回溯、贪心，是解题的「顶层心法」

每一篇都遵循「场景切入 → 本质与特性 → 核心操作与实现 → 复杂度与选型 → 高频题精讲 → 前端工程落地 → 面试高频问」的结构（按需裁剪），让你学完一篇就能「讲得清原理、答得出面试、落得了工程」。

### 分类练习 → 总结套路 → 定期回顾

这是刷题方法的灵魂，怎么强调都不为过：**一定要分类练习，而不是东一榔头西一棒子**。

- **分类练习**：一段时间内**只练一种类型**——比如这周只做二叉树，下周才开始做回溯。为什么？因为同一类型的题目有高度相似的套路，集中练习才能让你快速「看穿」这一类题的规律
- **总结套路**：练完一类题后，及时总结这类题的典型题目、解题方法、常见模板。下次遇到同类题，你能迅速判断「这属于哪类问题、用什么方法解」
- **定期回顾**：过一段时间回头再刷，检验自己是否真的掌握了——**如果你看到一个题目，还不能快速判断「它属于哪种数据结构或算法、是什么类型、用什么套路解」，说明这类题还没掌握，要多花时间**

判断自己是否掌握的标准就一句话：**看到一个题，能不能脱口而出「它是什么类型、用什么套路」**。不能，就还没学会。

### 题目怎么选：先《剑指offer》，再 LeetCode 简单/中等

关于题源和难度，两点建议：

- **题源**：先刷《剑指offer》，再刷 LeetCode。《剑指offer》里都是非常典型的题目，特别适合用来「发现和总结规律」，啃完它再刷 LeetCode 会轻松很多
- **难度**：LeetCode 以**简单、中等**为主。你的目标是「寻找规律、掌握典型题」，而不是挑战刁钻难题。当你把规律掌握了，再去解 hard 题也只是多花点时间的问题。**切忌一开始就在刁钻古怪的题目上耗费大量时间**——那会严重挫伤学习热情

数量上，建议保证 **300 题以上**，配合「多总结套路模板、多阅读源码（React、V8 等）、多把算法用于实战」，才是完整闭环。

### 如何刷 LeetCode：工具与流程

最后补一个「怎么用 LeetCode 这个工具」的实操层：

- **搜题**：可以通过题号搜，也可以通过难度、状态、列表、标签来筛选，还能按企业筛选
- **做题**：先看题目描述，再看评论和题解，理解思路后再自己写；可以设置语言和编辑器选项
- **提交**：执行代码看结果，提交代码看能否通过；用笔记本功能记录，随时查看做题进展

这些是「工具层」的事，熟悉就好，不用花太多精力。真正值得花精力的是上面两条——**分类练习**和**总结套路**。

### 四个面试核心问（完整答案）

第一节已经逐个拆解过，这里把四个高频问的「标准答案」集中在一起，方便你复习速查。

**问 1：React Fiber 为什么用链表，而不是普通树？**

✅ 链表可以在任意节点暂停遍历、记住位置、之后恢复，这是时间分片（Time Slicing）的基础。普通递归树依赖调用栈，一旦开始就必须一口气走完，无法中途让出主线程，长任务会阻塞渲染导致掉帧。Fiber 用 `child/sibling/return` 三个指针把组件树改造成「树 + 链表」混合结构，正是为了「可中断、可恢复」。

**问 2：虚拟 DOM diff 为什么只做同层对比？这个限制带来什么代价？**

✅ 跨层对比要找出任意节点间的最优移动方案，是树编辑距离问题，复杂度 O(n³)。跨层移动 DOM 是极低频操作，为其付 O(n³) 不划算，所以 React 只做同层对比，降到 O(n)。代价是跨层移动会被当作「删除 + 新建」处理，不是最优解。

**问 3：JS 数组的底层是真正的数组吗？打空洞会发生什么？**

✅ 不是。V8 按内容把数组归为多种内部类型，分「紧凑（PACKED）」和「含空洞（HOLEY）」两大类。打空洞会降级为 HOLEY，每次访问都要额外检查是否为空洞，性能差距可达 5 倍以上，且降级后不会自动恢复。

**问 4：microtask 和 macrotask 的调度顺序？为什么 Promise 比 setTimeout 先执行？**

✅ 事件循环维护两条 FIFO 队列：每轮先执行一个 macrotask，再清空整个 microtask 队列。`Promise.then` 进优先级更高的 microtask 队列，`setTimeout` 进 macrotask 队列，所以 Promise 回调先于下一轮的 setTimeout 执行。
