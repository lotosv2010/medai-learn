## 🔍 概念：向量是分布上的相近，不是逻辑上的等价

先看一个真实会翻车的现象。我们把 12 段药品说明书片段向量化，然后用「服药期间能否饮酒」去检索，期待命中「服用甲硝唑期间**禁止**饮酒」那条禁忌——结果排第一的，是「服用本品期间**可少量**饮酒」。

为什么？因为「禁止」和「可少量」这个差别，对整段的高维向量来说只是一点微调。逻辑上完全相反的两句话，词面几乎一样，向量就把它们摆得几乎一样近。

直觉会说「向量相似 = 语义相似」。**这个直觉只对了一半**：向量相似是**分布上的相近**——两个词在训练语料里经常出现在相似的上下文里，它们就会靠近。它不是**逻辑上的等价**——「禁止饮酒」和「可以少量饮酒」在逻辑上完全相反，但词面几乎一样，向量就会把它们摆得很近。

向量至少会在三类场景骗你：

- **否定句**：「可以饮酒」和「不可饮酒」的向量几乎一样，因为多一个「不」字对整段的高维向量来说只是微调
- **精确数字**：0.5g 和 5g 的向量距离，远小于「剂量」这个词带来的相似，所以「儿童剂量」很可能把「成人剂量」排在前面
- **专有名词**：两个都叫「某某胶囊」的药，向量很难只靠名字区分它们的适应症差异

> 💬 **面试官**：Embedding 是什么？「相似」在这个空间里到底意味着什么？
>
> ✅ **标准答案**：Embedding 是把文本映射到高维向量空间里的一个点，训练目标决定了「近」等于什么——是「经常出现在相似上下文里」，不是「意思相同」。所以向量相似度衡量的是分布上的接近，不是逻辑等价。
>
> 🎁 **加分答案**：能主动举出「向量相似 ≠ 语义等价」的具体失败场景——否定句、精确数字、专有名词。并能说出结论：这正是检索系统必须引入「混合检索 + 重排序」的原因（阶段四的主题），因为纯向量在这三类上系统性偏弱。

这三类失败，就是阶段四要引入「混合检索 + 重排序」的全部理由。这一篇先让你亲手撞两次——实验 B 会把「能否饮酒」的 Top-1 判给「可少量饮酒」，把「儿童剂量」的第二名让给「成人剂量」。

## ⚙️ 深入：向量化、三种度量、一次选型

### Embedding 的本质：训练目标决定「近」等于什么

一段文本进模型，出来是一个数组，比如 1024 个浮点数。这个数组就是一个高维空间里的坐标点。两个点距离近，说明两段文本「像」——但「像」的定义，是训练阶段定的：

- 训练目标是「预测上下文」，那「经常出现在相似上下文里的词」就会靠近——这是 word2vec 那一代的思路
- 训练目标是「对比学习」（正例拉近、负例推开），那「同一批标注为相似的文本对」就会靠近——这是 BGE、Qwen3-Embedding 这一代的做法

所以「近」不是绝对真理，是**某个训练任务下的副产品**。理解了这一点，你才不会把向量当成「语义的真相」，而只是「一张足够好用的地图」。

![把文本映射成向量：每个词、每段话都在高维空间里有一个坐标，语义相近的会自然地聚到一起](https://jalammar.github.io/images/word2vec/king-man-woman-embedding.png)

这张图是最经典的词向量示意：King、Queen、Man、Woman 四个词在向量空间里，性别与「皇室」两条轴各自拉开距离。要看见的不是「它在算语义」，而是「它只是把共现规律投影成了几何关系」。

### 三种度量：夹角、直线距离、投影

拿到两个向量，怎么量它们像不像？三种主流度量，分别量不同的东西：

```typescript
function dot(a: number[], b: number[]): number {
  let s = 0
  for (let i = 0; i < a.length; i++) s += a[i] * b[i]
  return s
}

function norm(a: number[]): number {
  return Math.sqrt(dot(a, a))
}

// 余弦：看夹角不看长度，文本检索默认
function cosine(a: number[], b: number[]): number {
  return dot(a, b) / (norm(a) * norm(b))
}

// 欧氏：看直线距离，越小越近
function euclidean(a: number[], b: number[]): number {
  let s = 0
  for (let i = 0; i < a.length; i++) s += (a[i] - b[i]) ** 2
  return Math.sqrt(s)
}

// 归一化：把所有向量长度压成 1，三种度量就统一了
function normalize(a: number[]): number[] {
  const n = norm(a)
  return a.map((x) => x / n)
}
```

三种度量的差别一句话说完：

- **余弦相似度**：看两个向量的**夹角**，不看长度。值在 -1 到 1 之间，1 表示同向、0 表示垂直、-1 表示反向。文本检索默认用它——因为一句话的长短不该影响它跟谁像
- **欧氏距离**：看两个点的**直线距离**，受向量长度影响。越小越近
- **点积**：看**投影**，两个向量都归一化之后，点积和余弦在数值上完全相等

![余弦相似度量的是两个向量的夹角，而不是它们之间的直线距离](https://jalammar.github.io/images/word2vec/cosine-similarity.png)

一个面试常考的结论，记住这句钩子就够了：**归一化之后，三种度量只在数值上不同，不在排序上不同。** 因为所有向量长度都变成 1，欧氏距离的平方恰好等于 2 - 2×余弦，点积恰好等于余弦。实验 C 会亲手验证这件事。

### 维度与成本：降维几乎免费，但会掉召回

向量维度越高，表达越细，但存储和计算成本线性上升。主流 embedding 模型都支持「降维」——比如 1024 维降到 256 维，存储省四分之三。**但这个降维几乎不免费，它会掉召回**：被裁掉的那几百维里，可能就藏着「否定词」那一点点区分信号。

所以降维的取舍要看场景：海量数据、成本敏感、精度要求不高时降维；医疗这类「漏一条禁忌可能出事」的场景，宁可多花点存储也要留足维度。

### 模型选择：为什么 DeepSeek 没有这一块

截至 2026-11 核实，**DeepSeek 不提供 embedding 接口**——这不是配置问题，是能力缺失。它只有对话（chat）接口。这条事实对前端 + Node 的你是双重提醒：

- 别默认「一家厂商的 API 全家桶」——chat 和 embed 经常是两套独立能力
- 它直接决定了下一篇（07）必须把 `ChatProvider` 和 `EmbeddingProvider` **拆成两个接口**，否则就是强迫 DeepSeek 去实现一个它做不到的 `embed`

本阶段实验默认本地 `qwen3-embedding:0.6b`（Ollama 拉取，零成本、中文检索优化，1024 维）。生产可用的 API 对照是通义 `qwen3.7-text-embedding-flash`（1024 维，约 ¥0.125/百万 token）。

### 批处理限制：一个最容易踩的坑

向量接口普遍有**每批条数和每批 token 数的上限**，超了直接报错。批量向量化时**必须分批 + 记录已处理偏移**，否则失败重跑会重复计费——这条在 API 场景尤其要命，本地模型宽松一些，但习惯要从现在养成。

> 💬 **面试官**：余弦相似度、欧氏距离、点积有什么区别？什么时候可以互换？
>
> ✅ **标准答案**：余弦量夹角、欧氏量直线距离、点积量投影。文本检索默认余弦，因为它不受文本长度影响。三者归一化后排序一致，可以互换。
>
> 🎁 **加分答案**：能说出「归一化后欧氏距离平方 = 2 - 2×余弦、点积 = 余弦」这个等量关系，并点出「所以归一化是把三种度量统一的关键操作」。再加一层：不归一化时，长文本（向量模长更大）会在点积和欧氏下天然占优，余弦则公平。

🔧 **真实场景**：药品说明书检索里，「0.5g 和 5g」这种剂量差别，用纯向量检索大概率被「剂量」这个词的相似度淹没。所以医疗检索不能只靠向量——一定要配一层「数字、专名精确匹配」的全文检索（阶段四的混合检索），否则剂量错一位就是安全事故。

## 🧪 动手实验：12 段说明书 × 相似度矩阵

> **说明**：实验目录 `labs/phase2-api/06-embedding/`，本地 Ollama 跑 `qwen3-embedding:0.6b`，零 API 成本。跑法：先 `ollama pull qwen3-embedding:0.6b`（首次，约 639MB），再 `pnpm --filter @medai/labs p2-embed`。

先看怎么把一段文本变成一个向量——就是一次 HTTP POST，纯 `fetch`，不引任何 SDK：

```typescript
async function embed(texts: string[]): Promise<number[][]> {
  const res = await fetch(`${OLLAMA_HOST}/api/embed`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ model: 'qwen3-embedding:0.6b', input: texts }),
  })
  const json = (await res.json()) as { embeddings: number[][] }
  return json.embeddings
}
```

三段文本进去，三个 1024 维数组出来。剩下的就是一道纯数学题：算相似度、排序、看结果。

### 实验 C：三度量对照

取同一个查询对 12 段的排序，分别用余弦、点积（归一化后）、欧氏三种度量各排一次。关键在点积那条——它先把向量归一化，再算点积：

```typescript
// 归一化后，点积和余弦在数值上相等，排序自然一致
const by = (fn: (a: number[], b: number[]) => number) =>
  SAMPLES.map((s, i) => ({ id: s.id, v: fn(q, docVec[i]) }))
    .sort((a, b) => b.v - a.v)
    .map((r) => r.id)
```

三种度量排出来的顺序（2026-11-11 实测）：

```text

   余弦（降序，越大越像）：S6 S5 S10 S4 S9 S3 S7 S1 S8 S2 S12 S11
   点积（归一化后，降序）：S6 S5 S10 S4 S9 S3 S7 S1 S8 S2 S12 S11
```

归一化之后，三行排序**逐位完全一致**。这就是「三种度量可以互换」的直接证据。

## 🚧 总结与边界

本篇压成一句话：

> **Embedding 是「相似度」这个模糊概念的可计算化；它便宜、快、可离线，但只解决「找候选」，不解决「选对的」。**

四条推论：

- **向量相似是分布上的相近，不是逻辑等价**——否定句、精确数字、专有名词是它的三个系统性盲区
- **三种度量归一化后排序一致**，文本检索默认余弦（不受长度影响）
- **DeepSeek 没有 embedding 接口**，chat 和 embed 是两套能力，接口必须拆开（下一篇）
- **批处理要分批 + 记偏移**，否则失败重跑重复计费

- **分块策略、向量库（pgvector）、Top-K 调参** → 阶段四
- **混合检索 + RRF + 重排序**（正是本篇三个失败的解法）→ 阶段四
- **用向量做长期记忆检索** → 阶段三
- **用向量做语义缓存** → 阶段九

## 🎤 面试追问链

**追问一：Embedding 是什么？「相似」在这个空间里意味着什么？**

Embedding 是把文本映射成高维向量，训练目标决定「近」等于什么——是「经常出现在相似上下文」，不是「意思相同」。所以向量相似度是分布上的接近，不是逻辑等价。

**追问二：余弦相似度、欧氏距离、点积有什么区别？什么时候可以互换？**

余弦量夹角、欧氏量直线距离、点积量投影。文本检索默认余弦，因为不受文本长度影响。归一化后三者排序一致，可以互换——因为长度都变成 1，欧氏平方 = 2 - 2×余弦，点积 = 余弦。

**追问三：为什么医疗场景的向量检索必须配混合检索？举一个纯向量失败的例子。**

因为纯向量在否定句、精确数字、专有名词上系统性偏弱。例子（本篇实测）：「服药期间能否饮酒」的 Top-1 是「可少量饮酒」，真正的禁忌「禁止饮酒」只排第二；「儿童剂量」检索把「成人剂量」排进前列。混合检索用全文检索补关键词精确匹配，用重排序做精筛。

**追问四：Embedding 维度和成本是什么关系？降维的代价是什么？**

维度越高表达越细，存储与计算成本线性上升。降维几乎免费但会掉召回——被裁掉的维度里可能藏着「否定词」的区分信号。医疗这类漏一条会出事的场景，宁可留足维度。
