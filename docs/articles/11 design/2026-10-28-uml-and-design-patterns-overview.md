## 🎯 这篇文章解决什么问题

背了 23 种设计模式的定义，看开源库源码还是一头雾水——问题不在你没记住，而在你跳过了中间那层：**图**。

设计模式的知识不是一个个孤立的名词，它长在一张张结构图上。看不懂图，模式就只是文字；看得懂图，模式就成了你读源码时的「望远镜」。

这篇文章只做三件事：

- **补识图能力**：UML 到底怎么来的、开发者真正用得上的是哪两类图、类图六种关系怎么一眼分清

- **破除错觉**：前端不是「用不上设计模式」，而是「设计模式藏得深」

全篇主线就一句：**先能看懂图，再谈模式**。读完之后，你手上会有两张东西：一张 UML 识图速查表，一张 23 种模式的全景图。

## 一、看不懂的那些图，本质都是 UML

先说一个可能让你意外的判断：**你每天在官方文档里看到的那些方框箭头图，没有一张是随手画的，它们全都有 UML 的语法出处。**

### Redux 数据流图、React 组件树图，都是简化版 UML

打开 Redux 官方文档，第一页那张 `View → Action → Store → View` 的循环图；打开 React 文档，那张父组件包着子组件的树状图；打开 Vue 文档，那张 `Template → Render Function → VNode → DOM` 的流程图。

它们看上去风格各异，但拆开看，用的都是 UML 里最基础的三个东西：**矩形代表结构单元、箭头代表流向或依赖、菱形和空心三角代表关系的类型**。

UML 从来不是「画给架构师看的重型工具」，它是**一套约定俗成的图形语法**。就像你不能因为日常聊天不用文言文，就说文言文不存在——你日常画的每一张简化图，都是这套语法的白话版本。

### 面试白板题的沟通语言

白板题是最不讲情面的一场考试，因为它考的不是你知不知道，而是**你能不能当场把想法组织出来**。

用不规范的方框连线，问题不在「丑」，而在于**信息丢失**。面试官看到一条没有箭头的实线，他无法判断：这是一次调用？一个字段引用？还是继承？他只能追问。而你每被追问一次，就损失 30 秒和一次建立专业印象的机会。

反过来，当你在白板上画出空心三角指向父类，面试官一瞬间就知道「这个人懂 is-a」；你画出实心菱形连着整体，他立刻明白「这个人分得清生命周期绑定」。**图的规范性，在面试里是效率，也是信号。**

### Code Review 时说不清关系

这是最日常、也最伤团队的一种损耗。

两个人评审同一段数据层设计，都说「这里是组合关系」——一个在说「父组件把 props 传给子组件」，另一个在说「这个 service 内部 new 了一个 client」。两种说法都不算错，但**指的根本不是同一件事**。等他们意识到这一点，二十分钟已经过去了。

🔧 **真实场景**：一次药品详情页的数据层评审，讨论「处方数据」和「药品数据」到底是什么关系。做前端的人说这是组合，因为处方对象里包含了药品；做后端的人说这是聚合，因为药品是独立主数据、处方只是引用它的 ID。两个人都没说错——**前端看到的是结构，后端看到的是生命周期**。这就是为什么必须先统一图形语言：图能强迫你把「结构」和「生命周期」分开描述。

> 💬 **面试官**：你觉得设计模式的学习，为什么通常从 UML 开始？
>
> ✅ 标准答案：因为设计模式的本质是「对象之间的关系和协作方式」，而 UML 类图和序列图正是描述这两件事的标准化语言。不懂 UML 时，模式只能靠文字死记——「装饰器模式是动态地给对象添加职责」，这句话背下来也不会用；懂 UML 后，你会看到装饰器就是「Decorator 实现 Component 接口同时持有一个 Component 引用」，结构一出来，什么时候该用它就自明了。
>
> 🎁 加分答案：能补一句——UML 的价值不只是「画图」，更重要的是它逼你把模糊的直觉变成精确的判断。比如「这两个类有关系」是模糊的，「这是聚合而非组合，因为被聚合对象的生命周期由外部管理」是精确的。面试和 Code Review 里，能被精确表达的判断才是有价值的判断。

## 二、软件是怎么造出来的：生命周期与三种开发模型

在聊设计模式之前，得先回答一个更基础的问题：**设计模式在软件的哪个环节被用到？**

这个问题看起来和前端无关，但它恰恰解释了为什么很多前端工程师「感觉自己不需要设计模式」。

### 软件生命周期的五个阶段

一个软件从想法到上线，通常要走完这条线：

**可行性分析报告和软件开发计划**——产出可行性分析报告。判断这件事值不值得做、技术上做不做得成。

**需求分析阶段**——由软件分析师来做，需要懂技术也需要懂业务，分析出软件需要完成什么功能，产出需求分析说明书和初步的用户手册。

**软件设计（概要设计和详细设计）**——由架构师/项目经理来做。根据团队技术基础确定用什么技术栈（Java/Node/PHP），确定部署的操作系统，使用什么数据库（Oracle/MySQL/SQLServer），设计数据库表，选择团队成员，产出软件设计文档。

**编码工作**——开发人员来做，把设计编成代码，产出源代码以及清单。

**测试阶段**——由测试工程师进行，分为白盒测试（单元测试）和黑盒测试（功能测试），产出测试报告。

**实施和运维**——由实施工程师执行，把项目按照需要安装和配置好，让客户使用并解决简单问题，产出软件维护报告。

这六个环节串起来，就是一条完整的生命周期。注意其中第三个——**软件设计**，它还分「概要设计」和「详细设计」两个层次。

### 瀑布模型

瀑布模型（Waterfall Model）是一个项目开发架构。

它的开发过程是通过设计一系列阶段顺序展开的，从系统需求分析开始直到产品发布和维护，每个阶段都会产生循环反馈。如果有信息未被覆盖或者发现了问题，那么最好「返回」上一个阶段并进行适当的修改，项目开发进程从一个阶段「流动」到下一个阶段——这就是瀑布模型名称的由来。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638355999173-5f8a6173-fa45-4172-b695-d4dc3bff3eca.png)

这张图把每个阶段的输入和产出列得很清楚：需求方和开发方共同确定软件开发目标，做可行性研究以确定项目可行；对需求方提出的所有需求进行详细分析，和客户反复确认，充分理解客户需求；根据需求分析的结果对整个软件系统进行抽象和设计，如系统框架设计、数据库设计；将架构设计和界面设计的结果转换成计算机能运行的程序代码；在编码完成后对可运行的结果对照需求分析文档进行严密的测试，如果测试发现问题需要修复；软件正式运行使用后需继续维护，修复错误和增加功能。

**瀑布模型的关键特征是「线性 + 可回退」**：阶段是顺序的，但不允许跳过；发现问题就退回上一阶段改。它的缺陷也很明显——真实项目里，需求几乎不可能在开工前就完全确定，所以整条瀑布走完才发现方向错了，代价极高。

### 增量开发模型

增量模型是把待开发的软件系统模块化，将每一个模块作为一个增量组件，从而分批次地分析、设计、编码和测试这些增量组件。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638356302276-e9857690-ed4b-470a-a7f3-56559b44f5f6.png)

这张图画的是增量的构建路径：以增量构件为单位定义需求框架，按照构件组成及其关系设计软件系统体系结构，再细化构件需求、设计构件、实现构件、验证构件，最后将构件集成进系统、验证系统，直到系统完成。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638356310554-ec8bc35b-ff01-4f87-8dc7-d4ef47d4727c.png)

第二张图对比了「整体模型」和「每个增量构件的模型」：整体上需求分析、设计、编码、测试、交付是分层的，但每个增量构件（增量 1/2/3/4）都会独立走一遍分析、设计、编码、测试、验证、交付，针对每个构件详细设计、编码和集成，经测试后交付给用户，最后统一维护。

**增量模型的思路，其实就是前端现在最熟悉的「迭代交付」**：先上一个能跑的版本，再一块一块往上加。它对前端的意义格外大——因为前端的页面天然就是可拆分的构件。

### 原型开发模型

原型模型指的是在执行实际软件开发之前，应当建立系统的一个工作原型。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638356863805-e82d4e0d-0078-44fa-8108-6cfae099260b.png)

这张图的流程是：简要获取需求 → 快速设计 → 建造原型 → 客户评价 → 评审、修改 → 再加工原型 → 循环，直到进入正式的开始与维护阶段。

**这个模型在今天几乎是前端的主场**——产品经理拿着 Figma 稿、前端快速搭一个能点的原型、拉上业务方试用、改完再定需求。你做的每一次「Demo」和「技术验证页」，本质上都在跑原型模型。

### 设计模式在哪一步登场

现在回到那个关键问题：**设计模式到底在生命周期的哪一步被用到？**

答案很明确：**软件设计阶段**，尤其是「详细设计」这一步。

需求分析回答「做什么」，编码回答「怎么敲出来」，而设计回答的是「**用什么结构组织**」——模块怎么切、类怎么分、谁依赖谁、变化点封在哪里。设计模式全部服务于最后一件事。

这也解释了一个很多人没说出口的困惑：**为什么在前端做业务开发，会「感觉不到」设计模式？**

因为大多数前端工程师常年在「编码」阶段打转。需求从产品那里来、接口从后端那里来、设计稿从 UI 那里来，中间那段「结构怎么设计」被跳过了——直接开始写组件、写 Hook、写请求。你没做过「设计」这件事，自然也就不需要设计模式的武器库。

而当你从「写页面」走向「搭架构」——设计一个跨项目的组件库、一套状态管理方案、一个可插拔的请求层——你就会在某个瞬间发现：**这些问题早就有人解决过了，而且解法的名字就叫设计模式**。

## 三、UML 从哪来：模型、组成与工具

### 盖楼先画图纸：模型是什么

建造一栋大楼前需要先把图纸画好，把外观、内部结构描述清楚——这些图纸就是模型。

**Unified Modeling Language（UML），又称统一建模语言或标准建模语言。** 注意它的名字里有「Language」，不是「Tool」——它是一套语言规范，不是某个软件。

### 模型的三个特点

一份好的模型有三个特点：

- **简单**：只保留必要的抽象，不画实现细节。组件图只画「有哪几个模块」，不画模块里有多少行代码
- **多视角**：同一个系统可以有多张模型图。架构图看整体结构，时序图看调用顺序，部署图看机器分布——它们不冲突，是同一件事的不同切面
- **通用符号**：符号是行业共通的，不需要额外解释。团队新人和老人看图看到的是同一件事，这就是模型能降低沟通成本的原因

### UML 的组成：事物、关系、图

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638358079665-457047db-dbb5-4821-9f16-ccfbf485ca99.png)

这张图信息量很大，但拆开看层次很清楚。UML 由三部分组成：

**事物**——UML 里最基础的构成单元，分四类：结构事物（类、接口、用例、组件、协作、节点）、行为事物（交互、状态机）、分组事物（包）、注释事物（注释）。

**关系**——把事物连起来的东西，包括关联关系、依赖关系、泛化关系、实现关系、聚合关系。

**图**——事物和关系组合成的完整视图，分为用例视图、逻辑视图、并发视图、组件视图、配置视图，每个视图下对应若干种图。

用一句大白话翻译这三个层级：**事物是名词，关系是动词，图是句子。** 你要读懂一张架构图，本质上就是读懂一句话——「谁和谁是什么关系」。

### 工具链：StarUML、PlantUML 与 Mermaid

记笔记时常用的是 **StarUML** 这类可视化工具：拖着方框和箭头画，所见即所得，适合画一次性的示意图。

但在真实项目里，更推荐 **PlantUML** 和 **Mermaid** 这种「写文本生成图」的工具，原因有两个：

- **能进 Git**：图是用代码描述的，所以图的每一次修改都有 diff、可 review、可回滚。拖拽工具画出来的 `.xmind`/`.uml` 二进制文件做不到这点
- **改起来快**：加一个类，改两行文本就行，不用重新拖框调位置

这篇文章里出现的所有类图，都用 Mermaid 的 `classDiagram` 语法写——读的时候顺便就学会了一套画图工具。

> 💬 **面试官**：你平时画架构图用什么工具？为什么？
>
> ✅ 标准答案：用 Mermaid 或 PlantUML 这类文本化工具，因为它们能以纯文本形式进版本库，图的修改能和代码一起 review、一起回滚。拖拽工具虽然出图快，但图是二进制文件，团队协作时无法 diff，改一次就要重新对齐一遍布局。
>
> 🎁 加分答案：能补充「图的目的决定工具」——如果是给非技术方看的一次性示意图，Figma/draw.io 更合适；如果是长期维护的系统文档，一定要用文本化工具，因为它和代码一样有生命周期。能提到「图也是需要维护的资产」，说明你对工程化的理解是成体系的。

## 四、设计模式到底是什么

### 它给的是套路，不是代码

设计模式是**可复用的解决方案**：针对软件设计中反复出现的某类问题，经过验证的通用解法。

注意这句话里最关键的三个字——**套路**，不是**代码**。

这是 GoF（Gang of Four，四人组）在 1994 年那本《设计模式：可复用面向对象软件的基础》里定下的调子。书里对每个模式都只描述四件事：**意图、结构、参与者、效果**。它从来不给「复制这段代码就能用」的完整实现，因为同一个模式在 Java、C++、JS 里的代码长得完全不同。

所以学设计模式最容易走的两条歪路是：

- **只背定义**：能说出「策略模式定义了一系列算法」，但遇到「表单校验规则越堆越多」这种场景时完全想不到它
- **只抄代码**：背下来某个 TS 实现，但只要代码结构一变（比如从 class 改成函数式），就认不出来了

正确的姿势是：**记住「什么问题 → 什么结构」这个映射**。

### 为什么必须按三类记

23 个模式听起来很多，但 GoF 已经帮你分好了组——按**问题域**分三类：

- **创建型（5 种）**：解决「对象怎么生产」的问题
- **结构型（7 种）**：解决「对象怎么组合」的问题
- **行为型（11 种）**：解决「对象怎么协作」的问题

这里有一个非常重要的认知：**这是「问题域」的分类，不是「实现」的分类。**

什么意思？意思是这三类对应的是**你在设计时遇到的三类困惑**：

- 需求一来，你先问「这个对象该由谁来创建？」——创建型的战场
- 再问「这些模块之间怎么拼装、怎么复用？」——结构型的战场
- 最后问「它们之间怎么通信、谁通知谁？」——行为型的战场

所以正确的学习路径是「**按问题找模式**」，而不是「背模式找问题」。前者是先有困惑再找工具，后者是先攒工具再等困惑——而后者的结果是，等到困惑真的来了，你已经想不起工具箱里有什么了。

把这三条路径画成一张树，就是 23 种模式的**问题域地图**——从「你正在纠结什么」往下走，就能找到该用的模式：

```text
你在纠结什么？
│
├── ① 对象怎么生产（创建型 5 种）
│   ├── 全局只留一个实例          → 单例
│   ├── 创建哪种对象由子类决定      → 工厂方法
│   ├── 要造一整个产品族           → 抽象工厂
│   ├── 参数太多、可选字段一堆      → 建造者
│   └── 造一个新对象成本太高        → 原型
│
├── ② 对象怎么组合（结构型 7 种）
│   ├── 老接口和新接口对不上        → 适配器
│   ├── 调一个功能要碰五个子系统    → 外观
│   ├── 想动态加能力、不改原代码    → 装饰器
│   ├── 想控制别人怎么访问我        → 代理
│   ├── 单个节点和整棵树要一样用    → 组合
│   ├── 两个维度都要独立变化        → 桥接
│   └── 对象太多、内存扛不住        → 享元
│
└── ③ 对象怎么协作（行为型 11 种）
    ├── 状态变了要通知一堆人        → 观察者
    ├── 同一功能要能换算法          → 策略
    ├── 多步处理要能插拔、能中断     → 职责链
    ├── 请求要能排队、能撤销        → 命令
    ├── 状态自己会迁移、行为跟着变    → 状态
    ├── 流程骨架固定、细节可变      → 模板方法
    ├── 想统一遍历方式、不暴露内部    → 迭代器
    ├── 一堆对象互相纠缠、改不动     → 中介者
    ├── 要存快照、能回滚           → 备忘录
    ├── 结构不变、操作却总在加       → 访问者
    └── 要解析自定义的小语言        → 解释器
```

这张树比一张平铺的清单有用得多——**它把「模式名」换成了「你会遇到的问题」**。下次设计时卡住了，先在上面三组里找一句像你现在处境的话，再顺着箭头找到模式，这就是「按问题找模式」的实际用法。

### 23 种模式全景表

严格对齐 GoF 1994 定义的 23 种模式：

| 分类 | 数量 | 模式清单 |
|------|------|---------|
| 创建型 | 5 | 单例、工厂方法、抽象工厂、建造者、原型 |
| 结构型 | 7 | 适配器、桥接、组合、装饰器、外观、享元、代理 |
| 行为型 | 11 | 职责链、命令、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者、解释器 |

记不住没关系，先记住这一句**记忆锚点**：

**创建型解决「对象怎么生产」，结构型解决「对象怎么组合」，行为型解决「对象怎么协作」。**

### 边界说明：简单工厂与发布订阅

有两组概念必须提前划清边界，否则后面读着读着容易怀疑人生：

- **简单工厂**：常被当成工厂模式讲，但它**不属于 GoF 23 种**。它是「一个函数里用 switch 决定 new 哪个类」，结构上更像一个策略，但违反了开闭原则。**先看清它的缺陷，才能理解工厂方法为什么必须存在**——后面讲工厂方法时，会拿它做对照
- **发布-订阅**：也不是 GoF 模式，它是**观察者模式加了中介之后的变体**。因为前端（EventBus、Node.js EventEmitter、消息队列）几乎到处都是它，讲观察者时会专门对比两者，但请记住它不属于 23 种

划清边界不是为了抠字眼，而是为了**面试时不被打脸**。面试官问「GoF 23 种模式里有哪些行为型」，你答了「发布订阅」，那就答错了。

### 根在 SOLID：脱离原则背模式没有意义

所有模式的底下，压着的是 **SOLID 五原则**：

- **SRP 单一职责**：一个类只该有一个改变的理由
- **OCP 开闭原则**：对扩展开放，对修改关闭
- **LSP 里氏替换**：子类必须能替换父类
- **ISP 接口隔离**：不强迫依赖它不需要的接口
- **DIP 依赖倒置**：都依赖抽象，不依赖具体实现

**每一个设计模式，都是某条原则的具体落地。** 策略模式是 OCP 的落地，依赖注入是 DIP 的落地，接口拆分是 ISP 的落地。

这就是为什么「先学原则，再学模式」的顺序不能反。**脱离原则死记模式，你记住的是一堆孤立的形状；懂了原则再看模式，你看到的是同一个思想的不同剪影。** 第 01 篇会把 SOLID 逐个拆开，配前端场景讲透。

> 💬 **面试官**：23 种设计模式为什么要分成创建型、结构型、行为型三大类？这个分类依据是什么？
>
> ✅ 标准答案：这是 GoF 按「问题域」做的分类，不是按实现方式。创建型解决「对象怎么生产」（把实例化逻辑从调用方抽离），结构型解决「对象怎么组合」（如何把类或对象拼成更大的结构），行为型解决「对象怎么协作」（对象间如何分配职责和通信）。按问题域分类的价值在于：真实设计时你面对的是「我现在纠结的是什么问题」，而不是「我记得哪个模式」——所以这个分类能让你从困惑倒推工具，而不是从工具倒推困惑。
>
> 🎁 加分答案：能补一句「分类不代表边界严格」——比如建造者既可以算创建型（管对象怎么造出来），又带着组合的思想（分步骤拼装）；访问者既有结构型的形状（两次分发），本质又是行为型（分离操作与结构）。能指出同一个模式可以从不同角度归类，说明你对模式的理解已经脱离了背清单的阶段。

## 五、前端为什么尤其需要

### 不是用得少，是藏得深

很多人有一个根深蒂固的印象：「设计模式是后端和框架作者用的，我做业务页面用不上。」

真相恰恰相反。**前端不是「设计模式用得少」，而是「设计模式藏得深」**——它们被 React、Redux、axios、浏览器这些框架和运行时封装到了 API 背后，你天天在用，只是没意识到。

看看你每天都在写的东西：

| 你每天在用的东西 | 背后的模式 |
|------|------|
| Redux 全局 Store | 单例 + 观察者 |
| React HOC `withAuth(Comp)` | 装饰器 |
| axios 请求/响应拦截器 | 职责链 |
| 虚拟列表、DOM 节点复用 | 享元 |
| ESM `export const store` | 单例（无意图版） |
| DOM 事件冒泡 | 职责链 |
| axios 统一 fetch/XHR | 适配器 |
| `for...of` / 展开运算符 | 迭代器 |

一个不落。区别只在于：**后端工程师要自己把这些结构写出来，所以「看得见」；前端工程师大多直接调用框架提供的封装，所以「看不见」。**

### 从「看懂语法」到「看懂设计意图」

这就是为什么读源码这件事，在不同人身上会有量级差异。

初级工程师读源码，读到的是语法：这里定义了一个 class，这里用了一个闭包，这里做了个递归。

资深工程师读源码，读到的是设计意图：**这里为什么要多包一层？因为要在不改变原接口的前提下加控制——这是代理；这里为什么要 `.reduce` 把一串函数串起来？因为要支持任意插拔的处理节点——这是职责链；这里为什么只导出实例而不导出类？因为要保证全局唯一——这是单例。**

这个差别，就是文章开头那个面试场景的答案。面试官问「这是聚合还是组合」，问的从来不是图形知识，而是：**你知不知道这段代码在管什么**。

🔧 **真实场景**：读 Koa 的 `koa-compose` 时，如果不知道职责链模式，你会觉得「一个递归的 `next` 函数」很绕，看完就忘。但如果先认出「这是职责链的洋葱变体」，你会立刻反应过来：`next()` 前后两段代码分别对应「进入」和「返回」，所以中间件的注册顺序和实际执行顺序是「正进反出」。**认模式，等于先把骨架画出来，再去填血肉——阅读速度不是一个量级。**

> 💬 **面试官**：你平时在项目里用过哪些设计模式？举一个真实例子。
>
> ✅ 标准答案：讲一个「有痛点 → 有方案 → 有收益」的完整链条，不要罗列模式名。比如：药品搜索页有 5 种排序算法（价格、销量、评分、距离、综合），一开始写在一个大函数里用 if-else 分支，每加一种排序就要改这个函数。后来改造成策略模式——每种排序是一个独立的函数，注册到一张 `Map<string, SortStrategy>` 里，调用方只按 key 取策略执行。新增排序只需要加一个函数，主流程一行不改。
>
> 🎁 加分答案：能带上「选择理由」和「代价」——比如能补一句「之所以选策略而不是状态模式，是因为用哪种排序完全由用户选择、由外部决定，算法之间不互相迁移；如果是订单状态流转那种自己会变化的情况，就该用状态模式」。能主动说出「为什么不是另一个更接近的模式」，是面试里最能体现深度的表达方式。

## 六、UML 家族全景：七种图，真正要深挖的只有两类

### 结构图与行为图的分界线

UML 2.5 规范里一共定义了 14 种图，但日常开发真正会画会读的只有 7 种，而其中值得深挖的只有 2 种。

先按 UML 的两大分类把这 7 种归位：

**结构图**——描述系统「是什么」，是静态的。包括用例图、类图、对象图、组件图、部署图。

**行为图**——描述系统「怎么运作」，是动态的。包括活动图、序列图、协作图。

之所以只深挖两类，是因为前端的日常需求非常简单：**看结构找类图，看调用找序列图。** 其余的图，了解「什么时候会用到」就够了。

### 用例图：系统能做什么

用例图建模最主要的功能是表达系统的功能性需求或行为。

两个核心概念：**参与者**，指与系统交互的角色，可以是人，也可以是事物或其他系统；**用例**，是系统为参与者提供的功能，用例名称一般是一个带有动作性的词语。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638408814640-6020fd9c-8fea-4b8f-833a-49ef2aa287f2.png)

这张图里有登录、找回密码、注册三个用例，并且用 `<extend>` 和 `<include>` 标出了它们的展开关系——「检查用户是否可用」是被登录包含的必经步骤，而「找回密码」是对登录的扩展场景。

用例图真正的价值不在图形本身，而在**用例描述的表格**。一张用例图只告诉你「有哪些功能」，具体行为要靠文字补全：

| **项目** | **内容** |
| --- | --- |
| 用例名称 | 登录 |
| 用例ID | login |
| 角色 | 用户 |
| 用例说明 | 描述用户的登录过程 |
| 前置条件 | 打开网址页面 |
| 基本事件流 | 1.点击登录 2.输入用户名和密码 3.点击登录 4.服务器会使用会话保存用户登录状态 |
| 其它事件流 | 1.用户名为空提示用户名不能为空 2.秘密为空提示密码不能为空 |
| 异常事件流 | 登录超时则返回登录页 |
| 后置条件 | 登录成功，进入个人中心 |

这张表的结构值得学：前置条件、基本事件流、其它事件流、异常事件流、后置条件——**它把「正常路径」「校验失败路径」「超时异常路径」全部拆开了**。你写表单校验时如果也按这个结构列需求，会少漏很多边界。

### 对象图：某一刻的快照

对象描述一组对象和他们之间的关系，它是系统状态的某一时刻的快照。

它的使用相当有限，主要用于了解系统在某个特定时刻的具体状况和数据结构。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638413625087-5db5129e-346b-464f-a3df-7e8333d35dd2.png)

对象表示方法和类图大致相同，区别在于——**对象图中的对象属性可以有具体值**。类图里的「部门」是一个抽象概念，对象图里的「总裁部」「销售部」「研发部」「财务部」是真实存在的四个实例。

还有一条容易忽略的对应关系：**类图中的一个类，可以对应成对象图中的多个对象。** 比如「部门」这个类的自关联，在对象图里就展开成了多个部门之间的实际关联。一句话概括：**类图是设计图纸，对象图是施工完成后的照片。**

### 活动图：UML 里的流程图

在 UML 里，**活动图本质上就是流程图**。它描述系统的活动、判断系统的活动、判断点和分支等。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638414776275-979db0a8-91c2-48fd-8c3b-d47fad49d4e8.png)

这张图就是最朴素的「点击登录 → 输入用户名和密码 → 登录成功」。

正因为活动图和流程图几乎等价，它在 UML 里反而**最不需要专门学**——你画流程图的直觉可以直接用。但要注意，这也意味着它是**最容易被误用**的一种图：很多人在该画序列图的时候画了活动图，结果丢掉了「是哪个对象负责这一步」这个关键信息（第八节会详细对比这两者）。

### 协作图：时序图的空间版本

协作图是时序图的一种变种。

它强调的是**发送和接收消息的对象之间的组织结构**——显示了一系列对象和在这些对象之间的联系，以及对象之间发送和接收的消息。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638418668426-e259e769-7d30-4a45-90c8-fb126f345b7e.png)

这张图和后面第八节要讲的登录时序图是**同一件事的两种画法**：时序图从「用户」往下垂直排列各对象，强调消息在**时间上的先后**；协作图把各对象水平铺开、用带编号的箭头连接，强调对象之间的**静态连接关系**。

判断标准很简单：**你关心「先调谁后调谁」就画时序图，你关心「谁连着谁」就画协作图。** 前端场景里 99% 的情况属于前者，所以协作图可以只作了解。

### 组件图：系统由哪些部件拼成

组件图用来建立系统的各个组件之间的关系——它们是通过软件或者文件组织在一起的。

使用组件图可以帮助读者了解某个功能位于软件包中的哪个位置，以及各个版本之间组件包含哪些功能。它也可以用来帮助设计系统的整体架构。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638418985547-28036da9-8749-4d8f-aa47-18e26968ca17.png)

这张图把系统拆成业务层组件、控制层组件、模型层组件、视图组件四块——**这就是经典的分层架构图**。你在项目 README 里画的那张「`apps/web` → `packages/ui` → `packages/shared`」的模块依赖图，本质上就是一张组件图。

### 部署图：部件跑在哪台机器上

部署图用来帮助读者了解软件中各个组件运行在什么硬件位置，以及这些硬件之间的交互关系。

两个核心元素：**节点**，用来表示一种硬件，可以是服务器、计算机等，节点的符号是一个三维盒子，在左上角包含节点名称；**通信关联**，节点通过通信关联建立彼此的关系，采用从节点到节点绘制实线表示关联。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638419370218-de8e66a7-b8d9-4eff-9cc8-13bb4caee78f.png)

这张图画的是最典型的前后端部署关系：浏览器 → nginx → Node.js → MySQL。

**部署图是唯一能回答「这段代码到底跑在哪」的图。** 当你需要跟人解释「为什么这个请求要多跳一层」「为什么本地能跑线上不能跑」时，一张部署图比十句话都有效。

## 七、类图：读懂开源库结构图的基石

终于到本篇最核心的一节。**如果你只学一种 UML 图，就学类图。** 因为 23 种设计模式里，有 20 种以上都要用类图来描述结构。

### 三段式结构：类名 / 属性 / 方法

类图（Class Diagram）描述类的静态结构，定义类以及描述类之间的联系，如关联、依赖、聚合等，还包括类的内部结构（类的属性和操作）。

一个类在类图里被画成一个矩形，分成上中下三段：

**上段：类名**。如果是接口，名字上方会标 `<<interface>>`；如果是抽象类，标 `<<abstract>>`。

**中段：属性**。格式是 `name: attribute type = default value`——名字、类型、默认值。

**下段：方法**。格式是 `name(parameter list): type of value returned`——方法名、参数列表、返回值类型。

| **类型** | **示例** |
| --- | --- |
| 属性格式 | name: attribute type = default value |
| 操作格式 | name(parameter list): type of value returned |

属性的可见性用符号前缀表示：

- `+` 表示 public
- `-` 表示 private
- `#` 表示 protected

**这套符号和 TypeScript 几乎是逐字对应的。** 你在 TS 里写 `private constructor()`，在类图上就是 `-constructor()`；你写 `public getInstance()`，类图上就是 `+getInstance()`。所以对前端来说，类图不是「另一套要学的语言」，而是「TS 代码的图形化投影」。

还有一个对应关系值得点出：**类图里的 `<<interface>>` 对应 TS 的 `interface`，普通类对应 TS 的 `class`**。而 `interface` 只能声明方法签名不能有实现——这正好对应下一节要讲的「实现关系」和「泛化关系」的区别。

### 六种关系的强度阶梯

这是全篇最容易糊的一节，也是面试最爱问的一节。UML 对这六种关系的定义，本身就是一条层层递进的线索：

- **依赖关系**：只要在类中用到了对方，那么它们之间就存在依赖关系，如果没有对方，连编译都通不过
- **泛化关系**：实际上就是继承关系，它是依赖关系的特例
- **关联关系**：实际上就是类与类之间的关系，它是依赖关系的特例；关联关系比依赖关系的关系更强
- **聚合关系**：表示整体和部分的关系，整体与部分可以分开；聚合是关联关系的特例，所以它具有关联的导向性和多重性
- **组合关系**：也是整体和部分的关系，但是整体与部分不可分开，两者的生命周期一致

从这些描述里能抽出两个维度的判断：

**第一个维度：耦合强度阶梯（has-a 家族）**

依赖 < 关联 < 聚合 < 组合——**越往后，两个类绑得越死**。

**第二个维度：is-a 还是 has-a**

- 泛化（继承）和实现（接口）属于 **is-a**：鸟「是一个」动物，所以鸟能替代动物出现
- 关联、聚合、组合属于 **has-a**：雁群「有一个」大雁

把这六个关系画成一张速查图：

```text
  is-a：是不是                      has-a：有没有
 ┌────────────────────────┐        ┌────────────────────────┐
 │ 泛化 Generalization     │        │ 关联 Association        │
 │ 实线 + 空心三角 ▲        │        │ 实线 + 箭头（可无）      │
 ├────────────────────────┤        ├────────────────────────┤
 │ 实现 Realization        │        │ 聚合 Aggregation        │
 │ 虚线 + 空心三角 ▲        │        │ 空心菱形 ◇ 生命周期独立  │
 └────────────────────────┘        ├────────────────────────┤
                                   │ 组合 Composition        │
 另外还有：                          │ 实心菱形 ◆ 生命周期绑定  │
 依赖 Dependency                    └────────────────────────┘
 虚线 + 箭头（临时使用）

                耦合强度：依赖 < 关联 < 聚合 < 组合
```

下面把这六种关系逐一过一遍，每一种都配一张图和一句「前端里它长什么样」。

**依赖关系（Dependency）**——只要在类中用到了对方，就存在依赖，没有对方连编译都通不过。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638413862637-28246a98-ab83-43c6-84e2-8c567c98bb89.png)

这张图里「水」和「动物」的关系，就是最弱的依赖。**前端里的对应**：一个函数接收一个工具类作为参数，用完就丢，不保存——这就是依赖。

**泛化关系（Generalization）**——即继承关系，是依赖关系的特例。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638413972592-4a51dc85-af58-417d-9d4f-17947924204f.png)

「鸟」继承「动物」，所以鸟有年龄、姓名，也会吃饭喝水，同时还多了翅膀和飞翔。**前端里的对应**：`class Bird extends Animal`。

**实现关系（Implementation）**——接口与实现类之间的关系。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638414093265-1f2e33b3-0589-4e17-bd53-c1ab5e6187ea.png)

「下蛋」这个行为被抽象成接口，「鸟」实现它并返回 2。**前端里的对应**：`class Bird implements Eggs`。

**关联关系（Association）**——类与类之间的关系，是依赖关系的特例，比依赖更强。

关联有两个特性值得记住：

- **导航性**：单向或双向，表示关系在哪一方维护
- **多重性**：用数字标注数量关系

多重性的常见写法，有这几种：

- `1`：表示有且仅有一个
- `0...*`：表示 0 或多个
- `0,1`：表示 0 或 1 个
- `n..m`：表示 n 到 m 个都可以
- `m...*`：表示至少 m 个

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638414467360-6ac1f566-02fe-4c42-af3c-ae63389ad1f4.png)

这张图信息最密：唐老鸭有 1 个爸爸（`1`）、有 0 到多个朋友（`0..*`）、有 0 或 1 个老婆（`0..1`）、有 1 到多个孩子（`1..*`）、有 0 到 2 套房子（`0..2`）。**多重性是把「关系」变成「数量约束」的工具**——它是最容易被忽略、但在数据建模时最有用的一个标注。

**聚合关系（Aggregation）**——整体和部分的关系，但整体与部分**可以分开**。

聚合是关联关系的特例，所以它具有关联的导向性和多重性。关键特征是：**聚合的双方生命周期是独立的。**

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638414618077-f59de57c-7ee8-4f3d-b761-45839059be5c.png)

「雁群」聚合了「大雁」——雁群散了，大雁还在。**前端里的对应**：一个列表组件接收一个 `items` 数组，组件卸载了，那些 item 数据还在外面活着。

**组合关系（Composition）**——也是整体和部分的关系，但**整体与部分不可分开**，整体和部分的生命周期一致。

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638414694524-ba071743-81fa-459b-8458-9c5f8f607b2c.png)

「大雁」组合了「翅膀」——大雁死了，翅膀也就不存在了。**前端里的对应**：一个类在构造函数里 `new` 出一个成员，外部拿不到、也无法替换，生命跟着宿主走。

### 完整代码对照：唐老鸭那套类怎么画

光看图没用，得把图和代码对上。下面是一份完整的 TypeScript 实现，我们逐块看。

第一块，最基础的类与依赖：

```typescript
class Water {}

class Animal {
  public name?: string;
  public age?: number;
  // 类的依赖关系在代码中的表示是属性关系，这就是依赖关系
  public water?: Water;
  public eat() {}
  public drink() {}
}
```

上面代码里那句注释写「依赖关系在代码中的表示是属性关系」。**它想表达的是「用到了就是依赖」，但严格来说需要修正**：把一个类声明成字段持有，在 UML 里对应的是**关联**（Association），不是依赖。真正对应「依赖」的是方法参数、局部变量、返回值这类**临时使用**：

```typescript
class Animal {
  // 关联：字段持有，长期知道对方存在
  public water?: Water;

  // 依赖：只在方法执行期间用到，用完即弃
  drink(w: Water) {
    /* 用一下 w，不保存引用 */
  }
}
```

这个区别不是抠字眼——它直接决定了两者的耦合强度。**字段持有意味着「我始终依赖你」，参数传递意味着「我只是这次需要你」。**

第二块，泛化 + 实现：

```typescript
// 接口是行为的抽象
interface Eggs {
  layEggs(): number;
}

class Bird extends Animal implements Eggs{
  public swing?: number;
  public fly() {}
  layEggs(): number {
    return 2;
  }
}
```

这一行 `extends Animal implements Eggs` 里同时出现了两种关系：`extends` 是**泛化**（is-a，鸟是动物），`implements` 是**实现**（鸟承诺具备下蛋的能力）。在类图上，前者是实线空心三角，后者是虚线空心三角——**差一个虚线的区别，语义完全不同**：泛化继承的是实现，实现只是继承契约。

第三块，多重性最丰富的一个类：

```typescript
class TangDuckFather {}
class TangDuckFriend{}
class TangDuckWife{}
class TangDuckChild{}
class TangDuckHouse{}
class TangDuck extends Bird {
  public father?: TangDuckFather;
  public friends?: Array<TangDuckFriend>;
  public wife?: TangDuckWife;
  public children?: Array<TangDuckChild>;
  public house?: Array<TangDuckHouse>;
}
```

对照前面那张关联图的多重性：`father?` 是 `0..1`，`friends?` 是 `0..*`，`children?` 是 `1..*`（这里用可选标记弱化了，实际业务里应该是必填），`house?` 是 `0..2`。

**一类字段写法，直接对应一套 UML 多重性标注**——这就是类图和代码的映射关系。

第四块，聚合与组合的对照：

```typescript
class Wing {}
class WildGoose extends Bird {
  public wings?: Wing[];
}
class WildGooseGroup {
  public wildGoose?: WildGoose[];
}
```

这里有两个「整体-部分」结构：`WildGoose` 有 `wings`，`WildGooseGroup` 有 `wildGoose`。**但从这段代码看不出哪个是聚合、哪个是组合**——因为两者在 TS 里的写法一模一样，都是字段声明。

这正是下一节要解决的问题。

### 聚合 vs 组合：代码长一样，区别在谁管生死

先给一句判断标准，把它刻在脑子里：

**不是看「有没有整体和部分」，而是看「部分由谁创建、由谁销毁」。**

```text
        外部创建，传进来                自己创建，自己销毁
    ┌──────────────────────┐     ┌──────────────────────┐
    │      聚  合  ◇        │     │      组  合  ◆        │
    │  整体死了，部分还活着   │     │  整体死了，部分跟着死   │
    └──────────────────────┘     └──────────────────────┘
            ↓                              ↓
    constructor(private x: X)        class A { private x = new X() }
    props 传进来的数据                组件内部 useMemo 出来的派生数据
```

举个前端里最直观的例子：

```typescript
// 聚合：外部传进来，组件卸载后数据依然在外部存活
class DrugList {
  constructor(private drugs: Drug[]) {}
}

// 组合：内部创建，宿主一销毁，翅膀也就没了
class WildGoose {
  private wings: Wing[] = [new Wing(), new Wing()]; // 👈 自己创建、自己销毁
}
```

🔧 **真实场景**：React 里 `props` 传进来的用户对象是**聚合**——父组件先有了这份数据，才传给你；你卸载了，数据还在父组件那儿。而组件内部用 `useMemo` 基于 props 算出来的派生列表是**组合**——它只在这个组件存活期间有意义，组件一卸载就该被回收。**理解这个区别，你就理解了为什么派生数据该用 `useMemo` 而不是 `useState` 缓存**：前者生命周期跟着渲染走，后者会独立存活、产生额外状态。

> 💬 **面试官**：类图里聚合和组合的区别是什么？举一个前端的例子。
>
> ✅ 标准答案：两者都是「整体-部分」关系，区别在**生命周期是否绑定**。聚合是空心菱形，整体与部分可以分开、生命周期独立——比如列表组件和它接收到的 `items` 数据，组件卸载了数据还在；组合是实心菱形，整体与部分不可分割、生命周期一致——比如组件和它在内部创建的子状态，宿主销毁则部分一起销毁。
>
> 🎁 加分答案：能补三点——① 在代码层面的判断依据不是「字段怎么写」，而是「谁负责创建和销毁」：外部注入是聚合，内部 `new` 是组合；② 这个区别在实际设计里有真实后果：组合关系下的部分不能泄漏到外部，否则会出现「宿主已销毁但部分仍被引用」的悬垂引用，React 里对应的就是组件卸载后仍持有 state 导致的泄漏；③ 可以提到「同一个业务概念在不同层次可以有不同的关系」——比如「处方」和「药品」，在数据模型层是聚合（药品是独立主数据），在 UI 层的某个处方卡片组件里可能是组合（卡片内部创建的展示态药品对象）。

## 八、序列图：看懂方法调用的时间顺序

类图回答「有哪些类、它们什么关系」，序列图回答「它们之间怎么按时间顺序交互」。**一个管结构，一个管行为**——读源码时这两张图配合使用，基本就能把一段逻辑吃透。

### 五个核心元素

时序图强调消息时间顺序的交互图。它描述系统中类与类之间的交互，将这些交互建模成消息交互，用于描述对象之间如何随着时间进行协作。

它由五个部分组成：**活动者（Actor）、对象（Object）、消息（Message）、生命线（Lifeline）、控制焦点（Focus Of Control）**。

不同的元素有不同的表示法，各有明确的含义：

- **对象**：一个矩形，对象名称下有下划线
- **消息**：方向箭头表示，调用时实线，返回消息时虚线
- **生命线**：纵向的虚线，代表对象的存在时间
- **控制焦点**：纵向的矩形，也就是活动条（Activation Bar），代表方法正在执行中

再加一条常被忽略但很重要的：**活动者**是那个发起整个流程的外部角色，通常画在图的最左边，用一个小人表示。

把五个元素串成一句话：**一条生命线是一个对象的「一辈子的时间轴」，活动条是它「正在干活」的时段，消息箭头是它跟别人说话。**

### 登录流程走一遍

![](https://cdn.nlark.com/yuque/0/2021/png/738210/1638417340721-07699420-96c7-4afc-8f9e-c1db8e85ecda.png)

这张图把一次登录的时间线完整画出来了，按编号念一遍：

1. 用户 → 登录页：转到登录页面
2. 用户 → 登录页：输入用户名和密码
3. 登录页 → LoginController：调用
4. LoginController → LoginService：查询数据库（经过 UserModel）
5. LoginService → LoginController：返回结果
6. LoginController → 登录页：返回登录是否成功
7. 登录页 → 成功页面：成功则跳转到成功页
8. 登录页 → 登录页：失败则跳回登录页
9. 提示用户

注意这张图里有两种箭头：**实线的同步调用**（3、4）和**虚线的返回**（5、6）。还有激活框——`LoginController` 和 `LoginService` 上那几段纵向的矩形，标出的是「这个方法正在执行中」的时间段。

**读序列图最关键的一点，是看激活框的嵌套关系。** 谁的活动条包含谁，就说明谁在等谁返回——这是理解异步/同步关系最直观的方式。

### 序列图 vs 流程图

这是本节的第一个面试核心问，必须讲清。

很多人把活动图（流程图）和序列图混为一谈，因为它们都长得像「一条条带箭头的流程」。但两者的关注点完全不同：

```text
        流 程 图（活动图）                序 列 图
    ┌────────────────────┐        ┌────────────────────┐
    │  关注：单条流程内部   │        │  关注：多个对象之间   │
    │  的步骤和分支判断     │        │  的消息先后与返回     │
    ├────────────────────┤        ├────────────────────┤
    │  ✅ 有 if / else 分支 │        │  ✅ 有「谁发起的」    │
    │  ✅ 有循环、并行      │        │  ✅ 有「返回了什么」  │
    │  ❌ 没有「对象」概念  │        │  ❌ 没有条件分支概念  │
    └────────────────────┘        └────────────────────┘
```

一句话概括：**流程图讲「这件事怎么做完」，序列图讲「这件事是谁让谁做的」。**

流程图的信息全在一个维度上（步骤），序列图多了一个维度（参与者）。所以当你需要表达「责任归属」时——比如「这个校验到底是谁做的、出错谁返回的」——流程图会丢掉这个信息，序列图不会。

### 用序列图读 Promise 链与中间件

这一节，是把序列图真正用到前端源码上的方法——**它比记住几个图形符号有用得多**。

**读 Promise 链，看的是「返回虚线的串联」。** 一条 `.then().then().then()` 的链，在序列图上是一条条向下的虚线返回逐级传递——每一层的 `then` 都在等上一层「返回」之后才开始。这解释了为什么 `.then` 里的代码是异步的：**它在序列图上永远是「收到返回之后」才激活的**。

```text
   PromiseA        then1          then2
      │              │              │
      │──resolve────▶│              │
      │              │  (执行)      │
      │◀────return───│              │
      │              │──value──────▶│
      │              │              │  (执行)
      │              │◀────return───│
```

**读 Koa 中间件，看的是「激活框的嵌套」。** 每个中间件在 `await next()` 之前和之后各有一段代码，在序列图上就是**自己的激活框把下一个中间件的激活框包起来**——这就是「洋葱模型」这个词的来源。

```text
   mw1      mw2      mw3
    │        │        │
    ├────────┼────────┤  ← 进入：mw1 前半 → mw2 前半 → mw3 前半
    │        ├────────┤
    │        │        │
    │        ├────────┤  ← 返回：mw3 → mw2 后半 → mw1 后半
    ├────────┼────────┤
    │        │        │
```

**这个「用序列图看嵌套」的能力，比记住「洋葱模型」四个字有价值得多**——因为下次遇到任何一个 `await` 前后都有逻辑的框架，你都能立刻画出它的执行顺序。

> 💬 **面试官**：序列图和流程图的本质区别是什么？
>
> ✅ 标准答案：流程图（活动图）描述的是**单个流程内部的步骤与分支**，关注「这件事怎么一步步做完」，没有「对象」概念，但支持条件判断和循环；序列图描述的是**多个对象之间消息交互的时间顺序**，关注「谁发起了什么、谁返回了什么」，有明确的对象和生命线概念，能表达调用与返回，但没有条件分支的概念。
>
> 🎁 加分答案：能补一句判断标准——「如果你需要表达责任归属（这个动作是谁做的），就用序列图；如果你需要表达决策走向（满足条件走哪条路），就用流程图」。再加一句实战体会：读框架源码时，序列图特别有用，因为框架的复杂度往往不在算法而在「调用链」，而序列图是唯一能同时画出「调用顺序」和「谁在等谁返回」的图——比如用序列图的激活框嵌套，能一眼看出 Koa 中间件为什么是洋葱模型。

## 💡 一张图总结（面试速记表）

| 识图与认知要点 | 一句话内核 | 考察频率 |
|------|------|------|
| 六种关系的强度阶梯 | 依赖 < 关联 < 聚合 < 组合；泛化/实现属 is-a，另有维度 | ⭐⭐⭐ 必考 |
| 聚合 vs 组合 | 不看「有没有整体-部分」，看「谁创建、谁销毁」 | ⭐⭐⭐ 必考 |
| 序列图 vs 流程图 | 前者讲「谁让谁做」，后者讲「这件事怎么做完」 | ⭐⭐⭐ 必考 |
| 23 种模式三类分法 | 创建型=怎么生产，结构型=怎么组合，行为型=怎么协作 | ⭐⭐⭐ 必考 |
| 类图与 TS 的映射 | 三段式对应 class/interface，`+ - #` 对应 public/private/protected | ⭐⭐ 高频 |

> 💡 记住这条主线：**看不懂开源库的架构图，不是因为图太复杂，而是因为你不认识它的语法。** 类图管结构、序列图管时序——把这两张图学会，23 种模式就从「一堆要背的名词」变成「一堆能认出来的形状」。
