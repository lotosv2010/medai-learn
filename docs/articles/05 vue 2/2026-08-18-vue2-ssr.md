# Vue 2 SSR 原理与实战：从 renderToString 到 Nuxt.js 生产部署（面试收藏级）

> 面试官问：「你的医疗门户 SEO 要求必须 SSR，服务端渲染究竟做了什么？」你答：「首屏返回 HTML 字符串，客户端再激活。」面试官接着追：「那 `renderToString` 到底怎么把组件变成字符串的？Hydration 失败会发生什么？为什么 data / store / router 都必须是工厂函数？asyncData 的数据是怎么传到客户端的？」一道 SSR 题，背后是双端入口、渲染管线、注水激活、状态隔离、缓存策略一整套体系。这篇文章从概念到源码到手写实现，把 SSR 一次性讲透，并单独加一章 Nuxt.js 由浅入深的讲解。

## 🎯 这篇文章解决什么问题

Vue 默认是**客户端渲染（CSR）**的框架——JS 在浏览器里运行，动态生成 DOM。但医疗门户这类场景，搜索引擎爬虫抓不到异步渲染的内容，SEO 做不上去；首屏还要等 JS 下载执行，白屏久。

**SSR（服务端渲染）把 Vue 组件在 Node 里渲染成 HTML 字符串，直接返回给浏览器**，爬虫能抓到，首屏秒开。但代价是服务端更复杂、状态容易串、生命周期和浏览器 API 都变了一个世界。

读完这篇，你既能**彻底看懂 SSR 的原理和源码**，也能**直接套用在面试上**：从 Nuxt 怎么用，到 renderToString 怎么实现，到手写一个可跑的药品门户 SSR，再到生产部署的缓存、PM2、Nginx 全链路。

## 🧩 一、为什么医疗门户必须 SSR

### 概念：放在浏览器渲染，还是放在服务器渲染

先看最朴素的定义。

**客户端渲染（CSR）**：浏览器加载一个空 #app，JS 接管后在浏览器里生成 DOM。SEO 不利——爬虫打开页面看到的是空的 div 和一堆 script，抓不到正文；异步数据还要等接口返回，更难抓取。

**服务端渲染（SSR）**：在 Node.js 里把组件渲染成 HTML 字符串，连同内容一起发给浏览器。爬虫一上来就拿到完整内容，能被抓取到。

`Vue.js` 默认构建客户端应用，在浏览器中输出组件、生成 DOM 和操作 DOM。但也可以把同一个组件渲染为服务端的 HTML 字符串，直接发送到浏览器，最后将这些静态标记「激活」为客户端上完全可交互的应用程序。

这种应用有个名字：**「同构」（isomorphic）或「通用」（universal）**——因为应用的大部分代码在服务端和客户端都能运行。

> **同构的关键含义**：同一份组件代码，服务端把它渲染成 HTML 字符串（给爬虫和白屏期首屏），客户端再复用同一份代码接管成可交互应用（给用户后续交互）。代码只写一份，两处运行。

### SSR 的特点

- 客户端渲染不利于搜索引擎优化（SEO）
- 服务端渲染是可以被爬虫抓取到的，客户端异步渲染很难被爬虫抓取到
- SSR 直接将 HTML 字符串传递给浏览器，大大加快了首屏加载时间
- SSR 占用更多的 CPU 和内存资源
- 一些常用的浏览器 API 可能无法正常使用
- 在 Vue 中只支持 `beforeCreate` 和 `created` 两个生命周期

> 💬 **面试官**：SSR 和 CSR 的渲染流程有何不同？各自适用什么场景？
>
> ✅ 标准答案：CSR 是浏览器加载空壳 HTML，JS 接管后拉数据、渲染 DOM，完整流程都在浏览器端；SSR 是 Node.js 先把组件渲染成 HTML 字符串发给浏览器，浏览器拿到的是有内容的 HTML。SEO 要求高、首屏性能要求高且页面相对稳定的场景适合 SSR；对 SEO 不敏感、交互密度高、首屏以用户操作为主的内部系统适合 CSR。
>
> 🎁 加分答案：能补充 SSR 不是银弹——它牺牲服务端 CPU/内存，且模板渲染器对每请求的资源开销远大于静态文件。真正生产往往是「SSR 首屏 + 客户端路由接力」：只首屏做 SSR，后续切换走前端路由的客户端渲染。

### 运行过程：只有首屏是 SSR

很多面试者把 SSR 理解成「整个应用都是服务端渲染」，这是错的。

**实际上是：只有首屏做 SSR，后续的切换逻辑，执行的全是客户端渲染（前端路由切换）**。

```
首次请求 → 服务器渲染出首屏 HTML → 浏览器展示（首屏秒开，爬虫可抓）
用户点击导航 → 前端路由切换 → 客户端渲染（CSR 接管后续交互）
```

### 整个打包过程：一份代码，打包出两份逻辑

```
┌─────────────────────────────────────────────────────┐
│              Universal Application Code             │
│                （一份组件代码）                         │
└──────────┬──────────────────────────┬───────────────┘
           │                          │
      Webpack 编译                 Webpack 编译
           ▼                          ▼
     client bundle                 server bundle
    （entry-client.js）           （entry-server.js）
           │                          │
           │                      Server Renderer
           │                          │
           ▼                          ▼
      Vue Components             renderToString
           │                     生产 HTML 字符串
           │                          │
           │                          ▼
           │                      Server Bundle
           │                          │
           │                          ▼
           └─────▶  HTML   ←─────────┘
                     │
                     ▼
               Hydrate 激活
                     │
                     ▼

```

一份代码打包出两份逻辑：前端拿到打包出来的 JS，后端通过打包的结果渲染出字符串。前端的 JS + 后端渲染的字符串 = 扔到浏览器上的完整页面。

> 前端拿到的 JS 负责「激活」和后续的客户端交互；后端打包出来的 server bundle 负责把组件渲成字符串。

## 🚀 二、Nuxt.js 由浅入深：不必手写，先搞懂框架替你做了什么

硬核手写 SSR 之前，先看工业界的标准答案——**Nuxt.js**。它把 SSR 的复杂性（webpack 双端配置、路由生成、数据预取）全部封装掉了，真正理解 SSR 的人，能一眼看穿 Nuxt 的每一层抽象背后在干什么。

### Nuxt.js 是什么

Nuxt.js 是一个基于 Vue 的应用框架，自带**服务端渲染（SSR）、静态站点生成（SSG）、约定式路由**三大能力。它解决的痛点是：手写 SSR 需要自己配 webpack（client + server 两套）、自己写 entry、自己处理数据预取和注水，工程化成本极高。

一句话概括：**Nuxt 把「SSR 工程化」变成了「目录约定 + 约定式 API」**。

### 安装与目录约定

新建项目：

```bash
npx create-nuxt-app nuxt-medical-portal
# 选择 Server（SSR）模式
cd nuxt-medical-portal
npm run dev   # 开发，带热更新
```

核心目录约定——这是 Nuxt 的灵魂，只要文件放对位置，框架自动接管：

```
nuxt-medical-portal/
├── pages/           ← 约定式路由：每个 .vue 文件自动成为一个路由
│   ├── index.vue        → /
│   ├── drug/_id.vue     → /drug/:id   （下划线前缀 = 动态参数）
│   └── about.vue        → /about
├── layouts/         ← 布局模板：default.vue 每次页面接管骨架，可自定义
│   └── default.vue
├── components/      ← 公共组件（约定目录，非路由）
├── store/           ← Vuex：index.js 为根模块，每个 .js 自动成为模块
│   └── index.js
├── static/          ← 静态资源（直接映射到根路径）
├── nuxt.config.js   ← 全局配置（head、plugins、css、modules）
└── package.json
```

**pages / layouts / components 三个目录的分工**：

| 目录 | 作用 | 关键机制 |
|------|------|---------|
| `pages/` | 页面组件，**目录结构 = 路由结构** | 框架读取文件名自动生成 vue-router 路由表 |
| `layouts/` | 页面骨架（导航、页脚、布局） | `<nuxt/>` 占位符渲染当前页面 |
| `components/` | 可复用组件，不可直接作为路由 | 按需在页面中 `import`，不生成路由 |

**约定式路由的底层**：Nuxt 在构建时扫描 `pages/` 目录，把文件路径映射成 `vue-router` 的路由配置——`pages/drug/_id.vue` 自动生成 `{ path: '/drug/:id', component: ... }`。这也是 Nuxt「封装了路由生成」的含义：手写 SSR 时你得自己 `new VueRouter({ routes: [...] })`，Nuxt 帮你从文件系统推导出来。

### Nuxt 页面骨架与数据预取：asyncData 与 fetch

页面组件里放好骨架，再用 Nuxt 的两个数据钩子填数据。先在 `layouts/default.vue` 定义页面骨架：

```vue
<!-- layouts/default.vue -->
<template>
  <div>
    <header>
      <nuxt-link to="/">首页</nuxt-link>
      <nuxt-link to="/drug/1">药品详情</nuxt-link>
    </header>
    <!-- nuxt 占位符：渲染当前匹配的页面组件 -->
    <nuxt/>
    <footer>医疗器械信息门户 © 2026</footer>
  </div>
</template>
```

然后写一个展示药品列表的页面，用 **asyncData** 在服务端提前拿到数据：

```vue
<!-- pages/index.vue -->
<script>
export default {
  asyncData({ $axios, error }) {
    // 👈 服务端执行（首屏），也支持客户端导航时执行
    return $axios.get('/api/drugs')
      .then(res => ({ drugList: res.data }))
      .catch(err => error({ statusCode: 500, message: '药品加载失败' }))
  },
  data() {
    return { drugList: [] }
  }
}
</script>

<template>
  <ul>
    <li v-for="drug in drugList" :key="drug.id">
      <nuxt-link :to="`/drug/${drug.id}`">{{ drug.name }}</nuxt-link>
  </ul>
</template>
```

`asyncData` 是 Nuxt 页面组件专属方法，**关键区别在它把返回值直接合并进组件的 data**——服务端执行完毕后，返回的数据会被注入到页面，渲染成 HTML。配合 SEO，写在 `asyncData` 里的数据会实实在在出现在服务端返回的 HTML 字符串里，爬虫能抓到。

再对比另一个钩子 `fetch`（Nuxt 2.12+）：

```vue
<!-- 用 fetch 组件内部填充 store/组件数据，但不会合并进 SSR 的 data -->
<script>
export default {
  async fetch({ store }) {
    // 服务端执行，把数据放进 store，适合「全局/模块化状态」
    await store.dispatch('drug/fetchList')
  },
  computed: {
    drugList() {
      return this.$store.state.drug.list
    }
  }
}
</script>
```

**asyncData 和 fetch 的区别（面试高频）**：

| 维度 | asyncData | fetch |
|------|-----------|-------|
| 使用位置 | 仅页面组件（pages/） | 任何组件（pages + components） |
| 返回数据 | 直接合并进组件 data | 不合并 data，通常写入 store |
| 是否阻塞服务端渲染 | 是，等待数据返回才出 HTML | 是，也阻塞，但不直接注入 data |
| 主要用途 | 页面级数据预取，保证 SEO 内容完整 | 拉取共享状态（store），或组件级数据 |
| 访问组件实例 | 不能（无 `this`，服务端还没有实例） | 可以通过 `this` 访问组件 |
| 客户端触发时机 | 页面刷新、路由守卫触发 | 路由切换、组件初始化 |

> 一句话区分：**页面数据用 asyncData（注入 HTML 供 SEO），共享/全局状态用 fetch（写入 store）**。asyncData 没有 `this`，因为服务端渲染时组件实例还不存在；fetch 有 `this`，能直接 `this.$store`。

### await 后的 SEO：为什么 asyncData 的数据能进 HTML

这是 SSR 的核心收益。手写 SSR 里，**页面级数据要在服务端先拉完、再让 renderToString 渲染**——这样服务端返回的 HTML 里就带着真实内容，爬虫能看到。Nuxt 的 asyncData 正是封装了这件事：构建时它能区分「这次是服务端渲染，要先等 asyncData」，然后注水传回客户端，避免客户端重复请求。

### SSG vs SSR：怎么选

很多团队纠结的问题。**SSG（静态站点生成）**在构建时就把所有页面生成静态 HTML 文件，部署的就是纯静态文件。

| 维度 | SSR | SSG |
|------|-----|-----|
| 生成时机 | 每次请求，服务器实时渲染 | 构建时一次性生成，复用静态文件 |
| 数据新鲜度 | 每次请求都是最新数据 | 只有重新构建才更新 |
| 服务端负载 | 高（每请求渲染，CPU/内存开销大） | 极低（直接返回静态文件） |
| 首屏性能 | 优，但受服务端渲染耗时影响 | 最快，静态文件 CDN 加速 |
| SEO | 完整支持 | 完整支持 |
| 适用场景 | 数据实时变化、依赖登录态 | 内容相对固定：文档站、博客、营销页、药品目录静态页 |

**医疗门户的决策建议**：药品说明书、疾病科普这类**内容固定**的页面用 SSG（构建时静态化 + CDN），性能最好、成本最低；**实时价格、库存、依赖用户数据**的页面用 SSR。一个 Nuxt 项目里可以混用——用 `generate` 生成静态页，用 `mode: 'spa'`/动态模块跑实时 SSR。

> 💬 **面试官**：SSG 和 SSR 的区别？医疗门户你会怎么选？
>
> ✅ 标准答案：SSG 构建时生成静态 HTML，SSR 每个请求实时渲染。SSG 数据不实时但性能最好，SSR 数据实时但服务端压力大。固定内容用 SSG，实时/个性化用 SSR，可以混合使用。
>
> 🎁 加分答案：能说出 Nuxt 支持两者混合，且 SSR 页面本身也能「按路由缓存」（配合 LRU 缓存显著降低实时渲染压力），这是面试官想听到的对「服务端压力和性能」这一核心矛盾的完整认知。

### Nuxt.js 与手写 SSR 的核心差异

现在可以总结 Nuxt 到底替你封装了什么——**这正是「看懂 Nuxt」和「看懂手写 SSR」交汇的地方**：

| 能力 | 手写 SSR | Nuxt.js |
|------|---------|---------|
| Webpack 双端配置 | 手写 webpack.client.js + webpack.server.js + merge + VueSSRClient/ServerPlugin | 内置，零配置 |
| 入口文件 | 手写 entry-client.js + entry-server.js + createApp 工厂 | 框架生成抽象入口 |
| 路由 | 手写 `new VueRouter({ routes })` + 服务端 `router.push(context.url)` + onReady | 扫描 pages/ 自动生成 |
| 数据预取 | 手写 asyncData 约定 + 服务端遍历匹配组件调用 | 内置 asyncData / fetch 钩子 |
| 状态注水 | 手写遍历组件 → 存 state → 序列化 → `window.__INITIAL_STATE__` | 内置，自动注入 `window.__NUXT__` |
| 模板注入 | 手写 index.ssr.html + 注释节点 + clientManifest 注入 | 内置 |
| 部署 | 手写 Express/Koa 路由 + 静态服务 | 内置 server，或 `nuxt generate` |

**核心差异一句话**：Nuxt 封装了 webpack 双端配置、路由生成、数据预取三大件，把「工程问题」变成「约定问题」——你只写页面组件和钩子，其余框架全包。

**服务器搭建 `server.js`**——这是 SSR 最直接的样子：

```javascript
const Koa = require('koa')
const Router = require('@koa/router')
const VueServerRender = require('vue-server-renderer')
const Vue = require('vue')

// 创建 vue 实例
const vm = new Vue({
  data() {
    return {
      message: 'this is the first vue ssr app'
    }
  },
  template: `<div>{{ message }}</div>`
})

// createRenderer，创建一个渲染函数 renderToString，渲染出一个字符串
const render = VueServerRender.createRenderer()

// 产生一个 app 实例
let app = new Koa() 
// 产生一个路由实例
let router = new Router()
router.get('/', async (ctx) => {
  ctx.body = await render.renderToString(vm)
})
// 将路由注册到应用上
app.use(router.routes())
// 监听 3000 端口号
app.listen(3000)
```

关键就两行：`createRenderer()` 创建一个渲染器，`renderToString(vm)` 把 Vue 实例渲染成一个 HTML 字符串。这个字符串就是首屏返回给浏览器的正文。

### 搭配 HTML 模板：暴露 `<!--vue-ssr-outlet-->` 插槽

上面返回的字符串只有组件的 DOM（比如 `<div>this is the first vue ssr app</div>`），没有完整的 `<html>` 骨架。用 `createRenderer({ template })` 传入模板，让字符串注入到模板的插槽里。

新建 `index.html`，注意**固定写法 `<!--vue-ssr-outlet-->`**——渲染结果会被替换到这个注释节点的位置：

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>ssr demo</title>
</head>
<body>
  <!-- 下面代码是固定写法 -->
  <!--vue-ssr-outlet-->
</body>
</html>
```

更新 `server.js`，读取模板并传给 `createRenderer`：

```javascript
const Koa = require('koa')
const Router = require('@koa/router')
const { createRenderer } = require('vue-server-renderer')
const Vue = require('vue')
const fs = require('fs')
const path = require('path')

// 创建 vue 实例
const vm = new Vue({
  data() {
    return {
      message: 'this is the first vue ssr app'
    }
  },
  template: `<div>{{ message }}</div>`
})

// 读取模板
const template = fs.readFileSync(path.resolve(__dirname, 'index.html'), 'utf-8')

// createRenderer，创建一个渲染函数 renderToString，渲染出一个字符串
const render = createRenderer({
  template
})

// 产生一个 app 实例
let app = new Koa() 
// 产生一个路由实例
let router = new Router()
router.get('/', async (ctx) => {
  ctx.body = await render.renderToString(vm)
})
// 将路由注册到应用上
app.use(router.routes())
// 监听 3000 端口号
app.listen(3000)
```

现在返回的是一个完整的 HTML 页面，正文就是组件渲染出来的字符串。

**注意**：这个 `createRenderer` 是**单实例渲染器**，生产一般用 `createBundleRenderer`（接打包后的 server bundle）。两者的区别在「六、缓存策略」和「七、源码解析」里展开。

### 双端入口设计：entry-client.js + entry-server.js

真实 SSR 项目不能像上面那样写死一个 Vue 实例——组件要能拆 `.vue` 文件、要路由、要状态管理。这就引出了 **SSR 双端入口**的架构：同一份应用代码，打包出客户端和服务端两套入口。

**核心约束：导出工厂函数，而不是实例**。因为服务端是「每请求一实例」，实例必须每次请求新建（原因详见「五、三个致命坑」）。

所以 `app.js` 不再导出 Vue 实例，而是导出一个工厂函数：

```javascript
// src/app.js
import Vue from 'vue'
import App from './App.vue'

// 1. Vue 在客户端运行的时候，每个客户端都拥有一个独立的实例
// 2. 每次客户端访问都要产生一个新的实例，所以这里导出一个函数
export default () => {
  const app = new Vue({
    render: h => h(App)
  })
  // 后续会导出路由、vuex 等
  return {
    app
  }
}
```

**客户端入口 `src/entry-client.js`**——直接挂载：

```javascript
import createApp from './app'
const { app } = createApp()

// 客户端直接挂载即可
app.$mount('#app')
```

**服务端入口 `src/entry-server.js`**——返回实例给渲染器：

```javascript
import createApp from './app'

export default () => {
  const { app } = createApp()
  // 这个实例每次都是新的
  return app
}
```

客户端 `$mount('#app')` 挂载到 DOM 上；服务端把实例交给 BundleRenderer 渲成字符串。两端入口共用同一份 `app.js` 工厂。

### 集成 Vuex：状态预取 + 注水 window.__INITIAL_STATE__

SSR 里 Vuex 最大的价值是**数据预取后注水**：服务端先把数据填进 store，渲染成 HTML，再把 store 状态序列化，客户端启动时用 `replaceState` 恢复——这样客户端就不需要再请求一遍。

**安装依赖**：

```bash
cnpm i vuex -S
```

**vuex 配置 `src/create-store.js`**——又是工厂函数，且客户端要通过 `window.__INITIAL_STATE__` 注水恢复状态：

```javascript
import Vue from 'vue'
import Vuex from 'vuex'

Vue.use(Vuex)

export default () =>{
  const store = new Vuex.Store({
    state: {
      name: 'robin'
    },
    mutations: {
      CHANGE_NAME(state, payload) {
        state.name = payload
      }
    },
    actions: {
      changeName({ commit }, payload) {
        return new Promise((resolve, reject) => {
          setTimeout(() => {
            commit('CHANGE_NAME', payload)
            resolve() // 执行完要返回
          }, 1000);
        })
      }
    }
  })
  // 在浏览器运行代码
  if (typeof window !== 'undefined' && window.__INITIAL_STATE__) {
    store.replaceState(window.__INITIAL_STATE__)
  }
  return store
}
```

> `window.__INITIAL_STATE__` 就是注水（hydration of state）：服务端把 store 状态序列化成一个 JS 对象写进 HTML，客户端启动时 `replaceState` 用它替换初始 state，两端状态一致。Nuxt 里的 `window.__NUXT__` 也是同一思路。

**配置组件 `src/components/Foo.vue`**——关键点在 `asyncData`：这是页面组件定义的**数据预取约定函数**，服务端会主动调用它（下面 entry-server 会遍历匹配到的组件逐个调）：

```vue

  <div class="foo">
    foo
    {{ this.$store.state.name }}
  </div>
</template>

<script>
export default {
  // mounted() {
  //   return this.$store.dispatch("changeName", 'hahha');
  // },

    return store.dispatch("changeName", 'test');
  }
}
</script>

<style scoped>

  color: red;
}
</style>
```

> 想想为什么不能写在 `mounted` 里（被注释的那段）：`mounted` 只在客户端执行，服务端渲染时根本不走 `mounted`，数据就不在首屏 HTML 里。所以要用 `asyncData` 这种服务端也执行的约定，先派发 action 填好 store，再渲染。

**服务端入口 `src/entry-server.js`**——真正的数据预取核心：取到匹配的组件，逐个调用 `asyncData(store)`，`Promise.all` 等全部完成，再把 store.state 挂到 `context.state`（框架会自动序列化并注入 `window.__INITIAL_STATE__`）：

```javascript
import createApp from './app'

// context.url 这里包含这当前访问服务端的路径
export default (context) => {
  return new Promise((resolve, reject) => {
    const { app, router, store } = createApp()
    // 默认跳转到路径里，有异步组件
    router.push(context.url)
    router.onReady(() => {
      // 获取路由匹配到的组件
      const matchComponents = router.getMatchedComponents();
      if (!matchComponents.length) {
        return reject({ code: 404 });
      }
      Promise.all(matchComponents.map((component) => {
        if(component.asyncData) {
          return component.asyncData(store)
        }
      })).then(() => {
        context.state = store.state; // 将store挂载在window.__INITIAL_STATE__
        resolve(app)
      }, reject)
    })
    // 这个实例每次都是新的
    // return app
  })
}
```

**这就是 asyncData 数据预取 + 状态注水的完整闭环**：

```
请求进入 → router.push(context.url) → onReady
  → getMatchedComponents() 取匹配的组件
  → 逐个调 asyncData(store)（填充 store）
  → context.state = store.state（待序列化注水）
  → resolve(app) → renderToString 渲染 HTML
  → 客户端启动读 window.__INITIAL_STATE__ → store.replaceState 恢复
```

> 💬 **面试官**：Vuex 的数据是怎么从服务端传到客户端的？

> ✅ 标准答案：服务端在渲染前先通过 `asyncData` 派发 action 填充 store，渲染完成后把 `store.state` 挂到渲染 context 的 `state` 字段上，框架自动序列化注入成 `window.__INITIAL_STATE__`；客户端启动时在 createStore 里读到这个全局变量，用 `store.replaceState` 恢复服务端算好的状态，避免重复请求。
>

## 💧 四、原理深挖：Hydration 激活与状态注水

上面跑通了整个流程，现在回到最核心的一个机制：**Hydration（客户端激活 / 水合）**。它是 SSR「打通两端」的命门，也是 Python 等语言团队的 SSR 最容易搞砸的地方。

### 服务端返回的是「活的 HTML 还是死的字符串」

服务端 `renderToString` 产出的只是一串 HTML 字符串。它展示了内容（SEO 能抓到、首屏能展示），但**不具备交互能力**——你点按钮没有任何反应，因为事件监听还没挂上。

Hydration 就是在浏览器端**把这串静态字符串"注水"成可交互应用**的过程：客户端复用同一份组件代码，重建 Vue 实例，跟页面上现有的 DOM 做匹配，挂上事件、建立响应式。

### data-server-rendered：让客户端"认出"服务端渲染过的 DOM

激活的关键是**让客户端判断当前 DOM 是不是服务端渲染的**。答案是根元素上的一个特殊标记属性：

```
data-server-rendered="true"
```

服务端渲染的输出会在根 DOM 节点上打这个标记。客户端 `$mount` 时看到它，就知道「这段 DOM 是服务端渲染好的」，于是走 **Hydration 分支**——**复用现有 DOM**（只挂事件钩子），而不是重新创建整个 DOM 树。

> 这就是「激活 / 水合」的字面含义：服务端给了干的 HTML，客户端给它注上水和生命，让它活起来。

### DOM 复用的硬性条件：结构必须 100% 匹配

Hydration 复用的是服务端渲染出来的 DOM，所以有个**最硬的红线**：

> **客户端渲染的结构，必须和服务端渲染的结构完全一致。** 客户端只会去找服务端渲染好的节点，在对应位置上「长」出事件和状态，它不会删除或重建不匹配的节点。

如果两端的模板结构不一致，就会触发前面「五」里讲过的 **Hydration 失败**（比如控制台出现 `The client-side rendered virtual DOM tree is not matching server-rendered content` 警告，页面事件会错位、甚至完全失效）。

**结构匹配的注意点**：不仅是标签要一致，**文本、属性、注释、样式，都要尽量一致**。常见的坑包括：模板里插了 `Math.random()`、`Date.now()` 这种两端值不同的表达式，或者不同的 `v-if` 分支在两边走了不同的结果。

> 💬 **面试官**：客户端激活（Hydration）是什么？DOM 复用的条件是什么？
>
> ✅ 标准答案：Hydration 是浏览器端 Vue 复用服务端渲染的静态 HTML，挂上事件和响应式状态，把它变成可交互应用的过程。复用的前提是客户端渲染结构与服务端字符串结构完全一致——客户端在服务端渲染的节点上「长」事件，不会重建不匹配的节点。
>
> 🎁 加分答案：能补一句通过根节点 `data-server-rendered="true"` 标记判断走到 Hydration 分支，且能指出结构不一致会导致激活失败（事件错位、不生效），这就是后面「Hydration 失败排查」要讲的场景。

## ☠️ 五、三个致命坑：状态污染、生命周期、浏览器 API

SSR 和 CSR 的最大差异，是全世界的 JS 都在同一个 Node 进程里跑。下面三个坑，面试几乎必考其一。

### 致命坑一：服务端全局状态污染——为什么必须工厂函数

这是 SSR 最著名的面试题，也是新手最容易踩的雷。

**客户端模型**：每个浏览器 tab 是独立进程，各自有独立的内存，`data` 是隔开的；而且 CSR 每次刷新都是重新加载全新的 JS，不存在「上一个用户的状态残留」。

**服务端模型**：所有用户的请求都打进**同一个 Node 进程**。如果 `data` / store / router 写成模块级单例（`export const store = new Store()`），那么：

```
用户 A 请求 → 创建 store（单例！）→ fill user A 的数据
用户 B 请求 → 复用同一个 store（！！！）→ 读到 A 的数据
  → 跨用户数据串台，医疗数据泄露风险
```

如果你在模块顶层 `export default () => { new Vue({ data: { ... } }) }` 里用**同一个共享的 data 对象**，还会遇到另一个问题：多个请求共享同一份引用，一个请求改了 `data.name`，别的请求全变了。

**所以，SSR 的黄金法则**：

> **每次请求都必须创建全新的 app 实例、全新的 router、全新的 store。** 三个都必须是工厂函数（每次调用返回新实例），而不是模块级单例。

- app 用工厂：`export default () => new Vue({...})`
- router 用工厂：`export default () => new VueRouter({...})`
- store 用工厂：`export default () => new Vuex.Store({...})`

这就是笔记里 `create-router.js`、`create-store.js`、`app.js` 全部 `export default () => {...}` 的原因——**entry-server 每次请求都会重新调用这些工厂**。

> 💬 **面试官**：为什么 SSR 中 data / store / router 必须是工厂函数？
>
> ✅ 标准答案：服务端同一个 Node 进程要服务所有用户。如果状态是模块级单例，不同请求会共享同一份数据，造成跨请求状态污染（用户 A 的数据串到用户 B）。工厂函数让每次请求都创建全新独立的实例，保证请求间的隔离。
>
> 🎁 加分答案：能延伸到「这是 CSR 和 SSR 本质差异的体现」——CSR 每次刷新重新加载、内存天然隔离；SSR 常驻进程共享内存，所以必须每请求新建。甚至可以补充异步组件也要注意时序，避免渲染还没结束就被下一个请求的实例抢走。

### 致命坑二：SSR 中不执行的生命周期

服务端没有真实的 DOM，只把组件渲染成字符串，所以相当一部分生命周期钩子在服务端**根本不会执行**：

服务端渲染只走 `beforeCreate` 和 `created`。以下生命周期在服务端全部不运行：

```
beforeMount ✗
mounted     ✗
beforeUpdate ✗
updated     ✗
beforeDestroy ✗
destroyed   ✗
```

`beforeMount` / `mounted` 这类和 DOM 强相关的钩子，服务端渲染期间不会触发（它们依赖真实 DOM 挂载）。`beforeUpdate` / `updated` / `beforeDestroy` / `destroyed` 同理。**只有组件的「创建」阶段（beforeCreate / created）在两端都会执行**。

所以：**依赖 DOM / 浏览器环境的逻辑不能放 created**，要放 `mounted`（客户端专属）。比如绑定 `window` 事件、操作 DOM、请求依赖浏览器的接口，都应该在 mounted 里做。

> 这也是为什么「五、致命坑一」里 asyncData 必须存在——页面数据预取要放在服务端也执行的钩子（asyncData / beforeCreate / created 阶段），不能只依赖 mounted。

### 致命坑三：浏览器 API 不可用——window / document 怎么处理

Node 进程里**没有 `window`、`document`、`localStorage`**。你在组件 `created` 里写 `if (document.querySelector(...))`，服务端渲染时会直接抛 `ReferenceError: document is not defined`。

**处理方式**：

- **必须只在客户端执行的逻辑**，放进 `mounted`（服务端不跑它）
- **模块顶层或 created 里要用浏览器 API**，加环境判断

```javascript
// ✅ 服务端也安全：用 typeof 判断环境
const isClient = typeof window !== 'undefined'

if (isClient) {
  localStorage.setItem('key', 'value')
}

// ✅ Nuxt / webpack DefinePlugin 注入的编译期判断
if (process.client) {
  // 这段只打包进客户端 bundle，服务端直接剪掉（tree-shaking）
  window.addEventListener('scroll', handler)
}
```

`process.client`（Nuxt 提供）和 `process.browser`（旧版）是**编译期布尔常量**，webpack 会根据目标平台把某一端的代码 tree-shaking 掉——服务端构建时 `process.client` 为 `false`，这段代码直接被删掉，连执行都不会发生。手写 SSR 则用 `typeof window !== 'undefined'` 这种**运行时判断**。

> 💬 **面试官**：SSR 中哪些生命周期不会执行？window/document 怎么处理？
>
> ✅ 标准答案：服务端只执行 beforeCreate 和 created，beforeMount / mounted / beforeUpdate / updated / beforeDestroy / destroyed 都不在服务端运行。浏览器 API 依赖（window / document / localStorage）在服务端不存在，需要放在客户端专属的 mounted 里，或在代码里用 `typeof window !== 'undefined'`（手写）或 `process.client`（Nuxt）判断后才访问。
>
> 🎁 加分答案：能点出 `process.client` 是编译期常量、会被 tree-shaking 删代码，而手写 SSR 用运行时 typeof 判断——两种机制本质不同（编译期 vs 运行时），这是区分普通回答和深度回答的关键。

## 💨 六、缓存策略：页面级 LRU + 组件级 serverCacheKey

SSR 最大的成本是**每个请求都要在服务器上跑一遍 Vue 渲染**——CPU 和内存开销远大于返回静态文件。缓存是压掉这部分成本的核心手段。

### 页面级 LRU 缓存

页面级缓存是最简单也最有效的：**对不随用户变化的页面，缓存 renderToString 的结果**。

`vue-server-renderer` 官方推荐用 `LRU-cache`（最近最少使用）维护一个缓存 Map，命中就直接返回缓存的 HTML 字符串，不重新渲染：

```javascript
const LRU = require('lru-cache')

// 缓存 1000 个页面，最大 500MB
const cache = new LRU({
  max: 1000,
  maxSize: 500 * 1024 * 1024,
  sizeCalculation: item => item.length
})

const renderer = createBundleRenderer(serverBundle, {
  cache,  // ⚠️ 注意：这里传给 bundle renderer 的是下面那种「组件级」用法
  // ...其他选项
})

server.get('/drug/:id', async (req, res) => {
  const key = `drug:${req.url}`

  // 命中缓存：直接返回体积较小的 HTML 字符串
  if (cache.has(key)) {
    return res.end(cache.get(key))
  }

  const html = await renderToString({ url: req.url })
  cache.set(key, html)  // 未命中：渲染后写入缓存
  res.end(html)
})
```

**适用条件（缓存到什么页面能安全复用）**：

- 页面内容**不因用户不同而变化**（不依赖登录态 / 个性数据）
- 数据**在一定时间内相对稳定**（药品说明、疾病科普类）
- 对**实时性不敏感**（可以接受轻微的内容延迟）

> 医疗门户正好匹配：药品说明书、疾病科普、产品目录这些不登录、不个性化、更新慢的页面，是最理想的 LRU 缓存对象。涉及登录态/价格的页面就不能缓存，否则用户看到别人的数据。

### 组件级缓存：serverCacheKey

更细粒度的是组件级缓存——**只有 `serverCacheKey` 方法返回的 key 一致时，才复用组件的渲染结果**。适合「同一组件被多个页面复用、但参数固定」的场景：

```javascript
// Vue 官方 SSR 指南的经典示例
export default {
  name: 'drug-info',           // 必须指定 name，缓存按它分桶
  props: ['drugId'],
  serverCacheKey: props => props.drugId,  // 同一 drugId 复用渲染结果
  template: `<div>药品 {{ drugId }} 信息</div>`
}
```

- 只有配置了 `serverCacheKey` 的组件才会被缓存
- `serverCacheKey` 返回相同的值 → 复用组件渲染结果
- **组件必须指定 `name`**，缓存按 `name` 索引
- 组件里**不能有副作用**（不能在渲染时调用随机数、依赖外部状态），否则缓存的是一次性的结果

> **组件级缓存比页面级更精细**：它缓存的是「组件的渲染片段」，主页面依旧每请求渲染，但复用的片段能省下组件树的递归开销。判断标准是看组件的 `serverCacheKey` 返回值是否稳定。

> 💬 **面试官**：SSR 服务端缓存有哪些？怎么选？
>
> ✅ 标准答案：分页面级和组件级。页面级用 LRU-cache 对整个渲染结果做缓存，适合内容固定、不依赖用户的数据，命中直接返回 HTML 字符串。组件级通过组件的 `serverCacheKey` 按片段缓存，适合被多处复用且参数确定的组件。都要注意：不能缓存依赖登录态的数据，不能缓存组件副作用。
>
> 🎁 加分答案：能说明「缓存是把服务端渲染从每次请求压缩成偶尔渲染」的工程本质——真正高并发 SSR 都是缓存先行，LRU 目的是控制内存上限，`maxSize`/`sizeCalculation` 是按字符串体积估算内存占用自动淘汰。

## 📖 七、源码解析：renderToString 到底做了什么

这一节进源码，看「服务端把组件渲染成字符串」这个动作在 `vue-server-renderer` 里到底怎么发生的。源码地址：GitHub 搜索 `lotosv2010/vue-ssr` 对应的依赖版本，以及 `vuejs/vue` 仓库的 `src/platforms/web/runtime/patch.js`。

### createRenderer：创建渲染器

`createRenderer` 返回一个渲染器对象，核心是 `renderToString` 方法。加缓存时，它内部维护一个模块级别的缓存实例：

```javascript
// vue-server-renderer/src/create-renderer.js（核心逻辑）
export function createRenderer (options = {}) {
  // 防止多次 createRenderer 时缓存被共享重置
  baseModules.forEach(m => { m.cache = Object.create(null) })

  return createRendererAPI({
    modules: baseModules,
    directives,
    isUnaryTag,
    cache: options.cache,   // 传入的 LRU 缓存（组件级 serverCacheKey 用）
    template: options.template
  })
}

// createRendererAPI 内部生成一个 renderToString
function createRendererAPI (options) {
  return {
    renderToString,
    renderToStream
  }
}
```

关键点：渲染器接收 `options.cache`（LRU），内部基于模块和指令组装出一个 `renderToString`。它本身不做模板解析，而是依赖 Vue 编译好的 **render 函数**——组件实例的 `$options.render`。

### renderToString：组件树渲染为 HTML 字符串

`renderToString` 的核心，是**拿到根实例，遍历它的虚拟 DOM 树，把 vnode 逐个转换成字符串**。

```javascript
// vue-server-renderer/src/renderer.js（逻辑核心，略去简化）
export function renderToString (vm, cb) {
  // vm 是 Vue 根实例
  renderNode(vm._vnode, opts)   // 从根虚拟节点开始
    .then(str => cb(null, str))
    .catch(cb)

  function renderNode (node, options) {
    const write = (text) => { ... }  // 拼接 HTML 片段
    // 递归走虚拟 DOM：元素、文本、组件、插槽…
    return Promise.all(node.children.map(child => renderNode(child, options)))
      .then(() => { ... 把当前节点序列化成 <tag attr>${children}</tag> ... })
  }
}
```

**源码层面的要点**：

- 渲染是**递归地进行**：从根 `vm._vnode` 出发，深度遍历整棵虚拟 DOM 树
- 每个 vnode 被序列化成 HTML 字符串：`'<div class="foo">'+ children + '</div>'`
- 组件类的 vnode 会被还原成其内部渲染的 HTML
- 整个流程是 **Promise 链**——所以能处理异步组件、等待 `beforeCreate`/`created` 里的副作用

**和 CSR 的差别**：客户端是 `patch`（虚拟 DOM → 真实 DOM diff + 更新），服务端是 `render`（虚拟 DOM → HTML 字符串，一次性输出）。两端共享同一个虚拟 DOM，只是输出目标不同——这正是「一份代码两处运行」的技术根基。

### Hydration 入口：patch.js 里的 hydrate 函数

客户端激活走的是 `patch` 里的 hydrate 分支。`$mount('#app')` 时，如果根节点有 `data-server-rendered` 标记，就进入 hydrate：

```javascript
// src/platforms/web/runtime/patch.js（hydrate 入口）
export const patch = createPatchFunction({ nodeOps, modules })

// 判断是否为服务端渲染过的节点
function isHydrating (vnode) {
  return vnode.elm && vnode.elm.getAttribute('data-server-rendered') === 'true'
}

// hydrate 的核心：复用现有 DOM，只在对应位置插入新 vnode
function hydrate (elm, vnode, insertedVnodeCb) {
  // 复用 elm（服务端渲染的节点），而不是 createElm 新建！
  vnode.elm = elm
  ...
  // 递归对子节点做同样的复用
  for (let i = 0; i < vnode.children.length; i++) {
    hydrate(child, vnode.children[i], insertedVnodeCb)
  }
}
```

**Hydration 源码的关键**：`hydrate` 直接把 `vnode.elm` 设为**已经存在的服务端 DOM 节点**（`elm` 参数），而不是走普通渲染的 `createElm` 新建节点。这就是「复用现有 DOM」的源码级证据——它只是把新 vnode 挂到旧节点上、挂事件，不重建。

> `data-server-rendered="true"` 就是这个分支的开关。只在根节点标记一次，但 hydrate 是整个虚拟 DOM 树的递归复用。

### 工厂函数 + 注水的源码闭环

把「工厂函数」和「注水」串起来看源码层：

- **entry-server.js** 导出一个函数，**每次渲染都调用它**，拿到全新的 app/router/store —— 对应「致命坑一」的隔离要求
- 服务端把 `context.state` 里的 store state 序列化，注入 `window.__INITIAL_STATE__`
- **entry-client.js** 启动时读到全局变量，`store.replaceState` 恢复 —— 对应「集成 Vuex」那节的注水

这四段源码（createRenderer / renderToString / hydrate / 工厂+注水）合起来，就是 SSR 从服务器到浏览器的完整实现真相。

> 💬 **面试官**：说一下 renderToString 的源码实现？
>
> ✅ 标准答案：createRenderer 返回带 renderToString 的渲染器；renderToString 拿到根实例，从根 vnode 深度遍历虚拟 DOM 树，把每个节点递归序列化成 HTML 字符串，整个过程用 Promise 串起来以支持异步组件。客户端这边，$mount 时若检测到 `data-server-rendered="true"` 就走 patch.js 的 hydrate 分支，复用现存 DOM 挂上事件，而不是重建。
>
> 🎁 加分答案：能点出「两端共享虚拟 DOM、只是输出目标不同（服务端转字符串、客户端做 diff 更新）」这就是同构的根基，并顺手把「工厂函数隔离请求」「window.__INITIAL_STATE__ 注水」串进同一个答案里，说明对整条链路有完整认知。

## 🏭 八、生产级最佳实践：缓存、部署、Hydration 失败排查

### 服务端部署拓扑：PM2 + Nginx + 健康检查

SSR 是真服务进程，生产要面对进程管理和负载均衡。

**PM2 管理 Node 进程**——崩溃自动重启、多进程并行、日志归集：

```bash
npm i -g pm2

# 启动（-i 指定进程数，cluster 模式利用多核）
pm2 start ecosystem.config.js

# 或最简单的方式
pm2 start server.js -i max --name "vue-ssr"
pm2 save              # 保存进程列表
pm2 startup           # 开机自启（生成开机启动命令）
```

**健康检查**：给服务端加一个 `/health` 路由，返回 200，让 Nginx / 负载均衡 / 监控系统可以探活：

```javascript
router.get('/health', async (ctx) => {
  ctx.status = 200
  ctx.body = 'ok'
})
```

**Nginx 反向代理**——把 `:80` 端口的请求代理到 Node 的 `:3000`，同时托管静态资源：

```nginx
server {
  listen 80;
  server_name  medical.example.com;

  # 静态资源（dist 下）走 Nginx，减轻 Node 压力
  location /dist/ {
    root /srv/vue-ssr;
    expires 30d;               # 带版本号的静态资源可长期缓存
    add_header Cache-Control "public, immutable";
  }

  # 其余请求交给 Node 渲染
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    # 健康检查探针
    location /health {
      proxy_pass http://127.0.0.1:3000/health;
    }
  }
}
```

> 关键点：**静态资源（`/dist/`）让 Nginx 直接服务**，只有 HTML 渲染请求才打给 Node——这大幅降低了 SSR 进程的压力，是「SSR 服务端压力大」这个核心矛盾的重要缓解手段。CDN 也能挂在 Nginx 前面进一步加速静态资源。

**SEO meta 优化**：页面的 `<title>` 和 meta 也要在服务端设置，否则爬虫拿不到。利用渲染模板的插值能力，在 entry-server 里根据路由设置 meta：

```javascript
// entry-server.js 渲染前
const meta = {
  title: '阿司匹林肠溶片 - 药品说明书',
  description: '阿司匹林的作用机理、适应症、用法用量、注意事项等完整药品说明'
}
context.meta = meta   // 模板里通过 {{ meta.title }} 读取
```

```html
<!-- index.ssr.html：用插值填充 SEO 元数据 -->
<head>
  <title>{{ meta.title }}</title>
  <meta name="description" content="{{ meta.description }}">
  <meta property="og:title" content="{{ meta.title }}">
</head>
```

> 这是医疗门户 SEO 的落地点：每个药品详情页动态产出独一无二的 title / description，爬虫爬到的每一页都是完整语义化的内容。

### Hydration 失败排查：结构不一致的常见原因

Hydration 失败的典型表现在控制台：`The client-side rendered virtual DOM tree is not matching server-rendered content ...`。**它不是崩溃，但会导致事件不生效、状态不同步、页面闪烁**。

常见原因与排查思路：

| 原因 | 表现 | 排查/解决 |
|------|------|----------|
| 两端数据不一致 | 同一表达式两端算出不同值 | 检查 `Date.now()` / `Math.random()` 等非确定性表达式，改用只在客户端阶段使用 |
| `v-if` 分支两端不同 | 服务端渲染 A 分支，客户端走 B 分支 | 条件依赖的不确定性状态，在服务端默认值固定 |
| 文本/空节点差异 | 注释、空文本节点两端数量不同 | 避免在组件根加无意义的空白 / 注释 |
| 浏览器插件改 DOM | 第三方脚本插入节点导致错位 | 排查浏览器扩展影响，生产环境少见 |
| 用了会改变结构的第三方库 | 渲染被库改写 | 对比两端渲染结构，统一处理 |

**通用排查流程**：

```
1. 先看服务端返回的 HTML（curl 页面 / 浏览器查看源代码）
2. 再看客户端渲染的结构（DevTools Elements）
3. 两端结构逐层对比，找出第一个不一致的节点
4. 定位该节点依赖的数据/表达式，两端是否一致
```

> 💬 **面试官**：Hydration 失败会发生什么？常见原因和排查思路？
>
> ✅ 标准答案：Hydration 失败是客户端渲染结构与服务端不一致，导致事件绑定错位、组件状态不同步、页面抖动，控制台有明确的 not matching 警告。常见原因是两端数据不一致（Date.now/Math.random）、v-if 分支两端结果不同、文本/注释节点差异、第三方脚本改 DOM。排查按「对比服务端 HTML 和客户端渲染结构 → 定位第一个不一致节点 → 看它依赖的数据」的思路。
>
> 🎁 加分答案：能指出 Hydration 失败的「根因」——服务端先算了一个结果，客户端又算了一个不同的结果，两套虚拟 DOM 对不上。所以解法本质是「保证两端的非确定性逻辑一致」，而不是只在控制台层面修。

```javascript
import Vuex from 'vuex'

Vue.use(Vuex)

// 模拟药品数据库
const DRUGS = {
  aspirin: { id: 'aspirin', name: '阿司匹林肠溶片', spec: '0.1g*100片', desc: '用于抗血小板聚集、预防血栓形成，需遵医嘱使用。' },
  ibuprofen: { id: 'ibuprofen', name: '布洛芬缓释胶囊', spec: '0.3g*20粒', desc: '用于缓解轻至中度疼痛，如头痛、关节痛、牙痛。' },
  metformin: { id: 'metformin', name: '盐酸二甲双胍片', spec: '0.5g*60片', desc: '用于治疗 2 型糖尿病，餐中服可减少胃肠反应。' }
}

// 工厂函数：每次请求都是新 store
export default () => {
  const store = new Vuex.Store({
    state: {
      drugs: {},
      currentDrug: null,
      loading: false
    },
    mutations: {
      SET_DRUG(state, drug) { state.currentDrug = drug },
      SET_LOADING(state, loading) { state.loading = loading }
    },
    actions: {
      // asyncData 里会调用：同步模拟拉取数据
      fetchDrug({ commit }, id) {
        commit('SET_LOADING', true)
        const drug = DRUGS[id] || null
        commit('SET_DRUG', drug)
        commit('SET_LOADING', false)
        return drug
      }
    }
  })

  // 注水：客户端启动时用服务端序列化的状态恢复，避免重复请求
  if (typeof window !== 'undefined' && window.__INITIAL_STATE__) {
    store.replaceState(window.__INITIAL_STATE__)
  }

  return store
}
```

> 真实项目里 `fetchDrug` 会是异步 API 请求，这里用同步模拟只是为了让示例 `asyncData` 能直接 `await`。重点是「注水」这行——`window.__INITIAL_STATE__` 让客户端无缝接管服务端算好的状态。

### 入口文件

**src/entry-server.js**——工厂 + 路由 + 数据预取 + 注水 context：

```javascript
import createApp from './app'

// 服务端入口：接收 context（含 url），返回 Promise(app)
export default (context) => {
  return new Promise((resolve, reject) => {
    const { app, router, store } = createApp()
    router.push(context.url)

    router.onReady(() => {
      // 取到匹配的组件，逐个执行 asyncData 预取数据
      const matched = router.getMatchedComponents()
      if (!matched.length) {
        return reject({ code: 404 })
      }
      Promise.all(matched.map(comp => {
        if (comp.asyncData) {
          return comp.asyncData(store, router.currentRoute)
        }
      })).then(() => {
        // 把 store 状态挂到 context，框架会序列化注水
        context.state = store.state
        resolve(app)
      }, reject)
    }, reject)
  })
}
```

### Express 服务端

**server.js**——Express + createBundleRenderer + 按路由生成 SEO meta：

```javascript
const express = require('express')
const path = require('path')
const fs = require('fs')
const { createBundleRenderer } = require('vue-server-renderer')

// 加载双端构建产物
const template = fs.readFileSync(path.resolve(__dirname, './public/index.ssr.html'), 'utf-8')
const serverBundle = require('./dist/vue-ssr-server-bundle.json')
const clientManifest = require('./dist/vue-ssr-client-manifest.json')

// 创建 BundleRenderer，clientManifest 自动注入客户端资源
const renderer = createBundleRenderer(serverBundle, {
  template,
  clientManifest
})

// 简单的页面 meta 数据源（真实项目从 DB 或 CMS 拉取）
const META = {
  aspirin:   { title: '阿司匹林肠溶片 - 药品说明书', description: '阿司匹林适应症、用法用量、注意事项完整说明，请遵医嘱使用。' },
  ibuprofen: { title: '布洛芬缓释胶囊 - 药品说明书', description: '布洛芬适应症、用法用量、禁忌事项完整说明，请遵医嘱使用。' },
  metformin: { title: '盐酸二甲双胍片 - 药品说明书', description: '二甲双胍的适应症、用法用量、不良反应完整说明，请遵医嘱使用。' }
}

const app = express()

// 静态资源：dist 目录（client bundle）
app.use('/dist', express.static(path.resolve(__dirname, 'dist')))

// 健康检查：供 Nginx / 负载均衡探活
app.get('/health', (req, res) => res.status(200).end('ok'))

// SSR 渲染入口：所有非静态请求交给渲染器，按 URL 生成 SEO meta
app.get('/(.*)', (req, res) => {
  // 从 URL 解析出药品 id，生成差异化 SEO meta
  const idMatch = req.url.match(/^\/drug\/(.*)$/)
  const meta = META[(idMatch && idMatch[1]) || ''] || {
    title: '药品信息门户',
    description: '药品说明书、用药指导信息聚合门户，仅供学习演示。'
  }

  // 渲染 context：url 给路由，meta 填充模板插值
  const context = { url: req.url, ...meta }

  renderer.renderToString(context, (err, html) => {
    if (err) {
      if (err.url) {
        res.status(404).end('404 | Page Not Found')
      } else {
        res.status(500).end('500 | Internal Server Error')
        console.error(err)
      }
      return
    }
    res.end(html)
  })
})

const PORT = 3000
app.listen(PORT, () => {
  console.log(`药品门户 SSR 已启动：http://localhost:${PORT}`)
})
```

> 这个 server 是你面试时能完整讲出来的「生产级手写 SSR」：`createBundleRenderer` 加载双端产物 → 健康检查 → 路由分发 → 按 URL 生成 SEO meta → renderToString 渲染。每一层都在讲「服务端到底做了什么」。

### 核心知识点速查表

| 知识点 | 一句话核心 | 面试考察频率 |
|--------|-----------|------------|
| SSR vs CSR | CSR 浏览器端渲染，SSR 服务端渲成 HTML 字符串，只首屏 SSR | ⭐⭐⭐⭐⭐ |
| 双端入口 | entry-client 挂载复用，entry-server 渲染字符串，共用 app 工厂 | ⭐⭐⭐⭐ |
| renderToString | 深度遍历虚拟 DOM 树，递归序列化成 HTML 字符串，Promise 串起 | ⭐⭐⭐⭐ |
| Hydration | 复用服务端 DOM 挂事件，`data-server-rendered` 触发，结构必须一致 | ⭐⭐⭐⭐⭐ |
| asyncData 注水 | 服务端预取填 store → context.state 序列化 → window.__INITIAL_STATE__ 客户端恢复 | ⭐⭐⭐⭐⭐ |
| 工厂函数 | 服务端常驻进程共享内存，必须每请求新建实例防跨请求污染 | ⭐⭐⭐⭐⭐ |
| 生命周期差异 | 服务端只走 beforeCreate / created，其余 6 个均不在服务端执行 | ⭐⭐⭐⭐ |
| 浏览器 API | window/document/localStorage 服务端不存在，typeof 或 process.client 判断 | ⭐⭐⭐⭐ |
| 服务端缓存 | 页面级 LRU + 组件级 serverCacheKey，缓存稳定片段/页面 | ⭐⭐⭐ |
| Nuxt.js | 封装 webpack 双端配置、路由生成、数据预取；asyncData vs fetch | ⭐⭐⭐⭐ |
| SSG vs SSR | SSG 构建时静态化，SSR 每请求实时渲染，固定内容用 SSG | ⭐⭐⭐ |

### SSR 完整链路图

```
浏览器请求 URL
      │
   Express/Koa 入口
      │  context.url
      ▼
createBundleRenderer
      │  读取 server-bundle + index.ssr.html + client-manifest
      ▼
 entry-server.js（工厂）
      │  每次请求新建 app/router/store（防污染）
      ▼
 router.push(context.url) → onReady
      │
      ▼
 getMatchedComponents()
      │  逐个 asyncData(store) 预取数据
      ▼
 context.state = store.state（待注水）
      │
      ▼
 renderToString：虚拟 DOM → HTML 字符串
      │  template 插值填充 SEO meta（title/description）
      ▼
 返回完整 HTML
   ├─ 爬虫：抓取到渲染好的内容 ✅
   └─ 浏览器：
        client-manifest 注入 <script>（client bundle）
        └─ entry-client.js
             ├─ window.__INITIAL_STATE__ → store.replaceState 注水
             └─ $mount → 检测 data-server-rendered → hydrate 复用 DOM
                ├─ 结构一致 → 挂事件，可交互
                └─ 结构不一致 → Hydration 失败，事件错位
```
