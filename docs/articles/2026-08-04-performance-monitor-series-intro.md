## 🔥 为什么「我也懂性能」还不够

前端性能是一个很容易陷入「碎片化优化陷阱」的领域。

你知道图片要懒加载，知道 JS 要做 Code Split，知道用 CDN，知道加 `Cache-Control`。但当线上真的出了问题——用户反馈「页面卡」「打开慢」——你打开 Lighthouse 看到红色，却不知道从哪里下手。更难的是，你搞不清楚「优化完了」的标准是什么。

这就是碎片化知识的本质问题：**知道很多点，但点和点之间没有连线；做了很多优化，但不知道影响最大的到底是哪一个。**

真实代价是可以量化的：

- **转化率**：电商场景下，页面首屏每慢 1 秒，转化率平均下降 7%；药品详情页这类决策链路长的页面，影响更显著
- **留存率**：搜索结果页 INP（交互响应延迟）超过 200ms，用户放弃率明显升高
- **SEO 权重**：Google 自 2021 年起将 Core Web Vitals 纳入搜索排名因素，LCP > 4s 的页面在移动搜索中会被降权

不做系统性能工作的团队，通常不是没有意识，而是没有方法论。不知道监控什么、不知道怎么定位、不知道优先优化哪一层。

这个系列解决的，正是「方法论」这件事：**先看得见问题，再系统解决问题**。

## 🧱 四层性能模型：看清性能问题的坐标系

性能优化的难点不在「怎么优化」，在「先优化什么」。做错顺序，投入大、收益小；找对层次，一个决策解决大半问题。

理解这四个层次，是所有优化决策的前提。

### 架构层

你选择什么渲染范式，决定了页面从服务器到用户手里的基础路径，也决定了其他层的优化空间上限。

SSR 在服务端生成首屏 HTML，TTFB 更快，但 hydration 有额外成本；CSR 把渲染全放客户端，灵活但首屏白屏问题难解；RSC（React Server Components）只把服务端组件的 JSON 传给客户端，做到零 bundle 体积；PPR（Partial Prerendering）把静态外壳和动态孔洞分离，让 CDN 缓存和动态内容共存。

**这一层的决策影响最大、最难逆转。** 骨架屏再精致，也盖不住 SSR 渲染链路选错带来的 8 秒白屏。

### 加载层

资源（HTML / JS / CSS / 图片 / 字体）以什么速度、什么顺序到达浏览器，是这一层要解决的问题。

HTTP/2 多路复用让并发请求不再阻塞；HTTP/3 的 QUIC 协议在弱网下表现更稳定；103 Early Hints 让预加载提前一个 RTT；`Cache-Control` 分层策略让静态资源命中率接近 100%；Speculation Rules API 让下一页提前在后台预渲染，用户点击时几乎即时出现。

构建产物的体积和 Code Split 策略也在这一层——产物小了，传输快了，解析也快了。

### 渲染层

浏览器拿到资源后，主线程和 GPU 流水线如何协作把像素画到屏幕上——这是渲染层的问题。

Layout Thrashing（强制同步布局）会让主线程在一帧内反复计算布局，直接导致掉帧；`transform` 和 `opacity` 触发合成层，绕开主线程，动画才能在 GPU 上跑到 60fps；React 的 Fiber 调度在并发模式下把渲染拆成可中断的小任务，让高优先级更新（用户输入）能插队执行，INP 因此改善。

这一层的问题表现是「页面卡顿」「动画掉帧」「点击没反应」，本质是主线程被堵死，无暇响应用户交互。

### 感知层

数据可能已经很好，但用户仍然觉得慢——这是感知性能和客观性能之间心理学层面的落差。

骨架屏让等待变得有期待；Optimistic UI 让操作感觉即时，哪怕服务端还没响应；View Transitions API 让页面切换不再突兀，而是带着动画连续过渡。这一层不改变实际加载速度，但能把「慢」从用户的感知里减掉一部分。

感知层是「客观数据之外的最后兜底」，但它无法替代前三层。**优化要从上往下打，从影响面最大的架构层开始。**

> 💬 **面试官**：如果让你主导一次性能优化专项，你会从哪里入手？
>
> ✅ 标准答案：先看数据——拿真实用户的 Web Vitals 找到最差的指标，再按四层模型归因：是架构问题、加载问题、渲染问题还是感知问题。优先解决影响面最大的层。
>
> 🎁 加分答案：「不做监控就做优化是盲人摸象。」先建度量体系，再建监控告警，再动手优化，最后用数据验证效果，形成闭环——优化完还要能证明「它确实变好了」。
