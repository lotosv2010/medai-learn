# Pinia 原理与手写实现：Vuex 为什么退场，Pinia 才是 Vue 3 的正确答案（面试收藏级）

> 面试官问：「项目里用 Pinia 还是 Vuex？」大多数人的答案是「Pinia 呀，官方推荐的」——再追一句「为什么官方推荐它，Pinia 到底解决了 Vuex 的什么问题」，答案就开始含糊了。「更简单」「没有 Mutation」这些都是**现象**，不是**原因**。

> 真正的原因是：Vuex 的设计是为 Options API 时代服务的，`this.$store.state.xxx` 这种访问方式天然拿不到精确的 TypeScript 类型；Mutation 存在的意义是给 Vuex 的时间旅行调试做「同步快照」保证，但这个约束在 Composition API 时代变成了纯粹的样板代码负担。Pinia 不是「更好用的 Vuex」，而是**用 Composable 的思路重新设计了一遍状态管理**，Mutation 消失、模块 namespaced 消失，都是这次重新设计的自然结果，不是删减功能。

> 这篇文章是「Vue 3 全家桶深度拆解」系列第 8 篇。前 7 篇拆过响应式、渲染、组件、Composition API、内置组件、编译优化，这篇要讲清楚状态管理这层——**Pinia 的 Store 本质上是什么，为什么它能做到"没有 Mutation 也能被 Devtools 时间旅行调试"，以及为什么类型推断可以做到滴水不漏**。

## 🎯 这篇文章解决什么问题

"Pinia 用起来很简单"和"Pinia 面试能讲清楚"是两件事——`defineStore` 三行代码能跑起来,但面试官问"Store 是全局单例吗""为什么没有 Mutation""插件系统怎么给 Store 加持久化能力"，很多人只能说个大概。

这篇文章要打通的是 Pinia 从"能用"到"能讲透"的这条链路：Store 本质上是一个特殊的 Composable，`reactive` 包状态、`computed` 包 getters，`defineStore` 只是把这套组合逻辑包了一层单例缓存；插件系统能给 Store "打补丁"的原理，和 Vue 插件系统一脉相承；类型推断全自动，是因为 `defineStore` 是一个纯粹依赖 TypeScript 结构化类型推导的泛型函数，不需要任何手写声明。读完你会同时拿到两样东西：**懂原理**（Pinia 为什么这样设计，和 Vuex 的每一处差异背后都有明确的取舍）和**会讲**（面试官从"为什么没有 Mutation"问到"Store 间调用为什么不需要 rootState"，你能用同一套"Composable 本质"的框架把所有追问串起来）。

## 🧩 一、基本使用

先看 Pinia 怎么用，三个核心概念、两种写法、Store 间怎么互相调用——原理留到下一节。

### 三个核心概念：state / getters / actions（没有 Mutation）

Pinia 把状态管理拆成三个概念，比 Vuex 的四个（state / getters / mutations / actions）少了一个：

```typescript
import { defineStore } from 'pinia'

export const useDrugStore = defineStore('drug', {
  // state：数据源，必须是一个函数，返回初始状态（避免多个组件实例共享同一份引用）
  state: () => ({
    stock: 100,
    drugName: '阿莫西林胶囊'
  }),
  // getters：派生状态，等价于组件里的 computed
  getters: {
    lowStock: (state) => state.stock < 10
  },
  // actions：修改状态的方法，同步/异步都写在这里，不再区分 mutation
  actions: {
    async restock(amount: number) {
      const res = await fetch(`/api/drug/restock?amount=${amount}`)
      this.stock += await res.json()
    }
  }
})
```

`state` 里的 `stock`、`drugName` 直接读写就行，`this.stock += xxx` 这种写法在 Vuex 里是被严格禁止的（必须走 `commit` 一个 mutation），Pinia 里 action 内部可以直接改。

### `defineStore` 两种写法：Options Store vs Setup Store

Options Store 是上面这种，传一个选项对象；Setup Store 直接写一个函数，函数体就是普通的 Composition API 代码：

```typescript
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

// Setup Store：函数体直接用 ref/reactive/computed，return 的内容就是 store 的公开接口
export const useDrugStore = defineStore('drug', () => {
  const stock = ref(100)
  const drugName = ref('阿莫西林胶囊')
  const lowStock = computed(() => stock.value < 10)

  async function restock(amount: number) {
    const res = await fetch(`/api/drug/restock?amount=${amount}`)
    stock.value += await res.json()
  }

  return { stock, drugName, lowStock, restock }
})
```

两种写法效果完全等价，`useDrugStore()` 拿到的 store 长得一模一样——这不是巧合，「二、原理」会讲清楚为什么 Options Store 最终也是"翻译"成 Setup Store 的形式跑起来的。

### Store 的使用：`useXxxStore()` 在组件 `setup` 中调用

```vue
<script setup>
import { useDrugStore } from '@/stores/drug'

const drugStore = useDrugStore()
</script>

<template>
  <p>{{ drugStore.drugName }}：库存 {{ drugStore.stock }}</p>
  <p v-if="drugStore.lowStock">库存告急，请及时补货</p>
  <button @click="drugStore.restock(50)">补货 50 件</button>
</template>
```

`drugStore.stock` 直接在模板里用，是响应式的——改了 `stock` 页面立刻更新，不需要像 Vuex 那样写 `mapState`/`mapActions` 或者 `this.$store.state.drug.stock` 这种深层访问路径。

### Store 间互相调用：直接 import 另一个 store 使用

```typescript
// stores/prescription.ts
import { defineStore } from 'pinia'
import { useDrugStore } from './drug'

export const usePrescriptionStore = defineStore('prescription', {
  actions: {
    async confirmPrescription(drugId: string, amount: number) {
      const drugStore = useDrugStore() // 直接调用另一个 store 的 useXxxStore
      if (drugStore.stock < amount) {
        throw new Error('库存不足，无法确认处方')
      }
      drugStore.stock -= amount
    }
  }
})
```

`usePrescriptionStore` 的 action 里直接 `import` 并调用 `useDrugStore()`，拿到的是同一个全局单例——不需要 Vuex 里那种 `this.$store.state.drug.stock`、也不需要 `rootGetters`，「二、原理」会讲清楚这背后的单例机制。

## 🧩 二、原理

Pinia 的所有设计都可以归结到一句话：**Store 本质是一个特殊的 Composable，`defineStore` 只是给这个 Composable 包了一层"按 id 缓存单例"的逻辑**。这一节按"Vuex 的问题 → Pinia 怎么解决 → 具体机制"的顺序展开。

### 1. Vuex 在 Vue 3 时代的三大问题

Vuex 4（配套 Vue 3 的版本）能用，但用起来处处是补丁，核心问题集中在三点：

**TypeScript 支持差**：`this.$store.state.drug.stock` 这种访问路径，TypeScript 完全没法推导出 `stock` 的类型——`$store` 本身是一个巨大的、扁平化的 `Store<RootState>` 类型，模块化之后 `state.drug` 这层嵌套需要手写模块类型声明再一层层 `as` 断言，写起来比不写类型还累。

**样板代码多**：改一个 `stock` 字段，Vuex 要求走三层：`dispatch('restock')` → action 内部 `commit('SET_STOCK', newValue)` → mutation 里真正赋值。三个函数只为了做一件事，Mutation 存在的唯一理由是保证状态修改"可追踪、同步"，但这个理由在下一小节会被证明不成立了。

**模块 namespaced 设计繁琐**：Vuex 模块默认全局注册，命名冲突要手动开 `namespaced: true`，之后所有 `dispatch`/`commit`/`mapActions` 调用都要带上模块路径字符串（`'drug/restock'`），路径字符串没有类型检查，写错了运行时才报错。

> 💬 **面试官**：Vuex 在 Vue 3 项目里主要有哪些痛点？
>
> ✅ 标准答案：TypeScript 类型推导差（`$store.state` 访问路径无法被类型系统跟踪）、Mutation 造成样板代码冗余（改一个字段要走 dispatch→commit 两层）、模块 namespaced 后字符串路径没有类型检查。
>
> 🎁 加分答案：能指出这三个问题的根源是同一个——Vuex 的设计基于「所有状态挂在一个巨大的 `$store` 对象上，靠字符串路径寻址」，这套机制在 Options API、JavaScript 为主的时代是合理的，但 Composition API + TypeScript 深度绑定之后，字符串寻址天然和静态类型系统不兼容。

### 2. Pinia 的核心设计：Store 本质是一个特殊的 Composable

Pinia 解决上面三个问题的思路不是「优化 Vuex」，而是「换一套完全不同的模型」——**一个 Store 就是一个 `reactive` 对象，state 用 `reactive()` 包装，getters 用 `computed()` 实现**，跟你平时写一个 `useXxx()` Composable 没有本质区别：

```typescript
// 简化心智模型：Options Store 内部大致长这样
function createOptionsStore(id, options) {
  const state = reactive(options.state())
  const getters = {}
  for (const key in options.getters) {
    getters[key] = computed(() => options.getters[key].call(store, state))
  }
  const store = reactive({ ...toRefs(state), ...getters, ...options.actions })
  return store
}
```

这就是为什么 Pinia 不需要 Mutation——**响应式对象的属性本身就是可追踪的**，Vue 的 `reactive()` 早就解决了"谁改了状态、什么时候改的"这个问题（依赖收集 + 触发更新），Mutation 在 Vuex 里额外做的事情——把每次状态变更都过一遍统一入口——Pinia 靠 `$subscribe` 订阅响应式对象的变化就能做到，不需要强制所有修改都走一个函数。

> **对比 Vue 2 / Vuex**：Vuex 的 Mutation 存在的历史原因是 Vue 2 的响应式系统基于 `Object.defineProperty`，只能拦截**已声明**的属性读写，且早期设计要求所有状态变更"同步、可回溯"，方便做 Devtools 时间旅行调试——Mutation 就是这套设计里"唯一合法修改入口"的产物。Vue 3 的 Proxy 响应式系统本身就能拦截任意属性的读写（不需要提前声明），时间旅行调试可以直接靠订阅 state 变化的快照来实现，不再需要一个专门的"修改函数"作为中转层。「为什么这样设计」：**Mutation 是给旧响应式系统的能力缺口打的补丁，Proxy 补上了这个缺口，补丁自然可以拿掉**。

### 3. `defineStore` 实现：单例缓存在 `pinia._s` Map

`defineStore` 返回的不是 store，是一个函数（`useStore`）——第一次调用时创建 store 并存进 `pinia._s`，后续调用直接从 Map 里取，这是"全局单例"的全部秘密：

```typescript
// packages/pinia/src/store.ts（笔记 35 原文）
export function defineStore(id, setup, setupOptions) {
  const isSetupStore = typeof setup === "function"
  const options = isSetupStore ? setupOptions : setup

  function useStore(pinia, hot) {
    const hasContext = hasInjectionContext()
    pinia = (activePinia && activePinia._testing ? null : pinia)
      || (hasContext ? inject(piniaSymbol, null) : null)
    if (pinia) setActivePinia(pinia)
    if (!activePinia) {
      throw new Error(`[🍍]: "getActivePinia()" was called but there was no active Pinia.`)
    }
    pinia = activePinia

    // 关键：按 id 查 _s，命中就直接返回缓存的 store，不再重新创建
    if (!pinia._s.has(id)) {
      if (isSetupStore) {
        createSetupStore(id, setup, options, pinia)
      } else {
        createOptionsStore(id, options, pinia)
      }
    }
    const store = pinia._s.get(id)
    return store
  }
  useStore.$id = id
  return useStore
}
```

这也解释了为什么「一、基本使用」里 `usePrescriptionStore` 和 `useDrugStore` 分别在不同文件、不同组件里调用，拿到的却是同一个对象——**`pinia._s` 是挂在 `createPinia()` 创建出来的 pinia 实例上的一个 Map，只要是同一个 pinia 实例（一个应用通常只有一个），同一个 id 永远命中同一份缓存**。

> 💬 **面试官**：Pinia 的 Store 是全局单例吗？怎么保证的？
>
> ✅ 标准答案：是。`defineStore` 返回的 `useStore` 函数内部维护了一个基于 `pinia._s`（Map，key 是 store 的 id）的缓存——第一次调用 `useStore()` 时创建 store 并存入 `_s`，后续所有调用（不管在哪个组件、哪个文件）只要 id 相同，直接返回缓存里的同一个引用。
>
> 🎁 加分答案：能提到"单例"是相对于**同一个 pinia 实例**而言的——测试环境用 `createTestingPinia` 创建的是独立的 pinia 实例，天然不会和生产环境的 store 互相污染，这也是 Pinia 测试隔离做得比 Vuex 简单的原因之一。

### 4. Setup Store 写法：与普通 Composable 完全同构

Setup Store 的 `setup` 函数会被丢进 `createSetupStore` 里直接执行，执行方式和你调用任何一个 `useXxx()` Composable 没有区别——`ref`/`reactive`/`computed` 正常用，`return` 出去的对象就是 store 的公开接口：

```typescript
// packages/pinia/src/store.ts（笔记 35 原文，createSetupStore 核心片段）
const setupStore = runWithContext(() =>
  pinia._e.run(() =>            // 父作用域：整个 pinia 实例的 effectScope
    (scope = effectScope()).run(  // 子作用域：这个 store 专属，$dispose 时单独停掉
      () => setup({ action })
    )
  )
) as Record<any, unknown>
```

`setup` 函数体执行时唯一"特殊"的地方是被包在两层 `effectScope` 里——外层 `pinia._e` 是整个应用共享的作用域，内层是这个 store 独有的作用域，`store.$dispose()` 只停掉内层，不影响其他 store。除此之外，函数体内部写的代码和你平时写一个 `useCounter()` Composable 一模一样——这正是为什么「一、基本使用」里 Setup Store 和普通 Composable 长得像双胞胎，因为它们本来就是同一套机制。

> **对比 Vue 2 / Vuex**：Vuex 的模块（module）本质是一个纯配置对象（`{ state, getters, mutations, actions }`），内部没有任何"函数式组合"的空间——想在一个模块里复用另一个 Composable 的逻辑几乎不可能，只能靠继承配置对象或者写 mixin。Pinia 的 Setup Store 因为本质就是 Composable，可以在 store 内部直接调用别的 `useXxx()`，把状态管理和逻辑复用统一到同一套心智模型里。「为什么这样设计」：**既然 Vue 3 已经有了 Composition API 这套逻辑复用基础设施，状态管理没必要另起一套体系，直接借用同一套原语（ref/reactive/computed/effectScope）成本最低、心智负担最小**。

### 5. Actions 天然支持异步：不需要区分 mutation（同步）和 action（异步）

Vuex 强制要求 mutation 必须是同步函数——这不是随意的限制，是为了保证"每次状态变更都能被 Devtools 精确记录成一帧快照"，如果 mutation 允许异步，Devtools 记录时间旅行的那一刻，可能有多个异步 mutation 同时在飞，快照就不再是"某一时刻状态的确定值"。

Pinia 的 action 里可以直接 `await`，改状态也直接改，不需要区分：

```typescript
actions: {
  // 异步逻辑和状态修改写在同一个函数里，不用拆成 dispatch + commit 两层
  async restock(amount: number) {
    this.loading = true
    const res = await fetch(`/api/drug/restock?amount=${amount}`)
    this.stock += await res.json()
    this.loading = false
  }
}
```

Pinia 能这么做的原因是它没有把"精确的同步快照"当作时间旅行调试的**唯一**实现方式——`$subscribe`/`$onAction` 订阅的是响应式对象变化的时机，而不是要求变化本身必须同步发生，「二、原理」第 8 小节会具体讲这套订阅机制怎么支撑 Devtools 集成。

> **对比 Vue 2 / Vuex**：Vuex 的 `mutation` 必须同步、`action` 可以异步但只能通过 `commit` 间接改状态，这个"同步快照"约束是 Vuex 3/4 时间旅行调试实现方式决定的强制拆分。Pinia 放弃了"必须同步"这个前提，转而用响应式系统本身的变化订阅（`$subscribe`）去捕获状态变更时刻，「为什么这样设计」：**既然 Proxy 响应式系统能精确知道"哪个属性、什么时候被改了"，就不需要开发者手动区分"同步/异步"来配合调试工具的实现细节，让调试工具自己适配响应式系统，而不是让开发者的代码结构去适配调试工具**。

### 6. Store 间互相调用：无需 rootState/rootGetters

「一、基本使用」里 `usePrescriptionStore` 直接 `import { useDrugStore }` 调用，能这么做的底层原因回到第 3 小节讲过的单例机制——**所有 store 共享同一个 `activePinia`，`useDrugStore()` 在任何地方调用，命中的都是 `pinia._s` 里同一份缓存**，不存在"当前在哪个模块里、要不要加模块路径前缀"的问题：

```typescript
// usePrescriptionStore 内部调用 useDrugStore，两者是平级关系，不是父子/嵌套关系
const drugStore = useDrugStore()
```

Vuex 的模块是**树状嵌套**的——一个模块想访问另一个模块的状态，要么把模块设为非 namespaced（污染全局命名空间），要么在 action 里手动传 `{ dispatch, commit, rootState, rootGetters }` 这几个上下文参数，用字符串路径 `dispatch('drug/restock', payload, { root: true })` 跨模块调用。Pinia 里没有"模块嵌套"这个概念，每个 `defineStore` 定义出来的 store 都是**平级的独立单例**，store 间调用就是普通的函数调用 + import，没有路径字符串，类型也是完整的。

> 💬 **面试官**：Pinia 里 Store 之间怎么互相访问？和 Vuex 的模块访问方式有什么区别？
>
> ✅ 标准答案：直接 `import` 另一个 store 的 `useXxxStore` 函数并调用即可，因为所有 store 基于同一个 `pinia._s` 单例缓存，在哪里调用都拿到同一个实例。不需要 Vuex 里的 `rootState`/`rootGetters`/`{ root: true }` 这类跨模块访问机制。
>
> 🎁 加分答案：能指出这背后的模型差异——Vuex 的模块是**树状嵌套**（子模块访问父模块要"提升到 root"），Pinia 的 store 是**平级独立**（没有父子关系，import 谁就是谁），这个模型简化直接消除了"跨模块访问"这个概念本身要解决的问题。

### 7. 插件系统：`pinia.use(plugin)` 给每个 Store 扩展能力

Pinia 的插件系统只有一个约定——插件是一个函数，接收 `{ store, app, pinia, options }` 上下文，返回值会被合并到 `store` 上：

```typescript
// pinia.use 注册插件，plugin 函数会在每个 store 创建时执行一次
pinia.use(({ store }) => {
  store.createdAt = new Date() // 给每个 store 都挂一个创建时间
})
```

**持久化插件**是插件系统最常见的应用——原理是订阅 `store.$subscribe`，state 变化时把当前状态写进 `localStorage`，store 创建时先从 `localStorage` 读一遍覆盖初始状态：

```typescript
// 简化版持久化插件：state 变化时写 storage，初始化时读 storage 覆盖 state
function persistPlugin({ store }) {
  const stored = localStorage.getItem(store.$id)
  if (stored) {
    store.$patch(JSON.parse(stored)) // 用存储的值覆盖初始 state
  }
  store.$subscribe((mutation, state) => {
    localStorage.setItem(store.$id, JSON.stringify(state))
  })
}
```

这套机制在真实项目里对应的是 `pinia-plugin-persistedstate`，「四、生产级最佳实践」会具体讲怎么配置。插件之所以能这么"侵入式"地扩展 store，是因为 `store` 本身是一个 `reactive` 对象——插件返回的属性通过 `Object.assign` 合并进去，和 store 原有的 state/getters/actions 没有任何特殊区别，都是同一个响应式对象上的普通属性。

> **对比 Vue 2 / Vuex**：Vuex 没有官方插件系统的等价物——想给所有模块统一加一个能力（比如自动持久化），只能靠手写一个通用的 mixin 或者在每个模块里重复配置，缺乏统一的注入点。Pinia 的插件是 Vue 插件思想（`app.use(plugin)`）在状态管理层的延续——「为什么这样设计」：**统一的插件注入点让"日志""持久化""Devtools 集成"这类横切关注点可以和业务 state/actions 完全解耦，一行 `pinia.use()` 就能给所有 store 统一打上某种能力，不需要逐个模块手动接入**。

### 8. `$onAction` 与 Devtools 集成：订阅机制实现时间旅行调试

Pinia 没有 Mutation，Devtools 怎么知道"状态在什么时候被改了、被哪个 action 改的"？答案是两套订阅机制配合：**`$subscribe` 订阅 state 本身的变化**（前面持久化插件用的就是这个），**`$onAction` 订阅 action 的调用时机**（action 开始执行、执行成功、执行失败三个阶段都能拿到回调）：

```typescript
// $onAction 能拿到 action 名称、参数、以及执行结果的三个回调时机
someStore.$onAction(({ name, args, after, onError }) => {
  console.log(`action ${name} 开始执行，参数：`, args)
  after((result) => {
    console.log(`action ${name} 执行成功，返回：`, result)
  })
  onError((error) => {
    console.log(`action ${name} 执行失败：`, error)
  })
})
```

Devtools 插件本质上就是官方写的一个"更精细的 `$subscribe` + `$onAction` 组合"——每次 action 执行前记录一份 state 快照，执行后记录另一份，时间旅行调试就是把这些快照按时间顺序存起来，需要"回到某一步"时直接把 state 整体替换成对应快照的值。

> ⚠️ **笔记未落地，补充讲解**：笔记这份手写实现里 `partialStore` 上的 `$onAction: null` 只是占位（`store.ts:361`），从未真正实现——`action()` 包装函数里也只留了 `// TODO 异步逻辑` 的注释（`store.ts:343`），没有调用任何 `$onAction` 回调。上面这段 `$onAction` 的使用方式和实现原理，是本文基于 Pinia 官方文档 + 真实源码机制补充的，帮你理解"没有 Mutation 时，时间旅行调试到底是怎么做到的"。

> 💬 **面试官**：Pinia 没有 Mutation，Devtools 是怎么做时间旅行调试的？
>
> ✅ 标准答案：靠两套订阅机制——`$subscribe` 订阅 state 整体的变化（拿到变化后的完整 state），`$onAction` 订阅每次 action 调用的开始/成功/失败时机。Devtools 插件在每次 action 执行前后各记录一份 state 快照，时间旅行本质是把 state 替换成历史快照的值。
>
> 🎁 加分答案：能提到这套机制不要求"同步"——因为快照记录的是 action 执行**前**和**后**这两个确定的时间点，中间的异步过程不影响快照的准确性，这也是 Pinia 能放弃 Vuex 的"mutation 必须同步"约束的关键（呼应第 5 小节）。

### 9. Store 的完整类型推断原理

`useXxxStore()` 调用处不用写任何类型声明，`store.stock`、`store.lowStock`、`store.restock()` 全部自动带类型提示——这不是编辑器插件做的魔法，是 `defineStore` 本身的类型签名设计出来的结果：

```typescript
// packages/pinia/src/store.ts 类型重载（简化示意）
export function defineStore<
  Id extends string,
  S extends StateTree = {},
  G extends {} = {},
  A = {}
>(
  id: Id,
  options: Omit<DefineStoreOptions<Id, S, G, A>, "id">
): StoreDefinition<Id, S, G, A>
```

`S`/`G`/`A` 三个泛型参数分别对应 `state`/`getters`/`actions` 三个字段的**字面量类型**——TypeScript 在你写 `defineStore('drug', { state: () => ({ stock: 100 }), ... })` 的时候，会结构化地推导出 `S` 就是 `{ stock: number }`，不需要手写任何标注。`StoreDefinition<Id, S, G, A>` 内部把这三者拼装成一个联合接口，`useXxxStore()` 的返回类型就是 `S & G & A`（外加 `$patch`/`$reset` 等内置方法），这也是为什么 `store.stock` 能推出 `number`、`store.restock` 能推出正确的函数签名——**全部来自你传给 `defineStore` 的那个选项对象本身的字面量类型，编译器只是在做结构化的类型拼接，不需要任何额外的类型标注**。

> **对比 Vue 2 / Vuex**：Vuex 4 想获得同等的类型体验，需要开发者手动维护一份 `State` 接口、手动给 `useStore<State>()` 传泛型参数、模块化之后还要手写模块类型声明再拼装成 `RootState`——每一步都要手写，而且模块路径字符串（`'drug/restock'`）本身没有类型系统能覆盖到。Pinia 的类型完全来自选项对象的字面量推导，零手写。「为什么这样设计」：**Pinia 设计之初就是 TypeScript-first——选项对象怎么写，类型就怎么推，开发者的心智负担从"额外维护一份类型声明"降到零，这也是官方在推荐理由里最常强调的一点**。

### 1. `defineStore`：返回 `useStore`，单例缓存于 `pinia._s`

```typescript
// packages/pinia/src/store.ts（笔记 35 原文）
export function defineStore(
  id: any,
  setup?: any,
  setupOptions?: any
) {
  let options: 
    | DefineStoreOptions<string, StateTree, {}, {}>
    | DefineSetupStoreOptions<string, StateTree, {}, {}>
  const isSetupStore = typeof setup === "function"
  options = isSetupStore ? setupOptions : setup

  function useStore(pinia?: Pinia | null, hot?: StoreGeneric): StoreGeneric {
    // 判断当前代码执行环境是否支持通过 provide 和 inject 进行依赖注入
    const hasContext = hasInjectionContext()
    // 获取当前活跃的 pinia
    pinia = (activePinia && activePinia._testing ? null : pinia) || (hasContext ? inject(piniaSymbol, null) : null)
    // 如果 pinia 存在，则设置当前活跃的 pinia
    if (pinia) setActivePinia(pinia) 

    // 如果当前激活的 pinia 不存在，则抛出错误
    if (!activePinia) {
      throw new Error(
        `[🍍]: "getActivePinia()" was called but there was no active Pinia. Are you trying to use a store before calling "app.use(pinia)"?\n` +
          `See https://pinia.vuejs.org/core-concepts/outside-component-usage.html for help.\n` +
          `This will fail in production.`
      )
    }

    // 让 pinia 设置当前 active pinia
    pinia = activePinia

    // 判断是否已经创建过 store，没有则创建并缓存到 _s 中
    if (!pinia._s.has(id)) {
      if (isSetupStore) {
        createSetupStore(id, setup, options, pinia)
      } else {
        createOptionsStore(id, options as any, pinia)
      }
    }

    // 获取 store
    const store: StoreGeneric = pinia._s.get(id)

    // 如果是 hot 模式，则删除并重新创建
    if (hot) {
      const hotId = '__hot' + id
      const newStore = isSetupStore
        ? createSetupStore(hotId, setup, options, pinia)
        : createOptionsStore(hotId, assign({}, options) as any, pinia, true);
      (hot as any)._hotUpdate(newStore)

      delete pinia.state.value[hotId]
      pinia._s.delete(hotId)
    }

    // 如果是 客户端 环境，从缓存中获取 store 实例
    if (IS_CLIENT) {
      const currentInstance = getCurrentInstance()
      if (currentInstance && currentInstance.proxy && !hot) {
        const vm: any = currentInstance.proxy
        const cache = '_pStores' in vm ? vm._pStores : (vm._pStores = {})
        cache[id] = store
      }
    }
    return store
  }
  useStore.$id = id
  return useStore
}
```

关键行是 `if (!pinia._s.has(id))` 这个判断——命中缓存直接 `pinia._s.get(id)` 返回，不命中才走 `createSetupStore`/`createOptionsStore` 真正创建，这就是第二节讲的单例机制在代码层面的落点。

### 2. state 响应式化：`reactive()` 包装 state

state 的响应式化发生在 `createSetupStore` 里，`toRefs` 把 `pinia.state.value[$id]` 这个已经是 `reactive` 的对象拆成一组 ref，方便后续和 actions/getters 合并成扁平的 store 对象：

```typescript
// packages/pinia/src/store.ts（笔记 35 原文，createOptionsStore 的 setup 函数）
function setup() {
  // 如果不是 hot 模式，且没有初始 state，则赋值 state
  if (!initialState && !hot) {
    pinia.state.value[id] = state ? state() : {}
  }
  // 创建 store 实例
  const localState = hot
    ? toRefs(ref(state ? state() : {}).value)
    : toRefs(pinia.state.value[id])
  // 合并 actions 和 getter，最后赋值到 store 实例
  return assign(
    localState, // states
    actions,    // actions
    /* ...getters，见下一小节 */
  )
}
```

`pinia.state.value` 本身在 `createPinia()` 里就已经是一个 `reactive` 的 `ref`（`scope.run(() => ref<Record<string, StateTree>>({}))`），`pinia.state.value[id] = state()` 赋值的那一刻，这份初始状态就被 Vue 的响应式系统接管——不需要在 `defineStore` 内部单独调用一次 `reactive()`，因为它已经嵌套在一个 `reactive` 的根对象里了。

### 3. getters computed 化：遍历 getters 生成 computed

```typescript
// packages/pinia/src/store.ts（笔记 35 原文，createOptionsStore 内）
Object.keys(getters ?? {}).reduce((computedGetters, name) => {
  if (name in localState) {
    console.warn(
      `[🍍]: A getter cannot have the same name as another state property. Rename one of them. Found with "${name}" in store "${id}".`
    )
  }
  computedGetters[name] = markRaw(
    computed(() => {
      setActivePinia(pinia)
      // 获取 store
      const store = pinia._s.get(id)
      // 这里的作用是给 getter 添加 store 的 this 指向
      return getters[name].call(store, store)
    })
  )
  return computedGetters
}, {} as Record<string, ComputedRef>)
```

每个 getter 函数都被包进一个 `computed()`，`getters[name].call(store, store)` 这一行是关键——`this` 和第一个参数都指向 `store` 本身，这就是为什么 `getters: { lowStock: (state) => state.stock < 10 }` 里的 `state` 参数实际上收到的是完整的 store（不仅有 state，还有其他 getters/actions），`markRaw` 则是为了防止这个 `ComputedRef` 对象本身被再套一层响应式代理（多余的性能开销）。

### 4. Setup Store 处理：`createSetupStore` 直接执行 setup 函数收集返回值

```typescript
// packages/pinia/src/store.ts（笔记 35 原文，createSetupStore 核心片段）
const runWithContext = pinia?._a?.runWithContext || fallbackRunWithContext
// 这里是为了划分父子作用域
const setupStore = runWithContext(() => 
  pinia._e.run(() => // 父作用域
    (scope = effectScope()).run( // 子作用域
      () => setup({ action })
    )
  )
) as Record<any, unknown>

// 覆盖 store 的属性
for (const key in setupStore) {
  const prop = setupStore[key]
  if ((isRef(prop) && !isComputed(prop)) || isReactive(prop)) {
    //! 只有setupStore 是 reactive 或 ref 的属性，才会被覆盖
    if (!isOptionsStore) {
      pinia.state.value[$id][key] = prop
    }
  } else if (typeof prop === 'function') {
    const actionValue = action(prop as _Method, key)
    setupStore[key] = actionValue
  }
}

// 合并 setupStore 结果
assign(store, setupStore)
assign(toRaw(store), setupStore)
```

这段 `for...in` 循环是 Setup Store 和 Options Store 走到最后"合流"的关键——`setup()` 函数体 `return` 出来的对象，遍历一遍区分三类：是 `ref`/`reactive`（非 `computed`）的，说明是"状态"，写进 `pinia.state.value[$id]`；是函数的，说明是"action"，包一层 `action()`（第 6 小节讲）再挂到 store 上；其余（比如 `computed` 结果）原样合并。这就是为什么 Setup Store 里 `ref` 声明的变量最终也能被 Devtools 追踪、能被 `$patch` 整体覆盖——它们和 Options Store 的 state 走的是同一条"写进 `pinia.state.value`"的路径。

### 5. `$onAction`：订阅 action 调用时机（笔记留空，本节补全）

笔记 35 的 `partialStore` 上 `$onAction: null` 只是占位（`store.ts:361`），`action()` 包装函数内部也只有一句 `// TODO 异步逻辑` 的注释（`store.ts:343`），从未真正触发过任何订阅回调。真实 Pinia 源码里，`action()` 包装函数会在函数执行的**前、成功后、失败后**三个时机分别触发订阅：

```typescript
// packages/pinia/src/store.ts（真实源码简化摘录，补全笔记 $onAction 的空实现）
const action = <Fn extends _Method>(fn: Fn, name: string = ''): Fn => {
  const wrappedAction = function (this: any) {
    setActivePinia(pinia)
    const args = Array.from(arguments)

    const afterCallbackSet = new Set<(resolvedReturn: any) => any>()
    const onErrorCallbackSet = new Set<(error: unknown) => unknown>()
    function after(callback) { afterCallbackSet.add(callback) }
    function onError(callback) { onErrorCallbackSet.add(callback) }

    // 执行前：把 after/onError 两个"登记回调"的函数传给所有订阅者
    triggerSubscriptions(actionSubscriptions, {
      args, name: wrappedAction[ACTION_NAME], store, after, onError,
    })

    let ret: unknown
    try {
      ret = fn.apply(this && this.$id === $id ? this : store, args)
    } catch (error) {
      triggerSubscriptions(onErrorCallbackSet, error) // 同步报错：立即触发 onError
      throw error
    }

    if (ret instanceof Promise) {
      return ret
        .then((value) => {
          triggerSubscriptions(afterCallbackSet, value) // 异步成功：触发 after
          return value
        })
        .catch((error) => {
          triggerSubscriptions(onErrorCallbackSet, error) // 异步失败：触发 onError
          return Promise.reject(error)
        })
    }

    triggerSubscriptions(afterCallbackSet, ret) // 同步成功：触发 after
    return ret
  } as MarkedAction<Fn>

  wrappedAction[ACTION_MARKER] = true
  wrappedAction[ACTION_NAME] = name
  return wrappedAction
}
```

`$onAction` 本身只是 `addSubscription.bind(null, actionSubscriptions)`——注册回调进 `actionSubscriptions` 这个 `Set`，`action()` 包装函数每次被调用时，就是靠 `triggerSubscriptions(actionSubscriptions, ...)` 把这次调用的上下文（`name`/`args`/`after`/`onError`）广播给所有订阅者。**这就是第二节第 8 小节讲的"Devtools 靠订阅记录快照"在代码层面的真正实现**——Devtools 插件订阅的就是这个 `actionSubscriptions`，每次 action 被调用都能拿到完整的上下文，配合 `$subscribe` 记录的 state 快照，拼出完整的时间旅行记录。

### 6. 插件机制：`pinia.use` + `_p` 插件数组遍历执行

```typescript
// packages/pinia/src/store.ts（笔记 35 原文，createSetupStore 尾部）
pinia._p.forEach((extender) => {
  if (IS_CLIENT) {
    const extensions: any = scope.run(() => {
      extender({
        store,
        app: pinia._a,
        pinia,
        options: optionsForPlugin
      })
    })
    Object.keys(extensions || {}).forEach(key => (store as any)._customProperties.add(key))
    assign(store, extensions)
  } else {
    assign(
      store,
      scope.run(() => {
        extender({ store, app: pinia._a, pinia, options: optionsForPlugin })
      })
    )
  }
})
```

`pinia._p` 是 `pinia.use()` 注册的插件函数数组（`createPinia.ts` 里维护），每个 store 创建完主体（state/getters/actions）之后，会把这个 store 依次"喂"给每个插件函数，插件返回的对象直接 `assign` 合并进 store——这正是「二、原理」第 7 小节持久化插件示例里，`store.createdAt = new Date()` 这种扩展能落地的机制来源。`scope.run()` 包一层是为了让插件内部如果用了 `watch`/`computed` 之类的响应式 API，其副作用也能被这个 store 的 `effectScope` 统一管理，`store.$dispose()` 时一并清理。

## 🧩 四、生产级最佳实践

### Options Store vs Setup Store 的选型

不是"哪个更好"，是"哪个场景更合适"：

| 维度 | Options Store | Setup Store |
| --- | --- | --- |
| 结构清晰度 | 高——state/getters/actions 分区明确，一眼看出全貌 | 中——逻辑混在一个函数体里，大文件容易乱 |
| 逻辑复用能力 | 弱——无法在 store 内直接调用其他 Composable | 强——可以像组件里一样调用任意 `useXxx()` |
| 适合场景 | 简单 CRUD、字段固定的业务 store（如用户信息、字典配置） | 逻辑复杂、需要复用已有 Composable 的场景（如复杂表单联动） |

医疗场景举例：`useUserStore` 只是存登录用户信息 + 简单的登出方法，用 Options Store 结构一目了然；`usePrescriptionFormStore` 需要复用 `useDrugSearch()`、`useDosageCalculator()` 这些已有 Composable 拼装成开处方的完整状态流转，Setup Store 更合适。

### `pinia-plugin-persistedstate` 持久化插件的使用与自定义存储策略

生产项目基本不会自己手写持久化插件（除非有特殊加密/过期需求），直接用社区维护的 `pinia-plugin-persistedstate`：

```typescript
// main.ts
import { createPinia } from 'pinia'
import piniaPluginPersistedstate from 'pinia-plugin-persistedstate'

const pinia = createPinia()
pinia.use(piniaPluginPersistedstate)
```

```typescript
// stores/drug.ts：单个 store 里声明要不要持久化、持久化哪些字段
export const useDrugStore = defineStore('drug', {
  state: () => ({ stock: 100, drugName: '阿莫西林胶囊', searchHistory: [] }),
  persist: {
    storage: localStorage, // 也可以传 sessionStorage，或自定义符合 Storage 接口的对象
    pick: ['searchHistory'] // 只持久化搜索历史，库存这类实时数据不应该被持久化覆盖
  }
})
```

`pick` 这个配置项直接对应「三、源码解析」第 5 小节讲的机制——插件内部还是靠 `store.$subscribe` 拿到变化后的完整 state，再按 `pick` 配置筛选出要写进 storage 的字段，原理和笔记里手写的持久化插件完全一致，只是做了更完善的配置项封装。

### 大型项目模块化拆分规范：按业务域拆 Store

Pinia 没有 Vuex 的"模块"概念，拆分规范完全靠团队约定——按业务域，一个 `defineStore` 对应一个内聚的业务领域：

```typescript
// stores/user.ts   —— 登录用户信息、权限
// stores/drug.ts   —— 药品库存、说明书
// stores/prescription.ts —— 处方单、开方流程
```

拆分粒度的判断标准：**这份状态是否有独立的生命周期和变更逻辑**——`useUserStore` 和 `useDrugStore` 的变更时机、变更原因完全不相关，拆开；如果两块状态总是一起变、一起用，合并成一个 store 反而更合理，不要为了"拆分"本身而过度拆分。

### Store 的测试：`createTestingPinia` 隔离测试 action 调用

测试组件或者测试 store 本身，需要一个独立的、不污染全局 `activePinia` 的 pinia 实例，`@pinia/testing` 包提供了 `createTestingPinia`：

`createTestingPinia` 靠的正是第二节第 3 小节讲的单例机制——它创建了一份**独立**的 pinia 实例并设为 `activePinia`（`_testing: true`），测试用例里 `useDrugStore()` 命中的是这份独立实例里的 `_s` 缓存，不会影响其他测试用例或者真实应用的状态。

### 与 Vuex 的对比表

| 维度 | Vuex 4 | Pinia |
| --- | --- | --- |
| 修改状态的方式 | `commit` mutation（同步）+ `dispatch` action（异步） | action 内直接改，同步/异步不区分 |
| 模块化 | 树状嵌套，需要 `namespaced: true` + 字符串路径跨模块调用 | 每个 store 平级独立，直接 import 调用 |
| TypeScript 支持 | 弱，需要大量手写类型声明和断言 | 强，`defineStore` 全自动类型推断 |
| 逻辑复用 | 困难，模块内无法直接用 Composable | 天然支持，Setup Store 本质就是 Composable |
| 插件/持久化 | 无官方插件系统，靠手写 mixin | `pinia.use()` 统一注入点 + 官方持久化插件 |
| Devtools 时间旅行 | 靠 Mutation 强制同步保证快照准确 | 靠 `$subscribe`/`$onAction` 订阅机制 |

```javascript
import { context } from "esbuild";
import minimist from "minimist";
import path from "path";
import fs from "fs";
import { fileURLToPath } from "url";
import { createRequire } from "module";

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);
const require = createRequire(import.meta.url);

// 解析命令行参数，返回构建配置
function parseBuildOptions(args) {
  const packageName = args.pkg || "reactivity"; // 默认包名
  const formatArg = args.f || "global"; // 默认格式
  const packageJsonPath = path.resolve(
    __dirname,
    `../packages/${packageName}/package.json`
  );
  const packageJson = require(packageJsonPath);
  // 规范化输出格式
  let outputFormat = "iife";
  if (formatArg.startsWith("esm")) outputFormat = "esm";
  else if (formatArg.startsWith("cjs")) outputFormat = "cjs";
  else if (formatArg.startsWith("umd")) outputFormat = "umd";
  // 输出文件路径
  const outputFile = path.resolve(
    __dirname,
    `../packages/${packageName}/dist/${packageName}.${formatArg}.js`
  );
  return {
    packageName,
    formatArg,
    packageJson,
    outputFormat,
    outputFile,
  };
}

// 执行单个包的构建并监听
async function buildAndWatch({
  packageName,
  packageJson,
  outputFormat,
  outputFile,
}) {
  const ctx = await context({
    entryPoints: [
      path.resolve(__dirname, `../packages/${packageName}/src/index.ts`),
    ],
    outfile: outputFile,
    bundle: true,
    sourcemap: true,
    minify: false,
    format: outputFormat,
    globalName: packageJson?.buildOptions?.name,
    platform: outputFormat === "cjs" ? "node" : "browser",
  });
  await ctx.watch();
  console.log(`watching ${packageName} (${outputFormat})...`);
}

// 获取所有 packages 目录下的包名
function getAllPackageNames() {
  return fs.readdirSync(path.resolve(__dirname, "../packages"));
}

// 主入口，解析参数并批量构建
async function main() {
  const args = minimist(process.argv.slice(2));
  const allPackages = getAllPackageNames();
  // 支持命令行指定包名（如 node dev.js reactivity runtime-core）
  const targetPackages = args._.length ? args._ : allPackages;
  // 支持多格式构建
  const formats =
    !args.f || args.f === "all" ? ["global", "esm", "cjs"] : [args.f || "esm"];
  // 遍历所有包和格式，执行构建
  for (const pkgName of targetPackages) {
    for (const format of formats) {
      const buildOptions = parseBuildOptions({ pkg: pkgName, f: format });
      await buildAndWatch(buildOptions);
    }
  }
}

main();
```

```typescript
import { Pinia, PiniaPlugin, piniaSymbol, setActivePinia } from "./rootStore";
import { StateTree } from "./types";

export function createPinia(): Pinia {
  // 全局作用域，后续可以停止这个作用域
  const scope = effectScope(true)
  // 这里是整个应用共享一个状态，后续通过 defineStore 创建的 store，会给其挂载到这里。
  const state = scope.run<Ref<Record<string, StateTree>>>(() =>
      ref<Record<string, StateTree>>({})
  );

  let _p: Pinia['_p'] = []
  let toBeInstalled: PiniaPlugin[]  = []
  const pinia = {
    install(app: App) {
      setActivePinia(pinia)
      pinia._a = app
      // 在这里挂载 pinia 对象给 Vue 的全局状态，方便后续在组件中使用 inject 函数获取，只能在 setup 中使用
      app.provide(piniaSymbol, pinia)
      // 给 app 挂载全局的属性，后续可以在组件中通过 this.$pinia 获取，这是 vue2 版本的，vue3 没有 this 属性
      // https://cn.vuejs.org/api/application.html#app-config-globalproperties
      app.config.globalProperties.$pinia = pinia as any
      toBeInstalled.forEach(plugin => _p.push(plugin))
      toBeInstalled = []
    },
    use(plugin): Pinia {
      if (!this._a) {
        toBeInstalled.push(plugin)
      } else {
        _p.push(plugin)
      }
      return this
    },
    _p,
    _a: null,
    _e: scope,
    _s: new Map<string, any>(), // 记录 store 
    state: state!
  };
  return pinia
}
```

```typescript
  const rawStore = toRaw(store)

  // TODO 这里直接遍历 store，会走依赖收集，浪费性能，所有需要使用 toRaw 把原始 store 取出来
```

```typescript
function mergeReactiveObject<
  T extends Record<any, unknown> | Map<unknown, unknown> | Set<unknown>
>(target: T, patchToApply: any): T {
  if (target instanceof Map && patchToApply instanceof Map) {
    patchToApply.forEach((value, key) => target.set(key, value))
  } else if (target instanceof Set && patchToApply instanceof Set) {
    patchToApply.forEach(value => target.add(value))
  }

  for (const key in patchToApply) {
    if (!patchToApply.hasOwnProperty(key)) continue
    const subPatch = patchToApply[key]
    const targetValue = target[key]
    if (
      isPlainObject(targetValue) &&
      isPlainObject(subPatch) &&
      target.hasOwnProperty(key) &&
      !isRef(subPatch) &&
      !isReactive(subPatch)
    ) {
      target[key] = mergeReactiveObject(targetValue, subPatch)
    } else {
      target[key] = subPatch
    }
  }
  return target
}

// options Api
function createOptionsStore<
  Id extends string,
  S extends StateTree,
  G extends {},
  A extends {}
>(
  id: Id,
  options: DefineStoreOptions<Id, S, G, A>,
  pinia: Pinia,
  hot?: boolean
): Store<Id, S, G, A> {

  const { state, getters, actions} = options;
  // 获取缓存的状态
  const initialState: StateTree | undefined = pinia.state.value[id]
  let store: Store<Id, S, G, A>

  // 定义 setup 函数，作用是创建 store 实例
  function setup() {
    // 如果不是 hot 模式，且没有有初始 state，则赋值 state
    if (!initialState && !hot) {
      pinia.state.value[id] = state ? state() : {}
    }
    // 创建 store 实例
    const localState = hot
      ? toRefs(ref(state ? state() : {}).value)
      : toRefs(pinia.state.value[id])
    // 合并 actions 和 getter，最后赋值到 store 实例
    return assign(
      localState, // states
      actions,    // actions
      // getters
      Object.keys(getters ?? {}).reduce((computedGetters, name) => {
        if (name in localState) {
          console.warn(
            `[🍍]: A getter cannot have the same name as another state property. Rename one of them. Found with "${name}" in store "${id}".`
          )
        }
        computedGetters[name] = markRaw(
          computed(() => {
            setActivePinia(pinia)
            // 获取 store
            const store = pinia._s.get(id)
            // 这里的作用是给 getter 添加 store 的 this 指向
            return getters[name].call(store, store)
          })
        )
        return computedGetters

      }, {} as Record<string, ComputedRef>)
    )
  }
  store = createSetupStore(id, setup, options, pinia, hot, true)
  return store as any
}

// composition api
function createSetupStore<
  Id extends string,
  SS extends Record<any, unknown>,
  S extends StateTree,
  G extends {},
  A extends {}
>(
  $id: Id,
  setup: (helper: SetupStoreHelpers) => SS,
  options:
    | DefineSetupStoreOptions<Id, S, G, A>
    | DefineStoreOptions<Id, S, G, A> = {},
  pinia: Pinia,
  hot?: boolean,
  isOptionsStore?: boolean
): Store<Id, S, G, A> {
  // 定义 作用域 这里是 子作用域
  let scope: EffectScope

  const optionsForPlugin = assign({
    actions: {}
  }, options)

  const $subscribeOptions: WatchOptions = { deep: true}

  let isListening: boolean
  let isSyncListening: boolean
  let subscriptions: Set<any> = new Set()
  let actionSubscriptions: Set<any> = new Set()
  let debuggerEvents: DebuggerEvent[] | DebuggerEvent
  const initialState = pinia.state.value[$id]

  if (!isOptionsStore && !initialState && !hot) {
    /* istanbul ignore if */
    pinia.state.value[$id] = {}
  }

  const $patch = (partialStateOrMutator: any) => {
    if (typeof partialStateOrMutator === 'function') {
      partialStateOrMutator(pinia.state.value[$id])
    } else {
      mergeReactiveObject(pinia.state.value[$id], partialStateOrMutator)
    }
  }
  const $reset = isOptionsStore
    ? function $reset(this: _StoreWithState<Id, S, G, A>) {
        const { state } = options as any
        const newState = state ? state() : {}
        this.$patch(($state) => {
          assign($state, newState)
        })
      }
    : () => {
      throw new Error(
        `🍍: Store "${$id}" is built using the setup syntax and does not implement $reset().`
      )
    }

    function $dispose() {
      scope.stop()
      subscriptions.clear()
      actionSubscriptions.clear()
      pinia._s.delete($id)
    }

  // 定义 action，作用是为了增加异步等逻辑
  const action = <Fn extends _Method>(fn: Fn, name: string = ''): Fn => {
    if (ACTION_MARKER in fn) {
      ;(fn as unknown as MarkedAction<Fn>)[ACTION_NAME] = name
      return fn
    }
    const wrappedAction = function(this: any) {
      setActivePinia(pinia)
      const args = Array.from(arguments)
      // TODO 异步逻辑
      let ret: unknown
      try {
        ret = fn.apply(this && this.$id === $id ? this : store, args)
      } catch (error) {
        throw error
      }
      return ret
    }
    wrappedAction[ACTION_MARKER] = true
    wrappedAction[ACTION_NAME] = name
    return wrappedAction as any
  }

  // 定义 partialStore 
  const partialStore ={
    _p: pinia,
    $id,
    $onAction: null,
    $patch,
    $reset,
    $subscribe(callback, options = {}) {
      const removeSubscription = assSubscriptions(
        subscriptions,
        callback,
        options.detached,
        () => stopWatcher()
      )
      const stopWatcher = scope.run(() => 
        watch(
          () => pinia.state.value[$id],
          (state) => {
            if (options.flush === 'sync' ? isSyncListening : isListening) {
              callback({
                  storeId: $id,
                  type: MutationType.direct,
                  events: debuggerEvents
                },
                state
              )
            }
          },
          assign({}, $subscribeOptions, options)
        )
      )

      return removeSubscription
    },
    $dispose
  } as _StoreWithState<Id, S, G, A>

  // 创建 响应式 store
  const store: Store<Id, S, G, A> = reactive(IS_CLIENT 
    ? assign({
      _customProperties: markRaw(new Set<string>())
    }, partialStore) 
    : partialStore
  ) as unknown as Store<Id, S, G, A>

  // 将 store 添加到 _s 缓存中
  pinia._s.set($id, store)

  const runWithContext = pinia?._a?.runWithContext || fallbackRunWithContext
  // 这里是为了划分父子作用域
  const setupStore = runWithContext(() => 
    pinia._e.run(() => // 父作用域
      (scope = effectScope()).run( // 子作用域
        () => setup({ action })
      )
    )
  ) as Record<any, unknown>

  // 覆盖 store 的属性
  for (const key in setupStore) {
    const prop = setupStore[key]
    if ((isRef(prop) && !isComputed(prop)) || isReactive(prop)) {
      //! 只有setupStore 是 reactive 或 ref 的属性，才会被覆盖
      if (!isOptionsStore) {
        pinia.state.value[$id][key] = prop
      }
    } else if (typeof prop === 'function') {
      const actionValue = action(prop as _Method, key)
      setupStore[key] = actionValue
    }
  }

  // 合并 setupStore 结果
  assign(store, setupStore)
  assign(toRaw(store), setupStore)

  // 创建 $state 属性
  Object.defineProperty(store, '$state', {
    get: () => pinia.state.value[$id],
    set: (state) => {
      $patch(($state) => {
        assign($state, state)
      })
    }
  })

  // 执行所有插件
  pinia._p.forEach((extender) => {
    if (IS_CLIENT) {
      const extensions: any = scope.run(() => {
        extender({
          store,
          app: pinia._a,
          pinia,
          options: optionsForPlugin
        })
      })
      Object.keys(extensions || {}).forEach(key => (store as any)._customProperties.add(key))
      assign(store, extensions)
    } else {
      assign(
        store,
        scope.run(() => {
          extender({
            store,
            app: pinia._a,
            pinia,
            options: optionsForPlugin
          })
        })
      )
    }
  })

  isListening = true
  isSyncListening = true
  return store
}

export function defineStore<
  Id extends string,
  S extends StateTree = {},
  G extends {} = {},
  A = {}
>(
  id: Id,
  options: Omit<DefineStoreOptions<Id, S, G, A>, "id">
): StoreDefinition<Id, S, G, A>
export function defineStore<Id extends string, SS>(
  id: Id,
  storeSetup: (helper: SetupStoreHelpers) => SS,
  options?: DefineSetupStoreOptions<
    Id,
    {},
    {},
    {}
  >
): StoreDefinition<Id, {}, {}, {}>

export function defineStore(
  id: any,
  setup?: any,
  setupOptions?: any
) {
  let options: 
    | DefineStoreOptions<
        string,
        StateTree,
        {},
        {}
      >
    | DefineSetupStoreOptions<
        string,
        StateTree,
        {},
        {}
      >
  const isSetupStore = typeof setup === "function"
  options = isSetupStore ? setupOptions : setup

  function useStore(pinia?: Pinia | null, hot?: StoreGeneric): StoreGeneric {
    // 判断当前代码执行环境是否支持通过 provide 和 inject 进行依赖注入
    const hasContext = hasInjectionContext()
    // 获取当前活跃的 pinia
    pinia = (activePinia && activePinia._testing ? null : pinia) || (hasContext ? inject(piniaSymbol, null) : null)
    // 如果 pinia 存在，则设置当前活跃的 pinia
    if (pinia) setActivePinia(pinia) 

    // 如果当前激活的 pinia 不存在，则抛出错误
    if (!activePinia) {
      throw new Error(
        `[🍍]: "getActivePinia()" was called but there was no active Pinia. Are you trying to use a store before calling "app.use(pinia)"?\n` +
          `See https://pinia.vuejs.org/core-concepts/outside-component-usage.html for help.\n` +
          `This will fail in production.`
      )
    }

    // 让 pinia 设置当前 active pinia
    pinia = activePinia

    // 判断是否已经创建过 store，没有则创建并缓存到 _s 中
    if (!pinia._s.has(id)) {
      if (isSetupStore) {
        createSetupStore(id, setup, options, pinia)
      } else {
        createOptionsStore(id, options as any, pinia)
      }
    }

    // 获取 store
    const store: StoreGeneric = pinia._s.get(id)

    // 如果是 hot 模式，则删除并重新创建
    if (hot) {
      const hotId = '__hot' + id
      const newStore = isSetupStore
        ? createSetupStore(hotId, setup, options, pinia)
        : createOptionsStore(hotId, assign({}, options) as any, pinia, true);
      (hot as any)._hotUpdate(newStore)

      delete pinia.state.value[hotId]
      pinia._s.delete(hotId)
    }

    // 如果是 客户端 环境，从缓存中获取 store 实例
    if (IS_CLIENT) {
      const currentInstance = getCurrentInstance()
      if (
        currentInstance &&
        currentInstance.proxy &&
        !hot
      ) {
        const vm: any = currentInstance.proxy
        const cache = '_pStores' in vm ? vm._pStores : (vm._pStores = {})
        cache[id] = store
      }
    }
    return store
  }
  useStore.$id = id
  return useStore
}

// 对于 pinia 而言有三种修改状态的方式：
//  1.store.xxx = yyy
//  2.store.action()
//  3.store.$patch()
```

## 💡 一张图总结（面试速记）

| 知识点 | 一句话解释 | 面试价值 |
| --- | --- | --- |
| Store 本质 | 一个特殊的 Composable，`reactive` 包 state，`computed` 实现 getters | 高频，是理解一切后续机制的根基 |
| 没有 Mutation | 响应式系统本身可追踪，不需要强制同步入口 | 高频，「为什么」类问题的标准考法 |
| 单例机制 | `defineStore` 返回的 `useStore` 按 id 缓存在 `pinia._s` Map 里 | 高频，配合 Store 间调用一起考 |
| Setup Store | `setup()` 直接执行，返回值按 ref/reactive/function 分类合流进 store | 中频，考查对 Composition API 的理解深度 |
| 插件系统 | `pinia.use()` 注册，插件返回值 `assign` 合并进 store | 中频，持久化插件是最常见的落地场景 |
| `$onAction` | 订阅 action 调用的 before/after/onError 三个时机，配合 `$subscribe` 支撑 Devtools 时间旅行 | 中高频，是「没有 Mutation 怎么调试」的标准答案 |
| 类型推断 | `defineStore` 泛型直接结构化推导 `state`/`getters`/`actions` 字面量类型 | 中频，体现 TypeScript-first 的设计取舍 |
