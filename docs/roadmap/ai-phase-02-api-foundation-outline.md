## 各篇详细大纲

### 第 01 篇：多模型接入与降级链：先把请求发出去、发得稳

**副标题**：兼容的是字段名，不兼容的是失败方式和增量格式

**学习目标**：能对着任意两家 API 文档，在 20 分钟内写出它们的字段映射表；给定一个错误码，能判断该重试、该降级、还是该直接抛给用户；能设计一条既省成本又保稳定的双层路由

**前置准备**：DeepSeek key（必做）；OpenAI / Anthropic key 可选（没有就跳过，用 fixture 与文档对照看结构）；预计花费 ¥0.5

> 本篇承担原导读篇的契约声明与依赖图 + 原 01/02 两篇的内容，是本阶段的「总纲 + 第一块地基」。

#### 一、概念：调用是一层系统，不是一次网络请求

- 三个把「调用」做小了的误判：把调用能力当成「会写 `fetch`」、把多模型接入当成「复制粘贴四份」、把「OpenAI 兼容」当成「真兼容」
- 三个误判的根是同一个：**把「调用」当成一次网络请求，而不是一层系统**。一次请求失败就重发、一次返回就直出、一个模型写死一家——脚本可以这么写，系统不行
- **四块地基的依赖图**（本篇唯一需要记住的图）：

  ```
  多模型接入(01) → 流式输出(02/03) → 结构化输出(04) → Function Calling(05) → 向量嵌入(06)
        │                   │                                                       │
        └──────────── 异步与并发(07)：横切前四块，管住次数与失败 ──────────────┘
                                     ↓
                          SDK 收口(07)：把上面所有代码变成 packages/ai-sdk
  ```

  > 写作提示：这张图在文章里必须换成真实配图（中文图注写清「箭头代表依赖，虚线框代表横切能力」），**不要用代码块或 mermaid**——公众号不渲染。

- **本阶段的契约（写作时反复回指）**：
  - 全程手写，不引入 Vercel AI SDK（阶段六才上）
  - 实验进 `labs/`，只有 07 篇的最终产物进 `packages/ai-sdk`
  - 每篇的实验都在给同一个网关加一块，不是七个独立脚本

#### 二、深入：四类差异、一次归一化、一张错误分类表

- **差异一：请求结构**——`system` 提示的三种放法（OpenAI 兼容层 `messages[0].role='system'`、Anthropic 顶层独立参数、部分厂商特殊 role）；工具定义、`response_format`、思考模式开关各写各的
- **差异二：响应结构**——正常文本的取法基本一致（`choices[0].message.content`），元数据不一致（`usage` 字段名、有无 `cached_tokens`、有无 `system_fingerprint`）
- **差异三：流式格式**——DeepSeek / OpenAI 兼容：每个 chunk 是 `chat.completion.chunk`，增量在 `choices[0].delta.content`；Anthropic 原生：`content_block_delta` + `delta.text` + 生命周期事件。**同一个「流」在不同厂商眼里是两种协议**
- **差异四：错误类型**——HTTP 状态码看似通用，语义不同（有的厂商 402 表余额不足、有的直接 403）；错误体结构完全不同，必须自己定义一层 `AIError`
- **归一化的两层设计**：
  - Adapter（形状层）：`ChatProvider.chat()` 返回统一 `ChatResult` / `AsyncIterable<Delta>`——这层能 100% 归一化
  - Error（失败层）：`classifyError()` 把各家错误映射成 `retryable | terminal | rate_limited | auth`——这层**只能近似**，因为原文信息不等价
  - 一句话：**形状可以归一化，语义只能约定**
- **错误二分法才是降级设计的地基**：
  - `retryable`（可重试/可降级）：限流（429）、服务端错误（500）、过载（503）、超时、网络中断
  - `terminal`（不重试，直接抛）：参数错误（400/422）、认证失败（401）、余额不足（402）、权限不足
  - **判据一句话：这个错误换成另一家厂商会不会消失？** 会 → 可以降级；不会 → 降级只是多烧一次钱
- **DeepSeek 的 7 个错误码**（2026-11-02 官方文档，写成一张表直接可用）：

  | 状态码 | 错误信息 | 分类 | 处置 |
  |---|---|---|---|
  | 400 | Invalid Format | terminal | 修请求体 |
  | 401 | Authentication Fails | terminal | 检查/重建 key，**不降级** |
  | 402 | Insufficient Balance | terminal | 充值，**不降级** |
  | 422 | Invalid Parameters | terminal | 修参数 |
  | 429 | Rate Limit Reached | retryable | 退避重试，再降级 |
  | 500 | Server Error | retryable | 重试，再降级 |
  | 503 | Server Overloaded | retryable | 重试，再降级 |

- **跨厂商的坑**：不要靠状态码做唯一判据，要同时看错误体里的 `code` / `type` 字段，并把这层映射写成显式表
- **降级链的三个设计问题**：顺序（按「成本 × 能力」排，阶段一备忘录结论 Flash 打底 + Pro 兜底）、次数（每层最多重试 1 次，整条链最多 3 家，防止一次故障放大成 9 倍请求）、状态（连续失败 N 次踢出链，是熔断雏形，07 篇展开）
- **双维路由**（与降级链叠加，不互斥）：按复杂度路由（省成本）+ 按可用性路由（保稳定）；决策顺序**先可用性过滤，再复杂度分流**
- **接口演进（了解即可）**：OpenAI Responses API 已成为推荐主接口；Batch API / Message Batches 大批量非实时场景可打 5 折。**不必在本阶段动手**，阶段六 AI SDK 会默认走新接口
- **边界声明**：**「一次调用里放什么内容、按什么顺序放」属于上下文工程，留到阶段三**。本篇只讲「同一份内容，怎么装进不同的信封」

#### 三、案例：能力矩阵 + 归一化 + 注入五类错误走降级链

- 项目：`labs/phase2-api/01-provider-router/`
- 实验 A：能力矩阵探测（原导读篇 `00-smoke` 并入）
  - 读 `.env.local`，对每个**已配置**的 provider 发一次最小聊天请求 + 一次 `stream: true`，打印一张能力矩阵：`有 key` / `流式可用` / `支持 response_format` / `提供 embedding 接口`
  - **要看见**：没配的 key 不影响开跑（列显示 `—`）；DeepSeek 的 embedding 列是空的（这个空缺一直延伸到 06 篇，成为「接口要拆」的论据）
- 实验 B：原始报文采集 + 归一化（**不许用任何 SDK，只用 `fetch`**）
  - 同一句医疗问题（如「阿莫西林胶囊的常见不良反应有哪些」）打 DeepSeek，打印请求体（脱敏）、非流式响应全文、流式前 3 帧与最后 1 帧；原始报文存进 `_fixtures/*.json`（带 `capturedAt` 与文档链接）

  - **要看见**：`ChatResult` 归一化成功，但**错误对象仍然各不相同**——直接引出实验 C
- 实验 C：降级链 + 双维路由（**全部走 mock，零成本**）

  - 20 条医疗问题按复杂度打标，三种策略（全走大模型 / 规则路由 / 规则路由 + 一条误判）对照成本

### 第 02 篇：SSE 服务端：流式不是「更快返回」，是「更早开始」

**副标题**：整段回答的总耗时没变，用户感知却从 8 秒变成 0.5 秒——变的是等待的形状

**学习目标**：能用 `curl -N` 判断一条流是真流式还是被缓冲了，并顺着链路定位缓冲发生在哪一层；能说清 SSE 为什么比 WebSocket 更合适

**前置准备**：DeepSeek key；只用 Node 内置模块，不引 Web 框架；预计花费 ¥0.3

#### 一、概念：流式的本质是 `AsyncIterable<Delta>`

- 现象：本地 `node server.ts` 逐字出现，部署后「憋八秒吐一次」——不是流式坏了，是**中间某一层把响应缓冲了**
- 直觉定义：流式不是「更快的返回」，是「更早的开始」。每一次 `for await` 拿到一小段文本增量，不是「完整的回答被切开发」

#### 二、深入：从 AsyncIterable 到字节流的三段式

- **第一段：LLM 的流是什么**——DeepSeek 的原始帧（本篇唯一需要记住的报文）：

  ```text
  data: {"object":"chat.completion.chunk","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}],"usage":null}

  data: {"object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"阿莫西林"},"finish_reason":null}],"usage":null}

  data: {"object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"常见不良反应"},"finish_reason":null}],"usage":null}

  data: {"object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":""},"finish_reason":"stop"}],"usage":{"prompt_tokens":18,"completion_tokens":42,"total_tokens":60}}

  data: [DONE]
  ```

  - 三个细节值得单独讲：① 首帧 `delta.role` 有值、`content` 为空；② 思考模式下会有 `delta.reasoning_content`，前端要不要展示是产品决策；③ **最后一个 chunk 带完整 `usage`**，不需要 `stream_options.include_usage` 也能拿到（`include_usage: true` 只是让中间帧也带 usage 字段，值是 `null`）
- **第二段：Node 的 `ReadableStream` 怎么接**——`new ReadableStream({ async start(controller) { for await (...) controller.enqueue(encoder.encode(...)) } })` 或直接 `res.write()` 逐帧写出；关键三个头 `Content-Type: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive` + **必须加的第四个** `X-Accel-Buffering: no`（缺了它就是「本地流、线上不流」的头号元凶）
- **第三段：SSE 帧格式**——一帧 = `data: {json}\n\n`（**两个换行**是帧结束符）；心跳 `: ping\n\n`（冒号开头是注释帧，不触发 `message` 事件）；结束 `data: [DONE]\n\n` 或 `event: done`
- **为什么是 SSE 不是 WebSocket**：AI 文本流是单向、服务端持续推、客户端只说一次；SSE 走 HTTP/1.1 与 HTTP/2、能过大多数代理、能自动重连（`Last-Event-ID`）、不需要额外握手；WebSocket 是全双工，用在这里等于「为了写信装了一部电话」；什么时候该换 WebSocket：需要客户端实时打断并立刻上行（语音对话的 barge-in，阶段十）
- **工程细节（本篇的价值区）**：客户端断开要通知上游（`req.on('close')` → `AbortController.abort()`，不然用户关页面了账单还在跑）；代理超时（Nginx `proxy_read_timeout` 默认 60s）；压缩中间件（`compression` 会攒缓冲，流式端点要排除它）；断线重连（浏览器内建自动重连 + `Last-Event-ID`，但「重连后补回没收到的那半句话」需要消息历史，留到阶段三）
- **边界声明**：**断线重连后的「从上次位置继续」涉及消息历史与状态管理，留到阶段三与阶段六**

#### 三、案例：裸流式端点 + 假流式对照 + 缓冲对照

- 项目：`labs/phase2-api/02-sse-server/`
- 实验 A：用 `node:http` 裸写 `/chat`（**不引 Express / Hono**，本篇要看见每一行）——逐 delta 写 `data:` + `\n\n`，首帧前先 `flushHeaders()`，加 `: ping` 心跳，客户端断开时 `abort()` 上游
  - **要看见**：`curl -N` 的字符随时间陆续出现；`curl` 不加 `-N` 会攒着——「客户端缓冲」的第一课
- 实验 B：假流式对照——版本 1 `await` 完整回答后 `res.end(text)`，版本 2 真流式；用 `curl -N -w '\n首字节: %{time_starttransfer}s  总耗时: %{time_total}s\n'` 各测一次
  - **要看见**：总耗时几乎相同，**首字节时间差一个数量级**——这是本篇结论的全部证据
- 实验 C：缓冲对照——中间加一个「会缓冲的代理」（20 行 Node 脚本，攒够 1KB 才转发），对比加不加 `X-Accel-Buffering: no`（这个头对这个自制代理无效，正好说明「每个代理的开关不一样」）
  - **要看见**：帧从「逐个到达」变成「成批到达」——上线后诡异的根因
- 关键结论：**流式改的不是速度，是等待的形状**
- 脚本要求：打印「3 次真实调用 × 4 种组合，约 ¥0.3」；服务端 10 分钟后自动关停，防止忘关

#### 四、总结

- 本篇结论：服务端的流式只有三件事——拿到 `AsyncIterable`、按 SSE 帧格式写、确保中间每一层都不缓冲
- 明确留到后面：浏览器怎么消费这条流（`EventSource` 为什么不行）→ 03 篇；框架的 Data Stream Protocol 与裸 SSE 的差异 → 阶段六；语音场景的双向流 → 阶段十

### 第 03 篇：前端接流式：接得上，更要接得住

**副标题**：每个 token 都 setState，等于把两百次渲染的账单寄给主线程

**学习目标**：能在 60fps 下渲染 2000 个 delta 而不掉帧，并解释为什么不能每个 delta 都触发一次完整更新

**前置准备**：第 02 篇的服务端跑着；浏览器能开 DevTools；预计花费 ¥0.3

#### 一、概念：消费一条流 = 解析 SSE 帧 + 处理字节边界 + 渲染调度

- 三个在前端接流时必踩的坑：`EventSource` 不能发 POST / 带 body / 传 `Authorization` 头；中文偶尔出现 `�`（`TextDecoder` 没开 `{ stream: true }`）；每收到一个 delta 就更新一次 DOM，长回答卡成幻灯片
- 三个坑的根不同：坑一是**协议能力**、坑二是**字节边界**、坑三是**渲染调度**。本篇按这个顺序拆

#### 二、深入：消费一条流的正确姿势

- **为什么 `EventSource` 不行 / 什么时候它行**：需要 POST（对话历史太长，URL 放不下）、自定义头（鉴权）、JSON body 时不行；纯 GET 订阅场景（新闻推送、任务进度）行。**AI 对话几乎一律用 `fetch` + `ReadableStream.getReader()`**
- **手写一个 SSE 解析器**（本篇第一段代码，30 行就够）：`reader.read()` → `decoder.decode(value, { stream: true })` → 按 `\n\n` 切帧 → 剥掉 `data: ` 前缀 → `JSON.parse`；**两个必须处理的边界**：一个 chunk 可能含半帧（留 buffer 拼下一轮）、一个 chunk 可能含多帧（循环切）。为什么不用库：这 30 行就是 `useChat` 底下那 30 行，阶段六看源码时会有既视感
- **`TextDecoder({ stream: true })` 的原理**：`read()` 返回 `Uint8Array`，一个汉字 UTF-8 编码 3 字节，网络分片可能把它切在中间；不开 `stream: true` 时解码器把不完整字节替换成 `�`，开了之后把残余字节留在内部状态里等下一片拼上
- **渲染调度（本篇第二段，也是前端的主场）**：错误做法 `onDelta(() => setText(prev => prev + delta))`——2000 次 setState → 2000 次协调；正确做法 `buffer += delta`，用 `requestAnimationFrame` 每帧提交一次；渲染次数从「delta 数」降到「帧数」（约 60/s），长回答下差 5~20 倍；进阶（了解）React 18+ 的 `useSyncExternalStore` + `startTransition`，本文只讲 rAF（框架无关的通用解）
- **中断（abort）**：`AbortController` 的 `signal` 传给 `fetch`，`abort()` 同时断开连接 → 服务端 `req.on('close')` 触发 → 上游 LLM 请求被取消；**要验证的不是「界面停了」，是「网络请求真的 cancelled 了」**（DevTools Network 里状态要变成 `(canceled)`）
- **为什么本阶段不用 React**：04 的学习目标是「流 + 字节边界 + 渲染调度」，不是「React 状态管理」；引入 React 会把注意力吸到 hooks 上，`useChat` 的对照留给阶段六；用原生 DOM + 一行 rAF 计数能把「渲染次数」量出来，React 里反而看不见
- **边界声明**：**消息历史管理、多轮上下文、会话持久化留到阶段三；`useChat` 的声明式封装留到阶段六**

#### 三、案例：两种渲染策略 + 字节边界 + abort 传播

- 项目：`labs/phase2-api/03-stream-client/`
- 实验 A：同一回答两种渲染策略——策略 A 每个 delta 直接改 `textContent`（模拟 naive `setState`），策略 B buffer + `requestAnimationFrame` 批量提交；页面同时显示三个计数：`delta 数` / `实际渲染次数` / `长任务数`（`PerformanceObserver`）
  - **要看见**：A 的渲染次数 ≈ delta 数，B ≈ 帧数；A 在长回答上出现 `longtask`，B 没有
- 实验 B：中文字节边界——服务端按字节切分（每 2 字节发一次）制造必然断字，对比 `TextDecoder()` 与 `TextDecoder({ stream: true })`
  - **要看见**：不开 `stream` 时出现 `�`；开了之后即使切在汉字中间也能正确拼回
- 实验 C：abort 传播链路——点「停止生成」→ 前端 `abort()` → 服务端日志「上游已取消」→ DevTools 请求状态 `(canceled)`
  - **要看见**：三处同时停下；对照版本（只停 UI 不停请求）会在服务端继续跑 10 秒
- 关键结论：**流式的难点不在「接上」，在「接得住」——字节边界、渲染频率、取消传播**
- 脚本要求：`esbuild` 把 TS 打到单文件；打印「本实验真实调用 3 次，约 ¥0.3」

#### 四、总结

- 本篇结论：前端消费流式的三件事——自己解析 SSE（因为 `EventSource` 不够用）、正确处理字节边界、把渲染收敛到帧
- 明确留到后面：`useChat` 把这 100 行封装成了什么 → 阶段六；生成式 UI、部分结果渲染、barge-in → 阶段十；中止后的部分结果要不要保存 → 阶段三

### 第 04 篇：结构化输出：把正确性押在 Schema 上

**副标题**：Prompt 是请求，Schema 是合同——能被机器拒绝的输出，才叫可靠

**学习目标**：能设计一个「模型不可能返回非法枚举」的 Schema，并让 TS 类型从它推导出来；能说清 `json_object` 与 `json_schema` 的可靠性鸿沟在哪

**前置准备**：DeepSeek + 通义两家 key（**DeepSeek 只有 `json_object`，`json_schema` 档用通义对照，正是本篇实验设计**）；`zod` 依赖；20 条处方文本样本（可手写）；**必须先关掉思考模式**；预计花费 ¥0.6

#### 一、概念：三档可靠性阶梯 Prompt < `json_object` < `json_schema`

- 现象：从「阿莫西林胶囊 0.5g 每日三次 口服 连用 7 天」里抽 `{药品, 剂量, 频次, 疗程, 给药途径}`，10 次里 3 次不能用
- 三种坏法：包了 Markdown 围栏、字段名漂移、枚举值自由发挥（「一天三次」而不是 `tid`）
- 直觉解释：「多加几句『只输出 JSON』就好了」——能好一点，但**它是请求，不是约束**
- 先讲清前提：**「支不支持 `json_schema`」不是所有厂商都给的能力**。2026-11 现状是分层的：只有 Prompt、只有 `json_object`、有 `json_schema` 三档。不谈这个前提，「结构化输出」就是一句空话

#### 二、深入：三条路径，一条比一条硬

- **路径一：Prompt 约定 JSON，靠模型服从**——做法：提示词写清格式 + 给示例 + 强调「只输出 JSON」；可靠性最低（围栏、前后解释、字段漂移、截断）；适用一次性原型
- **路径二：`response_format: { type: 'json_object' }`**——保证输出是**合法 JSON**，不保证字段名、类型、结构稳定
  - **DeepSeek 特有，必讲的三个坑**：① 提示词里**必须出现 `json` 字样**，否则报错；② 输出里非 JSON 的部分会被**替换成空格**（`U+0020`），所以 `content` 可能看起来是空的，而 `finish_reason` 仍是 `stop`——必须处理空 content 并重试；③ `max_tokens` 不设好会被截断成半个 JSON
- **路径三：`response_format: { type: 'json_schema', json_schema: { name, strict: true, schema } }`**——保证输出严格符合给定 JSON Schema（字段、类型、必需项、枚举、`additionalProperties: false`）
  - 现状（2026-11-02 核实）：**DeepSeek 官方文档只给出 `json_object`，未提供 `json_schema`**；通义 `qwen3.8-flash` 等 5 个模型支持 `json_schema`（建议 `strict: true`）
  - **这就是本篇最值钱的认知：同一段代码，换一家模型，可靠性档位就掉了两级。** 结构化输出不是一个「配置项」，是一个**选型维度**
- **无论哪条路径，最后都要过 Zod**：运行时校验（挡住模型的一切意外）+ 类型推导（`z.infer`）；三段式 `Schema 定义 → API 约束（能约束就约束）→ Zod 校验（永远校验）`；**永远校验的理由**：路径三约束的是「结构」不是「语义」——剂量可能抽到错误字段里，结构完全合法
- **Schema 设计原则（本篇第二块硬货）**：字段命名贴近业务语义（`给药途径` 而不是 `route`）；**枚举显式列出**，不要自由字符串；可选字段给默认值兜底；数字加范围约束（剂量必须 > 0）
- **System Prompt / Few-shot / CoT 的定位区分**（路线图 2.3 的知识点，一次性讲清）：System Prompt 定**角色与边界**；Few-shot 校正**输出格式**（2 个「输入 → 输出」示例比十句「请按格式输出」有效）；CoT 引导**推理过程**（复杂剂量换算才需要）；三者不是越多越好，**在抽取任务里加 CoT 会拖慢且更容易跑偏**
- **边界声明**：**流式与结构化输出的组合是真坑**——流式下每个 delta 都不是合法 JSON，不能边收边 parse。本篇只讲「收完后校验」，增量 JSON 解析留到阶段六

#### 三、案例：20 条处方 × 三条路径

- 项目：`labs/phase2-api/04-json-schema/`
- 实验 A：三条路径的可靠性对照——固定 Schema：`{ drug: string, dose: number, doseUnit: enum, frequency: enum('qd','bid','tid','qid','prn'), durationDays: number, route: enum }`；20 条样本 × 3 种方式（Prompt 约定 / `json_object` / `json_schema`，DeepSeek 那组没有第三档、改用通义跑）；记录四个指标：`解析失败率` / `字段缺失率` / `枚举漂移率` / `语义错误率`（人工看）
  - **要看见**：Prompt 组失败主要在围栏与截断；`json_object` 组几乎不失败但字段名会漂；`json_schema` 组结构上零失败，**但语义错误仍在**——「Schema 挡得住格式，挡不住理解」
- 实验 B：Zod 兜底的价值——把同一条「结构合法但语义错误」的样本喂给 Zod，看它是否放行
  - **要看见**：Zod 放行——所以真正的护栏是「Schema + 业务校验 + 抽样人工」，三层缺一不可
- 实验 C（对照组，必须做）：思考模式开着 vs 关着，同一 Schema 的失败率
  - **要看见**：`temperature` 在思考模式下不生效，按阶段一习惯调温度求稳定会得出假结论
- 关键结论：**能被机器拒绝的输出才叫可靠；而机器只能拒绝它被允许检查的那部分**
- 脚本要求：打印「20 条 × 3 组 ≈ 60 次调用，约 ¥0.6」；`--live` 才真实调用，默认读 fixture

#### 四、总结

- 本篇结论：结构化的可靠性是一条阶梯——Prompt < `json_object` < `json_schema` < Schema + Zod + 业务校验。**选模型时要看它站在哪一级**
- 明确留到后面：让模型输出「动作」而不是「数据」→ 05 篇；结构化抽取在真实文档上的脏活（PDF、表格）→ 阶段四第 4.6 节；用评估集量化「结构化成功率」→ 阶段九

### 第 05 篇：Function Calling：模型只写调用单，不执行

**副标题**：模型负责「说什么」，你的代码负责「做什么」——两者之间那条线就是 Agent 的边界

**学习目标**：能画出一次 tool call 的完整往返，并指出「模型负责哪一段、你的代码负责哪一段」；能在执行前拦住参数幻觉

**前置准备**：DeepSeek key（支持工具调用）；一个本地 mock 药品库（JSON 文件）；**先关思考模式**；预计花费 ¥0.4

#### 一、概念：模型不执行代码，它只输出结构化「调用单」

- 现象：给模型一个 `check_stock(drugId)` 工具，问「阿莫西林还有货吗」，回答很肯定地说「有，库存 120 盒」——但数据库里那条记录根本不存在
- 直觉解释：「它调用了工具啊」——它**没有**调用。它只返回了一段 XML/JSON，说明「我想调用 `check_stock`，参数是 `{drugId: 'AMX-500'}`」。真正执行的是**你的代码**；如果那段代码里写的是「查不到就返回 120」，它也会照实念出来
- 这个误判的代价直接对应到阶段五：Agent 的所有安全问题，都源于「模型能说，但不能做」这条边界被搞混

#### 二、深入：一次完整往返的五个步骤

- **步骤与责任划分**（本篇的核心图）：

  | 步骤 | 谁做的 | 做什么 |
  |---|---|---|
  | 1 | 你的代码 | 把工具定义（name / description / parameters 的 JSON Schema）发给模型 |
  | 2 | 模型 | 输出 `tool_calls`：函数名 + 参数（**纯文本，无副作用**） |
  | 3 | 你的代码 | 校验参数（Zod）→ 检查权限 → **执行真实函数** |
  | 4 | 你的代码 | 把结果作为 `role: 'tool'` 的消息回传 |
  | 5 | 模型 | 根据结果生成最终回答 |

- **关键认知一**：`tool_calls` 是**结构化意图**，不是执行。中间那一步（步骤 3）是你能插入一切安全措施的地方
- **关键认知二**：工具描述（`description`）就是给模型的 Prompt。写「查询药品库存」和写「查询指定 drugId 的实时库存，返回 available 与 warehouse，drugId 必须是药库中已存在的编号」——后者的调用准确率高一个档
- **关键认知三**：参数会幻觉。模型会编一个不存在的 `drugId`。**必须在步骤 3 校验**，校验失败就回传一条「该 drugId 不存在，可用编号有 A/B/C」的错误消息让模型自己纠正——这是 Agent 自我修正的雏形
- **关键认知四**：工具描述写太宽会误触发。如果 `check_stock` 的描述写成「查询药品信息」，那「阿莫西林是什么药」也会触发它
- **只读 vs 写操作的分界**（为阶段五埋线）：只读工具（查库存、查说明书）可以自动执行；写操作（下单、改处方）**必须**人机确认——这条规则在阶段五展开成 Human-in-the-Loop
- **为什么这不是 Agent**：本篇是**单次**往返：一问、一调、一答，结束；Agent 是**循环**：模型自己决定「还要不要再调一个」「什么时候停」——那个循环是阶段五。一句话：**Function Calling 是 Agent 的器官，不是 Agent 本身**
- **边界声明**：**多步编排、循环终止、规划模式（ReAct / Plan-and-Execute）留到阶段五**

#### 三、案例：一次完整往返 + 参数幻觉拦截 + 描述宽窄对照

- 项目：`labs/phase2-api/05-tool-call/`
- 实验 A：完整往返，逐帧打印——工具：`check_drug_interaction(drugA: string, drugB: string)`，本地 mock 药品库（10 条相互作用规则）；问题：「阿莫西林能和布洛芬一起吃吗」；打印 ① 发出去的 tools schema ② 收到的原始 `tool_calls`（**强调：此时没有任何网络请求发生**）③ 本地执行结果 ④ 回传的 `role: 'tool'` 消息 ⑤ 最终回答
  - **要看见**：模型在步骤 2 就停了，等你的代码；`arguments` 是一段**字符串**，要自己 `JSON.parse`
- 实验 B：参数幻觉——问一个 mock 库里没有的药，或把 `drugId` 改成自由字符串；先跑不校验版本（函数返回「暂无数据」，模型据错误结论），再跑校验版本（Zod 拦住 → 回传错误消息 → 模型换参数重试 → 成功）
  - **要看见**：同一次对话，加了校验就从「自信地错」变成「自己纠正」
- 实验 C：工具描述写太宽的对照——同一问题「阿莫西林是什么药」，先给宽描述（「查询药品信息」）再给窄描述
  - **要看见**：宽描述下模型会误触发工具；窄描述下直接答
- 关键结论：**模型能说的和能做的之间，隔着你的一个函数——那个函数就是全部安全边界**
- 脚本要求：打印「约 12 次调用，¥0.4」；mock 库与工具定义分离存放，方便 07 篇搬进 SDK

#### 四、总结

- 本篇结论：Function Calling 是「结构化输出的第二形态」——04 篇约束**数据**的形状，05 篇约束**动作**的形状
- 明确留到后面：让模型自己决定「调几次、调哪个」→ 阶段五（ReAct 循环）；工具结果被注入恶意指令（间接 Prompt Injection）→ 阶段九；把工具做成独立可复用服务 → 阶段五（MCP）
- 与本阶段代码的关系：05 的工具执行器会在 07 篇被并发调度，在 07 篇被搬进 SDK

- Function Calling 是模型在调用函数吗？（这题答错基本就废了）
- 一次 tool call 的完整流程有哪几步？哪一步是你能插入安全检查的？

### 第 06 篇：Embedding：把「意思相近」变成一道可以算的减法

**副标题**：向量不是语义的真相，只是一张足够好用的地图

**学习目标**：能解释为什么余弦相似度会在否定句和数字上失败，并据此选模型与维度；能跑通「文本 → 向量 → 比相似度」的完整链路

**前置准备**：本地 `bge-small-zh`（transformers.js，首次下载约 100MB，**零成本**；DeepSeek 不提供 embedding 接口）；12 段说明书片段；预计花费 ¥0

#### 一、概念：向量是分布上的「相近」，不是逻辑上的「等价」

- 现象：把 12 段说明书片段向量化，用「服药期间能否饮酒」去检索，排第一的是「用酒精擦浴物理降温」——因为「酒精」这个词的相似度压过了「服药期间」这个场景
- 直觉解释：「向量相似 = 语义相似」——只对了一半。向量相似是**分布上的相近**，不是**逻辑上的等价**
- 它会在三类情况下骗你：**否定句**（「可以饮酒」和「不可饮酒」向量几乎一样）、**精确数字**（0.5g 与 5g）、**专有名词**（两个都叫「某某胶囊」的药）
- **这三类失败，就是阶段四要引入「混合检索 + 重排序」的全部理由**——本篇先让你亲手撞一次

#### 二、深入：向量化、三种度量、一次选型

- **Embedding 的本质**：把文本映射到一个高维空间里的点，**训练目标决定了「近」等于什么**——是「经常出现在相似上下文里」，不是「意思相同」
- **三种度量**：余弦相似度（看夹角不看长度，文本检索默认）；欧氏距离（看直线距离，受向量长度影响）；点积（看投影，**归一化之后点积与余弦的排序完全一致**——实验会验证）。一句话记忆钩子：**归一化之后，三者只在数值上不同，不在排序上不同**
- **维度与成本**：维度越高表达越细，但存储与计算成本线性上升；主流 embedding 模型支持「降维」（如通义 `qwen3.7-text-embedding-flash` 可选 1024 / 768 / 512 / 256）。**降维几乎免费，但会掉召回**——这个取舍要在实验里看见
- **模型选择（2026-11-02 现状）**：
  - **DeepSeek 不提供 embedding 接口**——这不是配置问题，是能力缺失。这个事实直接决定了 07 篇必须把 `ChatProvider` 与 `EmbeddingProvider` **拆成两个接口**（否则就是 ISP 违例）
  - 本阶段默认本地 `bge-small-zh`：零成本、质量够学习用；**不要用 `bge-m3`**（2GB+，学习场景不划算）
  - 生产可用对照（了解）：通义 `qwen3.7-text-embedding-flash`（1024 维，¥0.125/百万 token，每批 ≤ 20 条）、`text-embedding-v4`（支持 64/128 等更细维度档）
- **批处理限制（易踩）**：每批条数与每批 token 数都有上限，超了直接报错。写批量向量化时**必须分批 + 记录已处理偏移**，否则失败重跑会重复计费
- **边界声明**：**「怎么分块、存在哪、怎么检索出来拼进 Prompt」是 RAG，留到阶段四**。本篇只讲「文本怎么变成一个能比大小的数组」

#### 三、案例：12 段说明书 × 相似度矩阵

- 项目：`labs/phase2-api/06-embedding/`
- 实验 A：12×12 相似度矩阵——12 段片段覆盖：适应症 / 禁忌 / 相互作用 / 用法用量 / 特殊人群 / 储存；算出 12×12 的余弦相似度矩阵，热力表打印（`printTable`）
  - **要看见**：同类片段（如两段「禁忌」）相似度高；但**「不宜饮酒」与「可以少量饮酒」的相似度也高**——第一篇的直觉被推翻
- 实验 B：5 个查询的 Top-3——查询包括：「服药期间能否饮酒」「儿童剂量怎么算」「和阿司匹林能一起吃吗」「孕妇能不能用」「忘了吃药怎么办」
  - **要看见**：「饮酒」那题命中了「酒精擦浴」；「儿童剂量」那题把「成人剂量」排在了前面（数字不敏感）
- 实验 C：度量与维度——对同一批向量，比较余弦 / 欧氏 / 点积（先归一化再算）的排序
  - **要看见**：归一化后余弦与点积排序**完全相同**
- 关键结论：**向量能告诉你「像」，不能告诉你「对」；剩下那一步是检索工程，不是数学**
- 脚本要求：本地 `bge-small-zh` 零成本；打印「本次向量化 N 段文本，本地计算 ¥0」

#### 四、总结

- 本篇结论：Embedding 是「相似度」这个模糊概念的可计算化；它便宜、快、可离线，但只解决「找候选」，不解决「选对的」
- 明确留到后面：分块策略、向量库（pgvector）、Top-K 调参 → 阶段四；混合检索 + RRF + 重排序（正是本篇三个失败的解法）→ 阶段四；用向量做长期记忆检索 → 阶段三；用向量做语义缓存 → 阶段九

### 第 07 篇：并发、超时与 SDK 收口：从脚本到可切换的包

**副标题**：并发不是「同时发出去」，是「同时发出去还能收得回来」；抽象层的验收标准不是代码少，是「换模型只改一行、且这一行有测试兜底」

**学习目标**：能给一批 LLM 调用加上并发上限、超时、退避与熔断，并算出它省下多少墙钟时间、付出多少失败率代价；能设计一个「换模型只改一行」的 SDK 包，并用契约测试守住这个承诺

**前置准备**：01~06 的实验代码都在；DeepSeek key；20 条问题；错误全部用 mock 注入，真实调用只做 3 次校验；`zod`；`vitest` 或 `node:test`；预计花费 ¥1.2

#### 一、概念：并发是「收得回来」，收口是「把换一家变成一次配置」

- 现象一：同时问 3 个模型做对比，`await Promise.all([a, b, c])`，其中一个网络抖动超时——**另外两个即使成功了，结果也拿不到**
- 现象二：01~06 的代码跑得挺好，现在要把主力从 DeepSeek 换成通义——发现 `runner.ts`、`retry.ts`、三个实验脚本里一共 5 处硬编码了 provider
- 直觉解释：「all 就是一起等」「抽个函数就好了」——`Promise.all` 是**全有或全无**；抽函数只能解决「调用写法」，解决不了「能力不对等」
- 两种不对等：**能力不对等**（DeepSeek 没有 embedding 接口，`AIProvider` 同时要求 `chat` 与 `embed` 就逼着 DeepSeek 实现一个假 `embed`）；**格式不对等**（三家的流式增量、错误体、usage 字段各不相同）

#### 二、深入：五个面，一个执行器；三个接口，一次收口

- **面一：事件循环与 LLM 调用**——LLM API 是典型 I/O 密集型：等网络的时间远大于 CPU 时间，所以「并发」在 Node 里几乎不消耗 CPU，**真正的约束是对方的 QPS 上限和你自己的预算**，不是本机线程数
- **面二：`Promise.all` / `allSettled` / 手写信号量**——`all` 全有或全无（适合「缺一个结果就没意义」）；`allSettled` 拿到所有结果与错误（适合「有几个用几个」）；**信号量限流**把并发控制在 N（这才是「批量调用」的正确形态）。一句话：**`all` 管成败，`allSettled` 管归集，信号量管节奏**
- **面三：超时与重试**——`AbortSignal.timeout(ms)` 是 Node 18+ 内置能力，不需要手写 `setTimeout + reject`；指数退避 `delay = base * 2^n`，**必须加 jitter**（`+ random(0, base)`），否则所有重试在同一秒撞在一起把限流变成雪崩；「超时」不是「失败」：超时应归 `retryable`（01 篇分类表），但**超时的请求可能已经计费**，重试前要想清楚
- **面四：熔断器**——三态 `closed` → `open`（连续失败 N 次直接拒绝）→ `half-open`（放一个探针试探）；它是 01 篇「连续失败后踢出链」的正式实现；熔断的意义不是省失败，是**在故障期保护自己与对方**
- **面五：背压与死信**——背压：上游产出快于下游消费（流式场景常见），要么暂停读、要么丢弃中间帧；死信队列：重试耗尽后不丢弃，落盘/入库等人工补偿
- **Batch API 作为「另一种并发形态」（了解）**：不是「并发」，是「离线批量」：提交任务 → 几小时内完成 → 结果下载，价格约 5 折；适用于「1 万份说明书字段抽取」这类非实时场景——**它和本篇的并发控制解决的是不同问题**
- **接口拆分的依据是能力矩阵（01 篇那张表）**：
  - `ChatProvider`：`chat()`（非流式）+ `streamChat()`（流式）+ `modelId`
  - `EmbeddingProvider`：`embed(texts: string[])`
  - **必须拆开**：不是所有 chat provider 都能 embed（DeepSeek 就是），硬塞一个接口就是**接口隔离原则（ISP）违例**——实现类被迫提供它做不到的能力。这条设计有 2026-11 的实证支撑：DeepSeek 官方只提供对话与 Search / Fetch 接口
- **依赖注入与工厂**：业务层只依赖 `ChatProvider` 接口，由 `createProvider(config)` 在启动时注入；`AIRouter` 持有 `ChatProvider[]`，按 01 篇的降级链与 07 篇的熔断状态选一个。一句话：**换模型只改工厂那一行，因为别处根本没有模型名**
- **包边界怎么划**：`packages/ai-sdk` 拥有接口定义、各厂商 Adapter、错误分类、路由器、执行器；它不拥有业务 Prompt、Schema（业务方定义）、缓存策略（阶段三）、检索（阶段四）。**为什么要有这条线**：SDK 一旦开始懂业务，就会开始为业务写特例，最后变成第二个 Controller 层
- **契约测试（本篇的核心工程手法）**：写一套测试用 `MockChatProvider` 跑全部用例（流式与非流式、错误分类、降级、超时、abort）；再写一份「接口契约」：任何新 Adapter 只要通过这套测试，就保证行为一致。**要看见**：新增一个 provider 时，测试会立刻指出「你没实现 `streamChat`」或「你的 401 被分类成了 retryable」
- **第一次进 `pnpm typecheck`**：这是阶段二唯一一次「实验代码变生产代码」——07 篇的目录不再进 `labs/`，而是进 `packages/ai-sdk`；必须写 `tsconfig.json` 继承根配置、`package.json` 声明 `exports`、接入 `turbo.json` 的 `build` / `typecheck` 链路
- **边界声明**：**断线重连后的消息历史、多轮上下文管理留到阶段三；用 Vercel AI SDK 重写留到阶段六**

#### 三、案例：20 题 × 3 模型 × 三种策略 + 搬迁 + 契约测试

- 项目：`labs/phase2-api/07-concurrency-sdk/`（脚本 + 说明）→ 产物落到 `packages/ai-sdk/`
- 实验 A：三种策略的墙钟时间与成功率——20 个医疗问题 × 3 个 mock provider（mock 里注入 20% 超时、10% 500）；策略 1 `Promise.all` 全量并发；策略 2 `Promise.allSettled` 全量并发；策略 3 信号量限流（并发 3）+ `AbortSignal.timeout(8000)` + 指数退避（带 jitter，最多 2 次）；记录 `总墙钟时间` / `成功数` / `失败数` / `总请求数`
  - **要看见**：策略 1 一失败全批丢；策略 2 保留了部分结果但耗时最长；策略 3 墙钟时间中等、成功率 100%、请求数因重试增加——**三者的真实权衡**
- 实验 B：jitter 的作用——同一限流场景，退避有 jitter vs 无 jitter
  - **要看见**：无 jitter 时重试在同一时刻成簇，mock 的 429 计数暴涨；有 jitter 后被打散
- 实验 C：熔断器——让一个 provider 连续返回 500，观察它何时被 `open`，`half-open` 探针何时放行
  - **要看见**：熔断后该 provider 的请求数骤降为 0——不是「重试更努力」，是「先别打它」
- 实验 D：搬迁与拆分 + 契约测试 + 五条验收——把 `_sdk/` 里的 `ChatProvider` 拆成 `ChatProvider` + `EmbeddingProvider`；DeepSeek Adapter 只实现 `ChatProvider`，通义 Adapter 两个都实现（**要看见**：TS 立刻告诉你「DeepSeek 不能当 EmbeddingProvider 用」）；用 `MockChatProvider` 跑 8 条用例（正常/流式/429 降级/401 抛出/超时/abort/空 content/长回答）；逐条跑 01 篇的五条验收清单
  - **要看见**：契约测试是一份**可执行的接口文档**；第 3 条「非法率 0」不是靠模型变乖，是靠 `json_schema` + Zod 挡住了
- **验收清单逐条打勾**（回指 01 篇）：
  1. 能切 3 家模型，业务代码不改 → 演示 `createProvider('dashscope')` 改一行
  2. SSE 首字节 < 1s（本地网络，非高峰档）→ 用 02 篇的 `curl -N -w` 再测一次
  3. 结构化输出的解析非法率为 0 → 用 04 篇的 20 条样本跑一遍
  4. 并发 3 时部分失败不拖垮整批 → 用本实验策略 3
  5. 换模型只改一行，且这一行有测试兜底 → 契约测试
- 关键结论：**并发控制的目标不是「更快」，是「失败不扩散、成本可控、系统能恢复」；抽象的意义不是少写代码，是把「换一家」从一次重构变成一次配置**
- 脚本要求：打印「实验 A/B/C 主要走 mock；真实调用 3 次校验，约 ¥1.2」；`MAX_CALLS` 环境变量硬上限

#### 四、总结

- 本篇结论：`Promise.all` 只适合「全成功才有意义」；生产批量调用的默认形态是「限流 + 超时 + 退避带 jitter + 熔断」。阶段二产出的不是七个实验脚本，是一个能换模型的 SDK 包 + 一份可执行的契约
- **阶段二总结**：到这里你已经能回答路线图阶段二的三条里程碑——
  1. 多模型可切换 + SSE 流式 + 结构化输出的最小 Node 服务
  2. 前端接入流式输出，打字机效果不卡顿
  3. 并发调用多个 LLM，控制并发数并处理超时降级
- 明确留到后面：上下文组装、历史压缩、长期记忆、Prompt 缓存 → 阶段三；把这个网关接上说明书检索 → 阶段四；用 Vercel AI SDK 重写并对比代码量 → 阶段六；评估、监控、安全、成本 → 阶段九
- **成果物交付**：`packages/ai-sdk` + 一份《AI 网关接口契约》说明（含接口定义、错误分类表、验收清单），落到 `docs/articles/00 AI/02 应用底座/`
