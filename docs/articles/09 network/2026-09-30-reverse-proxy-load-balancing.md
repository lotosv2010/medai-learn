## 一、代理是什么 + 正向 vs 反向代理

### 1. 代理：一个「中介」的角色

代理（Proxy）的本质特别简单——**A 和 B 本来可以直连，中间插入一个 C，这个 C 就是中介（代理）**。C 收下 A 发给 B 的请求，转交给 B；B 的响应再由 C 转回给 A。

为什么要多此一举插个中介？因为中介能做的事，比「原样转发」多得多：它可以缓存、可以鉴权、可以记录日志、可以把内网和外网隔开。而这些能力，取决于这个中介**站在哪一边**——站在客户端一边叫「正向代理」，站在服务端一边叫「反向代理」。

### 2. 正向代理：客户端的跳板机

正向代理（Forward Proxy）类似一个**跳板机**，代理客户端去访问外部资源。

最经典的例子是访问 Google：你在国内直接访问 `google.com` 访问不到，但可以通过一个**正向代理服务器**——请求先发到这个代理服务器，这个代理服务器能访问 Google，于是它替你从 Google 取回数据、再返回给你。这样你就「访问到了」Google。

正向代理站在**客户端一侧**，它的典型用途有四个：

- **访问原本无法访问的资源**：如上面的 Google，突破网络限制
- **做缓存**：加速访问资源，多个用户访问同一资源时由代理直接返回缓存
- **对客户端访问授权、上网认证**：企业内网要求先通过代理认证才能上网
- **记录用户访问记录（上网行为管理）、对外隐藏用户信息**：服务端看到的是代理的 IP，不是真实客户端

正向代理的拓扑长这样——客户端要先在系统/浏览器里**显式配置代理服务器地址**，请求才会绕道代理：

![正向代理：客户端配置代理服务器地址后绕道访问](https://cdn.nlark.com/yuque/0/2021/png/738210/1638173165267-a52cb650-9f37-4bde-ab45-42db5795f4e0.png)

### 3. 反向代理：服务端侧的唯一入口

反向代理（Reverse Proxy）的实际运行方式，是**以代理服务器来接受 Internet 上的连接请求，然后把请求转发给内部网络上的服务器，再把内部服务器返回的结果转回给 Internet 上发起请求的客户端**。此时，代理服务器对外就表现为**一个服务器**。

反向代理站在**服务端一侧**，它的核心作用有两个：

- **保证内网安全、阻止 Web 攻击**：大型网站通常把反向代理作为公网访问地址，真正的 Web 服务器藏在内网里，公网用户永远接触不到真实后端
- **负载均衡**：通过反向代理服务器把请求分发到多台真实后端，优化网站的负载

反向代理的拓扑——客户端只看到代理这一个入口，不知道后面有几台真实服务器：

![反向代理：客户端只看到代理入口，不知道真实后端](https://cdn.nlark.com/yuque/0/2021/png/738210/1638173290911-a6aac8d2-4b2d-4092-8e79-578aa889e246.png)

生产环境里，反向代理几乎都由 **Nginx** 承担。Nginx 配一个最简反向代理只需要 `proxy_pass` 一个指令：

```nginx
# 客户端请求 Nginx（监听 80），Nginx 转发到真实后端 8089
server {
    listen 80;
    server_name drug.example.com;

    location / {
        proxy_pass http://127.0.0.1:8089;   # 👈 把请求原样转发给后端，响应再原样返回
    }
}
```

这里的关键是「**原样转发、原样返回**」：Nginx 收到请求后自己重新向后端发一个 HTTP 请求，拿到后端响应后再返回给客户端——客户端从头到尾以为自己在和 Nginx 说话。

### 4. 到底「反」在哪、对谁透明

这一节要回答一个高频被追问的问题：**正向代理和反向代理，网络位置和数据流向其实完全一样，那它们到底区别在哪？**

答案是：**区别在于「代理的是谁、对谁透明」**。

- **正向代理**：站在**客户端**一侧，代理客户端。服务端不知道真实客户端是谁——它看到的只是代理服务器的 IP。也就是说，正向代理**对服务端透明**。
- **反向代理**：站在**服务端**一侧，代理服务端。对外表现为「唯一的服务入口」，客户端不知道请求最终被转发到了集群里的哪一台真实服务器。也就是说，反向代理**对客户端透明**。

一句话收口：**正向代理是「客户端的代理」，反向代理是「服务端的代理」**。反过来记也成立——正向代理**对服务端隐藏了客户端**，反向代理**对客户端隐藏了服务端**。

其实 proxy 在两种代理里做的事都一样——**代为收发请求和响应**——只不过从结构上看正好左右互换了一下，所以把后出现的那种代理方式叫成了「反向代理」。

拿生活场景打比方，两张图记得特别牢：

![看图理解一：正向代理像外卖平台、反向代理像商家集合](https://cdn.nlark.com/yuque/0/2021/png/738210/1638173425146-15efeead-6cc6-4b9e-bfa7-ebabc5adba2a.png)

![看图理解二：正向代理 proxy 和 client 同属一个 LAN，反向代理 proxy 和 server 同属一个 LAN](https://cdn.nlark.com/yuque/0/2021/png/738210/1638173447000-1f10b66e-8b51-4733-9e2e-31105b10d21c.png)

- **正向代理中，proxy 和 client 同属一个 LAN，对 server 透明**
- **反向代理中，proxy 和 server 同属一个 LAN，对 client 透明**

再换个更形象的总结，一句话就记住了：

**正向代理：买票的黄牛**（你找黄牛，票务方不知道你是谁）；**反向代理：租房的托管**（你找中介租到房，房东可能换了你都不知道）。

> 💬 **面试官**：正向代理和反向代理的本质区别是什么？分别站在谁的角度、对谁透明？
>
> ✅ 标准答案：正向代理站在客户端一侧，代理客户端，**对服务端透明**——服务端只知道代理的 IP，不知道真实客户端；反向代理站在服务端一侧，代理服务端，**对客户端透明**——客户端只知道唯一的入口，不知道请求被转发给了集群里的哪台真实服务器。两者的网络位置和数据流向其实一样，区别就在「代理的是谁、对谁透明」。
>
> 🎁 加分答案：能补两个点——① 反向代理因为「对客户端透明」这个特性，天然带来两个架构收益：**内网安全**（真实后端藏在代理后面，公网不可直达）和**负载均衡**（客户端不感知后端有几台、是否增减）；② 还能提到 `X-Forwarded-For` 头——因为反向代理把真实客户端 IP 藏起来了，后端拿 `remote_addr` 看到的是代理的 IP，所以代理要在转发时把真实客户端 IP 塞进 `X-Forwarded-For` 头，后端才拿得到。这是「反向代理『隐藏』了客户端」这个特性带来的一个实际工程问题。

## 二、虚拟主机：一个 IP 服务多个域名

现实里，一台服务器、一个公网 IP，往往要同时服务多个域名。怎么做到的？答案是**虚拟主机（Virtual Host）**——通过 `Host` 请求头实现多个网站共用一个端口、多个网站共用一个服务器。

### 1. Nginx 用 `server_name` 配置虚拟主机

假设医院 HIS 系统里，「处方服务」和「患者服务」是两个独立的后端，分别跑在 8089 和 8090 端口，但对外只暴露一个 Nginx 入口：

```nginx
server {
    listen 80;
    server_name rx.his.com;               # 👈 处方服务的域名

    location / {
        proxy_pass http://127.0.0.1:8089;
    }
}

server {
    listen 80;
    server_name pt.his.com;               # 👈 患者服务的域名

    location / {
        proxy_pass http://127.0.0.1:8090;
    }
}
```

同一个 IP、同一个 80 端口，但 Nginx 会**读请求头里的 `Host` 字段**：是 `rx.his.com` 就转给 8089（处方服务），是 `pt.his.com` 就转给 8090（患者服务）。这就是「一个 IP 服务多个域名」的本质。

Node.js 里用 `http-proxy` 实现同样的效果，思路完全一致——读 `req.headers['host']` 做路由：

```javascript
// server.js —— 虚拟主机路由：按 Host 头分发到不同后端
const http = require('http');
const httpProxy = require('http-proxy');
const proxy = httpProxy.createProxyServer();

const config = {
  'a.gwb.com': 'http://localhost:8089',
  'b.gwb.com': 'http://localhost:8090',
}

const app = http.createServer((req, res) => {
  let host = req.headers['host'];
  host = host?.split(':')[0];
  const target = config[host];
  if(!target) return res.end('NOT FOUND');
  proxy.web(req, res, {
    target
  })
});
app.listen(8088, () => {
  console.log(`server start port 8088`);
})
```

```javascript
// proxy1.js —— 后端 1，监听 8089
const http = require('http');
http.createServer((req, res) => {
  res.end('8089');
}).listen(8089);
```

```javascript
// proxy2.js —— 后端 2，监听 8090
const http = require('http');
http.createServer((req, res) => {
  res.end('8090');
}).listen(8090);
```

测试时，先启动三个进程（`server.js`、`proxy1.js`、`proxy2.js`），然后用浏览器分别访问 `a.gwb.com:8088` 和 `b.gwb.com:8088`（本地开发时在 hosts 文件里把这两个域名指向 127.0.0.1），会看到：

访问 `a.gwb.com:8088`，请求头里 `Host: a.gwb.com:8088`，被路由到 8089，页面显示 `8089`：

![访问 a.gwb.com 路由到 8089 后端](https://cdn.nlark.com/yuque/0/2021/png/738210/1638175564690-d44e25a6-45ed-43ac-af54-05a38d11e206.png)

访问 `b.gwb.com:8088`，请求头里 `Host: b.gwb.com:8088`，被路由到 8090，页面显示 `8090`：

![访问 b.gwb.com 路由到 8090 后端](https://cdn.nlark.com/yuque/0/2021/png/738210/1638175597806-ba20aac6-4300-4889-9fe8-ec47bfa98442.png)

两张图里注意看 **Request Headers 的 `Host` 字段**——它才是虚拟主机路由的唯一依据。

### 2. 原理：`Host` 头是唯一的地址

这一节回答「一台物理服务器、一个 IP，怎么能同时承载多个完全独立的域名？」

关键在于 **`Host` 请求头**。从 **HTTP/1.1 起，`Host` 头成为强制字段**——每个请求都必须在头部写明「我想访问的是哪个域名」。服务端（或反向代理）拿到请求后，**第一步就是读 `Host` 头**，判断客户端想访问哪个域名，再路由到对应的站点配置。

想象一下没有 `Host` 头会怎样：早期 HTTP/1.0 时代，一个 IP 只能绑定一个网站——因为服务端收到请求后没有任何信息告诉它「客户端到底想访问这个 IP 上的哪个站点」，只能默认一个。有了 `Host` 头，一台服务器上可以挂任意多个域名，服务端靠这个字段做路由，这就是**虚拟主机**。

这也解释了前面为什么访问 `a.gwb.com:8088` 和 `b.gwb.com:8088` 能到不同后端——两个域名解析到同一个 IP（127.0.0.1）、同一个端口（8088），**唯一的区分依据就是 `Host` 头的值**。

关于 `Host` 头还有两个细节值得记：

- **没有 `Host` 头或 Host 不匹配**：HTTP/1.1 里请求必须带 `Host`，不带的话服务端通常直接返回 400（Bad Request）；带了但匹配不到任何 `server_name`，Nginx 会命中「默认 server」（第一个 server 块，或显式配置了 `default_server` 的那个）
- **HTTPS 下的 SNI**：这里有个关键转折——TLS 握手发生在 HTTP 请求**之前**，握手时服务端还拿不到 `Host` 头，那 HTTPS 怎么决定用哪个证书？答案是一个叫 **SNI（Server Name Indication）** 的 TLS 扩展——客户端在握手的 ClientHello 阶段就把要访问的域名**明文**发出去（第 03 篇 TLS 讲过握手过程），服务端据此选证书。所以 SNI 本质上是「把 `Host` 头提前到 TLS 握手阶段」，做的是同一件事：**在服务端看到 HTTP 之前，先告诉它「我要访问哪个域名」**

> 💬 **面试官**：虚拟主机是怎么基于一个 IP 服务多个域名的？和 `Host` 请求头有什么关系？
>
> ✅ 标准答案：HTTP/1.1 起 `Host` 头是强制字段，每个请求都声明自己访问的域名。服务端/反向代理拿到请求后先读 `Host` 头，再路由到对应的站点配置（Nginx 里就是 `server_name`）。所以一个 IP 之所以能承载多个域名，就是因为「域名」这个信息被 `Host` 头从 IP 里独立出来了——IP 负责定位机器，`Host` 负责定位机器上的哪个站点。
>
> 🎁 加分答案：能补两点——① 没有 `Host` 头或匹配不到时，Nginx 走「默认 server」，这是「为什么访问 IP 会命中某个默认站点」的原因；② HTTPS 下读不到 `Host` 头（TLS 握手先于 HTTP），所以用 **SNI 扩展**在 ClientHello 阶段明文传域名来选证书，本质是把 `Host` 提前到握手阶段——能讲出 SNI 和虚拟主机的关系，说明你真正理解了「域名路由」这件事在 HTTP 和 HTTPS 两个阶段的区别。

## 三、负载均衡算法（重点 · 面试高频）

反向代理最核心的价值之一，就是把请求**分摊到多台后端**。Nginx 用 `upstream` 块定义一组后端，然后用不同的算法决定「这次请求给谁」。

负载均衡的本质一句话：**把一群请求，按某种策略，分摊到一群后端服务器上**。策略不同，适用的场景就完全不同。下面把五种最常见的算法逐个讲透，最后给一张对比表。

### ① 轮询（Round Robin）

最简单的策略：把后端排成一圈，请求依次分发，第一个给 A、第二个给 B、第三个给 C、第四个又回到 A……如此循环。

- **优点**：实现最简单，绝对公平——每个后端拿到的请求数一模一样
- **缺点**：完全无视后端之间的性能差异和实时负载。如果 A 是 8 核、B 是 2 核，两者拿到的请求一样多，B 会被压垮而 A 闲着

### ② 加权轮询（Weighted Round Robin）

轮询的改进：给每个后端一个 `weight` 权重，按权重分配请求比例。权重 3 的后端，平均每 4 个请求里分到 3 个。

- **优点**：解决了「机器性能不同」的问题——性能强的机器权重高、多承担请求
- **缺点**：权重是**静态配置**的，无法感知运行时的实时负载（一台机器临时变慢，权重不会自动降）

Nginx 里 `weight` 参数按权重分配请求比例：

```nginx
# 处方服务部署了 2 台机器，配置不同，按 3:1 分配请求
upstream rx_backend {
    server 127.0.0.1:8089 weight=3;   # 👈 这台性能强，承担 75% 请求
    server 127.0.0.1:8090 weight=1;   # 👈 这台弱一点，承担 25% 请求
}

server {
    listen 80;
    server_name rx.his.com;

    location / {
        proxy_pass http://rx_backend;   # 👈 转发到 upstream 组，自动负载均衡
    }
}
```

后端的两个服务分别返回自己的端口号（8089 / 8090），用 `curl` 反复请求，统计返回值的分布来验证 3:1：

```bash
# 反复请求 12 次，统计 8089 和 8090 出现的次数
for i in $(seq 1 12); do
  curl -s http://rx.his.com/ | grep -o '8089\|8090'
done
# 期望结果：8089 出现 9 次（weight=3）、8090 出现 3 次（weight=1），比例 3:1
```

### ③ IP 哈希（IP Hash）

对客户端的 IP 地址做哈希，用哈希结果决定落到哪台后端。同一个 IP 的哈希结果不变，所以**同一个客户端的请求永远落在同一台机器上**。

```nginx
upstream rx_backend {
    ip_hash;                            # 👈 开启 IP 哈希负载均衡
    server 127.0.0.1:8089;
    server 127.0.0.1:8090;
}
```

- **优点**：天然实现**会话保持（sticky session）**——不需要额外的 cookie 或共享存储，就能让同一用户的连续请求都打在同一台机器上，机器内存里的会话状态不会丢
- **缺点**（也是关键）：**某个后端下线时，该后端负责的那一段 IP 用户会「全部」切换到新后端**——因为哈希空间重新分配，原本落在下线机器上的所有用户，会话状态瞬间全丢。这是 IP 哈希最容易被追问的代价

为什么需要 `ip_hash`？因为某些业务状态存在单台机器的内存里（比如用户登录态、购物车），如果同一个用户的连续请求被轮询随机分到不同机器，状态就丢了。`ip_hash` 保证「同一 IP → 同一台机器」。

用同一个客户端连续请求验证：

```bash
# 用同一个客户端连续请求多次，观察返回值是否始终是同一个端口
for i in $(seq 1 5); do
  curl -s http://pt.his.com/
done
# 期望结果：5 次返回同一个端口（如全是 8091），说明 ip_hash 生效
```

### ④ 一致性哈希（Consistent Hashing）

IP 哈希的进化版，是理解「为什么长连接/缓存场景要它」的关键。它的核心设计是**环形哈希空间**：

```
把哈希空间排成一个环（0 ~ 2^32 - 1）：

                    ┌─────────────────────────┐
                    │       哈希环             │
                    │      (0 ~ 2^32-1)        │
                    │                          │
                    │    ● B（节点 B 的哈希位置）│
                    │   /    \                 │
                    │  /      \                │
                    │ ● A     ● C              │
                    │ (节点A)  (节点C)          │
                    │                          │
                    └─────────────────────────┘
```

具体做法分三步：

1. **后端节点映射到环上**：对每个后端的标识（如 IP + 端口）做哈希，得到一个环上的位置
2. **请求 key 也映射到环上**：对请求的关键字段（如客户端 IP、缓存 key）做哈希，得到环上的一个位置
3. **顺时针找最近节点**：请求 key 落在环上后，**顺时针方向遇到的第一个后端节点**，就是它要命中的那台机器

一致哈希相比 IP 哈希的关键优势，在于**扩缩容时的「影响范围」**：

- 普通哈希（IP 哈希属于这种）：后端数量一变，哈希取模的分母就变，几乎**所有 key 的映射关系都会变**——加一台机器，几乎所有请求都会重新分配，缓存/会话大面积失效
- 一致性哈希：加一台机器，只影响环上**它落点逆时针方向相邻那一小段**的请求——因为这些请求原本「顺时针找」会找到别家，现在被新节点截胡了，其余绝大部分 key 的映射不变

这个「扩缩容只影响相邻一小段」的特性，让一致性哈希成为**分布式缓存（如 Memcached/Redis 集群）和长连接负载均衡**的标准解法——加机器时不至于让缓存瞬间雪崩，减机器时只有一小部分请求受影响。

**那节点少的时候会不会分布不均？** 会，这就是「哈希倾斜」问题：如果只有 2 台机器，它们的哈希位置可能恰好都落在环的一侧，导致环的另一侧一大片区域的 key 都「顺时针」落到同一台，负载严重不均。解法是**虚拟节点**——给每个真实节点在环上放置多个虚拟副本（比如每个真实节点生成 100 个虚拟节点散落在环上），虚拟节点均匀分布后，key 落点就会均匀，倾斜就被抹平了。**「虚拟节点」是面试追问一致哈希时的高频加分点**。

呼应第 06 篇 WebSocket 的结论：长连接一旦建立，后续所有帧都要路由到同一个后端实例，所以「轮询」这种每次随机分配的策略对长连接是灾难——一致哈希/IP 哈希正是这里的「具体解法」。

### ⑤ 最少连接数（Least Connections）

实时统计每个后端**当前正在处理的连接数**，把新请求优先分发给**最空闲（连接数最少）**的那一台。

- **优点**：能感知实时负载——「连接多 = 忙」，动态把请求导向空闲机器，比静态的加权轮询更贴近真实负载
- **缺点**：连接数并不完全等于「忙的程度」（一个连接可能只是挂着不动，另一个连接在疯狂跑重计算），且实时统计本身有开销
- **适用场景**：请求耗时差异大、或长连接场景——因为长连接里「连接数」能比较真实地反映机器压力

### 五种算法对比

| 算法 | 分配策略 | 会话保持 | 适用场景 | 主要局限 |
|------|---------|---------|---------|---------|
| 轮询 | 依次循环 | 无 | 后端性能一致、无状态 | 无视性能/负载差异 |
| 加权轮询 | 按权重比例 | 无 | 后端性能不同 | 权重静态，不感知实时负载 |
| IP 哈希 | 按客户端 IP 哈希 | 天然保持 | 需会话保持的无状态服务 | 后端下线整段用户全切换 |
| 一致性哈希 | 环形空间顺时针找 | 按 key 保持 | 缓存集群、长连接 | 节点少时需虚拟节点防倾斜 |
| 最少连接 | 发给最空闲机器 | 无 | 耗时差异大、长连接 | 连接数≠真实繁忙度 |

用 `ab`（Apache Benchmark，或 `wrk`）压测，观察负载在多后端实例间的分发：

```bash
# 并发 10、总请求 100，压测处方服务
ab -n 100 -c 10 http://rx.his.com/
```

压测后，登录两台后端各自看访问日志（或统计计数器），能看到请求按 3:1 的比例被分发到 8089 和 8090——这就是「负载均衡」最直观的证据。

> 💬 **面试官**：常见的负载均衡算法有哪些？分别适用什么场景？
>
> ✅ 标准答案：轮询（依次循环，最简单公平）、加权轮询（按权重分配，适配机器性能差异）、IP 哈希（按客户端 IP 哈希，天然会话保持）、一致性哈希（环形哈希空间，扩缩容只影响相邻一小段，适合缓存集群和长连接）、最少连接数（实时统计连接数发给最空闲的，适合耗时差异大的场景）。
>
> 🎁 加分答案：能讲清**每条算法的代价**，而不只是背名字——① 轮询/加权轮询是无状态的，问题在于「会话状态存在机器内存」的场景下，同一用户连续请求被分到不同机器会丢状态；② IP 哈希能保持会话，但「后端下线会导致该 IP 段用户全部切换」，会话全丢；③ 一致性哈希的「扩缩容只影响相邻」正是为了解决「加机器导致缓存雪崩」，但节点少时要靠虚拟节点防哈希倾斜；④ 最少连接数适合长连接，因为长连接里「连接数」比「请求数」更能反映真实压力。能把「为什么」讲清楚，比把五种名字背全重要得多。

> 💬 **面试官**：为什么长连接场景的负载均衡更适合用一致性哈希或 IP 哈希，而不是普通轮询？
>
> ✅ 标准答案：长连接（如 WebSocket）一旦建立，后续所有帧都必须路由到**同一个后端实例**——如果每次按轮询随机分配，同一连接的后续帧会打到不同机器，而连接状态只存在最初那台机器上，直接导致连接失效。IP 哈希/一致性哈希能保证「同一个客户端/同一个 key 永远落到同一台机器」，所以是长连接的正确选择。
>
> 🎁 加分答案：能补充「一致性哈希比 IP 哈希更好在哪」——两者都能保持会话，但 IP 哈希在后端数量变化时会导致**大范围的 key 重新映射**（会话大面积失效），而一致性哈希的环形空间设计让扩缩容**只影响相邻一小段请求**。所以在「后端会动态增减」的长连接/缓存场景，一致性哈希是更优解；如果是「后端相对固定、只需简单会话保持」，IP 哈希配置更简单。

## 四、图片防盗链

### 1. 使用：`valid_referers` 与 Node.js 实现

很多时候，别的网站直接把你的图片资源拿去在他们的页面里展示，但消耗的是**你的带宽和流量**。防盗链就是要解决这个问题——只允许来自本站页面的请求访问图片，别的站点引用就拒绝。

Nginx 里用 `valid_referers` 指令，只允许来自本站域名的请求访问药品图片资源：

```nginx
server {
    listen 80;
    server_name drug.example.com;

    # 只允许空 Referer（如直接地址栏访问）和本站域名
    location ~* \.(png|jpg|jpeg|gif|webp)$ {
        valid_referers none blocked drug.example.com *.drug.example.com;
        if ($invalid_referer) {
            return 403;                 # 👈 非法来源直接 403
            # 或者 rewrite 到一张占位图：rewrite ^/ /forbid.png;
        }
    }
}
```

`valid_referers` 后面跟着的是「允许的来源白名单」：`none` 表示允许没有 `Referer` 头的请求（如直接输入图片 URL）、`blocked` 表示允许 `Referer` 被防火墙/代理清空的情况、`drug.example.com` 是本站域名。凡是 `Referer` 不在白名单里的，`$invalid_referer` 就为真，返回 403 或重定向到占位图。

笔记里也提供了 Node.js 的完整实现，思路完全一致——读 `Referer` 和 `Host` 做对比，不一样就返回一张「盗链提示图」：

```javascript
// index.js —— 防盗链：Referer 和 Host 不一致时返回占位图
let fs = require("fs");
let path = require("path");
let url = require("url");
const server = require("http");

/**
 * @description 解析host
 * @param {string} referStr 需要解析的refer字符串
 */
let getHostName = (referStr) => {
  let { hostname } = url.parse(referStr);
  return hostname;
};

// 白名单
let whiteList = ["b.gwb.com"];

const app = server.createServer((req, res) => {
  // 拿到refer
  let refer = req.headers["referer"] || req.headers["referrer"];

  // 判断是否又refer，有可能没有refer
  let { pathname } = url.parse(req.url);
  // p代表我们要找的文件
  let p = path.join(__dirname, "public", "." + pathname); // 这里是请求文件

  // 判断请求的文件有没有，没有的话直接结束，有的话在读取文件
  // 读取文件，返回给浏览器
  fs.stat(p, (err) => {
    if (!err) {
      if (refer) {
        // 先看一下refer的值，还要看图片的请求路径
        let referHostName = getHostName(refer);
        let host = req.headers["host"].split(":")[0];
        // 这里判断， referHostName ！= host
        // 白名单 加入判断 !whiteList.includes(referHostName)
        if (referHostName != host && !whiteList.includes(referHostName)) {
          // 防盗链
          fs.createReadStream(
            path.join(__dirname, "public", "./timg.png")
          ).pipe(res);
        } else {
          // 正常展示
          fs.createReadStream(p).pipe(res);
        }
      } else {
        // 正常展示
        fs.createReadStream(p).pipe(res);
      }
    } else {
      res.end();
    }
  });
});
app.listen(3000, () => {
  console.log(`server start port 3000`);
});
// 当服务器错误时调用
app.on("error", (err) => {
  if (err.code == "EADDRINUSE") server.listen(++port);
  if (err) console.log(err);
});

// 当服务器关闭时调用
app.on("close", () => {
  console.log("服务端关闭");
});
```

### 2. 原理与局限

防盗链的原理就是：服务端读请求头里的 `Referer`，判断请求是不是从本站页面发出来的，不是就拒绝。

但这一节要讲的是**它的局限**——这也是面试真正会挖的地方。

核心局限一句话：**`Referer` 完全可以被客户端伪造或清空**。

- **清空**：页面可以通过 `Referrer-Policy: no-referrer` 主动不发送 `Referer` 头；或者用 `<meta name="referrer" content="never">`（前面 `index.html` 里被注释掉的那行就是）；甚至浏览器插件、隐私模式都能让 `Referer` 消失
- **伪造**：客户端直接构造请求，把 `Referer` 头设成任意值（`curl -e "http://允许的域名"` 就能绕过）

所以，防盗链的本质是**一道「提高盗链成本」的墙，而不是可靠的安全边界**——它防的是「不懂技术的顺手盗链」，防不了「专门伪造 Referer 的爬虫」。

这个结论，和第 07 篇 CSRF 防御里「校验 Referer/Origin 只能作为辅助手段」是**同一个局限性的两种应用场景**：CSRF 里不能只靠 `Referer` 判断「是不是用户本人发起」，防盗链里不能只靠 `Referer` 判断「是不是本站页面发起」——因为它们都建立在「`Referer` 可信」这个脆弱的假设上，而 `Referer` 恰恰是最不可信的一个头。

> 💬 **面试官**：图片防盗链的原理是什么？它的安全性局限在哪里？
>
> ✅ 标准答案：原理是服务端检查请求头的 `Referer`，判断请求是否从本站页面发出，非本站（`Referer` 的域名和本站 `Host` 不一致）就拒绝，返回 403 或占位图。局限在于 `Referer` 完全可以被客户端伪造或清空——`Referrer-Policy: no-referrer` 能主动不发送，`curl` 也能伪造任意 `Referer`，所以它只是「提高盗链成本的墙」，不是可靠的安全边界。
>
> 🎁 加分答案：能点出它和 CSRF 防御的同源性——第 07 篇讲过「校验 Referer/Origin 只能作为 CSRF 的辅助手段」，和防盗链的局限是同一个根因：**都假设 `Referer` 可信，而 `Referer` 恰恰最不可信**。更进一步还能提出真正的加固方向：防盗链想要更强，要么配合**签名 URL**（图片地址带上带时效的签名参数，签不上名就 403），要么配合**访问频率限制/Token**，把「靠头判断」升级为「靠凭证判断」。

## 五、网关状态码 502 vs 504 + Node.js 对比

### 1. 502 vs 504（排障高频）

最后讲两个反向代理场景下最常见、也最容易被问倒的网关状态码：**502 和 504**。

它们都是「网关（反向代理）替上游服务器返回」的错误码，共同点是**问题出在上游，不在网关自己**。区别在「上游是返回了错误，还是根本没返回」：

- **502 Bad Gateway（错误网关）**：网关从上游服务器收到了一个**无效的响应**——比如上游进程崩溃、连接被拒绝、返回了格式错误的响应。关键词是「**上游返回了，但返回的是错的**」
- **504 Gateway Timeout（网关超时）**：网关在**等待上游响应时超时**——比如上游处理太慢、被压垮迟迟不返回。关键词是「**上游根本没返回**」

怎么记？**502 = 上游「答错了」，504 = 上游「没答」**。

排查的第一步（也是面试里最能体现工程经验的一句话）：**先 `curl` 直连上游，区分「网关的问题还是上游的问题」**——

- 如果 `curl` 直连上游也失败 → 问题在上游本身（进程挂了/太慢），去查上游日志、重启上游
- 如果 `curl` 直连上游正常、但走网关就 502/504 → 问题在网关（配置错了、上游地址填错、超时时间设太短）

这一步「二分定位」是网关排障的第一步，也是把问题范围砍掉一半的关键动作。502/504 和 05 篇讲过的 4xx 一起，构成完整的 4xx（客户端问题）/5xx（服务端问题）状态码体系。

用一套完整的 Nginx 配置，配合 `curl`/`ab` 做验证，把四个核心能力串起来：`proxy_pass`（反向代理）、`server_name`（虚拟主机）、`upstream`（负载均衡）、`valid_referers`（防盗链）：

```nginx
# 处方服务：两台后端，加权轮询
upstream rx_backend {
    server 127.0.0.1:8089 weight=3;
    server 127.0.0.1:8090 weight=1;
}

# 患者服务：两台后端，IP 哈希做会话保持
upstream pt_backend {
    ip_hash;
    server 127.0.0.1:8091;
    server 127.0.0.1:8092;
}

server {
    listen 80;
    server_name rx.his.com;

    location / {
        proxy_pass http://rx_backend;   # 反向代理 + 加权轮询负载均衡
    }
}

server {
    listen 80;
    server_name pt.his.com;

    location / {
        proxy_pass http://pt_backend;   # 反向代理 + ip_hash 会话保持
    }
}

server {
    listen 80;
    server_name drug.example.com;

    # 药品图片防盗链
    location ~* \.(png|jpg|jpeg|gif|webp)$ {
        valid_referers none blocked drug.example.com *.drug.example.com;
        if ($invalid_referer) {
            return 403;
        }
    }

    location / {
        proxy_pass http://127.0.0.1:8093;
    }
}
```

模拟后端宕机，直观看到网关状态码的产生：

```bash
# 1. 正常时，走网关请求处方服务，返回 200
curl -i http://rx.his.com/          # 200 OK

# 2. 停掉 8089 后端（模拟上游进程崩溃）
#    然后在 Nginx 配置里临时把 proxy_pass 指向一个不存在的端口（如 9999），
#    或者直接 kill 掉 8089 后端，重载 Nginx
curl -i http://rx.his.com/          # 502 Bad Gateway —— 上游连接被拒绝，返回了「无效响应」

# 3. 模拟上游「太慢不返回」：写一个 sleep 很久的后端，把 Nginx 的 proxy_read_timeout 调短
#    proxy_read_timeout 3s;
curl -i http://rx.his.com/          # 504 Gateway Timeout —— 上游 3 秒没返回，网关超时
```

这一步跑完，你会对「502 = 上游答错了、504 = 上游没答」有切身体会——它不再是背的，而是**亲手停掉一个后端看到的现象**。排查时那句「先 `curl` 直连上游」也在这里得到印证：直接 `curl http://127.0.0.1:8089/` 就能立刻判断「是网关的问题还是上游的问题」。

> 💬 **面试官**：502 和 504 分别代表什么？排查思路是什么？
>
> ✅ 标准答案：502 Bad Gateway 表示网关从上游收到了无效响应（上游进程崩溃、返回格式错误）；504 Gateway Timeout 表示网关等待上游响应超时（上游太慢、被压垮没返回）。共同点是「问题在上游」，区别是「上游返回了错误（502）」还是「上游根本没返回（504）」。
>
> 🎁 加分答案：能给出排查思路——**第一步先 `curl` 直连上游**：直连也失败，问题在上游本身（查进程、日志、重启）；直连正常但走网关失败，问题在网关（查 `proxy_pass` 地址对不对、`proxy_read_timeout` 超时时间是否太短）。这个「先二分定位在网关还是上游」的动作，比背状态码定义值钱得多。

### 2. 对比 Node.js：`http-proxy` 底层原理

最后落地到 Node.js，这是理解「反向代理到底做了什么」最直接的方式——把 `http-proxy` 的 `proxy.web` 源码拆开看。

笔记里给出了 `proxy.web` 的实现（简化版），核心就一行思路：**用 `http.request` 向后端发一个请求，再把后端的响应 `pipe` 回客户端的响应**：

```javascript
// proxy.web 的简化实现 —— 反向代理的底层就是一个「请求转发 + 响应回灌」
const http = require('http');
const url = require('url');

function web(req, res, options) {
  const {host, port, pathname: path} = url.parse(req.url);
  const {method, headers} = req;
  const opts = {
    host,
    port,
    method,
    path,
    headers
  }
  opts.host = options.target;
  http.request(opts, (response) => {
    response.pipe(res);
  });
}
```

这段代码揭示了反向代理的本质：**它不是一个「魔法」，而是「收一个请求 → 再发一个请求 → 把响应原样搬回去」**。Nginx 做的也是同一件事，只是用 C 写的、性能更高、封装了更多功能。

那问题来了：**什么场景该用 Nginx 做网关，什么场景可以直接在 Node.js 应用层做请求转发？** 这是个很有区分度的问题，答案是看这几个维度：

- **性能与稳定性**：Nginx 是 C 写的、事件驱动、专为高并发转发设计，处理纯转发能力远超 Node.js；Node.js 应用层转发要经过 JS 层，多一层开销。**纯转发、静态资源、SSL 终止**这些「通用能力」交给 Nginx 更稳
- **业务逻辑耦合**：如果转发时需要**动态计算目标、按业务规则改写请求/响应**（比如按用户等级路由到不同后端、按请求内容做灰度），这种「和业务强相关的转发逻辑」放在 Node.js 应用层更灵活，Nginx 的配置写起来会很别扭
- **热更新**：Nginx 改配置要 `reload`；Node.js 转发逻辑就是代码，随应用一起发布部署

一句话收口：**Nginx 负责「通用、高性能、稳定」的网关能力（反向代理、负载均衡、静态资源、SSL），Node.js 负责「业务相关的转发逻辑」**。理解了两者的边界，就不会在架构评审时「什么都塞进 Nginx」或「什么都自己写转发」了。

> 💬 **面试官**：反向代理的底层原理是什么？什么场景该用 Nginx、什么场景用 Node.js 自己转发？
>
> ✅ 标准答案：反向代理的底层就是「收一个请求 → 用 `http.request`（Nginx 则是内部事件循环）向后端再发一个请求 → 把后端响应 `pipe` 回客户端」。Nginx 适合纯转发、静态资源、SSL 终止、负载均衡这类「通用、高性能、稳定」的能力；Node.js 应用层转发适合「按业务规则动态路由、改写请求/响应」这类和业务强耦合的逻辑。
>
> 🎁 加分答案：能点出「转发时对头部的处理」这个易错细节——反向代理转发时，`Host` 头通常要改写成后端地址、真实客户端 IP 要塞进 `X-Forwarded-For`、还要处理 `Connection`/`Upgrade` 头（WebSocket 升级转发必须正确透传这两个头，否则升级失败）。能提到「长连接升级要透传 `Connection: Upgrade`」说明你真的写过反向代理，不只是看过配置。

|--------|-----------|---------|
| 正向 vs 反向代理 | 正向代理客户端（对服务端透明），反向代理服务端（对客户端透明），本质是「代理谁、对谁透明」 | ⭐⭐⭐ 必考 |

> 💡 记住这条主线：**反向代理是站在集群最前面的「唯一入口」，它靠 `Host` 头决定「请求去哪个站点」（虚拟主机），靠负载均衡算法决定「站点内去哪台机器」（轮询→加权→IP 哈希→一致性哈希→最少连接），靠 `Referer` 保护资源（防盗链），而上游一旦出问题，就体现为 502（答错）/504（没答）**。把这条线串起来，网关相关的所有面试题都能从原理推到答案。
