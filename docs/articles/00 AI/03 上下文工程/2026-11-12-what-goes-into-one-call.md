# 上下文组装：一次调用里放了什么、各占多少（面试收藏级）

> 你以为是把「一个问题」发给模型，实际是把一整张桌子摊到了它面前——System Prompt 压在桌面最上角，几十轮聊天记录堆成一摞，检索出来的药品说明书、工具的调用说明、工具刚吐回来的一大段 JSON，全都摊在上面。模型并没有「只读」你最后问的那句话，它读的是这一整张桌子。而桌子的面积，是要按 token 付费、而且有上限的。token 是什么、怎么数，我在阶段一《从 Token 到上下文窗口》里已经拆解过，这篇默认你懂它，只聚焦一件事：这张桌子到底该怎么摆。

---

## 🎯 这篇文章解决什么问题

写了大半年 AI 应用，你大概率踩过这三类坑，而且常常说不清原因：

- **token 越用越多**：一个简单的问答接口，跑着跑着单次请求的 token 数翻了十倍，账单跟着涨，你却不知道钱花在哪一段上。
- **加了一段「无关」历史，答案反而错了**：明明多给了模型上下文，它却开始把话题带偏，甚至编出上下文里根本不存在的结论。
- **同样的内容换个顺序，效果天差地别**：一段关键资料放在开头模型能答对，塞到中间它就「看不见」了。

这三个坑，指向的是同一个能力——**上下文组装（Context Assembly）**。

一句话定义：**上下文组装 = 决定「有限的上下文窗口里，放什么、放多少、按什么顺序放」。**

它是「上下文工程（Context Engineering）」这条主线里的第一道工序，也是所有 RAG、Agent、多轮对话系统绕不开的地基。这篇文章会带你由浅入深走完三件事：

1. 一次调用里到底「塞」了几类内容；
2. 每类内容各占多少 token（附实测预算表）；
3. 顺序和采样方式如何悄悄影响结果（附对照实验）。

## 🔍 概念：一次调用，你到底「发」了什么

先别急着看代码。我们把「一次 API 调用」想象成**往模型的桌子上摆卡片**。不同的系统摆的卡片不一样，但绝大多数 AI 应用，一次调用里会有下面六类卡片。

![一次调用把上下文窗口切分成六块：对话历史占 47.6%，工具返回占 16.4%，检索片段占 13.8%，System Prompt 占 11.2%，工具描述占 7.6%，用户当前输入只占 3.5%——真正「你说的话」往往只占整个请求的一小角。](https://jianda-cmsstatic.oss-cn-shenzhen.aliyuncs.com/assets/charts/202611/1794473525400_meeru7o8pp.png)

### 六类卡片，一张桌子

**① System Prompt（系统提示词）**——桌面上永远压在最上面的那张「规则卡」。它定义模型的角色、边界、输出格式。每次调用都原样带着，且几乎不变。

**② 对话历史（History）**——之前所有轮次的「你问我答」记录。多轮对话做得越久，这摞卡片越厚，而且是**每次调用都全量重发一遍**的。

**③ 检索片段（RAG Chunks）**——从向量库里检索出来的相关资料，比如药品说明书片段、文档段落。这是 RAG 系统的核心卡片。

**④ 工具描述（Tool Definitions）**——告诉模型「你有这些工具可以用」的函数签名与参数说明。Agent 系统里几乎必带。

**⑤ 工具返回结果（Tool Results）**——模型调完工具后，工具吐回来的结构化数据。比如查药品相互作用的接口返回的一段 JSON。

**⑥ 用户当前输入（User Input）**——就是这一轮你真正打出来的那句话。

看到这张表你可能已经明白了：**你打的那句话，只是桌子上的最后一张小卡片**。真正吃掉窗口的，是前面五张。

### 拼起来长什么样

把六类卡片拼装成一次真实请求，就是一段 `messages` 数组。下面是简化后的完整结构（医疗用药咨询场景，本系列实验统一用 TypeScript 表达）：

```typescript
// 一次调用的完整请求体（节选，六类内容都在里面）
type Message = { role: string; content: string }

const messages: Message[] = [
  { role: 'system',    content: '你是审慎的用药咨询助手，不得凭空推测剂量与禁忌……' },          // ① System Prompt
  { role: 'user',      content: '我最近感冒了，能吃退烧药吗？' },                             // ② 对话历史
  { role: 'assistant', content: '可以，但需先确认你的年龄、有无肝肾疾病……' },               // ② 对话历史
  { role: 'user',      content: '【检索资料】对乙酰氨基酚：成人一次 0.3~0.6 g……' },            // ③ 检索片段
  { role: 'assistant', content: '[工具调用] query_drug_interaction(缬沙坦, 布洛芬)' },      // ④ 工具描述 + 调用
  { role: 'tool',      content: '{"severity":"moderate","advice":"建议避免联用……"}' },        // ⑤ 工具返回结果
  { role: 'user',      content: '那我发烧到 38.5 度，能同时吃退烧药吗？' },                    // ⑥ 用户当前输入
]
```

> 💬 **面试官**：一次 LLM 的 API 调用里，除了用户问题，通常还混着哪些内容？
>
> ✅ **标准答案**：System Prompt、对话历史、检索片段、工具描述、工具返回结果、用户当前输入，六类。多轮对话和 Agent 系统里，历史和工具相关的内容往往才是大头。
>
> 🎁 **加分答案**：还能列举两种可选的扩展卡片——**Few-shot 示例**（把示例拼进 System Prompt）和**长期记忆**（从记忆库捞出的用户画像）。它们本质都是「上下文」，都要占 token，也要纳入预算管理。

## ⚙️ 深入一：先把「尺子」亮出来——数 token 用的工具

「占多少」的前提是能「数出来」。上下文不是按「字」算的，是按 **token** 算的——token 是什么、BPE 怎么分词、为什么中文比英文贵，这些我在阶段一《从 Token 到上下文窗口》里已经从头拆过，这里不重复，只交代这篇实验用的两把「尺子」：

- **预算表用 `gpt-tokenizer`**（tiktoken 的 TS 实现，纯本地跑、零 API 调用）——本系列实验统一用 TypeScript，数 token 也是；
- **顺序对照实验用真实模型**（deepseek-chat），看采样方式如何影响命中率。

为什么用 TS 而不是 Python？本项目的实验代码都放在 `labs/` 里统一用 TypeScript 维护，和阶段一的 token 实验、阶段二的 SSE 实验共用一套工具链。`gpt-tokenizer` 一行就能数：

```typescript
import { countTokens } from 'gpt-tokenizer'

const userInput = '示例药 X-7 与抗凝药 W 的相互作用风险等级是几级？只回答等级，不要解释。'
countTokens(userInput)   // 👈 28，正是下面预算表里「用户输入」那一行的数字
```

> 💬 **面试官**：中文场景做 token 预算，最容易犯的错是什么？
>
> ✅ **标准答案**：**按字数估、不按 token 数**。中文一个汉字常占 1~2 个 token，同样字数下中文的 token 数比英文多一倍以上（阶段一有实测），照抄英文教程的比例会系统性低估预算。
>
> 🎁 **加分答案**：能进一步说出——正因为中英差异大，预算上限要**按 token 设**，截断也要用分词器的 `encode`/`decode` 来切，而不是字符串切片；按字符硬切可能把一个多字节 token 拦腰截断。

## ⚙️ 深入二：各占多少——Token 预算表

知道了怎么数，接下来看一个真实问题：**一次调用，钱到底花在哪一段上？**

我构造了一次贴近生产的用药咨询场景——含 System Prompt、12 轮对话历史、3 段检索资料、2 个工具描述、1 段工具返回，用 `gpt-tokenizer` 逐类统计（2026-11-12 实测，脚本见文末实验）：

| 类别 | token 数 | 占比 |
|---|---|---|
| System Prompt | 90 | 11.2% |
| **对话历史** | **384** | **47.6%** |
| 检索片段 | 111 | 13.8% |
| 工具描述 | 61 | 7.6% |
| **工具返回结果** | **132** | **16.4%** |
| 用户当前输入 | 28 | 3.5% |
| **合计** | **806** | **100%** |

![一次调用的六类内容按 token 数排开：对话历史 384、工具返回 132、检索片段 111、System Prompt 90、工具描述 61、用户输入 28——历史与工具返回合计吃掉约六成窗口，才是预算失控的主犯。](https://jianda-cmsstatic.oss-cn-shenzhen.aliyuncs.com/assets/charts/202611/1794473527756_dl9e37ci848.png)

这张表藏着三个反直觉的结论，面试高频：

**结论一：真正的你，只占 3.5%。** 你打的那句话 28 个 token，是整个请求的零头。模型「读」的成本绝大部分花在了它自己之前说过的话、工具吐回的数据上。

**结论二：历史 + 工具返回，合计 64.0%，是预算失控的头号主犯。** 对话历史 47.6% + 工具返回 16.4%，加起来接近三分之二。多轮对话每多一轮，历史就全量重发一遍；Agent 每调一次工具，返回结果就整段塞回上下文。这两个是「指数级膨胀」的源头。

**结论三：检索片段反而不是大头。** 很多人以为 RAG 的检索最烧钱，实测它只占 13.8%。因为它通常会被截断到固定长度（比如每段 160 字），是「有上限的」；而历史和工具返回是「无上限累积的」。

> 💬 **面试官**：一个 RAG + 工具的 Agent 应用，token 预算最容易失控的是哪部分？为什么？
>
> ✅ **标准答案**：对话历史和工具返回结果。历史随轮次线性增长且每轮全量重发，工具返回是整段 JSON 塞回上下文。两者合计常超六成，且没有天然上限。
>
> 🎁 **加分答案**：能指出「检索片段有截断上限、反而可控」这一反直觉点；并进一步说明——正因如此，压缩和预算管理的优先级应该是「先掐历史和工具返回」，而不是先去抠检索。

## ⚙️ 深入三：预算配额——先定配额，再往里装

既然窗口是有限的、钱是按 token 花的，正确姿势不是「装到哪算哪」，而是**先给每一类卡片定一个配额上限，再往里装**。

这就是「预算配额（Token Quota）」。典型做法是给六类内容各设一个上限，比如：

```typescript
// 预算配额：先定上限，再往里装
type BlockKind = 'system' | 'history' | 'rag' | 'toolDesc' | 'toolResult' | 'user'
type Quota = Partial<Record<BlockKind, number>>   // 每一项都可选，没写的那一类不截断

const QUOTA: Quota = {
  system:      400,   // System Prompt 固定，通常不超
  history:     800,   // 对话历史：超了就压缩/滑窗（后续篇讲）
  rag:         600,   // 检索片段：每段截断 + 限制段数
  toolDesc:    300,   // 工具描述：精简参数说明
  toolResult:  500,   // 工具返回：超了做字段裁剪
  user:        200,   // 用户输入：一般不截
}
```

超了配额，只有三条路，对应三个动词：

- **截断 truncate**：物理上切掉超出部分。最快，但会丢信息。
- **压缩 compress**：把「长原文」换成「短摘要」，比如把 8 轮历史摘要成 3 行。保信息但慢、可能失真。
- **精简 prune**：按重要性丢弃，比如工具返回里只保留 `severity` 和 `advice` 两个字段，扔掉 `source`、`latency_ms` 这些噪音字段。

组装器做起来也很直接：**先按 token 截断，再按顺序拼装**。核心是「按 token 切，而不是按字符切」：

```typescript
import { encode, decode } from 'gpt-tokenizer'

// 按 token 截断（用分词器切，不按字符硬切）
function truncateTo(text: string, maxTokens: number): string {
  const ids = encode(text)
  if (ids.length <= maxTokens) return text
  return decode(ids.slice(0, maxTokens))        // 👈 按 token 切片后再解码
}

// 组装：固定顺序 + 逐类套配额
function assemble(blocks: Array<{ kind: BlockKind; content: string }>, quota: Quota) {
  const parts: string[] = []
  for (const { kind, content } of blocks) {
    const limit = quota[kind]
    parts.push(limit != null ? truncateTo(content, limit) : content)  // 👈 每类先截到配额内
  }
  return parts.join('\n\n')                                          // 再按序拼起来
}
```

> 💬 **面试官**：上下文超预算时，截断、压缩、精简三者的区别和取舍是什么？
>
> ✅ **标准答案**：截断是物理切割、最快但丢信息；压缩是摘要化、保信息但慢且可能失真；精简是按重要性丢弃字段。工程上通常「截断保底、压缩降量、精简去噪」三者配合。
>
> 🎁 **加分答案**：能指出一个关键设计原则——**组装器本身只做「排序 + 截断」，真正的压缩算法（摘要、滑窗）是另一层**。职责分离后，预算配额就是触发压缩的「开关」，而不是把压缩逻辑硬塞进组装器。

## ⚙️ 深入四：顺序影响——Lost in the Middle

放什么、放多少解决之后，还剩最后一个变量：**顺序**。

模型的注意力在长上下文中是**不均匀的**。学界有一个著名结论，来自 2023 年斯坦福那篇论文《Lost in the Middle》——把「能回答问题的那段关键信息」放在上下文的不同位置，模型的准确率会画出一条 **U 形曲线**：

![相关段落放在不同位置，模型准确率呈 U 形：放最前约 78%、放最后约 79%，放到中间只有约 50%——开头（首因偏差）和结尾（近因偏差）记得牢，中间最容易「看不见」。](https://jianda-cmsstatic.oss-cn-shenzhen.aliyuncs.com/assets/charts/202611/1794471998719_m8gfsc2ulxr.png)

翻译成工程语言，就是两条纪律：

1. **关键信息放头尾**：最重要的约束、最新的检索结论，别埋在中间。
2. **稳定内容放最前**：System Prompt 这类每次调用都一样的卡片，永远放在最前、永不挪动。

第二条背后藏着一个更深的收益，是很多面试官的追问点：**顺序不仅服务「注意力」，还服务「缓存」**。主流模型的 Prompt Caching 是**按前缀匹配**的——只有从开头起连续不变的内容才能命中缓存。所以「稳定内容放最前」这一条顺序，同时满足了两个目标：**注意力上让稳定规则不抢关键位置的注意力，成本上让不变的前缀最大化命中缓存**。

> 💬 **面试官**：为什么关键信息要放头尾，而不是中间？这和「缓存友好」怎么统一？
>
> ✅ **标准答案**：模型存在首因偏差（开头记得牢）和近因偏差（结尾记得牢），中间的信息最容易被忽略，这就是 Lost in the Middle。工程上把关键信息放头尾。
>
> 🎁 **加分答案**：能进一步说出「稳定内容放最前」同时服务缓存——Prompt Caching 按前缀匹配，不变的内容放最前才能命中缓存；于是**一条顺序同时服务「注意力」和「成本」两个目标**，这是上下文组装里最漂亮的设计点之一。

## 🧪 动手实验

纸上谈兵不算数。下面两个实验，一个零成本本地跑，一个花几毛钱调真实模型。

> **说明**：实验代码与数据来自本仓库 `labs/phase3-context/02-context-assembly/`，模型 `deepseek-chat`。预算表用 `gpt-tokenizer` 本地统计、零 API 调用；顺序对照实验 24 次调用，约 ¥0.5。（2026-11-12 实测）

### 实验 A：Token 预算表（本地，零成本）

上文「深入二」那张占比表就是这个实验的产出。完整脚本只有十几行：`buildBlocks()` 定义六类文本 → 用 `gpt-tokenizer` 逐类 `countTokens` → 统计并打印占比。任何人复制下来就能数自己的上下文：

```typescript
// labs/phase3-context/02-context-assembly/ —— 实验 A 核心逻辑（节选）
import { countTokens } from 'gpt-tokenizer'
import { buildBlocks } from './fixtures.ts'   // 六类内容：System + 12 轮历史 + 3 段检索 + 2 个工具描述 + 1 段工具返回 + 用户输入

const blocks = buildBlocks()
const total = blocks.reduce((sum, b) => sum + countTokens(b.content), 0)

for (const { kind, content } of blocks) {
  const n = countTokens(content)
  console.log(`${kind.padEnd(12)} ${String(n).padStart(5)}  ${((n / total) * 100).toFixed(1)}%`)   // 👈 逐类占比
}
```

结论已经在上面：**历史 + 工具返回 ≈ 64.0%，是预算失控的主犯**。

### 实验 B：顺序对照实验里的「隐藏变量」——temperature

先说清楚这个实验**在验证什么、不在验证什么**。

「关键信息放头尾」这件事，我在阶段一已经用 needle-in-a-haystack（9 格矩阵）亲手复现过：把唯一一条事实埋进 5k/20k/80k 的干草堆的头/中/尾，中间列 3 次只中 1 次。那才是位置效应的干净证据。

这个实验补的是**方法这一课**：做顺序对照实验，有个变量不掐住，你测到的根本不是「位置」，是「采样随机性」——它就是 **temperature**。

构造 26 段「示例药 X-7 与抗凝药 W 相互作用」的档案，其中只有一段是「3 级（高）」，其余 25 段是 1/2 级的干扰段。把这段「3 级」分别放在**头部（第 1 段）、中间（第 13 段）、尾部（第 26 段）**，每种采样方式各跑 4 轮，看模型能不能锁定那份「3 级」：

![顺序对照实验的命中率：temperature=0 与默认采样在头/中/尾三个位置全部命中（各 4 轮全中）——小样本下采样漂移是「偶发」不是「必然」，不能拿它当位置效应的证据。](https://jianda-cmsstatic.oss-cn-shenzhen.aliyuncs.com/assets/charts/202611/1794473813622_gu6ylh4rt89.png)

本轮实测命中率（4 轮，2026-11-12）：

| 采样方式 | 关键段在头部 | 关键段在中间 | 关键段在尾部 |
|---|---|---|---|
| temperature = 0 | 4/4 | 4/4 | 4/4 |
| 默认采样 | 4/4 | 4/4 | 4/4 |

这一轮，两行全中，没有任何漂移。**这本身也是证据**——而且比「恰好中间丢一次」更能说明问题：

### 实验 C（加分）：temperature 为什么是隐藏变量

看这张全中的表，很容易得出「位置根本不影响」的结论。但这是个陷阱。

`temperature=0` 是**贪心解码**，每步都选概率最高的 token，把「模型对某个位置其实没那么有把握」这件事整个藏了起来——它就算对中间那份「3 级」信心不足，也会硬着头皮每次都给出同一个答案。而默认采样下，这种信心不足才会以「有时答对、有时答错」的形式偶尔显形。

但注意：**「偶尔」的意思是——跑一轮一个样**。26 段相似档案这个规模下，默认采样的漂移是偶发的，不是必然的；这一轮它没漂，下一轮可能就漂在中间或别的某个位置。样本只有 4 轮，谁拿它去下「位置效应」的结论，谁就是在拿随机性当规律。

所以一条铁律：**做顺序、编排、Prompt 这类对照实验，temperature 是必须显式控制的变量**；不掐住它、轮数又不够，你测到的不是「位置」，是「采样随机性」。位置效应的干净结论，得靠阶段一 needle 实验和 Lost in the Middle 论文那种「多轮 + 分层」的设计。这是面试里最能拉开差距的一个点。

> 💬 **面试官**：如果让你设计实验证明「关键信息放头尾更有效」，你会怎么设计？
>
> ✅ **标准答案**：控制变量——固定上下文内容、固定模型，只改变关键信息的位置（头/中/尾），每组多轮采样，统计命中率。
>
> 🎁 **加分答案**：能主动补上「必须先把 temperature 固定（甚至设为 0）」这一条，并解释原因——贪心解码会掩盖信心不足，默认采样才能让位置效应显形；不控制采样，实验结论会被随机性污染。

## 🚧 总结与边界

把整篇文章收成三句话：

1. **一次调用里有六类内容**：System、历史、检索、工具描述、工具返回、用户输入。你的那句输入只是零头。
2. **预算失控的主犯是「历史 + 工具返回」**（实测合计 64.0%），不是检索片段；所以预算配额要先掐这两类。
3. **顺序影响效果，且要服务两个目标**：关键信息放头尾（注意力），稳定内容放最前（缓存）。

而**上下文组装本身，只做两件事：排序 + 截断**。它不该把压缩算法、缓存策略这些复杂逻辑都吞进去——那些是「压缩」「缓存」两个独立课题，各有各的活儿。

这篇文章的边界同样要讲清楚：**怎么压缩历史（摘要、滑窗）、怎么做跨会话记忆、Prompt Caching 的完整原理和成本账**，都属于更深的课题，不是「组装」这一环要解决的事，留到后续单独展开。
