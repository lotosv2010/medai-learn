## 各篇详细大纲

### 第 01 篇：为什么前端也需要算法？React Fiber/虚拟 DOM/事件队列里的数据结构

**副标题**：从真实前端源码切入，看懂工程背后的数据结构选型逻辑

> 本篇为导读，采用「认知驱动」专用骨架，不套七步骨架。

#### 一、你写的 React/V8 代码里，处处是数据结构

- React Fiber 架构：每个组件对应一个 FiberNode，通过 `child/sibling/return` 三个指针构成链表+树的混合结构——为什么不用普通数组？因为链表可以在任意位置暂停和恢复，支持时间分片
- 虚拟 DOM diff：React 的 reconcile 算法本质是树的层序遍历 + 双指针对比子节点列表——为什么同层对比？因为跨层移动 DOM 代价极高，这个工程妥协把 O(n³) 降为 O(n)
- 浏览器事件循环：macrotask 队列（FIFO 队列）+ microtask 队列（优先级更高的 FIFO）+ 渲染时机——为什么 `Promise.then` 比 `setTimeout` 先执行，本质是两个不同优先级的队列调度
- V8 引擎的数组优化：JS 数组底层根据内容分为 `PACKED_SMI_ELEMENTS`（连续整数）、`PACKED_ELEMENTS`（连续混合类型）、`HOLEY_ELEMENTS`（含空洞）等多种内部类型，访问性能差距可达 5 倍以上

#### 二、数据结构与算法到底是什么

- 数据结构是"组织数据的方式"，算法是"操作数据的步骤"——两者共同决定了一段代码的时间/空间成本
- 抽象数据类型（ADT）：接口（什么操作）与实现（怎么存储）分离，同一个 ADT 可以有多种实现，性能特征各不相同（如"队列"可以用数组或链表实现，但摊还复杂度不同）

#### 三、前端为什么尤其需要

- 浏览器主线程单线程、JS 执行时间直接影响帧率（16.6ms/frame）、内存受限——这些约束让数据结构选型的权衡与服务端有所不同
- 前端不是"数据结构用得少"，而是"数据结构藏得深"：DOM、虚拟 DOM、事件循环、缓存、路由、依赖图，处处是栈/队列/链表/树/图/散列表

#### 四、本系列怎么学

- 16 篇学习地图：导读 → 复杂度分析 → 线性结构（栈/队列/链表/集合与散列表）→ 非线性结构（树/堆/图）→ 算法基础（排序/搜索/递归）→ 设计思想（分治/动态规划/贪心/回溯）
- 刷题方法：分类练习（一段时间只练一个类型）→ 总结套路 → 定期回顾；建议 300 题以上，先从《剑指offer》再刷 LeetCode 简单/中等，不在一开始啃刁钻 hard 题

#### 五、总结：重点难点

- 数据结构：**链表和树**跟前端最相关
- 算法：链表/树/图的遍历、数组的排序和搜索（面试）
- 设计思想：**分而治之、动态规划**比较常考，贪心、回溯次之

**面试核心问**：
- React Fiber 为什么用链表而不是普通树？链表在这里解决了什么问题？
- 虚拟 DOM diff 为什么只做同层对比？这个限制带来了什么代价？
- JS 数组的底层实现是真正的数组吗？打空洞会发生什么？
- microtask 和 macrotask 的调度顺序是怎样的？为什么 Promise 比 setTimeout 先执行？

### 第 02 篇：时间与空间复杂度：从前端代码瓶颈到 Big-O 分析体系

**副标题**：用 performance.now 实测 O(n) vs O(n²) 的增长曲线，建立前端性能直觉

#### 一、场景切入：为什么 includes 比 Set.has 慢 100 倍

- 真实前端瓶颈：`Array.includes` 在大列表里是 O(n)，换成 `Set.has` 是 O(1)——药品搜索列表去重场景，10 万条数据下两者耗时差 100 倍以上
- 深克隆的隐患：递归深克隆对深层嵌套对象是 O(n·d)（n 是节点数，d 是深度），医疗表单保存时频繁触发深克隆会直接卡帧
- 循环嵌套陷阱：两层 `for` 循环渲染处方-药品关联关系，n 个处方 × m 种药品 = O(n×m)，超过千条数据后 TTI 肉眼可见

#### 二、复杂度是什么

- 数据结构和算法解决的是"如何让计算机更快时间、更省空间地解决问题"
- 从执行时间和占用空间两个维度评估性能，分别对应时间复杂度和空间复杂度，统称复杂度
- 复杂度描述的是算法执行时间（或占用空间）与数据规模的增长关系

#### 三、大 O 表示法

- `T(n) = O(f(n))`、`S(n) = O(f(n))`：T/S 分别代表总时间/总空间，f(n) 代表代码执行总次数
- 为什么忽略常量、低阶、系数：时间复杂度只看增长趋势，n 足够大时它们不决定性作用
- **补全 O / Ω / Θ 三者区分**：O 是上界（最坏情况）、Ω 是下界（最好情况）、Θ 是紧确界（平均情况）——面试中说"这个算法是 O(n log n)"默认指最坏情况

#### 四、时间复杂度分析四法则

- 只关注循环执行次数最多的一段代码
- 加法法则：总复杂度等于量级最大的那段代码的复杂度
- 乘法法则：嵌套代码的复杂度等于内外代码复杂度的乘积
- 多规模求加法/乘法：`cal(m, n)` 两个参数分别控制循环 → O(m+n) / O(m*n)

#### 五、常见复杂度阶（逐个 + 代码 + 曲线）

- 多项式阶：O(1) 常数 / O(logn) 对数（忽略底数）/ O(n) 线性 / O(nlogn) 线性对数 / O(n²) 平方 / O(n³) 立方
- 非多项式阶：O(2ⁿ) 指数 / O(n!) 阶乘——n 稍大即爆炸，非常低效
- 增长速度：O(1) < O(logn) < O(n) < O(nlogn) < O(n²) < O(n³) < O(2ⁿ) < O(n!) < O(nⁿ)
- 操作数量实例表：15→O(1)、3n+5→O(n)、2ⁿ+1→O(2ⁿ) 等

#### 六、时间复杂度类型

- 最好情况 / 最坏情况 / 平均情况（加权平均 = 期望时间复杂度）
- **均摊时间复杂度（面试重点）**：绝大多数情况低复杂度、个别高复杂度且有顺序关系时，把高复杂度均摊到低复杂度——`Array.push` 均摊 O(1) 即此

#### 七、空间复杂度：递归到底占不占内存

- `S(n) = O(f(n))`，看申请的额外存储空间随 n 的增长关系
- 常见：O(1) / O(n) / O(n²)；O(logn) 很少见
- **递归调用栈占用的内存也计入空间复杂度**（每次递归调用 push 一个栈帧）

#### 八、复杂度与性能：怎么用复杂度定位瓶颈

- 用复杂度分析指导优化（替代"复杂度的优化"这个虚章）：把 O(n) 的累加改成 `n*(n+1)/2` 的 O(1)，`console.time` 实测对比

**面试核心问**：
- O(n log n) 和 O(n²) 在 n=10000 时实际差多少倍？
- Array.push 的时间复杂度是 O(1) 还是 O(n)？为什么？
- 如何分析一个递归算法的时间复杂度？
- 空间复杂度里的"递归调用栈"算在哪里？
- 大 O、大 Ω、大 Θ 三者有什么区别？

### 第 03 篇：栈：浏览器调用栈/undo 历史/单调栈高频题型全解

**副标题**：LIFO 的本质与单调栈的剪枝思想，拆解 LeetCode 高频栈题

#### 一、场景切入：调用栈溢出与 undo/redo

- 浏览器调用栈：JS 引擎用栈追踪函数调用，每次调用 push 一个执行上下文，返回时 pop——栈溢出（Maximum call stack size exceeded）就是这个栈满了
- undo/redo 实现：富文本编辑器（如医疗病历系统）的撤销历史天然是两个栈，undo 栈存操作历史，redo 栈在撤销时接收操作

#### 二、栈是什么

- 后进先出（LIFO）：最后入栈的元素最先出栈
- JS 中没有栈，但可以用 Array 实现栈的所有功能（`push`/`pop` 天然就是栈顶操作）

#### 三、核心操作

- push（入栈）/ pop（出栈）/ peek（查看栈顶 `stack[stack.length - 1]`）均 O(1)
- 关键代码片段（数组模拟栈，不贴完整类 + 测试）

#### 四、经典场景

- 十进制转二进制：余数后算出来却要排前面，入栈再出栈即倒序
- 有效括号：越靠后的左括号对应的右括号越靠前，左括号入栈、遇右括号出栈匹配
- 函数调用堆栈：最后调用的函数最先执行完

#### 五、单调栈（高频考点）

- 维护栈内元素单调递增/递减，新元素破坏单调性时出栈并处理——每个元素最多入栈/出栈一次，O(n) 而非 O(n²)
- 适用场景：找每个元素左/右侧第一个更大/更小值（Next Greater Element 系列）

#### 六、高频题精讲

- 20 有效括号（栈匹配）
- 155 最小栈（O(1) 获取最小值，用辅助栈/存差值）
- 739 每日温度（单调栈 vs 暴力 O(n²) 对比）

**LeetCode 重点题**：20（有效括号）/ 155（最小栈）/ 739（每日温度）/ 84（柱状图最大矩形）/ 85（最大矩形）

#### 七、前端工程落地

- ECMA-262 执行上下文栈：规范 §8.3 里的 Execution Context Stack 就是 JS 调用栈，栈在语言规范层面的直接体现
- React ErrorBoundary 的栈追踪：`ReactFiberWorkLoop.js` 捕获错误时沿 `fiber.return` 链追溯组件栈——用 Fiber 链表模拟可中断的"调用栈"

### 第 04 篇：队列：事件循环任务队列/BFS/双端队列与滑动窗口

**副标题**：FIFO 结构在浏览器事件循环与图搜索中的两种核心用法

#### 一、场景切入：setTimeout 和 Promise 谁先执行

- 浏览器 macrotask/microtask 队列：`setTimeout` 回调进 macrotask 队列，`Promise.then` 进 microtask 队列——每次事件循环执行一个 macrotask 后清空全部 microtask，这就是两者执行顺序差异的直接原因
- `setTimeout(() => console.log(1), 0); console.log(2);` → 输出 2 再 1

#### 二、队列是什么

- 先进先出（FIFO）：最先入队的元素最先出队
- JS 中没有队列，但可以用 Array 实现（push 入队 / shift 出队）
- 经典场景：食堂排队 / JS 异步任务队列 / 计算最近请求次数

#### 三、核心操作与实现陷阱

- enqueue（push）/ dequeue（shift）/ peek（queue[0]）
- **为什么 shift 是 O(n)**：数组头部删除需搬移后续所有元素
- **循环队列**：用头指针而非 shift，`head = (head + 1) % capacity` 实现复用，避免假溢出

#### 四、双端队列 Deque

- 两端均可入队/出队
- 滑动窗口最大值（LeetCode 239）的标准解法：单调双端队列，O(n) 解决 O(n²) 暴力

#### 五、优先队列（引出堆）

- 按优先级出队而非入队顺序，本质是堆，在第 08 篇展开

#### 六、高频题精讲

- 232 用栈实现队列
- 239 滑动窗口最大值（双端队列）
- 102 二叉树层序遍历（BFS 队列）

**LeetCode 重点题**：232（用栈实现队列）/ 641（设计循环双端队列）/ 239（滑动窗口最大值）/ 102（二叉树层序遍历）

#### 七、前端工程落地

- HTML 规范 Event Loop 任务队列：task queue 是"集合"而非严格 FIFO（允许特定情况跳过任务），与直觉的细微差别曾被考察
- Node.js libuv 六阶段：timers → pending callbacks → idle → poll → check → close，解释 `setImmediate` 与 `setTimeout(fn, 0)` 的执行顺序差异

### 第 05 篇：链表：React Fiber 链表结构与 LRU Cache 手写实现

**副标题**：指针操作的心智模型、哑节点技巧，以及链表在工程中的真实形态

#### 一、场景切入：React Fiber 为什么用链表

- React Fiber 链表：每个 FiberNode 有 `child`（第一个子节点）、`sibling`（下一个兄弟节点）、`return`（父节点）三个指针——把整棵组件树编码为链表结构，可在任意节点暂停遍历（时间分片的基础）

#### 二、链表是什么

- 多个元素组成的列表，元素存储不连续，用 next 指针连在一起
- JS 中没有链表，但可以用 Object 模拟
- 数组 vs 链表：数组增删非首尾元素需搬移，链表只需改 next 指向

#### 三、链表类型

- 单链表：只有 `next`，删除节点需找前驱（O(n)）
- 双链表：`prev`/`next` 双向，删除节点 O(1)
- 循环链表：`tail.next === head`，适合轮转场景
- 有序链表：插入时按序找位置

#### 四、核心技巧

- **哑节点（Dummy Node）**：头部插哨兵节点，统一头节点与非头节点边界，消除大量 `if head === null` 判断——80% 的链表题可用
- **快慢指针**：慢1步/快2步——检测环（Floyd 判圈，相遇则有环）、找中点、找倒数第 k 个节点

#### 五、高频题精讲

- 206 反转链表（双指针一前一后）
- 21 合并有序链表（归并思想）
- 142 环形链表 II（快慢指针找入环点）
- 146 LRU Cache（双链表 + HashMap，O(1) get/put）

**LeetCode 重点题**：206（反转链表）/ 21（合并有序链表）/ 142（环形链表 II）/ 146（LRU 缓存）/ 25（K 个一组翻转链表）

#### 六、前端工程落地

- LRU Cache 语义：药品搜索历史、有限容量的最近搜索记录，天然是 LRU
- **JS 原型链本质是链表**：`obj → Object.prototype → null`，沿 `__proto__` 链查找属性；`instanceof` 原理就是沿原型链找 `B.prototype`

### 第 07 篇：树：DOM 遍历/虚拟 DOM diff/BST/Trie 前缀树实战

**副标题**：递归与迭代遍历、BST 有序性、Trie 前缀匹配——前端高频树形结构全解

#### 二、树是什么

- 分层数据的抽象模型，JS 中没有树，用 Object + Array 构建
- 树的常用操作：深度/广度优先遍历、先中后序遍历

#### 三、遍历（重点）

- 深度优先 DFS（递归：先访问根，再对 children 依次 DFS）
- 广度优先 BFS（队列：根入队 → 队头出队访问 → children 入队）
- 二叉树的先中后序：
  - 先序（根→左→右）：复制树、序列化

- 左子树所有值 < 根 < 右子树所有值；插入/搜索/删除平均 O(logn)
- 删除三种情况：无子节点直接删 / 单子节点上移 / 双子节点用右子树最小节点替换
- 最坏退化 O(n)（退化为链表），引出平衡树

#### 五、平衡树（概念，不要求手写）

- AVL：严格平衡，旋转频繁
- 红黑树：近似平衡，旋转较少——解释"为什么 Java HashMap 链表超 8 转红黑树"

#### 六、Trie 前缀树

- 每个节点一个字符，根到某节点路径代表一个前缀；插入/查询 O(m)（m 为字符串长度）
- 空间消耗大，可用压缩 Trie（radix tree）优化

### 第 10 篇：排序：V8 TimSort 源码解析/快排/归并/稳定性全解

**副标题**：比较排序的 O(n log n) 下界、稳定性的实际影响、V8 为什么从快排切换到 TimSort

#### 一、场景切入：`sort` 到底稳不稳定

- 前端列表排序：药品列表按价格/销量/字母排序——ES2019 前 `Array.prototype.sort` 在不同浏览器实现不同，相同键值元素顺序可能变化，ES2019 起规范强制要求稳定性
- 稳定性的实际影响：先按科室排序再按优先级排序，若 `sort` 不稳定，两次排序后同优先级内科室顺序会乱——稳定排序是多键值排序的基础

#### 二、排序基础：稳定性 / 内外部排序 / 复杂度全景

- 稳定 vs 不稳定：a=b 时排序后 a 是否仍在 b 前面
  - 稳定：冒泡、插入、归并、基数
  - 不稳定：选择、快速、希尔、堆
- 内排序（内存中完成）vs 外排序（数据在磁盘，内存与磁盘交换）
- 复杂度全景表：平方阶（简单排序）→ 线性对数阶（快排/堆/归并）→ 线性阶（基数/桶/计数）

#### 三、简单排序（O(n²)）

- 冒泡排序：相邻比较交换，每轮把最大"冒"到最后，最好 O(n)、最坏/平均 O(n²)、稳定
- 选择排序：每轮找最小放到前面，始终 O(n²)、不稳定
- 插入排序：从第二个往前插，最好 O(n)、最坏/平均 O(n²)、稳定——小数组/基本有序时优于快排

#### 四、进阶排序（O(n log n)）

- 快速排序：选基准分区，递归——平均 O(nlogn)、最坏 O(n²)（已排序+选首元素为基准）、不稳定、原地
- 归并排序：分半递归再合并——始终 O(nlogn)、稳定、需 O(n) 额外空间
- 堆排序：建大顶堆 + 反复交换堆顶——O(nlogn)、不稳定、原地

#### 五、线性排序（O(n)，非比较）

- 计数排序（稳定，要求整数范围确定）、桶排序（计数升级，均匀分布）、基数排序（按位分配收集，稳定）——突破比较排序下界靠"不比较"

#### 六、比较排序的下界与 TimSort

- 比较排序下界：n 个元素 n! 种排列，决策树至少 log₂(n!) ≈ n logn 次比较，最坏不可能优于 O(nlogn)
- TimSort（V8 实际使用）：归并 + 插入混合，短序列(<64)用插入，长序列识别有序 run 再归并——对真实数据接近 O(n)、稳定、最坏 O(nlogn)

### 第 12 篇：递归：递归三要素/尾递归/记忆化到 DP 的跨越

**副标题**：从递归到迭代的思维转换，以及为什么 JS 里不用指望尾递归优化

#### 一、场景切入：递归遍历树与斐波那契的指数爆炸

- 树遍历的自然递归：React 组件递归渲染、DOM 树递归克隆——递归代码与树结构完美对应
- 斐波那契的朴素递归：`fib(40)` 卡死——指数级 O(2ⁿ)，引出记忆化

#### 二、递归是什么

- 解决问题的方法，从各个小部分开始直到解决大问题，函数调用自身
- 每个递归函数必须有**基线条件**（base case，不再递归调用的停止点），防止无限递归

#### 三、递归三要素

1. **基本情况**（base case，终止条件）
2. **递推关系**（把大问题拆成同类小问题）
3. **信任递归**（假设子问题已正确解决，直接用结果）——写不好递归的根因是总想追踪调用栈

#### 四、递归的代价与尾递归

- 每次调用 push 一个栈帧，深度过大栈溢出——JS 调用栈约 10000~15000 层
- **尾递归优化（TCO）**：递归调用是函数最后一个操作时，理论上可复用栈帧——ES6 规范要求支持，但 V8 出于调试体验一直未实现（Safari/JavaScriptCore 严格模式下支持）

#### 五、记忆化到动态规划的跨越

- **记忆化（Memoization）**：用 Map 缓存已算子问题，指数级降为 O(n)——自顶向下
- 与自底向上 DP 表等价，写法更直觉——这是理解 DP 的最佳路径（衔接第 13 篇）

#### 六、递归改迭代

- 所有递归都可用显式栈改写为迭代（消除栈溢出风险）
- 经典示例：阶乘、斐波那契（迭代版 O(n)/O(1) 空间）

#### 七、高频题精讲

- 509 斐波那契数（朴素递归 vs 记忆化 vs 迭代，三种版本对比）
- 70 爬楼梯（记忆化 / DP）
- 104 二叉树最大深度（递归）
- 226 翻转二叉树（递归 / 分治）

**LeetCode 重点题**：509（斐波那契数）/ 70（爬楼梯）/ 104（二叉树最大深度）/ 226（翻转二叉树）

#### 八、前端工程落地

- V8 调用栈深度实测：递归计数可测出当前 Node 版本最大调用栈深度（约 10000-15000，取决于每帧大小）
- V8 对 TCO 的态度：V8 issue #4698 明确拒绝实现 TCO 的原因（调试栈帧丢失、难定位错误）

### 第 13 篇：动态规划：状态转移方程建模/编辑距离/背包问题

**副标题**：从"暴力 → 记忆化 → DP 表 → 空间优化"的四步推导，拆解动态规划建模思路

#### 一、场景切入：编辑距离与代码分割

- 编辑距离：药品名称纠错（"阿莫西林" vs "阿莫西琳"，编辑距离为 1）——Myers diff（Git diff 基础）是编辑距离的 DP 变体
- 前端构建优化：代码分割（code splitting）最优策略是一个 DP 问题——如何分包使总加载时间最短

#### 二、动态规划是什么

- 把问题分解为**相互重叠**的子问题，通过反复求解子问题解决原问题
- 步骤：定义子问题 → 反复执行（自底向上求解）

#### 三、DP vs 分而治之（关键辨析）

- 分治子问题**相互独立**（各算各的，不共享）；DP 子问题**相互重叠**（有公共子问题，需缓存）
- 例：斐波那契是 DP（重叠），翻转二叉树是分治（独立）

#### 四、适用 DP 的两个必要条件

1. **最优子结构**：大问题的最优解包含子问题的最优解
2. **无后效性**：已确定的子问题答案不会被后续决策改变

#### 五、四步推导法

1. **暴力递归**：先写朴素递归，确认递推关系
2. **记忆化**：加 Map 缓存消除重复计算
3. **DP 表**（自底向上）：记忆化翻译为循环，消除递归栈开销
4. **空间优化**：转移只依赖相邻行/列，用滚动数组 O(n²)→O(n)

#### 六、经典 DP 模型

- 线性 DP：最长递增子序列（LIS）、最长公共子序列（LCS）、爬楼梯、打家劫舍
- 区间 DP：矩阵链乘、最优括号化
- 背包 DP：0-1 背包（选或不选）、完全背包（可选多次）——遍历顺序不同
- 状态机 DP：买卖股票系列（持有/不持有状态转移）

- 300 最长递增子序列
- 1143 最长公共子序列

- 322 零钱兑换 / 518 零钱兑换 II（完全背包）

**LeetCode 重点题**：70（爬楼梯）/ 62（不同路径）/ 300（最长递增子序列）/ 1143（最长公共子序列）/ 72（编辑距离）/ 322（零钱兑换）/ 518（零钱兑换 II，完全背包）

### 第 14 篇：分治：快排/归并/快速幂与主定理分析

**副标题**：递归 + 合并的范式，从「拆分到合并」理解分治，以及它与动态规划的分野

#### 一、场景切入：归并排序与深比较两棵树

- 归并排序即分治：数组分半分别排序再合并——「分解 → 解决 → 合并」最直观体现
- 深比较两棵处方对象树：先比根节点，再递归比左右子树，最后合并比较结果——树结构天然适合分治
- 分片处理大数据：一次性排 1000 万条用药记录会撑爆内存，拆成多分片各自排序再归并（外排序思想）

#### 二、分而治之是什么

- 把一个问题分解成多个和原问题相似的小问题，递归解决小问题，再合并结果解决原问题

#### 三、分治三步骤

1. **分解（Divide）**：大问题拆成规模更小的同类子问题
2. **解决（Conquer）**：递归求解子问题（足够小时直接求解）
3. **合并（Combine）**：子问题解组合成原问题解——「合并」步是分治区别于普通递归的关键

#### 四、分治 vs 递归 vs 动态规划

- 分治一定是递归，但递归不一定是分治（分治强调子问题独立 + 存在合并步）
- 分治子问题**相互独立**，DP 子问题**相互重叠**——归并排序不需要记忆化、斐波那契需要的原因

#### 五、主定理（Master Theorem）

- 求解 `T(n) = aT(n/b) + f(n)` 的分治递归式——归并排序 `T(n) = 2T(n/2) + O(n)` 对应 case 2 → O(nlogn)
- 经典分治算法清单：归并排序 / 快速排序（分解步不均衡）/ 二分搜索（每次只处理一半）/ 归并 K 个链表 / 快速幂

#### 六、高频题精讲

- 23 合并 K 个升序链表（两两合并的分治 vs 顺序合并，O(kn logk) vs O(k²n)）
- 169 多数元素（分治求众数）
- 50 Pow(x, n)（快速幂，指数拆半 O(logn)）
- 100 相同的树 / 101 对称二叉树（树的分治比较）

**LeetCode 重点题**：23（合并 K 个升序链表）/ 169（多数元素）/ 50（Pow(x, n)）/ 148（排序链表）/ 493（翻转对）

#### 七、前端工程落地

- V8 TimSort 的归并步：识别有序 run 后用归并合并（衔接第 10 篇）
- React reconcile 树 diff：把整棵树对比拆成「单节点 diff」「多节点 diff」两个独立子问题——分治在 diff 里的应用
- Webpack tree-shaking 可达性分析：从入口出发递归拆到每个依赖子图独立判断再合并

### 第 15 篇：回溯：全排列/子集/N 皇后与剪枝艺术

**副标题**：DFS + 剪枝 + 撤销选择，把「试错 → 回退」的枚举过程抽象成模板

#### 一、场景切入：级联下拉与药品配伍组合

- 表单校验规则引擎：级联下拉「省 → 市 → 区」完整路径枚举、动态表单字段组合校验——本质是回溯遍历一棵「选择树」
- 药品配伍禁忌组合检测：从一组药品枚举所有联合用药组合检查禁忌——子集/组合枚举是回溯经典场景
- 处方药品推荐排列：若干药品按疗程排列出所有可行方案再筛掉不满足剂量约束的——排列 + 约束 = 回溯

#### 二、回溯算法是什么

- 渐进式寻找并构建问题解决方案的策略：先从一个可能的动作开始，不行就回溯换另一个动作，直到解决
- 有「出路」也有「死路」的问题适合回溯

#### 三、回溯三要素

1. **路径（path）**：已经做出的选择
2. **选择列表（choices）**：当前还能做的选择
3. **结束条件（base case）**：到达决策树底层，把路径加入结果集

#### 四、核心模板与剪枝

- 模板：`for (选择 of 选择列表) { 做选择 → 递归(路径, 新的选择列表) → 撤销选择 }`——「撤销选择」让同一变量反复复用，是回溯区别于普通 DFS 的关键
- **剪枝（pruning）**：递归前判断当前路径是否不可能产生合法解，若是则提前 return——不剪枝全排列 O(n!)，剪枝大幅减少无效分支（N 皇后剪枝后能跑 N=8 甚至更高）
- 回溯 vs DFS：DFS 是「沿着一条路走到黑」，回溯是「DFS + 撤销选择 + 剪枝」，强调试错回退的状态恢复

#### 五、复杂度

- 回溯通常是**指数级/阶乘级**，用「决策树有多少个节点」描述——剪枝的价值不在降低上界，而在剪掉大量实际不会走的无效节点

#### 六、高频题精讲

- 46 全排列（模板 + `path.push`/`path.pop` 演示撤销）
- 78 子集（保证后选数字都是后面的）
- 51 N 皇后（对比剪枝前后遍历节点数）
- 39 组合总和 / 79 单词搜索

**LeetCode 重点题**：46（全排列）/ 78（子集）/ 51（N 皇后）/ 39（组合总和）/ 79（单词搜索）

#### 七、前端工程落地

- React `completeUnitOfWork` 的回溯：节点处理完子节点后沿 `fiber.return` 回溯到父节点——「完成一个分支回到上一层」正是回溯的遍历形态
- 正则回溯与 ReDoS：`(a+)+b` 嵌套量词触发指数级回溯导致 CPU 阻塞——「灾难性回溯」是回溯复杂度的真实安全威胁

### 第 16 篇：贪心：区间调度/哈夫曼编码与正确性证明

**副标题**：局部最优 → 全局最优，为什么贪心「看起来简单」却需要严格的正确性证明

#### 一、场景切入：医院诊室排班

- 区间调度：每个医生有若干可用时间段，求最多安排多少不冲突问诊——每次选「结束最早」的区间，最经典贪心
- 药品库存分配：把有限库存分给需求最急、用量最小的处方，追求「满足最多处方」
- 找零问题：面额 [1,3,4] 凑 6 贪心得 4+1+1 三张，最优是 3+3 两张——「局部最优≠全局最优」的反例

#### 二、贪心算法是什么

- 每一步都做「当前看起来最优」的选择，**不回溯、不返工**——期望局部最优推出全局最优
- 结果**不一定是最优**

#### 三、适用条件

1. **最优子结构**：问题最优解包含子问题最优解
2. **贪心选择性质**：当前最优选择能安全固定下来，不需考虑未来——两者同时满足才敢用贪心

#### 四、贪心 vs 动态规划

- 贪心每一步只看「当前一步」就定死，不做选择间比较；DP 遍历所有子问题取最优
- 贪心更快（通常 O(nlogn)）但适用范围窄、正确性更难保证

#### 五、经典贪心算法与正确性证明

- 区间调度（按结束时间排序）/ 哈夫曼编码（每次合并频率最小的两个节点）/ Dijkstra（每次选距离最小的未确定节点）/ Prim（每次选权值最小的边）
- **正确性证明**：贪心不能靠「感觉对」，需**数学归纳法**或**交换论证（exchange argument）**证明局部最优能推出全局最优

#### 六、陷阱：什么时候贪心会错

- 0-1 背包不能贪心（按性价比排序会错，必须 DP）
- 找零问题面额特殊时贪心失效

- 435 无重叠区间（按结束时间排序）
- 121/122 买卖股票最佳时机 I/II（II 贪心每天差价）
- 55 跳跃游戏 / 45 跳跃游戏 II

**LeetCode 重点题**：455（分发饼干）/ 435（无重叠区间）/ 55（跳跃游戏）/ 121（买卖股票最佳时机）/ 122（买卖股票 II）/ 45（跳跃游戏 II）

#### 八、前端工程落地

- 哈夫曼编码与 HTTP/2 HPACK：头部压缩用哈夫曼编码，出现频率越高编码越短——「高频短码」贪心思想在真实协议的落地
- Dijkstra 的贪心选择：每次从未确定节点选距离起点最近的「确定下来」——「选当前最小并固定」就是贪心选择
