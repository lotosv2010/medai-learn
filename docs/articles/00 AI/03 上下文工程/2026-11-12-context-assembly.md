# 上下文组装：一次调用里放了什么、各占多少（面试收藏级）

> 你的 Prompt 已经写得像一份合同了——角色、边界、格式约束样样齐全，回归测试也跑得通。可一上多轮对话，模型还是偶尔「答非所问」。你盯着那串 messages 看：System Prompt、20 轮历史、50 段检索结果、一堆工具返回……到底谁把谁挤出了注意力？

---

## 🎯 这篇文章解决什么问题

上一篇《Prompt 工程进阶》把 Prompt 当资产管起来了，但它只回答了「你给模型的指令该怎么写」。这一篇回答下一个问题，也是阶段三真正的主角：

**指令写好之后，放进这一次调用里的其他东西——历史、检索片段、工具描述、工具返回——该怎么拼？**

读到这里你可能已经猜到答案的方向了：窗口是一块有配额的地方，不是越大越好的保险柜。这篇文章拆两件事：

- **预算**：一次调用里的六类内容，每类该占多少 token，超了怎么截
- **顺序**：谁放最前、谁放最后，为什么「关键信息放中间」是个坑

照旧，每段配「面试官会怎么问」。读完你拿到一张可复用的组装器 `assemble.ts`，和一套「怎么回答『上下文怎么设计』这类面试题」的话术。

---

## 🔍 概念：一次调用 = 六类内容拼出来的一个「现场」

先看一个很多人踩过的坑。

做一个用药咨询助手，用户问「这个药和我正在吃的药，能一起吃吗」。开发的做法很自然：把 System Prompt、过去 20 轮聊天记录、检索到的 50 段说明书、5 个工具描述、工具返回的一大坨 JSON，全部拼进 messages 发出去。结果模型开始「答非所问」——不是它变笨了，是**某类内容把其他内容挤出了注意力的有效范围**。

一次真实调用的上下文，通常由六类内容拼成：

| 类别 | 是什么 | 谁在涨 |
|---|---|---|
| System Prompt | 角色、边界、格式约束（上一篇的四要素） | 你写的，稳定 |
| 对话历史 | 之前每一轮的你问我答 | 每轮都在涨 |
| 检索片段（RAG） | 从知识库召回的相关段落 | 随查询涨 |
| 工具描述 | 每个工具的用途与参数说明 | 随工具数涨 |
| 工具返回结果 | 工具执行后回传的内容 | 随调用涨 |
| 用户输入 | 用户当前问的这一句 | 每次一条 |

**上下文组装（Context Assembly），就是「把哪几类、以什么顺序、各占多少 token 拼进这一次调用」的决策过程。** 注意这个词的落点——它不是「把能塞的都塞进去」，而是「分配预算 + 排定顺序」。

> 💬 **面试官**：一次 LLM 调用的上下文里，通常有哪些内容？
>
> ✅ **标准答案**：六类——System Prompt、对话历史、RAG 检索片段、工具描述、工具返回结果、用户输入。它们共用同一个上下文窗口，任何一类膨胀都会挤占其他类。
>
> 🎁 **加分答案**：能把这六类按「谁在涨」分成两类——**稳定内容**（System、工具描述、few-shot 示例，你自己写死的）和**易变内容**（历史、检索、工具返回、用户输入，每次调用都不一样）。这个「稳定/易变」的切法，是后面讲顺序和缓存（05 篇）的共同地基。

这六类里，最容易被低估的是**历史**和**工具返回**。它们看起来「不多」，但历史每轮都在涨，工具返回常常是一大坨没人精简过的 JSON。预算失控，十有八九不是检索片段，是这两样。

## ⚙️ 深入：预算配额 + 顺序排布

### 预算配额：先定配额，再往里装

窗口是硬上限，但「有效注意力」比硬上限更小（阶段一 02 篇已经讲过 Lost in the Middle）。给每类内容分配配额，目的只有一个：**防止某一类把其他类挤出去**。

给一个用药咨询场景的配额示例（数字因场景而异，关键是「先定配额、再装」这个动作）：

| 类别 | 配额 | 超了怎么办 |
|---|---|---|
| System Prompt | 5% | 本身就很短，一般不超 |
| 对话历史 | 30% | 超了走压缩（03 篇） |
| 检索片段 | 40% | 截断到 Top-K |
| 工具返回 | 15% | 精简，只留结论 |
| 用户输入 | 10% | 用户说的话，尽量别动 |

注意这张表真正的价值不在数字，在于它逼你回答一个问题：**每一类内容的上限是谁定的？** 定了上限，下游手段才有了触发条件——历史超配额才去压缩，检索超配额才去截断，工具返回超配额才去精简。**预算管理是这些下游手段的「开关」，不是一句「别塞太多」的空话。**

落地到代码，就是给每一类一个 token 配额，装的时候超了就截断：

```typescript
// labs/phase3-context/_sdk/assemble.ts —— 组装器（节选）
import { countTokens, encode, decode } from 'gpt-tokenizer'

// 按 token 数截断，不是按字符数——中文一个汉字可能是 1~3 个 token
export function truncateTo(text: string, maxTokens: number): string {
  const ids = encode(text)
  if (ids.length <= maxTokens) return text
  return decode(ids.slice(0, maxTokens))
}

// 排定顺序 + 按配额截断，组装成 messages
export function assemble(blocks: Block[], quota: Partial<Record<BlockKind, number>>) {
  const sorted = [...blocks].sort((a, b) => ORDER.indexOf(a.kind) - ORDER.indexOf(b.kind))
  const byKind = new Map<BlockKind, string>()
  for (const b of sorted) {
    const prev = byKind.get(b.kind)
    byKind.set(b.kind, prev ? `${prev}\n${b.content}` : b.content)
  }
  return ORDER.filter((k) => byKind.has(k)).map((kind) => ({
    role: ROLE[kind],
    content: quota[kind] != null ? truncateTo(byKind.get(kind)!, quota[kind]) : byKind.get(kind)!,
  }))
}
```

这段代码只有两件事：**排序**（按 `ORDER` 数组）和**截断**（按 `quota`）。没有魔法，但「排序 + 截断」就是上下文组装的全部。

### 顺序排布：关键放头尾，稳定放前面

顺序为什么重要？回指阶段一 02 篇的结论：Lost in the Middle——**关键信息放在上下文中间，模型「看到但没给够权重」**，命中率明显低于头尾。

这个结论落到工程上，就是一条可执行的规则：**关键信息放头尾**。

- **System Prompt 在最前**：定角色、定边界，这是「你是谁、什么不能做」的锚点
- **用户当前输入 + 最相关的检索片段，靠近尾部**：临门一脚时离生成最近，注意力最强
- **历史、工具返回放中间**：它们重要，但容忍被稀释

顺序还有一个隐藏收益，和 05 篇要讲的 Prompt Caching 方向一致：**稳定内容在前、易变内容在后**。System、工具描述、few-shot 示例这些「每轮都不变」的内容放最前，请求的前缀才稳定，缓存才能命中。注意力维度和缓存维度，方向恰好一致，所以你只需要记一条顺序：

```
system → 工具描述 → 历史 → 检索片段 → 工具返回 → 用户输入
   └── 稳定，放前 ──┘   └────────── 易变/关键，放后 ──────────┘
```

![一次调用的六类内容按 token 占比排开：历史与工具返回合计吃掉约六成窗口，而它们恰好该放中间容忍稀释——稳定内容在前、关键内容在尾，注意力与缓存两条考量指向同一条顺序](https://jianda-cmsstatic.oss-cn-shenzhen.aliyuncs.com/assets/charts/202611/1794450122392_47r0bnx6cku.png)

> 💬 **面试官**：为什么「关键信息放中间」效果差？工程上怎么规避？
>
> ✅ **标准答案**：Lost in the Middle——模型在长上下文里对中间位置信息的利用率显著低于头尾，呈现 U 形。规避办法是编排而非调参：System 放最前定规则，用户输入和最相关检索片段靠近尾部，历史与工具返回放中间，必要时在结尾重复关键指令。
>
> 🎁 **加分答案**：能点出顺序的两个维度——**注意力**（头尾权重高）和**缓存**（稳定前缀在前才命中，05 篇）。两者方向恰好一致，所以「稳定在前、关键在尾」一条规则同时服务两个目标，不用纠结怎么折中。

### 顺序和缓存，方向一致

这里先埋一个伏笔，05 篇展开：如果你把时间戳、随机串这类「每轮都变」的东西放在最前面，等于每轮请求的前缀都不一样，缓存一次都命中不了。**「稳定在前、易变在后」不是风格偏好，是缓存命中率的硬约束。**

而它恰好也是注意力要的顺序。所以组装顺序只有一条黄金法则，记它就行：

> **稳定的往前放，关键的靠尾放，容易膨胀的放中间。**

## 🧪 动手实验：一张预算表 + 一次「隐藏变量」现形

> **说明**：实验代码 `labs/phase3-context/02-context-assembly/`，模型 `deepseek-chat`。跑法（仓库根目录）：先 `nvm use 22`，再 `pnpm --filter @medai/labs p3-assemble`；需先在 `.env.local` 里配好 `DEEPSEEK_API_KEY`（缺 key 时脚本给中文提示）。实验 A 纯本地零调用；实验 B 24 次真实调用，约 ¥0.5。

### 实验 A：六类内容各占多少 token

构造一次真实的用药咨询调用——System Prompt + 12 轮历史 + 3 段检索片段 + 2 个工具描述 + 1 段工具返回 + 用户输入，用 `gpt-tokenizer` 统计每类的 token 占比（2026-11-12 实测）：

```typescript
// labs/phase3-context/_sdk/assemble.ts —— measureBudget：先测现状，再谈配额（节选）
export function measureBudget(blocks: Block[]): Array<{ kind: BlockKind; tokens: number; ratio: number }> {
  const total = blocks.reduce((s, b) => s + countTokens(b.content), 0)
  const byKind = new Map<BlockKind, number>()
  for (const b of blocks) byKind.set(b.kind, (byKind.get(b.kind) ?? 0) + countTokens(b.content))
  return ORDER.filter((k) => byKind.has(k)).map((kind) => {
    const tokens = byKind.get(kind)!
    return { kind, tokens, ratio: total === 0 ? 0 : tokens / total }
  })
}
```

> 注意它的定位：**测量是配额的前提。** 上一章你见到的 `truncateTo` / `assemble` 是「按配额截断」，这一段 `measureBudget` 是「先算出六类现在各吃多少 token」——不知道现状，「先定配额」就是拍脑袋。下面这张表，就是它对 `buildBlocks()` 的一次输出。

| 类别 | token 数 | 占比 |
|---|---|---|
| System Prompt | 90 | 11.2% |
| 对话历史 | 384 | 47.6% |
| 检索片段 | 111 | 13.8% |
| 工具描述 | 61 | 7.6% |
| 工具结果 | 132 | 16.4% |
| 用户输入 | 28 | 3.5% |

一眼看出来的结论：**对话历史 + 工具结果，两类合计吃掉了 64% 的窗口**——而这两类恰恰是「每轮都在涨、还最容易写得冗长」的那两个。检索片段只占 13.8%，远没有你想象的那么「占地方」。

这个占比表和直觉正好相反：大家都以为「检索结果太多了」，其实真正在失控的是**历史**（多轮对话越聊越长）和**工具返回**（没人精简的一坨 JSON）。预算管理的第一刀，应该砍在这两样上。

### 实验 B：temperature 是「顺序对照」里的隐藏变量

大纲原本设想：把一条关键事实分别放头/中/尾，看「中间会不会丢」。但真跑起来，我发现了一个更值得写的东西——**这个实验本身藏着一个必须先掐住的变量**。

先说我踩过的坑：如果用「唯一事实埋中间」，在 DeepSeek 上无论把上下文拉到 20k、60k，还是换成 20 轮信息密集的历史、连贯长文档，中间那份唯一事实都**稳定命中**——因为答案在上下文里只有一份，模型扫一眼就能挑出来，位置效应根本不显形。

真正让位置效应显形的是「**多候选要区分**」：当上下文里同时有 26 段都写着「X-7 与 W 的风险等级」、只有一段是 3 级、其余是 1/2 级时，中间那份「3 级」的信心最弱，最先被邻近的 2 级带偏。

但就算这么设计了，还有一个更隐蔽的坑：**temperature**。看同一份多候选上下文，temperature=0 和默认采样各跑 4 轮（2026-11-12 实测）：

```typescript
// labs/phase3-context/02-context-assembly/fixtures.ts —— 实验 B 的「针」：26 段相似候选（节选）
const TARGET = '【药品相互作用档案】…风险等级为「3 级（高）」…'   // 唯一一份「3 级」
function distractor(i: number): string {
  const level = i % 2 === 0 ? '1 级（低）' : '2 级（中）'            // 25 段干扰，1/2 级交替
  return `【药品相互作用档案】…风险等级为「${level}」…`
}
// 三组（头 / 中 / 尾）唯一差异：TARGET 那份「3 级」排在 26 段的哪个位置
// 两次调用唯一差异是温度：callModel(key, messages, { temperature: 0 })（掐住）vs callModel(key, messages)（默认采样）
```

![同一个多候选上下文，temperature=0 时头中尾 12/12 全中，贪心解码把「位置信心不足」整个藏了起来；默认采样下漂移开始出现，这一轮中间位置命中率最低（2/4）——对照实验不掐温度，测到的就是采样随机性](https://jianda-cmsstatic.oss-cn-shenzhen.aliyuncs.com/assets/charts/202611/1794450060085_xb73upwbyx.png)

```text
采样方式         3 级档案的位置        命中率（4 轮）
temperature = 0  头（第 1 段）         4/4
temperature = 0  中（第 13 段）        4/4
temperature = 0  尾（第 26 段）        4/4
默认采样         头（第 1 段）         3/4
默认采样         中（第 13 段）        2/4
默认采样         尾（第 26 段）        4/4
```

两条读数：

**temperature=0 把「位置信心不足」整个藏了起来。** 贪心解码永远选概率最高的那个 token，于是 12/12 全中——你看着以为「位置没影响」，其实是贪心替你锁定了答案。

**默认采样下，漂移显形了。** 这一轮中间位置命中率最低（2/4），尾部最稳（4/4）——方向上和 Lost in the Middle 一致。但样本只有 4 轮，我不会拿它当「位置效应」的证据：哪个位置漂，跑一轮一个样。

所以实验 B 真正的结论是方法论的：

> **做任何「顺序 / 编排」的对照实验，temperature 是必须先掐住的变量。** 不掐住它，你测到的不是「位置」，是「采样随机性」。

而「关键信息放头尾」本身的干净证据，在阶段一 02 篇的 needle 实验（3 长度 × 3 位置的 9 格矩阵）和 Lost in the Middle 论文里。本篇实验 B 补的是这一课：**先掐住温度，多轮统计，才敢谈顺序。**

## 🚧 总结与边界

本篇压成一句话：

> **上下文组装不是「塞进去」，是「分配预算 + 排定顺序」——先定配额，再决定什么被截断。**

四条推论：

- **六类内容共用一个窗口**——System、历史、检索、工具描述、工具返回、用户输入，任何一类膨胀都会挤占其他类
- **预算失控的头号嫌疑是历史和工具返回**——实验 A 里它们合计吃掉 64%，检索片段只占 13.8%
- **顺序两条维度，方向一致**——注意力要「关键放头尾」，缓存要「稳定放前面」，一条顺序同时服务两者
- **对照实验先掐温度**——不控制采样，你测到的顺序效应是噪音

**里程碑 1 验收**：`assemble.ts` 就是「System + 历史 + RAG 片段 + 工具结果各有配额」这个组装方案的代码化——给定六类内容和配额，输出一份按「稳定在前、关键在尾」排好序的 messages。

有意识地留到后面：

- **历史太长怎么压**（摘要化 / 滑动窗口 / 关键信息提取）→ 03 篇
- **检索片段怎么少而准**（分块、Top-K、重排序）→ 阶段四
- **配额定了，怎么让前缀少花钱**（Prompt Caching）→ 05 篇

## 🎤 面试追问链

**追问一：一次 LLM 调用的上下文里有哪些内容？你怎么分配预算？**

见「概念」章。加分点：把六类按「稳定/易变」切分，先说「先定配额、再装」，再举例——历史 30%、检索 40%、工具返回 15%，超了分别走压缩、截断、精简。面试官要听的不是具体数字，是「你有『配额』这个概念，且知道它驱动下游手段」。

**追问二：为什么「关键信息放中间」效果差？工程上怎么规避？**

见「深入」章。加分点：别只说「Lost in the Middle」，要说清它是**结构性偏差不是能力不足**，换更强模型只会减弱不会消失，所以解法永远是编排。再补一条：做顺序对照实验要先掐 temperature，否则测到的是采样随机性。

**追问三：检索结果有 50 段，你全塞进去会怎样？怎么处理？**

全塞进去 = 三重代价：token 爆预算、注意力被稀释、真正相关的那段可能落在中间被漏掉。处理办法是**先截断再排位**——截到 Top-K，把最相关的放在靠近用户输入的尾部，其余丢弃或摘要。

**追问四：上下文的顺序和 Prompt Caching 有什么关系？**

缓存只对「请求前缀完全一致」的部分生效。所以「稳定内容在前、易变内容在后」直接决定缓存命中率——System、工具描述、few-shot 放最前，历史用户输入往后放。顺序排错了，缓存形同虚设。这和注意力的「关键放头尾」方向一致，一条规则两个收益。

你的用药咨询助手，现在一次调用要装：System Prompt（约 90 token）、30 轮历史、检索到的 20 段说明书、8 个工具描述、工具返回的一坨 JSON、用户当前问题。

- 你会给这六类分别定多少配额？超了各怎么处理？
- 如果产品要求「每次都要带上最近 30 轮历史，不能丢」，你的预算会先砍哪一类？为什么？
- 提示：先想清楚「丢了谁的代价最大」，再想「谁的 token 最不值钱」。
