## 🧩 场景切入：级联下拉与药品配伍组合

回溯的直觉，其实你每天写业务代码时都在用，只是没把它和「算法」两个字连起来。先看三个真实场景。

### 表单校验规则引擎：级联下拉的路径枚举

🔧 **真实场景**：在药品电商的「收货地址」或「门店选择」表单里，经常有级联下拉——「省 → 市 → 区」。用户每选一层，下一层的可选项就跟着变。要在前端做**完整的路径校验**（比如判断「这个省-市-区组合是否在允许配送范围内」），本质就是在遍历一棵**选择树**：

```
              省（选择一个）
            /    |    \        \
       广东省  江苏省  浙江省  四川省 ...
         |       |       |
       市（基于已选省，选择下一个）
      /  |  \
   深圳市 广州市 佛山市 ...
      |
    区（基于已选市，选择下一个）
   /  |  \
 南山区 福田区 宝安区 ...
```

这棵树就是回溯里的**决策树**：每往下一层，就是「在已选省级的前提下，选一个市」，选完了这一支，再**退回去**换下一个市。8 万个行政区划的笛卡尔积不可能全部展开，但「一条从根到叶的路径」对应一个合法的省-市-区组合——**枚举所有合法路径，正是回溯在做的事**。

### 药品配伍禁忌组合检测：子集/组合枚举

🔧 **真实场景**：医生开处方时，系统要检查「多药联用」是否存在配伍禁忌。假设一单里有阿司匹林、华法林、布洛芬三种药，系统要检测的组合有：任意两两组合（3 种）、任意三三组合（1 种），再加上单药（3 种）——**从一组药品里枚举出所有子集，逐个送去禁忌库匹配**。这就是**子集/组合枚举**，是回溯最经典的应用场景之一。

### 处方药品推荐排列：排列 + 约束

🔧 **真实场景**：某类慢病需要「多药序贯治疗」，比如按疗程顺序服用 A、B、C 三种药。要把所有可能的服用顺序列出来，再**筛掉不满足剂量约束或间隔要求的方案**。这就是**排列 + 约束**——排列是回溯，约束就用来**剪枝**。

三个场景看完，一个共同点浮出水面：**它们都在「一棵树上，逐个尝试所有可能的分支，走到死路就退回来换一条」**。这个「试错 → 回退」的动作，就是回溯的全部。

## 📌 回溯算法到底是什么

先下定义。

**回溯算法（Backtracking Algorithm）** 是**算法设计**中的一种方法。它是一种**渐进式**寻找并构建问题解决方式的策略：会先从一个可能的动作开始解决问题，如果不行，就**回溯**并选择另一个动作，直到将问题解决。

拆开来看，有两个要点：

- **渐进式**：它不是一步到位地算出答案，而是**一个选择一个选择地往前搭**，搭到一半发现走不通，就退回来改
- **试错 + 回退**：往前走叫「试错」，往后退叫「回退」——**能退回去，是回溯区别于普通暴力枚举的关键**

那么什么样的题适合用回溯？一句话判断：

> **有很多条路（组合），这些路里既有「出路」（能到答案），也有「死路」（到不了答案）。**

「有出路也有死路」这个描述，和前面几篇的设计思想刚好对照：

| 设计思想 | 适用特征 |
|---------|---------|
| 分治 | 问题可以拆成**相互独立**的子问题 |
| 动态规划 | 子问题**相互重叠**，需要缓存 |
| 贪心 | 每一步的**局部最优**能直接推出全局最优 |
| **回溯** | **需要枚举所有可能性，边走边试，走不通就退** |

注意到没有：**分治、DP、贪心都是在「求一个最优解」，而回溯常常是「枚举所有解」或「找一个可行解」**。这是回溯在四种设计思想里最独特的地方——它不追求「更聪明」，而是把「穷举」这件事做得**有组织、可回退、能剪枝**。

## ⚙️ 回溯三要素与核心模板

回溯听起来绕，但落到代码上只有三样东西要管，这就是**回溯三要素**。

### 路径（Path）：已经做出的选择

**路径**记录的是「我现在已经选了哪些」。在省-市-区例子里，就是「已经选了广东省、深圳市」；在全排列例子里，就是「已经排了 `[1, 3]`」。

它通常用一个数组（如 `path`）来维护。

### 选择列表（Choices）：当前还能做的选择

**选择列表**指的是「在当前的路径下，我下一步还能选什么」。它是**动态的**——取决于你现在走到哪了：

- 全排列里，下一步能选的，是「还没被放进 `path` 的那些数字」
- 子集里，下一步能选的，是「当前下标**之后**的数字」（为了防止 `[1,2]` 和 `[2,1]` 被当成两个不同子集）

### 结束条件（Base Case）：到达决策树底层

当路径已经构成一个完整解时，就把它**收集进结果集**，然后返回。

- 全排列里：`path.length === nums.length`，说明排满了
- 子集里：长度到了 `l`，收集
- 后面 N 皇后里：行号走到了棋盘底部

### 核心模板：做选择 → 递归 → 撤销选择

三要素落到代码，得到回溯的**万能模板**：

```typescript
function backtrack(路径 path, 选择列表 choices) {
  if (满足结束条件) {
    结果集.push(path 的拷贝);   // 👈 收集一个完整解，注意要拷贝
    return;
  }
  for (const 选择 of 选择列表) {
    做选择;                     // 👈 把「选择」加进 path
    backtrack(路径, 新的选择列表);  // 👈 带着新路径往下递归
    撤销选择;                   // 👈 把「选择」从 path 里拿掉，回到上一层
  }
}
```

这个 `for` 循环就是「**站在当前节点，把所有可能的分支都试一遍**」，而每试完一支，都要**撤销**、把状态恢复原样，才能干净地去试下一支。

### 为什么「撤销选择」必不可少

这是回溯的灵魂，也是面试最爱追问的地方。用一个最小的例子说透。

假设你要枚举 `[1, 2]` 的所有排列，用**同一个 `path` 数组**来维护：

```typescript
path = []
// 选 1
path.push(1)          // path = [1]
  // 往下递归，在 [1] 基础上再选 2
  path.push(2)        // path = [1, 2]  👈 找到一个完整解 [1,2]
  path.pop()          // path = [1]     👈 撤销 2，否则下一轮会带着 2
path.pop()            // path = []      👈 撤销 1，回到最开始
// 选 2
path.push(2)          // path = [2]
  path.push(1)        // path = [2, 1]  👈 找到 [2,1]
  path.pop()
path.pop()            // path = []
```

如果不撤销会怎样？`path` 会累积成 `[1, 2]`，然后在「选 2」这轮变成 `[1, 2, 2]`——**上一支的残留污染了下一支**，所有结果全错。

所以**撤销选择的本质是两点**：

- **状态恢复**：让 `path` 回到「进入这个分支之前」的样子，保证每一条分支都在**干净的状态**上开始
- **内存复用**：正是有了「撤销」，同一个 `path` 变量才能被所有分支反复复用，不必为每条分支新建一个数组——这也是回溯区别于普通 DFS 的关键

⚠️ 这里有个**必须记住的坑**：把结果收进 `res` 时，一定要推**拷贝**（`[...path]` 或 `path.slice()`），不能推 `path` 本身。因为 `path` 是引用类型，之后还会被修改，如果直接 `res.push(path)`，最后 `res` 里的每一项都会指向同一个（已经被清空的）数组——**结果全是空数组**。

> 💬 **面试官**：回溯的三要素是什么？「撤销选择」为什么必不可少？
>
> ✅ 标准答案：三要素是**路径（已经做出的选择）、选择列表（当前还能做的选择）、结束条件（到达决策树底层，收集结果）**。「撤销选择」必不可少，因为它让**状态恢复到进入分支之前**——同一层的下一个分支必须在一个干净的状态上开始，否则上一支的残留会污染下一支结果。同时撤销也让同一个路径变量能被反复复用，不必每条分支都新建数组。
>
> 🎁 加分答案：能补两个容易被忽略的细节——① **收集结果时必须推拷贝**（`res.push([...path])`），直接推 `path` 会因引用共享导致所有结果都指向同一个被清空的数组，这是新手最常见的 bug；② 「撤销」不只是 `pop` 数组——凡是**在递归过程中被修改过的状态**（比如后面讲 N 皇后时用到的「列占用 / 对角线占用」标记），都必须成对地「做标记 → 递归 → 撤销标记」，一进一出严格对称，这就是回溯的「**镜像对称**」原则。

### 另一种写法：`concat` 返回新数组

上面用的是「复用同一个 `path` + `push/pop`」的写法。还有一种**更简单、但更耗内存**的写法：**每一步都返回新数组**，从不修改原数组。

笔记里的全排列，用的就是这种写法：

```typescript
// todo 全排列
export function permute(nums: number[]): number[][] {
  const res: number[][] = [];
  const backtrack = (path: number[]) => {
    // console.log(path, res)
    if(path.length === nums.length) {
      res.push(path);
      return;
    }
    nums.forEach(n => {
      // console.log('n', n)
      if(path.includes(n)) return;
      backtrack(path.concat(n)); // path为引用类型这里要使用concat，返回一个新数组，防止输出结果都为空
    });
  }
  backtrack([]);
  return res;
};
```

注意 `path.concat(n)` 这一行：`concat` **不修改 `path`，而是返回一个全新的数组**。所以这里根本不需要 `path.pop()`——因为**原来那个 `path` 从头到尾都没被改过**，下一个分支拿到的是同一个干净的 `path`。

两种写法等价，取舍是：

| 写法 | 是否修改原数组 | 是否需要显式撤销 | 空间开销 |
|------|--------------|----------------|---------|
| `path.push` + `path.pop` | ✅ 修改 | ✅ 需要 | 小（复用同一个数组） |
| `path.concat`（返回新数组） | ❌ 不改 | ❌ 不需要 | 大（每层都新建数组） |

⚠️ 但要注意：**「不修改原数组」只适合「路径本身就是全部状态」的题**。像后面 N 皇后那种还要维护「列、对角线占用标记」的题，这些标记是**独立于 `path` 的额外状态**，`concat` 救不了你——**必须显式撤销**。所以工程上更通用、更推荐的是 `push/pop` 那套「做完就撤销」的写法。

## ✂️ 剪枝艺术：让回溯从「暴力」变得「聪明」

如果说「撤销选择」是回溯的灵魂，那**剪枝（Pruning）就是回溯的性能来源**。

**剪枝**的做法是：在递归**之前**，先判断「沿着当前这条路径走下去，还可能产生合法解吗」——如果**不可能**，就直接 `return`，不再往下递归。这一 `return`，就相当于把这一整根子树（及其所有子孙分支）**一刀剪掉**。

为什么剪枝这么重要？因为回溯的本质是**穷举一棵决策树**，而这棵树的分支数往往是指数级、阶乘级的。剪掉一根子树，省掉的可能是成千上万个节点。

拿 N 皇后举例（下面高频题会细讲）：8 皇后如果**完全不做剪枝**，要尝试 `8^8 ≈ 1677 万` 种摆法；而**只要加一个「同列不能有皇后」的判断**，就能在搜到第 2 行时剪掉大量分支，实际访问的节点数会掉好几个数量级。**这就是剪枝的威力——同样的算法骨架，加了剪枝就能从「跑不动」变成「秒出解」。**

### 剪枝的两种典型形式

剪枝没有固定公式，但常见两种：

- **可行性剪枝**：当前选择**违反约束**，直接跳过。比如 N 皇后里「这一列已经有皇后了」；组合总和里「当前和已经超过 `target` 了」
- **最优化剪枝**：在求解最优解的场景里，当前路径已经**不可能是最优**，直接跳过。（本篇聚焦枚举，这种剪枝在分支限界法里更常见）

### 剪枝降低的是什么：上界还是实际节点数

这就是本篇最重要的**认知纠偏点**，也是面试官最爱追问的。

**剪枝不改变复杂度的上界（Big-O），它改变的是实际遍历的节点数。**

原因很简单：剪枝是「**在运行时根据具体数据判断走不走**」——它无法在「算法复杂度的数学分析」层面保证一定剪掉某个比例。最坏情况下（数据极端刁钻），你可能一个分支都剪不掉，复杂度上界还是原来的指数级。

举个例子：N 皇后的理论复杂度上界仍然是 `O(n!)`——因为「最坏情况下」你还是得尝试接近阶乘数量级的摆法。但**实际运行时**，因为每一行都剪掉了绝大多数非法位置，真正访问的节点数远小于上界，所以 8 皇后能秒出、甚至能跑到更大的 n。

> 💬 **面试官**：剪枝的作用是什么？它降低的是复杂度上界，还是实际节点数？
>
> ✅ 标准答案：剪枝的作用是**在递归前判断当前路径是否不可能产生合法解，若不可能就提前 return，剪掉整根子树**。它降低的是**实际遍历的节点数，而不是理论复杂度上界**——复杂度分析看的是最坏情况，而最坏情况下剪枝可能一个分支都剪不掉，所以上界（比如 N 皇后的 `O(n!)`）不变。剪枝的价值在于「对**真实输入**大幅减少无效分支」，让原本跑不动的指数级搜索变得可行。
>
> 🎁 加分答案：能点出剪枝的**两种分类**（可行性剪枝「违反约束就跳过」、最优化剪枝「当前路径不可能更优就跳过」），以及一句关键区分——**「降低上界」靠的是换算法（比如把指数级枚举换成 DP），而「降低实际节点数」靠的是剪枝**。能举 N 皇后「8^8 ≈ 1677 万种摆法 vs 加一个同列判断后节点数掉几个数量级」这个具体数字，说服力会强很多。还可以补一句：**剪枝的收益高度依赖数据分布**，这也是为什么算法分析里不能把剪枝算进 Big-O。

## 🆚 回溯 vs DFS：一字之差

很多人把「回溯」和「深度优先搜索（DFS）」当成一回事，其实它们的关系是「**包含**」，不是「等于」。

### DFS 是遍历策略，回溯是加了特性的 DFS

**DFS（深度优先搜索）** 是一种**遍历策略**：沿着一条路一直走到底，走不动了再回退到上一个岔路口，换一条路继续走。它强调的是「**怎么遍历一棵树 / 一张图**」。

**回溯**是在 DFS 的基础上，额外加了三样东西：

- **撤销选择**：显式地把状态恢复到进入分支之前
- **剪枝**：走到不可能有解的地方就提前掉头
- **收集解**：路径构成完整解时，把它记下来

一句话概括：

> **回溯 = DFS + 撤销选择 + 剪枝。**

也就是说：**回溯一定是 DFS（它靠深度优先的方式遍历决策树），但 DFS 不一定是回溯**——比如「遍历一棵二叉树打印所有节点」，它是 DFS，但它既没有「撤销选择」的需求（不需要恢复什么状态），也没有「选择列表」的概念，所以不是回溯。

对照第 11 篇《搜索》里讲的 DFS：那里 DFS 是「**探索所有路径、检测环、拓扑排序**」的通用遍历工具；而这里的回溯，是 DFS 在「**枚举 + 约束**」问题上的专门形态。

### 回溯和递归 / 分治 / DP 的关系

把本篇和前两篇串起来，得到这张「关系网」表，面试时能把这张表说出来，理解深度立刻不一样：

| 概念 | 核心特征 | 与回溯的关系 |
|------|---------|-------------|
| 递归 | 函数调用自身的**机制** | 回溯**用递归**来实现「往下试一支」 |
| DFS | 深度优先的**遍历策略** | 回溯是**带了撤销和剪枝的 DFS** |
| 分治 | 子问题**相互独立** + 有合并步 | 分治是「拆完再组装」，回溯是「枚举所有可能」 |
| 动态规划 | 子问题**相互重叠** + 取最优 | DP 求**最优解**，回溯求**所有解/可行解** |
| **回溯** | 枚举决策树 + 撤销选择 + 剪枝 | —— |

> 💬 **面试官**：回溯和 DFS 的区别是什么？
>
> ✅ 标准答案：**回溯 = DFS + 撤销选择 + 剪枝**。DFS 只是一种「沿着一条路走到黑、走不通就回退」的**遍历策略**，它本身不强调状态恢复；回溯是在 DFS 的框架上，**显式地做「选择 → 递归 → 撤销选择」，并配合剪枝提前掉头**。所以回溯一定用 DFS，但 DFS 不一定是回溯——比如单纯遍历二叉树就是 DFS，不是回溯。
>
> 🎁 加分答案：能进一步点出回溯的**问题类型**——它专门解决「**枚举所有可能**（全排列、子集、组合）」或「**找一个可行解**（N 皇后、单词搜索）」的问题，而 DFS 更多用于「**遍历/搜索图或树本身**」（连通性、拓扑排序、最短路径的穷举版）。再补一句区分回溯和 DP：**DP 求最优解、回溯求全部解**——如果题目问「有多少种」「列出所有」，想想是不是回溯；如果问「最少/最多是多少」，想想是不是 DP。能主动做这个分类判断，说明你不只是背了模板。

## 📐 复杂度：用「决策树有多少节点」来描述

回溯的复杂度，不能像排序那样简单地标一个 `O(n log n)`——因为它常常是**指数级（`O(2ⁿ)`）或阶乘级（`O(n!)`）**。

正确的描述方式，是**数决策树的节点数**：

- **全排列**：第 1 层有 n 个选择，第 2 层有 n−1 个，第 3 层有 n−2 个……决策树的叶子数是 `n × (n−1) × … × 1 = n!`，所以时间复杂度 `O(n!)`
- **子集**：每个元素都有「选 / 不选」两种可能，一共 n 个元素，所以是 `2ⁿ` 个子集，复杂度 `O(2ⁿ)`
- **N 皇后**：理论上界 `O(n!)`

**注意「上界」和「实际」的差别**：上面的 `O(n!)` / `O(2ⁿ)` 是**最坏情况的上界**。加了剪枝后，实际遍历的节点数通常远小于上界——但**复杂度的数学上界写出来还是那个指数级**。这就是为什么上一节要反复强调「剪枝降的是实际节点数，不是上界」。

空间复杂度方面，回溯的开销主要是**递归调用栈的深度**：全排列递归 n 层，N 皇后递归 n 层，所以空间复杂度通常是 `O(n)`（不含结果集本身）。

📌 顺带对照一下笔记里给的数据：全排列时间复杂度 `O(n!)`、空间复杂度 `O(n)`；子集时间复杂度 `O(2ⁿ)`、空间复杂度 `O(n)`——**和上面按决策树数节点的方法完全一致**。

### 全排列：模板的标准演示

**题目（LeetCode 46）**：给定一个**没有重复**的数字序列，返回其所有可能的全排列。

**思路**：

- 要求「所有排列情况」且「没有重复元素」
- 有出路、也有死路 → 使用回溯

**解题步骤**：

- 用递归模拟出所有情况
- 遇到包含重复元素的情况，就回溯
- 收集所有到达递归终点的情况，并返回

先把笔记里的**回溯树**搬出来，这张图是理解一切的关键——它画的就是「选择 → 撤销 → 再选择」的完整过程：

![全排列的回溯决策树：每一步「选择」进入下一层，每一步「撤销」回到上一层再换一个选择](https://cdn.nlark.com/yuque/0/2022/png/738210/1642430963361-7ec6edff-e629-499c-a66e-88c2ba81a22d.png)

图里的关键，藏在那句注释里：**「正是因为在上一步撤销了对 2 的选择，在这一步才能再选择 2——这是在深度优先遍历的过程中，需要状态重置的意义。」** 换句话说，图上每一条「往上退回」的箭头，都是一次 `path.pop()`；没有这些「退回」，后面那些分支根本选不了。

**笔记原版实现（`concat` 写法）**：

```typescript
// todo 全排列
export function permute(nums: number[]): number[][] {
  const res: number[][] = [];
  const backtrack = (path: number[]) => {
    // console.log(path, res)
    if(path.length === nums.length) {
      res.push(path);
      return;
    }
    nums.forEach(n => {
      // console.log('n', n)
      if(path.includes(n)) return;
      backtrack(path.concat(n)); // path为引用类型这里要使用concat，返回一个新数组，防止输出结果都为空
    });
  }
  backtrack([]);
  return res;
};
```

复杂度：

- 空间复杂度：`O(n)`

**再看「标准模板版」（`push/pop` 写法）**，方便你做对照——它才是更通用、更该记的那一套：

```typescript
export function permuteTemplate(nums: number[]): number[][] {
  const res: number[][] = [];
  const path: number[] = [];                  // 👈 路径：复用的同一个数组
  const used: boolean[] = [];                 // 👈 选择列表用 used 标记：尚未被选的才可选

  const backtrack = () => {
    if (path.length === nums.length) {        // 👈 结束条件：排满了
      res.push([...path]);                    // 👈 推「拷贝」，不能推 path 本身
      return;
    }
    for (let i = 0; i < nums.length; i++) {
      if (used[i]) continue;                  // 👈 剪枝：已用过的跳过
      used[i] = true;                         // 做选择
      path.push(nums[i]);
      backtrack();                            // 递归
      path.pop();                             // 撤销选择
      used[i] = false;                        // 👈 撤销「标记」，与做选择严格对称
    }
  };

  backtrack();
  return res;
}
```

对比一下：`used` 数组就是**显式的选择列表**，而 `used[i] = true` 和 `used[i] = false` 这一对，正是上一节讲的「**镜像对称**」——**凡是被改过的状态，都要在递归回来后原样撤销**。

> 💬 **面试官**：全排列里，为什么 `res.push(path)` 会出 bug，而 `res.push([...path])` 不会？
>
> ✅ 标准答案：数组是**引用类型**。`res.push(path)` 存的是**同一个数组的引用**，之后 `path.pop()`、`path.push()` 会持续修改这个数组，导致 `res` 里所有项最终都指向同一个（被清空的）数组，结果全是空的。`[...path]` 做了一个**浅拷贝**，存进去的是一个快照，后续 `path` 怎么变都不影响它。
>
> 🎁 加分答案：能顺带指出**同类陷阱**——比如 `path.slice()`、`Array.from(path)` 都是拷贝，效果一样；再往深一层说，`concat` 写法之所以天然没这个问题，就是因为它每一步返回的都是新数组，所以它既不用 `push/pop` 也不用拷贝，代价是每层都新建数组、空间开销更大。能对比出「**牺牲空间换代码简单**」这个取舍，说明你理解两种写法的本质区别。

### 子集：用 `start` 保证「后选的都在后面」

**题目（LeetCode 78）**：给你一个**没有重复**元素的整数数组，返回该数组所有可能的子集。

**思路**：

- 要求「所有子集」且「没有重复元素」
- 有出路、也有死路 → 使用回溯

**解题步骤**：

- 用递归模拟出所有情况
- **保证接的数字都是后面的数字**（这一点是子集题的关键，往下看）
- 收集所有到达递归终点的情况，并返回

**笔记原版实现**：

```typescript
// todo 子集
export function subsets(nums: number[]): number[][] {
  const res: number[][] = [];
  const backtrack = (path: number[], l: number, start: number) => {
    if(path.length === l) { // 递归结束条件
      res.push(path);
      return;
    }
    for (let i = start; i < nums.length; i++) {
      backtrack(path.concat(nums[i]), l, i + 1);
    }
  }
  for (let i = 0; i <= nums.length; i++) {
    backtrack([], i, 0);
  }
  return res;
};
```


复杂度：

- 时间复杂度：`O(2ⁿ)`
- 空间复杂度：`O(n)`

**为什么子集要用 `start`？** 这是组合类问题的通用技巧，值得单独说。

如果子集也用全排列那套「`used` 标记 + 从 0 开始遍历」，那么 `[1,2]` 和 `[2,1]` 会被当成**两个不同的子集**——但子集是无序的，这俩其实是同一个。所以子集必须**去重**，办法就是：**每次只允许选「当前位置之后」的元素**，用一个 `start` 参数控制下标。

```
从 [1,2,3] 选子集：
  选了 1（start 记为 0 之后）→ 下一步只能从下标 1 往后选 → 得到 [1,2]、[1,3]
  选了 2 → 下一步只能从下标 2 往后选 → 得到 [2,3]     ← 不会出现 [2,1]
  选了 3 → 后面没了 → 得到 [3]
```

**「保证后选数字都是后面的」这一句，就是组合类问题和排列类问题的分水岭**：排列关心顺序（谁在后面都行），组合/子集不关心顺序（只能往后选）。记住这个区别，`39 组合总和`、`40 组合总和 II`、`77 组合` 一大票题都能直接套。

> 💬 **面试官**：子集问题里，为什么不能像全排列那样从 0 开始遍历，而要用 `start` 控制起点？
>
> ✅ 标准答案：因为**子集是无序的**，`[1,2]` 和 `[2,1]` 是同一个子集。如果从 0 开始遍历、不做限制，就会把同一个子集的**不同排列**重复收集，结果大量重复。用 `start` 参数限制「每一步只能选当前下标之后的元素」，就强制了「后选的元素一定在后面」，从而每个子集**只被枚举一次**。
>
> 🎁 加分答案：能把这个技巧**归类**——「**排列**关心顺序，用 `used` 标记；**组合/子集**不关心顺序，用 `start` 下标」是回溯题型的两大分支，一看到题目问「所有组合」就往 `start` 想、问「所有排列」就往 `used` 想。再深一层能提：如果数组**有重复元素**（如 LeetCode 40、90），还要加一步「**同层去重**」——在同一层里跳过和前一个相等的元素（通常配合先排序），否则会产出重复子集。能主动想到「有序 / 有重复」这个变体，说明你刷的不是一道题而是一类题。

### N 皇后：剪枝的标杆案例

**题目（LeetCode 51）**：n 皇后问题，研究的是如何将 n 个皇后放置在 `n × n` 的棋盘上，并且使皇后彼此之间**不能相互攻击**。皇后可以攻击**同一行、同一列、同一条对角线上**的棋子。给你一个整数 n，返回所有不同的解决方案。

这个问题是**剪枝的教科书案例**，因为它的搜索空间大得离谱，全靠剪枝才能跑得动。

**先把「不剪枝有多恐怖」算清楚**：n=8 时，8 个皇后、每个皇后有 8 行可选，朴素枚举是 `8^8 = 16,777,216` 种摆法。而实际上 8 皇后只有 **92 个解**——也就是说，99.9995% 的尝试都是白费的。剪枝要做的，就是在「明显不可能」的时候提前掉头。

**回溯 + 剪枝的思路**：

- **决策树的每一层 = 棋盘的一行**，在每一行里，**选一个列**放皇后
- **剪枝条件（三个约束）**：放下皇后前，检查这个位置是否和已放的皇后冲突——① 同列冲突 ② 主对角线冲突 ③ 副对角线冲突，任一冲突就 `continue` 跳过
- **结束条件**：放满了 n 行（`row === n`），收集一个解

下面这张图画的就是「一行一行往下放，每放一个就立刻检查冲突」的过程：

![N 皇后回溯示意：逐行放置皇后，每一行只尝试不与之前冲突的列（发布前请自行转存素材库）](https://assets.leetcode-cn.com/solution-static/51/51_fig1.PNG)

**对角线冲突怎么快速判断？** 这是实现上的关键技巧——用数学关系把「同一条对角线」压成一个下标：

- **主对角线（左上 → 右下，`\`）**：同一对角线上的格子，满足 `行 - 列` 相等，所以用 `row - col` 作索引（可能为负，加个偏移量 `n - 1` 转正）
- **副对角线（右上 → 左下，`/`）**：同一对角线上的格子，满足 `行 + 列` 相等，所以用 `row + col` 作索引（范围 `0 .. 2n-2`）

这样，判断「是否和已放皇后同对角线」就从「扫一遍所有已放的皇后」降成了 **O(1) 的一次数组查询**。

```typescript
export function solveNQueens(n: number): string[][] {
  const res: string[][] = [];
  // 👈 三个「占用标记」数组：这就是「剪枝」所依赖的状态
  const cols = new Set<number>();                 // 已占用的列
  const diag1 = new Set<number>();                // 已占用的主对角线（row - col）
  const diag2 = new Set<number>();                // 已占用的副对角线（row + col）
  const board: number[] = [];                     // 路径：board[row] = col，表示第 row 行皇后放在第 col 列

  const backtrack = (row: number) => {
    if (row === n) {                              // 👈 结束条件：n 行都放好了
      res.push(board.map(col =>                     // 把 [col] 转成 "..Q." 形式的字符串
        Array.from({ length: n }, (_, c) => (c === col ? 'Q' : '.')).join('')
      ));
      return;
    }
    for (let col = 0; col < n; col++) {
      // 👈 剪枝：当前列、两条对角线任一被占，就跳过这个位置
      if (cols.has(col) || diag1.has(row - col) || diag2.has(row + col)) continue;

      cols.add(col);                              // 做选择
      diag1.add(row - col);
      diag2.add(row + col);
      board.push(col);

      backtrack(row + 1);                         // 递归：处理下一行

      board.pop();                                // 撤销选择（与做选择严格对称）
      cols.delete(col);
      diag1.delete(row - col);
      diag2.delete(row + col);
    }
  };

  backtrack(0);
  return res;
}
```

复杂度：

- 时间复杂度：上界 `O(n!)`（**剪枝不改变这个上界**），但实际访问节点数远小于上界
- 空间复杂度：`O(n)`（递归栈 + 三个标记集合）

**注意：剪枝前后对比**——把上面 `if (cols.has(col) || ...) continue;` 这一行**删掉**，不剪枝版本会去尝试 `n^n` 种摆法（n=8 时 1677 万种），虽然也能跑出正确结果，但耗时会长好几个数量级。这就是「同一套回溯骨架，加一行剪枝，性能天壤之别」。

> 💬 **面试官**：N 皇后里，你是怎么判断两条对角线冲突的？为什么可以 O(1) 判断？
>
> ✅ 标准答案：用**行、列坐标的线性关系**。同一条**主对角线**（左上到右下）上的格子满足 `row - col` 相等，同一条**副对角线**（右上到左下）上的格子满足 `row + col` 相等。所以只要维护两个集合记录「已被占用的 `row - col` / `row + col`」，放下皇后时查一次集合就能 O(1) 判断冲突，不用去遍历所有已放的皇后。
>
> 🎁 加分答案：能补两点——① 用集合时 `row - col` 可能为负数，如果改用数组做标记需要加偏移量 `n - 1` 转成非负下标；② 这体现了回溯里一个重要的性能思想：**把「每次都要重新扫描的检查」预处理成「可 O(1) 查询的标记」**，代价是维护标记（做选择时加、撤销时删）。这个思想在「组合总和里维护当前和」「单词搜索里就地修改棋盘」里都会反复出现——**用额外的状态换检查的效率**。

### 组合总和：带「和」约束的剪枝

**题目（LeetCode 39）**：给你一个**无重复元素**的整数数组 `candidates` 和一个目标整数 `target`，找出 `candidates` 中可以使数字和为 `target` 的**所有不同组合**。`candidates` 中的同一个数字可以**无限制重复被选取**。

**思路**：它和子集高度相似（都是组合枚举），区别在于**多了两个约束**——① 数字可以重复用 ② 要凑到 `target`。这两点直接决定了两种剪枝。

**解题步骤**：

- 用回溯枚举所有组合
- **用 `start` 控制起点**（和子集一样，避免组合重复）
- **剪枝一（可行性）**：当前和已经**超过** `target`，直接 `return`
- **剪枝二（排序优化）**：先把数组**排序**，一旦某个数加上去就超标，后面更大的数更超标，直接 `break`
- **允许重复选取**：递归时传 `i` 而不是 `i + 1`

```typescript
export function combinationSum(candidates: number[], target: number): number[][] {
  const res: number[][] = [];
  const path: number[] = [];
  candidates.sort((a, b) => a - b);              // 👈 排序，为「剪枝二」服务

  const backtrack = (start: number, sum: number) => {
    if (sum === target) {                        // 👈 结束条件：正好凑够
      res.push([...path]);
      return;
    }
    for (let i = start; i < candidates.length; i++) {
      if (sum + candidates[i] > target) break;   // 👈 剪枝二：已排序，后面的更大，直接 break
      path.push(candidates[i]);                  // 做选择
      backtrack(i, sum + candidates[i]);         // 👈 传 i（不是 i+1）：允许重复选自己
      path.pop();                                // 撤销选择
    }
  };

  backtrack(0, 0);
  return res;
}
```

复杂度：

- 时间复杂度：`O(n^(target/min))` 级别（受 `target` 和最小元素限制），剪枝后实际节点数大幅减少
- 空间复杂度：`O(target / min)`（递归栈深度）

⚠️ **注意「传 `i` 还是传 `i + 1`」这个一字之差**：传 `i + 1` 是「每个数只能用一次」（那就是 LeetCode 40 组合总和 II）；传 `i` 才是「同一个数可以重复用」（LeetCode 39）。**这是组合类回溯最容易写错的地方，也是面试官特别爱问的一个细节。**

### 单词搜索：在网格上做回溯

**题目（LeetCode 79）**：给定一个 `m × n` 的二维字符网格 `board` 和一个字符串单词 `word`，如果 `word` 存在于网格中，返回 `true`。单词必须按照字母顺序，通过**相邻的格子**（上、下、左、右）内的字母构成，同一个格子内的字母**不允许被重复使用**。

**思路**：这是回溯在**二维网格**上的应用——决策树的每一层是「当前格子的四个方向」，选择列表是「四个相邻格子」。

**解题步骤**：

- **遍历每个格子作为起点**，对每个起点跑一次回溯
- **结束条件**：匹配到了单词的最后一个字符，返回 `true`
- **剪枝**：越界、字符不匹配、格子已被访问过，任一情况直接返回 `false`
- **状态恢复（关键）**：访问过的格子**先标记，递归后恢复**——这正是回溯的「撤销选择」在网格题里的形态

```typescript
export function exist(board: string[][], word: string): boolean {
  const rows = board.length;
  const cols = board[0].length;

  const backtrack = (r: number, c: number, idx: number): boolean => {
    if (idx === word.length) return true;                 // 👈 结束条件：单词匹配完
    // 👈 剪枝：越界 / 字符不匹配 / 已访问
    if (r < 0 || r >= rows || c < 0 || c >= cols) return false;
    if (board[r][c] !== word[idx]) return false;

    const temp = board[r][c];
    board[r][c] = '#';                                    // 做选择：标记已访问（就地修改）
    const found =
      backtrack(r + 1, c, idx + 1) ||                     // 往四个方向递归
      backtrack(r - 1, c, idx + 1) ||
      backtrack(r, c + 1, idx + 1) ||
      backtrack(r, c - 1, idx + 1);
    board[r][c] = temp;                                   // 👈 撤销选择：恢复原字符

    return found;
  };

  for (let r = 0; r < rows; r++) {
    for (let c = 0; c < cols; c++) {
      if (backtrack(r, c, 0)) return true;                // 任一格子作为起点能搜到即返回 true
    }
  }
  return false;
}
```


复杂度：

- 时间复杂度：`O(m × n × 3^L)`，L 是单词长度，每个格子开始搜索、每个位置最多往 3 个方向扩展（不回头的方向）
- 空间复杂度：`O(L)`，递归栈深度等于单词长度

⚠️ **这道题最妙的一点是「就地修改棋盘」**：我们没有额外开一个 `visited` 数组，而是直接把走过的格子改成 `'#'`，递归回来再改回原字符。**「改掉 → 递归 → 改回」这一对操作，就是「做选择 → 递归 → 撤销选择」在二维网格上的直接对应**。能看出「单词搜索和全排列其实是同一套模板」，说明你真的把回溯抽象出来了。

## 🔧 前端工程落地

回溯不只是刷题的思想，它在你每天用的框架和引擎里也真实地跑着。这一节对上两处。

### React 的 `completeUnitOfWork`：一次教科书级的「回溯」

第 03 篇《栈》、第 11 篇《搜索》里都提到过 React Fiber：它的工作循环是一个**「递推 + 回溯」**的迭代过程，两个核心函数就是 `performUnitOfWork` 和 `completeUnitOfWork`。

- **`performUnitOfWork`（递推 / 「做选择」）**：处理当前 Fiber 节点，然后往下钻到它的 `child`（第一个子节点）
- **`completeUnitOfWork`（回溯 / 「撤销选择」）**：当一个节点的**所有子节点都处理完了**，就**沿着 `fiber.return` 指针回到父节点**，继续处理父节点的下一个兄弟

```
  performUnitOfWork：往下钻，处理 child
       │
       ▼
    [节点 A] ──child──▶ [节点 B] ──child──▶ [节点 C]  ← 一直往下（DFS 递推）
       ▲
       │  所有子节点处理完，completeUnitOfWork 沿 fiber.return 退回父节点
       └────────────────────────────────────────────────
```

看出来了吗？**「一个分支处理完，沿着 `return` 指针回到上一层，再换一个兄弟分支继续」——这正是回溯的遍历形态**。区别只在于：React 的 Fiber 遍历**不需要「撤销选择」**，因为它走的是「一次性构建/更新整棵树」，而不是「枚举所有可能的解后再回退」。

📌 这里正好点出一个重要区别：**「回溯返回上一层」是遍历形态（DFS 的共性），而「回溯算法」还额外要求「撤销选择」和「剪枝」**。React 的 Fiber 遍历有前者、没有后者，所以它是 DFS 而非「回溯算法」——这也印证了上一节「回溯 = DFS + 撤销选择 + 剪枝」那个公式。

### 正则回溯与 ReDoS：灾难性回溯的真实威胁

这是回溯复杂度的**最真实、最有杀伤力的工程案例**，也是前端安全里一个常被忽略的坑。

**正则引擎（尤其是回溯型引擎，如 JS 的 RegExp）在匹配时用的就是回溯**：当一条路径匹配失败，引擎会**回退到上一个「选择点」，换一种方式继续尝试**。绝大多数时候这没什么问题——但如果正则有**嵌套量词**，回溯量会指数级爆炸。

看这个经典的危险正则：

```javascript
const evil = /(a+)+b/;              // 👈 嵌套量词：(a+)+ —— 外层 + 套着内层 +
const input = 'aaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!';  // 30 个 a，末尾是没有 b 的非法串

evil.test(input);                  // ⚠️ 会卡住，CPU 直接飙升
```

**为什么会爆炸？** 因为 `(a+)+` 允许「这些 `a` 被分组」的方式有**指数多种**——30 个 `a` 可以有 `2^29` 种分组方式。当末尾找不到 `b` 时，引擎会把**每一种分组方式都试一遍**，确认全部失败才返回 `false`。30 个字符就能让浏览器标签页卡死，这就是 **ReDoS（Regular Expression Denial of Service，正则拒绝服务攻击）**。

```
(a+)+b 匹配 "aaaa...a!"（末尾无 b）
  ├─ 第 1 个 a 单独成组 → 剩下 "aaa...a!"...
  ├─ 前 2 个 a 一组 → 剩下 "aa...a!"...
  ├─ 前 3 个 a 一组 → ...
  └─ ...每个分法都要试到末尾发现没 b 才放弃 → 2^29 量级的尝试
```

🔧 **真实场景**：如果前端有一个「用户自定义正则校验」的功能（比如运营配置药品编码的校验规则），或者后端的接口用正则校验输入，攻击者只要构造一个精心设计的输入串，就能让 **主线程的 JS 或后端进程 CPU 打满、服务不可用**。这在前端是「页面卡死」，在后端就是「服务被拖垮」。

**怎么避免？** 三条实用原则：

- **避免嵌套量词**：`(a+)+`、`(a*)*`、`(a|a)*` 这类「量词套量词」的结构是重灾区，尽量改写成等价但不嵌套的写法，如 `(a+)+b` 可写成 `a+b`
- **用非回溯（原子组 / 占有量词）**：JS 较新版本支持**原子组 `(?>...)`** 和**后行断言**来切断回溯；如果环境不支持，可以用「**先锚定、再逐步匹配**」的写法限制回溯范围
- **限制输入长度 + 设超时**：对用户输入的正则和待匹配文本都做长度上限；Node.js 端可以用 `worker_threads` 把正则匹配放到独立线程，加超时兜底

> 💬 **面试官**：正则的 ReDoS（灾难性回溯）是怎么产生的？如何避免？
>
> ✅ 标准答案：ReDoS 来自正则引擎的**回溯机制**。当正则有**嵌套量词**（如 `(a+)+`）时，同一个输入串会有**指数多种匹配分组方式**；一旦匹配失败，引擎要把每一种分组方式都回溯试一遍，才能确认失败。像 `(a+)+b` 匹配一串 `a` 加一个非 `b` 结尾的串，回溯次数就是 `2^n` 量级——30 个字符就能让 CPU 打满，导致页面或服务不可用。
>
> 🎁 加分答案：能点出「**这本质上是回溯的最坏复杂度在真实世界的体现**」——和 N 皇后不剪枝一样，都是「决策树爆炸」，只不过这里的「决策」是「如何切分字符串」。再补上**工程解法**：① 改写正则以消除嵌套量词（`(a+)+b` → `a+b`）；② 用原子组 `(?>...)`、占有量词切断回溯；③ 对输入长度设上限、给正则匹配加超时（Node 里放 `worker_threads` 独立线程）。能顺带说「这也是为什么代码扫描工具会把 `(a+)+` 这类模式标为高危」，说明你有安全视角，不只是会写正则。

## 🎓 面试高频问（汇总标准答案）

把本篇四个核心面试问集中在这里，方便复习速查。

**问 1：回溯的三要素是什么？「撤销选择」为什么必不可少？**

✅ 三要素是**路径（已经做出的选择）、选择列表（当前还能做的选择）、结束条件（到达决策树底层，收集结果）**。「撤销选择」必不可少，因为它让**状态恢复到进入分支之前**——同层下一个分支必须在干净状态上开始，否则上一支的残留会污染结果；同时撤销也让同一个路径变量能被反复复用，不必每条分支都新建。注意收集结果时要推**拷贝**（`[...path]`）。

**问 2：回溯和 DFS 的区别是什么？**

✅ **回溯 = DFS + 撤销选择 + 剪枝**。DFS 只是一种「沿着一条路走到黑、走不通再回退」的**遍历策略**；回溯在 DFS 的框架上额外做了「选择 → 递归 → 撤销选择」和「剪枝提前掉头」。所以回溯一定用 DFS，但 DFS 不一定是回溯——单纯遍历二叉树是 DFS，不是回溯。补一句：**DP 求最优解，回溯求所有解/可行解**。

**问 3：剪枝的作用是什么？它降低的是复杂度上界还是实际节点数？**

✅ 剪枝的作用是**递归前判断当前路径不可能产生合法解，若不可能就提前 return、剪掉整根子树**。它降低的是**实际遍历的节点数，不是理论复杂度上界**——复杂度看最坏情况，最坏时剪枝可能一个分支都剪不掉，上界（如 N 皇后的 `O(n!)`）不变。剪枝的价值是对**真实输入**大幅减少无效分支，让指数级搜索变得可行。8 皇后不剪枝要试 `8^8 ≈ 1677 万`种摆法，加剪枝后节点数掉好几个数量级。

**问 4：正则的 ReDoS（灾难性回溯）是怎么产生的？如何避免？**

✅ 正则引擎匹配时用的就是回溯。当正则有**嵌套量词**（如 `(a+)+`）时，同一串输入有**指数多种分组方式**，匹配失败时引擎要逐一把每种方式都回溯试一遍，`(a+)+b` 匹配 `a^n` 就是 `2^n` 量级，30 个字符就能打满 CPU（ReDoS）。避免方法：① 消除嵌套量词（`(a+)+b` → `a+b`）；② 用原子组 `(?>...)` / 占有量词切断回溯；③ 限制输入长度、给正则匹配加超时（Node 里放 `worker_threads` 独立线程）。
