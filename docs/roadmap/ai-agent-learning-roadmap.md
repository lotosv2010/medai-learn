### 1.0 本文件 / 阶段大纲 与 docs/plans/ 系列大纲的区别

> 这一节回答一个容易被忽略的问题：**同样是「大纲」，为什么 AI 这条路要单独一个文件、单独一套流程。**

| 维度 | `docs/plans/` 系列大纲 | 本路线图 + 阶段大纲 |

### 1.1 职业定位（三合一）

> 本章回答「往哪里去」，后续主线回答「怎么去」。

```
┌─────────────────────────────────────────┐
│           FDE / 解决方案工程师            │  ← 对外：客户场景、需求洞察、方案包装
│         （医疗行业背景变现）              │
├─────────────────────────────────────────┤
│           AI Agent 开发者                │  ← 纵深：Agent架构、Tool Use、工作流编排
│         （技术深度护城河）                │
├─────────────────────────────────────────┤
│           AI 应用工程师                  │  ← 基础：RAG、Prompt、流式对话、工程化
│         （工程化能力底盘）                │
└─────────────────────────────────────────┘
```

| 层级 | 角色 | 一句话定位 | 对应主线阶段 |
|------|------|-----------|-------------|
| **L1 基础层** | AI 应用工程师 | 把 AI 应用做出来、做得稳 | 阶段一~四、八、九 |
| **L2 纵深层** | AI Agent 开发者 | 把应用做聪明、能自主行动 | 阶段五、六 |
| **L3 场景层** | FDE / 解决方案工程师 | 把方案卖出去、落下去 | 贯穿 + 阶段十 |

**为什么是这个组合**：前端 10 年经验天然擅长「客户界面」与工程化交付，是 FDE 最稀缺的能力；医疗电商背景构成行业壁垒；Agent 开发提供技术护城河。三层互相拉动——能「做出来」→「做聪明」→「卖出去」。

> FDE 的完整转型路径、Echo/Delta 能力框架与市场数据，见已发布文章 `docs/articles/00 AI/2026-09-09-fde-forward-deployed-engineer-career-transition.md`。

**目标公司类型**：

| 类型 | 代表 | 切入角色 |
|------|------|----------|
| 医疗AI公司 | 医渡科技、讯飞医疗、百度灵医 | AI应用工程师 → 技术负责人 |
| 互联网医疗 | 京东健康、平安健康、微医 | Agent开发 / FDE |
| AI Infra公司 | 百川、智谱、月之暗面 | FDE / 解决方案架构师 |
| 传统药企数字化 | 辉瑞、诺华、药明康德 | FDE / 技术顾问 |
| AI Native初创 | 各类医疗AI创业公司 | 全栈AI工程师 / 技术合伙人 |

### 1.2 两条核心原则

**1. 应用开发优先，原理够用即止**

转型 AI 应用工程师，重心在**「怎么把大模型用对、用好、用稳」**，不在「怎么造模型」。

- Transformer 的数学推导、注意力机制的矩阵计算、预训练的数据工程——这些**理解到「能解释现象」即可**（例如：为什么上下文窗口有限、为什么长上下文会「注意力稀释」），不必深挖论文与公式。
- 微调（Fine-tuning）需要知道**原理、场景、工具、数据格式**，但要动手的是「LoRA 微调一个开源模型跑通闭环」，而不是「从零预训练一个模型」。

> 一句话：**你是模型的使用者与编排者，不是模型的训练者。** 除非明确的岗位方向是算法/训练，否则把 80% 的精力投在应用层。

**2. JS/TS 生态优先，扬长避短**

作为前端 + Node.js 全栈，你的独特优势在**应用层工程化**，这是纯算法背景的人补不来的：

| 你的既有优势 | 在 AI 应用层的对应战斗力 |
|-------------|------------------------|
| TypeScript 类型系统 | Schema 设计、Function Calling 类型约束、端到端类型安全 |
| SSE / 流式处理经验 | Token 流式渲染、打字机效果、边生成边渲染 |
| React / Next.js 工程化 | AI 对话 UI、生成式 UI、RSC Streaming |
| Node.js 后端 + BFF | AI 网关、多模型路由、降级链、语义缓存 |
| 前端监控 / 可观测性 | LLM 调用链路追踪、成本监控、质量反馈 |

**框架选型的清醒认知**：JS/TS 生态下，**Vercel AI SDK 是前端 AI 应用的第一主力**（原生拥抱 Next.js / React / SSE），LangChain 家族作为「跨语言通识」学习其概念抽象（Chain / Agent / Retriever / LangGraph），但**不必把它当 JS 生态的实践主线**——LangChain 的 Python 生态更成熟，JS 版维护节奏偏慢。

### 1.3 一条主线：从「会调用」到「能生产」

整个路线图沿一条数据流主线递进：

```
认知地基 → 调用能力 → 上下文工程 → 检索增强 → 智能体 → 模型定制 → 生产落地 → 前沿扩展
  认识        API         Context        RAG       Agent      微调/部署    评估安全     多模态
```

- **前置思想**：先「认识大模型」建立正确心智模型，避免把 LLM 当搜索引擎或数据库用。
- **应用底座**：所有上层能力（RAG / Agent）都建立在「调用 + 流式 + 结构化输出 + Embedding」四件事之上，必须先打牢。
- **核心进阶**：Context Engineering 是 2025 年后的关键认知跃迁——**Agent 效果的天花板，往往取决于你把什么内容、以什么顺序放进了上下文窗口**。
- **两大能力**：RAG（检索增强）与 Agent（智能体）是 AI 应用的两条主线，分别解决「知识不足」与「行动能力不足」。
- **生产收尾**：微调、部署、评估、安全、可观测——决定 Demo 能否变成生产系统。

**阶段依赖关系**（串行主线 + 可并行支线）：

```
一（认知）→ 二（调用）→ 三（上下文）→ 四（RAG）→ 五（Agent）→ 九（生产化）
                          └───────────────┐        └──── 六（框架整合）↗
                                          ↓
                          七（微调）→ 八（部署）
                          
                    十（前沿扩展，可随时按需切入）
```

- **串行主线**：一 → 二 → 三 → 四 → 五，前五阶段是能力递进，不可跳。
- **可并行支线**：七（微调）依赖四、八（部署）依赖二（七的产物为八的可选输入）；六（框架整合）依赖二与五，可与九并行推进。
- **按需切入**：十（前沿扩展）无硬性依赖，完成阶段二后随时可选做。

## 二、主线

### 阶段一：认知地基（认识大模型）

> 解决「大模型是什么、能信多少、该用哪个」的心智模型问题。

**前置依赖**：无

> **文章大纲**：`docs/roadmap/ai-phase-01-cognitive-foundation-outline.md`（5 篇，每篇配一个 `labs/phase1-cognition/` 下的真实 API 实验）
> **文章归档**：`docs/articles/00 AI/01 认知地基/`

**学习目标**：建立对 LLM 的正确心智模型，能理性判断「什么能信、什么不能信、什么时候该用哪个模型」。

#### 核心知识点

| 知识点 | 要点 | 掌握程度 |
|--------|------|---------|
| LLM 的本质 | 预测下一个 token 的概率机器，不是搜索引擎、不是数据库、不是推理引擎 | 能向同事解释清楚 |
| 核心概念 | Token / 上下文窗口 / 温度 / Top-p / Top-k / 推理模型（o1、R1 类） | 会调参、知道影响 |
| 能力边界 | 幻觉（Hallucination）、知识截止（Knowledge Cutoff）、注意力稀释 | 知道触发条件与规避手段 |
| 模型图谱与选型 | GPT / Claude / Gemini / 通义 / DeepSeek / 开源模型怎么选 | 能按任务选型 |
| 训练全景（了解） | 预训练 → SFT → RLHF 三阶段，推理 vs 训练、开源 vs 闭源 | 建立全局地图即可 |
| Tokenizer 与计费 | 分词原理、Token 与计费关系、中文 token 开销 | 会估算成本 |

#### 关键认知

- **幻觉不是 bug，是特性**：模型本质是在「生成最可能的续写」，不是「检索事实」。凡是要求事实准确性的场景（医疗、法律、金融），都必须靠 RAG 或工具调用兜底，不能指望模型记忆。
- **上下文窗口 ≠ 有效注意力**：窗口号称 128K、200K，但「中间内容」的召回率显著下降（Lost in the Middle）。长上下文不是免费午餐。
- **推理模型 ≠ 普通模型**：o1 / DeepSeek-R1 类模型会「先思考再回答」，适合复杂推理任务，但更慢更贵，简单任务用不上。

#### 学习里程碑

- [ ] 能解释「为什么大模型会一本正经地胡说八道」
- [ ] 能根据任务（简单问答 / 复杂推理 / 长文档理解）选择合适的模型与参数

**产出物**：一份「模型选型 + 成本估算」备忘录（记录常用模型的价格、上下文窗口、适用场景与选型理由）。

### 阶段二：应用底座（调用能力）

> 解决「怎么把模型调用起来」的问题，是前端 + Node 的主场。

**前置依赖**：阶段一

**学习目标**：掌握「调用大模型」的四块地基——多模型接入、流式输出、结构化输出、向量嵌入。**这是前端 + Node 的主场，必须扎实。**

#### 模块 2.1 — API 接入与多模型抽象

- 主流 API 对比：OpenAI / Anthropic / 通义千问 / DeepSeek 的请求结构、流式格式、错误类型差异
- **多模型抽象（Strategy Pattern）**：定义统一的 `AIProvider` 接口（`chat` / `embed`），业务层只认接口，换模型不改业务代码
- **降级链设计**：区分「限流 / 暂时不可用」（应 fallback）与「参数错误 / 权限错误」（应直接抛出）
- **模型路由**：按任务复杂度路由（省成本）vs 按可用性路由（保稳定），两个维度可叠加
- **接口演进（了解）**：OpenAI Responses API 已成为推荐主接口（相对 Chat Completions）；离线批处理（Batch API / Message Batches）用于大批量、非实时场景降成本
- Node.js 后端：如何封装统一的 AI 网关层（对应 `packages/ai-sdk` / `apps/ai-engine`）

#### 模块 2.2 — 流式输出（Streaming / SSE）

- LLM 流式的本质：`AsyncIterable<Delta>`，每个 Delta 是一小段 token
- **SSE vs WebSocket vs 轮询**：AI 文本流是单向「服务端持续推」场景，SSE 是标准答案，不必上 WebSocket
- 服务端：`ReadableStream` + `text/event-stream`，逐 Delta 写出
- 前端消费：`EventSource` / `fetch + ReadableStream.getReader()`，避免每个 token 触发一次完整重渲染
- Node.js 侧注意：代理/网关的超时设置、心跳保活、断线重连

#### 模块 2.3 — 结构化输出与 Function Calling

- **System Prompt / Few-shot / CoT 的定位区分**：分别解决「定角色边界 / 校正输出格式 / 引导推理」——不是越多越好
- **结构化输出两条路径**：① Prompt 约定 JSON + 依赖模型服从；② 原生 `response_format: json_schema` / Tool 定义（API 层强制约束，更可靠）
- **Function Calling 的本质**：模型不执行代码，只输出「该调用哪个函数、传什么参数」的结构化意图，**真正的执行在你的代码里**——这是 Agent 的地基
- **Schema 设计原则**：字段命名贴近业务语义、可选字段默认值兜底、枚举值显式列出
- TypeScript 配合：用 Zod 定义 Schema，运行时校验 + 类型推导一举两得

#### 模块 2.4 — Embedding 与语义相似度

- Embedding 的本质：把文本映射到高维向量空间，语义相近则向量距离近
- 相似度度量：余弦相似度 / 欧氏距离 / 点积，各自适用场景
- Embedding 模型选择：`text-embedding-3-small/large`、开源 `bge` 系列，维度与成本权衡
- 这是 RAG（阶段四）的直接前置，先把「文本 → 向量 → 比相似度」这条链路跑通

#### 模块 2.5 — AI 应用的异步与并发

- **Node.js 事件循环与 LLM 调用**：LLM API 是典型 I/O 密集型，避免阻塞主线程
- **并发控制**：`Promise.all` / `Promise.allSettled` 批量调用、限流（Rate Limiting）、队列管理
- **超时与重试**：指数退避、熔断器模式（Circuit Breaker）、死信队列
- **背压（Backpressure）**：流式场景下，下游消费慢于上游产出时的缓冲策略

- [ ] 跑通一个「多模型可切换 + SSE 流式 + 结构化输出」的最小 Node 服务
- [ ] 前端接入流式输出，实现打字机效果，且不因逐 token 渲染而卡顿
- [ ] 实现并发调用多个 LLM API（如同时调 3 个模型对比输出），控制并发数并处理超时降级

### 阶段三：上下文工程（Context Engineering）★核心进阶

> 解决「有限的上下文窗口里放什么、按什么顺序放」的问题。

**前置依赖**：阶段二

> **这是本路线图相较「只会调用 API」的传统路径最重要的认知补充。** 2025 年业界共识：Agent / RAG 的效果上限，往往不由模型决定，而由**你如何组织送进模型的那一段上下文**决定。

**学习目标**：理解「上下文窗口是稀缺资源」，学会像管理内存一样管理上下文。

#### 模块 3.1 — Prompt 基础（上下文工程的下位概念）

- 角色设定（Role / Persona）、指令清晰化、分隔符使用
- Few-shot 示例设计（示例数量、顺序敏感性与偏差）
- **思维链 CoT**：让模型「先推理再作答」，提升复杂任务准确率
- **ReAct**：Reasoning + Acting，Agent 的前置思想（阶段五展开）
- 反思（Reflection）：让模型自我批判、自我修正
- System Prompt 设计规范：角色、边界、拒绝策略、输出格式约束
- **Prompt 版本管理**：把 Prompt 当代码管理（版本化 / 可回滚 / 可 A/B / 可回归测试），为阶段九评估铺路

#### 模块 3.2 — 上下文组装（Context Assembly）

- 一次调用的上下文里可能同时有：System Prompt + 对话历史 + RAG 检索片段 + 工具描述 + 工具返回结果 + 用户输入
- **上下文预算管理**：为每类内容分配 Token 配额，避免某一类（如超长检索结果）挤占其他
- 内容顺序的影响：关键信息放头部/尾部 vs 中间（Lost in the Middle）

#### 模块 3.3 — 上下文压缩与裁剪

- 历史对话压缩：摘要化（Summary Buffer）、滑动窗口、关键信息提取
- RAG 片段裁剪：只保留真正相关的句子而非整块
- 工具结果精简：不要把冗长的工具原始返回直接塞进上下文

#### 模块 3.4 — 记忆系统（Memory）

- **短期记忆**：对话窗口内历史（进程内 / Redis 会话）
- **长期记忆**：跨会话记忆，通常用向量库存储「事实片段」，按需检索回上下文
- 记忆写入策略：什么值得记、什么时候记、如何避免噪音污染
- 记忆的遗忘与更新：过期、冲突、错误记忆的修正

#### 模块 3.5 — Prompt Caching 与成本优化（易漏）

- **Prompt Caching 原理**：把不变的前缀（System Prompt / 工具定义 / 长文档）缓存起来，命中时按更低价格计费——Anthropic / OpenAI / 通义均已支持
- **缓存友好的上下文排列**：**稳定内容在前、易变内容在后**（前缀一变，后面全部失效）
- 与「上下文压缩」的取舍：压缩省的是每次调用的 token，缓存省的是重复前缀的钱，两者可叠加
- 实测：多轮对话场景下，Prompt Caching 通常能把输入成本降到 1/5 ~ 1/10

#### 模块 3.6 — 长上下文策略（Long Context）

- **长上下文 vs RAG 的取舍**：窗口够大 ≠ 该把整本书塞进去——成本、延迟、注意力稀释三重代价
- 常见策略：分段 Map-Reduce 摘要、递归摘要、关键段落定位后再精读
- 上下文窗口扩展技术（了解）：RoPE 外推、位置插值——知道「长上下文能力是怎么来的」即可

#### 关键认知

- **上下文是新的「内存」，Token 是新的「成本单位」**：每一次调用都在花预算，工程目标是在效果与成本之间找平衡。
- **Context Engineering ⊃ Prompt Engineering**：Prompt 只是上下文的一小块，真正难的是「多来源内容如何编排进有限窗口」。

#### 学习里程碑

- [ ] 设计一个对话系统的上下文组装方案：System + 历史压缩 + RAG 片段 + 工具结果，各有配额
- [ ] 实现一个「跨会话长期记忆」，验证 Agent 能记住上一轮会话里说过的事实
- [ ] 对比开启/关闭 Prompt Caching 的成本差异（同一对话 10 轮），量化缓存收益

**产出物**：一个带上下文组装、历史压缩、长期记忆与 Prompt Caching 的对话系统。

### 阶段四：RAG（检索增强生成）

> 解决「模型知识不足 / 知识过期」的问题，让模型基于外部知识回答。

**前置依赖**：阶段二、阶段三

**学习目标**：掌握「让模型基于外部知识回答」的完整链路，从索引构建到检索优化，再到高级 RAG 范式。

#### 模块 4.1 — RAG 原理与架构

- RAG 完整链路：文档预处理 → 分块 → 向量化 → 存储 → 检索 → 重排序 → 拼接 Prompt → 生成
- **RAG vs 微调**（面试高频）：RAG 是「检索时注入知识，可随时更新，不改模型参数」；微调是「训练时把知识编码进权重，更新需重训」。**知识频繁更新的场景（医疗说明书）优选 RAG**。

#### 模块 4.2 — 文档分块（Chunking）

- 分块策略：固定长度 / 语义边界（按段落、标题、章节）/ 滑动窗口（重叠）
- **Chunk 大小的权衡**：太大 → 检索精度低、稀释注意力；太小 → 语义不完整
- 医疗场景实践：按说明书章节（适应症 / 用法用量 / 禁忌）切块，保留标题作为语义锚点

#### 模块 4.3 — 向量数据库

- 选型：**pgvector**（已有 Postgres 时首选，工程成本最低）/ Milvus / Qdrant / Chroma / Weaviate
- 索引原理（了解即可）：HNSW / IVFFlat，知道「建索引换召回率 vs 速度」
- 应用层设计：向量列 + 原文列 + 结构化元数据列；检索前过滤 vs 检索后过滤

#### 模块 4.4 — 检索优化

- **Top-K 调参**：从 Top-10 起步，用测试集统计 Recall@K，找曲线拐点
- **混合检索（Hybrid Search）**：向量检索（语义）+ 全文检索（关键词精确匹配，如 PostgreSQL FTS），用 **RRF** 融合排序——弥补纯向量对专有名词、精确数字不敏感的短板
- **重排序（Reranking）**：向量检索是「粗筛」，Cross-Encoder 重排序是「精筛」——两阶段配合是检索系统通用范式
- **排查顺序**：RAG 效果差 → 先查分块 → 再查 Top-K → 再查重排序 → 最后才考虑换 Embedding 模型
- **Contextual Retrieval（了解）**：Anthropic 提出——为每个 chunk 前置一段「该 chunk 的上下文说明」，让检索更精准
- **多向量 / 延迟分块（了解）**：ColBERT 多向量、Late Chunking，用更细粒度表示提升召回
- **评估意识前置**：正式的评估体系在阶段九展开，但「测试集 + 量化指标」的意识应从本阶段建立并延续

#### 模块 4.5 — 高级 RAG

| 范式 | 解决什么问题 |
|------|-------------|
| **HyDE** | 用「假想答案」而非原问题去检索，提升召回 |
| **Self-RAG** | 模型自我判断「检索是否必要 / 检索结果是否有用」 |
| **GraphRAG** | 用知识图谱组织实体关系，解决多跳推理与全局性问题 |
| **Agentic RAG** | 让 Agent 自主决定「查什么、查几次、要不要换工具查」 |
| **多路召回 + 融合** | 多个检索器并行，结果融合，提升覆盖 |
| **多模态检索（了解）** | ColPali 等，直接对文档图像做视觉检索 |

#### 模块 4.6 — 文档解析与数据工程（易漏但必需）

- **PDF 解析**：扫描件 OCR、双栏排版、表格还原——真实企业文档的脏活
- **结构化抽取**：从说明书/法规文档中抽取「适应症 / 禁忌 / 剂量」等字段
- **增量索引**：文档更新时只重建变化部分，避免全量重跑
- **数据版本管理**：知识库版本与检索结果可追溯（合规场景必需）
- 工具：Unstructured / LlamaParse / MinerU（PDF 解析）

#### 模块 4.7 — 多租户与知识库隔离（企业级）

- 不同客户/科室的知识库物理或逻辑隔离
- 检索时强制过滤条件（`tenant_id`），防止跨租户数据泄露
- 向量库的分区策略与索引隔离

#### 学习里程碑

- [ ] 用 pgvector 搭一个药品说明书问答，跑通「分块 → 向量化 → 检索 → 生成」
- [ ] 构造测试集，量化对比「纯向量检索」vs「混合检索 + 重排序」的 Recall 差异
- [ ] 处理一份真实 PDF 说明书（含表格），抽取出结构化字段并回答准确率验证

**产出物**：药品说明书 RAG 问答（第一个可见成果，贯穿项目的起点）。

### 阶段五：Agent（智能体）

> 解决「模型只能答、不能做」的问题，让模型自主决策、调用工具、多步完成任务。

**前置依赖**：阶段三、阶段四

**学习目标**：从「单次问答」跨越到「能自己决定做什么、调用工具、多步完成任务」的智能体系统。

#### 模块 5.1 — Agent 基础：Tool Use / Function Calling

- **Agent vs Chatbot**（面试高频）：Chatbot 文本进文本出；Agent 能感知环境（调用工具）、自主决定下一步，是「感知-决策-行动」循环
- Tool Use 完整流程：传工具 Schema → 模型输出调用意图 → 你的代码执行工具 → 结果回传模型 → 模型生成最终回答
- **单次工具调用 vs 多步编排**：简单场景一问一工具；复杂场景需连续调用多个工具

#### 模块 5.2 — 规划模式（Planning）

| 模式 | 核心思想 |
|------|---------|
| **ReAct** | Thought → Action → Observation 循环，边想边做 |
| **Plan-and-Execute** | 先规划完整步骤，再逐步执行 |
| **Reflection** | 执行后自我批判、修正重试 |
| **Tree of Thoughts** | 多路径探索，适合复杂决策（了解） |

#### 模块 5.3 — 单 Agent 实战

- 工具设计原则：**只读查询 vs 写操作**必须显式区分权限
- 错误处理：工具失败、参数幻觉、API 超时
- **循环终止**：最大步数上限（`maxSteps`），防止无限循环烧成本
- 常见失败模式：工具调用死循环、幻觉不存在的工具或参数
- **人机协作（Human-in-the-Loop）**：关键决策点暂停、人工审批后继续——医疗场景必需
- **断点续跑**：长流程中断后恢复，状态持久化与幂等性设计

#### 模块 5.4 — 多智能体系统（Multi-Agent）

- **Supervisor 模式**：协调者路由任务给专家 Agent，专家执行后返回汇总（路径可控、易调试，**推荐起步**）
- **Peer-to-Peer 模式**：Agent 间直接传消息，无中心协调者（适合扁平协作）
- 框架：LangGraph（状态机 / 图编排）、AutoGen、CrewAI（了解选型）
- **工程风险**：路由错误、循环死锁（协调者反复来回路由）→ 需最大跳转次数 + 显式终止状态

#### 模块 5.5 — MCP 协议（Model Context Protocol）

- MCP 是什么：Anthropic 主导的**开放协议**，统一「AI 客户端如何发现和调用外部工具 / 数据源」
- 三种能力原语：Tools（可调用函数）/ Resources（可读数据）/ Prompts（提示词模板）
- 架构角色：MCP Host / Client / Server；传输层 stdio（本地）与 Streamable HTTP（远程，已取代早期 HTTP+SSE）
- **认证与安全（了解）**：MCP 已加入 OAuth 授权规范，生产部署需权限范围控制
- **MCP vs 手写 Function Calling**：手写是「项目私有协议」，MCP 是「标准化、可插拔、可分发」——把工具能力做成独立服务，被任意兼容客户端（Claude Desktop / Claude Code）复用
- 用 TypeScript 写 MCP Server 实战
- 安全边界：暴露 MCP Server 等于开放内部能力，需权限范围控制 + 审计日志

#### 模块 5.6 — Agent 安全与护栏（Guardrails）

- 输入护栏：注入检测、敏感话题拦截
- 工具护栏：写操作二次确认、权限最小化、执行沙箱（Agent 沙箱 / 容器隔离）
- 输出护栏：敏感信息过滤、免责声明、事实校验
- 预算护栏：最大步数、最大 Token、超时熔断

#### 模块 5.7 — Agent 可观测与调试（易漏）

- **Trace 可视化**：一次 Agent 运行中每一步的「思考 → 工具调用 → 结果」全链路回放
- **失败归因**：区分「模型选错工具 / 参数填错 / 工具本身失败 / 结果理解错」
- **回归测试集**：为 Agent 建「黄金任务集」，每次改动跑一遍防止能力退化
- **工具 Mock 与单元测试**：用 mock 工具替身隔离外部依赖，先测「编排逻辑」再测「真实集成」
- 工具：LangSmith / Langfuse / Braintrust

#### 模块 5.8 — Agent 架构演进（前沿了解）

- **Computer Use / Browser Use**：Agent 直接操作图形界面（Claude Computer Use、Playwright MCP）
- **Agentic Workflow vs Autonomous Agent**：前者是「预定义流程 + LLM 节点」，后者是「LLM 自主决策」——生产环境通常优先前者（可控性）
- **A2A 协议**（Agent-to-Agent）：跨厂商 Agent 互操作协议（Google 主导，了解即可）

#### 学习里程碑

- [ ] 手写一个 ReAct 循环 Agent（含步数上限与异常兜底），完成「查库存 → 查价格 → 汇总」多步任务
- [ ] 把内部检索能力包装成 MCP Server，用 Claude Code 作为 Host 验证工具被正确发现与调用
- [ ] 给 Agent 接入 Trace 平台，完整回放一次失败运行的每一步，定位失败根因

**产出物**：用药咨询 Agent（基于阶段四的 RAG，增加多步工具调用与护栏）。

### 阶段七：模型定制（私有化微调）

> 解决「要不要微调、怎么微调」的问题，但默认优先 RAG 与 Prompt。

**前置依赖**：阶段四

**学习目标**：理解「什么时候该微调」，跑通一次 LoRA 微调闭环，但**默认优先 RAG 与 Prompt**。

#### 模块 7.1 — 微调决策（先想清楚要不要做）

> **微调 vs RAG vs Prompt 的选择**：绝大多数「知识不足」问题用 RAG 解决；「格式 / 风格 / 语气」问题用 Prompt 解决；只有当需要「把特定能力固化进模型」（如固定输出格式、领域术语、任务特化）时才考虑微调。

| 需求 | 首选方案 |
|------|---------|
| 补充/更新知识 | RAG |
| 控制输出格式/风格 | Prompt + 结构化输出 |
| 固化特定任务能力、降低推理成本 | 微调（LoRA） |
| 对齐人类偏好 | DPO / RLHF（进阶） |

#### 模块 7.2 — 微调原理与方式

- **全量微调 vs 参数高效微调（PEFT）**：LoRA / QLoRA 原理——只训练少量低秩适配器，显存与成本大幅降低
- **SFT（有监督微调）**：构造「指令 - 回答」数据对
- **对齐进阶（了解）**：DPO（直接偏好优化）、RLHF

#### 模块 7.3 — 数据准备与标注

- SFT 数据格式：指令 / 输入 / 输出，或对话式 messages 格式
- 数据质量 > 数量：少量高质量样本往往胜过大量脏数据
- 数据构造方法：真实业务日志清洗、LLM 生成 + 人工校验、开源数据集复用

#### 模块 7.4 — 工具链

- **LLaMA-Factory**：一站式微调框架（WebUI + 命令行），适合入门
- **Unsloth**：高效微调，速度快、显存省
- **Axolotl**：配置驱动的微调工具链
- 硬件现实：消费级 GPU（如 24G 显存）可跑通 QLoRA 微调 7B 级模型

#### 学习里程碑

- [ ] 用 LLaMA-Factory + QLoRA 微调一个 7B 开源模型，让它学会一种固定输出格式
- [ ] 对比微调前后模型在同一测试集上的表现，验证微调是否真的必要

**产出物**：一个跑通 LoRA 微调闭环的开源模型（固化医疗领域输出格式）。

### 阶段八：部署与推理优化

> 解决「模型怎么跑起来、跑得动、跑得省」的问题。

**前置依赖**：阶段二

> 部署并不依赖微调——用 Ollama / vLLM 跑开源模型本身不需要先做阶段七。阶段七的微调产物只是本阶段「部署微调后模型」那个里程碑的**可选输入**，非必经前置。

**学习目标**：把模型「跑起来」并「跑得动」——本地部署、云端部署、推理加速与量化。

#### 模块 8.1 — 推理优化基础

- **量化**：GGUF（llama.cpp 生态，CPU/混合）/ GPTQ / AWQ（GPU）——用精度换显存与速度
- **KV Cache**：缓存注意力键值，避免重复计算（理解长上下文为何吃显存）
- 批处理（Batching）：连续批处理提升 GPU 利用率
- **推理优化进阶（了解）**：投机解码（Speculative Decoding）、PD 分离（Prefill/Decode 分离）、chunked prefill

#### 模块 8.2 — 推理框架选型

| 框架 | 定位 |
|------|------|
| **Ollama** | 本地一键跑模型，开发调试首选 |
| **llama.cpp** | CPU / 混合推理，GGUF 量化生态 |
| **vLLM** | 高吞吐生产级 GPU 推理（PagedAttention） |
| **SGLang** | 与 vLLM 并列的生产级推理引擎，RadixAttention 缓存优化 |
| **TGI** | Hugging Face 推理服务框架 |

#### 模块 8.3 — 部署形态

- **本地部署**：Ollama + Open WebUI，个人 / 内网场景
- **云端部署**：GPU 云（按需 / 竞价）、Serverless 推理（冷启动 vs 成本）
- **容器化**：Docker 打包、K8s 编排、GPU 资源调度
- **API 网关**：自建网关做多模型路由、限流、鉴权、计费
- **端侧 / 浏览器推理**：Transformers.js / WebLLM 在浏览器 WebGPU 本地跑小模型，适配隐私敏感、离线场景，与云端推理互补

#### 模块 8.4 — 性能与成本监控

- 延迟指标：TTFT（首字节）、TPS（每秒 token）、端到端耗时
- 吞吐与并发：QPS、并发数、GPU 利用率
- 成本核算：显存占用、GPU 时长计费、按 Token 计费

#### 学习里程碑

- [ ] 用 Ollama 本地跑一个开源模型，并用 OpenAI 兼容接口接入自己的应用
- [ ] 用 vLLM 部署一个模型，压测对比 Ollama 的吞吐差异

**产出物**：用 Ollama / vLLM 部署阶段七微调后的模型，接入自己的应用。

### 阶段九：生产化（评估 / 可观测 / 安全 / 成本）

> 解决「Demo 怎么变成生产系统」的问题。

**前置依赖**：阶段四、阶段五

**学习目标**：把 Demo 变成「可度量、可监控、可兜底、成本可控」的生产系统。

#### 模块 9.1 — 评估体系（Evals）

- **离线评估**：固定测试集在改动前后跑，对比量化指标（Recall@K / MRR / 生成质量分），低成本可重复
- **在线评估**：真实流量 A/B 测试，成本高但反映真实用户行为
- **LLM as Judge**：用另一个模型给回答打分（相关性 / 准确性 / 有害性）——**不能完全替代人工**，高风险场景（医疗）需人工抽样校准
- 测试集构建：覆盖边界情况（模糊问题、超纲问题、易触发幻觉的问题），持续从真实反馈补充失败案例
- 工具：Ragas（RAG 评估）/ LangSmith / 自建评估套件

#### 模块 9.2 — 可观测性（Observability）

- 日志：完整 Prompt / Response / 耗时 / Token 数
- 指标：P50/P95 延迟、错误率、Token 消耗趋势、按模型/功能拆分的成本
- 追踪：一次请求跨越「RAG 检索 → 模型调用 → Agent 工具调用」的完整链路耗时分布
- AI 特有维度：输出质量信号（用户点赞/点踩），是评估体系获取真实数据的来源
- 工具：LangSmith / Langfuse / OpenTelemetry

#### 模块 9.3 — 安全（Security）

- **Prompt Injection**：直接注入（用户输入恶意指令）vs 间接注入（恶意指令藏在 Agent 读取的第三方内容里，更危险）
- 为什么难根治：LLM 无法从结构上区分「开发者指令」与「用户输入」，都是同一窗口里的文本
- **分层防御**：①System Prompt 边界 + 拒绝策略；②输入侧模式检测；③工具权限边界（只读 vs 写）；④输出侧敏感信息过滤
- 数据泄露：防止 System Prompt、内部工具列表、用户隐私被套取
- OWASP Top 10 for LLM Applications

#### 模块 9.4 — 成本控制

- **成本构成拆解**：输入 Token（通常更便宜）+ 输出 Token（更贵）+ Embedding 调用 + 重排序 API
- **模型分级路由**：简单任务走 mini 模型，复杂任务走强模型
- **语义缓存**：基于向量相似度判断「这个问题问过类似的」，直接返回缓存——区别于普通缓存的精确匹配
- **上下文精简**：控制 RAG 片段数量与长度、历史压缩，减少无用输入 Token
- **预算告警**：按用户/租户/功能维度设成本上限，超阈值告警或降级

#### 模块 9.5 — 数据隐私与合规（医疗场景必补）

- **PII / PHI 脱敏**：调用外部模型前对姓名、身份证、病历号做掩码或替换
- **数据不出境**：境内业务用境内模型；敏感数据走私有化部署
- **数据留存策略**：日志里的 Prompt / Response 是否含隐私，保留多久，谁能看
- **合规红线**：个保法 / 数据安全法 / 生成式 AI 服务管理暂行办法 / 算法备案 / 大模型备案 / 深度合成规定 / 医疗AI器械审批（二类/三类证）的边界认知
- **审计留痕**：谁在什么时候问了什么、模型答了什么，可追溯

#### 学习里程碑

- [ ] 给一次完整问答请求埋点，画出「检索 / 模型 / 工具 / 生成」各环节耗时分布
- [ ] 构建一个含边界题的测试集，量化对比两版 Prompt 的效果
- [ ] 设计一套医疗场景的数据脱敏方案：哪些字段脱敏、在哪一层脱敏、脱敏后效果如何验证

**产出物**：给「多智能体会诊」项目补上评估、监控、安全与成本控制，形成生产级系统。

## 三、附录

### A. 前端 + Node.js 定制学习建议

**1. 扬长：把已有优势变成差异化**

- **阶段二（调用能力）与阶段十（前端 AI 工程化）是主场**，投入最多精力打磨到「能讲能写能落地」。
- TypeScript 类型系统 → 直接用在 Schema 设计、Function Calling 类型约束、端到端类型安全（tRPC 思路迁移）。
- SSE / Node 后端经验 → 直接用在 AI 网关、流式服务、降级链。

**2. 避短：不在非主场深挖**

- 阶段一不深挖 Transformer 数学；阶段七不追求从零训练；原理理解到「能解释现象、能讲清取舍」即可。

**3. 框架选型清醒**

- **实践主线：Vercel AI SDK**（JS/TS 原生、拥抱 Next.js/React/SSE）。
- **概念通识：LangChain 家族**（理解 Chain / Agent / Retriever / LangGraph 抽象，不追 JS 版源码）。

**4. 一条贯穿的落地项目**

用**一个医疗 AI 助手**贯穿全部阶段，边学边出成果：

```
药品说明书 RAG 问答  →  用药咨询 Agent  →  多智能体会诊  →  私有化部署 + 微调  →  带评估/监控的生产系统
```

每一步都复用前一步的产物，最终汇成一个完整的作品集项目（对齐本项目 `apps/ai-engine` / `packages/ai-sdk`）。

**5. 两条学习节奏**

- **快速上手线**（拿正反馈）：阶段一 → 二 → 三 → 四 → 五（跳过微调/部署，先把「能用」跑通）。
- **系统进阶线**（全面完整）：一 → 二 → 三 → 四 → 五 → 六 → 七 → 八 → 九，微调/部署/评估作为生产化收尾。

**6. FDE 能力培养（贯穿始终）**

FDE 不是独立阶段，而是**贯穿所有阶段的视角**：

| 学习阶段 | 技术目标 | FDE 视角 |
|---------|---------|---------|
| 阶段二 调用能力 | 跑通多模型切换 | 能向客户解释「为什么选这个模型」「成本怎么算」 |
| 阶段四 RAG | 搭建药品说明书问答 | 能演示「知识更新后效果立竿见影」，对比微调方案 |
| 阶段五 Agent | 实现多步工具调用 | 能设计「客户业务流程 → Agent 工作流」的映射 |
| 阶段九 生产化 | 评估、监控、安全 | 能交付「效果报告 + 风险清单 + 迭代计划」 |
| 项目实战 | 完成医疗AI助手 | 能输出「需求文档 → 技术方案 → POC 演示 → 交付报告」全套材料 |

**核心心法**：每学一个技术点，问自己三个问题——**这解决什么业务问题？客户愿意为此付多少钱？我怎么证明它有效？**
