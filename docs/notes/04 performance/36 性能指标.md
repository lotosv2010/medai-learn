# 核心Web指标（Core Web Vitals）
## LCP (Largest Contentful Paint)
+ **定义**：页面主要内容加载完成的时间点，即视口内最大的内容元素渲染完成的时间
+ **计算方法**： 
    - 从页面开始加载到最大内容元素（图片、视频、块级文本等）渲染完成的时间
    - 通过 PerformanceObserver API 监听：`new PerformanceObserver((list) => {...}).observe({type: 'largest-contentful-paint', buffered: true})`
    - 或使用 `web-vitals` 库：`import {onLCP} from 'web-vitals'`
+ **意义**：衡量页面加载性能，反映用户感知的页面加载速度
+ **标准**：良好 < 2.5s，需要改进 2.5-4s，差 > 4s

## FID (First Input Delay)
+ **定义**：用户首次与页面交互（点击链接、按钮等）到浏览器实际响应的延迟时间
+ **计算方法**： 
    - 交互事件触发时间到事件处理函数开始执行的时间差
    - 通过 PerformanceObserver 监听 `first-input` 类型
    - `web-vitals` 库：`onFID(callback)`
+ **意义**：衡量页面交互响应性，反映主线程是否被长任务阻塞
+ **标准**：良好 < 100ms，需要改进 100-300ms，差 > 300ms
+ ⚠️ ‼️ **<font style="color:#DF2A3F;">现已逐渐被 INP 替代</font>**

## CLS (Cumulative Layout Shift)
+ **定义**：页面整个生命周期中所有意外布局偏移的累积分数
+ **计算方法**： 
    - 布局偏移分数 = 影响分数 × 距离分数
    - 通过 PerformanceObserver 监听 `layout-shift` 类型
    - 累加所有非用户操作导致的布局偏移
+ **意义**：衡量视觉稳定性，避免用户误点击
+ **标准**：良好 < 0.1，需要改进 0.1-0.25，差 > 0.25

## INP (Interaction to Next Paint)
+ **定义**：从用户交互到下一帧绘制的延迟时间，取整个页面生命周期中最差的交互延迟
+ **计算方法**： 
    - 测量从交互开始到视觉反馈呈现的完整时间
    - 包含输入延迟、处理时间、渲染延迟
    - 通过 Event Timing API 获取
+ **意义**：取代 FID，更全面地衡量页面交互响应性
+ **标准**：良好 < 200ms，需要改进 200-500ms，差 > 500ms

# 加载性能指标
## FCP (First Contentful Paint)
+ **定义**：页面首次渲染任何文本、图像、非白色canvas或SVG的时间点
+ **计算方法**： 
    - `performance.getEntriesByType('paint').find(entry => entry.name === 'first-contentful-paint')`
    - Navigation Timing API 提供
+ **意义**：标志页面开始加载的视觉反馈
+ **标准**：良好 < 1.8s，需要改进 1.8-3s，差 > 3s

## FP (First Paint)
+ **定义**：浏览器首次渲染任何内容到屏幕上的时间点
+ **计算方法**： 
    - `performance.getEntriesByType('paint').find(entry => entry.name === 'first-paint')`
+ **意义**：页面开始渲染的最早时间点，白屏时间的结束
+ **标准**：通常应 < 1s

## TTI (Time to Interactive)
+ **定义**：页面完全可交互的时间点，主线程空闲且可以快速响应用户输入
+ **计算方法**： 
    - FCP 之后，5秒窗口期内没有长任务（>50ms）
    - 网络请求基本完成
    - 通常使用 Lighthouse 或 `tti-polyfill` 计算
+ **意义**：衡量页面何时真正可用
+ **标准**：良好 < 3.8s，需要改进 3.9-7.3s，差 > 7.3s

## FMP (First Meaningful Paint)
+ **定义**：页面主要内容对用户可见的时间点
+ **计算方法**： 
    - 已被 LCP 替代，Lighthouse 6.0 后不再使用
    - 之前通过最大布局变化来估算
+ **意义**：衡量用户感知的首屏渲染时间
+ **标准**：⚠️ ‼️ **<font style="color:#DF2A3F;">已弃用，建议使用 LCP</font>**

## SI (Speed Index)
+ **定义**：页面内容视觉填充的速度，数值越小越好
+ **计算方法**： 
    - 通过视频帧分析或视觉进度计算
    - Lighthouse 提供此指标
    - 计算可见内容填充的平均时间
+ **意义**：综合反映页面加载的视觉体验
+ **标准**：良好 < 3.4s，需要改进 3.4-5.8s，差 > 5.8s

## TTFB (Time to First Byte)
+ **定义**：从浏览器发起请求到接收到服务器返回的第一个字节的时间
+ **计算方法**： 
    - `performance.timing.responseStart - performance.timing.requestStart`
    - 或使用 Navigation Timing API Level 2
+ **意义**：衡量服务器响应速度和网络延迟
+ **标准**：良好 < 600ms，需要改进 600ms-1s，差 > 1s

## DCL (DOMContentLoaded)
+ **定义**：HTML 文档被完全加载和解析完成的时间点
+ **计算方法**： 
    - `performance.timing.domContentLoadedEventEnd - performance.timing.navigationStart`
    - 或监听 `DOMContentLoaded` 事件
+ **意义**：标志 DOM 树构建完成，脚本可以安全操作 DOM
+ **标准**：通常应 < 2s

## L (Load/onLoad)
+ **定义**：页面所有资源（图片、样式、脚本等）加载完成的时间点
+ **计算方法**： 
    - `performance.timing.loadEventEnd - performance.timing.navigationStart`
    - 或监听 `load` 事件
+ **意义**：标志页面完全加载完成
+ **标准**：通常应 < 5s

## 白屏时间 (Time to First Paint / Blank Screen Time)
+ **定义**：从用户开始访问页面到页面开始有内容呈现的时间，即页面出现第一个像素点的时间
+ **计算方法**： 
    - **方法1（推荐）**：使用 FP (First Paint) 指标

```javascript
const fp = performance.getEntriesByType('paint')
  .find(entry => entry.name === 'first-paint');
const whiteScreenTime = fp ? fp.startTime : 0;
```

+ **方法2**：传统方式（不太准确）

```javascript
// 在 <head> 中尽早执行
const startTime = Date.now();
// 在 <body> 开始或首个可见元素处
const whiteScreenTime = Date.now() - startTime;
```

+ **方法3**：使用 Navigation Timing API

```javascript
// domLoading 是文档开始解析的时间点
const whiteScreenTime = performance.timing.domLoading - 
  performance.timing.navigationStart;
```

+ **方法4**：更精确的自定义埋点

```javascript
// 在 HTML <head> 最前面
window.pageStartTime = Date.now();

// 在首屏关键内容渲染后
window.whiteScreenTime = Date.now() - window.pageStartTime;
```

+ **意义**： 
    - 反映用户感知的最直接指标，白屏时间过长会让用户认为页面"卡住了"
    - 影响用户留存率，研究表明白屏超过 3 秒会导致用户流失率显著上升
    - 是最重要的首屏性能指标之一，直接影响用户体验
+ **标准**： 
    - 优秀：< 1s
    - 良好：1-2s
    - 需要优化：2-3s
    - 差：> 3s
+ **优化方向**： 
    - 减少 DNS 查询时间（DNS 预解析）
    - 优化服务器响应时间（TTFB）
    - 使用 CDN 加速静态资源
    - 减少关键路径资源（critical resources）
    - 内联关键 CSS，延迟加载非关键 CSS
    - 减少首屏 JavaScript 体积
    - 使用骨架屏或 Loading 占位符改善感知性能
    - 启用 HTTP/2 或 HTTP/3
    - 使用 SSR（服务端渲染）或 SSG（静态生成）
+ **与其他指标的关系**： 
    - **白屏时间 ≈ FP**：白屏结束通常就是 FP 时刻
    - **白屏时间 < FCP**：FCP 是有意义内容的绘制
    - **白屏时间 << LCP**：LCP 是主要内容加载完成
    - 关系链：**白屏时间(FP) → FCP → LCP → TTI**
+ **注意事项**： 
    - 白屏时间是用户体验的"生死线"，应该作为最高优先级指标监控
    - 不同的统计方法可能得出不同结果，建议使用标准的 FP 指标
    - 单页应用(SPA)的白屏时间往往比传统多页应用(MPA)更长，需要特别优化

## 首屏时间 (Above the Fold Time / First Screen Time)
+ **定义**：页面首屏内容完全展示所需的时间，即用户可见区域（viewport）内的所有内容加载并渲染完成的时间点
+ **计算方法**： 
    - **方法1（推荐）**：使用 LCP (Largest Contentful Paint) 作为近似值

```javascript
import {onLCP} from 'web-vitals';

onLCP((metric) => {
  const firstScreenTime = metric.value;
  console.log('首屏时间:', firstScreenTime);
});
```

+ **方法2**：自定义埋点 - MutationObserver 监听 DOM 变化

```javascript
let firstScreenTime = 0;
const observer = new MutationObserver(() => {
  // 计算首屏元素是否加载完成
  const firstScreenElements = document.querySelectorAll('.first-screen');
  const allLoaded = Array.from(firstScreenElements).every(el => {
    return el.complete || el.readyState === 'complete';
  });

  if (allLoaded && !firstScreenTime) {
    firstScreenTime = performance.now();
    observer.disconnect();
  }
});

observer.observe(document.body, {
  childList: true,
  subtree: true
});
```

+ **方法3**：图片加载完成检测

```javascript
window.addEventListener('load', () => {
  const images = document.querySelectorAll('img[data-first-screen]');
  let loadedCount = 0;

  images.forEach(img => {
    if (img.complete) {
      loadedCount++;
    } else {
      img.addEventListener('load', () => {
        loadedCount++;
        if (loadedCount === images.length) {
          const firstScreenTime = performance.now();
          console.log('首屏时间:', firstScreenTime);
        }
      });
    }
  });
});
```

+ **方法4**：基于首屏高度计算（较传统）

```javascript
const screenHeight = window.innerHeight;
const startTime = performance.timing.navigationStart;

// 使用 Intersection Observer 监听首屏内容
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting && entry.target.complete) {
      // 检查所有首屏元素是否加载完成
      checkFirstScreenComplete();
    }
  });
});

function checkFirstScreenComplete() {

    window.innerWidth / 2, 
    screenHeight - 10
  );

}
```

+ **方法5**：Lighthouse / WebPageTest 工具计算

```javascript
// 通过 Lighthouse API 获取
const lighthouse = require('lighthouse');
const result = await lighthouse(url);
// 参考 Speed Index 或自定义指标
```

+ **意义**： 
    - **核心用户体验指标**：首屏内容是用户最先看到和关注的部分，直接影响第一印象
    - **业务价值高**：首屏通常包含最重要的信息（标题、核心功能、关键图片等）
    - **转化率相关**：首屏加载速度直接影响用户留存和转化
    - **SEO 影响**：搜索引擎将首屏时间作为排名因素之一
    - **与白屏时间互补**：白屏时间反映"有内容"，首屏时间反映"内容完整可用"
+ **标准**： 
    - 优秀：< 1.5s
    - 良好：1.5-2.5s
    - 需要优化：2.5-4s
    - 差：> 4s
    - **移动端标准更严格**：优秀 < 2s，良好 < 3s
+ **影响因素**： 
    - 首屏资源数量和大小（HTML、CSS、JS、图片）
    - 关键渲染路径长度
    - 服务器响应时间（TTFB）
    - 网络带宽和延迟
    - 浏览器渲染性能
    - 第三方脚本阻塞
    - 字体加载时间
+ **优化方向**： 
    - **资源优化**： 
        * 压缩首屏图片（WebP、AVIF 格式）
        * 懒加载非首屏图片
        * 使用 srcset 实现响应式图片
        * 雪碧图合并小图标
    - **关键路径优化**： 
        * 内联关键 CSS（Critical CSS）
        * 异步加载非关键 CSS：`<link rel="preload" as="style">`
        * 延迟加载非首屏 JavaScript
        * 减少首屏 JavaScript 执行量
    - **渲染优化**： 
        * 使用 SSR/SSG 预渲染首屏内容
        * 骨架屏提升感知性能
        * 优先渲染首屏，渐进式加载
    - **网络优化**： 
        * CDN 加速静态资源
        * HTTP/2 多路复用
        * DNS 预解析、预连接
        * 资源预加载（Preload、Prefetch）
    - **代码分割**： 
        * 路由级别代码分割
        * 组件级别懒加载
        * Tree Shaking 移除无用代码
+ **与其他指标的关系**： 
    - **首屏时间 ≈ LCP**：LCP 通常可以代表首屏时间，是官方推荐的替代指标
    - **首屏时间 > FCP**：FCP 是首次内容绘制，首屏时间是首屏内容完整呈现
    - **首屏时间 < Load**：首屏完成通常早于所有资源加载完成
    - 关系链：**FP → FCP → 首屏时间(≈LCP) → TTI → Load**
+ **测量难点**： 
    - **首屏定义不统一**：不同业务对"首屏"的定义可能不同
    - **动态内容**：单页应用、懒加载、骨架屏等使首屏边界模糊
    - **个性化内容**：不同用户看到的首屏内容可能不同
    - **视口差异**：不同设备屏幕尺寸导致首屏范围不同
    - **异步渲染**：React/Vue 等框架的异步渲染增加测量复杂度
+ **最佳实践**：

```javascript
// 综合方案：结合 LCP 和自定义标记
import {onLCP} from 'web-vitals';

// 1. 使用 LCP 作为基准
onLCP((metric) => {
  reportMetric('LCP', metric.value);
});

// 2. 自定义首屏完成标记
function markFirstScreenComplete() {
  performance.mark('first-screen-complete');
  const firstScreenTime = performance.measure(
    'first-screen-time',
    'navigationStart',
    'first-screen-complete'
  );
  reportMetric('FirstScreen', firstScreenTime.duration);
}

// 3. 在首屏关键内容渲染完成后调用
// 例如：在 React 中
useEffect(() => {
  if (firstScreenDataLoaded && firstScreenImagesLoaded) {
    markFirstScreenComplete();
  }
}, [firstScreenDataLoaded, firstScreenImagesLoaded]);
```

+ **监控建议**： 
    - **核心指标**：将首屏时间作为 P75/P95 百分位监控
    - **分段监控**：区分不同页面类型（首页、列表页、详情页）
    - **设备分类**：分别监控移动端和桌面端
    - **地域分析**：不同地区网络环境差异大
    - **告警机制**：首屏时间超过阈值时及时告警

# 资源加载指标
## FCI (First CPU Idle)
+ **定义**：页面首次达到最小可交互状态的时间
+ **计算方法**： 
    - FCP 之后首个至少有 5 秒窗口期的时刻
    - 已被 TTI 替代
+ **意义**：早期可交互时间点
+ **标准**：⚠️ ‼️ **<font style="color:#DF2A3F;">已弃用</font>**

## Resource Timing
+ **定义**：各种资源（脚本、样式、图片等）的详细加载时序
+ **计算方法**： 
    - `performance.getEntriesByType('resource')`
    - 包含 DNS 查询、TCP 连接、请求响应等阶段
+ **意义**：诊断具体资源的加载瓶颈
+ **关键字段**：`duration`, `transferSize`, `domainLookupTime`, `connectTime`

## Long Tasks
+ **定义**：执行时间超过 50ms 的主线程任务
+ **计算方法**： 
    - `new PerformanceObserver((list) => {...}).observe({type: 'longtask', buffered: true})`
    - Long Tasks API 提供
+ **意义**：识别阻塞主线程的耗时操作，影响交互响应
+ **标准**：应尽量减少，单个任务 < 50ms

## Total Blocking Time (TBT)
+ **定义**：FCP 和 TTI 之间所有长任务阻塞时间的总和
+ **计算方法**： 
    - 所有长任务超过 50ms 的部分相加
    - Lighthouse 提供此指标
+ **意义**：量化主线程被阻塞的程度
+ **标准**：良好 < 200ms，需要改进 200-600ms，差 > 600ms

# 运行时性能指标
## FPS (Frames Per Second)
+ **定义**：每秒渲染的帧数
+ **计算方法**： 
    - 使用 `requestAnimationFrame` 计算两帧之间的时间间隔
    - `fps = 1000 / frameTime`
+ **意义**：衡量页面动画和滚动的流畅度
+ **标准**：良好 ≥ 60 FPS（16.67ms/帧）

## Memory Usage
+ **定义**：JavaScript 堆内存使用情况
+ **计算方法**： 
    - `performance.memory.usedJSHeapSize` （Chrome）
    - 通过 DevTools Performance Monitor
+ **意义**：检测内存泄漏，优化内存占用
+ **标准**：根据应用复杂度，避免持续增长

## CPU Usage
+ **定义**：JavaScript 执行对 CPU 的占用率
+ **计算方法**： 
    - 通过 DevTools Performance 面板分析
    - 计算脚本执行时间占总时间的比例
+ **意义**：识别 CPU 密集型操作
+ **标准**：主线程空闲时间应 > 50%

# 用户体验指标
## Bounce Rate（跳出率）
+ **定义**：用户只访问一个页面就离开的比例
+ **计算方法**： 
    - 通过分析工具（GA、百度统计等）统计
    - 单页访问数 / 总访问数
+ **意义**：反映页面内容质量和用户满意度
+ **标准**：< 40% 较好，因行业而异

## Time on Page
+ **定义**：用户在页面停留的时间
+ **计算方法**： 
    - 页面卸载时间 - 页面加载时间
    - 通过 `visibilitychange` 事件更精确计算
+ **意义**：衡量用户参与度
+ **标准**：根据内容类型，通常 > 1分钟为好

## Conversion Rate（转化率）
+ **定义**：完成目标操作的用户占比
+ **计算方法**： 
    - 完成目标的用户数 / 总访问用户数
+ **意义**：衡量页面有效性和业务价值
+ **标准**：因业务目标而异

# 网络性能指标
## DNS Lookup Time
+ **定义**：DNS 域名解析耗时
+ **计算方法**： 
    - `performance.timing.domainLookupEnd - performance.timing.domainLookupStart`
+ **意义**：网络连接第一步，可通过 DNS 预解析优化
+ **标准**：< 100ms

## TCP Connection Time
+ **定义**：建立 TCP 连接耗时
+ **计算方法**： 
    - `performance.timing.connectEnd - performance.timing.connectStart`
+ **意义**：网络延迟的重要组成部分
+ **标准**：< 100ms

## SSL Handshake Time
+ **定义**：HTTPS SSL/TLS 握手耗时
+ **计算方法**： 
    - `performance.timing.connectEnd - performance.timing.secureConnectionStart`
+ **意义**：HTTPS 额外开销，可优化协议版本
+ **标准**：< 200ms

## Network Latency
+ **定义**：网络请求的往返延迟
+ **计算方法**： 
    - RTT (Round Trip Time)
    - 通过 Resource Timing API 分析
+ **意义**：影响资源加载速度
+ **标准**：< 100ms（优秀），< 300ms（可接受）

# 框架特定指标
## React - Render Time
+ **定义**：组件渲染耗时
+ **计算方法**： 
    - React DevTools Profiler
    - `<Profiler>` 组件 API
+ **意义**：识别渲染性能瓶颈
+ **标准**：单次渲染 < 16ms

## Vue - Component Update Time
+ **定义**：Vue 组件更新耗时
+ **计算方法**： 
    - Vue DevTools Performance 面板
    - 自定义 performance hooks
+ **意义**：优化响应式更新
+ **标准**：< 16ms

## Bundle Size
+ **定义**：JavaScript/CSS 打包后的文件大小
+ **计算方法**： 
    - Webpack Bundle Analyzer
    - `ls -lh dist/`
    - Lighthouse 报告
+ **意义**：影响下载和解析时间
+ **标准**：JS < 200KB（gzip后），首屏 JS < 100KB

## Code Coverage
+ **定义**：实际使用的代码占比
+ **计算方法**： 
    - Chrome DevTools Coverage 面板
    - 已使用字节数 / 总字节数
+ **意义**：识别冗余代码，优化 bundle 大小
+ **标准**：使用率 > 80%

# 指标全景时间线（帮你构建整体认知）
+ 一个典型页面加载与体验链路是：

```plain
TTFB → FP → FCP → LCP → TTI → INP（交互体验） → CLS（稳定性）
```

+ 这是现代前端性能优化的 **主战场时间轴**。
