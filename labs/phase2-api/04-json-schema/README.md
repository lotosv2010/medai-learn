# 04 — 结构化输出：把正确性押在 Schema 上

对应文章：第 04 篇《结构化输出：把正确性押在 Schema 上》

## 要验证什么

让 DeepSeek 把一条处方抽成结构化数据，比较两种约束方式，再用 Zod 做最后一层校验。

```
index.ts    主脚本：实验 A（两档对照）+ B（Zod 语义盲区）+ C（思考模式对照）
schema.ts   Zod 定义：字段、枚举、「严格模式」
samples.ts  6 条处方样本 + 人工标准答案
```

代码只回答四个问题：

1. **只靠提示词约定，模型会不会按结构输出**？用 6 条样本测能解析、通过 Zod、完全正确三个比例。
2. **`response_format: json_object` 换来了什么，又没换来什么**？它保证「是合法 JSON」，不保证字段名、枚举、类型。
3. **Zod 能拦住什么，拦不住什么**？它能拦结构错误，拦不住「结构合法、剂量抄错」。
4. **思考模式会不会改变结果**？开启时 temperature 不生效，所以实验 A/B 全程显式关闭，C 单独对照。

## 怎么跑

```bash
# 仓库根目录，Node 22
pnpm install
pnpm --filter @medai/labs p2-schema
```

需要 `.env.local` 里有 `DEEPSEEK_API_KEY`。缺失时脚本会给出中文提示，不会抛栈。

> ⚠️ **关键前提**：脚本默认显式带 `thinking: { type: 'disabled' }`。思考模式下 temperature 行为不同，会污染两档对比。

## 看到什么算成功

### 实验 A：两档可靠性

成功的标志是：两档的「能解析 JSON」都是 100%，而「完全正确」明显低于它。这说明「合法」与「正确」是两回事。

本机实测（2026-11-10，跑 1 轮，共 14 次调用）：

| 路径 | 能解析 JSON | 通过 Zod | 完全正确 | token 合计 |
|---|---|---|---|---|
| Prompt 约定 | 6/6（100%） | 3/6（50%） | 3/6（50%） | 1143 |
| json_object | 6/6（100%） | 3/6（50%） | 3/6（50%） | 1305 |

> 观察：两档的通过率在这 6 条上一样。`json_object` 没有比 Prompt 约定更好，因为它只约束「括号配对」，字段对不对依然靠模型自觉。

### 实验 B：Zod 的语义盲区

构造一条「剂量 5（应为 0.5）、频次 qid（应为 tid）」的输出。Zod 放行。

结论：Zod 只保证形状，不保证语义。这一层要靠业务规则或人工复核补。

### 实验 C：思考模式对照

同一条样本 S1，思考关闭：推理 token 0，总 token 211；思考开启：推理 token 44，总 token 280。两者都通过 Zod。

结论：思考模式在这种简单抽取上没有带来正确率提升，却多花了推理 token。

## 故意留下的不完美

| 不完美 | 为什么不修 | 对应观察点 |
|---|---|---|
| 样本只有 6 条，统计没有置信区间 | 精简版，成本与时间的取舍；数字只作现象参考 | 文章只报告「这次跑出的数」 |
| S2、S6 的疗程被模型填成 `0`，S4 填成 `null` | 这是模型在「编造缺失值」，Schema 应当拒绝，不能为了通过率放宽 | Zod 拦住了它，但拦的是「形状」，不是「该不该填」 |
| S6 的频次被模型判成 `prn`，标准答案是 `qd` | 模型的真实判错，保留作为真实错误样本 | 枚举归一的能力差异 |
| 只测了 DeepSeek，没测 `json_schema` 档 | 当前 DeepSeek 不提供 `json_schema`；通义档因无 key 暂缺 | 留给后续补测，文章不对未实测档下结论 |
| 模型返回的 `model` 字段是 `deepseek-flash`，请求是 `deepseek-chat` | 服务端别名，不影响本实验对比 | 实验记录的是服务端实际模型名 |
