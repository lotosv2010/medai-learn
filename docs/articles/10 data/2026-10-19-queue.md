## 一、场景切入：setTimeout 和 Promise 谁先执行

先看一段你每天都在写、但未必想清楚的代码：

```javascript
setTimeout(() => console.log(1), 0);
console.log(2);
// 输出：2 → 1
```

`setTimeout` 明明写了 0 毫秒，为什么它反而排在同步代码 `console.log(2)` 后面？因为 **`setTimeout` 的回调根本不会立刻执行，它被塞进了一个队列，要等当前所有同步代码跑完**。

那如果再加一个 `Promise` 呢？

```javascript
console.log('1');

setTimeout(() => {
  console.log('2');   // 👈 macrotask 队列
}, 0);

Promise.resolve().then(() => {
  console.log('3');   // 👈 microtask 队列
});

console.log('4');

// 输出顺序：1 → 4 → 3 → 2
// 为什么 3 在 2 前面？因为两个回调被塞进了两个不同优先级的队列
```

答案藏在浏览器事件循环里。事件循环维护了**至少两条任务队列**：

```
┌────────────────────────────────────────────────────┐
│                   一次事件循环（tick）                 │
│                                                      │
│  ① 执行一个 macrotask（宏任务）                       │
│     └─ setTimeout / setInterval / I/O / 事件回调       │
│                                                      │
│  ② 清空整个 microtask 队列（微任务）                  │
│     └─ Promise.then / MutationObserver / queueMicrotask │
│                                                      │
│  ③ 渲染（如果需要）                                   │
│                                                      │
│  ④ 回到 ①，取下一个 macrotask                         │
└────────────────────────────────────────────────────┘
```

这两条队列都是 **FIFO（先进先出）队列**——先入队的任务先执行。区别在于**优先级和调度时机**：macrotask 队列每次事件循环只取出**一个**执行；而 microtask 队列一旦开始清空，就**一口气把当前队列里所有微任务全部执行完**，期间新产生的微任务也会被插队到本轮继续执行。

所以 `Promise.then` 的回调进了优先级更高的 microtask 队列，永远比下一轮的 `setTimeout` 先执行。

![](https://cdn.nlark.com/yuque/0/2022/png/738210/1641120048422-4e8c0e44-5e88-438c-a8b9-10e7431c85b7.png)

上面这张图就是事件循环的全景：左侧的调用栈（Call Stack）执行同步代码，右侧是 Web APIs 处理异步任务，回调被分门别类地推入**宏任务队列（macrotask）**和**微任务队列（microtask）**。记住一个关键点：**调用栈清空后，先清空微任务队列，再取下一个宏任务**。

来一道面试里真实的「输出顺序」题，你可以先心算一遍再看答案：

```javascript
async function async1() {
  console.log('A');
  await async2();
  console.log('B');          // 👈 关键：await 后面的代码相当于 then 回调，进 microtask
}

async function async2() {
  console.log('C');
}

console.log('D');

setTimeout(() => {
  console.log('E');
}, 0);

async1();

new Promise((resolve) => {
  console.log('F');
  resolve();
}).then(() => {
  console.log('G');
});

console.log('H');

// 输出顺序：D → A → C → F → H → B → G → E
```

逐步拆解：同步代码先跑完（`D`、`async1` 里 `A`、进入 `async2` 打 `C`、`F`、`H`）；`await` 把 `console.log('B')` 包装成 microtask 入队，`Promise.then` 的 `G` 也是 microtask——同步结束后清空 microtask 队列（`B` → `G`）；最后下一轮事件循环才轮到 macrotask `E`。注意 **`await` 后面的代码本质上就是 `then` 回调**，这是很多人栽跟头的地方。

你看，你每天都在写 `Promise` 和 `setTimeout`，但它们的执行顺序，完全是「**队列 + 优先级**」这个数据结构概念决定的。队列不只是课本里的「先进先出」，它就是浏览器调度的骨架。

> 💬 **面试官**：`Promise.then` 为什么比 `setTimeout` 先执行？底层队列机制是什么？
>
> ✅ 标准答案：浏览器事件循环维护两条任务队列，都是 FIFO 队列。每轮循环先执行一个 macrotask（如 `setTimeout` 回调），然后**清空整个 microtask 队列**（如 `Promise.then` 回调），清空期间新产生的微任务也会本轮执行，最后才是渲染、再进入下一轮取下一个 macrotask。`Promise.then` 的回调进的是优先级更高的 microtask 队列，所以永远比下一轮的 `setTimeout` 快一步。
>
> 🎁 加分答案：能点出三个细节——① microtask 是在**当前 macrotask 结束后、渲染之前**被清空的，所以在微任务里改 DOM 会在本次渲染前生效，而宏任务里的改要等下一轮；② microtask 队列是「清空为止」，如果不断 `queueMicrotask` 会产生微任务风暴、阻塞渲染；③ `await` 后面的代码等价于 `then` 回调，也进 microtask 队列——这是判断 async 输出顺序题的关键。再补一句：Node 里还有个优先级更高的 `process.nextTick` 队列，比 Promise 微任务还先执行。

## 二、队列是什么

回到最朴素的定义：

- **队列（Queue）**：一个**先进先出**的数据结构
- JavaScript 里没有内置队列，但可以用 **Array 实现队列的所有功能**（`push` 入队、`shift` 出队）

![](https://cdn.nlark.com/yuque/0/2022/png/738210/1641124218646-38210135-9e87-4565-a53c-21b0ac2b7d4a.png)

看这张图就懂了：元素从**队尾（rear）**入队，从**队首（front）**出队，先来的先走，绝不插队。1 先进去，1 就先出来；3 最后进去，3 就最后出来。

记住两个专业词汇，面试会用到：

- **enqueue（入队）**：从队尾添加元素
- **dequeue（出队）**：从队首移除元素

### 队列的经典应用场景

什么场景需要「先进先出」？本质上是**需要保证处理顺序**的场景：

- **食堂排队打饭**：只留一个窗口，学生排队似春运——先进先出，保证有序公平
- **JS 异步中的任务队列**：JS 是单线程，无法同时处理异步中的并发任务，于是用任务队列**先后处理** Promise、定时器、事件回调
- **计算最近请求次数**：有新请求就入队，把 3000ms 前发出的请求出队，**队列的长度就是最近的请求次数**（下面第六节会完整讲这道题）

### 一个关键的认知：队列是「借口」，不是「实现」

这里要接上第 01 篇讲过的一个概念——**抽象数据类型（ADT）**。

「队列」描述的是**接口**：你只能从队尾加、从队首取。至于内部是用数组存、还是用链表存、还是用 `Map` 存，那是**实现**问题。**同一套队列接口，可以有多种实现，而它们的复杂度天差地别**——这正是下一节要讲的核心。

举个最直白的对比例子：用数组 `push` 入队是 O(1)，但用 `shift` 出队却是 O(n)；换一种实现（双指针 / 循环队列），出队就能做到 O(1)。**「队列」这个概念没变，性能却可以差一个数量级**——这就是为什么面试官总爱追问「你怎么实现这个队列」。

## 三、核心操作与实现陷阱

队列的三个核心操作：

| 操作 | 含义 | 数组实现 | 复杂度 |
|------|------|---------|--------|
| enqueue | 从队尾入队 | `queue.push(x)` | O(1) |
| dequeue | 从队首出队 | `queue.shift()` | **O(n)** ⚠️ |
| peek | 查看队首元素 | `queue[0]` | O(1) |

先看最直觉的**数组实现**。

### 数组方式实现队列

`src/data-structures/queue/queue-array.ts`

```typescript
class Queue {
  private queue: any[];
  constructor() {
    this.queue = [];
  }
  enqueue(element: any) {
    this.queue.push(element);
  }
  dequeue() {
    this.queue.shift();
  }
  peek() {
    return this.queue[0];
  }
  isEmpty() {
    return this.size() === 0;
  }
  size() {
    return this.queue.length;
  }
  clear() {
    this.queue = [];
  }
  toString() {
    return this.queue.toString();
  }
}
export default Queue;
```

### Map 方式实现队列：换个思路绕开 `shift`

数组版有个致命的性能问题（下面马上讲），先看另一种实现——**用 `Map` + 双指针**：

`src/data-structures/queue/queue.ts`

```typescript
class Queue<K, V> {
  private queue: Map<K, V>;
  private end: number;
  private start: number;
  constructor() {
    this.queue = new Map();
    this.end = 0;
    this.start = 0;
  }
  enqueue(element: any) {
    const key: any = this.end++;
    this.queue.set(key, element);
  }
  dequeue() {
    const key: any = this.start++;
    const res = this.queue.get(key);
    this.queue.delete(key);
    return res;
  }
  peek() {
    const key: any = this.start;
    return this.queue.get(key);
  }
  isEmpty() {
    return this.size() === 0;
  }
  size() {
    return this.queue.size;
  }
  clear() {
    this.queue.clear();
    this.start = 0;
    this.end = 0;
  }
  toString() {
    return Array.from(this.queue.values()).toString();
  }
}
export default Queue;
```

请留意一件有意思的事：**这两个测试文件的断言一模一样**——因为它们测的是**同一个队列接口**。这正印证了上一节说的 ADT 思想：**接口不变，实现随便换**。数组版和 Map 版对外表现完全一致，内部却是两套完全不同的存储机制。

那 Map 版到底「高明」在哪？关键在这两行：

```typescript
enqueue(element: any) {
  const key: any = this.end++;     // 👈 队尾指针自增，不搬移任何元素
  this.queue.set(key, element);
}
dequeue() {
  const key: any = this.start++;   // 👈 队首指针自增，不搬移任何元素
  const res = this.queue.get(key);
  this.queue.delete(key);
  return res;
}
```

**注意：出队时它只是把 `start` 指针往后挪了一格，没有搬移任何元素。** 这就是它比数组版 `shift` 快的根本原因——而这也正是数组版必须解决的问题。下面就来拆解。

### 陷阱一：为什么 `shift` 是 O(n)

数组的 `push` 是在**末尾**加元素，不影响已有元素的位置，所以是 O(1)。但 `shift` 是从**头部**删元素——删完之后，为了保持数组「元素在内存里连续」，**后面所有元素都得整体往前搬一格**：

```
shift() 出队一个元素，后面的元素全部要往前搬一格

初始队列 [10, 20, 30, 40, 50]
┌────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │
└────┴────┴────┴────┴────┘
  ↑
 出队

shift 后（= 10），每个元素向前移动一格
┌────┬────┬────┬────┬────┐
│ 20 │ 30 │ 40 │ 50 │    │
└────┴────┴────┴────┴────┘
  ↑        ↑   ↑    ↑
 20 ← 30 ← 40 ← 50   每个元素都搬了一次 → 一次出队 O(n)
```

队列里有多少元素，出队就要搬多少次。**一次 `shift` 是 O(n)，连续 n 次出队就是 O(n²)**——这就是数组版队列的性能陷阱，也是面试官最爱卡人的地方。

> 💬 **面试官**：用数组实现队列时，为什么不能直接用 `shift`？循环队列怎么解决这个问题？
>
> ✅ 标准答案：`shift` 从数组头部删除元素，为了保持元素在内存中连续，必须把后面所有元素整体前移一格，所以单次出队是 O(n)，n 次出队退化成 O(n²)。循环队列（Circular Queue）用**头指针 + 尾指针**代替元素搬移：出队时只把头指针往后挪一格（`head = (head + 1) % capacity`），入队时只挪尾指针，**数据本身始终不动**，这样入队和出队都是 O(1)。当指针走到数组末尾时，用取模运算让它「绕回」开头，从而**复用前面已经出队腾出的空间**，避免「假溢出」（明明前面有空位，却因为尾指针到头而报满）。
>
> 🎁 加分答案：能补两点——① **空间复用的核心是取模**：`(tail + 1) % capacity` 让「线性数组」变成「首尾相接的环」，这就是「循环」二字的来源；② 判断队满/队空容易踩坑——如果只用 `head === tail` 判空会分不清满和空，规范解法是**空出一个位置**（`(tail + 1) % capacity === head` 判满），或者**额外维护一个 count 变量**记录元素个数，`count === capacity` 判满、`count === 0` 判空，后者更直观。

### 陷阱二：循环队列——让指针绕圈，而不是搬数据

既然问题出在「搬数据」，那解法就是**别搬，让指针动**。这就是循环队列。

用「头指针 `head` + 尾指针 `tail` + 计数器 `count`」三个变量，配合取模运算，就能让 O(1) 的入队出队在固定大小的数组上循环复用空间：

```typescript
class CircularQueue<T> {
  private items: (T | undefined)[];
  private head = 0;      // 队首下标
  private tail = 0;      // 队尾下标（下一个要写入的位置）
  private count = 0;     // 当前元素个数，用来区分「满」和「空」

  constructor(private capacity: number) {
    this.items = new Array(capacity);
  }

  enqueue(item: T): boolean {
    if (this.count === this.capacity) return false;   // 队满
    this.items[this.tail] = item;
    this.tail = (this.tail + 1) % this.capacity;       // 👈 取模回绕，是关键
    this.count++;
    return true;
  }

  dequeue(): T | undefined {
    if (this.count === 0) return undefined;            // 队空
    const item = this.items[this.head];
    this.items[this.head] = undefined;
    this.head = (this.head + 1) % this.capacity;       // 👈 只挪指针，不搬数据
    this.count--;
    return item;
  }

  peek(): T | undefined {
    return this.count === 0 ? undefined : this.items[this.head];
  }

  isEmpty(): boolean { return this.count === 0; }
  isFull(): boolean { return this.count === this.capacity; }
  size(): number { return this.count; }
}
```

看它怎么「绕圈」——容量为 5 的循环队列：

```
enqueue(10)、enqueue(20)、enqueue(30) 后：
              tail
               ↓
[ 10 ][ 20 ][ 30 ][    ][    ]
   ↑
  head

dequeue() 拿走 10（只挪 head），再 enqueue(40)、enqueue(50)：
                            tail
                             ↓
[    ][ 20 ][ 30 ][ 40 ][ 50 ]
          ↑
         head
        （head 已挪到下标 1，前面空出的 0 号位被记录下来）

此时再 enqueue(60)，tail 走到末尾后回绕：
        tail
         ↓
[ 60 ][ 20 ][ 30 ][ 40 ][ 50 ]
   ↑          ↑
 新写入       head
 —— 用上了 dequeue 腾出的 0 号位，空间被循环复用
```

**这就是「循环队列」四个字的全部含义**：数组长度是死的，但通过 `(index + 1) % capacity` 让头尾指针首尾相接，把「线性数组」用成了一个「环」，前面出队腾出的空间立刻能被后面入队复用。**入队 O(1)、出队 O(1)、空间 O(capacity)**——这就是它比 `shift` 版强的地方。

⚠️ 一个容易踩的坑：**如果只用 `head === tail` 判断，你分不清队列是「空」还是「满」**（两种情况下指针都可能重合）。所以要么空出一个位置专门用来判满，要么像我上面这样**额外维护一个 `count`**——后者更直观，也是面试时推荐写出来的版本。

## 四、双端队列：两端都能进出的「加强版队列」

普通队列只能「一头进、另一头出」。但如果把两头都打开呢？

- **双端队列（Deque，double-ended queue）**：一种允许我们**同时从前端和后端**添加和移除元素的特殊队列

```
普通队列：      队首 ←出队 ──── ──── 入队→ 队尾
                 （只能一头进、一头出）

双端队列 Deque：队首 ←出队 / 入队 ──── 出队 / 入队→ 队尾
                 （两头都能进、两头都能出）
```

它相当于把「队列」和「栈」的能力合到了一起——从同一端进出，它就是个栈；从两端分别进出，它就是个队列。这种灵活性，让它成为**滑动窗口**类算法（比如「滑动窗口最大值」）的秘密武器，下面第六节会详细讲。

### 双端队列的两种实现

和普通队列一样，Deque 也有「数组版」和「Map 版」两种写法，**两套代码测的是同一个接口**。

数组版最直观——数组天然支持两端操作（`unshift`/`push` 入队，`shift`/`pop` 出队）：

`src/data-structures/queue/deque-array.ts`

```typescript
class Deque {
  private deque: any[];
  constructor() {
    this.deque = [];
  }
  addFront(element: any) {
    this.deque.unshift(element)
  }
  addBack(element: any) {
    this.deque.push(element);
  }
  removeFront() {
    return this.deque.shift();
  }
  removeBack() {
    return this.deque.pop();
  }
  peekFront() {
    return this.deque[0];
  }
  peekBack() {
    return this.deque[this.size() - 1]
  }
  isEmpty() {
    return this.size() === 0;
  }
  size() {
    return this.deque.length;
  }
  clear() {
    this.deque = [];
  }
  toString() {
    return this.deque.toString();
  }
}
export default Deque;
```

> ⚠️ 数组版 Deque 有个隐蔽的性能问题：`addFront` 用的 `unshift` 和 `removeFront` 用的 `shift` **都是 O(n)**（头部插入/删除要搬移所有元素）。所以数组版 Deque 只是「好写」，并不「高效」——真正的工程实现（比如 C++ STL 的 `deque`、Java 的 `ArrayDeque`）底层是一块「分段的环形缓冲区」，两端操作都接近 O(1)。

Map 版则用**双指针**实现，`addFront` 时如果前面还有空位就把 `start` 往前挪，否则需要搬移——请看这段逻辑最复杂的代码：

`src/data-structures/queue/deque.ts`

```typescript
class Deque<K, V> {
  private deque: Map<K, V>;
  private start: number;
  private end: number;
  constructor() {
    this.deque = new Map();
    this.start = 0;
    this.end = 0;
  }
  addFront(element: any) {
    if(this.isEmpty()) {
      this.addBack(element);
    } else if(this.start > 0)  {
      const key: any = --this.start;
      this.deque.set(key, element);
    } else {
      for (let i: any = this.end; i > 0; i--) {
        const k: any = i - 1;
        const v: any = this.deque.get(k)
        this.deque.set(i, v);
      }
      this.end++;
      const key: any = this.start = 0;
      this.deque.set(key, element);
    } 
  }
  addBack(element: any) {
    const key: any = this.end;
    this.deque.set(key, element);
    this.end++;
  }
  removeFront() {
    if(this.size() === 0) return undefined;
    const key: any = this.start++;
    const res = this.deque.get(key);
    this.deque.delete(key);
    return res;
  }
  removeBack() {
    if(this.size() === 0) return undefined;
    const key: any = --this.end;
    const res = this.deque.get(key);
    this.deque.delete(key);
    return res;
  }
  peekFront() {
    if(this.size() === 0) return undefined;
    const key: any = this.start;
    return this.deque.get(key);
  }
  peekBack() {
    if(this.size() === 0) return undefined;
    const key: any = --this.end;
    return this.deque.get(key);
  }
  isEmpty() {
    return this.size() === 0;
  }
  size() {
    return this.deque.size;
  }
  clear() {
    this.deque.clear();
  }
  toString() {
    return Array.from(this.deque.values()).toString();
  }
}
export default Deque;
```

`addFront` 的三个分支值得单独讲：

- **队空时**：直接复用 `addBack`，不用特殊处理
- **`start > 0` 时**：前面还有空位，`--this.start` 把指针往前挪一格即可，O(1)
- **`start === 0` 时**：前面没空间了，只能把已有元素**整体后移一格**（那个 `for` 循环），腾出 0 号位——这一步是 O(n)，和数组版的 `unshift` 本质相同

> 💬 **面试官**：双端队列（Deque）和普通队列的区别是什么？它解决了什么问题？
>

## 五、优先队列：队列家族里的「特权阶层」

讲完双端队列，队列家族还差最后一个成员——**优先队列（Priority Queue）**。

前面讲的所有队列都遵循同一个规则：**谁先来，谁先走**（FIFO）。但现实里常有一种需求：**不是按「来的先后」，而是按「优先级高低」出队**。

- 医院的**急诊分诊**：不是按挂号顺序看病，而是按病情紧急程度——重伤员优先
- 操作系统的**任务调度**：高优先级进程先获得 CPU
- 前端打包工具（如 Webpack）的**任务队列**：`entry` 依赖的模块优先构建

**优先队列的接口和普通队列几乎一样**（`enqueue` / `dequeue` / `peek`），唯一的区别是：`dequeue` 出的**不是最早入队的元素，而是优先级最高的元素**。

```
普通队列（FIFO）：先进先出
  入队顺序 [A, B, C] → 出队顺序 [A, B, C]

优先队列（按优先级）：优先级高的先出
  入队 (A,优先级3) (B,优先级1) (C,优先级2)
  → 出队顺序 [B(1), C(2), A(3)]   ← 和入队顺序无关
```

⚠️ **这里埋一个关键问题**：优先队列该怎么实现？如果每次 `dequeue` 都遍历找最大值，那是 O(n)；有没有办法让它「高效地取出优先级最高的元素」？

答案是有的——**用「堆（Heap）」实现优先队列，入队和出队都是 O(log n)**。堆是第 08 篇的主角，它会讲透「完全二叉树的数组表示」「上浮 / 下沉」「O(n) 建堆」这些高频考点。这里你只需要先记住一句话：

> **「优先队列」是一种抽象数据类型（接口），而「堆」是它最常用的高效实现。**

这也是一个绝佳的 ADT 例子：**接口（优先队列）和实现（堆）分离**——面试时被问「优先队列是怎么实现的」，答「用堆」是标准答案，但如果能补一句「优先队列是接口、堆是实现，也可以用有序数组或平衡 BST 实现，只是复杂度不同」，就立刻显出深度。

### 933 计算最近请求次数：队列的「滑动窗口计数」

**题目**：写一个 `RecentCounter` 类，记录最近 3000 毫秒内的请求次数。每次调用 `ping(t)`（`t` 是毫秒时间戳），返回过去 3000ms 内（含当前）的请求次数。

**解题思路**：

- 越早发出的请求，越早不在最近 3000ms 内的请求里——**「先来先过期」，天然的先进先出**
- 所以用一个**队列**装时间戳：新请求入队，超出时间窗口的老请求出队

**解题步骤**：

- 新建一个队列
- 有新请求就入队，把 3000ms 前发出的请求出队
- 队列的**长度**就是最近的请求次数

`src/data-structures/queue/leet-code.ts`

```typescript
export class RecentCounter {
  private q: any = [];
  constructor() {}

  ping(t: number): number {
    this.q.push(t);
    while(this.q[0] < t - 3000) {
      this.q.shift()
    }
    return this.q.length;
  }
}
```

`src/data-structures/queue/test/leet-code.test.ts`

```typescript
    const recentCounter = new RecentCounter();
    recentCounter.ping(1);     // requests = [1]，范围是 [-2999,1]，返回 1

```

**复杂度**：

- 时间复杂度：O(n)——最直观的说法是「n 次 `ping` 总共 O(n)」
- 空间复杂度：O(n)

> 💬 **面试官**：这道题的时间复杂度到底是 O(1) 还是 O(n)？
>
> ✅ 标准答案：**单次 `ping` 是「摊还 O(1)」，n 次 `ping` 总计 O(n)**。关键在 `while` 循环——虽然某一次 `ping` 可能连续 `shift` 好几次，但**每个元素一辈子只会入队一次、出队一次**，所以把 n 次调用的总工作量加起来是 2n 次操作，平均到每次就是 O(1)。
>
> 🎁 加分答案：能用「摊还分析」这个词点破本质——和 `Array.push` 偶尔触发扩容、但均摊下来是 O(1) 是同一个道理（第 02 篇讲过）。面试里很多候选人会纠结「`while` 明明可能循环多次，怎么会是 O(1)」，能主动说清「每个元素最多被 `shift` 一次」这一点，就说明你真的理解了摊还复杂度。

### 232 用栈实现队列：两个栈的「负负得正」

**题目**：只用两个栈实现一个队列，支持 `push`（入队）、`pop`（出队）、`peek`（看队首）、`empty`。

栈是 LIFO、队列是 FIFO，方向正好相反。**单个栈翻不过来，但两个栈可以**——这就是「负负得正」。

- 用 `inStack` 负责**入队**：元素进来就往里压
- 用 `outStack` 负责**出队**：需要出队时，如果 `outStack` 是空的，就把 `inStack` 里的元素**全部倒过来**压进 `outStack`

一倒过来，原本在栈底的「最早入队元素」就翻到了 `outStack` 的栈顶，正好可以弹出——顺序就对了。

```typescript
class MyQueue {
  private inStack: number[] = [];    // 只负责入队
  private outStack: number[] = [];   // 只负责出队

  push(x: number): void {
    this.inStack.push(x);
  }

  pop(): number {
    this.move();                     // 👈 出队前先把 inStack 倒进 outStack
    return this.outStack.pop()!;
  }

  peek(): number {
    this.move();
    return this.outStack[this.outStack.length - 1];
  }

  empty(): boolean {
    return this.inStack.length === 0 && this.outStack.length === 0;
  }

  // 只有当 outStack 为空时，才把 inStack 全部倒过去
  private move(): void {
    if (this.outStack.length === 0) {
      while (this.inStack.length > 0) {
        this.outStack.push(this.inStack.pop()!);
      }
    }
  }
}
```

走一遍 `push(1) push(2) push(3)` 再 `pop()` 的过程：

```
入队 1、2、3：全部压入 inStack
inStack:  [1, 2, 3]   outStack: []

第一次 pop()，move() 触发，把 inStack 全部倒入 outStack：
inStack:  []          outStack: [3, 2, 1]
                                  ↑ 栈顶是 1，最早入队的元素浮到了栈顶
pop() 弹出 1 —— 完全符合 FIFO！

之后再来 push(4)：只进 inStack
inStack:  [4]         outStack: [3, 2]
再 pop()：outStack 非空，不触发 move，直接弹 2 —— 顺序依然正确
```

**复杂度**：`push` 是 O(1)；`pop`/`peek` 是**摊还 O(1)**——因为每个元素最多被「从 `inStack` 搬到 `outStack`」一次，搬完就一直在 `outStack` 里等着，不会被反复搬。

> 💬 **面试官**：用栈实现队列，为什么 `pop` 的平均复杂度是 O(1)？
>
> ✅ 标准答案：核心是「**每个元素最多被搬运一次**」——`pop`/`peek` 触发 `move()` 时，会把 `inStack` 里的元素一次性全部倒入 `outStack`；倒过去之后，这个元素要么一直待在 `outStack` 里直到被弹出，绝不会再被搬回 `inStack`。所以 n 次操作里，每个元素的总搬运次数是常数级，均摊下来每次 `pop` 是 O(1)。
>
> 🎁 加分答案：能指出「**必须只在 `outStack` 为空时才倒**」这个关键约束——如果每次 `pop` 都无脑倒一遍，元素会被反复搬运，复杂度就退化成 O(n²) 了。这个「只在必要时刻搬运」的思路，和 `Array.push` 的批量扩容、第 11 篇滑动窗口的惰性收缩都是同一类优化思想。

### 239 滑动窗口最大值：单调双端队列的封神之作

**题目**：给你一个整数数组 `nums` 和一个窗口大小 `k`，窗口从左向右滑动，返回**每个窗口里的最大值**。

**暴力解法（O(n·k)）**：每个窗口都重新扫一遍找最大值。n 个窗口 × 每个窗口 k 个元素 = O(n·k)，数据量大时直接超时。

**最优解法（O(n)）：单调双端队列**。核心思想只有一句话——**维护一个「单调递减」的队列，队首永远是当前窗口的最大值**。

具体做法是：队列里存的是**数组下标**（不是值本身），并且**让队列里的值从队首到队尾单调递减**。每来一个新元素 `nums[i]`：

- **从队尾弹出所有比它小的元素**——因为新元素又大、又更靠右（活得比它们久），那些小的永远没机会当最大值了
- **把新元素的下标从队尾入队**
- **从队首弹出已经滑出窗口的下标**（`下标 <= i - k`）
- 从 `i >= k - 1` 开始，**队首下标对应的值就是当前窗口最大值**

看 `nums = [1, 3, -1, -3, 5, 3, 6, 7]`，`k = 3` 的滑动过程：

```
i=0  nums[0]=1   队列[0]        值[1]
i=1  nums[1]=3   3>1，弹掉 0 →  队列[1]        值[3]
i=2  nums[2]=-1  -1<3，直接入 → 队列[1,2]      值[3,-1]      ← 窗口[1,3,-1] 最大值 3 ✅
i=3  nums[3]=-3  -3<-1，入队 →  队列[1,2,3]    值[3,-1,-3]   ← 窗口[3,-1,-3] 最大值 3 ✅
i=4  nums[4]=5   5 弹掉 -3、-1、3 全部 → 队列[4]  值[5]      ← 窗口[-1,-3,5] 最大值 5 ✅
i=5  nums[5]=3   3<5 入队 →     队列[4,5]      值[5,3]       ← 窗口[-3,5,3] 最大值 5 ✅
i=6  nums[6]=6   6 弹掉 3、5 →  队列[6]        值[6]         ← 窗口[5,3,6]  最大值 6 ✅
i=7  nums[7]=7   7 弹掉 6 入队 → 队列[7]       值[7]         ← 窗口[3,6,7]  最大值 7 ✅
```

结果 `[3, 3, 5, 5, 6, 7]`。注意每一步都**从队尾弹小的、从队首弹过期的**——这正是**双端队列（Deque）**的用武之地（普通队列只能两头各管一件事）。

```typescript
function maxSlidingWindow(nums: number[], k: number): number[] {
  const result: number[] = [];
  const deque: number[] = [];   // 存下标，对应值单调递减

  for (let i = 0; i < nums.length; i++) {
    // ① 队尾弹出所有比当前值小的下标 —— 它们永远不可能成为最大值了
    while (deque.length > 0 && nums[deque[deque.length - 1]] <= nums[i]) {
      deque.pop();
    }
    // ② 当前下标入队
    deque.push(i);
    // ③ 队首弹出已经滑出窗口的下标（下标 <= i - k）
    if (deque[0] <= i - k) {
      deque.shift();
    }
    // ④ 窗口形成后（i >= k - 1），队首就是当前窗口最大值
    if (i >= k - 1) {
      result.push(nums[deque[0]]);
    }
  }
  return result;
}
```

**复杂度**：时间 O(n)、空间 O(k)。为什么是 O(n) 而不是 O(n·k)？因为**每个元素的下标最多入队一次、出队一次**——虽然内层有 `while` 和 `if` 的弹出，但所有元素被弹出的总次数是 O(n)，均摊到每个元素就是 O(1)。这和上一节「用栈实现队列」的摊还分析是同一个套路。

> 💬 **面试官**：滑动窗口最大值为什么要用单调双端队列？时间复杂度是多少？
>
> ✅ 标准答案：因为窗口滑动时需要**同时从两端操作**——队尾要弹出「不如新元素有竞争力的小值」（新元素更大且更靠右，那些小值再也当不上最大值了），队首要弹出「已经滑出窗口的过期值」，还要从队首读取当前最大值。这三个动作普通队列做不到，只有双端队列能同时满足，所以是最合适的结构。**时间复杂度 O(n)**：每个元素最多入队一次、出队一次，均摊 O(1)。
>
> 🎁 加分答案：能点破「**单调队列 = 剪枝的暴力**」这个本质——暴力解法每个窗口重扫 k 个元素，重复比较了大量「注定当不了最大值」的元素；单调队列把这些废元素提前从队尾弹掉，做了「记忆化剪枝」，把 O(n·k) 降到 O(n)。另外要强调**队列里存的是下标而不是值**——存下标才能判断「过期」（`下标 <= i - k`），存值没法知道它还在不在窗口内。这两点说出来，说明你不是背题而是真懂。

### 102 二叉树层序遍历：BFS 的队列本色

**题目**：按「层」遍历二叉树，返回二维数组，每一层一个子数组。

**为什么必须用队列**：层序遍历（BFS）的本质是「**先遇到的先处理，处理谁就把谁的子节点排队**」——这恰恰是 FIFO 的定义。所以 BFS 天然属于队列，而 DFS（深度优先）才用栈。

关键技巧是：**每处理一层之前，先记录当前队列的长度 `size`**——这个 `size` 就是这一层的节点数，循环处理这 `size` 个节点，把它们的孩子入队，下一轮循环自然就进入下一层。

```typescript
interface TreeNode {
  val: number;
  left: TreeNode | null;
  right: TreeNode | null;
}

function levelOrder(root: TreeNode | null): number[][] {
  if (root === null) return [];
  const result: number[][] = [];
  const queue: TreeNode[] = [root];      // 队列初始放入根节点

  while (queue.length > 0) {
    const levelSize = queue.length;      // 👈 先记住这一层的节点数
    const level: number[] = [];

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift()!;       // 队首出队
      level.push(node.val);
      if (node.left) queue.push(node.left);    // 子节点从队尾入队
      if (node.right) queue.push(node.right);
    }
    result.push(level);
  }
  return result;
}
```

```
      3
     / \
    9   20
       /  \
      15   7

第 1 轮：queue = [3]        → 处理 3，入队 9、20    → level = [3]
第 2 轮：queue = [9, 20]    → 处理 9、20，入队 15、7 → level = [9, 20]
第 3 轮：queue = [15, 7]    → 处理 15、7            → level = [15, 7]
结果：[[3], [9, 20], [15, 7]]
```

**复杂度**：时间 O(n)（每个节点入队出队各一次）、空间 O(n)（队列最多装一层，最坏是最后一层的一半节点）。

> 💬 **面试官**：为什么层序遍历用队列，而深度优先遍历用栈？这个 `levelSize` 是干什么的？
>
> ✅ 标准答案：层序遍历要「先来的先处理」，正好是队列的 FIFO；而深度优先要「后来居上、原路返回」，是栈的 LIFO。`levelSize` 是为了**按层切分结果**——每轮循环开始时记录当前队列长度，这一长度就是本层的节点数，只处理这么多节点，本层处理完时新入队的恰好全是下一层的节点，于是自然分层。
>
> 🎁 加分答案：能联系到「BFS 找最短路径」——BFS 第一次访问到目标节点时的层数就是最短距离（因为 BFS 是逐层扩散的），这是 BFS 相比 DFS 的核心优势，第 11 篇会专门讲。另外可以提一句：如果题目只要求「按层输出」不需要分层，就省掉 `levelSize`、直接一个 `while` 循环出队即可，但那样就没法知道当前是第几层了。

## 七、前端工程落地：两种风格完全不同的队列

讲了这么多算法，最后回到前端工程师最关心的问题：**队列在浏览器和 Node 里，到底是怎样的？**

### 浏览器：任务队列竟然不是「队列」，而是「集合」

在第一节我们说「macrotask 队列是 FIFO 队列」。这个说法**足够你答对 95% 的面试题**，但如果面试官想压你一下，他会问一个规范层面的细节：

> **HTML 规范里，task queue（任务队列）其实不是严格意义上的「队列」，而是一个「集合（set）」。**

这意味着什么？两点反直觉之处：

1. **规范里有多个 task queue**（不是一条大队列），浏览器会**按优先级挑选**该从哪个队列取任务——比如把「用户输入」相关任务放在高优先级队列，保证点击响应及时，而把「网络回调」放在较低优先级队列
2. **同一队列内，规范只保证「先进先出」的大致语义，但允许实现（浏览器）在特定情况下选择性地跳过某些任务**——因为规范把它定义成 set 而非 queue，就是给浏览器留了优化空间

所以你可能会遇到「定时器比预期提前触发」「同样 `setTimeout(fn, 0)` 顺序偶尔不平直觉」的现象。**这不是 bug，而是规范有意为之的弹性。**

> 💬 **面试官**：HTML 规范里任务队列是严格 FIFO 的吗？
>
> ✅ 标准答案：不是严格的。规范把 task queue 定义为一个 **set（集合）**，而且存在多个不同优先级的 task queue，浏览器实现可以从多个队列里**挑选**下一个要执行的任务。规范只要求「同一来源（task source）的任务按顺序执行」，并不要求全局严格 FIFO。这一点和大多数人「任务队列就是先进先出」的直觉不同，但正是它给了浏览器做优先级调度的空间（比如优先响应用户交互）。
>
> 🎁 加分答案：能补一句「**微任务队列才是严格 FIFO**」——microtask 队列一旦开始清空，必须一路清到空，期间新产生的微任务也按顺序追加，不会插队。另外可以提「task source」这个概念：`setTimeout`、DOM 事件、网络请求各有自己的 task source，浏览器的优先级调度正是按 task source 分的——这是「为什么用户点击总比图片 `onload` 响应快」的规范依据。

### Node.js：libuv 的六个阶段，解释了 setImmediate 的玄学

浏览器之外，**Node.js 的事件循环是完全另一套实现**——它由 **libuv** 这个 C 库驱动，一次循环分为**六个阶段**，按顺序执行：

```
每个事件循环 tick 依次经过六个阶段：

  ① timers          ── 执行到期的 setTimeout / setInterval 回调
  ② pending callbacks ── 执行延迟到下一轮的 I/O 回调（如 TCP 错误）
  ③ idle / prepare  ── 仅内部使用
  ④ poll            ── 等待并执行 I/O 回调（大部分业务回调在这里）
  ⑤ check           ── 执行 setImmediate 回调
  ⑥ close callbacks ── 执行 socket 等资源的 close 回调
```

这张六阶段时序图建议你搜「Node.js event loop phases 官方图」找一个对照理解——它是理解 Node 异步调度的总纲。

**这就能解释一个经典玄学问题了：`setImmediate` 和 `setTimeout(fn, 0)` 谁先执行？**

关键在于它们的回调分别在**不同阶段**执行：

- `setTimeout(fn, 0)` 的回调进 **timers 阶段**（第 ① 阶段）
- `setImmediate(fn)` 的回调进 **check 阶段**（第 ⑤ 阶段）

按顺序看，timers 在 check **之前**，所以直觉上 `setTimeout` 应该先执行。但**真相是「看情况」**：

- **在主模块（顶层）里**：两者的执行顺序**不确定**！因为 Node 启动、准备事件循环也需要时间，`setTimeout(fn, 0)` 会被「向上取整」到 1 毫秒，如果准备事件循环耗时超过 1ms，timers 阶段就绪时定时器已经到期，`setTimeout` 先跑；否则如果还没到 1ms，就跳过 timers 直接到 check 阶段，`setImmediate` 先跑——**顺序取决于机器性能，是随机的**
- **在 I/O 回调内部**：`setImmediate` **永远先于** `setTimeout(fn, 0)`！因为 I/O 回调在 **poll 阶段（④）**执行，poll 之后紧接着就是 **check 阶段（⑤）**，`setImmediate` 的回调就在下一站，而 `setTimeout` 要等**下一个 tick** 的 timers 阶段才轮到

```javascript
// 场景一：主模块里 —— 顺序不确定
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// 输出可能是 timeout→immediate，也可能是 immediate→timeout，取决于进程启动耗时

// 场景二：I/O 回调里 —— setImmediate 永远先
const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// 输出永远是：immediate → timeout
```

> 💬 **面试官**：Node.js 里 `setImmediate` 和 `setTimeout(fn, 0)` 谁先执行？
>
> ✅ 标准答案：**取决于执行环境**。在主模块（顶层）里，两者顺序不确定——`setTimeout(fn, 0)` 会被向上取整到 1ms，若事件循环准备耗时超过 1ms，`setTimeout` 先执行，否则 `setImmediate` 先执行，实际取决于进程启动的快慢。但在 **I/O 回调内部**，`setImmediate` **永远先于** `setTimeout(fn, 0)`——因为 I/O 回调在 poll 阶段执行，紧接着的 check 阶段就会执行 `setImmediate`，而 `setTimeout` 要等到下一个 tick 的 timers 阶段。
>
> 🎁 加分答案：能画出 libuv 的六个阶段（timers → pending callbacks → idle/prepare → poll → check → close），并指出 `setImmediate` 对应 check 阶段、`setTimeout` 对应 timers 阶段。再深一层可以提：Node 里还有 `process.nextTick`，它的优先级**高于** Promise 微任务——`nextTick` 队列会在**每个阶段切换之间**清空，所以它比 `setImmediate`、比 Promise 都更「早」执行，这是 Node 独有的、浏览器没有的队列。
