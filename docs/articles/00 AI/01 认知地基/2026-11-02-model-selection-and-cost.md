# 模型图谱与选型：把成本算清楚

> 不是选「最强的模型」，是选「刚好够用且算得起的那一个」。

---

## 🎯 这篇文章解决什么问题

上一篇收尾时我留了一个问题：

> 既然同一个模型有便宜有贵、有快有慢、有开推理有不开推理，**你到底该用哪一个？**

前四篇教的是「它怎么工作」：它是概率续写机器、它的计量单位是 token、它会编、它的参数只是旋钮。这一篇要教的是另一件事——**怎么为它付钱**，以及付钱之前怎么决定付给谁。

先说清楚这里要拆掉的那个直觉：**很多人以为选型是个技术偏好题。**

喜欢 Claude 的回答风格，喜欢 DeepSeek 的价格，喜欢开源的掌控感，喜欢国产的合规安心——这些都不是选型的依据。选型是一道约束求解题：在「数据能不能出境」「这道题要不要多想」「窗口够不够长」「预算撑不撑得住」四个约束下，找那个还剩下的、最便宜的解。

一个具体的例子。原型阶段你随手用了当时最强的模型，效果很好。上线后日均 1000 次问诊，月底看账单，四位数。这时候你去查价格表，发现有个模型的单价只有它的十分之一——**但那个模型的单价便宜，不代表你的账单便宜**。这两件事之间隔着三层你没算过的东西。

这篇文章要讲四件事：

- 模型分成哪几类，每一类的代价到底在哪，为什么「开源一定便宜」是错觉
- 为什么「单价」不能直接比，以及必须先统一的三条口径
- 选型的四个维度，为什么顺序不能反，为什么合规要排第一
- 怎么把单价换算成一张真实的月度账单，以及路由能省下多少

每一段照旧配「面试官会怎么问」，以及标准答案和加分答案。读完这一篇，你不只是知道有哪些模型，**你能拿着一份需求，算出该选谁、为什么、花多少**。

而这一篇也是阶段一的收官——它的产出物不是一篇读起来很爽的文章，是一张能直接拿去做技术决策的表。

## 🔍 认知切入：一个上线前才发现的账单

先说一个几乎所有团队都踩过的坑。

原型阶段，你选模型的标准只有一个：**它答得最好**。反正一天就几十次调用，最贵的模型一天也就几块钱。于是你用最强的那个，prompt 写得又长又详细，每条回答都要求「分点说明、附上注意事项、给出剂量提示」。

上线后，日均 1000 次。一个月后账单来了。

你回头看当时的决策，会发现三件事每一个单独看都合理，加起来却很贵：

- **prompt 越写越长**，因为你想让它答得更准，而输入是全量计费的
- **回答越写越长**，因为你想让它更完整，而输出比输入贵 3 到 5 倍
- **每条都走最强的模型**，包括「阿莫西林属于哪类抗生素」这种一句话就能答的问题

这里是三个错位，值得逐条摆出来：

| 你以为 | 实际 |
|---|---|
| 单价低就是便宜 | 单价只是乘法里的一个因子，另两个是 token 数和输出占比 |
| 选最强的总没错 | 最强的模型在 70% 的简单任务上是纯浪费 |
| 成本是运营的事 | 成本是架构决策，写代码的时候就定死了 |

有一条是前四篇里反复出现的：**模型本身没有变贵，是你的用法把它变贵了。**

![FrugalGPT 把降本手段分成三类：改提示词（挑示例、合并问题）、近似替代（缓存、用小模型微调替代大模型）、以及级联（先问便宜的，不放心再问贵的）——这三类正好对应「输入、输出、选谁」三个可调的变量](https://ar5iv.labs.arxiv.org/html/2305.05176/assets/FPGT_Intro.png)

这张图出自 FrugalGPT，它做的事情很朴素：把「省钱的招」拆成三组。第一组改输入（少放几个示例），第二组改替代品（缓存、用小模型微调替代大模型），第三组改选择（先问便宜的，答不好再问贵的）。**注意这张图里没有「换个更便宜的模型」这一条**——因为那不是省钱的招，那是换一个产品的能力上限。

所以真正的问题是：这三组手段里，哪一组你能在架构层就设计进去？

先看模型的图谱，因为图谱决定了你的候选集有多大。

## ⚙️ 原理讲透：模型图谱与选型框架

### 四类模型的分野

市面上几百个模型，按「谁承担推理成本」和「数据去哪」两条线，其实只有四类：

| 类型 | 代表 | 优势 | 代价 |
|---|---|---|---|
| 闭源旗舰 | Claude / GPT / Gemini 系列 | 能力上限最高，长任务稳定 | 最贵；数据出境要单独评估 |
| 国产商用 | DeepSeek / 通义 / 智谱 等 | 价格低，境内合规，中文 token 效率好 | 顶配能力略逊，版本迭代快、接口常变 |
| 开源可部署 | Qwen / Llama / GLM 开源版 | 数据不出内网，可微调 | 自扛 GPU 与运维，成本从「按次」变成「按小时」 |
| 推理档 | 同一模型的思考模式（不再是独立模型名） | 多步任务准确率高 | 慢，思考 token 按输出计费 |

第四类要单独说一句，因为它 2026 年已经变形了。

早期「用推理」意味着换一个模型名：`o1`、`deepseek-reasoner`。现在主流做法是把推理做成**同一个模型的开关**（`thinking: enabled` + `reasoning_effort`）。这一点的工程后果上一篇讲透了：**你不能再把「推理模型」当成一个独立的选项去比价，它是同一个模型的一个档位。**

这也意味着：你的候选池不是「5 个模型」，而是「4 个模型 × 若干档位」。档位会改变输出 token 的量，而输出 token 是账单里最贵的那一项。

> 💬 **面试官**：开源模型可以自己部署，是不是一定比调 API 便宜？
>
> ✅ **标准答案**：不一定，取决于调用量。自部署的成本是「GPU 小时 × 数量 + 运维人力」，是固定成本，与调用量无关；调 API 是变动成本，按 token 走。**低调用量下自部署必然更贵**——你为一台 24G 显存的机器付全款，却只用掉它 1% 的算力。只有当调用量把 API 账单推到超过「机器 + 人力」时，自部署才划算。
>
> 🎁 **加分答案**：再补两条常被忽略的。一是**自部署买到的不只是价格，是数据不出内网的合规价值**——医疗场景里这一条可能比价格重要得多，所以要分清「为了省钱」还是「为了合规」自部署，两个目的的盈亏平衡点完全不同。二是**开源模型的能力上限不等于同参数量的闭源模型**，同尺寸下闭源通常更强，所以自部署往往要在「能力」和「成本」之间做二次取舍。

🔧 **真实场景**：一份药品说明书 RAG 问答，日均只有 200 次。有人提议自部署一个 7B 模型省钱。算一下账：一张 24G 显卡按云上 ¥4/小时算，一个月 ¥2880；同样的量走 API，每次约 ¥0.003，一个月 ¥18。**差了 160 倍。** 真正该自部署的理由是「说明书里有未公开的批次数据」，不是省钱。

### 单价不是成本：三个必须先统一的口径

这一节是本篇最该带走的部分。因为面试里「哪个模型更便宜」这道题，九成的人答的是单价，而单价恰恰是最不该先答的东西。

**口径一：输入价和输出价是两个价。**

主流模型输出都比输入贵 3 到 5 倍。拿这一篇核对过的数字看：

| 模型 | 输入（元/百万） | 输出（元/百万） | 倍数 |
|---|---|---|---|
| DeepSeek Flash | 1 | 4 | 4× |
| DeepSeek V4 Pro | 4.5 | 13.5 | 3× |
| Claude Sonnet 5.5 | 14.2 | 71 | 5× |

这意味着什么？意味着**同一个模型，让回答短一半，账单能砍掉一大截**。一个 800 输入 / 300 输出的问诊，输入成本是 800 份，输出成本是 300 × 4 = 1200 份——**输出占了总成本的六成，但它只占 token 数的四分之一。**

所以「请用不超过 50 字回答」这句话，从来不只是产品要求，它是一条成本指令。

**口径二：缓存命中价，可能是未命中价的 1/20。**

DeepSeek Flash 的缓存命中输入价是 ¥0.02，未命中是 ¥1——**50 倍**。Claude Sonnet 5.5 的命中价是 $0.10，未命中 $2——**20 倍**。

这条对医疗问答尤其重要，因为「固定的 System Prompt + 同一份药品说明书」是这类产品的常态形态：每次调用前面那几千 token 一模一样。走缓存和不走，是两个成本结构。

（怎么排布前缀才能命中、缓存的有效期多长、跨轮次怎么保持——这些属于上下文工程，留到阶段三。这一篇只算它对账单的影响。）

**口径三：tokenizer 不同，token 数就不同，单价不可直接横比。**

这一条最隐蔽。Anthropic 官方文档写得很清楚：Claude 4.7 及以后的模型用了一个新 tokenizer，**同一段文本产出的 token 数比旧版多约 30%**。而中文又比英文更费 token（第一篇讲过，主流分词器以英文语料为主）。

![同一句话在不同 tokenizer 下被切成不同的子词序列——「单价更便宜」的那一方，可能在同一句话上多出三成 token](https://static.simonwillison.net/static/2023/gpt-token-encoder-decoder.jpg)

这两条加起来，就出现了一个必须警惕的情况：**你以为自己比的是价格，实际比的是「价格 × 分词效率」。**

我在这一篇的实验里就撞上了一个活生生的例子，后面实验章节会细说：**Claude Haiku 5.5 的单次成本算出来比 DeepSeek Flash 还低**（¥0.00163 对 ¥0.0020），但如果把 30% 的 tokenizer 差异补回去，算出来是 ¥0.00212——**反而更贵一点**。

**这就是为什么「单价差一倍，哪个便宜」这道题没有标准答案——它取决于你没量的那两个变量。**

> 💬 **面试官**：两个模型，A 的输入单价是 B 的一半，输出单价也是 B 的一半，是不是 A 一定更便宜？
>
> ✅ **标准答案**：不一定。要统一三个口径再比：第一，**输入输出的配比**——如果你的任务输出占比高，A 的优势会被放大；如果输入占比高（长文档问答），优势会被压缩。第二，**缓存命中率**——如果重复前缀很多，谁的缓存折扣更狠，谁就更便宜，这个折扣幅度可能到 20 倍，远大于单价差。第三，**tokenizer 是否同口径**——同一段文本在不同分词器下的 token 数可能差 30%。
>
> 🎁 **加分答案**：还有一层更根本的：**单价比的是「单位 token 的钱」，而你真正要买的是「单位任务的钱」。** 一个便宜一半但需要两轮才能答对的模型，单位任务成本是翻倍的——它多花了一倍的 token，还多了一次延迟。所以正确的比价单位不是元/百万 token，是**元/每次成功任务**，这个数字只能自己跑测试集量出来。这也解释了为什么「换模型」这件事在生产环境里必须走评估，不能靠看价格表拍板。

🔧 **真实场景**：药品说明书问答里，检索出来的说明书片段常常有 3000 token，而回答只有 150 token。这时候输入占总成本的八成以上（3000×1 对 150×4，即 3000 对 600）。**在这种任务上，「换便宜的模型」几乎没用，「减少检索片段数量」立竿见影**——这也是为什么 RAG 的召回精度直接等于成本。

### 缓存：被低估的 20 倍价差

单独把缓存拎出来讲，是因为它在成本结构里的权重被严重低估。

看下面这张表，同一个模型，输入命中率从 0% 提到 80%，月成本掉了三分之一：

| 模型 | 命中率 | 月成本 |
|---|---|---|
| DeepSeek Flash | 0% | ¥840 |
| DeepSeek Flash | 80% | ¥558 |
| Claude Sonnet 5.5 | 0% | ¥1.36 万 |
| Claude Sonnet 5.5 | 80% | ¥9747 |

（场景：日均 10000 次，输入 1200 / 输出 400 token）

这个数字有个反直觉的前提：**输入价越贵的模型，缓存带来的绝对节省越大。** Sonnet 从 ¥1.36 万降到 ¥9747，省了 ¥3900；Flash 只省了 ¥282。所以在「贵的模型 + 长固定前缀」这个组合上，缓存不是优化项，是必选项。

但缓存有个硬约束，值得在这里先埋一句：**它只对「前缀完全一致」的部分生效，前缀一变，后面全部失效。** 这一句的工程后果是——你在 System Prompt 末尾加一个动态的当前时间，整个缓存就废了。

> 💬 **面试官**：Prompt Caching 为什么能省 80% 以上的输入成本？它有什么前提？
>
> ✅ **标准答案**：它的原理是**把不变的前缀计算一次、复用多次**。Transformer 处理输入时，前面 token 的中间结果只依赖它之前的 token，所以一段固定的前缀（System Prompt、工具定义、长文档）算过一次之后，下次遇到完全相同的前缀可以直接读缓存，价格通常是未命中的 1/10 到 1/20。前提是**前缀必须逐字节一致**，并且要在有效期内命中（不同厂商有效期不同，从几分钟到一小时）。
>
> 🎁 **加分答案**：工程上真正难的不是「开缓存」，是**让前缀稳定下来**。常见破坏缓存的写法有三种：把动态时间戳放在 System Prompt 开头、把用户 ID 拼进固定模板、以及每轮都重组一遍历史消息导致顺序变化。正确的心法是**稳定内容在前、易变内容在后**，而且这条约束会反过来影响你的上下文组装顺序——这就把「缓存」和「上下文工程」绑在一起了，所以它不该被当成一个单纯的成本开关。

🔧 **真实场景**：一个用药咨询助手，System Prompt 里写了「当前时间：2026-11-02 10:23」。看起来贴心，实际上每次调用的前缀都不一样，缓存命中率恒为 0。把时间挪到用户消息里，命中率立刻上到 90% 以上。

### 选型的四个维度：顺序不能反

有了口径，才能谈决策。选型的四个维度，**顺序是有意义的，不能打乱**：

```text
① 合规（硬门槛，先过滤候选集）
   数据能否出境？不能 → 只剩境内模型 / 私有化
        ↓ 过滤后的才是候选池
② 任务复杂度（决定档位）
   多步推算 → 开思考档
   抽取分类 → 关思考档
        ↓
③ 上下文需求（决定窗口下限）
   单轮短问答 → 32K 够
   长文档理解 → 128K 起
        ↓
④ 成本（最后算）
   每次成本 × 日均量 × 30 = 月账单
```

为什么合规排第一？因为它不是优化项，是**过滤项**。你没有办法通过「优化」把一个不能出境的数据变成能出境的。合规不过关的模型，能力再强也只能从候选集里划掉——先划掉，再谈性价比。

为什么成本排最后？因为前三步已经把你的候选集缩小到了两三个，这时候再算钱才有意义。反过来先看价格表，你会把一堆根本不合适的模型放进比较里，最后得出一个「便宜」但错误的结论。

在医疗场景里，第①步通常直接砍掉一半候选。这一条不是保守，是**产品边界**。

> 💬 **面试官**：给你一个医疗问答需求，你怎么选模型？
>
> ✅ **标准答案**：按四个维度依次过。先看合规——医疗数据能不能出境，不能就只看境内模型或私有化部署，这一步决定候选集。再看任务复杂度——是简单抽取还是多步推算，决定要不要开思考档。再看上下文——是短问答还是长文档理解，决定窗口下限。最后算成本——把单价换算成每次调用成本，乘日均量乘 30，比较月账单，同时评估缓存和路由能省多少。
>
> 🎁 **加分答案**：真正的加分点是补一句**「这四步的顺序本身是回答的一部分」**。很多人会把这四项并列讲成 checklist，但在真实决策里它们是依次收窄的漏斗：合规是硬约束（不可优化）、复杂度是能力约束（决定档位）、上下文是规格约束（决定下限）、成本是经济约束（决定最终解）。把顺序讲出来，等于告诉面试官你做过真实的技术选型，而不是背过一张对比表。再补一句：选型结论要**写成文档并标注价格核对日期**，因为模型价格半年就能变一轮，没有日期的选型文档三个月后就失效了。

🔧 **真实场景**：一个院内用药咨询系统，日均 3000 次。候选里本来有 Sonnet，能力最强。但「患者病历号可能出现在 prompt 里」这一条直接把它划掉了——不是它不好，是它过不了第一道筛子。最后落在国产模型上，能力低一档，但系统能上线。

### 模型路由：成本是设计出来的

走到这里，假设你在合规筛完之后还剩两个模型：一个小而快，一个大而准。你该选哪个？

**答案是都不用选，两个都要。**

思路很朴素：**问题不是均匀分布的。** 真实业务里 70% 以上是简单问题——查个药品分类、问个禁忌、写一句提醒；剩下 30% 才是需要多步推算的（儿童剂量折算、相互作用判断）。简单问题用大模型，是拿跑车的油钱开去买菜。

![RouteLLM 把「性能」和「每次调用成本」画在同一张散点上：黑点是各个模型，红色是可学习的路由策略——注意那条红线落在两个模型连线的外侧，说明路由不是简单地在两个模型之间挑一个，而是按问题难度分流](https://lmsys.org/images/blog/routellm/main.png)

这张图值得多看几眼。横轴是成本，纵轴是能力。单个模型是散点，两个模型连起来是一条直线——**直线上每一点代表「按固定比例分流」，而红线（真实的路由策略）落在直线外侧，说明它比随机分流更聪明：简单问题它真的能认出来。**

这就是路由的本质：**不是「轮流用」，是「先判断难度，再决定交给谁」。**

这一篇的实验算了两组：

| 方案 | 月成本 | 相对全用强模型 |
|---|---|---|
| 全部走 DeepSeek V4 Pro | ¥3240 | 100% |
| 70/30 路由（Flash + V4 Pro） | ¥1560 | 48% |
| 全部走 Claude Sonnet 5.5 | ¥1.36 万 | 100% |
| 70/30 路由（Flash + Sonnet） | ¥4678 | 34% |

（场景：日均 10000 次，输入 1200 / 输出 400 token）

同厂商双档路由省了 52%，跨厂商路由省了 66%。**注意跨厂商那一组的节省更大，但它的风险也更大**——两套 API 的错误格式、限流策略、流式协议都不一样，这部分工作量是阶段二「多模型抽象」要解决的问题。

这里必须说清楚一件事：**路由不是免费的。** 它的代价是三样东西——

- **判断成本**：路由本身要么用规则（关键词、长度），要么用小模型分类，要么用置信度，每一种都有误判率
- **一致性成本**：同一个用户两轮对话分别落到两个模型上，回答风格会跳
- **运维成本**：两套 key、两套限额、两套降级策略

所以路由的判据不是「能省多少」，而是**「省下来的钱，够不够覆盖误判带来的体验损失」**。简单问题误判成大模型，只是多花钱；复杂问题误判成小模型，是答错——后者在医疗场景里是事故。

> 💬 **面试官**：模型路由怎么做？怎么防止把复杂问题路由到小模型上？
>
> ✅ **标准答案**：三个层次。**规则路由**——按任务类型、输入长度、是否含数值计算等显式特征分流，可解释、零成本，但覆盖不全。**分类器路由**——训练一个小模型判断「这题难不难」，RouteLLM 这类工作就是在做这个，效果比规则好但要标注数据。**置信度路由**——先让小模型答，答完用打分模型（或小模型自评）判断可靠性，不可靠再升级，类似级联。防误判的关键是**把「升级」做成单向兜底**：小模型可以升级到大模型，大模型不降级，并且设一个保守阈值。
>
> 🎁 **加分答案**：加分点在于指出**路由的失败模式是非对称的**。简单问题误路由到强模型，代价是多花钱；复杂问题误路由到弱模型，代价是答错——这两个方向的损失差一个数量级。所以生产上的正确姿势不是「优化平均成本」，是**「把误判的代价不对称性编进阈值」**：宁可多花钱，也不让复杂问题落到小模型上。进一步的工程做法是给低置信度的回答加一层「不确定提示」或强制人工复核，这在医疗场景里比省钱重要得多。

🔧 **真实场景**：用药咨询助手的路由规则很土——prompt 里出现「剂量」「折算」「相互作用」「能不能一起」这些词，或者含数字，就走思考档；其余走普通档。规则朴素，但它把「该不该多想」这件事故意做成了可审计的判定，出问题能复盘。

### 成本估算：把单价换算成一张账单

到这一步，方法本身很简单，只有一行：

```text
单次成本 = (输入 token × 输入单价 + 输出 token × 输出单价) / 1,000,000
月成本   = 单次成本 × 日均调用量 × 30
```

关键不在公式，在**代入的数字从哪来**。三个数字必须是从你自己系统里量出来的，不能拍脑袋：

- **平均输入 token**：不是你以为的 prompt 长度，是「System Prompt + 历史 + 检索片段 + 用户问题」的总和。做成 RAG 之后这个数字会翻几倍。
- **平均输出 token**：不是 max_tokens，是实际产出的均值。
- **日均调用量**：注意是**调用次数**，不是用户数。一个用户一轮对话可能是 5 次调用。

拿成长期场景算一遍完整的：

```text
DeepSeek Flash，输入 1200 / 输出 400
  单次 = (1200 × 1 + 400 × 4) / 1,000,000 = 0.0028 元
  日成本 = 0.0028 × 10,000 = 28 元
  月成本 = 28 × 30 = 840 元

Claude Sonnet 5.5，同场景
  单次 = (1200 × 14.2 + 400 × 71) / 1,000,000 = 0.0454 元
  日成本 = 0.0454 × 10,000 = 454 元
  月成本 = 454 × 30 = 13,632 元
```

**同样的任务，同样的 token 数，月账单差了 16 倍。** 这个差距不是「顺手省一点」，它是「这个产品能不能商业化」的量级。

![FrugalGPT 的准确率-成本权衡曲线：横轴是成本，纵轴是准确率，每一个点是一种策略——曲线是凹的，说明「多花一点钱换更多准确率」的边际收益在快速递减，所以最优点往往不在最贵的那一端](https://ar5iv.labs.arxiv.org/html/2305.05176/assets/tradeoffs_full.png)

这张图说明一件很重要的事：**成本和准确率不是线性关系。** 曲线很快就变平了——从最贵那端往左走一小段，准确率只掉一点点，成本掉一大截。这条曲线的形状，就是「选型」这件事存在的理由：如果是一个直线，那答案永远是「看预算」；正因为它是凹的，才存在一个「刚好够用且算得起」的点。

> 💬 **面试官**：日均 1 万次调用，你怎么把成本压下来？
>
> ✅ **标准答案**：按「影响面 × 改动成本」排序。第一步是**分级路由**——70% 简单任务走小模型，这一条通常能砍一半。第二步是**缓存**——把稳定的 System Prompt 和固定文档做成前缀缓存，输入价能降到 1/10 到 1/20。第三步是**上下文精简**——少放检索片段、压缩历史、控制回答长度，让 token 数下降。第四步是**语义缓存**——相似问题直接返回上一次的答案，命中率高时效果显著。第五步才是**换更便宜的模型**，因为它的代价是能力，前四步的代价只是工程量。
>
> 🎁 **加分答案**：一定要补一句「**先建立度量再优化**」。没有按「功能 / 用户 / 租户」拆分的成本报表，你根本不知道钱花在哪——真实情况往往是 20% 的功能吃掉 80% 的成本，而那 20% 里有一半是没人用的。所以正确顺序是：先埋点（记录每次调用的模型、token 数、功能标签），再看分布，再砍。另外补一个反直觉的：**输出侧往往比输入侧更值得下手**，因为输出单价贵 3 到 5 倍，而且很多人根本没意识到自己让模型「详细说明」花了多少钱。

🔧 **真实场景**：一个问诊产品的账单复盘发现，60% 的成本来自「药品信息介绍」这一个功能——而这个功能的回答有 800 字，用户实际只看前 100 字。把它改成「先给 50 字结论 + 展开按钮」，输出 token 掉了八成，月成本直接腰斩。

## 🧪 动手实验：写一个成本估算器

> **说明**：下面是脚本的**运行形态示意**，其中的输出内容与各项数值均为示意值，真实数值以你本机运行为准。脚本已就绪：`labs/phase1-cognition/04-cost/`。

这个实验和前三篇不一样——**它不调 API，花费 ¥0**。因为成本估算本来就是一道纯计算题，你要练的是「怎么把一个需求翻译成一张账单」，而不是再花一次钱。

脚本里有 6 个候选模型，价格全部核对于 2026-11-02，每一条都在 `prices.ts` 里写了来源。

```bash
# 在仓库根目录
pnpm --filter @medai/labs cost
```

不需要任何 API key。

### 实验 B：缓存与路由

把调用量放大到日均 10000 次（输入 1200 / 输出 400），再跑两组对照：缓存命中率 0% / 50% / 80%，以及 70/30 路由在「同厂商双档」和「跨厂商」下的节省比例。

```text
缓存命中率     DeepSeek Flash    Claude Sonnet 5.5
   0%              ¥840              ¥1.36 万
  50%              ¥664              ¥1.12 万
  80%              ¥558              ¥9747

路由方案                          月成本      相对全用强模型
全部走 DeepSeek V4 Pro            ¥3240          100%
70/30 → Flash + V4 Pro            ¥1560          48%
全部走 Claude Sonnet 5.5          ¥1.36 万        100%
70/30 → Flash + Sonnet            ¥4678          34%
```

### 四条读数

**第一，叫「Max」「Pro」「Sonnet」的这些名字，价差比你想的更大。**
同样一组 token，最便宜和最贵的候选差了 20 倍（¥49 对 ¥980）。这个倍数比「换一个厂商」带来的差异大得多——所以选型的第一个动作不是选厂商，是选档位。

**第二，推理档贵不是贵在单价，是贵在量。**
DeepSeek V4 Pro 的单次成本是 Flash 的 3.8 倍，但这个数字还是按同样的输出 token 算的。真实情况是思考档会先生成一大段推理 token，而推理 token 按输出计费——**所以实际倍数会比 3.8 更高，可能到 10 倍以上。** 这条要记住：成本表里的「推理档」永远是乐观估计。

**第三，Claude Haiku 5.5 算出来比 DeepSeek Flash 还便宜，但这个结论不能直接用。**
¥0.0016 对 ¥0.0020，看起来 Haiku 赢了。但 Haiku 用的是新的 tokenizer，同一段文本多约 30% token。补回去之后是 ¥0.00212 对 ¥0.0020——**结论直接翻过来，Haiku 更贵。** 这是这一篇最想让你记住的一个瞬间：**裸单价表会骗人，而且是往「看起来更便宜」的方向骗。**

**第四，路由的节省比例，取决于两个模型之间的价差有多大。**
同厂商双档（Flash + V4 Pro）省 52%，跨厂商（Flash + Sonnet）省 66%。但跨厂商那一组的工程成本也更高——两套 API 的差异要自己吸收。**省钱和省事，在这里是一道明码标价的取舍题。**

![FrugalGPT 在真实数据集上的级联案例：只用最强模型五分之一的预算，准确率反而更高——因为很多问题便宜模型就能答对，而它错的那部分恰好被强模型救回来](https://ar5iv.labs.arxiv.org/html/2305.05176/assets/FGPTcasestudy.png)

这张图是 FrugalGPT 最有力的一个证据：**在 1/5 的预算下准确率还更高。** 原因不是「便宜模型更好」，而是「很多问题根本不需要贵模型」——把贵模型留给它真正擅长的那部分，同时避免了贵模型在某些题上的偶发错误。

> 💬 **面试官**：你做完成本估算，发现月账单超预算三倍，你从哪下手？
>
> ✅ **标准答案**：先查分布，再动手。第一步把账单按「功能 / 模型 / 输入输出」三个维度拆开，找到吃掉 80% 成本的那一小部分。第二步判断那部分是否值得——如果是一个没人用的功能，直接下线；如果是一个高频功能但输出过长，先砍输出。第三步才做技术优化：缓存、路由、上下文精简。这个顺序的理由是：**前两步是业务决策，收益最大且不增加系统复杂度；后一步是工程决策，有维护成本。**
>
> 🎁 **加分答案**：补一句「**别在没定位问题前就换模型**」。换模型是最容易被想到、也最容易做错的动作——它同时改了三件事：能力、价格、以及所有 prompt 的适配。正确做法是先把账单拆开，因为超预算的原因通常是「某个功能被高频调用」或「某个 prompt 太长」，而不是「模型选贵了」。真实案例里，把「详细说明」改成「50 字结论」这一类改动，往往比换模型省得多。

🔧 **真实场景**：把这张表直接拿去开评审会，比讲「我们用 DeepSeek 因为便宜」有说服力得多——因为表里每一行都能点开 `priceUrl` 复核，每一列都是业务方关心的单位（每次多少钱、一天多少、一个月多少）。

## 🚧 结论与边界

本篇压成一句话：

> **成本是设计出来的，不是省出来的。**

四条推论：

- **单价不是成本。** 单价要乘上 token 数和输出占比才是成本，而输出价比输入价贵 3 到 5 倍，所以「让模型少说废话」是被低估的省钱手段。
- **比价前先统一三个口径**：输入输出配比、缓存命中率、tokenizer 是否同口径。三个都不统一就报单价，等于在比一个不存在的数字。
- **选型的顺序不能反**：合规（硬门槛）→ 复杂度（档位）→ 上下文（窗口）→ 成本（账单）。先算钱会选错，跳过合规会翻车。
- **路由和缓存是两笔独立收益**，可以叠加。但路由有误判成本和运维成本，它的判据不是「省多少」，是「省下来的够不够覆盖误判」。

到这里，阶段一要回答的两个问题都有答案了。

路线图里写着阶段一的里程碑是两条：能解释「为什么大模型会一本正经地胡说八道」，能根据任务选择合适的模型与参数。第一条在第 00 篇给了根因（目标是求像不是求真），第 01 到 03 篇给了它的三个侧面（token 预算、能力边界、采样随机）。第二条就是这一篇：四个维度、三条口径、一张账单。

**这五篇加起来，构成的是一个判断力，而不是一堆名词。** 当你下次看到「某模型降价 50%」的新闻时，你应该问的不是「要不要换」，而是——我的输入输出比是多少？缓存能命中多少？它的分词器和现在这个差多少？这三问答不上来，降价消息对你就没有意义。

有意识地留到后面三件事：

- **怎么把「选型」落地成一套可切换的代码**：统一的 provider 接口、降级链、按任务路由 → 阶段二（多模型抽象）
- **怎么让输出不靠「抽签抽得好」**：JSON Schema 约束、结构化输出、Function Calling → 阶段二（结构化输出）
- **自建推理的真实成本**：GPU 小时、量化、吞吐，以及它什么时候真的比 API 便宜 → 阶段八（部署与推理优化）

## 🎤 面试追问链

单个问题答对只能拿及格分。真正的区分度在追问——面试官会顺着你的答案往下挖。

**追问一：「你说要用路由省钱，那路由判断错了怎么办？」**

分方向看。简单问题误判到大模型，代价只是多花钱，可以接受；复杂问题误判到小模型，代价是答错，必须兜住。所以设计上把路由做成**单向可升级**的：低置信度一定升级，高置信度也不降级。具体做法是给每个回答打一个可靠性分（小模型自评、或独立的打分模型），低于阈值就交给强模型重答。另外要接受一个事实——**路由一定会误判，所以它是成本优化手段，不是正确性保障手段**。正确性要靠评估集和人工复核兜底。

**追问二：「为什么医疗场景常优先国产模型或私有化部署？」**

不是能力问题，是**合规和风险归属问题**。三条：数据出境需要单独评估，患者信息属于敏感个人信息，走境外 API 要过合规关；境内模型在备案与监管接口上更顺；私有化部署能保证数据物理不出内网。这三条里第一条是硬门槛，后两条是加分项。反过来讲，如果场景是公开的药品说明书问答、不含任何患者信息，那条境外模型的限制就松很多——**要区分「数据里有什么」，而不是一律保守**。

**追问三：「什么时候用推理档是纯浪费？」**

判据是这题有没有「中途发现想错了」的空间。多步计算、逻辑推理、需要反复权衡的方案——有，值得付思考的钱。单步抽取、分类、格式转换、简单事实问答——没有，开了就是把钱花在几百个 token 的自我确认上。再补一个量化的角度：思考 token 按输出计费，输出又是最贵的那一项，所以**开思考档的成本倍数不是 2 倍 3 倍，可能是 10 倍**。判断「值不值」要拿这个倍数去和「答错一次的代价」比。

**追问四：「两个模型，一个单价便宜一半，你怎么判断哪个划算？」**

不能只看单价。三件事：第一，我这个任务的输入输出配比是多少——输出占比高的话，输出单价的差异会被放大；第二，我的缓存命中率是多少——如果重复前缀多，缓存折扣（可能 20 倍）比单价差重要得多；第三，两个模型的 tokenizer 是不是同一口径——同一段文本的 token 数可能差 30%。三个都对齐之后再比，而且比的单位应该是**「每次成功任务的钱」**，不是元每百万 token。

**追问五：「你怎么向产品经理解释为什么这个功能很贵？」**

不要讲 token 单价，讲**单位业务指标的成本**。「这个问诊功能每回答一次是 3 分钱，一天 1 万次是 300 块，一个月 9000。」然后拆开讲哪部分贵：「其中六成花在让模型详细说明上，而用户平均只读前 100 字。」——用业务方听得懂的单位，用他们能改的旋钮。技术细节留在他追问的时候再说。
