# 02 — SSE 服务端：把一个模型的流，转成一条 SSE

对应文章：第 02 篇《SSE 服务端：流式不是「更快返回」，是「更早开始」》

## 要验证什么

调 DeepSeek 的流式接口，把模型吐出来的增量用 SSE 帧格式转发给浏览器。

```
index.ts   主案例：/sse 真流式 + /block 整段发（对照）
proxy.ts   可选：一个「攒够 512 字符才转发」的缓冲代理（实验 C）
```

代码只回答四个问题：

1. **流式调用多加了什么**？就一个 `stream: true`，响应体从一段 JSON 变成一条字节流。
2. **四个响应头分别干什么**？尤其 `X-Accel-Buffering: no`——本地删了没感觉，上线删了就是「憋八秒吐一次」。
3. **为什么要按「两个换行」切帧**？一个网络分片可能是半帧，也可能同时带来好几帧。
4. **用户关页面后，上游为什么必须停**？不写 `res.on('close')`，钱就继续烧。

## 怎么跑

```bash
# 终端 1：主服务
nvm use 22
pnpm --filter @medai/labs p2-sse

# 终端 2（可选，实验 C 才需要）：缓冲代理
pnpm --filter @medai/labs p2-sse-proxy
```

需要 `.env.local` 里配 `DEEPSEEK_API_KEY`，缺 key 时给中文提示并退出。

## 看到什么算成功

### 实验 A：分片数 ≠ 帧数

```bash
curl -N http://127.0.0.1:3002/sse
# 想看每个分片什么时候到，加 --trace 重启服务：
# pnpm --filter @medai/labs p2-sse -- --trace
```

文字随时间一段段出现，中间能看见 `: ping` 心跳，末尾是 `data: [DONE]`。同时终端 1 打印：

```text
✅ 这一次：29 个网络分片 → 61 个 data 帧（分片数 ≠ 帧数）
```

两个数字对不上——客户端收到的是字节块，帧是服务端按 `\n\n` 自己切出来的。

### 实验 B：首字节 vs 总耗时

```bash
curl -N -o /dev/null -w '首字节 %{time_starttransfer}s 总耗时 %{time_total}s\n' http://127.0.0.1:3002/sse
curl -N -o /dev/null -w '首字节 %{time_starttransfer}s 总耗时 %{time_total}s\n' http://127.0.0.1:3002/block
```

本机实测（2026-11-06，各跑 3 次取区间）：

| 路径 | 首字节 | 总耗时 |
|---|---|---|
| `/sse` 真流式 | 130 ~ 170ms | 1160 ~ 1510ms |
| `/block` 整段发 | 1195 ~ 1219ms | 1195 ~ 1219ms |

`/block` 的首字节 ≈ 总耗时，用户全程一个字节都收不到。`/sse` 的总耗时没变，但第一个字一百多毫秒就到了。**这就是本篇结论的全部证据。**

再验证客户端自己的缓冲：同一条命令去掉 `-N`，逐字会变成「先干等，再整段出现」。

### 实验 C：中间加一个会缓冲的代理

```bash
curl -N -o /dev/null -w '%{time_starttransfer}s\n' http://127.0.0.1:3002/sse   # 直连
curl -N -o /dev/null -w '%{time_starttransfer}s\n' http://127.0.0.1:3003/sse   # 经代理
```

实测首字节从 130 ~ 170ms 变成 636 ~ 711ms。**服务端一行代码没改**——病在中间那一层。注意代理照搬了上游的 `X-Accel-Buffering: no` 却照攒不误，因为它压根不认识这个头。

## 故意留下的两处「不完美」

| 没做的事 | 为什么 | 留在哪 |
|---|---|---|
| 不解析 `delta.content` | 服务端只负责找帧边界，解读内容交给客户端——剥掉业务逻辑才能看清 SSE 本身 | 第 03 篇（前端消费） |
| 断线重连后不补发 | 需要消息历史 | 阶段三 |

## 预算

每打一次 `curl` 就是一次真实调用，约 ¥0.01；做完全部观察（A 1 次 + B 2 次 + C 2 次）约 ¥0.05，远低于本篇 ¥2 上限。
