### 第 01 篇：为什么前端也需要算法？React Fiber/虚拟 DOM/事件队列里的数据结构

**副标题**：从真实前端源码切入，看懂工程背后的数据结构选型逻辑

#### 一、使用与实践

- React Fiber 架构：每个组件对应一个 FiberNode，通过 `child/sibling/return` 三个指针构成链表+树的混合结构——为什么不用普通数组？因为链表可以在任意位置暂停和恢复，支持时间分片
- 虚拟 DOM diff：React 的 reconcile 算法本质是树的层序遍历 + 双指针对比子节点列表——为什么同层对比？因为跨层移动 DOM 代价极高，这个工程妥协把 O(n³) 降为 O(n)
- 浏览器事件循环：macrotask 队列（FIFO 队列）+ microtask 队列（优先级更高的 FIFO）+ 渲染时机——理解为什么 `Promise.then` 比 `setTimeout` 先执行，本质是两个不同优先级的队列调度
- V8 引擎的数组优化：JS 数组在底层根据内容分为 `PACKED_SMI_ELEMENTS`（连续整数）、`PACKED_ELEMENTS`（连续混合类型）、`HOLEY_ELEMENTS`（含空洞）等多种内部类型，访问性能差距可达 5 倍以上

#### 二、设计与原理

- 数据结构是"组织数据的方式"，算法是"操作数据的步骤"——两者共同决定了一段代码的时间/空间成本
- 抽象数据类型（ADT）：接口（什么操作）与实现（怎么存储）分离，同一个 ADT 可以有多种实现，性能特征各不相同（如"队列"可以用数组或链表实现，但摊还复杂度不同）
- 前端特有的约束：浏览器主线程单线程、JS 执行时间直接影响帧率（16.6ms/frame）、内存受限——这些约束让数据结构选型的权衡与服务端有所不同

#### 三、工程落地参考

- React FiberNode 定义：`packages/react-reconciler/src/ReactInternalTypes.js` 中 `Fiber` 类型的 `child`/`sibling`/`return` 字段——这三个指针把整棵组件树编码为一个可中断遍历的链表结构
- V8 元素类型枚举：`src/objects/elements-kind.h`（V8 源码）中 `ElementsKind` 枚举——展示 V8 为数组内部维护的 21 种元素类型，说明"JS 数组是动态数组"这个说法掩盖了多少底层复杂性

#### 四、实践演示与验证

用 Node.js 跑一个基准测试，对比同等长度的 `PACKED_SMI` 数组与 `HOLEY` 数组在 `forEach` 遍历上的耗时差异，直观建立"数组打空洞有代价"的认知；再用 Chrome DevTools 的 Memory Snapshot 观察 FiberNode 链表在内存中的实际布局。

#### 五、参考

- React reconciler 源码：`packages/react-reconciler`（facebook/react 仓库）
- V8 元素类型优化：https://v8.dev/blog/elements-kinds
- HTML 规范 Event Loop：https://html.spec.whatwg.org/multipage/webappapis.html#event-loops

### 第 02 篇：时间与空间复杂度：从前端代码瓶颈到 Big-O 分析体系

**副标题**：用 performance.now 实测 O(n) vs O(n²) 的增长曲线，建立前端性能直觉

#### 一、使用与实践

- 真实前端瓶颈：`Array.includes` 在大列表里是 O(n)，换成 `Set.has` 是 O(1)——药品搜索列表去重场景，10 万条数据下两者耗时差 100 倍以上
- 深克隆的隐患：递归深克隆对深层嵌套对象是 O(n·d)（n 是节点数，d 是深度），医疗表单保存时频繁触发深克隆会直接卡帧
- 循环嵌套陷阱：两层 `for` 循环渲染处方-药品关联关系，n 个处方 × m 种药品 = O(n×m)，超过千条数据后 TTI 肉眼可见

#### 二、设计与原理

- Big-O / Big-Ω / Big-Θ 的区分：O 是上界（最坏情况）、Ω 是下界（最好情况）、Θ 是紧确界（平均情况）——面试中说"这个算法是 O(n log n)"默认指最坏情况，要理解这个约定
- 常见复杂度增长速度：O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) < O(n!)——n=1000 时，O(n²) = 百万次操作，O(2ⁿ) = 宇宙热寂
- 摊还分析：JavaScript 数组 `push` 的均摊复杂度是 O(1)，偶尔触发扩容时是 O(n)——摊还分析让我们评估"长期平均代价"而非单次最坏代价
- 递归树展开法：分析递归算法复杂度的标准工具，每层节点数 × 每层操作数 × 层数

#### 三、工程落地参考

- V8 Torque 中 `Array.prototype.sort` 的注释：`builtins/array-sort.tq`——注释里直接标注了"最坏情况 O(n log n)"，解释为什么 V8 从 QuickSort 切换到 TimSort（稳定性 + 最坏复杂度保证）
- ECMAScript 规范中的复杂度暗示：Array `push`/`pop` 规范里的步骤数与 O(1) 的关系——规范不直接说复杂度，但步骤数可以推断

#### 四、实践演示与验证

用 `performance.now` 分别测试 n = [100, 1000, 10000, 100000] 下 O(1)/O(n)/O(n²) 操作的耗时，用对数坐标绘制增长曲线，让复杂度从"概念"变成"可观测的曲线斜率"。

#### 五、参考

- V8 TimSort 博客：https://v8.dev/blog/array-sort
- 《算法导论》第3章：增长量级的记号
- MDN performance.now：https://developer.mozilla.org/zh-CN/docs/Web/API/Performance/now

### 第 03 篇：栈：浏览器调用栈/undo 历史/单调栈高频题型全解

**副标题**：LIFO 的本质与单调栈的剪枝思想，拆解 LeetCode 高频栈题

#### 一、使用与实践

- 浏览器调用栈：JS 引擎用栈追踪函数调用，每次调用 push 一个执行上下文，返回时 pop——栈溢出（Maximum call stack size exceeded）就是这个栈满了
- undo/redo 实现：富文本编辑器（如医疗病历系统）的撤销历史天然是两个栈，undo 栈存操作历史，redo 栈在撤销时接收操作
- 括号/标签匹配：HTML 标签嵌套验证、JSON 合法性校验、代码编辑器的括号高亮——入栈开符号、遇到闭符号时出栈匹配
- 表达式求值：中缀转后缀（逆波兰表达式），计算器类问题的标准解法

#### 二、设计与原理

- LIFO（Last In First Out）原则：最后入栈的元素最先出栈——核心操作 `push`/`pop`/`peek` 均 O(1)
- 数组实现 vs 链表实现：数组实现内存连续、缓存友好、扩容时 O(n)；链表实现无需预分配、每次操作 O(1) 但有额外指针开销——JS 中直接用数组模拟栈（`arr.push`/`arr.pop`）是最常见且性能最好的选择
- **单调栈**（高频考点）：维护一个栈内元素单调递增或递减的栈，当新元素"破坏单调性"时，出栈并处理——时间复杂度 O(n)，因为每个元素最多入栈/出栈一次。适用场景：找每个元素左/右侧第一个更大/更小值（Next Greater Element 系列）

#### 三、工程落地参考

- ECMA-262 执行上下文栈：规范 §8.3 "Execution Contexts" 和 §8.4 "Jobs and Host Operations"——规范里的 Execution Context Stack 就是 JS 的调用栈，每次函数调用对应一次 Push，是栈数据结构在语言规范层面的直接体现
- React ErrorBoundary 的栈追踪：`packages/react-reconciler/src/ReactFiberWorkLoop.js` 中捕获错误时读取 `fiber.return` 链追溯组件栈——React 用 Fiber 链表模拟了一个可中断的"调用栈"

#### 四、实践演示与验证

手写一个支持 `push`/`pop`/`min` 的最小栈（LeetCode 155）；再实现"每日温度"（LeetCode 739）的单调栈解法，对比暴力 O(n²) 与单调栈 O(n) 的实际耗时差。

LeetCode 重点题：20（有效括号）/ 155（最小栈）/ 739（每日温度）/ 84（柱状图最大矩形）/ 85（最大矩形）

#### 五、参考

- ECMA-262 执行上下文：https://tc39.es/ecma262/#sec-execution-contexts
- labuladong 单调栈框架：https://labuladong.online/algo/data-structure/monotonic-stack/

### 第 04 篇：队列：事件循环任务队列/BFS/双端队列与滑动窗口

**副标题**：FIFO 结构在浏览器事件循环与图搜索中的两种核心用法

#### 一、使用与实践

- 浏览器 macrotask/microtask 队列：`setTimeout` 回调进 macrotask 队列，`Promise.then` 进 microtask 队列——每次事件循环执行一个 macrotask 后，清空全部 microtask 队列，这是两者执行顺序的直接原因
- Node.js 消息队列：libuv 的事件循环有 6 个阶段（timers → pending callbacks → idle → poll → check → close），每个阶段内部是队列——理解这个可以解释为什么 `setImmediate` 比 `setTimeout(fn, 0)` 在某些场景更快
- BFS 层序遍历：医疗组织架构树的层级展示、React 组件树的宽度优先搜索——BFS 天然用队列实现，保证按层访问
- 打印机任务队列/消息推送缓冲：FIFO 语义与真实业务场景的对应

#### 二、设计与原理

- FIFO（First In First Out）原则：最先入队的元素最先出队——核心操作 `enqueue`/`dequeue` 均 O(1)
- 循环队列：用数组实现队列时，`dequeue` 时直接移动头指针而非 `shift`（`shift` 是 O(n)），通过模运算 `head = (head + 1) % capacity` 实现循环复用，避免假溢出
- 双端队列（Deque）：两端均可入队和出队——`滑动窗口最大值`（LeetCode 239）的标准解法，用单调双端队列在 O(n) 时间内解决 O(n²) 的暴力问题
- 优先队列：按优先级出队而非按入队顺序——本质是堆，在第 08 篇展开

#### 三、工程落地参考

- HTML 规范 Event Loop 的任务队列定义：https://html.spec.whatwg.org/multipage/webappapis.html#task-queue——规范里任务队列（task queue）是一个"集合"而非严格队列（允许某些情况下跳过特定任务），与我们通常理解的 FIFO 队列有细微差别，这个差别在面试中被考察过
- Node.js libuv 事件循环源码：`deps/uv/src/unix/core.c` 中 `uv_run` 函数——可以看到六个阶段的循环结构，每个阶段处理对应队列

#### 四、实践演示与验证

用 Node.js 写一段代码，混合 `Promise.then`/`queueMicrotask`/`setTimeout`/`setImmediate`，预测并验证执行顺序，彻底搞清楚 microtask/macrotask 的调度机制；再实现滑动窗口最大值（LeetCode 239）的双端队列解法，对比暴力和优化版本耗时。

LeetCode 重点题：232（用栈实现队列）/ 641（设计循环双端队列）/ 239（滑动窗口最大值）/ 102（二叉树层序遍历）

#### 五、参考

- HTML 规范 Event Loop：https://html.spec.whatwg.org/multipage/webappapis.html#event-loops
- Node.js 事件循环官方文档：https://nodejs.org/en/docs/guides/event-loop-timers-and-nexttick

### 第 05 篇：链表：React Fiber 链表结构与 LRU Cache 手写实现

**副标题**：指针操作的心智模型、哑节点技巧，以及链表在工程中的真实形态

#### 一、使用与实践

- React Fiber 链表：每个 FiberNode 有 `child`（第一个子节点）、`sibling`（下一个兄弟节点）、`return`（父节点）三个指针——这三个指针把整棵组件树编码为一个链表结构，让 React 可以在任意节点暂停遍历（时间分片的基础）
- LRU Cache（最近最少使用缓存）：浏览器的 HTTP 缓存、前端状态管理中的缓存淘汰——用双链表 + HashMap 实现 O(1) 的 `get` 和 `put`：HashMap 存 key → 节点的映射，双链表维护访问顺序（最近访问放头部，淘汰时移除尾部）
- 药品搜索历史：有限容量的最近搜索记录，天然是 LRU 语义

#### 二、设计与原理

- 单链表/双链表/循环链表：单链表只有 `next` 指针，删除节点需要找到前驱（O(n)）；双链表有 `prev`/`next` 双向指针，删除节点 O(1)；循环链表的 `tail.next === head`，适合轮转场景
- **哑节点（Dummy Node）技巧**：在链表头部插入一个哨兵节点，统一处理头节点和非头节点的边界情况，消除大量 `if head === null` 的特殊判断——80% 的链表题用这个技巧可以简化代码
- 快慢指针：两个指针以不同速度遍历链表——检测环（慢1步/快2步，相遇则有环）、找中点（快指针到尾时慢指针在中间）、找倒数第 k 个节点

#### 三、工程落地参考

- React Fiber 的链表遍历：`packages/react-reconciler/src/ReactFiberWorkLoop.js` 中 `performUnitOfWork` 函数——这是 React 的工作循环，通过 `fiber.child`/`fiber.sibling`/`fiber.return` 三个指针实现 DFS 遍历，可以在任意位置被中断和恢复，这正是链表相比树数组结构的优势

#### 四、实践演示与验证

手写 LRU Cache（LeetCode 146）的 TypeScript 实现：先实现双链表类（`addToHead`/`removeNode`/`removeTail`），再用 Map 存 key-节点映射，组合为完整的 LRU；同时在 React DevTools 里观察 FiberNode 的 `__reactFiber` 链表结构。

LeetCode 重点题：206（反转链表）/ 21（合并有序链表）/ 142（环形链表 II）/ 146（LRU 缓存）/ 25（K 个一组翻转链表）

### 第 07 篇：树：DOM 遍历/虚拟 DOM diff/BST/Trie 前缀树实战

**副标题**：递归与迭代遍历、BST 有序性、Trie 前缀匹配——前端高频树形结构全解

#### 一、使用与实践

- **Trie（前缀树）**：每个节点是一个字符，从根到某节点的路径代表一个前缀——插入/查询 O(m)（m 是字符串长度）；空间消耗大，可用压缩 Trie（radix tree）优化

### 第 08 篇：堆：优先队列/Top-K/数据流中位数手写最小堆

**副标题**：完全二叉树的数组表示、上浮/下沉操作，O(n) 建堆的原理

#### 一、使用与实践

- 任务优先队列：医院急诊分诊系统按病情紧急度排序——每次取优先级最高的任务，用堆可以做到 O(log n) 的插入和 O(log n) 的取最大/最小
- Top-K 问题：药品销量前 10 名、日志系统里访问量最多的 K 个 API——不需要全排序，维护一个大小为 K 的堆即可 O(n log K)
- 数据流中位数：实时医疗监测数据的中位数——双堆（一个最大堆存较小半部分，一个最小堆存较大半部分）可以 O(1) 获取中位数
- Node.js 定时器：Node.js 的 `setTimeout` 定时器内部用最小堆管理，每次取堆顶（最早到期的定时器）

#### 二、设计与原理

- 完全二叉树的数组表示：堆用数组存储，下标 `i` 的父节点是 `(i-1)>>1`，左子节点是 `2i+1`，右子节点是 `2i+2`——内存连续、无需指针、缓存友好
- **上浮（sift up）**：插入新元素时放在末尾，然后与父节点比较，若违反堆性质则交换，重复直到满足——O(log n)
- **下沉（sift down）**：删除堆顶时把末尾元素移到顶部，然后与较大/较小的子节点比较交换，直到满足——O(log n)
- **O(n) 建堆**：从最后一个非叶节点开始，依次对每个节点执行下沉操作——直觉上是 O(n log n)，但通过数学分析（大部分节点是叶节点，下沉距离短）可以证明实际是 O(n)

#### 三、工程落地参考

- Node.js 定时器堆：`lib/internal/timers.js` 中 `timerListQueue`（一个最小堆）——Node.js 用最小堆按到期时间排序所有定时器，事件循环的 timers 阶段每次取堆顶检查是否到期

### 第 10 篇：排序：V8 TimSort 源码解析/快排/归并/稳定性全解

**副标题**：比较排序的 O(n log n) 下界、稳定性的实际影响、V8 为什么从快排切换到 TimSort

#### 一、使用与实践

- 前端列表排序：药品列表按价格/销量/字母排序——ES2019 前 `Array.prototype.sort` 在不同浏览器实现不同，排序结果可能不稳定（相同键值的元素顺序可能变化），ES2019 规范强制要求稳定性后才统一
- 稳定性的实际影响：先按科室排序，再按优先级排序，如果 `sort` 不稳定，两次排序后同一优先级内科室顺序会乱——稳定排序是多键值排序的基础
- 大数据集的分页排序：100 万条用药记录，服务端分页返回后前端只排当前页——这时 O(n log n) 和 O(n²) 的差距在前端侧很小，但全量数据的服务端排序差距巨大

#### 二、设计与原理

- 比较排序的下界：任何基于比较的排序算法，最坏情况不可能优于 O(n log n)——可以用决策树模型证明：n 个元素有 n! 种排列，需要至少 log₂(n!) ≈ n log n 次比较才能区分所有情况
- **快速排序**：选 pivot，分区（小于 pivot 的放左边，大于的放右边），递归——平均 O(n log n)，最坏 O(n²)（已排序数组 + 选第一个元素为 pivot）；三路分区解决大量重复元素的问题；原地排序、空间 O(log n)；**不稳定**
- **归并排序**：分半，递归排序两半，然后合并——始终 O(n log n)，无最坏情况；**稳定**；但需要 O(n) 额外空间
- **TimSort**（V8 实际使用）：归并排序 + 插入排序的混合——对短序列（< 64 个元素）用插入排序（小数组上常数因子小），对长序列识别已有序的 "run"（连续递增/递减子序列），然后用归并排序合并这些 run——对真实数据（通常有部分有序性）比纯归并快得多；**稳定**，O(n log n) 最坏，接近 O(n) 最好

#### 三、工程落地参考

- V8 TimSort 实现：`builtins/array-sort.tq`（V8 源码，Torque 语言）——可以看到 `INSERTION_SORT_THRESHOLD = 64` 的常量，以及识别 run、计算 runLength、MergeCollapse 合并策略的完整实现
- TC39 ES2019 稳定排序：`Array.prototype.sort` 规范从 ES2019 起明确要求"If comparefn is not provided, the sort is implementation-defined, **stable**"——这是明确写进 ECMAScript 规范的稳定性保证

#### 四、实践演示与验证

手写快速排序（三路分区版本）和归并排序，对比在 [随机数组 / 已排序数组 / 大量重复元素数组] 三种场景下的耗时；再用 Chrome DevTools 验证 `Array.prototype.sort` 的稳定性（同键值元素排序前后顺序不变）。

### 第 11 篇：搜索：二分搜索变体精讲/BFS 最短路径/DFS 回溯

**副标题**：循环不变式建立二分思维，BFS/DFS 选择策略，双指针与滑动窗口

#### 一、使用与实践

- 有序列表快速查找：药品价格区间筛选（在有序价格列表里找满足条件的边界）、版本号二分查找（找最后一个正常版本）
- 前端路由匹配：前缀树（Trie）+ DFS 实现复杂路由规则匹配（如动态路由 `/user/:id/profile`）
- BFS 找最短路径：迷宫问题、社交网络中两人的最短关系链——BFS 保证第一次到达目标时走的是最短路径（无权图）

#### 二、设计与原理

- **二分搜索的本质**：每次把搜索范围缩小一半，O(log n)——关键在于**循环不变式**：每次循环后，答案一定在 `[left, right]` 区间内；`left <= right` 时继续搜索，退出时 `left > right`
- **二分的四种变体**（高频考点）：
  1. 找目标值（标准版）
  2. 找第一个 ≥ target 的位置（下界 lower_bound）
  3. 找最后一个 ≤ target 的位置（上界 upper_bound）
  4. 在旋转数组中查找（LeetCode 33）
- **BFS vs DFS 的选择**：BFS 找最短路径（第一次到达即最短）、层序遍历；DFS 探索所有可能路径、检测环、拓扑排序、回溯——DFS 代码通常更简洁（递归），BFS 需要显式队列
- **双指针**：两个指针在数组/链表上相向或同向移动，O(n) 解决 O(n²) 的暴力问题——前提是数组有序或有某种单调性
- **滑动窗口**：在字符串/数组上维护一个可变大小的窗口，用于求"满足条件的最短/最长子串"——右指针扩张窗口，条件满足后左指针收缩

#### 三、工程落地参考

- React Fiber 的 DFS 工作循环：`packages/react-reconciler/src/ReactFiberWorkLoop.js` 中 `workLoopSync`——React 的 reconcile 过程是对 Fiber 树的 DFS，通过 `performUnitOfWork` 递推，`completeUnitOfWork` 回溯，是 DFS 迭代（非递归）实现的真实案例

#### 四、实践演示与验证

手写四种二分变体并用单元测试覆盖边界（空数组、全相同元素、目标不存在）；实现"最小覆盖子串"（LeetCode 76）的滑动窗口解法，理解左右指针的收缩时机。

### 第 12 篇：递归：递归三要素/尾递归/记忆化到 DP 的跨越

**副标题**：从递归到迭代的思维转换，以及为什么 JS 里不用指望尾递归优化

#### 一、使用与实践

- 树遍历的自然递归：React 组件的递归渲染、DOM 树的递归克隆——递归代码与树的结构完美对应，可读性极高
- 文件系统遍历：递归扫描目录（`fs.readdirSync` + 递归）是文件处理脚本的标配
- 斐波那契/动态规划的递归形式：从"自顶向下递归 + 备忘录"到"自底向上 DP 表"的演化过程，是理解动态规划的最佳路径

#### 二、设计与原理

- 递归三要素：① **基本情况**（base case，终止条件，防止无限递归）② **递推关系**（把大问题拆解为同类小问题）③ **信任递归**（假设子问题已经正确解决，直接用结果）——"信任递归"是很多人写不好递归的根因，总想在脑子里追踪调用栈
- 递归的代价：每次调用都 push 一个栈帧，深度过大导致栈溢出——JS 引擎的调用栈一般在 10000~15000 层左右（浏览器和 Node.js 略有差别）
- **尾递归优化（TCO）**：如果递归调用是函数的最后一个操作，理论上可以复用当前栈帧——ES6 规范要求支持 TCO，但 V8 出于调试体验原因一直未实现（截至 2026 年仍未支持），Safari/JavaScriptCore 实现了但需要严格模式
- **记忆化（Memoization）**：用 `Map` 缓存已计算的子问题结果，把指数级的朴素递归降为 O(n)——这是自顶向下动态规划的本质，与自底向上的 DP 表等价但写法更直觉

#### 三、工程落地参考

- V8 中调用栈深度的实测：通过递归计数可以测出当前 Node.js 版本的最大调用栈深度（通常约 10000-15000，取决于每帧大小）——这是面试中"递归为什么有风险"的定量依据
- V8 对 TCO 的态度：V8 团队 issue #4698 中明确说明拒绝实现 TCO 的原因（调试栈帧丢失，难以定位错误位置），这个工程决策与语言规范的分歧是理解 JS 运行时设计的好案例

#### 四、实践演示与验证

实现斐波那契的三种版本：① 朴素递归（指数级）② 记忆化递归（O(n)）③ 迭代 DP（O(n)，O(1) 空间）；对比三者在 n=40 时的耗时；再把一个递归树遍历改写为显式栈迭代版本，理解"所有递归都可以用栈改写"。

LeetCode 重点题：509（斐波那契数）/ 70（爬楼梯）/ 104（二叉树最大深度）/ 226（翻转二叉树）

#### 五、参考

- SICP（《计算机程序的构造和解释》）第1章递归
- V8 TCO issue：https://bugs.chromium.org/p/v8/issues/detail?id=4698

### 第 13 篇：动态规划：状态转移方程建模/编辑距离/背包问题

**副标题**：从"暴力 → 记忆化 → DP 表 → 空间优化"的四步推导，拆解动态规划建模思路

#### 一、使用与实践

- 编辑距离：医疗 NLP 中药品名称纠错（"阿莫西林" vs "阿莫西琳"，编辑距离为 1）——Myers diff 算法（Git diff 的基础）本质是编辑距离的 DP 变体
- 路由/资源分配：在有限带宽预算下分配 CDN 资源——0-1 背包问题的变体
- 前端构建优化：代码分割（code splitting）的最优策略是一个 DP 问题——如何分包使得总加载时间最短
- 文本编辑器：光标移动路径的最优化、自动补全的相似度排序

#### 二、设计与原理

- **适用 DP 的两个必要条件**：① **最优子结构**：大问题的最优解包含子问题的最优解 ② **无后效性**：已经确定的子问题答案不会被后续决策改变——这两个条件同时满足才能用 DP
- **四步推导法**：
  1. **暴力递归**：先写出朴素递归，确认递推关系
  2. **记忆化**：加 `Map` 缓存消除重复计算
  3. **DP 表**（自底向上）：把记忆化翻译为循环，消除递归栈开销
  4. **空间优化**：观察 DP 表的转移只依赖相邻行/列，用滚动数组把 O(n²) 空间降为 O(n)
- **经典 DP 模型**：
  - **线性 DP**：最长递增子序列（LIS）、最长公共子序列（LCS）
  - **区间 DP**：矩阵链乘、最优括号化
  - **背包 DP**：0-1 背包（每件物品选或不选）、完全背包（每件物品可选多次）
  - **状态机 DP**：买卖股票系列（持有/不持有状态转移）

#### 三、工程落地参考

- Myers diff 与编辑距离：Git 使用 Myers 差分算法计算两个文件的 diff——Myers 算法本质是在编辑图上找最短路径，与编辑距离 DP 的关系：Myers 找最少操作数，经典 DP 找最少操作数并能还原操作序列，两者目标一致但路径不同
- snabbdom（Vue 虚拟 DOM 库）的 diff：`src/init.ts` 中 `updateChildren` 函数——snabbdom 的双端 diff 是线性 DP 的工程近似，用贪心策略在 O(n) 时间内找到"足够好"（不一定最优）的 patch 序列

#### 四、实践演示与验证

实现"编辑距离"（LeetCode 72）的四个版本（暴力 → 记忆化 → DP 表 → 滚动数组），记录每个版本的空间/时间消耗，可视化 DP 表的填充过程；再实现 0-1 背包问题，理解"为什么遍历顺序必须从大到小"。

LeetCode 重点题：70（爬楼梯）/ 62（不同路径）/ 300（最长递增子序列）/ 1143（最长公共子序列）/ 72（编辑距离）/ 322（零钱兑换）/ 518（零钱兑换 II，完全背包）

#### 五、参考

- 《算法导论》第15章动态规划（CLRS 著）
- labuladong DP 框架：https://labuladong.online/algo/dynamic-programming/
