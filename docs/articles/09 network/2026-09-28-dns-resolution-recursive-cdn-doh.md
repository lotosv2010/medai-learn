## 一、使用与实践

### 1. DNS 是什么、在网络分层里的位置

DNS（Domain Name System，域名系统）的本质是一张**全球分布式、分层级的「电话簿」**：人记不住 `142.250.72.14` 这样的 IP 地址，但能记住 `google.com`，所以需要一套机制把「域名」翻译成「IP 地址」。

它之所以叫「系统」而不是「服务」，是因为它不是一个单点服务，而是由全球成千上万台服务器共同组成的一个**树状分层结构**：

```
                          ┌─────────────┐
                          │  根域名服务器  │  （全球 13 组，用 a~m.root-servers.net 命名）
                          └──────┬──────┘
                ┌────────────────┼────────────────┐
           ┌────┴────┐      ┌────┴────┐      ┌────┴────┐
           │  .com   │      │  .org   │      │  .cn    │   （顶级域 TLD 服务器）
           └────┬────┘      └────┬────┘      └────┬────┘
        ┌───────┴───────┐         │               │
   ┌────┴────┐     ┌────┴────┐    │               │
   │example.com│   │ google.com│  ...            ...    （权威域名服务器）
   │ 权威服务器  │   │ 权威服务器  │
   └─────────┘     └─────────┘
```

这个分层结构是理解后面「递归 vs 迭代」的地基：**每一层只知道「下一层该找谁」，而不是知道全世界的所有域名**。根服务器知道所有顶级域（`.com`/`.org`/`.cn`…）的服务器地址；顶级域服务器知道它管辖下所有二级域名的权威服务器地址；权威服务器才知道某个具体域名的最终 IP。

**DNS 跑在哪个协议上**？绝大多数 DNS 查询走 **UDP 53 端口**，无连接、一次往返。为什么不用 TCP？因为单条 DNS 查询报文很小（通常几十到几百字节），一次往返就能完成，用 TCP 的三次握手开销不划算。只有当响应超过 512 字节（如大量记录、或启用 DNSSEC 时）或做区域传送（AXFR）时，才会回退到 TCP 53。这个「UDP 优先、TCP 兜底」的设计，正是第 02 篇「UDP vs TCP」对比的绝佳引子。

### 2. 认识 DNS 记录类型（看懂 dig 输出前的必备）

在看 `dig` 输出之前，必须先认识几种最常见的 DNS 记录类型——它们是 `dig` 结果里 `ANSWER SECTION` 那一行的「类型」字段。**查询一个域名时，不同类型的记录走的是同一条查询链路，只是权威服务器返回的记录内容不同**：

| 记录类型 | 含义 | 一句话用途 | 典型例子 |
|---------|------|-----------|---------|
| `A` | 域名 → IPv4 地址 | 把域名指向一个 IPv4 | `drug.example.com → 93.184.216.34` |
| `AAAA` | 域名 → IPv6 地址 | 把域名指向一个 IPv6（「四倍 A」） | `drug.example.com → 2606:2800:220:1::1` |
| `CNAME` | 域名 → 另一个域名（别名） | 别名指向，常用于 CDN 回源、子域名接第三方 | `www.drug.com → drug.cdn.example.net` |
| `NS` | 该域名的权威 DNS 服务器是谁 | 把子域名的解析权委派给某台服务器 | `drug.com → ns1.dnsprovider.com` |
| `MX` | 该域名的邮件服务器 | 指定收邮件走哪台服务器 | `drug.com → mail.drug.com` |

这里最关键、也最容易被问的是 **`CNAME`**：它不直接给出 IP，而是告诉你「这个域名其实是另一个域名的别名，继续去查那个域名」。为什么需要它？一个典型场景是**接入 CDN 或第三方服务**——你要把自己的域名 `www.drug.com` 交给云厂商的 CDN，但 CDN 的边缘节点 IP 是厂商的、会动态变化，你不可能自己去维护那堆 IP，于是配一条 `CNAME` 把 `www.drug.com` 指向 `drug.cdn.vendor.com`，之后 IP 变化由厂商在它自己的域名下维护，你完全不用管。

> 💬 **面试官**：`A` 记录和 `CNAME` 记录有什么区别？
>
> ✅ 标准答案：`A` 记录把域名直接映射到 IPv4 地址（`AAAA` 映射到 IPv6）；`CNAME` 把域名映射到**另一个域名**（别名），不直接给 IP，查 `CNAME` 后还要继续解析目标域名才能拿到最终 IP。`CNAME` 常用于 CDN 回源、子域名接入第三方服务——因为目标 IP 会动态变化，用别名可以让服务商在自己的域名下维护 IP。
>
> 🎁 加分答案：能补充 `CNAME` 的两个约束——① `CNAME` 不能和同名的其他记录（如 `MX`）共存（一个域名有了 `CNAME` 就不能再有 `A`/`MX` 等），所以**根域（apex domain，如 `drug.com` 本身）不能配 `CNAME`**，只能配 `A` 记录或使用 `ANAME`/`ALIAS` 这类厂商扩展；② `NS` 是「委派」记录，`CNAME` 是「别名」记录，两者语义完全不同。

### 3. `nslookup` / `dig` 查解析结果与耗时

`dig`（Domain Information Groper）是排查 DNS 的首选工具，比 `nslookup` 输出更详细、更接近原始报文。Windows 自带 `nslookup`，`dig` 需要装 BIND（或使用 WSL/云主机）。

先看最基本的查询：

```bash
# 查询 drug.example.com 的 A 记录（IPv4 地址）
dig drug.example.com
```

输出（关键部分）：

```text
;; QUESTION SECTION:
;drug.example.com.               IN      A

;; ANSWER SECTION:
drug.example.com.        300     IN      A       93.184.216.34

;; Query time: 23 msec
;; SERVER: 10.0.0.2#53(10.0.0.2)
```

三个关键信息要会看：

- **`ANSWER SECTION`**：真正的解析结果。`300` 是这条记录的 **TTL**（存活时间，秒），`A` 是记录类型，`93.184.216.34` 是最终 IP
- **`Query time`**：本次查询耗时（毫秒），排查「解析慢」时直接看这里
- **`SERVER`**：实际响应这次查询的本地 DNS 服务器（这里是 `10.0.0.2`，通常是你家路由器或 ISP 的）

如果只想快速拿到结果，用 `+short`：

```bash
dig drug.example.com +short
# 输出只有一个 IP：93.184.216.34
```

`nslookup` 的等价命令是 `nslookup drug.example.com`，输出更简洁，但排查复杂问题时信息不如 `dig` 全。

### 4. `dig +trace example.com` 从根域名服务器开始的完整链路

`+trace` 是理解「DNS 到底递归了几步」最有价值的参数——它让 `dig` 不借助本地 DNS 服务器的缓存，而是**自己从根域名服务器开始，模拟「迭代查询」逐级往下问**：

```bash
dig +trace drug.example.com
```

输出会分多段，每段就是「向下问一层」。这是理解后面「递归 vs 迭代」的直观素材（这里先看个全貌，第二部分拆解每一跳的含义）：

```text
# 第 1 跳：从根服务器开始，根告诉你「.com 顶级域的服务器是谁」
.                       518400  IN      NS      a.root-servers.net.
...
com.                    172800  IN      NS      a.gtld-servers.net.
a.gtld-servers.net.     172800  IN      A       192.5.6.30

# 第 2 跳：问 .com 顶级域服务器，它告诉你「example.com 的权威服务器是谁」
example.com.            172800  IN      NS      a.iana-servers.net.
a.iana-servers.net.     172800  IN      A       199.43.135.53

# 第 3 跳：问 example.com 的权威服务器，它才给你最终 IP
drug.example.com.       300     IN      A       93.184.216.34
```

注意每一跳**返回的内容不一样**：根和顶级域返回的是「下一级服务器是谁」（`NS` 记录 + 那个服务器的 `A` 记录），只有最后的权威服务器返回「最终 IP」。这个「每一跳只给下一级地址、不直接给最终答案」的模式，就是**迭代查询**——第二部分会重点展开。

### 5. 三级本地缓存与 `ipconfig /flushdns`

DNS 解析之所以「平时感觉不到延迟」，是因为它有一层层的缓存。在真正发起网络查询之前，会先命中三级本地缓存：

| 层级 | 缓存位置 | 说明 |
|------|---------|------|
| ① 浏览器缓存 | Chrome/Firefox 进程内 | 最近访问过的域名，命中即直接用，不发出系统调用 |
| ② 操作系统缓存 | OS 的 DNS resolver 缓存 | 浏览器没命中才查这里（Windows 由 DNS Client 服务维护） |
| ③ 本地 DNS 服务器缓存 | 路由器/ISP/公共 DNS | OS 没命中才发网络请求到本地 DNS，它也有自己的缓存 |

**只有这三级缓存都没命中，才会触发真正的网络查询**。所以「改了解析记录为什么没立刻生效」，第一反应就该想到：可能还卡在这三级缓存的某一级里。

Windows 上清空操作系统这一级缓存的命令：

```bash
ipconfig /flushdns          # 清空 Windows 的 DNS Client 缓存
ipconfig /displaydns        # 查看当前缓存的解析记录
```

> 💬 **面试官**：浏览器访问一个域名，DNS 查询会先查哪几层缓存？
>
> ✅ 标准答案：先查浏览器缓存 → 未命中查操作系统缓存 → 未命中查本地 DNS 服务器（路由器/ISP）缓存 → 都未命中才发起真正的网络递归查询。
>
> 🎁 加分答案：能落到「改了记录为什么不生效」的排查——先确认 TTL 没到期、再清浏览器/OS 缓存（`ipconfig /flushdns`）、再看本地 DNS 服务器是否还持有旧缓存，逐级定位卡在哪一层。

### 6. 开启 DoH 观察变化

DoH（DNS-over-HTTPS）把 DNS 查询封装进 HTTPS，后面第二、四部分会讲原理和验证。这里先知道怎么开：

- **Chrome**：设置 → 隐私和安全 → 安全 → 使用安全 DNS → 开启并选择服务商（默认用系统，可选 Cloudflare/Google 或自定义）
- **Firefox**：设置 → 隐私与安全 → 底部的「基于 HTTPS 的 DNS」→ 开启

开启后，DNS 查询不再走明文 UDP 53，而是变成对 `https://dns.google/dns-query` 这类端点的 HTTPS 请求——在 Wireshark 里就看不到 `udp.port == 53` 的明文报文了，这正是第四部分的验证点。

## 二、设计与原理

这是本篇的核心。下面六个小节按「先讲完整链路 → 再拆递归与迭代的区别 → 缓存 → CDN → 安全 → Node.js 对比」的顺序，由浅入深讲透。

### 1. DNS 解析的完整链路

从浏览器输入 `drug.example.com` 到拿到 IP，完整的解析链路是这样一条**自下而上再自上而下**的路径：

```
浏览器缓存 ──▶ 操作系统缓存 ──▶ 本地 DNS 服务器 ──▶ 根域名服务器
                                                       │
                                              （返回 .com 服务器地址）
                                                       ▼
                                                  .com 顶级域服务器
                                                       │
                                              （返回 example.com 权威服务器地址）
                                                       ▼
                                                 example.com 权威服务器
                                                       │
                                              （返回最终 IP 93.184.216.34）
                                                       ▼
                                                 本地 DNS 服务器 ──▶ 客户端
```

关键要理解的是**「客户端只发一次请求」**这个事实：

- 客户端（浏览器）对操作系统/本地 DNS 服务器发起的是**一次**查询，然后**等待最终结果**——它自己不会去问根、问顶级域、问权威
- 后续「问根 → 问顶级域 → 问权威」这一整条链路，是**本地 DNS 服务器代替客户端**完成的

这个过程叫**递归查询（recursive query）**：客户端只发一次请求，本地 DNS 服务器代替客户端完成后续所有查询，最后把最终结果一次性返回给客户端。这个「代劳」的分工，是整个 DNS 体系最核心的设计——下一小节把它和「迭代查询」的边界讲清楚。

### 2. 递归查询 vs 迭代查询（重点 · 面试必考）

这是全篇最核心、也最容易被问倒的一个点。它的本质是一句话：**「递归」和「迭代」描述的是两段不同的查询关系，而不是两个不同的协议**。

先给定义，再对照 `dig +trace` 落地：

**递归查询（Recursive）**：客户端 → 本地 DNS 服务器。客户端发出一次请求，要求本地 DNS 服务器「无论你问多少人，最后把最终结果告诉我」，自己坐等结果。查询报文里会把 **RD（Recursion Desired）标志位置 1**。

**迭代查询（Iterative）**：本地 DNS 服务器 → 根/顶级域/权威服务器。本地 DNS 服务器对上层服务器发起的是迭代查询，**每次只拿到「下一级服务器是谁」**（一条 `NS` 记录 + 它的 IP），然后自己拿着这个地址**继续往下问**，像剥洋葱一样一层层问下去，直到权威服务器给出最终 IP。

一张图看懂两者分工：

```
客户端（你的浏览器）                   本地 DNS 服务器                根 / 顶级域 / 权威
        │                                  │                              │
        │ ──① 递归查询（RD=1）──▶           │                              │
        │   「把 drug.example.com 解析出来」  │                              │
        │                                  │ ──② 迭代查询──▶ 根服务器       │
        │                                  │ ◀── 「.com 的 NS 是 a.gtld」── │
        │                                  │ ──③ 迭代查询──▶ .com 服务器    │
        │                                  │ ◀── 「example.com 的 NS 是 a.iana」│
        │                                  │ ──④ 迭代查询──▶ 权威服务器     │
        │                                  │ ◀── 「最终 IP 是 93.184.216.34」│
        │ ◀──⑤ 递归结果（最终 IP）──────     │                              │
```

对应回上一节的 `dig +trace` 输出：**`dig +trace` 展示的正是②③④这三段「迭代查询」**——`dig` 自己扮演「本地 DNS 服务器」的角色，从根开始逐级问，每一跳返回的要么是「下一级服务器地址」（根、顶级域），要么是「最终 IP」（权威）。而你在终端里执行 `dig` 对本地 DNS 服务器发起的，才是①这段递归查询。

> 💬 **面试官**：DNS 递归查询和迭代查询的区别是什么？递归到底发生在哪一步？
>
> ✅ 标准答案：递归查询是「客户端 → 本地 DNS 服务器」这一段——客户端只发一次请求、等最终结果，本地 DNS 服务器代替它完成后续所有查询；迭代查询是「本地 DNS 服务器 → 根/顶级域/权威」这一段——每次只拿到下一级服务器地址，自己逐级往下问。所以「递归」发生在客户端和本地 DNS 服务器之间，「迭代」发生在本地 DNS 服务器和上层服务器之间。
>
> 🎁 加分答案：能点出报文层的关键标志——客户端发的递归查询报文里 **RD（Recursion Desired）位 = 1**，请求对方「帮我递归到底」；本地 DNS 服务器对上层发的是 RD=0 的迭代查询，只要「下一级地址」。再加一句 `dig +trace` 展示的正是那段迭代链路，能把它每一跳返回的内容（NS 地址 vs 最终 IP）讲清楚，说明你真的跑过、不只是背过。

### 3. TTL 与缓存层级

TTL（Time To Live，存活时间）是 DNS 记录上的一个「有效期」字段，单位秒。上面 `dig` 输出里 `300` 就是 TTL——它告诉各级缓存：「这条记录最多缓存 300 秒，过期后必须重新查询」。

**TTL 是整个 DNS 缓存体系的「计时器」**。上一节讲的三级本地缓存（浏览器/OS/本地 DNS 服务器），每一级都按 TTL 决定「缓存多久后失效重新查询」。为什么是「各级各自计时」？因为一次解析结果会被逐级缓存下来：

- 权威服务器返回的记录带 TTL（如 300 秒）
- 本地 DNS 服务器缓存它，从这一刻开始倒计时 300 秒
- 操作系统缓存拿到结果后，也可能按自己的策略缓存（通常也参考 TTL）
- 浏览器缓存同理

**这就是「修改了域名解析记录，为什么全网生效需要一段时间」的直接原因**：你改了权威服务器上的记录，但各级缓存里还存着旧的记录，要等它们的 TTL 到期、重新查询后，新记录才会生效。TTL 越长，旧记录「赖着不走」的时间就越长。

生产上有个经典操作：**变更前先把 TTL 调短**（比如从 86400 秒调到 300 秒），等旧 TTL 过期、全网都缓存了「短 TTL 的新记录」，再执行真正的 IP 切换，切换后就能在几分钟内生效。反之，如果 TTL 一直是 24 小时，切换后要等一整天全网才能同步过来。

> 💬 **面试官**：修改了 DNS 记录，为什么生效有延迟？和什么参数有关？
>
> ✅ 标准答案：因为 DNS 有**多层缓存**（浏览器/操作系统/本地 DNS 服务器），各级缓存都会按记录的 **TTL** 决定缓存多久才失效重查。改了权威服务器上的记录后，各级缓存里还存着旧记录，要等它们各自的 TTL 到期、重新查询，新记录才逐步生效。延迟直接和 TTL 有关——TTL 越长，生效越慢。
>
> 🎁 加分答案：能补充生产实践——「先降 TTL 再切换」：变更前把 TTL 调到很短（如 300 秒），等旧长 TTL 过期后，全网缓存的是短 TTL 的新记录，此时再切换 IP 就能快速生效；切完、稳定后再把 TTL 调回正常值。以及排查思路：先确认 TTL 是否到期 → 逐级清缓存（浏览器/`ipconfig /flushdns`/本地 DNS）定位卡在哪一级。

### 4. CDN 如何利用 DNS 做就近调度

这一节把「DNS」和「CDN」连起来，是理解「为什么不同地区 `dig` 同一个 CDN 域名会得到不同 IP」的关键。

CDN 的核心诉求是：**让用户访问离他最近的边缘节点**。但 CDN 在全国/全球有成百上千个节点，怎么决定给「这个用户」返回哪个节点的 IP？答案正是 DNS——这就是 **GSLB（Global Server Load Balance，全局负载均衡）** 最常见的实现方式之一。

原理是这样：

1. 你的域名（如 `static.drug.com`）配了一条 `CNAME`，指向 CDN 服务商的调度域名（如 `drug.cdn.vendor.com`）
2. 用户查询 `static.drug.com` 时，最终会问到 CDN 服务商的**权威 DNS 服务器**
3. 这台权威 DNS 服务器**不是无脑返回一个固定 IP**，而是看「这次查询是从哪个**本地 DNS 服务器**转发来的」——本地 DNS 服务器的出口 IP 暴露了用户的大致地理位置和网络线路
4. CDN 权威 DNS 根据这个位置/线路，动态返回**离用户最近、线路最优**的边缘节点 IP

```text
北京用户 ──▶ 北京本地 DNS ──▶ CDN 权威 DNS ──▶ 返回「北京边缘节点 IP」
上海用户 ──▶ 上海本地 DNS ──▶ CDN 权威 DNS ──▶ 返回「上海边缘节点 IP」
                        ▲
            同一个域名，因「发起查询的本地 DNS 位置不同」得到不同 IP
```

**所以「就近调度」的本质是：CDN 的权威 DNS 根据「发起查询的本地 DNS 服务器的地理位置/网络线路」动态返回不同的边缘节点 IP**。这也是为什么用 `dig @8.8.8.8`（Google 公共 DNS，出口在美国/全球任播）和 `dig @1.1.1.1`（Cloudflare）查询同一个 CDN 域名，会得到**不同的 IP**——因为两者「替用户发起查询的位置」不同，CDN 判断的「最近节点」也不同（第四部分会实证）。

> 💬 **面试官**：CDN 是怎么利用 DNS 实现「就近调度」的？
>
> ✅ 标准答案：CDN 的权威 DNS 服务器会根据**发起查询的本地 DNS 服务器的地理位置/网络线路**，动态返回离用户最近的边缘节点 IP——而不是固定返回同一个 IP。这就是 GSLB（全局负载均衡）最常见的实现方式。域名先 `CNAME` 到 CDN 的调度域名，最终由 CDN 权威 DNS 按「查询来源」做就近解析。
>
> 🎁 加分答案：能补充两个关键细节——① CDN 判断用户位置依赖的是**本地 DNS 服务器的出口 IP**，而不是用户真实 IP，所以如果用户配置了异地公共 DNS（如用美国的 8.8.8.8 查询国内 CDN），会拿到「非最优」的节点，这解释了「为什么有的人改 DNS 后变卡了」；② 这也是 `dig` 对比 `@8.8.8.8` 和 `@1.1.1.1` 拿到不同 IP 的原因——两者「替用户查询的位置」不同。更进一步还能提到：纯 DNS 调度的粒度是「本地 DNS 出口 IP」，想按用户真实 IP 调度需要配合 **ECS（EDNS Client Subnet，把用户网段传给权威 DNS）** 或 HTTP 层面的调度（如 Anycast、HTTP 重定向）。

### 5. DNS 明文查询的隐私与安全

到这里，DNS 的功能性讲完了。但传统 DNS 有一个结构性缺陷：**它是明文 UDP 传输**。

这意味着什么？两条风险：

**① 窃听**：运营商或中间网络设备能看到你查询的**每一个域名**。你访问了哪些网站、用了哪些 App，在 DNS 层面对中间人完全透明——这是比 HTTP 明文更底层的隐私泄露，因为即使网站本身是 HTTPS 的，**DNS 查询发生在 HTTPS 建立之前**，仍然暴露了你「要去访问哪个域名」。

**② 篡改（DNS 污染 / DNS 劫持）**：明文查询不仅能看到，还能**改**。中间人可以在响应返回前篡改成错误的 IP——这就是「DNS 污染/劫持」：要么让你访问到错误的服务器（钓鱼），要么直接返回一个不存在的 IP 让域名「打不开」。你明明输入的域名是对的，却被引导到了别处。

**解法：DoH 和 DoT**。两者思路一致——把 DNS 查询**加密**，让中间人既看不到、也改不了：

| 方案 | 全称 | 传输 | 端口 | 特点 |
|------|------|------|------|------|
| **DoH** | DNS over HTTPS | 封装进 HTTPS | 443 | 伪装成普通 HTTPS 流量，难以被识别/阻断 |
| **DoT** | DNS over TLS | 独立 TLS 连接 | 853 | 专用端口，简单直接，但端口可被识别阻断 |

DoH（RFC 8484）把 DNS 查询封装进 HTTP 的 GET/POST 请求，`Content-Type` 是 `application/dns-message`，请求发到 `https://dns.google/dns-query` 这类端点。因为走 443 端口、和普通 HTTPS 完全一样，**在流量上难以区分「这是 DNS 查询还是普通网页请求」**，所以更难被中间人针对性拦截。

但加密不是没有代价，两点权衡：

- **额外连接开销**：明文 UDP 一次往返就搞定；DoH/DoT 要先建 TLS/HTTPS 连接（多几次握手往返），单次查询延迟略增（但配合 keep-alive 复用连接后差异不大）
- **隐私集中化**：普通 DNS 查询分散在全球成千上万的 DNS 服务器，而 DoH 把查询集中交给少数几个大型服务商（Cloudflare 的 1.1.1.1、Google 的 8.8.8.8）——**你躲开了运营商的窥探，却把「访问了哪些域名」这个信息集中交给了这几家大厂**，这是 DoH 引入的新争议点

> 💬 **面试官**：DNS 明文查询有什么安全隐患？DoH/DoT 是怎么解决的？
>
> ✅ 标准答案：传统 DNS 是明文 UDP 传输，中间人既能**窃听**（看到你访问的每个域名，泄露隐私）也能**篡改**（DNS 污染/劫持，把域名解析到错误 IP）。DoH（DNS over HTTPS，封装进 443 的 HTTPS）和 DoT（DNS over TLS，走 853 的独立 TLS 连接）把 DNS 查询加密，防止窃听和篡改。
>
> 🎁 加分答案：能补充权衡——① DoH 伪装成普通 HTTPS 流量，更难被识别/阻断，而 DoT 用专用 853 端口、可被识别；② 加密的代价是引入 TLS 连接建立开销（靠连接复用缓解），以及「隐私集中化」新争议（把域名查询信息集中交给 Cloudflare/Google 少数几家大厂）。还能点出：DoH/DoT 解决的是「传输过程」的窃听篡改，**并不能解决「权威 DNS 服务器知道你查了什么」本身**，彻底隐私要靠 DNSSEC/匿名化 DNS 等更进一步的方案。

### 6. 对比 Node.js 实现：`dns.lookup` vs `dns.resolve`

最后落地到 Node.js，这是网络原理和 Node.js 系列的交汇点，也是「同一个域名在 Node.js 里用不同 API 解析结果不一致」这类诡异问题的根源。

Node.js 的 `dns` 模块有两组 API，走的是**两条完全不同的代码路径**：

| API | 底层实现 | 是否查 hosts/系统缓存 | 行为 |
|-----|---------|---------------------|------|
| `dns.lookup()` | 走 **libuv 的 `getaddrinfo`**（操作系统解析器） | **会**查 hosts 文件 + 系统缓存 | 和浏览器/`ping` 走同一条系统解析路径 |
| `dns.resolve()` | 走 **`c-ares` 库**直接发起网络查询 | **不会**查 hosts 文件 | 直接对 DNS 服务器发起 DNS 查询，绕开系统 |

```javascript
const dns = require('dns');

// 方式一：dns.lookup —— 走操作系统解析器（查 hosts + 系统缓存）
dns.lookup('drug.example.com', (err, address, family) => {
  console.log('lookup 结果:', address, family); // 93.184.216.34 4
});

// 方式二：dns.resolve —— 走 c-ares 直接发起网络 DNS 查询（不查 hosts）
dns.resolve4('drug.example.com', (err, addresses) => {
  console.log('resolve 结果:', addresses);       // ['93.184.216.34']
});
```

**为什么结果会不一致？** 关键就在 `lookup` 会查 `hosts` 文件、`resolve` 不查。举个例子：你在本机 `/etc/hosts`（或 Windows 的 `C:\Windows\System32\drivers\etc\hosts`）里把 `drug.example.com` 手动指向了 `127.0.0.1` 做本地调试：

- `dns.lookup('drug.example.com')` → 返回 `127.0.0.1`（命中了 hosts）
- `dns.resolve4('drug.example.com')` → 返回真实的公网 IP（绕过了 hosts，直接问 DNS）

**同一个域名、同一个进程、两个 API，结果不一样**——这就是「诡异问题」的根源。所以使用时要分清语义：`lookup` 适合「我就想得到浏览器/系统会怎么解析这个域名」（系统视角），`resolve` 适合「我要直接问 DNS 服务器拿权威记录」（DNS 视角）。这组区分，正是 Node.js 系列「核心 API 大全」篇 `dns` 小节要重点展开的内容，本篇只讲清「为什么会有两条路径」。

> 💬 **面试官**：Node.js 的 `dns.lookup` 和 `dns.resolve` 有什么区别？
>
> ✅ 标准答案：`dns.lookup()` 走操作系统的解析器（libuv 的 `getaddrinfo`），会用到本地 hosts 文件和系统缓存；`dns.resolve()` 走 `c-ares` 库直接发起网络 DNS 查询，不查 hosts 文件。所以「改了 hosts 文件」只影响 `lookup`，不影响 `resolve`，这就是「同一个域名两个 API 结果不一致」的根源。
>
> 🎁 加分答案：能落到语义选择——`lookup` 是「系统视角」（浏览器/`ping` 走同一条路径，得到的就是系统会用的结果）；`resolve` 是「DNS 视角」（直接问权威/递归服务器，适合需要真实 DNS 记录、绕过 hosts 的场景）。再加一个细节：`lookup` 的回调签名是 `(err, address, family)`（单个结果 + 地址族），`resolve4` 是 `(err, addresses)`（地址数组），且 `lookup` 走线程池（getaddrinfo 是阻塞系统调用，被丢到 libuv 线程池避免阻塞事件循环），而 `resolve` 是异步的、不占线程池。

## 三、工程落地参考

原理讲完，落到「工程落地」时看哪些权威资料。本节列出三个核心参考，指明「去哪看、看什么」：

### 1. DNS 报文格式与递归流程（RFC 1035）

RFC 1035 是 DNS 协议的奠基规范，定义了 DNS 报文的二进制结构。一个 DNS 报文由这几部分组成：

| 报文段 | 作用 | 关键字段 |
|--------|------|---------|
| **Header**（固定 12 字节） | 标识与标志位 | `ID`（匹配请求/响应）、`QR`（是查询还是响应）、`RD`（递归期望位）、`RA`（递归可用位）、`RCODE`（响应状态码，0 表示无错误） |
| **Question** | 查询内容 | `QNAME`（要查的域名）、`QTYPE`（记录类型 A/AAAA/CNAME/NS…）、`QCLASS`（通常 IN=Internet） |
| **Answer** | 回答记录 | 查询结果，含 TTL + 记录数据 |
| **Authority** | 权威信息 | 迭代查询时返回的 `NS` 记录（「下一级服务器是谁」） |
| **Additional** | 附加信息 | 权威服务器的 `A` 记录（顺手把下一级服务器的 IP 也给你，省一次查询） |

这里有个巧妙的设计值得注意：**迭代查询时，`Authority` 段放「下一级的 NS 记录」、`Additional` 段顺手放「那个 NS 服务器的 A 记录」**——这样本地 DNS 服务器拿到「下一级是谁」的同时，也拿到了「下一级的 IP」，不用再单独查一次，这就是 `dig +trace` 里 `NS` 记录和 `A` 记录成对出现的原因。

### 2. DoH 规范（RFC 8484）

RFC 8484 定义了 DNS 查询如何封装进 HTTP。核心要点：

- **GET 方式**：把 DNS 查询报文 base64url 编码后放进 URL 查询参数 `?dns=<base64>`，适合小查询、可被缓存
- **POST 方式**：把原始 DNS 报文作为请求体，`Content-Type: application/dns-message`，适合大查询
- 响应同样以 `application/dns-message` 返回二进制 DNS 报文
- 端点示例：`https://dns.google/dns-query`、`https://cloudflare-dns.com/dns-query`

### 3. Node.js `dns` 模块（`lib/dns.js`）

Node.js 源码里 `lib/dns.js` 能清晰看到两条路径的分流：

- `dns.lookup` → 内部调用 libuv 的 `getaddrinfo`，这是操作系统提供的解析接口，走系统解析器（hosts + 系统缓存），因为是阻塞调用、被丢进 libuv 线程池
- `dns.resolve` → 内部走 `c-ares`（一个 C 写的异步 DNS 解析库），直接构造 DNS 查询报文、用 UDP 发给配置的 DNS 服务器，**不经过操作系统的 hosts/缓存**

> 引用规范：正文不出现具体人名/账号名，权威来源见文末参考资料。对应本节的三个规范——DNS 报文结构（RFC 1035）、DoH 封装（RFC 8484）、Node.js `dns` 模块源码，搜索关键词见文末。

## 四、实践演示与验证

原理讲透了，最后动手「把 DNS 看进眼里」。用四个实验把前面每个抽象概念落到可观测的现象上。

### 1. `dig +trace` 逐跳追踪，看「递归 vs 迭代」的分工

```bash
dig +trace drug.example.com
```

重点观察每一跳 `ANSWER`/`AUTHORITY` 段返回的是「下一级服务器地址」还是「最终 IP」：

- 根、顶级域两跳：返回 `NS` 记录（下一级是谁），是**迭代查询**的证据
- 权威一跳：返回 `A` 记录（最终 IP），递归链路在这里收口

这一跳一跳看下来，「递归发生在客户端↔本地 DNS、迭代发生在本地 DNS↔上层」的分工就不再是背的，而是看到的。

### 2. `dig @8.8.8.8` vs `dig @1.1.1.1` 对比同一 CDN 域名的不同 IP

```bash
# 用两个不同的公共 DNS 查询同一个 CDN 域名，观察 IP 是否不同
dig @8.8.8.8 static.drug.com A +short
dig @1.1.1.1 static.drug.com A +short
```

因为两台公共 DNS 服务器「替用户发起查询的出口位置」不同，CDN 权威 DNS 判断的「最近边缘节点」也不同，返回的 IP 往往不一样——**这就是「就近调度」最直观的证据**。

### 3. `dig +https` 验证加密查询

较新版本的 `dig`（≥ 9.18）支持 `+https` 参数直接走 DoH：

```bash
dig +https drug.example.com
```

对比普通 `dig`（走 UDP 53 明文）和 `dig +https`（走 HTTPS 443 加密），在 Wireshark 里前者能看到明文域名、后者只有加密流量，隐私差异一目了然。

### 4. Wireshark 抓真实 DNS 报文，逐字段对照 RFC 1035

```bash
# Wireshark 过滤表达式：只抓 DNS 流量
udp.port == 53
```

抓一次真实查询（比如访问任意网站），展开 DNS 报文，逐字段对照第三节的报文结构：

- **Header** 里的 `ID`、`QR`、`RD`、`RCODE` 字段
- **Question** 里的 `QNAME`（域名）、`QTYPE`（A）
- **Answer** 里的 TTL、`A` 记录、最终 IP

抓完这一包，你会直观理解那句话：**DNS 本质是跑在 UDP 之上的一个简单二进制协议**——几十个字节的报文，字段结构完全由 RFC 1035 规定，没有任何「魔法」。

| DoH/DoT | 明文 UDP 可窃听篡改；DoH 走 443、DoT 走 853 加密，代价是连接开销 + 隐私集中化 | ⭐⭐⭐ 必考 |
| `lookup` vs `resolve` | `lookup` 走系统解析器（查 hosts）；`resolve` 走 c-ares 直接问 DNS（不查 hosts） | ⭐⭐ 高频 |

> 💡 记住这条主线：**DNS 是一张「分层电话簿」，客户端只发一次递归请求，本地 DNS 服务器用「迭代」逐级向下问到最终 IP；TTL 让结果能被各级缓存一段时间，而「按本地 DNS 位置返回不同 IP」正是 CDN 就近调度的原理；因为查询是明文 UDP，才有了 DoH/DoT 的加密演进**。把这条线串起来，DNS 的所有面试题都能从原理推到答案。

## 💡 面试核心问

- **DNS 递归查询的完整链路是怎样的？递归查询和迭代查询的区别是什么？**（浏览器缓存→OS 缓存→本地 DNS→根→顶级域→权威→IP；客户端↔本地 DNS 是递归、本地 DNS↔上层是迭代）
- **修改了 DNS 记录，为什么生效有延迟？和什么参数有关？**（多层缓存按 TTL 决定失效重查；TTL 越长生效越慢，生产上「先降 TTL 再切换」）
- **CDN 是怎么利用 DNS 实现「就近调度」的？**（CDN 权威 DNS 按发起查询的本地 DNS 地理位置/线路动态返回最近边缘节点 IP，即 GSLB）
- **DNS 明文查询有什么安全隐患？DoH/DoT 是怎么解决的？**（明文 UDP 可窃听/篡改（污染劫持）；DoH 走 HTTPS 443、DoT 走 TLS 853 加密，代价是连接开销 + 隐私集中化）
- **Node.js 的 `dns.lookup` 和 `dns.resolve` 有什么区别？**（`lookup` 走系统解析器查 hosts + 系统缓存，`resolve` 走 c-ares 直接问 DNS 不查 hosts，是「结果不一致」的根源）
