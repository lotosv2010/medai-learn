# TCP 深度：三次握手四次挥手/拥塞控制四阶段/滑动窗口流量控制（面试收藏级）

> **副标题**：连接建立与断开的状态机、拥塞控制如何应对网络拥塞、滑动窗口如何做流量控制

> 面试官问「TCP 为什么要三次握手、四次挥手？」——十个人有九个能背出 SYN → SYN+ACK → ACK 的流程。但继续追问「一个 TCP 报文段从你的浏览器出发，穿过哪几层、每层加了什么头、沿途交换机和路由器分别在哪一层工作、到了对端为什么还能原样还原」，能答全的不到两成。

> 这篇文章不只要让你「会背三次握手」，更要让你**看懂一个 TCP 报文段的完整旅程**——它怎么从应用层的数据一路封装成比特流发出去，又怎么在对端一层层拆回来。理解了这条旅程，TCP 的序列号、确认号、滑动窗口、拥塞窗口这些字段「在哪一层起作用」才真正立得住。

## 一、使用与实践

动手之前，先建立全局坐标系，把工具和代码跑起来。

### 1. 网络分层的坐标系：OSI 七层 vs TCP/IP 四层/五层

任何一本网络教材第一章都是「分层模型」，但大多数人把它当八股背完就扔。这里请你带着一个具体的问题去看分层：**你浏览器里发出的一段数据，是怎么变成电信号传出去的？**

分层的本质是「**分工带来效能**」——把「两台计算机之间传输数据」这件极其复杂的事，拆成几个功能相对单一的子任务，每个子任务只负责一件事。这样整个流程更清晰，出了问题也更容易定位到具体某一层：

- **应用层（Application）**：提供网络与用户应用软件之间的接口服务（HTTP）
- **表示层（Presentation）**：提供格式化的表示和转换数据服务，如加密和压缩
- **会话层（Session）**：提供包括访问验证和会话管理在内的建立和维护应用之间通信的机制
- **传输层（Transmission）**：提供建立、维护和取消传输连接功能，负责可靠地传输数据（TCP）
- **网络层（Network）**：处理网络间路由，确保数据及时传送（路由器）
- **数据链路层（DataLink）**：负责无错传输数据，确认帧、发错重传等（交换机）
- **物理层（Physics）**：提供机械、电气、功能和过程特性（网卡、网线、双绞线、同轴电缆、中继器）

下图是 OSI 七层各自的主要设备、协议和功能：

![OSI 七层模型各层主要设备与协议](https://cdn.nlark.com/yuque/0/2021/png/738210/1636556608826-f8a9e1ca-ec3b-428f-8e1a-dde7a6e333d2.png)

另一张更贴近「应用开发者视角」的图，把每一层的「常见内容」列了出来（数据在每一层都有不同的称呼：传输层叫「数据段 Segment」、网络层叫「分组/数据包 Packet」、链路层叫「帧 Frame」、物理层叫「比特 Bit」）：

![OSI 七层各层功能与常见协议](https://cdn.nlark.com/yuque/0/2021/png/738210/1636556682300-a22a162c-5949-4b71-89e7-79cdbbfddd1d.png)

不过 OSI 七层是个「理想化的参考模型」，实际互联网真正在用的是 **TCP/IP 模型**。TCP/IP 是传输控制协议/互联网协议的简称，早期的 TCP/IP 模型是一个**四层结构**，从下往上依次是网络接口层、互联网层、传输层、应用层；后来借鉴 OSI 七层，把网络接口层拆成物理层和数据链路层，形成了**五层结构**：

![OSI 七层 / TCP/IP 四层 / TCP/IP 五层模型对比](https://cdn.nlark.com/yuque/0/2021/png/738210/1636600245971-81d70447-283a-4c1e-b351-1e0df5c4f976.png)

三套模型的对应关系，这张图看得最清楚——**TCP/IP 五层模型是我们这篇文章的地基**（因为物理层和数据链路层确实职责不同，拆开讲更清晰）：

![OSI、TCP/IP 四层、五层协议体系结构对应关系](https://cdn.nlark.com/yuque/0/2021/png/738210/1636555530740-a0586f0c-0776-4165-86ea-fbf8e949a52b.png)

**协议**是什么？就是**为了让计算机能够通信而定义的通信规则**——规则有多种，协议也就有多种；本质上，协议 = **数据封装格式 + 传输规则**。

TCP/IP 不是单个协议，而是一个**很大的协议集合**：由网络层的 IP 协议和传输层的 TCP 协议组成，物理层和数据链路层没有定义任何协议（支持所有标准和专用协议）。下面这张图是五层模型里的常用协议全景：

![TCP/IP 五层模型常用协议](https://cdn.nlark.com/yuque/0/2021/png/738210/1636600509897-a3a2b50c-3152-40ef-8241-da8c3439f179.png)

| 层级 | 名称 | 含义 |
| --- | --- | --- |
| 应用层 | HTTP | 超文本传输协议，互联网上应用最广的网络协议 |
| 应用层 | FTP | 文件传输协议，网络上传输文件的一套标准协议 |
| 应用层 | SMTP | 简单邮件传输协议，Internet 传输 Email 的事实标准 |
| 应用层 | DNS | 域名系统，把域名和 IP 相互映射的分布式数据库（第 01 篇已讲透） |
| 传输层 | TCP | 面向连接的、可靠的、基于字节流的传输层协议 |
| 传输层 | UDP | 无连接的、提供简单不可靠信息传送的传输层协议 |
| 网络层 | IP | 互联网协议地址，分配给设备的数字标签 |
| 网络层 | ARP | 地址解析协议，根据 IP 地址获取物理地址 |
| 网络层 | ICMP | 控制报文协议，传递网络不通、主机是否可达等控制消息 |

> 💬 **面试官**：为什么要分层？OSI 七层和 TCP/IP 模型有什么区别？
>
> ✅ 标准答案：分层是为了**把复杂的网络通信拆成职责单一的子任务**（分工带来效能），每一层只依赖下一层提供的服务、只对上一层提供服务，出了问题可以精确定位到某一层。OSI 七层是理想化的参考模型（多了表示层、会话层）；TCP/IP 是实际使用的模型，早期分四层（网络接口层/互联网层/传输层/应用层），后来把网络接口层拆成物理层和数据链路层，形成五层。
>
> 🎁 加分答案：能说清「为什么 OSI 没被实际采用」——OSI 的表示层、会话层在实践中功能太薄、边界模糊，TCP/IP 把它们的职责（加密压缩、会话管理）并入应用层或传输层实现更务实；还能点出「每层有每层的设备」：路由器在网络层、交换机在数据链路层、网卡/网线在物理层，这是「交换机为什么认 MAC、路由器为什么认 IP」的根因。

### 2. 数据封装与解封装：一段数据的「套娃」过程

理解了分层，再看数据怎么「套娃」。发送方从高层到低层，每过一层就加一层头部；接收方从低层到高层，每过一层就剥掉一层头部：

![数据封装与解封装过程（自顶向下加头、自底向上拆头）](https://cdn.nlark.com/yuque/0/2021/png/738210/1636559419193-e3c5b771-6d03-43af-8aa4-4c1db3364fe5.png)

具体到应用层往下：**数据 → 传输层（加 TCP 头，变成段 Segment）→ 网络层（加 IP 头，变成包 Packet）→ 数据链路层（加 MAC 头 + 尾部，变成帧 Frame）→ 物理层（变成比特流）**：

### 3. Node.js `net` 模块：跑通一个 TCP 服务端/客户端

原理之后动手，用 Node.js 的 `net` 模块跑一个最简 TCP 服务端和客户端。这是理解后面「socket 事件」最直观的方式。

`server.js`（TCP 服务端）：

```javascript
const net = require('net');
const server = net.createServer((socket) => {
  // 监听客户端发过来的数据
  socket.on('data', (data) => {
    console.log(data.toString());
    socket.write('world');               // 👈 收到数据后回一句 world
  });
  // 监听客户端断开连接
  socket.on('end', () => {
    console.log('end');
  });
  socket.on('error', (error) => {
    console.log(error)
  });
});
server.listen(8089, () => {
  console.log(`server started at 8089 port`);
})
```

`client.js`（TCP 客户端）：

```javascript
const net = require('net');
const socket = new net.Socket();
socket.connect(8089, 'localhost');
socket.on('connect', (data) => {
  socket.write('hello');                 // 👈 连接建立后主动发 hello
});
socket.on('data', (data) => {
  console.log(data.toString());
  socket.destroy();                      // 👈 收到响应后主动关闭连接
});
socket.on('error', (error) => {
  console.log(error)
});
```

这两个文件背后藏着一个关键事实：**`socket.on('connect')` 触发时，底层已经悄悄完成了三次握手**；`socket.on('end')` 触发时，底层已经走完了四次挥手。Node.js 把这些 TCP 状态机的细节封装成了事件，但理解背后的状态机（第二节讲），才能真正读懂这些事件。

### 4. Node.js `dgram` 模块：跑通 UDP 的三种模式

TCP 之外，笔记里还记录了 UDP 的三种典型用法——点对点、广播、组播，这正好是理解「UDP 无连接」的最佳实践素材。

**点对点**（一对一收发）：

`src/server.js`

```javascript
const dgram = require('dgram');
const socket = dgram.createSocket('udp4');
socket.on('message', (msg, rinfo) => {
  console.log(msg.toString());
  console.log(rinfo);
  socket.send(msg, 0, msg.length, rinfo.port, rinfo.address);
})
socket.bind(41234, 'localhost');
```

`src/client.js`

```javascript
const dgram = require('dgram');
const socket = dgram.createSocket('udp4');
socket.on('message', (msg, rinfo) => {
  console.log(msg.toString());
  console.log(rinfo);
})
socket.send(new Buffer.from('hello world'), 0, 11, 41234, 'localhost', (error, bytes) => {
  console.log('发送了%d字节', bytes);
});
socket.on('error', (error) => {
  console.error(error);
})
```

**广播**（一对多，同网段所有主机都能收到）：

`src/server.js`

```javascript
// 广播
const dgram = require('dgram');
const socket = dgram.createSocket('udp4');
socket.on('message', (msg, rinfo) => {
  const buf = Buffer.from('已经接收客户端发送的数据:'+msg.toString());
  socket.setBroadcast(true);             // 👈 开启广播
  socket.send(buf, 0, buf.length, 41235, 'localhost');
})
socket.bind(41234, 'localhost');
```

`src/client.js`

```javascript
// 广播
const dgram = require('dgram');
const socket = dgram.createSocket('udp4');
socket.bind(41235, 'localhost');
const buf = Buffer.from('hello');
socket.send(buf, 0, buf.length, 41234, 'localhost');
socket.on('message', (msg, rinfo) => {
  console.log('received:', msg);
})
socket.on('error', (error) => {
  console.error(error);
})
```

**组播**（把同一业务类型逻辑分组，组内成员都能收到，组外收不到）：

`src/server.js`

```javascript
// 组播
const dgram = require('dgram');
const socket = dgram.createSocket('udp4');
socket.on('listening', () => {
  socket.setMulticastTTL(128);
  socket.setMulticastLoopback(true);
  socket.addMembership('230.185.192.108');   // 👈 加入组播组
})
function broadcast () {
  const buf = Buffer.from(new Date().toLocaleDateString());
  socket.send(buf, 0, buf.length, 8080, '230.185.192.108');
}
setInterval(broadcast, 1000);
```

`src/client.js`

```javascript
// 组播
const dgram = require('dgram');
const socket = dgram.createSocket('udp4');
socket.on('listening', () => {
  socket.addMembership('230.185.192.108');   // 👈 客户端也加入同一组
});
socket.on('message', (msg, rinfo) => {
  console.log(msg.toString());
  console.log(rinfo);
})
socket.bind('8080', '192.168.1.103');
```

组播使用 **D 类地址**作为组播地址，范围 `224.0.0.0～239.255.255.255`：`224.0.0.0～224.0.0.255` 是局部组播地址（为路由协议等保留）、`224.0.1.0～238.255.255.255` 是预留组播地址、`239.0.0.0～239.255.255.255` 是管理权限组播地址（组织内部用，不可用于 Internet）。

> 💬 **面试官**：从这段代码看，UDP 和 TCP 最直观的区别是什么？
>
> ✅ 标准答案：TCP 用 `net.createServer` + `socket.on('data')`，是**面向连接**的（要先 `connect` 建立连接、双方有独立的 socket）；UDP 用 `dgram.createSocket('udp4')` + `socket.on('message')`，**无连接**——不需要握手，`send` 时直接指定目标端口和地址，一次 send 就是一份独立的报文（保留消息边界）。
>
> 🎁 加分答案：能点出 `dgram` 的 `message` 回调签名是 `(msg, rinfo)`，`rinfo` 里带来源地址和端口——这正是「无连接」的体现：UDP 不维护连接状态，所以每次收包都要对方在报文里「自报家门」；而 TCP 因为建立了连接，`data` 回调里不用带来源信息。

### 5. `netstat -an` 查看连接状态

TCP 是有状态机的一连串状态（第二节会讲透）。运行中的连接处于哪个状态，用 `netstat -an` 能看到：

```bash
netstat -an          # Windows：查看所有 TCP 连接及状态
netstat -an | grep 8089   # Linux/macOS：过滤指定端口
```

输出里重点关注这几个状态：

| 状态 | 含义 | 是谁、在什么阶段 |
|------|------|-----------------|
| `LISTEN` | 监听中，等待连接 | 服务端启动后，`server.listen()` 之后 |
| `ESTABLISHED` | 连接已建立 | 双方完成三次握手，正在传输数据 |
| `TIME_WAIT` | 主动关闭方等待 2MSL | **主动发 FIN 的一方**关闭后短暂停留 |
| `CLOSE_WAIT` | 被动关闭方等待应用层关闭 | **收到 FIN 的一方**，还没调用 close |

其中 `TIME_WAIT` 和 `CLOSE_WAIT` 是生产环境排查的「高危状态」——第二节会重点讲它们为什么会堆积、堆积说明什么问题。

从这张图能看到完整的报文序列（Info 列）：

```text

No.2  [SYN, ACK]       Seq=0 Ack=1                    ← 三次握手②：服务端回 SYN+ACK
No.3  [ACK]            Seq=1 Ack=1                    ← 三次握手③：客户端回 ACK
No.4  [PSH, ACK]       Seq=1 Ack=1  Len=6             ← 传数据：客户端发 "hello"
No.5  [ACK]            Seq=1 Ack=7                    ← 确认收到（ack = 1 + 6 = 7）
No.6  [FIN, ACK]       Seq=1 Ack=7                    ← 四次挥手①：客户端发 FIN
No.7  [ACK]            Seq=7 Ack=2                    ← 四次挥手②：服务端回 ACK
No.8  [FIN, ACK]       Seq=7 Ack=2                    ← 四次挥手③：服务端发 FIN
No.9  [ACK]            Seq=2 Ack=8                    ← 四次挥手④：客户端回 ACK
```

Wireshark 里展开一个报文还能看到 TCP 头部的每一个字段（源/目的端口、Sequence number、Acknowledgment number、Flags 等），这就是第三节「TCP 报文头」的实物对照：

## 二、设计与原理

这是本篇的核心。下面按「**一个 TCP 报文段的完整旅程**」自顶向下讲透：从应用层诞生，到传输层被装上 TCP 头（本文重心），再到网络层、数据链路层、物理层层层封装，最后到对端解封装。每一站都把「这一层发生了什么、加了什么头、面试会怎么考」讲清楚。

### 第 1 站 · 应用层：数据诞生的地方

旅程的起点是应用层。你在浏览器里点了一下「提交处方」，HIS 系统前端把一段 JSON 数据交给操作系统——这一步还没发生任何网络传输，只是**产生了一份「上层数据」**。

应用层是离用户最近的一层，它定义了一堆**应用层协议**，每个协议都「住在」一个固定的端口上：

![应用层协议通过端口号对应传输层](https://cdn.nlark.com/yuque/0/2021/png/738210/1637055583010-a707dd37-5ba5-4018-8362-534779120401.png)

常见的应用层协议：

- **HTTP** 超文本传输协议（网页）
- **FTP** 文件传输协议（文件上传下载）
- **SMTP**（发邮件）和 **POP3**（收邮件）

这里要理解一个关键概念——**端口号**。应用层协议那么多（HTTP、FTP、SMTP、DNS……），数据到了传输层，怎么知道「这份数据是给哪个应用的」？靠的就是端口号。每个应用层协议绑定一个固定端口（HTTP 绑 80、DNS 绑 53、SMTP 绑 25、POP3 绑 110），传输层用「端口号」来标识「这份数据属于哪个上层应用」。

> 💬 **面试官**：端口号的作用是什么？它是在哪一层起作用的？
>
> ✅ 标准答案：端口号标识的是**上层应用/进程**——一台机器可能同时跑多个网络应用（一边发邮件一边浏览网页），传输层靠端口号把数据分发给正确的应用。端口号定义在传输层（TCP/UDP 头部里各 16 位），但「服务」的意义是应用层的。
>
> 🎁 加分答案：能区分「IP 定位到哪台机器、端口定位到哪个进程」——IP 地址在网络层，负责把数据送到「哪台主机」；端口号在传输层，负责把数据交给主机上的「哪个进程」。所以一个完整的通信端点（socket）是「IP + 端口」的四元组概念。

**应用层之外的两个「邻居协议」：DNS 与 DHCP**

应用层还有两个协议值得顺手带一句，它们都在我们日常上网的「第一步」出场：

**DNS 服务器**：域名系统，把域名翻译成 IP（这一块第 01 篇已经完整讲透，这里只做呼应）。早期用 Hosts 文件解析域名，但存在「名称重复、主机维护困难」两个问题，于是有了分布式、层次性的 DNS。域名空间从根域 → 顶级域（组织域/国家地区域）→ 二级域名逐层展开，DNS 的查找过程如下图（本地 DNS 缓存未命中后，从根服务器逐级问到权威服务器）：

### 第 2 站 · 传输层：TCP 报文段诞生（全文重心）

数据从应用层下来，到达**传输层**。这里是本篇的主角——传输层把上层数据切成一段段，每段装上一个 **TCP 头部**，变成「TCP 报文段（Segment）」。

传输层是**面向连接的、可靠的进程到进程通信**的协议，TCP 提供**全双工服务**（数据可同时双向传输），把若干个字节构成一个数组（报文段）。传输层对可靠性要求高的上层协议提供可靠保证——数据丢失、损坏时怎么保证可靠；而网络层只管把数据传出去，成功与否它不关心。

**2.1 TCP 报文头逐字段拆解**

要理解 TCP 的一切，先把这个头部记住。TCP 头部（不含选项）固定 **20 字节**，字段如下：

![TCP 报文头格式（源端口、目标端口、序列号、确认号、控制位、窗口大小、校验和）](https://cdn.nlark.com/yuque/0/2021/png/738210/1636892774959-311d177c-e9b0-46ce-ab2c-3c1de4ea3023.png)

逐字段拆解：

**源端口号 / 目标端口号**（各 16 位）：计算机靠端口号识别「访问哪个服务」。发送方端口是随机端口，目标端口决定「接收方哪个程序来接收」。

**32 位序列号（Sequence Number）**：TCP 用序列号对数据包标记，以便到达目的地后重新组装。假设当前序列号为 `s`、发送数据长度为 `l`，则下次发送数据的序列号是 `s + l`。建立连接时，由计算机生成一个随机数作为序列号的初始值：

![32 位序列号字段的作用](https://cdn.nlark.com/yuque/0/2021/png/738210/1636894966560-872d15ce-25ba-43cc-a20c-2fdd1c2daeb8.png)

**确认应答号（Acknowledgment Number）**：它表示「**下一次期望收到的数据的序列号**」。假设发送的序列号为 `s`、数据长度为 `l`，接收方返回的确认应答号就是 `s + l`——发送端收到这个确认号，就可以认为「这个序号之前的所有数据都已被正常接收」：

![确认应答号字段的作用](https://cdn.nlark.com/yuque/0/2021/png/738210/1636895227845-6e05fa8e-aa81-4ab0-ad45-5dffbfeb03ea.png)

**首部长度**：TCP 首部长度，单位 4 字节。没有可选字段时值为 5，表示 TCP 首部 20 字节。

**6 个控制位**：TCP 的连接、传输和断开都受这六个控制位指挥：

- **URG**（urgent 紧急位）：紧急信号
- **ACK**（acknowledgement 确认）：为 1 表示确认号有效
- **PSH**（push 急迫位）：缓冲区将满，立刻传输
- **RST**（reset 重置位）：连接断了重新连接
- **SYN**（synchronous 同步序号位）：TCP 建立连接时置为 1
- **FIN**（发送端完成位）：提出断开连接的一方把 FIN 置 1

其中 **SYN**、**ACK**、**FIN** 是理解三次握手/四次挥手的三个关键位：

![SYN 控制位：请求建立连接](https://cdn.nlark.com/yuque/0/2021/png/738210/1636895484227-c4b356d8-e11a-4352-a315-9cf78247b4af.png)

![ACK 控制位：确认序列号有效](https://cdn.nlark.com/yuque/0/2021/png/738210/1636895521583-0d045060-3b87-4da7-a1fb-139f793af099.png)

![FIN 控制位：请求断开连接](https://cdn.nlark.com/yuque/0/2021/png/738210/1636895558012-962cdbc0-124c-4063-9450-b2688664720d.png)

**16 位窗口大小（Window Size）**：说明「本地还能接收多少数据段」，这个值可变——网络通畅时调大加快传输，网络不稳定时调小保证可靠。**它就是滑动窗口流量控制的核心字段**（第 2.7 节展开）：

![16 位窗口大小字段：流量控制的核心](https://cdn.nlark.com/yuque/0/2021/png/738210/1636895649335-a34d5c7d-e174-459c-8d52-f27bcb0a3e80.png)

**校验和**：做差错控制。TCP 校验和计算包括 TCP 首部、数据和其它填充字节；发送端算一次，到达目的端再算一次，两次一致说明数据正确，否则认为数据被破坏，接收端丢弃：

![校验和字段：实现差错控制](https://cdn.nlark.com/yuque/0/2021/png/738210/1636896324317-6644e3fd-a385-4dc1-9609-1eb002ed92f9.png)

**紧急指针**：仅在 URG 控制位为 1 时有效，表示紧急数据的末尾在 TCP 数据部分的位置，通常在暂时中断通信时使用（如输入 CTRL+C）。

> 💬 **面试官**：TCP 报文头里有哪些关键字段？它们分别是干什么的？
>
> ✅ 标准答案：源/目的端口（定位收发双方的进程）、32 位序列号（标记每个字节、用于按序重组）、32 位确认号（「期望收到的下一个字节序号」）、6 个控制位（URG/ACK/PSH/RST/SYN/FIN，指挥连接建立、传输、断开）、16 位窗口大小（流量控制，通告「我还能收多少」）、校验和（差错控制）。
>
> 🎁 加分答案：能说清「序列号和确认号是同一个字段吗」——不是，它们配对使用：序列号是「我发的这个字节的编号」，确认号是「我期望你下一个发来哪个编号」，两者都基于「每个字节都有序号」这个前提；还能点出 ACK 位的语义——「ACK=1 才说明确认号字段有效」，SYN 和 FIN 报文也各占用一个序号。

**2.2 可靠传输的基石：序列号 + 确认应答 + 超时重传**

TCP 为什么「可靠」？就靠三个最基础的机制，理解它们是理解后面所有高级机制（快速重传、滑动窗口）的前提：

**① 序列号（seq）**：每个字节都有序号，保证数据能按序到达、能发现丢失和重复。

**② 确认应答（ack）**：接收方对连续收到的字节回 ACK 确认，ack 表示「**期待收到的下一个字节序号**」——`ack = N` 的意思是「N 之前的所有字节我都收到了，请从第 N 个字节继续发」。

**③ 超时重传**：发送方为每个未确认的段设置超时定时器，超时没收到 ACK 就重传。

这三件套合起来，就回答了那个经典问题——**「TCP 怎么保证不丢、不重、不乱序」**：不乱序靠序列号（按序重组），不丢靠超时重传（丢了的重新发），不重靠确认号（确认过的不会再被当作有效数据）。

**特别要记住「确认号」的语义**：它不是「我收到了第 N 个」，而是「我期待收到第 N 个」。这个微妙的区别，是理解后面「收发数据」小节里 `ack = 1 + 6 = 7` 这类计算的关键。

> 💬 **面试官**：TCP 可靠传输依赖哪几个基础机制？它们分别解决什么问题？
>
> ✅ 标准答案：序列号（seq）+ 确认应答（ack）+ 超时重传。序列号给每个字节编号，保证按序到达、发现丢失；确认应答告诉发送方「期待的下一个字节序号」，确认已连续收到；超时重传保证超时未确认的段会被重发。三者合起来实现「不丢、不重、不乱序」。
>
> 🎁 加分答案：能点出确认号的精确语义——「ack 表示期待的下一个字节序号，不是『收到第几个』」，并说明这是理解后面「快速重传（收到 3 个重复 ACK 立即重传）」和「滑动窗口（ACK 驱动窗口滑动）」的钥匙；还能补充「累积确认」的概念——TCP 的 ACK 是累积的，`ack=N` 一次性确认了 N 之前的所有字节，而不是逐字节确认。

**2.3 三次握手：建立连接的状态机**

TCP 是面向连接的协议，它在源点和终点之间建立**虚拟连接**（不是物理连接）。在数据通信之前，发送端与接收端要先建立连接；数据发完后再断开。TCP 连接的每一方都由一个 IP 地址和一个端口组成。

**三次握手**的过程：

- **第一次握手**：客户端将标志位 SYN 置 1，随机产生一个值 `seq=J` 发给服务端，客户端进入 **SYN_SENT** 状态，等待服务端确认
- **第二次握手**：服务端收到后，由 SYN=1 知道客户端请求建连，服务端将 SYN 和 ACK 都置 1，`ack=J+1`，随机产生 `seq=K` 发给客户端以确认，服务端进入 **SYN_RCVD** 状态
- **第三次握手**：客户端收到后，检查 ack 是否为 J+1、SYN 是否为 1，正确则将 ACK 置 1、`ack=K+1` 发给服务端；服务端检查 ack 是否为 K+1、ACK 是否为 1，正确则连接建立成功，**双方进入 ESTABLISHED 状态**，开始传输数据

三次握手的**目的**有两个：① 双方同时确认「我能发、我能收」；② 同步各自的**初始序列号**（后续所有数据包的序号都以此为基准，用于保证按序到达和丢包重传）。

下面这张状态机图把三次握手 + 四次挥手 + 收发数据完整画了出来（`connect()` → SYN_SENT → SYN_RCVD → ESTABLISHED → 数据交换 → FIN_WAIT_1/2 → CLOSE_WAIT → LAST_ACK → TIME_WAIT → CLOSED）：

![TCP 连接建立、数据传输、断开完整状态机](https://cdn.nlark.com/yuque/0/2021/png/738210/1636896517031-a5ffd1a3-4757-43ad-ad26-c53e4fca00f5.png)

> 💬 **面试官**：说一下三次握手的完整流程。
>
> ✅ 标准答案：① 客户端发 SYN（`seq=x`）进入 SYN_SENT；② 服务端回 SYN+ACK（`seq=y, ack=x+1`）进入 SYN_RCVD；③ 客户端回 ACK（`ack=y+1`），双方进入 ESTABLISHED。目的是同步双方的初始序列号、并确认双方收发能力都正常。
>
> 🎁 加分答案：能说清每一步的 seq/ack 变化（第三次握手客户端的 ack 是 `y+1`、服务端校验 `K+1`），并点出「SYN 和 FIN 各占一个序号」——所以第二次握手的 ack 是 `x+1` 而不是 `x`，第四次挥手的 ack 也是 `序号+1`。

**2.4 为什么两次握手不够？**

这是面试里「三次握手」最常被追问的一层。核心矛盾在**服务端的被动性**：

如果只有两次握手（客户端发 SYN → 服务端回 SYN+ACK 就认为连接建立），那么服务端发出 SYN+ACK 后就**单方面认为连接建立了**——但服务端无法确认「自己发出的 ACK 客户端是否真的收到」。

如果这个包在网络中丢失或延迟：

- 客户端可能认为连接还没建立（它没收到 SYN+ACK），不会发数据
- 服务端却已经开始「等数据」，白白占用资源

更糟的是**历史遗留的重复请求包**：网络里可能残留着某个早已失效的旧 SYN，如果两次握手，服务端无法区分「这是新连接还是旧连接的重复 SYN」，会把历史包误认为新连接。**SYN 洪水攻击**正是利用了这个不对称性——攻击者大量发送伪造源地址的 SYN，服务端回 SYN+ACK 后就进入 SYN_RCVD 半连接状态等待，资源被耗尽而无法服务正常请求。

三次握手让**客户端也参与一次确认**（第三次 ACK），服务端只有在收到客户端最终的 ACK 后才建立连接，从而确认「客户端确实收到了我的 SYN+ACK、且这是它真实想要的新连接」。

> 💬 **面试官**：为什么建立连接需要三次握手，两次不够吗？
>
> ✅ 标准答案：两次握手时服务端发出 SYN+ACK 后就认为连接建立，但无法确认「客户端是否真的收到、是否真的是新连接」——如果 SYN+ACK 丢失，客户端以为没建立，服务端却空等；而且无法区分历史遗留的重复 SYN。第三次握手让客户端回 ACK，服务端确认客户端「真的收到了且要连」，才建立连接。SYN 洪水攻击正是利用两次握手的这个不对称性。
>
> 🎁 加分答案：能落到「本质是防止失效的连接请求报文突然又传到服务端产生错误」——三次握手的第三次 ACK 让服务端确认客户端还「在线」；还能点出 SYN 洪水攻击的缓解思路（SYN Cookie、限制半连接数），说明这是「资源耗尽型攻击」而非「破坏数据型攻击」。

**2.6 四次挥手为什么比握手多一次**

断开连接要**四次**挥手，比握手多一次。原因是 **TCP 是全双工的**——两个方向的数据流**独立关闭**。

**四次挥手**过程：

- **第一次挥手**：客户端发 FIN，关闭「客户端 → 服务端」的数据传送，客户端进入 **FIN_WAIT_1** 状态
- **第二次挥手**：服务端收到 FIN 后回 ACK，确认序号 = 收到序号 + 1（和 SYN 一样，一个 FIN 占用一个序号），服务端进入 **CLOSE_WAIT** 状态
- **第三次挥手**：服务端发 FIN，关闭「服务端 → 客户端」的数据传送，服务端进入 **LAST_ACK** 状态
- **第四次挥手**：客户端收到 FIN 后进入 **TIME_WAIT** 状态，回一个 ACK（确认序号 = 收到序号 + 1），服务端收到后进入 **CLOSED** 状态，完成挥手

**为什么不能像握手一样把中间两步合并成三次？** 这就是笔记里「经典问答」的答案：

> 服务端在 LISTEN 状态下，收到建连请求的 SYN 报文后，能把 ACK 和 SYN 放在**一个报文**里发回。但关闭连接时，收到对方的 FIN 报文，**仅仅表示对方不再发数据、但还能接收数据**——己方未必已经把数据都发完了。所以己方可以立即 close，也可以**先发一些数据给对方，再发 FIN** 表示「同意现在关闭」。因此，己方的 ACK 和 FIN 一般都会**分开发送**。

一句话总结：**握手时服务端的 SYN 和 ACK 能合并（它本来就要同时「确认」和「同步自己的序号」）；挥手时服务端「确认收到 FIN」和「自己也要关闭」是两个时间点的事（中间可能还有数据没发完），所以 ACK 和 FIN 必须分开**。

> 💬 **面试官**：为什么断开连接需要四次挥手，而不是像建立连接一样三次？
>
> ✅ 标准答案：因为 TCP 是**全双工**的，两个方向独立关闭。主动关闭方发 FIN 表示「我这方向没数据了」，但被动方可能还有数据没发完，所以先回一个 ACK 确认收到 FIN，等自己的数据也发完后再单独发一个 FIN——这中间两步（ACK 和 FIN）不能合并，因为「确认收到」和「自己也要关闭」是两个时间点的事。
>
> 🎁 加分答案：能对比握手——握手时服务端的 SYN 和 ACK 能合并（同时「确认」和「同步自己的序号」，本来就在同一时刻发生）；挥手时被动方的 ACK 和 FIN 之间存在「我还想再发点数据」的时间差，所以必须分开发。还能点出「被动方不发数据的极端情况也可以 ACK+FIN 一起发，但协议允许分别发，所以标准形态是四次」。

**2.7 TIME_WAIT 状态存在的意义**

四次挥手里有个「赖着不走」的状态：主动关闭方发出最后一个 ACK 后，**不会立刻释放连接，而是进入 TIME_WAIT 状态，等 2 个 MSL（Maximum Segment Lifetime，最大报文段生存时间）**。为什么要等？

**作用①（防最后一个 ACK 丢失）**：主动关闭方发的最后一个 ACK 如果丢了，被动方会重发 FIN。如果主动方立刻释放连接，就再也收不到这个重发的 FIN、无法再回 ACK，导致被动方一直停在 LAST_ACK 等不到确认。TIME_WAIT 期间主动方「还活着」，收到重发的 FIN 还能再回一次 ACK。

**作用②（防旧报文串扰新连接）**：等 2MSL 确保「本连接产生的所有报文段」都从网络中消失。否则，如果这条连接的四元组（源 IP+端口 / 目的 IP+端口）被立刻复用建立新连接，上一条连接的**旧报文**可能迟到、被误当成新连接的数据，造成串扰。

生产环境的**排查意义**：

- **大量 TIME_WAIT**：说明是「主动关闭方」在频繁短连接创建销毁（每次 HTTP 请求一个连接，用完就关）。缓解方式是用 **keep-alive 连接复用**（一个连接承载多次请求），减少连接的频繁建立和销毁
- **大量 CLOSE_WAIT**：说明是「被动关闭方」收到 FIN 后**没有调用 close() 关闭 socket**——通常是代码 bug（忘了关闭连接/资源泄漏），连接会一直挂着占用资源

> 💬 **面试官**：TIME_WAIT 状态存在的意义是什么？生产环境大量 TIME_WAIT 堆积说明什么问题？
>
> ✅ 标准答案：TIME_WAIT 是主动关闭方发出最后一个 ACK 后进入的状态，等 2MSL。两个作用：① 防最后一个 ACK 丢失——若被动方重发 FIN，主动方还能再回 ACK；② 防旧报文串扰——等 2MSL 让本连接的所有旧报文都从网络中消失，避免污染复用四元组的新连接。大量 TIME_WAIT 说明是「主动关闭方」在频繁短连接（反复建连断连），通常用 keep-alive 连接复用缓解。
>
> 🎁 加分答案：能区分 TIME_WAIT 和 CLOSE_WAIT——TIME_WAIT 是**主动关闭方**的正常状态（等 2MSL），堆积多说明「短连接频繁」；CLOSE_WAIT 是**被动关闭方**收到 FIN 后没调用 close() 的状态，堆积多说明「代码 bug、连接泄漏」，这才是真正需要警惕的。还能点出「谁主动 close 谁进 TIME_WAIT」——所以大量 TIME_WAIT 通常出现在「主动关闭」的服务端（如反向代理主动断开）。

**2.8 滑动窗口与流量控制**

前面的可靠传输三件套有个性能缺陷：**一问一答的效率太低**——发一个段、等一个 ACK、再发下一个。为了不浪费往返时间（RTT），TCP 引入**滑动窗口**，允许发送方**在没收到确认之前连续发多个段**。

**滑动窗口本质是一种流量控制技术**：接收方通过 TCP 头部的 **Window Size（窗口大小）** 字段告诉发送方「我还能接收多少数据」，发送方据此控制**未确认数据的发送量**，防止发送速度超过接收方处理能力。

核心机制（笔记「窗口机制」）：

- 发送方维持一个「**允许发送的帧序号**」连续区间，叫**发送窗口**；接收方维持一个「允许接收的帧序号」区间，叫**接收窗口**
- 发送窗口内的序列号，代表「已发送但未确认的帧」或「可以发送的帧」
- 发送窗口和接收窗口的上下界不一定要一样，大小也可以不同
- **窗口大小 = 接收方还有多大的缓冲区**；当窗口为 0 时，发送方一般不能再发数据（两种例外：可以发紧急数据；可以发 1 字节数据通知接收方重新声明窗口大小）

![发送方的发送窗口与发送缓存](https://cdn.nlark.com/yuque/0/2021/png/738210/1636993717743-6149cdaa-4035-4c66-9f60-b7d189ebc1c6.png)

![接收方的接收窗口与接收缓存](https://cdn.nlark.com/yuque/0/2021/png/738210/1636993744791-ac31f236-22f1-4f67-84cc-5bfad462e6d3.png)

这里有个**极易混淆的点**，必须单独拎出来：

- **流量控制（滑动窗口）**：保护**接收方**。接收方通过 Window Size 告诉发送方「我处理不过来了，你慢点」，防止发送方把接收方的缓冲区打爆
- **拥塞控制**：保护**网络整体**。发送方根据「网络拥塞信号」（丢包、延迟）自我调节发送速率，防止把网络链路打爆

**两者是两个不同维度的问题**，容易被混淆——流量控制是「接收方能力」约束，拥塞控制是「网络容量」约束。下一节讲拥塞控制时，你会看到它们如何「共同决定发送方一次能发多少数据」。

> 💬 **面试官**：滑动窗口的流量控制和拥塞控制是同一个机制吗？分别保护的是谁？
>
> ✅ 标准答案：不是。流量控制（滑动窗口）保护的是**接收方**——接收方通过 TCP 头部的 Window Size 字段通告「我还能收多少」，发送方据此控制未确认数据的发送量；拥塞控制保护的是**网络整体**——发送方根据丢包/延迟等拥塞信号自我调节发送速率。一个是「接收方能力」约束，一个是「网络容量」约束。
>
> 🎁 加分答案：能说清两者的「窗口」来源——流量控制的窗口由**接收方报的 Window Size** 决定；拥塞控制的窗口（拥塞窗口 cwnd）由**发送方自己根据拥塞信号调节**。最终发送方一次能发多少 = **min(接收窗口, 拥塞窗口)**，两者共同决定。这就是「为什么先讲流量控制、再讲拥塞控制」的递进逻辑。

**2.9 拥塞控制四阶段（重点）**

早期网络通信中，通信双方不考虑网络拥挤、直接发数据，导致中间节点阻塞掉包、谁也发不了。**拥塞控制**就是来解决「如何在不了解全局网络状况的前提下，自适应逼近网络承载能力」。

TCP 为每条连接维护一个**拥塞窗口（cwnd）**，限制「端到端之间未确认分组的数量」。**拥塞窗口本质是「发送方侧的滑动窗口」**——它由发送方根据网络拥塞信号自我调节（而流量控制的窗口由接收方报）。理解这个对应关系，是理解「先流量控制后拥塞控制」递进逻辑的关键。

拥塞控制分**四个阶段**：

**① 慢启动（Slow Start）**：拥塞窗口从一个很小的初始值（通常 2 个 MSS，最大分段大小）开始，**指数级增长**——每收到一个确认，cwnd 就增加一个 MSS，所以每个 RTT 内 cwnd 能翻倍。虽然叫「慢启动」，其实增长极快，只是起点低。

**② 拥塞避免（Congestion Avoidance）**：cwnd 增长到阈值（ssthresh）后，从指数增长改为**线性增长**（加法增大），更谨慎地探测网络容量。

**③ 快速重传（Fast Retransmit）**：当收到 **3 个重复 ACK**（说明某个段丢了，但后续段还在陆续到达），发送方**立即重传丢失的包，不等超时**。

**④ 快速恢复（Fast Recovery）**：快速重传后，**不直接回到慢启动**，而是把 cwnd 减半（乘法减小）后继续线性增长，避免吞吐量骤降。

这套机制背后的思想是 **AIMD（Additive-Increase / Multiplicative-Decrease，加法增大、乘法减小）**：正常时线性增加（谨慎探测），检测到拥塞时乘法减小（快速降速），多个使用 AIMD 的 TCP 流量最终会收敛到对线路的**等量公平竞争**。经验规律是：**未确认的数据包数量 ≈ 带宽 × 延迟**（即带宽-延迟积），**发现丢包就立刻减半**。

> 💬 **面试官**：拥塞控制分哪几个阶段？慢启动和拥塞避免的区别是什么？
>
> ✅ 标准答案：四个阶段——慢启动（cwnd 从小初始值指数级增长）、拥塞避免（超过阈值后线性增长）、快速重传（收到 3 个重复 ACK 立即重传）、快速恢复（减半后继续线性增长，不回到慢启动）。慢启动是**指数增长**（每 RTT 翻倍），拥塞避免是**线性增长**（加法增大），分界点是阈值 ssthresh。
>
> 🎁 加分答案：能点出「为什么快速重传等 3 个重复 ACK 而不是 1 个」——1 个重复 ACK 可能是乱序，3 个重复 ACK 几乎可以确定是丢包（后面已有 3 个段陆续到达）；还能说清「快速恢复 vs 慢启动」的设计动机——传统做法是超时后直接回慢启动（cwnd 归 1，吞吐量骤降），快速恢复只减半、保持较高吞吐，应对「丢包但不严重」的场景；超时（RTO）才是真正的严重拥塞信号，才回到慢启动。

**2.10 UDP 封装格式与 TCP 的本质区别（重点）**

讲完 TCP，再看它的「对照组」UDP。UDP 是无连接、不保证可靠性的传输层协议——发送端不关心数据是否到达、是否出错，收到数据的主机也不会告诉发送方是否收到，可靠性由上层协议保障。UDP 首部结构极简，能实现最小开销，适合「报文很短、对可靠性要求不高」的场景。

**差错控制（可选）**：UDP 校验和是可选的，这点和 TCP（必须校验）不同：

![UDP 校验和字段（可选）](https://cdn.nlark.com/yuque/0/2021/png/738210/1637045943482-8c49c055-9d7f-41ee-82c2-2da146362698.png)

**UDP vs TCP 的本质区别**，就三条：

- **UDP 无连接**：发送前不握手、不建立连接
- **UDP 不可靠**：不确认、不重传、不保证顺序
- **UDP 没有拥塞控制**：发送方可以以任意速率发包，网络拥塞时也不会自动降速

这三条本质决定了它的适用场景：

- **DNS**：单条查询很小、一次往返，用 TCP 握手开销不划算，丢包由上层重试（这就是第 01 篇说的「DNS 跑在 UDP 53 上」的原因）
- **QUIC / HTTP3**：在 UDP 之上自己实现可靠传输和拥塞控制，摆脱 TCP 的队头阻塞
- **实时音视频 / 在线游戏**：宁可丢一帧，也不愿为等重传而卡顿（TCP 的重传会让实时流「卡住等重传」）

反过来，凡是需要「保证完整、保证顺序」的数据（文件传输、网页、数据库），都用 TCP。UDP 的典型应用：QQ、视频软件、TFTP（简单文件传输协议，像「短信」一样发小报文）。

> 💬 **面试官**：UDP 和 TCP 的本质区别是什么？为什么 DNS、QUIC、实时音视频都选 UDP？
>
> ✅ 标准答案：本质区别三条——UDP 无连接（不握手）、不可靠（不确认/不重传/不保证顺序）、没有拥塞控制（任意速率发包、拥塞也不降速）。DNS 选 UDP 因为单条查询很小、一次往返、TCP 握手不划算（丢包由上层重试）；QUIC/HTTP3 选 UDP 是为了在 UDP 上自己实现可靠传输和拥塞控制、摆脱 TCP 队头阻塞；实时音视频/游戏选 UDP 因为「宁可丢一帧、不愿为等重传而卡顿」。
>
> 🎁 加分答案：能补充「反过来」——需要保证完整和顺序的（文件、网页、数据库）都用 TCP；还能点出 UDP 的「消息边界」特性（每次 send 是独立报文，接收方按报文收，不像 TCP 是字节流要自己粘包拆包），以及 QUIC 选 UDP 的深层原因（TCP 在操作系统内核实现、迭代慢，UDP 上可自定义，且能解决 TCP 的队头阻塞）。

**2.11 对比 Node.js 实现：背压 vs 流量控制**

最后落地到 Node.js。理解 TCP 层的滑动窗口流量控制，能帮你理解 Node.js Stream 的「背压（backpressure）」设计为什么采用类似的「暂停/恢复」思路。

Node.js 的 `net.Socket` 对象遇到「接收方处理不过来」时，同样会体现背压：

```javascript
const net = require('net');
const server = net.createServer((socket) => {
  // 模拟持续写入大量数据
  const ok = socket.write(largeBuffer);
  if (!ok) {
    // 👈 write() 返回 false：内核发送缓冲区已满，说明接收方消费不过来了
    socket.once('drain', () => {
      // 👈 等缓冲区排空后再继续写
    });
  }
});
```

当 `socket.write()` 返回 `false`，意味着写入缓冲区堆积——这和 TCP 层的「接收窗口为 0、发送方暂停」是**两个不同抽象层级、但目标一致的机制**：

- **TCP 层**：接收方用 Window Size 字段通告「缓冲区快满了」，发送方暂停
- **Node.js 层**：内核写入缓冲区满 → `write()` 返回 `false` → 触发「暂停」，等 `drain` 事件「恢复」

两者都是「接收方处理不过来 → 发送方减速」的**背压**思路，只是一个发生在内核协议栈、一个发生在应用层 Stream 抽象。理解了 TCP 的流量控制，就能理解 Node.js Stream 背压的「暂停/恢复」为什么是必要的（这部分呼应 Node.js 系列 04 篇 I/O 体系）。

> 💬 **面试官**：Node.js 的 `write()` 返回 `false` 意味着什么？它和 TCP 的流量控制有关系吗？
>
> ✅ 标准答案：`write()` 返回 `false` 表示内核的发送缓冲区已满（接收方消费不过来了），触发「背压」——此时应暂停写入、监听 `drain` 事件再恢复。它和 TCP 流量控制是两个层级但目标一致的机制：TCP 层靠 Window Size 让发送方减速，Node.js 层靠 write 返回 false + drain 事件让应用暂停/恢复，本质都是「接收方处理不过来 → 发送方减速」。
>
> 🎁 加分答案：能点出「背压」这个概念贯穿了从内核到应用层的整条链路——TCP 窗口（内核协议栈）→ socket 发送缓冲区（内核）→ write 返回 false + drain（Node.js）→ Stream 的 `pause()`/`resume()`（应用层），层层都是同一个「背压」思想的体现。

### 第 3 站 · 网络层：TCP 段变成 IP 包

TCP 段从传输层下来，到达**网络层（互联网层）**。网络层位于传输层和网络接口层之间，负责把数据从源主机经过若干中间节点送到目标主机，做**路由**和**选址**的工作。

**选址**：交换机靠 MAC 寻址，但 MAC 地址是无层次的，所以要靠 IP 地址确认计算机的位置：

**路由**：在能选择的多条道路之间选择一条最短的路径：

**3.1 IP 头部逐字段**

网络层给 TCP 段装上一个 **IP 头部**，变成「IP 数据报（Packet）」。IP 报头最小 20 字节：

![IP 头部格式（固定 20 字节 + 可选字段）](https://cdn.nlark.com/yuque/0/2021/png/738210/1636711149485-59f43b66-561c-4d5d-996c-ca022ee16a0c.png)

| 字段 | 说明 |
| --- | --- |
| 版本 | 占 4 位，IP 协议版本（IPv4 = 4） |
| 首部长度 | 占 4 位，单位 32 位字长（4 字节），常用值 5 表示 20 字节 |
| 区分服务（TOS） | 占 8 位，用于获得更好的服务 |
| 总长度 | 首部 + 数据之和，16 位，最大 65535 字节 |
| 标识 | 16 位，标识数据报，分片时各分片复制同一值用于重组 |
| 标志 | 3 位，DF（不分片）/ MF（更多分片） |
| 片偏移 | 13 位，分片后标记在原报文中的相对位置，以 8 字节为单位 |
| 生存时间（TTL） | 8 位，每经过一个路由器减 1，减到 0 就丢弃，防止无限传输 |
| 协议 | 8 位，上层协议类型（TCP=6、UDP=17、ICMP=1） |
| 首部检验和 | 16 位，校验首部（每经一个路由器 TTL 变化需重算） |
| 源地址 / 目的地址 | 各 32 位，源 IP / 目的 IP |
| 可选字段 + 填充 | 测试/调试/安全用，填充保证首部是 32 位整数倍 |

这里有个字段值得单独说——**TTL（生存时间）**：它由源主机设置，指明数据报在网络中最多经过多少个路由器。路由器转发前先把 TTL 减 1，减到 0 就丢弃。这是防止「无法交付的数据报在网络中无限循环传输、消耗资源」的机制。

> 💬 **面试官**：IP 头部的 TTL 字段是干什么的？为什么需要它？
>
> ✅ 标准答案：TTL（生存时间）由源主机设置，每经过一个路由器减 1，减到 0 就丢弃该数据报。作用是**防止无法交付的数据报在网络中无限循环**（如路由环路时），消耗网络资源。TTL 最大 255。
>
> 🎁 加分答案：能点出「TTL 减到 0 时会回 ICMP 报文（Time Exceeded）」——这也是 `traceroute`/`tracert` 的原理：故意发 TTL=1、2、3… 的包，逐跳探测路径上每一跳的路由器；还能点出 IP 头部的「协议」字段——它告诉目的主机「上层是 TCP 还是 UDP 还是 ICMP」，是「数据部分交给谁」的分发依据。

**3.2 IP 地址：格式、组成、分类**

在网络中，每台计算机都有一个唯一地址方便别人找到它，这个地址就是 **IP 地址**。IP 地址是一个网络编码，由 **32 位二进制**组成，通常写成**点分十进制**（每 8 位一段）：

![IP 地址格式（32 位二进制，点分十进制表示）](https://cdn.nlark.com/yuque/0/2021/png/738210/1636803134629-ec440c48-8d73-428e-b612-0fc712cacc25.png)

IP 地址由两部分组成：**网络部分（network，标识不同网络）+ 主机部分（host，标识网络内特定主机）**：

![IP 地址组成：网络部分 + 主机部分](https://cdn.nlark.com/yuque/0/2021/png/738210/1636803289097-06ed98ee-a756-420a-941c-c684b514fdce.png)

IP 地址网络部分由 Internet 分配机构统一分配以保证唯一性。几个特殊地址：全 1 的 `255.255.255.255` 是**限制广播地址**（发给所有网络所有主机）；全 0 的 `0.0.0.0` 表示启动时的 IP（尚未分配）；`127` 开头的地址（除 `127.255.255.255`）都代表**本机**，用于测试。

IP 地址按「网络部分 + 主机部分」的划分方式分为 **A/B/C 类**：

![IP 地址分类：A/B/C 类地址范围与主机数量](https://cdn.nlark.com/yuque/0/2021/png/738210/1636804012293-6adccd15-970f-4358-9f4f-e174b57a0566.png)

- **A 类**：`1-126`，主机数量 2^24 - 2
- **B 类**：`128-191`，主机数量 2^16 - 2
- **C 类**：`192-223`，主机数量 2^8 - 2

IP 地址还分**公有地址**和**私有地址**：

| 分类 | 范围 |
| --- | --- |
| A 类私有 | 10.0.0.0～10.255.255.255 |
| B 类私有 | 172.16.0.0～172.31.255.255 |
| C 类私有 | 192.168.0.0～192.168.255.255 |

其它范围的 IP 均为公有地址。

**3.3 子网掩码**

**子网掩码（Subnet mask）**是一种用来指明「一个 IP 地址哪些位是主机所在的子网、哪些位是主机位」的掩码。几个要点：

- 子网掩码不能单独存在，必须结合 IP 地址使用
- 子网掩码唯一的作用：把 IP 地址划分成「网络地址 + 主机地址」两部分
- 子网掩码也是 32 位：对应 IP 网络部分用 1，主机部分用 0
- IP 地址和子网掩码做**逻辑与运算**得到网络地址（0 与任何数都是 0，1 与任何数等于其本身）
- A/B/C 类各有默认子网掩码：A 类 `255.0.0.0`、B 类 `255.255.0.0`、C 类 `255.255.255.0`

![子网掩码划分网络地址与主机地址](https://cdn.nlark.com/yuque/0/2021/png/738210/1636807744070-f4bdb1c1-5bcc-4bec-a861-3b5cfaeee677.png)

**为什么需要子网掩码？** 判断两台计算机是否在同一个网段、能否直接通信。笔记里有个很直观的例子：A 类地址 `100.50.20.2` 和 `100.50.20.3`，掩码 `255.0.0.0`，它们网络 ID 都是 `100.0.0.0`，所以在同一网段、能直接通信；而 `100.50.30.2`、`100.60.30.2` 就和它们不在同一网段：

![子网掩码判断是否同一网段](https://cdn.nlark.com/yuque/0/2021/png/738210/1636808155158-4862aab5-aa42-4923-95b2-786e57a75754.png)

用代码验证「判断两个 IP 是否在同一网络内」（笔记代码完整保留）：

```javascript
// 判断两个IP是否在同一个网络内
const ip1 = '100.50.20.2';
const ip2 = '100.60.30.2';
const mask = '255.0.0.0';
const same = (ip1, ip2, mask) => {
  ip1 = ip1.split('.').map(item => parseInt(item).toString(2).padStart(8, '0')).join('');
  ip2 = ip2.split('.').map(item => parseInt(item).toString(2).padStart(8, '0')).join('');
  mask = mask.split('.').map(item => parseInt(item).toString(2).padStart(8, '0')).join('');
  return (parseInt(ip1, 2)&parseInt(mask, 2)) === (parseInt(ip2, 2)&parseInt(mask, 2))
}
const result = same(ip1, ip2, mask);
console.log(result) // true
```

> 💬 **面试官**：子网掩码的作用是什么？怎么判断两个 IP 是否在同一网段？
>
> ✅ 标准答案：子网掩码把 IP 地址划分成「网络地址 + 主机地址」两部分。判断同一网段：IP 地址和子网掩码做**按位与**得到网络地址，两个 IP 的网络地址相同就在同一网段、可直连；不同则需要路由转发。
>
> 🎁 加分答案：能说清掩码的二进制形态（网络位全 1、主机位全 0），并能举例子——如 `255.0.0.0` 是 A 类默认掩码，`192.168.1.0/24` 的 `/24` 就是前 24 位为网络位（即 `255.255.255.0`）；还能点出「私有地址不能直接上公网，需要 NAT」——这是理解「为什么家里多台设备共用一个公网 IP」的关键。

### 第 4 站 · 数据链路层：IP 包变成帧

IP 包从网络层下来，到达**数据链路层**。这一层在物理层提供的服务基础上向网络层提供服务，最基本服务是「把源自网络层的数据可靠传输到相邻节点的目标机网络层」。数据链路层把数据组合成**帧（Frame）**，帧是这一层的传输单位。

**4.1 ARP 协议：IP 地址怎么变成 MAC 地址**

网络层用 IP 寻址，但真正在局域网里传输要落到 MAC 地址。**ARP（Address Resolution Protocol，地址解析协议）**就是「根据 IP 地址获取物理（MAC）地址」的协议。

ARP 的工作过程（笔记完整流程）：

- 主机 A 和 B 在同一网段，A 要向 B 发信息
- A 先查自己的 ARP 表，若找到 B 的 MAC 地址，直接用它对 IP 包做帧封装发送
- 若找不到，A 缓存该数据报文，**广播**一个 ARP 请求（目标 MAC 为全 0，目标 IP 为 B 的 IP），网段上所有主机都能收到，但只有被请求的主机（B）处理
- B 比较自己的 IP 和请求中的目标 IP，相同则：把 A 的 IP 和 MAC 存入自己的 ARP 表，然后**单播**回 ARP 响应（含自己的 MAC）
- A 收到响应后，把 B 的 MAC 加入自己的 ARP 表，用于后续报文转发

ARP 报文格式（28 字节请求/应答）：

![ARP 报文格式](https://cdn.nlark.com/yuque/0/2021/png/738210/1636699605806-095a081b-273e-4905-9be5-9055cfc9bd94.png)

| 字段 | 说明 |
| --- | --- |
| 硬件类型 | 发送方想知道的硬件接口类型，以太网为 1 |
| 协议类型 | 要映射的协议地址类型，0x0800 表示 IP 地址 |
| 硬件地址长度 / 协议长度 | 以太网 MAC 为 6 字节，IP 为 4 字节 |
| 操作类型 | ARP 请求为 1，ARP 响应为 2，RARP 请求为 3，RARP 响应为 4 |
| 发送方 MAC / IP 地址 | 发送方设备的硬件地址和 IP |
| 目标 MAC / IP 地址 | 接收方设备的硬件地址和 IP |

ARP 地址解析过程示意图：

![ARP 地址解析过程](https://cdn.nlark.com/yuque/0/2021/png/738210/1636708540947-0e805c90-8c59-4d87-8781-db3d0a131512.png)

**ARP 有个安全隐患**：它建立在「网络中各主机相互信任」的基础上——主机可自主发送 ARP 应答，其他主机收到应答时**不校验真实性**就记入本机 ARP 缓存。攻击者可发送伪造的 ARP 应答，使目标主机把数据发到错误的目的地，这就是 **ARP 欺骗**。

**4.2 以太网与 MAC 地址**

**以太网（Ethernet）**是一种计算机局域网技术，IEEE 802.3 标准制定了它的技术标准。以太网标准拓扑是总线型拓扑，使用 **CSMA/CD**（载波多重访问/碰撞侦测）技术。在以太网上，每个节点有全球唯一的 **48 位地址**——即制造商分配给网卡的 **MAC 地址**，保证所有节点能互相鉴别。

MAC 地址 48 位二进制，通常分 6 段、用 16 进制表示，前 24 位是**供应商标识**、后 24 位是**供应商对网卡的唯一编号**：

![MAC 地址结构（供应商标识 + 唯一编号）](https://cdn.nlark.com/yuque/0/2021/png/738210/1636606924952-50f0e523-8474-4b68-9e06-cfb1cb6f7a1d.png)

**4.3 以太网帧格式**

在以太网链路上的数据包叫**以太帧**：起始是前导码和帧开始符，后面是目的/源 MAC 地址的以太网报头，中间是负载（如 IP 协议数据报），末尾是 32 位冗余校验码（FCS，检验数据是否损坏）：

![以太网帧格式](https://cdn.nlark.com/yuque/0/2021/png/738210/1636607567657-39cf29ec-605f-4ed5-b23f-55bfa79d99c0.png)

以太网帧各字段的详细说明：

![以太网帧各字段说明](https://cdn.nlark.com/yuque/0/2021/png/738210/1636607818374-68261dce-4aea-40b6-8011-3353b9f9b438.png)

| 字段 | 说明 |
| --- | --- |
| 前导符 | 由 1 和 0 交替构成，共 7 字节，用于时钟同步 |
| 帧起始定界符 | 1 字节，表示一个帧的开始 |
| 目的 MAC / 源 MAC | 各 6 字节，标识目的/源 MAC 地址 |
| 长度 / 类型 | 2 字节，表示上层协议类型 |
| 数据 | 负载内容，数据长度为 46～1500 字节 |
| 帧校验序列（FCS） | 4 字节，CRC 校验值 |

**4.4 总线型拓扑与 CSMA/CD**

**总线型拓扑**用单根传输介质作为共享介质，所有计算机通过硬件接口和电缆连到共享总线上。核心问题是「确保多个端用户同时发数据时不冲突」，控制策略就是 **CSMA/CD（载波监听多路访问/冲突检测）**：

![总线型拓扑结构](https://cdn.nlark.com/yuque/0/2021/png/738210/1636605660860-a6714278-914c-43f3-8489-c4a9cc500f68.png)

CSMA/CD 的核心思想（笔记原文）：

- **先听后讲**：信道空闲则发送，信道忙则等待
- **边听边讲**：发送信号时不断检测信道是否碰撞
- **碰撞即停**：检测到冲突就停止发送
- **退避重传**：用二进制指数退避算法计算等待时间后重传
- **多次碰撞**：放弃发送，最多 16 次

冲突检测时，发送站在发送数据的同时监听信道，若监听到干扰信号说明产生冲突，就停止发送，计算退避等待时间（**二进制指数退避算法**），然后用 CSMA 方法继续尝试。

> 💬 **面试官**：CSMA/CD 的核心思想是什么？它解决的是什么问题？
>
> ✅ 标准答案：CSMA/CD（载波监听多路访问/冲突检测）解决总线型拓扑里「多节点共享信道、同时发送会冲突」的问题。核心是「先听后讲、边听边讲、碰撞即停、退避重传」——发送前监听信道是否空闲，发送中检测是否碰撞，碰撞后按二进制指数退避算法计算等待时间重传。
>
> 🎁 加分答案：能点出「为什么交换式以太网出现后 CSMA/CD 不再重要」——总线型是共享介质，多节点真的会「抢同一根线」；交换机是「点到点」的，每个端口独占通道，冲突基本消除（全双工下不再有碰撞）；还能点出 CSMA/CD 是「半双工」时代的机制，全双工以太网无需冲突检测。

### 第 5 站 · 物理层：帧变成比特流

帧到达最底层的**物理层**。计算机传递数据本质是传 0 和 1 的数字，物理层关心的是「**用什么信号表示 0 和 1**」、能否双向通信、连接如何建立/终止。物理层要屏蔽物理设备和传输媒介的差异，为数据链路层提供「在一条物理介质上传送和接收比特流」的能力。

物理层需要解决「数字信号编码」——用何种物理信号表示 0 和 1，两种常见编码：

**非归零编码**：

![非归零编码（高电平表示 0，低电平表示 1）](https://cdn.nlark.com/yuque/0/2021/png/738210/1636603382075-4c6a1870-4b0d-476b-a8d2-ea8e1a83f509.png)

- 优点：编/译码简单
- 缺点：内部不含时钟信号，收/发端同步困难
- 用途：计算机内部，或低速数据通信

**曼彻斯特编码**：

![曼彻斯特编码（自含时钟信号）](https://cdn.nlark.com/yuque/0/2021/png/738210/1636603695353-a52e22e3-ccf1-4fe6-962e-3f3982e42c4c.png)

- 优点：内部自含时钟，收/发端同步容易；抗干扰能力强
- 缺点：编/译码复杂；占用更多带宽（同样波特率下比非归零多占一倍信道带宽）
- 用途：802.3 局域网（以太网）

> 💬 **面试官**：非归零编码和曼彻斯特编码的区别是什么？
>
> ✅ 标准答案：非归零编码用高低电平直接表示 0/1，编解码简单但不含时钟信号、收发端同步困难，用于计算机内部/低速通信；曼彻斯特编码在每个比特中间跳变、自含时钟，同步容易、抗干扰强，但编码复杂、占用带宽翻倍，用于以太网。
>
> 🎁 加分答案：能点出「自含时钟」的含义——曼彻斯特编码靠「每个比特位中间的跳变」自带同步时钟，接收端能从信号里恢复时钟，不需要额外时钟线；而这个问题本质是「如何在无时钟线上同步收发」，是物理层最核心的编码设计考量。

### 第 6 站 · 到达对端：解封装与真实网络环境

数据比特流到达对端后，就是**反向的解封装**过程——从低层到高层逐层拆头：

- 物理层：把电信号转成二进制数据，传给数据链路层
- 数据链路层：拆掉 MAC 头，剩余数据传给上一层
- 网络层：拆掉 IP 头，剩余数据传给上一层
- 传输层：拆掉 TCP 头，把真实数据传给应用层

![接收方从低层到高层解封装](https://cdn.nlark.com/yuque/0/2021/png/738210/1637058225054-99631377-2a54-4e20-a40c-3fdbe009f964.png)

但真实网络环境里，发送方和接收方之间**可能隔着多个硬件中转设备**（交换机、路由器），数据在传输中不断封装、解封装。**每层设备只能处理那一层的数据**：

- **交换机**属于数据链路层（认 MAC 地址）
- **路由器**属于网络层（认 IP 地址）

![真实网络环境中的交换机和路由器](https://cdn.nlark.com/yuque/0/2021/png/738210/1637058809183-b9b2f0b9-e981-483c-828d-6d6c10b36f73.png)

到这里，「一个 TCP 报文段的完整旅程」走完了：**应用层数据 → 传输层加 TCP 头（段）→ 网络层加 IP 头（包）→ 数据链路层加 MAC 头（帧）→ 物理层变比特流 → 经交换机/路由器转发 → 对端逐层拆头还原**。

补一个容易搞混的称谓对照（不同层的数据单元叫法不同）：

| 称谓 | 起点/终点 |
| --- | --- |
| 帧（Frame） | 数据链路层 |
| 包（Packet） | 网络层 |
| 段（Segment） | 传输层 |
| 消息（Message） | 应用层 |

**附录：IP 头服务类型（TOS）的优先级分级**

IP 首部里的服务类型（TOS）字段共 8 位，其中 3 bit 是优先权字段（取值 000-111）、4 bit 是 TOS 子字段、1 bit 未用但必须置 0。3 bit 优先权定义了 8 个优先级（从高到低）：

| 优先级 | 二进制 | 用途 |
| --- | --- | --- |
| Network Control | 111 | 网络控制（路由） |
| Internetwork Control | 110 | 网间控制 |
| Critic | 101 | 语音数据 |
| Flash Override | 100 | 视频会议、视频流 |
| Flash | 011 | 语音控制 |
| Immediate | 010 | 数据业务 |

这个字段在旧标准里叫「服务类型」，但一直没被真正使用；1998 年 IETF 把它改名为「区分服务（Differentiated Services，DS）」，只有在使用区分服务时才起作用。

## 三、工程落地参考

原理讲完，落到「工程落地」时看哪些权威资料：

### 1. TCP 状态机与连接管理（RFC 9293）

RFC 9293 是 TCP 现行规范（取代 RFC 793），权威定义了连接建立（三次握手）和关闭（四次挥手）的完整状态转换图。上文第二节讲的 SYN_SENT → SYN_RCVD → ESTABLISHED → FIN_WAIT_1/2 → CLOSE_WAIT → LAST_ACK → TIME_WAIT → CLOSED 这套状态机，以及「SYN/FIN 各占一个序号」「TIME_WAIT 等 2MSL」这些细节，都以它为准。

### 2. 拥塞控制算法（RFC 5681）

RFC 5681 定义了 TCP Congestion Control——慢启动、拥塞避免、快速重传、快速恢复四个阶段的具体算法，包括 ssthresh 阈值、加法增大/乘法减小的具体规则、3 个重复 ACK 触发快速重传的判定。面试里「拥塞控制四阶段」的标准答案，源头就在这里。

### 3. Node.js `net` 模块（`lib/net.js`）

Node.js 源码里 `lib/net.js` 的 `Socket` 类是对底层 **libuv 的 TCP handle** 的封装。概览级理解：`net.Socket` 把 libuv 的异步 TCP 事件（连接建立、数据到达、关闭）映射成 Node.js 的 EventEmitter 事件（`connect`/`data`/`end`/`close`/`error`），所以上文第 2.1 节说「`socket.on('connect')` 触发时三次握手已经完成」——封装层把协议栈的状态机藏在了事件之下。

## 四、实践演示与验证

原理讲透了，最后动手「把 TCP 看进眼里」。用四个实验把抽象概念落到可观测的现象上。

### 1. Wireshark 抓完整连接，逐帧对照握手/数据/挥手

```bash
# Wireshark 过滤表达式：只看某端口的 TCP 流量
tcp.port == 8080
```

抓一次真实连接（比如访问一个网站或跑上面第 2.1 节的 Node.js 示例），逐帧对照第一节第 6 小节的报文序列：

- **三次握手**：SYN → SYN+ACK → ACK（3 帧）
- **数据传输**：PSH+ACK（带数据）→ ACK（确认）
- **四次挥手**：FIN → ACK → FIN → ACK（4 帧）

重点看每一帧的 **Sequence number** 和 **Acknowledgment number** 如何随数据长度推进，验证 `ack = seq + 数据长度` 的规律。

### 2. `netstat -an` / `ss -s` 观察 TIME_WAIT

```bash
netstat -an | findstr TIME_WAIT      # Windows：统计 TIME_WAIT 数量
ss -s                                 # Linux：汇总各状态 socket 数量
```

主动关闭方（短连接场景里通常是频繁发请求又关闭的一方）会积累 TIME_WAIT。跑一个「每 100ms 建一次 TCP 连接、收到响应就关」的脚本，观察 TIME_WAIT 数量的攀升——这就是「短连接频繁创建销毁」的直接证据，生产上靠 keep-alive 复用连接缓解。

### 3. `ss -tin` 看窗口参数，把流量控制/拥塞控制落地

```bash
ss -tin   # Linux：查看每个 TCP 连接的传输层参数
```

重点看两个字段：

- **`rcv_wnd`（接收窗口）**：对应「滑动窗口流量控制」——接收方通告的接收窗口大小
- **`cwnd`（拥塞窗口）**：对应「拥塞控制」——发送方当前维护的拥塞窗口大小

亲眼看到这两个值，你就能理解「流量控制（接收方报的 rcv_wnd）和拥塞控制（发送方调的 cwnd）是两个独立参数、共同决定发送量」——抽象的 `min(接收窗口, 拥塞窗口)` 变成了可观测的内核参数。

### 4. Node.js 跑通 net/dgram，观察背压

跑第 2.1 节的 TCP 示例和第 2.11 节的背压示例，观察：

- `socket.on('connect')` 触发时机（三次握手完成后）
- `socket.write()` 返回 `false` 的时机（接收方处理不过来时）
- `dgram` 的 `message` 回调里 `rinfo` 带来源地址（UDP 无连接的体现）

| UDP vs TCP | UDP 无连接/不可靠/无拥塞控制；DNS/QUIC/实时音视频选 UDP | ⭐⭐⭐ 必考 |
| IP/ARP/子网 | IP 定位主机、MAC 定位网卡、子网掩码划分网段 | ⭐⭐ 高频 |

> 💡 记住这条主线：**一个 TCP 报文段从应用层诞生，在传输层装上 TCP 头（序列号、确认号、窗口），在网络层装上 IP 头（IP 地址、TTL），在数据链路层装上 MAC 头（ARP 解析 MAC），在物理层变成比特流发出去，到对端再逐层拆回来。TCP 的可靠靠「序列号 + 确认 + 重传」三件套，效率靠「滑动窗口流量控制（保护接收方）+ 拥塞控制（保护网络）」，连接的建立与断开是「三次握手 + 四次挥手」的状态机**。把这条线串起来，TCP 的所有面试题都能从原理推到答案。

## 💡 面试核心问

- **为什么建立连接需要三次握手，两次不够吗？**（两次时服务端发 SYN+ACK 就认为建立，无法确认 ACK 送达、无法区分历史重复连接，且被 SYN 洪水攻击利用；第三次 ACK 让服务端确认客户端真的收到）
- **为什么断开连接需要四次挥手，而不是像建立连接一样三次？**（TCP 全双工、两方向独立关闭；被动方收到 FIN 后可能还有数据没发完，ACK 和 FIN 分开发送，不能像握手的 SYN+ACK 那样合并）
- **TCP 可靠传输依赖哪几个基础机制？它们分别是干什么的？**（序列号编号排序、确认应答确认已收、超时重传补丢，合起来实现不丢/不重/不乱序）
- **TIME_WAIT 状态存在的意义是什么？生产环境大量 TIME_WAIT 堆积说明什么问题？**（主动关闭方等 2MSL，防最后 ACK 丢失 + 防旧报文串扰；大量堆积说明短连接频繁，用 keep-alive 缓解；若是 CLOSE_WAIT 堆积则是代码 bug 连接泄漏）
- **拥塞控制分哪几个阶段？慢启动和拥塞避免的区别是什么？**（慢启动/拥塞避免/快速重传/快速恢复；慢启动指数增长、拥塞避免线性增长，分界是 ssthresh 阈值）
- **滑动窗口的流量控制和拥塞控制是同一个机制吗？分别保护的是谁？**（不是；流量控制保护接收方（Window Size 通告），拥塞控制保护网络（cwnd 自适应），发送量 = min(接收窗口, 拥塞窗口)）
- **UDP 和 TCP 的本质区别是什么？为什么 DNS、QUIC、实时音视频都选 UDP？**（UDP 无连接/不可靠/无拥塞控制；DNS 小查询一次往返、QUIC 摆脱队头阻塞、实时音视频宁可丢帧不卡顿）
