# 03 — 前端接流式：接得上，更要接得住

对应文章：第 03 篇《前端接流式：接得上，更要接得住》

## 要验证什么

第 02 篇把流从服务端推出来了，这一篇看浏览器怎么「接住」它。代码只回答三个问题：

1. **为什么 `EventSource` 不够用**？它只能 GET、不能带 `Authorization` 头、不能发 JSON body——AI 对话几乎一律用 `fetch` + `ReadableStream.getReader()`。
2. **中文为什么偶尔乱成 `�`**？一个汉字 UTF-8 编码 3 字节，网络分片可能把它切在中间，`TextDecoder` 不开 `{ stream: true }` 就把残片替换成 `�`。
3. **为什么长回答会卡成幻灯片**？每个 delta 都改一次 DOM，渲染次数 = delta 数；用 `buffer + requestAnimationFrame` 收敛到帧数，差一个数量级。

## 怎么跑

```bash
# 仓库根目录
nvm use 22
pnpm --filter @medai/labs p2-client            # 终端 1：起实验页
pnpm --filter @medai/labs p2-client-measure    # 终端 2（可选）：命令行复现实验 A 的数字
```

然后浏览器打开 http://127.0.0.1:3004/

需要 `.env.local` 里配 `DEEPSEEK_API_KEY`，缺 key 时给中文提示并退出。

## 看到什么算成功

### 实验 A：两种渲染策略

点「策略 A（naive）」「策略 B（rAF 批量）」各跑一次，看表格三列。

本机实测（2026-11-09，`p2-client-measure` 跑 3 次取区间，同一道题）：

| 指标 | 实测区间 |
|---|---|
| 首字节时间 | 111 ~ 410 ms |
| 总耗时 | 2842 ~ 3117 ms |
| delta 数 | 286 ~ 363 |
| 策略 A 渲染次数 | = delta 数（构造上必然） |
| 策略 B 渲染次数 | 91 ~ 101 |
| A / B 倍数 | 2.8 ~ 3.6 倍 |

**同一个流、同样的 delta 数，写 DOM 的次数差约 3 倍**——策略 A 每收到一小段就写一次，策略 B 攒到下一帧再写。

> 为什么倍数只有 3 倍而不是 20 倍？因为 DeepSeek 的 delta 到达速率约 130~150 个/秒，而 60fps 每秒只有 60 帧，理论上限就是约 2.4 倍；实测 3 倍左右是因为首帧前的等待和 TCP 攒批让部分 delta 挤进同一帧。**渲染策略的收益上限由「产出速率 ÷ 帧率」决定**，这一点文章会讲。

`p2-client-measure` 把这两个数字用同一份真实流算出来，不依赖浏览器截图，人人可复跑。

### 实验 B：字节边界

点「跑字节边界对照」，看表格：

- `TextDecoder()`（不开 stream）→ 12 字节解出 10 个 `�`，一个字都没还原
- `TextDecoder({stream:true})` → 正确拼回「阿莫西林」4 个字

**同一个字节序列，只差一个 `{ stream: true }`，结果从全乱码变成完全正确。**

### 实验 C：abort 传播

点「开始生成」，生成途中点「停止生成」，同时看三处：

1. 按钮变灰（前端停了）
2. 服务端终端打印「🛑 客户端主动断开，上游请求被取消」
3. DevTools Network 里 `/sse` 请求状态变 `(canceled)`

三处同时停下，才是「停止生成 = 停止计费」。对照：只把界面清空、不断开连接的写法，服务端会继续跑完整个回答。

## 故意留下的两处「不完美」

| 没做的事 | 为什么 | 留在哪 |
|---|---|---|
| 不用 React / `useChat` | 本篇学「流 + 字节边界 + 渲染调度」，不是「React 状态管理」，原生 DOM + rAF 才能把「渲染次数」量出来 | 阶段六 |
| 断线重连不补发 | 需要消息历史 | 阶段三 |

## 预算

每点一次「开始」就是一次真实调用，约 ¥0.01；做完全部观察（A 2 次 + 测量 1 次 + C 1 次 ≈ 4 次）约 ¥0.04，远低于本篇 ¥2 上限。
