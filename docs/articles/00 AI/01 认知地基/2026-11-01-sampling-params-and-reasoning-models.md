# 采样参数与推理模型：temperature 到底在调什么

> 它调的不是「创造力」，是「从概率分布里怎么抽签」。

---

## 🎯 这篇文章解决什么问题

上一篇收尾留了一句话：面对模型的能力边界，先想着换输入，而不是换模型。

这句话还有一个前提没交代。**你以为的「同一个输入」，在模型那边并不是同一个输入。**

做一个用药提醒功能，同一个 prompt 连问两次：「阿莫西林胶囊需空腹服用，写成一句 30 字内的提醒」。第一次给你「请空腹服用阿莫西林胶囊」。第二次给你「饭前半小时服用效果更好，请遵医嘱」。

两条都像人写的。但第二条把「空腹」变成了「饭前半小时」，在医疗场景里这是两件事。

这时候绝大多数人的第一反应是「模型不稳定」。然后去查，查到一堆名词：temperature、Top-p、Top-k、推理模型。文档里写着 0 到 2，写着「越大越有创造性」，你把它调成 0，跑了十次，有九次一致，第十次还是不一样。

于是你更困惑了：**它不是调到 0 了吗？**

这篇文章要解决四件事：

- 模型每一步到底在做什么，为什么会有「随机」这回事
- temperature / Top-k / Top-p 各自改的是什么，为什么容易搞混
- temperature=0 为什么仍然不保证一致——以及这件事能不能修
- 推理模型贵在哪，什么时候开它是浪费

每一段照旧配「面试官会怎么问」，以及标准答案和加分答案。最后一部分会讲一个 2026 年才出现的坑：**你调的参数可能根本没生效**。

## 🔍 认知切入：两条都像人写的回答

先把问题摆正。

不是「模型答错了」，是「模型答对了两次，但两次不完全一样」。这两种情况的处理方式完全不同：

| 你以为的问题 | 实际的问题 |
|---|---|
| 模型不稳定，需要修 | 模型本来就在随机抽签，这是设计而非缺陷 |
| 调低温度就能一致 | 温度只控制抽签倾向，不控制「一定抽到同一个」 |
| 参数调对就安全了 | 医疗场景的确定性要靠日志与人工，不靠参数 |

这里有个很关键的分野，很多人一辈子没分清：

**「随机」有两个来源，一个你能调，一个你调不了。**

- 第一个是**采样随机**：模型算出概率分布，然后按分布抽一个词。这个你有旋钮。
- 第二个是**基础设施随机**：同一份权重、同一个输入、temperature=0，跑在服务器上仍然可能每次略有差别。这个你没有旋钮。

绝大多数「我调了温度还是不一样」的困惑，都源于把第二类当成第一类使劲。后面会分别讲清。

先看第一步：模型在「抽」什么。

## ⚙️ 原理讲透：从概率分布到具体那个词

### 模型每步吐出的不是一个词，是一整条分布

回到第 00 篇那个定义：自回归生成——给定前文，算下一个 token 的概率分布。

这里有个容易被跳过的细节：**模型输出的不是「一个词」，是「词表里每个词各有多大可能」**。

以「阿莫西林胶囊需」这半句为例，模型这一步可能给出这样一组数：

```text
token          概率
空腹           0.62
饭前           0.11
饭后           0.08
餐前           0.05
温水           0.03
...（其余几万个 token 分摊剩下的 0.11）
```

这几万个数加起来等于 1。模型到这一步就交差了——**选哪个，是后面「采样」这一步的事。**

采样就是从这条分布里抽一个出来，接到句子末尾，然后把整段重新送进模型，再算下一条分布。

![每一步都按概率随机挑词：选中一个接上去，再重新算一遍分布重新挑——所以同一条输入，两次生成的路径可能完全不同](https://huggingface.co/blog/assets/02_how-to-generate/sampling_search.png)

看这张图的时候注意一件事：**每走一步都在重算**。它不是「先想好整句再吐出来」，是「一步一抽，抽完立刻影响下一步」。所以哪怕只差一个 token，后面的路可能完全不同——这就是「模型不稳定」的全部物理来源。

那为什么不直接每次选概率最高的那个？因为那样生成的东西会变得极其呆板、重复，同一句话反复出现，还容易陷入「反复说同一句」的死循环。**随机性是这几代模型的性能来源，不是它的 bug。**

我们做的所有参数调节，本质都是在回答同一个问题：**这条分布，我允许抽得多自由？**

> 💬 **面试官**：模型输出是确定性的还是随机的？
>
> ✅ **标准答案**：分两段看。前向计算（输入 → logits）在固定权重与固定输入下是确定性的；但生成时会在 softmax 得到的分布上**采样**，这一步是随机的。所以整个推理过程默认是随机的，温度等参数只是改变了这个随机性的形状与范围。
>
> 🎁 **加分答案**：再补一层——「确定性」这个词在生产环境里要拆成三件事：**同输入同权重的前向是确定的**、**采样是可随机可贪心的**、**服务端的数值实现是不可保证的**（浮点非结合性 + 批处理形状随并发变化）。第三项才是「temperature=0 也不复现」的真正原因，也只有在理解这三层之后，你才知道该在哪里投入工程成本。

🔧 **真实场景**：做一个「药品信息抽取」的批处理任务，一次几千条。如果靠 temperature=0 保证结果可复现，你会发现重跑一次总有几十条对不上。正确做法是**把每次的原始输出落库**，差异比对以库里的记录为准，而不是「重新跑一遍看是否一致」。

### temperature：改分布的形状

这是被误解最深的一个参数。

很多人以为它叫「随机性开关」，越大越乱。更准确的描述是：**它是一把把分布削尖或压平的尺子。**

数学上只做了一件事：把每个 logit 除以 T，再做 softmax。

```text
p_i = exp(z_i / T) / Σ exp(z_j / T)
```

T 越小，除法把差距放大得越狠，softmax 之后高概率词更接近 1；T 越大，差距被压平，所有词的概率趋于平均。

![同一个模型、同一步的两条分布：温度一变形状就变——尖的那条让高频词几乎必选，平的那条让冷门词也拿得到票](https://huggingface.co/blog/assets/02_how-to-generate/sampling_search_with_temp.png)

所以就出现了这三个行为：

- **T 接近 0**：分布削成一根针，最高概率那个词拿走几乎全部权重 → 实际效果等同于「永远选 top-1」，也就是贪心解码。
- **T = 1**：模型原始分布，不做任何改变。
- **T > 1**：分布被压平，原本排第五的词也有明显机会 → 输出发散、偶尔离谱。

**这里有个反直觉的点值得记住：温度不是「往结果里加随机噪声」。它是先改分布，再按新分布抽签。** 这个区别决定了一件事——低温不是「少一点随机」，而是「几乎只抽 top-1」；它没有消除随机，只是把随机几乎压缩到零。

> 💬 **面试官**：temperature 到底改了什么？
>
> ✅ **标准答案**：它缩放 logits（除以 T）后再做 softmax，改变的是概率分布的**形状**。T 小于 1 让分布更尖锐、高概率词几乎必选；T 大于 1 让分布更平坦、低概率词也有机会。它不是加噪声，是改分布。
>
> 🎁 **加分答案**：要强调一个推论——**temperature 只影响「怎么从分布里抽」，不影响「分布本身准不准」**。如果模型这一步根本没算对（比如它压根不知道这个药的剂量），把温度调到 0 只会让它**稳定地**给出那个错误答案。稳定 ≠ 正确，这是两个正交的维度。很多团队调完温度发现「效果没变好」就是这个原因：问题出在知识或检索，不在采样。

🔧 **真实场景**：医疗内容里最典型的温度事故不是「胡编」，是**表述漂移**。「空腹」漂成「饭前」，「不超过 3 天」漂成「3 到 5 天」。这类偏移在语义上很接近，人眼扫过去不会警觉，但落到说明书对照上就是错。所以医疗场景的温度策略是**默认压最低 + 关键字段用规则硬校验**，两条一起上，缺一不可。

### Top-k 与 Top-p：改候选集的范围

温度改的是分布形状。还有另一类参数，改的是**「谁有资格参与抽签」**。

**Top-k：只留概率最高的 k 个。**

```text
1. 把词表按概率排序
2. 砍掉第 k 个之后的所有 token
3. 剩下的重新归一化（让它们加起来等于 1）
4. 从这个小集合里抽
```

![Top-k 的做法是每步只保留概率最高的 k 个候选（图里 k=6），其余全部丢掉、剩下的重新归一化后再抽](https://huggingface.co/blog/assets/02_how-to-generate/top_k_sampling.png)

Top-k 的问题在于 **k 是写死的**。而分布的形状是每步都在变的：

- 分布很尖的时候（比如「阿莫西林」后面必然接「胶囊」），前 3 个词就占了 99.9%，硬留 40 个候选等于**把一堆垃圾词放进了抽签池**。
- 分布很平的时候（比如要选一个形容词），前 40 个词每个都只有一点点概率，砍掉第 41 个之后等于**扔掉了合理的候选**。

固定 k 无法同时适配这两种情况。这就是 Top-p 出现的原因。

**Top-p（核采样）：只留「累积概率达到 p」的最小集合。**

不是按个数切，是按概率质量切：从高到低累加，加到刚好超过 p（比如 0.92）为止，后面的全部砍掉。

![Top-p 按累积概率划界（图里 p=0.92），候选集大小随分布自适应：分布尖时只留两三个词，分布平时能留十几个](https://huggingface.co/blog/assets/02_how-to-generate/top_p_sampling.png)

对比一下就明白它为什么取代了 Top-k：

| 分布形态 | Top-k（k=40）留下 | Top-p（p=0.92）留下 |
|---|---|---|
| 极尖（几乎确定） | 40 个，其中 39 个是垃圾 | 2 到 3 个，正好 |
| 中等 | 40 个，大致合理 | 8 到 15 个 |
| 极平（高度不确定） | 40 个，砍掉了合理候选 | 30 个以上，自适应放宽 |

**候选集大小跟着分布走**，这就是自适应。所以现在几乎所有厂商的默认推荐都是「temperature + Top-p」，Top-k 保留但很少需要单独调。

> 💬 **面试官**：Top-p 和 Top-k 有什么区别？为什么现在更常用 Top-p？
>
> ✅ **标准答案**：两者都改候选集，Top-k 按**个数**截断，Top-p 按**累积概率质量**截断。Top-p 的候选集大小能随分布形状自适应——分布尖时自动收窄、分布平时自动放宽，而 Top-k 的 k 固定，无法同时适配两种形态，所以 Top-p 成了主流默认。
>
> 🎁 **加分答案**：补一句工程上的取舍——Top-p 的自适应也有代价，**它的行为不可预测**。同样设 p=0.92，在可复现性要求高的场景里，不同输入会导致候选集大小差别很大，这使得「为什么这次输出变了」的归因更难。所以医疗这类要求可审计的场景，更稳的做法是**把温度压到极低 + 关键输出做结构化约束**，而不是指望 Top-p 帮你收敛。

### 三者怎么叠加（最容易搞混的地方）

面试常问「它们有什么区别」，但真正拉开差距的是「它们怎么配合」。

执行顺序是固定的：

```text
logits
  ↓ 除以 T（temperature）        ← 改形状
  ↓ 按 Top-k 砍掉尾部            ← 改范围
  ↓ 按 Top-p 再砍一次            ← 改范围
  ↓ 重新归一化
  ↓ 采样
```

一句话概括：

- **temperature 改形状**（每个词之间相对可能性怎么变）
- **Top-k / Top-p 改范围**（谁有资格参与）
- 两者可以叠加，叠加时**先改形状，再定范围**

叠加的效果会相乘，这是很多线上事故的根源。设 temperature=1.2 同时 Top-p=0.95，实际的有效随机性比你以为的大得多——因为温度先把分布压平了，Top-p 划界时要覆盖更多词才够 0.95，候选集反而变大。

反过来说，**低温 + 低 Top-p 是双重收紧**。医疗场景把 temperature 压到 0.1、Top-p 压到 0.5，效果是「几乎只抽 top-1，第二名的词基本没机会」。这时候你其实已经接近贪心解码了，再继续调下去收益极小——**该去修别的环节了。**

### 按任务设参数：一张能直接抄的表

| 任务类型 | temperature | 说明 |
|---|---|---|
| 事实问答 / 抽取 / 结构化输出 | 0 ~ 0.2 | 要稳定、要可解析，几乎不要多样性 |
| 客服对话 / 文案改写 | 0.5 ~ 0.7 | 既不能呆板，也不能跑偏 |
| 创意发散 / 起标题 / 头脑风暴 | 0.8 ~ 1.0 | 要的就是多样性，跑偏可以人工筛 |
| 多步推理 / 数学 | 0 ~ 0.3 | 中间步骤一步错，全盘错 |

最后加一条医疗专用的：**默认压到最低档，用确定性换可复现。**

注意这个选择不是「因为医疗要求准确所以温度低」，逻辑反了。正确理解是：**温度低不提高准确性，它只是让同一个错误变得可复现。** 可复现的价值在于——你能定位它、能复现它、能用测试集回归它。医疗场景真正需要的是这个，而不是「温度低所以更对」。

> 💬 **面试官**：你们线上医疗问答的温度怎么设的？为什么？
>
> ✅ **标准答案**：默认设在 0 到 0.2 之间，接近贪心解码。理由不是「低温更准确」，而是「低温让输出可复现」——同样的输入得到同样的输出，才能用固定测试集做回归、才能定位线上问题、才能在合规审计时复核。
>
> 🎁 **加分答案**：要主动指出这条路的边界——**低温只降低采样随机，不消除输出随机**。真正让「同一个问题给出不同关键结论」这件事收敛的，是三层：模型层（低温 + 固定模型版本）、网关层（固定 prompt 模板 + 缓存）、评估层（用固定测试集监控漂移）。只调温度就想拿到确定性，是把工程问题当成参数问题。

### temperature=0 为什么不等于完全确定

到这一节，前面埋的伏笔要收了。

temperature 设成 0，理论上等价于「永远选概率最高的那个 token」。那为什么实践里还是会不一致？

三个原因，一层比一层难修：

**第一，浮点运算不满足结合律。** `(a + b) + c` 和 `a + (b + c)` 在浮点世界里可能差最后几位。而 softmax 涉及几万个数求和，只是把这个误差放大到足以改变 top-1 的结果。

**第二，服务端的批大小随并发变化。** 这是最容易被忽略的一环。GPU 为了吞吐会把多个用户请求打包成一个 batch 一起算，而 **batch 形状会改变某些算子的归约顺序**（分块大小不同，加法顺序就不同），于是同一个请求在低峰和高峰算出来的 logits 末位不同。

反过来推一遍你就明白了：

```text
并发低 → batch 里只有你一条 → 一种归约顺序
并发高 → batch 里有别人几十条 → 另一种归约顺序
        → logits 末位略有差异
        → 若 top-1 与前二名极度接近，就可能翻转
```

**第三，模型本身在变。** 厂商会静默更新权重、调整推理引擎、切换量化版本。这不是「不稳定」，是「版本变了」——而你从 API 返回里看不到版本号。

所以正确的预期是：

- **temperature=0 能显著提高一致性，但不能保证逐字复现。**
- 逐字复现要自己造：把原始输入输出落库、记模型版本、用固定测试集做回归。
- 「完全可复现」这件事在闭源 API 上基本做不到，在自部署场景下通过固定 batch 配置和固定算子是可以逼近的（阶段八会展开）。

> 💬 **面试官**：temperature 设成 0，同一个问题是不是每次结果都一样？
>
> ✅ **标准答案**：不一定。temperature=0 只是让采样退化为贪心（总选 top-1），但前向计算本身不保证逐 bit 一致——浮点非结合性、服务端批大小随并发变化、底层算子实现差异都会让 logits 末位不同，若 top-1 与前二名概率极接近就可能翻转。此外模型版本静默更新也会改变输出。
>
> 🎁 **加分答案**：要能说出「怎么测」：把同一请求发 N 次，统计输出差异率；再分别在高并发与低并发下跑，对比差异率是否上升——如果上升，就证明是批处理导致的数值不稳定，而不是采样问题。这个实验本身比结论更有价值，因为它把「玄学不稳定」变成了可归因的现象。至于怎么真正拿到确定性，答案是**自部署 + 固定算子配置**，闭源 API 只能逼近不能保证。

### 推理模型：先写草稿再回答

讲完采样，另一半是「模型本身」。

推理模型（o1、DeepSeek-R1 系）不是「更聪明的普通模型」。这个说法不准，往下想会全错。

准确的说法是：**它把「想」变成了一次显式的生成过程。**

普通模型面对一道题，直接开始往外吐答案 token。推理模型面对同一道题，先产出一大段**推理 token**——试错、退回来、换个路子、验算，然后才吐最终答案。

![同一个问题的两种回答方式：左边普通模型直接给结论，右边推理模型把中间计算摊开——差别不在结论对错，在「先算后答」](https://substackcdn.com/image/fetch/$s_!8oZo!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Ff2987079-25f4-45fb-a020-1ac936ed16cb_1424x820.png)

看这张图的时候注意两件事，都很重要：

**第一，那段落草稿是计费的。** 它和答案一样是输出 token，按输出单价算。而输出单价本来就是输入的好几倍。所以在推理模型上，「想得久」直接等于「贵」。

**第二，草稿不是给人看的。** OpenAI 的 o1 系列把推理过程隐藏，只返回摘要；DeepSeek-R1 早期把 `reasoning_content` 直接给你。但无论给不给，它都真实发生了、真实计费了。

这个「用长度换准确率」的代价，在一张图里看得最清楚：

![训练推进时 AIME 2024 的准确率从 15.6% 升到 71%，同一张图里每道题的输出长度也在同步暴涨——这条曲线说明的正是「准确率是拿 token 换的」](https://www.philschmid.de/static/blog/deepseek-r1/r1-zero.png)

横轴是训练步数，两条线一起往上走：一条是基准成绩，一条是平均输出长度。**这两条线同向，不是巧合。** 模型学会的第一件事不是「更聪明」，是「先多写一点中间步骤」。

这就推出一条很实用的判断标准：

- **多步逻辑 / 数学 / 需要反复权衡的任务** → 开推理，它真的会变好。
- **简单抽取、分类、一问一答** → 开推理是纯浪费。它会把「阿莫西林属于青霉素类」这件事想上 300 个 token，答案一字不差，账单翻十倍。

> 💬 **面试官**：推理模型和普通模型的本质区别是什么？
>
> ✅ **标准答案**：不是参数量或「更聪明」，而是**推理被显式化为生成**。推理模型在给答案之前先生成一大段推理 token，用更多的计算换取多步任务上的准确率。代价是延迟和成本——推理 token 按输出计费，通常比普通回答贵数倍。
>
> 🎁 **加分答案**：补一层工程判断——**「该不该用推理模型」不是一个技术偏好题，是一个成本结构题**。你真正要问的是：这个任务里错误答案的成本，是否高过思考 token 的成本？儿童剂量算错要赔命，那多想 2000 token 完全值得；药品分类归错、有后续人工复核兜着，那开推理就是白烧钱。这也是后面第 04 篇要用「每次成本 × 日均量」来做的选型判断。

🔧 **真实场景**：把「儿童剂量折算 + 是否超过成人上限」这种多步题交给普通模型，它经常在第二步就错——忘了先判每日最大剂量、或者直接把 mg 当 g。这类题的错不是「知识不够」，是「算不完」。推理模型能救，但它的思考 token 会计入账单，所以产品上的正确做法是**按任务分级**：简单问用便宜模型，涉及剂量计算、相互作用判断才切到推理模型。这就是第 04 篇要算的「模型路由」。

### 2026 年的新情况：推理成了开关，参数会互相覆盖

这一节是这篇文章最值得你带走的工程细节，因为它是 2026 年才出现的形态。

早期要「用推理」，你得换一个模型名（`deepseek-reasoner`、`o1`）。现在主流做法是把推理做成**同一个模型的开关**。

以 DeepSeek 当前的 API 为例（其他厂商结构类似，但具体规则各不相同，必须查自己的文档）：

```typescript
// 同一个模型，两种模式
{
  model: 'deepseek-flash',
  thinking: { type: 'enabled' },   // 或 'disabled'
  reasoning_effort: 'high',        // none / low / high / max，默认 high
}
```

看起来只是多了一个参数。但它带来了一整套**参数互相覆盖**的规则，而文档里这些规则往往埋得很深：

| 参数 | 思考模式下 | 非思考模式下 |
|---|---|---|
| `temperature` | 传了不报错，但**不生效** | 生效，0 到 2 |
| `top_p`（flash） | 只在 0.95 到 1.0 生效，低于 0.95 按 0.95 处理 | **恒为 1.0，传入值被忽略** |
| `frequency_penalty` / `presence_penalty` | 已废弃，接受但无效果 | 同左 |

看到第一行了吗。**思考模式是默认开启的，而思考模式会忽略 temperature。**

这意味着什么？意味着一个 2026 年最常见的事故是：

```text
开发者：我把 temperature 从 0 调到 0.3、0.7、1.0，跑了一遍……
结果：四档输出几乎一模一样。
结论：这个模型的温度参数没用。
真相：四档全在思考模式下跑，temperature 从头到尾被忽略。
```

这不是模型的错，是**参数生效的前提没确认**。所以调参之前的第一件事，永远是问自己一句：**我现在是不是在思考模式里？**

还有一层更细的坑：注意 `top_p` 那一行——在非思考模式下它**恒为 1.0，传值被忽略**。也就是说，如果你习惯用「temperature 0.2 + top_p 0.5」这套收紧组合，在很多当前实现里，后半段根本没起作用。你以为做了双重收紧，实际只收紧了一层。

> 💬 **面试官**：你线上调 temperature 没效果，怎么排查？
>
> ✅ **标准答案**：先确认参数是否真的生效，而不是先怀疑模型。排查顺序是：① 是否处在思考 / 推理模式（很多实现会忽略 temperature）；② 该参数在这个模型上是否有取值范围限制或被固定值覆盖；③ 请求是否命中了网关层的默认值或缓存；④ 是否在比对不同模型版本。参数「传了但不生效」是最常见的一种，且不报错，只能靠查文档和打印实际请求来发现。
>
> 🎁 **加分答案**：可以说出一条更硬的工程习惯——**把「实际生效的参数」记进日志，而不是记录「你传的参数」**。两者在参数被覆盖时完全不同，而线上事故的归因几乎全靠这份日志。更深一层的认知是：**推理模式与采样参数是两套互相排斥的控制体系**——前者用「想多久」控制质量，后者用「怎么抽签」控制多样性。当推理开启时，厂商的隐含判断是「这一步已经不该靠采样来调节了」，所以直接关掉采样参数。

🔧 **真实场景**：把「同一问题两次答案不同」当成 bug 提给模型厂商，很可能被回一句「这是预期行为」。真正该做的是**在自己这侧建立可观测性**：记录每次请求的模型名 + 实际生效参数 + 是否思考模式 + 输出原文。有了这份日志，「为什么这次不一样」就从玄学变成了可查询的事实。

## 🧪 动手实验：两次对照

> **说明**：下面是脚本的**运行形态示意**，其中的输出内容与各项数值均为示意值，真实数值以你本机运行为准。脚本已就绪：`labs/phase1-cognition/03-params/`。

这个实验的设计目标有两个：**把「温度到底调了什么」跑成你自己的数据**，以及**亲眼看到「思考模式会忽略 temperature」这个坑**。

```bash
# 在仓库根目录
pnpm install
cp .env.local.example .env.local    # 需要 DEEPSEEK_API_KEY
pnpm --filter @medai/labs params
```

20 次短调用 + 4 次对照调用，约 ¥2–3，脚本启动会先打印预估。

### 实验 A：temperature 扫描

固定一个 prompt，temperature 取 0 / 0.3 / 0.7 / 1.0，每档跑 5 次：

```typescript
const PROMPT_A = '给「阿莫西林胶囊需空腹服用」这条用药提醒写一句话版本，不超过 30 字。'

for (const t of [0, 0.3, 0.7, 1.0]) {
  for (let i = 0; i < 5; i++) {
    // 👈 关键：必须关掉思考模式，否则 temperature 不生效，四档输出会几乎一样
    await call(apiKey, false, PROMPT_A, t)
  }
}
```

注意那行注释。**如果不关思考模式，这个实验会给你一个完全错误的结论**——四档输出几乎相同，你会以为「温度没用」。这正是上一节讲的内容，实验把它变成你亲手踩过的坑。

示意结果：

```text
temperature  不同条数  平均字数  首条示例
0            1/5        22        空腹服用阿莫西林胶囊，疗效更佳
0.3          2/5        23        阿莫西林胶囊请空腹服用，避免效果打折
0.7          5/5        25        注意：阿莫西林胶囊宜空腹服用
1.0          5/5        27        饭后半小时服用阿莫西林胶囊效果更好  ← 偏移
```

### 实验 B：思考关闭 vs 思考开启

同一道多步剂量计算题，同一模型，只切模式。

示意结果（多步题）：

```text
模式        耗时    输入 token  输出 token  思考 token  本次成本
思考关闭    2.1s    148         86          ≈0          ¥0.00049
思考开启    14.7s   148         1,240       1,050       ¥0.00511
```

同一道**简单题**（「阿莫西林属于哪一类抗生素」）再跑一遍：

```text
模式        耗时    输入 token  输出 token  思考 token  本次成本
思考关闭    1.2s    32          18          ≈0          ¥0.00010
思考开启    6.4s    32          310         260         ¥0.00127
```

### 四条读数

**第一，0 档接近一致，但不是绝对一致。**

五次里四次一模一样，那次例外通常只是句末多了个「请」。**这就是「温度低 ≠ 完全确定」的直观形态**：你看到的是几乎一致，不是完全一致。

**第二，1.0 档出现的不只是措辞变化，是事实偏移。**

看最后一行的那句「饭后半小时服用」。它读起来比另外三条更「贴心」，但它把**空腹**说成了**饭后**。

这是这篇最该记住的一条读数：**高温度不是让文字更花哨，是让低概率的语义分支有机会被选中。** 而在医疗内容里，低概率分支往往就是错的那些。所以「温度高一点让文案自然些」这种想法，在医疗场景里等同于「允许它偶尔改一下事实」。

**第三，思考模式的成本不是贵一点，是贵一个量级。**

同一道题：耗时从 2.1s 到 14.7s（7 倍），成本从 ¥0.00049 到 ¥0.00511（10 倍）。这十倍的构成很清楚——思考 token 1050 个，全部按输出单价计费，而输出单价是输入的 4 倍。

这条读数直接决定了产品设计：**推理模式不能全局开**。一千次问诊里可能只有 50 次真的需要它，剩下的开就是在替简单问题付推理的价。

**第四，简单题上，两个模式几乎拉不开差距。**

第二张表里，思考模式为一道「阿莫西林属于青霉素类」的题花掉了 260 个思考 token，答案和关闭时一字不差，成本是十倍。

**这就是「什么时候不该用推理模型」的实证。** 判据不是题目看起来难不难，是**这道题有没有「想错了还能自己发现」的空间**。一道知识题没有，一道多步计算题有——后者才值得付思考的钱。

> 💬 **面试官**：你怎么证明「加约束 / 调参数 / 换模式」真的起作用了？
>
> ✅ **标准答案**：做单变量对照——固定 prompt、固定模型、固定判定规则，只改变一个变量（温度档位 / 思考开关），每组跑多次，统计「输出多样性与事实偏移率」两个指标。整体平均会掩盖问题，必须按档位分开看。
>
> 🎁 **加分答案**：这个实验里最值钱的一步是**先确认参数真的生效**。实验 A 如果忘了关思考模式，得到的四档数据全是一个假阳性结论。所以任何参数实验的第一条应该是**「噪声实验」**：把参数设成差异极大的两档，确认输出确实不同，再去做细粒度对比。跳过这一步，后面所有结论都建立在沙子上——这也是线上调参最常见的返工原因。

🔧 **真实场景**：这套方法直接迁移到线上。上线前用固定测试集跑「温度 0 vs 0.7」两版，统计的指标不是「准确率」，而是三条：**关键字段偏移率**（剂量、频次、禁忌有没有变）、**多样性**（同一问题多次回答的差异度）、**成本**。三条一起看，你才能回答「这次调参是不是划算」。

## 🚧 结论与边界

本篇压成一句话：

> **参数是成本与稳定性的旋钮，不是智能程度的旋钮。**

四条推论：

- 模型每步输出的是一整条分布，采样是「按分布抽签」。所谓「不稳定」不是故障，是这套机制的固有形态。
- temperature 改分布形状，Top-k / Top-p 改候选集范围，先改形状再定范围，叠加时效果相乘。
- temperature=0 只让采样退化为贪心，**不消除前向计算的数值不确定**。逐字复现要自己造，不能靠参数要。
- 推理模型不是更聪明，是「先写草稿再答」，思考 token 按输出计费。**该不该开，是一道成本题，不是能力题。**

还有一条 2026 年才变成常识的：**参数会互相覆盖，调参前先确认它有没有生效。**

而这一篇真正的落点在这里——**温度低不提高准确性，它只是让错误变得可复现。** 所以「医疗场景把温度压到 0」不是安全方案，它只是安全方案的**第一步**：先让问题可复现，然后才有办法度量、回归、拦截。

那下一个问题就自然浮现了：既然同一个模型有便宜有贵、有快有慢、有开推理有不开推理，**你到底该用哪一个？**

这个问题的答案不在参数里，在成本表里。用甜的语气提问，和用推理模式提问，单价可能差十倍；而日均一千次的量级会把这种差距放大成一张真实的账单。

有意识地留到后面三件事：

- **怎么让输出稳定成可解析的结构，从根上不依赖「抽签抽得好」** → 阶段二（结构化输出 / JSON Schema 约束）
- **怎么量化「改了参数之后效果是变好还是变坏」** → 阶段九（评估体系）
- **怎么在预算里编排上下文，让模型少想一些没用的** → 阶段三（上下文工程）

## 🎤 面试追问链

单个问题答对只能拿及格分。真正的区分度在追问——面试官会顺着你的答案往下挖。

**追问一：「你说 temperature=0 就是贪心解码，那为什么我线上还是看到同一个请求两次结果不同？」**

因为贪心解码只解决了「采样」这一环，前向计算这一环没解决。三个来源：浮点非结合性（几万个数求和的顺序不同）、服务端批大小随并发变化（归约顺序跟着变）、模型版本静默更新。前两个在闭源 API 上无法控制，第三个你甚至看不到。所以要区分两件事——**你要的是「统计上稳定」还是「逐字复现」**：前者靠低温 + 固定 prompt；后者只能在自部署 + 固定算子配置下逼近。

**追问二：「Top-p 已经取代 Top-k 了，那是不是完全不用管 k 了？」**

不是「取代」，是「默认更合适」。Top-k 的价值在于**硬上限**：它保证你永远不会在候选集突然变得巨大时抽到离谱的词。这在长尾词很多的任务里有用（比如专有名词密集的医疗文本）。实际生产中常见配置是「Top-p 为主 + 一个较大的 Top-k 兜底」，两者叠加时先 k 后 p，效果是「先砍长尾，再按概率质量自适应」。所以正确的说法是 **Top-p 调行为、Top-k 调护栏**，不是二选一。

**追问三：「推理模型一般用在什么场景？什么时候坚决不用？」**

判据是**这道题有没有「中途发现想错了」的空间**。多步计算、逻辑推理、需要反复权衡的方案设计——有，值得付思考的钱。单步抽取、分类、格式转换、简单事实问答——没有，开了就是把钱花在 300 个 token 的自我确认上。这条判据比「难不难」更准，因为「难」是主观感受，「能不能自纠」是结构判断。

**追问四：「我调 temperature 完全没反应，从哪查起？」**

按这个顺序：**一查模式**（是否在思考 / 推理模式，很多实现会忽略温度参数）；**二查取值**（这个模型是否把该参数固定或限制在某个区间，比如某些非思考模式直接固定 top_p=1.0）；**三查网关**（是否被统一配置或缓存覆盖）；**四查版本**（是否在比对不同模型版本）。最关键的习惯是——**日志里记「实际生效的参数」，而不是「你传的参数」**。这两者在被覆盖时完全不同，而线上归因几乎全靠这份日志。
