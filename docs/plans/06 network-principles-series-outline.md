## 系列定位

**「网络原理深度拆解」系列**

- 篇数：10 篇
- 核心主线：DNS 域名解析 → TCP 传输层机制 → HTTPS/TLS 安全传输 → HTTP 协议演进 → HTTP 语义基础（内容协商/状态码/方法语义）→ WebSocket 实时通信 → 跨域与浏览器安全 → HTTP 缓存体系 → API 设计范式（RESTful vs GraphQL）→ 反向代理与负载均衡——按"协议栈自底向上"排列，每篇涉及的底层机制都已在前面篇章讲过，不再需要前向引用。**为什么 DNS 这个应用层协议却排在开头**：一方面，浏览器加载页面的"第一跳"就是 DNS 解析，以它开篇最有代入感；另一方面，DNS 跑在 UDP（53 端口、无连接、报文通常不超过 512 字节）之上，它天然是引出第 02 篇"UDP vs TCP"对比的引子——所以把 DNS 放在 TCP 之前，是"自底向上"主线里唯一一处刻意为之的例外，其余篇章严格按分层依赖排序
- 内容结构：**统一首尾骨架 + 各篇主题主线**（不再套统一五段式）。开篇（标题/副标题/面试钩子/🎯 解决什么问题）与结尾（一张图总结/面试核心问/留个问题/上一篇下一篇）全系列固定，保住系列辨识度；中间主体按每篇主题的天然主线自由展开（如 DNS 篇"一次解析的旅程"、TCP 篇"一个报文段的旅程"、REST 篇"两种范式对比"），实操命令/工具演示紧跟对应原理小节，不再单独设"使用与实践"与"实践演示与验证"两章，RFC 规范出处并入文末参考资料。详见下方「主线说明」
- 特色：每篇 3-5 个「面试官会问」；示例统一沿用医疗场景命名（药品/处方/患者/医院管理系统 HIS）；涉及可与后续 Node.js 系列对照的知识点显式标注「对比 Node.js 实现」

### 主线说明（每篇主体的组织方式）

协议类文章与框架 API 类文章不同——协议是"看不见摸不着"的东西，`dig`/`curl`/`openssl` 这类工具的"使用"本质上就是在观察协议原理，"先会用再懂原理"的写法在这里不自然。因此本系列不再套统一五段式，改为：

**统一首尾骨架**（全 10 篇固定）：
- 开篇：`# 标题` + `> 副标题` + `> 面试官问…` 钩子段 + `## 🎯 这篇文章解决什么问题`（问题意识 + 分层大地图定位 + 本篇三件事）
- 结尾：`## 💡 一张图总结（面试速记表）` + `## 💡 面试核心问` + `## 📝 留个问题` + `> 🔖 上一篇/下一篇` 导航块

**各篇主题主线**（中间主体自由展开，默认遵循认知递进，可裁剪/合并）：

```
① 是什么 & 为什么  —— 概念直觉 + 它要解决的痛点（引出问题）
② 机制拆解        —— 核心原理，由浅入深逐层讲透（主体重心，占 50%+）
③ 权衡与边界      —— 对比 / 选型 / 局限 / 常见坑（面试高频）
④ 实战与验证      —— 用工具/命令/代码把上面「看见」，落到医疗场景
```

相对旧五段式的三条改造原则：
1. **「使用与实践」与「实践演示与验证」合并**——实操命令不再单独成段，而是拆散进各主题小节、紧跟对应原理（讲"递归 vs 迭代"时当场 `dig +trace`，讲"就近调度"时当场对比两个 DNS 的 IP），实现"讲到哪里、看到哪里"。
2. **「工程落地参考」降级为文末参考附录**——RFC 编号 + Node.js 源码指针并入结尾「参考资料」，只保留规范出处与搜索关键词，不再占正式章节打断主线。
3. **「设计与原理」不再单列**——原理即主体，按主题主线逐层展开，主线就是认知递进本身。

### 分层总地图（每篇的落点锚点）

10 篇覆盖了从应用层到传输层的完整协议栈，TLS 严格位于"应用层与传输层之间"（在 OSI 模型里对应会话层/表示层）。写作时每篇开头用一句话标注"本篇落在第 X 层"，让读者始终能在大地图里定位当前内容：

```
┌─────────────────────────────────────────────────────────────┐
│ 应用层   01 DNS │ 04 HTTP演进 │ 05 HTTP语义 │ 06 WebSocket   │
│         07 安全 │ 08 缓存 │ 09 REST/GraphQL │ 10 反向代理    │
├─────────────────────────────────────────────────────────────┤
│ 会话/表示层  03 TLS/HTTPS   ← 位于应用层与传输层之间         │
├─────────────────────────────────────────────────────────────┤
│ 传输层   02 TCP / UDP（含拥塞控制、滑动窗口、端口）           │
├─────────────────────────────────────────────────────────────┤
│ 网络层   IP 寻址/路由/子网/私有地址/NAT（不独立成篇，在 02 篇 │
│          分层小节交代定位，为 QUIC 连接迁移、WebSocket 僵尸   │
│          连接等后文概念兜底）                                 │
├─────────────────────────────────────────────────────────────┤
│ 链路层/物理层   不在本系列范围（对应用工程师价值递减）        │
└─────────────────────────────────────────────────────────────┘
```

> 与《04 性能与前端监控》系列的分工备忘：该系列已发布的 `network-resource-loading-complete-guide.md`（`docs/articles/04 performance/2026-08-11-network-resource-loading-complete-guide.md`）已覆盖 preload/prefetch/HTTP2/缓存策略等**网络性能优化落地**内容。本系列与其的边界是——本系列讲"协议本身的原理"，那篇讲"怎么用这些协议做加载优化"，两者不重复：本系列第 04 篇（HTTP2 多路复用原理）和第 08 篇（缓存机制原理）是那篇优化手段的"地基"，写作时如涉及优化落地，用「搜索关键词」索引到那篇即可，不在本系列重复展开性能优化。
