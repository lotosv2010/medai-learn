## 🎯 这篇文章解决什么问题

这是「**前端数据结构与算法**」系列的第 **2 篇**。第 1 篇导读解决了「**为什么要学**」，这一篇解决一个更基础、更前置的问题——「**怎么衡量一段代码到底好不好**」。

你可能会觉得：「性能好不好，跑一下不就知道了？」但真实情况是：同一段代码，在 Mac 上和 Windows 上、在 Chrome 和 Safari 里、在数据量 1 万和 100 万时，耗时天差地别。如果每次都要「跑一下」才能下结论，那这个结论既不可迁移、也不可靠。

复杂度分析，就是那把**不依赖环境、只反映本质**的尺子。这一篇只做三件事：

- **讲清它是什么**：时间复杂度、空间复杂度，以及描述它们的「大 O 表示法」
- **讲清怎么算**：四个分析法则 + 从 O(1) 到 O(n!) 的完整复杂度谱系，让你能**五秒看穿一段代码**
- **讲清怎么用**：用它定位前端性能瓶颈、实测增长曲线、答出面试高频问

全篇一条主线：**复杂度是后面 14 篇所有判断的「尺子」**。后面每一篇说「栈的 push/pop 是 O(1)」「链表删除是 O(1)」「快排平均 O(nlogn)」，全都建立在这把尺子上。这一篇没吃透，后面所有「谁比谁快」的结论都悬在空中。

> 💬 **面试官**：为什么要用复杂度分析，而不是直接把代码跑一遍计时？
>
> ✅ 标准答案：因为实际计时受执行环境影响太大——CPU、内存、操作系统、语言运行时、甚至当前机器的负载都会影响结果，跑出来的数据**不可迁移、不可比较**。而复杂度分析描述的是「执行时间（或空间）随数据规模增长的趋势」，只和算法本身有关，与环境无关。
>
> 🎁 加分答案：能点出复杂度分析的三个工程价值——**不依赖执行环境**（一台机器一个数，但 O(n²) 到哪儿都是 O(n²)）、**成本低效率高**（不用真的把 n 跑到 100 万，纸上就能推出来）、**指导性强**（在写代码之前就能判断哪种方案量级更优，避免把 O(n²) 的实现写完上线才发现卡）。还可以补一句：复杂度分析不能替代性能测试——它忽略常数因子，两个都是 O(n) 的算法，谁快谁慢还是得实测；两者是「选型前先判断量级，选型后再微调常数」的关系。

## 一、场景切入：为什么 includes 比 Set.has 慢 100 倍

先不急着背定义。我们先看三个真实的前端瓶颈，它们都有一个共同点——**表面是「代码写得不优雅」，本质是「复杂度量级不同」**。看懂这三个场景，你就能理解复杂度为什么要被单独拎出来讲。

🔧 **真实场景一：药品搜索列表去重**。药品电商的搜索页，用户输入关键词后要返回上千条药品卡片，其中药品编码（SKU Code）经常重复，需要去重后展示。最常见的写法是：

```javascript
const dedup = (list) =>
  list.filter((item, index) => list.indexOf(item) === index); // 👈 indexOf 每次都要从头扫一遍
```

`indexOf` 和 `includes` 一样，都是**顺序遍历数组、逐个比对**，查找一个元素是 O(n)。而整个 `filter` 里又对每个元素都调了一次 `indexOf`，于是整体变成 O(n²)。10 万条数据，就是 100 亿次比对——页面直接卡死。

换一种写法：

```javascript
const dedup = (list) => [...new Set(list)]; // 👈 Set 内部是哈希表，判存是 O(1)
```

`Set` 底层是哈希表，`has`/`add` 都是 O(1)（均摊）。整个去重降到 O(n)。同样是 10 万条数据，一个是 100 亿次操作，一个是 10 万次操作——**差 100 倍以上**。

🔧 **真实场景二：深克隆的隐患**。医疗表单保存时，前端经常要对表单对象做深克隆（比如保存前先 clone 一份做对比、或者做撤销快照）。递归深克隆的复杂度是 **O(n·d)**——n 是对象里节点的总数，d 是嵌套深度。一个深达十几层的病历对象，频繁触发深克隆，主线程直接卡帧。

🔧 **真实场景三：循环嵌套陷阱**。渲染「处方 × 药品」的关联关系时，如果用两层 `for` 循环：n 个处方、每个处方 m 种药品，复杂度就是 **O(n×m)**。超过千条数据后，TTI（可交互时间）肉眼可见地变慢。

这三个场景的共性是什么？**它们慢，不是因为你机器不好，而是因为算法本身「随数据规模增长」的速度不一样**。而这个「增长速度」，就是复杂度要精确描述的东西。

> 💬 **面试官**：`includes` 和 `Set.has` 都是「判断元素在不在」，为什么性能差这么多？
>
> ✅ 标准答案：因为两者底层数据结构不同。`includes` 是在数组上**顺序遍历**，从第一个元素逐个比对到最后一个，最坏要扫完整数组，是 O(n)；`Set` 底层是**哈希表**，通过哈希函数直接把 key 映射到桶的位置，平均 O(1) 就能命中。数据量大时，O(n) 和 O(1) 的差距会被放大到数量级。
>
> 🎁 加分答案：能点出「O(1) 不是免费的」——① `Set` 的 O(1) 是**均摊**的，哈希表有冲突和扩容，扩容时整表重哈希是 O(n)，只是均摊到每次操作后仍为 O(1)；② `new Set(list)` 构造本身就 O(n)，所以「查一次」的场景里，直接 `includes` 反而更划算，只有**大量重复查找**（如去重、频繁判存）时转 `Set` 才赚；③ 还能提到 `Set` 额外占内存（哈希表有负载因子、有空桶），这是用空间换时间。

## 二、复杂度是什么：一把衡量算法好坏的尺子

看完了现象，我们正式定义它。

数据结构和算法，解决的是同一件事——**如何让计算机更快时间、更省空间地解决问题**。所以评估一段代码的性能，天然要从两个维度看：

- **执行时间**——跑得快不快，对应**时间复杂度**
- **占用空间**——内存花得多不多，对应**空间复杂度**

二者统称**复杂度**。

这里要抓住最核心的一句话：**复杂度描述的是「算法执行时间（或占用空间）与数据规模之间的增长关系」**。注意，它描述的是**增长关系（趋势）**，而不是一个精确的秒数或字节数。

为什么「为什么用复杂度分析」这件事值得单独强调？因为和「直接跑性能测试」相比，复杂度分析有几个硬优势：

- **不依赖执行环境**：同一个 O(n²) 算法，在顶配服务器和十年前的老笔记本上耗时不一样，但「它是 O(n²)」这件事到哪里都不变
- **成本低、效率高**：不用真的构造 100 万条数据跑一遍，纸上推几步就能得出量级
- **易操作、指导性强**：能在写代码**之前**就判断哪种方案量级更优，从源头避免「写完上线才发现 O(n²) 卡死」的返工

> 💬 **面试官**：复杂度分析描述的是「增长趋势」而不是「精确耗时」，这个区别为什么重要？
>
> ✅ 标准答案：因为精确耗时受环境、常数、编译器优化等大量因素影响，换个环境结论就失效；而「增长趋势」只由算法本身决定，是稳定、可迁移的结论。复杂度分析的意义在于**在编码前就排除掉量级上不可行的方案**。
>
> 🎁 加分答案：能主动点出「趋势 vs 常数」的边界——复杂度忽略了常数因子，所以它**不能替代**性能测试。两个都是 O(n) 的算法，A 每轮干 3 件事、B 每轮干 300 件事，实际耗时差 100 倍，但复杂度看都是 O(n)。正确姿势是「先用复杂度筛掉量级差的方案，再用实测在量级相同的方案里选常数小的」。

## 三、大 O 表示法：只看增长趋势，忽略常量

有了「复杂度」这个概念，下一步是**怎么把它写出来**。答案就是大 O 表示法。

### 定义：T(n) = O(f(n))

大 O 表示法用两个公式描述算法的复杂度：

```javascript
T(n) = O(f(n))   // 时间复杂度：T 是执行总时间
S(n) = O(f(n))   // 空间复杂度：S 是占用总空间
```

其中：

- **T** 代表算法需要执行的**总时间**，**S** 代表算法需要的**总空间**
- **n** 是**数据规模**（问题的大小）
- **f(n)** 是**代码执行的总次数**（随 n 变化的函数）
- **O(...)** 读作「大 O」，表示「增长趋势不超过某个量级」

举个最直观的例子，看这段双层循环：

```javascript
function go(n) {
  var item = 0;                          // 这里执行了 1 次
  for (var i = 0; i < n; i++) {          // 这里执行了 n 次
    for (var j = 0; j < n; j++) {        // 这里执行了 n*n 次
      item = item + i + j;               // 这里执行了 n*n 次
    }
  }
  return item;                           // 这里执行了 1 次
}
```

逐行数执行次数：`1 + n + n² + n² + 1 = 2 + n + 2n²`。所以这段代码的 `T(n) = O(2 + n + 2n²)`。

但前面说过，时间复杂度看的是**增长趋势**。当 n 很大时，`2n²` 这一项完全主导了增长，`n` 和常量 `2` 在它面前可以忽略不计。所以最终：

> **T(n) = O(n²)**

这就是大 O 时间复杂度的完整含义——**它不代表代码真正的执行时间，而是表示代码随数据规模增长的变化趋势**，简称**时间复杂度**。你可以想象一下「y = n²」这条抛物线：n 每增大一点，y 就往天上蹿。

### 为什么忽略常量、低阶、系数

这是很多人第一次接触大 O 时最别扭的地方：`2n² + 2n + 2` 凭什么能直接写成 O(n²)？那个「2」和「2n」呢？

答案是：**时间复杂度描述的是增长趋势，当 n 足够大时，常量、低阶项、系数都不起决定性作用**。

- **常量**（如 `+2`）：n 从 1 万变成 10 万时，`+2` 还是 `+2`，纹丝不动，对趋势零影响
- **低阶项**（如 `2n`）：n 从 1 万变成 10 万时，`2n` 从 2 万变成 20 万（涨了 10 倍），但 `n²` 从 1 亿变成 100 亿（涨了 100 倍）——低阶项的增长被高阶项彻底碾压
- **系数**（如 `2n²` 里的 2）：它只是把曲线「拉高/压扁」一点，但**曲线的形状（二次方的增长方式）不变**

所以大 O 分析的口诀就一句：**关注「变」，忽略「不变」**。「变」是随 n 变化的变量部分，「不变」是常量、系数、低阶项这些不改变趋势的东西。

### 补全：O、Ω、Θ 到底有什么区别

面试里经常被追问：「你说 O(n)，那 Ω 和 Θ 又是什么？」这里必须分清，因为**这三个符号描述的是三种不同的「界」**：

```
O(g(n))：渐进上界 —— 增长「不会超过」g(n) 这个量级（对应最坏情况）
Ω(g(n))：渐进下界 —— 增长「至少需要」g(n) 这个量级（对应最好情况）
Θ(g(n))：渐进紧确界 —— 上界和下界重合，精确刻画「恰好同阶」
```

更精确地说：如果 f(n) 的增长速率**不超过** g(n)，记为 `f(n) = O(g(n))`；**不低于** g(n)，记为 `f(n) = Ω(g(n))`；**既不超过也不低于**（上下界一致），记为 `f(n) = Θ(g(n))`。

一个例子帮你记住：数组里顺序查找一个元素，**最好情况**第一个就是它（O(1)），**最坏情况**扫到最后一个或根本不存在（O(n)）。所以这个查找算法是「最坏 O(n)、最好 Ω(1)」。而绝大多数情况下，我们说「这个算法是 O(n)」或「是 O(n log n)」，**默认指的是最坏情况的上界**——这是面试和工程里的通用约定。

> 💬 **面试官**：大 O、大 Ω、大 Θ 三者有什么区别？
>
> ✅ 标准答案：O 是渐进上界，描述算法最坏情况「增长不会超过多少」；Ω 是渐进下界，描述最好情况「至少需要多少」；Θ 是渐进紧确界，表示上下界一致、增长阶被精确确定。日常说「这个算法是 O(n)」默认指最坏情况上界。
>
> 🎁 加分答案：能举出「上下界不一致」的例子——快排**平均 Θ(nlogn)** 但**最坏 O(n²)**（比如数组已有序又选第一个元素当基准时），所以快排只能说「最坏 O(n²)、平均 Θ(nlogn)」，不能说「就是 O(nlogn)」。能主动区分「上/下/紧确界」和「最坏/最好/平均情况」这两组概念，说明你不是死记硬背：前者是数学上的「界」，后者是输入分布上的「情况」，两者常用 O/Ω 分别去描述最坏/最好，但本质是两套坐标。

## 四、时间复杂度分析四法则：五秒看穿一段代码

大 O 的概念搞懂了，下一步是**怎么快速算出来**。这里给你四个法则，学完就能「五秒看穿」绝大多数业务代码的复杂度。

在进入法则之前，先感受一下「数执行次数」的节奏，看三个由浅入深的例子：

**例子 1（O(1)）**

```javascript
function aFun() {
  console.log("Hello, World!");   // 需要执行 1 次
  return 0;                       // 需要执行 1 次
}
```

这个方法一共执行 2 次运算，和 n 无关，是 O(1)。

**例子 2（O(n)）**

```javascript
function bFun(n) {
  for(let i = 0; i < n; i++) {    // 需要执行 (n + 1) 次
    console.log("Hello, World!"); // 需要执行 n 次
  }
  return 0;                       // 需要执行 1 次
}
```

一共 `(n + 1) + n + 1 = 2n + 2` 次，忽略常量系数，是 O(n)。

**例子 3（O(n²)）**

```javascript
function cal(n) {
  let sum = 0;                    // 1 次
  let i = 1;                      // 1 次
  let j = 1;                      // 1 次
  for (; i <= n; ++i) {           // n 次
    j = 1;                        // n 次
    for (; j <= n; ++j) {         // n * n 次，即 n² 次
      sum = sum +  i * j;         // n * n 次，即 n² 次
    }
  }
}
```

二层 for 循环，内层执行 n² 次。注意这里是 `++i`，和例子 2 的 `i++` 不同——这是「先加」和「后加」的区别（在这里对循环次数没影响，但面试时可能会被问到）。总次数 `n² + n² + n + n + 1 + 1 + 1 = 2n² + 2n + 3`，忽略低阶和常量，是 O(n²)。

**小结**：以时间复杂度为例，由于它描述的是**增长变化趋势**，所以**常量、低阶、系数**对趋势不产生决定性影响，分析时一律忽略。三个例子的结果分别是 O(1)、O(n)、O(n²)。

下面四个法则，就是把这个「数次数 → 忽略」的过程提炼成套路。

### 法则一：只关注循环执行次数最多的一段代码

单段代码，抓执行次数最多的那部分——通常就是循环。

```javascript
function cal(n) {
  let sum = 0;
  let i = 1;
  for (; i <= n; ++i) {
    sum = sum + i;
  }
  return sum;
}
```

执行次数最多的是 `for` 循环及里面的代码，执行了 n 次，所以时间复杂度是 O(n)。

### 法则二：加法法则——总复杂度等于量级最大的那段

一段代码里有多个并列的片段时，**总复杂度等于量级最大的那一段**。多段代码取最大，而不是累加。

```javascript
function cal(n) {
  let sum_1 = 0;
  let p = 1;
  for (; p < 100; ++p) {          // 第一部分：跑 100 次
    sum_1 = sum_1 + p;
  }

  let sum_2 = 0;
  let q = 1;
  for (; q < n; ++q) {            // 第二部分：跑 n 次
    sum_2 = sum_2 + q;
  }

  let sum_3 = 0;
  let i = 1;
  let j = 1;
  for (; i <= n; ++i) {           // 第三部分：跑 n² 次
    j = 1;
    for (; j <= n; ++j) {
      sum_3 = sum_3 +  i * j;
    }
  }

  return sum_1 + sum_2 + sum_3;
}
```

三段代码分别求 `sum_1`、`sum_2`、`sum_3`，只看循环部分：

- 求 `sum_1` 的循环执行了 100 次，和 n 无关，是**常量级**，不反映增长趋势，复杂度 O(1)
- 求 `sum_2` 的循环是 O(n)
- 求 `sum_3` 的双层循环是 O(n²)

三段取最大量级，最终复杂度是 **O(n²)**。同理类推：3 层 for 循环是 O(n³)，4 层就是 O(n⁴)。一句话——**总的时间复杂度就等于量级最大的那段代码的时间复杂度**。

### 法则三：乘法法则——嵌套代码复杂度等于内外乘积

嵌套的代码（循环里调函数、函数里又循环），复杂度是**内外两层复杂度的乘积**。

```javascript
function cal(n) {
  let ret = 0;
  let i = 1;
  for (; i < n; ++i) {
    ret = ret + f(i);             // 👈 重点：循环里调用了 f(i)
  }
}

function f(n) {
  let sum = 0;
  let i = 1;
  for (; i < n; ++i) {
    sum = sum + i;
  }
  return sum;
}
```

`cal` 的循环里调用了 `f`，而 `f` 里也有循环。`cal` 的循环是 O(n)，`f` 是 O(n)，所以整个 `cal()` 的时间复杂度是：

> T(n) = T1(n) × T2(n) = O(n × n) = O(n²)

### 法则四：多规模——两个参数要分别算

前面的例子都只有一个规模 n，但如果一个函数有**两个参数分别控制两个循环**，就不能简单合并，要分「加法」和「乘法」两种情况。

**多规模求加法（O(m + n)）**：两个独立的循环，各自受一个参数控制，复杂度相加。

```javascript
function cal(m, n) {
  let sum_1 = 0;
  let i = 1;
  for (; i < m; ++i) {            // 受 m 控制
    sum_1 = sum_1 + i;
  }

  let sum_2 = 0;
  let j = 1;
  for (; j < n; ++j) {            // 受 n 控制
    sum_2 = sum_2 + j;
  }

  return sum_1 + sum_2;
}
```

求 `sum_1` 的数据规模是 m，求 `sum_2` 的数据规模是 n，两者是**并列关系**，所以时间复杂度是 O(m + n)。公式：`T1(m) + T2(n) = O(f(m) + g(n))`。

**多规模求乘法（O(m × n)）**：两个参数控制**嵌套**的两个循环，复杂度相乘。

```javascript
function cal(m, n) {
  let sum_3 = 0;
  let i = 1;
  let j = 1;
  for (; i <= m; ++i) {
    j = 1;
    for (; j <= n; ++j) {
      sum_3 = sum_3 +  i * j;
    }
  }
}
```

两层 for 循环，外层受 m 控制、内层受 n 控制，是**嵌套关系**，所以复杂度是 O(m × n)。公式：`T1(m) × T2(n) = O(f(m) × g(n))`。

> 💬 **面试官**：`cal(m, n)` 有两个参数，它的复杂度是多少？为什么不能直接写成 O(n²)？
>
> ✅ 标准答案：要看两个参数是**并列**还是**嵌套**。两个独立的循环各自受 m、n 控制，是 O(m + n)；两层嵌套循环分别受 m、n 控制，是 O(m × n)。不能直接写成 O(n²)，是因为 m 和 n 是两个独立的规模，可能相差悬殊，`n²` 无法表达「m 很小、n 很大」这种真实情况。
>
> 🎁 加分答案：能点出「什么时候能合并」——只有当 m 和 n 是同一量级（如 m ≈ n）时，O(m + n) 才可简写为 O(n)、O(m × n) 才可简写为 O(n²)。反之，如果题目里说 m 远小于 n，那 O(m + n) 就不能省略 m。这个细节在「两个数组」「两个链表」的题里经常考，很多人顺手就写 O(n²) 被扣分。

## 五、常见复杂度阶：从 O(1) 到 O(n!) 的增长曲线

法则会用了，现在把「常见复杂度阶」一次性铺开，逐个配代码、讲清推导。这部分是面试的重头戏——**你要能对任意一段代码，脱口而出它的量级**。

复杂度阶分成两大类：**多项式阶**（增长可控，工程里可接受）和**非多项式阶**（增长爆炸，能不用就不用）。

### 多项式阶

**O(1) 常数阶**——效率固定，与数据量无关，是最优的复杂度。

```javascript
function total() {
  var sum = 0;
  for(var i=0;i<100;i++) {   // 👈 虽然循环了 100 次
    sum += i;
  }
}
```

虽然有个 for 循环，但它**固定执行 100 次**，代码的执行时间不随 n 增大而增长，所以复杂度是 O(1)。这里的「1」代指常量——不管循环 100 次还是 100 万次（只要和 n 无关），都是 O(1)。

**O(logn) 对数阶**——每次把规模砍半，二分查找、二叉树里最常见，但也是比较难理解的一种。

```javascript
function print(n){
  let i=1;
  while (i <= n) {
    i = i * 2;   // 👈 每次翻倍
  }
}
```

代码从 1 开始，每次循环 `i` 乘以 2，当 `i > n` 时循环结束。i 的取值是一个等比数列：2⁰、2¹、2² … 2ˣ = n。

我们只要知道 x 是多少，就知道循环执行了多少次。由 2ˣ = n 求解 x，得 **x = log₂n**。所以这段代码的时间复杂度是 O(log₂n)。

但实际写的时候，我们都记作 O(logn)，**忽略对数的底数**。为什么？因为对数之间可以互相转换：log₃n = log₃2 × log₂n，其中 log₃2 是一个**常量**。根据「忽略常量」的原则，O(log₃n) = O(C × log₂n) = O(log₂n)。所以**不管底数是 2、3 还是 10，对数阶统一记为 O(logn)**。

**O(nlogn) 线性对数阶**——在对数阶的算法外再嵌一层循环。

```javascript
function aFun(n){
  let i = 1;
  while (i <= n)  {
     i = i * 2;
  }
  return i;
}

function cal(n) {
   let sum = 0;
   for (let i = 1; i <= n; ++i) {
     sum = sum + aFun(n);   // 👈 循环里调用 O(logn) 的 aFun
   }
   return sum;
}
```

`aFun` 是 O(logn)，`cal` 是 O(n)，乘法法则一乘，`T(n) = O(logn) × O(n) = O(nlogn)`。归并排序、快速排序（平均）都是这个量级。

**O(n) 线性阶**——执行时间随 n 线性增长。

```javascript
function print(n){
  let a = 0;
  for (let i=0;i<n;i++){
    console.log(i);
  }
}
```

假设每行代码执行时间是 T，这段代码就是 `T + n×T = (n+1)T`，忽略常量后是 nT，即 O(n)。这里的 O(n) 反应的就是「随着 n 的变化，执行时间线性增长」这个趋势。

**O(n²) 平方阶**——双层循环。

```javascript
function go(i) {
  var sum = 0;
  for (var j = 0; j < i; j++) {
    sum += i;
  }
  return sum;
}
function main(n) {
  var res = 0;
  for (var i = 0; i < n; i++) {
    res = res + go(i);   // 👈 循环里调用 go，go 里又是循环
  }
}
```

外层 n 次，每次调用 `go` 又循环 i 次，总共是 `1 + 2 + 3 + ... + n = n(n+1)/2` 次，量级是 O(n²)。

**O(n³) 立方阶**——三次循环。笔记原文只给了一句「三次循环就是立方阶，k 次循环就是 k 次方阶」，这里补一个最直白的三层循环示例：

```javascript
function cubic(n) {
  let count = 0;
  for (let i = 0; i < n; i++) {         // 第一层：n 次
    for (let j = 0; j < n; j++) {       // 第二层：n² 次
      for (let k = 0; k < n; k++) {     // 第三层：n³ 次
        count++;
      }
    }
  }
  return count;
}
```

三层嵌套，量级是 O(n³)。工程里一旦出现三层循环，基本就要警惕了——n 稍微大一点就是天文数字。

### 非多项式阶

**O(2ⁿ) 指数阶**——n 稍大即爆炸。

```javascript
function fibonacci( n ) {
  if (n <= 1) {
    return 1;
  } else {
    return aFunc(n - 1) + aFunc(n - 2);
  }
}
```

> ⚠️ 笔记原文里这里把函数名误写成了 `aFunc`，正确应该是 `fibonacci(n - 1) + fibonacci(n - 2)`——保留原样并在此注明，避免你照着写跑出「aFunc is not defined」。

显然运行次数满足 T(0) = T(1) = 1，且 T(n) = T(n - 1) + T(n - 2) + 1（最后的 +1 是那一次加法）。这是个斐波那契数列，通过归纳法可证：当 n ≥ 1 时 T(n) < (5/3)ⁿ，当 n > 4 时 T(n) ≥ (3/2)ⁿ。所以时间复杂度可表示为 O((5/3)ⁿ)，简化后记作 **O(2ⁿ)**。可见它随 n 指数级增长——你分别用 n=1、10、100 跑一下，就能直观感受到「指数爆炸」。

**O(n!) 阶乘阶**——比指数还恐怖。

```javascript
function factorial(){
  if(num <= 1){
    return 1;
  }else{
    return num * factorial(num - 1);
  }
}
```

> ⚠️ 同样，笔记原文里 `factorial` 少了参数 `num`，正确写法是 `function factorial(num)`——保留原样并注明。

阶乘型的时间复杂度按 `(n! + (n-1)! + (n-2)! + … + 1) + ((n-1)! + (n-2)! + … + 1) + …` 的方式计算。注意这里是**多个阶乘的和**，不只是 `n × (n-1) × (n-2) × … × 1`。假设 n 从 0 到 10，它的复杂度依次是 1、4、15、64、325、1956、13699、109600、986409、9864100……

对比一下有多可怕：O(2ⁿ) 在 n=10 时才 1024，n=100 时浏览器直接卡死；而 O(n!) 才到 n=10 就接近 1000 万了——真把 n 设成 100，算到机器烧了也算不出来。

### 增长速度排序 + 操作数量实例表

把所有阶排个序，从左到右越来越慢：

> **O(1) < O(logn) < O(n) < O(nlogn) < O(n²) < O(n³) < O(2ⁿ) < O(n!) < O(nⁿ)**

再给一张「操作数量实例表」，帮你把抽象符号对应到具体的数字：

| 操作数量实例 | 大O表示法 | 术语 |
| --- | --- | --- |
| 15 | O(1) | 常数阶 |
| 3logn | O(logn) | 对数阶 |
| 3n+5 | O(n) | 线性阶 |
| 4nlogn | O(nlogn) | 线性对数阶 |
| 5n²+3n+1 | O(n²) | 平方阶 |
| 6n³+4n+2 | O(n³) | 立方阶 |
| 2ⁿ+1 | O(2ⁿ) | 指数阶 |
| n!+1 | O(n!) | 阶乘阶 |

当数据规模 n 增长时，**非多项式量级**（O(2ⁿ)、O(n!)）的执行时间会急剧增加，所以它们是非常低效的算法，工程里要极力避免。

>
> 🎁 加分答案：能顺势讲出「为什么排序要优化到 O(nlogn)」——因为排序是很多系统的地基，n 稍微大一点，O(n²) 的冒泡/选择/插入排序就完全不可用，必须用归并、快排、堆排这些 O(nlogn) 的算法。还能补一句：log₂10000 ≈ 13.3 这个数可以心算——2¹⁰=1024、2¹³=8192、2¹⁴=16384，所以 log₂10000 在 13 和 14 之间。这种「心算对数」的能力在面试里很加分。

## 六、时间复杂度类型：最好/最坏/平均/均摊

前面分析的都是「一个确定的值」，但真实算法在不同输入下，耗时可能差别巨大。于是时间复杂度又分四种类型。先看这段「在数组里找 x」的经典代码：

```javascript
// n 表示数组 array 的长度
function find(array, n, x) {
  let i = 0;
  let pos = -1;
  for (; i < n; ++i) {
    if (array[i] == x) {
      pos = i;
      break;
    }
  }
  return pos;
}
```

### 最好情况时间复杂度（best case）

**最理想情况下执行这段代码的复杂度**。上面例子中，如果数组第一个值就是 x，一次比对就命中，复杂度是 O(1)。所以最好情况时间复杂度是 **O(1)**。

### 最坏情况时间复杂度（worst case）

**最糟糕情况下执行这段代码的复杂度**。如果数组里不存在 x，或者 x 在最后一个位置，就必须遍历完整个数组，复杂度是 **O(n)**。

### 平均情况时间复杂度（average case）

最好和最坏都是极端，更常见的是问「平均下来是多少」。分析方法是：**代码在所有可能情况下的执行次数，取加权平均值**。

还是上面找 x 的例子：x 在数组中的位置有 n+1 种情况——在 0～n-1 这 n 个位置中，或者根本不在数组里。先把每种情况需要遍历的元素个数加起来，再除以 n+1：

![平均时间复杂度的推导：所有情况遍历次数相加后取平均（发布前请自行转存素材库）](https://cdn.nlark.com/yuque/0/2021/png/738210/1639995526075-baa9f48c-3ad9-42e7-be6b-aea48987f8f4.png)

省略掉系数、低阶、常量后，这个公式简化得到的平均时间复杂度就是 O(n)。

但这里有个漏洞：上面把每种情况「等概率」处理了。实际上「在数组里」和「不在数组里」的概率未必各一半。假设各为 1/2，且「在数组里」时出现在 0～n-1 每个位置的概率相等（都是 1/n），那么根据概率乘法法则，x 出现在任意一个具体位置的概率就是 1/(2n)。把每种情况的概率考虑进去，计算就变成：

![加权平均时间复杂度的推导：把每种情况的发生概率考虑进去（发布前请自行转存素材库）](https://cdn.nlark.com/yuque/0/2021/png/738210/1639995592465-c3d09aa6-3dee-4c86-b23d-a36b4d8cb8b7.png)

这个值就是概率论里的**加权平均值**，也叫**期望值**。所以「平均时间复杂度」的全称应该叫**加权平均时间复杂度**，或者**期望时间复杂度**。计算下来，它的结果仍然是 **O(n)**。

### 均摊时间复杂度（amortized，面试重点）

最后这个是最容易考、也最容易被忽视的。它的应用场景很特殊：**一段代码绝大多数情况下是低复杂度，只有个别情况是高复杂度，且这些高复杂度情况之间有顺序关系**（比如「攒够一批才触发一次」）。这时可以把个别高复杂度均摊到低复杂度上，基本结果就等于那个低复杂度。

最经典的例子是 **`Array.push`**。你可能一直以为 `push` 就是 O(1)——往数组尾部塞一个元素，确实不用搬移。但问题是：**数组的容量是有限的**。

```
容量 4 的动态数组，逐个 push：
push(1)  → [1, _, _, _]    O(1)
push(2)  → [1, 2, _, _]    O(1)
push(3)  → [1, 2, 3, _]    O(1)
push(4)  → [1, 2, 3, 4]    O(1)
push(5)  → 满了！扩容到 8，把 4 个元素复制过去 O(4)，再插入 O(1)
push(6)  → [1..5, 6, _, _] O(1)
push(7)  → O(1)
push(8)  → O(1)
push(9)  → 扩容到 16，复制 8 个元素 O(8)
```

当数组满了再 push 时，V8 会**开辟一块更大的新内存（通常是翻倍），把旧元素全部复制过去**——这一次复制就是 O(n)。但扩容不是每次都发生，而是「翻倍」地间歇发生。把 n 次 push 的总代价加起来：

- n 次插入本身：O(n)
- 所有扩容复制加起来：1 + 2 + 4 + 8 + … ≈ 2n（等比数列求和，是 O(n)）

所以 n 次 push 总代价是 O(n)，**均摊到每次 push 就是 O(n)/n = O(1)**。这就是「push 是均摊 O(1)」的完整含义——单看某一次 push 可能是 O(n)（恰好触发扩容那一次），但整体均摊下来是 O(1)。

> 💬 **面试官**：`Array.push` 的时间复杂度是 O(1) 还是 O(n)？为什么？
>
> ✅ 标准答案：是**均摊 O(1)**。push 到尾部本身是 O(1)，但数组容量满时会触发扩容——开辟一块更大的新内存（通常翻倍）并把旧元素全部复制过去，这一次是 O(n)。由于扩容是「翻倍」式地间歇发生（不是每次 push 都扩容），把扩容成本均摊到 n 次 push 上，每次的均摊代价仍是 O(1)。
>
> 🎁 加分答案：能算出「为什么翻倍策略让均摊是 O(1)」——如果用「每次只扩 1 个位置」的傻策略，n 次 push 的复制总量就是 1+2+3+…+n = O(n²)，均摊就退化成了 O(n)；而「翻倍扩容」让复制总量是等比数列 1+2+4+…+n ≈ 2n = O(n)，均摊才是 O(1)。还能顺势引出「均摊分析 vs 平均分析」的区别：平均分析假设所有输入等概率，均摊分析针对的是一系列操作的**顺序关系**（扩容有「攒够才触发」的时序），两者不是一回事。

## 七、空间复杂度：递归到底占不占内存

时间说完了，轮到空间。空间复杂度全称**渐进空间复杂度（asymptotic space complexity）**，表示**算法的存储空间与数据规模之间的增长关系**。公式同样是：

```javascript
S(n) = O(f(n))   // n 是问题规模，f(n) 是语句关于 n 所占存储空间的函数
```

看这段代码：

```javascript
function print(n) {
  const newArr = [];          // 第 2 行：申请一个空数组
  newArr.length = n;          // 第 3 行：把长度改成 n，每项是 undefined
  for (let i = 0; i < n; ++i) {
    newArr[i] = i * i;
  }

  for (let j = n-1; j >= 0; --j) {
    console.log(newArr[i])
  }
}
```

第 2 行申请了一个空数组 `newArr`，第 3 行把它的长度改成 n（每项值为 undefined），除此之外没有占用更多空间。所以整段代码的空间复杂度是 **O(n)**。

### 常见的空间复杂度

常见的空间复杂度就是 O(1)、O(n)、O(n²)，像 O(logn)、O(nlogn) 这样的对数阶平时基本用不到。

**O(1)**：只申请了固定数量的变量，和 n 无关。

```javascript
let a = 1;
let b = 1;
let c = 1;
let d = 1;
```

**O(n)**：申请一个长度为 n 的数组。

```javascript
let arr = Array(n)
```

**O(n²)**：申请一个 n×n 的二维数组。

```javascript
let arr=[]
for (var i = 0; i < n; i++) {
    arr[i]=i
    for (var j = 0; j < n; j++) {
        arr[i][j]=j
    }
}
```

### 递归调用栈也计入空间复杂度

这是空间复杂度里最容易被漏掉、也最常考的一个点：**递归调用栈占用的内存，也要计入空间复杂度**。

为什么？因为每次递归调用，JS 引擎都会在调用栈上 push 一个栈帧（保存局部变量、参数、返回地址等），直到递归返回才 pop 掉。

```
factorial(3)
  └─ factorial(2)        ← 栈帧 1：factorial(3) 压栈
       └─ factorial(1)   ← 栈帧 2：factorial(2) 压栈
            └─ return 1  ← 栈帧 3：factorial(1) 压栈（base case）

调用栈的深度 = 递归的深度 = n
每次递归占用一个栈帧 → 空间复杂度 O(n)
```

所以：递归求斐波那契 `fib(n)`，即便你没申请任何额外数组，它的空间复杂度也是 O(n)——因为调用栈要同时挂住 n 层栈帧。而一个「递归深度是 n、每层又申请一个 n 长度的数组」的算法，空间复杂度就是 O(n²)。

> 💬 **面试官**：空间复杂度里的「递归调用栈」算在哪里？递归算法的空间复杂度怎么算？
>
> ✅ 标准答案：递归调用栈占用的内存**必须计入空间复杂度**。每次递归调用都会在调用栈上 push 一个栈帧（保存参数、局部变量、返回地址），递归深度是多少，栈帧就有多少层。所以递归算法的空间复杂度 = **递归深度 × 每层占用的空间**。比如递归求斐波那契，虽然没申请额外数组，空间复杂度也是 O(n)（调用栈挂住 n 层）。
>
> 🎁 加分答案：能讲清「递归空间 ≠ 递归里申请的数据空间」——两者要分别算再取较大者。例如深克隆一棵树，递归深度 O(d)（树的深度），而每层还要复制节点数据 O(n)，总空间是 O(n) 而非 O(d)。还能提一句「尾递归优化（TCO）」：理想情况下尾递归能复用栈帧、把空间压到 O(1)，但 V8 一直没实现 TCO，所以 JS 里别指望靠尾递归省栈空间（这个在第 12 篇递归里会展开）。

## 八、复杂度与性能：怎么用复杂度定位瓶颈

学完了「是什么」「怎么算」，最后落到「怎么用」。复杂度分析最有价值的地方，是**在动手优化之前，先定位出瓶颈在哪一段、瓶颈是什么量级**。

一个最简单的优化例子：累加 1 到 n。

```javascript
console.time('a')
function go(n) {
  var item = 0;
  for (var i = 1; i <= n; i++) {
    item += i;
  }
  return item;
}
console.timeEnd('a')

console.time('b')
function go2(n) {
  var item = n*(n+1)/2   // 👈 高斯求和公式，一次算出
  return item;
}
console.timeEnd('b')

go(1000)
go2(1000)
```

> ⚠️ 笔记原文里 `console.time`/`timeEnd` 包住的是函数**定义**、而调用 `go(1000)` 在计时之外，实测时会失真——正确做法是把调用放在 `time` 和 `timeEnd` 之间。这里保留原样，下面用 `performance.now` 给一版可复现的正确写法。

同样是求 1 到 n 的和，`go` 用循环累加，是 O(n)；`go2` 用高斯求和公式 `n×(n+1)/2`，是 O(1)。当 n 足够大时，两者天差地别。这就是「用复杂度定位瓶颈」的威力——**先看出它是 O(n)，再想办法把它降到 O(1) 或 O(logn)**。

### 用 performance.now 实测 O(n) vs O(n²) 的增长曲线

光说不练假把式。这里给一段可直接在浏览器控制台 / Node 里跑的代码，实测 O(n) 和 O(n²) 的增长差异，兑现副标题的承诺：

```javascript
// O(n)：单层循环
function linear(n) {
  let sum = 0;
  for (let i = 0; i < n; i++) sum += i;
  return sum;
}

// O(n²)：双层循环
function quadratic(n) {
  let count = 0;
  for (let i = 0; i < n; i++) {
    for (let j = 0; j < n; j++) count++;
  }
  return count;
}

// 计时工具
function measure(fn, n) {
  const start = performance.now();
  fn(n);
  return (performance.now() - start).toFixed(2) + 'ms';
}

// 数据规模翻倍，观察耗时增长
for (const n of [1000, 2000, 4000, 8000]) {
  console.log(`n=${n}  O(n)耗时 ${measure(linear, n)}   O(n²)耗时 ${measure(quadratic, n)}`);
}
```

跑出来的结果大致是这样（不同机器绝对值不同，但**趋势一致**）：

| 数据规模 n | O(n) 耗时 | O(n²) 耗时 |
| --- | --- | --- |
| 1000 | ≈0.01ms | ≈0.5ms |
| 2000 | ≈0.02ms | ≈2ms |
| 4000 | ≈0.04ms | ≈8ms |
| 8000 | ≈0.08ms | ≈32ms |

看到规律了吗？**n 每翻一倍，O(n) 耗时翻一倍（线性），而 O(n²) 耗时翻四倍（平方）**。这就是「增长趋势」最直观的样子——你不需要记任何公式，只要看懂「n 翻倍，耗时怎么变」，就能反推出复杂度量级。

把这个方法用到真实项目里：当页面卡顿时，别急着无脑加缓存，先用「数据量翻倍看耗时变化」定位出**是哪段代码在 O(n²) 甚至 O(2ⁿ) 地增长**，再针对性优化——把 O(n²) 的双层循环改成 O(n) 的哈希查找、把 O(n) 的线性扫描改成 O(logn) 的二分。**先定位量级，再优化实现**，这才是复杂度分析在工程里的正确打开方式。

> 💬 **面试官**：如何分析一个递归算法的时间复杂度？
>
> ✅ 标准答案：常用三种方法——① **递归树法**：把每次递归调用画成一棵树，算出每一层的代价再求和；② **递推式法**：写出 T(n) 与 T(n-1)（或 T(n/2)）的关系式，如归并排序 T(n) = 2T(n/2) + O(n)；③ **主定理**：对形如 T(n) = aT(n/b) + f(n) 的分治递归式直接套结论。以斐波那契为例，T(n) = T(n-1) + T(n-2) + O(1)，递归树是一棵接近满二叉树，节点数约 2ⁿ，所以是 O(2ⁿ)。
>
> 🎁 加分答案：能举出「递归树高度」和「每层节点数」如何相乘——比如归并排序递归树高度 O(logn)、每层合并代价 O(n)，所以 O(nlogn)。还能主动指出「递归空间复杂度」要单独算（调用栈深度），并预告主定理的适用条件（必须能写成 T(n) = aT(n/b) + f(n) 的形式）。递归和主定理的完整展开，分别在第 12 篇「递归」和第 14 篇「分治」里，这里先建立「递归复杂度 = 递归树节点数之和」的心智模型。

## 💡 一张图总结（面试速记表）

| 复杂度阶 | 一句话内核 | 前端典型场景 | 考察频率 |
| --- | --- | --- | --- |
| O(1) | 常数时间，与规模无关 | Set/Map 哈希查找、数组下标访问 | ⭐⭐ 高频 |
| O(logn) | 每次砍半 | 二分搜索、二叉搜索树查找 | ⭐⭐⭐ 必考 |
| O(n) | 线性，逐个遍历 | 数组遍历、一次去重 | ⭐⭐⭐ 必考 |
| O(nlogn) | 砍半 × 线性 | 快排/归并排序、TimSort | ⭐⭐⭐ 必考 |
| O(n²) | 双层循环 | 嵌套 for、冒泡/选择/插入排序 | ⭐⭐ 高频 |
| O(2ⁿ) / O(n!) | 指数/阶乘爆炸 | 朴素递归斐波那契、全排列 | ⭐ 中频 |

> 💡 记住这条主线：**复杂度描述的是「随数据规模增长的趋势」，不是精确耗时**。分析时口诀是「关注变、忽略不变」——只盯循环最多的代码，用「加法取最大、乘法求乘积、多规模分开算」三招，就能五秒看穿任何一段代码。最常见的复杂度是 O(1)、O(logn)、O(n)、O(nlogn)、O(n²)，遇到 O(2ⁿ)、O(n!) 要立刻警惕。面试里，`Array.push` 均摊 O(1)、递归栈计入空间、O/Ω/Θ 三者区分，是三个最容易被追问的高频点。
