## 系列定位

**「阶段三：上下文工程（Context Engineering）」**

- 篇数：**6 篇**（正篇 6，无独立导读篇、无收口篇），对应路线图阶段三的模块 3.1~3.6，建议周期 2 周
- 核心主线：**先把 Prompt 当资产管起来**（Prompt 工程进阶 + 版本化）→ **看清一次调用里放了几类东西、各占多少**（上下文组装）→ **让历史不越聊越超预算**（压缩）→ **让事实跨会话存得下来**（记忆）→ **让重复前缀少花钱**（Prompt Caching）→ **让长文档别硬塞**（长上下文策略）
- 编排原则：按「**一段上下文从产生到被消费的生命周期**」排列——怎么写进资产、怎么拼进一次调用、怎么在历史里收窄、怎么跨会话留存、怎么靠缓存省前缀、怎么在窗口边界上做取舍。每篇都回答一个**读者此刻真实会踩的坑**，而不是模块知识点平铺
- **每篇统一的六段式骨架**：**概念 → 深入 → 案例 → 总结 → 面试 → 参考**
  - 概念：这一篇的核心概念是什么，先给直觉定义（延续阶段二「概念」段的纠偏作用）
  - 深入：底层原理 + 工程细节 + 为什么这样设计（对应阶段一的「原理讲透」）
  - 案例：**动手实验**——可运行的 TS 脚本，跑起来看真实输出。这是本系列与 `docs/plans/` 下其他系列大纲的关键差异：0 基础新学必须靠真实 API 调用把抽象认知变成手感
  - 总结：结论 + 边界——什么能做什么不能做、留给后面哪一阶段
  - 面试：4 个「面试官会问」+ 答题要点
  - 参考：官方文档 / 规范 / 延伸阅读的精确链接（本篇真正用到的 2~4 条）
- **本阶段独有的形态：增量实验**。阶段一的实验是五个互不相干的脚本；阶段二的实验是同一个网关逐篇长大；本阶段的实验是**同一个对话系统逐篇长大**——`_sdk/` 在 02 篇建起上下文组装器，03 加压缩，04 加记忆，05 加缓存，06 加长文本处理；01 篇先产出「可版本化的 Prompt 模板」供后续每篇复用。实验目录编号即系统演进顺序

### 为什么 6 篇、为什么不设导读/收口

**为什么 6 篇一一对应模块 3.1~3.6，不拆不并**：阶段二把 2.2、2.3 拆成两篇，是因为它们各自含「技能栈完全不同的两半」（服务端 vs 浏览器、数据契约 vs 意图契约）。阶段三的六个模块每一个都是一块独立技能栈——Prompt 是「文案工程」，组装是「预算调度」，压缩是「信息取舍」，记忆是「存储检索」，缓存是「成本机制」，长上下文是「架构权衡」——硬合并才会臃肿。所以一一对应，不拆不并。

**为什么取消独立导读篇**：导读要承担的元认知纠偏（**Context Engineering ⊃ Prompt Engineering**、**上下文是稀缺资源**）下沉到 01 篇「概念」段——讲 Prompt 时天然要回答「Prompt 在上下文里是什么位置」，这是最自然的切入（阶段二已有「取消独立导读、契约下沉到 01」的先例）。

**为什么取消收口篇**：阶段二的收口篇存在，是因为「实验代码要变成生产 SDK 包」（07 篇搬进 `packages/ai-sdk`）。本阶段的产物是「带记忆与缓存的对话系统 demo」，本就留在 `labs/`，不存在「搬进 packages」的收口动作——阶段二 07 篇已划清边界：**SDK 不拥有缓存策略（本阶段）、检索（阶段四）**，上下文层是应用侧能力，不属于 SDK 边界。路线图三条里程碑各自在对应篇验收：里程碑 1（组装方案）→ 02 篇，里程碑 2（长期记忆）→ 04 篇，里程碑 3（缓存成本）→ 05 篇。

## 各篇详细大纲

### 第 01 篇：Prompt 工程进阶：提示词从文案到资产

**副标题**：Prompt 只是上下文的一小块——但这一小块值得像代码一样管理

**学习目标**：能说清 System Prompt / Few-shot / CoT / ReAct / Reflection 各自解决什么、在什么任务里是多余；能把 Prompt 当代码管理——版本化、可回滚、可 A/B、可回归

**前置准备**：DeepSeek key；沿用阶段二 07 篇 `_sdk/` 的 `ChatProvider`（若已搬进 `packages/ai-sdk` 则直接引包）；预计花费 ¥0.5

#### 一、概念：先站对位——Context Engineering ⊃ Prompt Engineering

- 现象：很多人以为「提示词写得好不好」决定了模型输出的全部，于是把大量时间花在打磨一段 prompt 的措辞上；真正的效果上限却在「这段 prompt 放进上下文时，身边还放了什么、放了多少」
- 直觉定义：Prompt 是「你给模型的指令」，上下文是「模型这次能看到的一切」。**前者是后者的一小块**
- 先立阶段三最重要的一个认知（本篇与整阶段反复回指）：**Context Engineering ⊃ Prompt Engineering**。路线图的阶段三之所以叫「上下文工程」而不是「Prompt 工程进阶」，正是因为：把内容放进窗口这件事，比「这句话怎么写」更决定效果
- 那为什么还要单独一篇讲 Prompt？因为它是上下文里**唯一由你完全控制、且值得沉淀成资产**的那一部分——它要按代码管理

#### 二、深入：五种手段的定位 + 一份 System Prompt 规范 + 版本化

- **五种手段的定位区分**（路线图 3.1 的核心，一次性讲清，不是越多越好）：
  - **角色设定（Role / Persona）**：定「你是谁」，收敛回答的语气与专业边界——医疗场景里用来锚定「这是用药咨询，不是开处方」
  - **指令清晰化 + 分隔符**：指令要可执行，多段内容用 `###` / `<context>` 分隔，防止模型把指令与资料混在一起（**分隔符是防注入的第一道篱笆，阶段九展开**）
  - **Few-shot**：校正输出格式，2 个「输入 → 输出」示例比十句「请按格式输出」有效（阶段二 04 篇讲过，这里补「示例数量与顺序敏感性」——示例的顺序会影响模型学到什么，这不是玄学）
  - **CoT**：引导推理过程，「先算再答」能提升复杂任务准确率；但在抽取/简单问答里加 CoT 会拖慢且跑偏（阶段二 04 篇的结论，升华）
  - **ReAct / Reflection**：只做「思想预告」——ReAct 是「边想边做」（阶段五展开），Reflection 是「答完自我批判再修正」；**本阶段不展开循环，只讲清思想**
- **System Prompt 设计规范**（本篇第二块硬货）：角色、边界（什么能做/什么不做/什么要转人工）、拒绝策略（「不知道就说不」，承接阶段一 02 篇的结论）、输出格式约束（回指阶段二 04 篇的 Schema）
- **Prompt 版本管理**（本篇的「资产」落点，为阶段九评估铺路）：把 Prompt 当代码——**版本化**（每条 prompt 有版本号与变更记录）、**可回滚**、**可 A/B**（同一测试集跑两版对比）、**可回归**（每次改 prompt 都要跑一遍固定测试集，防止「改好了 A 场景、改坏了 B 场景」）
- **边界声明**：CoT 的完整推理循环、ReAct 的动作-观察循环留阶段五；用评估集量化「哪版 Prompt 更好」留阶段九；本阶段只把「版本化 + 固定测试集回归」的最小机制跑通

#### 三、案例：3 版 Prompt × 5 题对照 + 最小版本管理器

- 项目：`labs/phase3-context/01-prompt-asset/`
- 实验 A：三版 Prompt 的对照——同一用药咨询场景，v1（裸指令「回答这个用药问题」）/ v2（角色 + 边界 + 输出格式约束）/ v3（v2 + 2 个 Few-shot 示例）；固定 5 个测试题（正常咨询 / 问剂量换算 / 问「能不能自己加量」/ 问超出范围的问题 / 问处方解读），记录三个指标：**格式符合率 / 边界触达（该拒绝时是否拒绝）/ 每次平均 token**
  - **要看见**：v1 格式乱、该拒绝时不拒绝；v2 格式稳、边界生效；v3 格式更稳但 token 变多——**每一版都在「效果」和「成本」之间挪动，没有免费午餐**
- 实验 B：最小版本管理器——写 `runEval(promptVersion, testCases)`：给定一个 prompt 版本号，跑固定测试集，输出一张「题号 → 通过/失败」表；改一版 prompt，重跑，立刻看出「哪个题被改坏了」
  - **要看见**：加一句「拒绝策略」后，拒绝题通过了，但某个正常题被误拒——**回归测试的价值：改动的影响是可量化的，不是感觉**
- 关键结论：**Prompt 不是写完就完了的文案，是要能回滚、能回归的资产；而它只是上下文工程的一小块**
- 脚本要求：启动打印「3 版 × 5 题 = 15 次调用，约 ¥0.5」；prompt 版本用独立文件存放，方便 02~06 篇复用

#### 四、总结

- 本篇结论：五种 Prompt 手段各有定位，不是越多越好；Prompt 要版本化 + 回归测试；但 Prompt 只是上下文的一块，真正的大头在「编排」
- 明确留到后面：多来源内容怎么拼进一次调用（预算 + 顺序）→ 02 篇；CoT / ReAct 的完整循环 → 阶段五；评估体系 → 阶段九

#### 五、面试

- System Prompt、Few-shot、CoT 分别解决什么问题？在什么任务里加 CoT 是负优化？
- 你怎么管理 Prompt 的迭代？怎么保证改一处不把别处改坏？
- 为什么说「Context Engineering ⊃ Prompt Engineering」？举一个「Prompt 没变但效果变了」的场景。
- 分隔符除了排版，还有什么作用？

### 第 02 篇：上下文组装：一次调用里放了什么、各占多少

**副标题**：窗口是预算，不是保险柜——每类内容都要有配额，关键信息要放头尾

**学习目标**：能拆解一次调用的上下文由哪几类内容构成，并为每类分配 Token 配额；能说清「关键信息放中间会丢」的原理与规避

**前置准备**：DeepSeek key；`gpt-tokenizer`（labs 已有依赖）；预计花费 ¥0.5

#### 一、概念：一次调用 = 六类内容拼出来的一个「现场」

- 现象：把 System Prompt、20 轮历史、50 段检索结果、5 个工具描述、工具返回的一大坨 JSON 全塞进去，问「为什么回答变蠢了」——因为**某类内容把其他内容挤出了注意力的有效范围**
- 直觉定义：上下文组装（Context Assembly）是「**把哪些内容、以什么顺序、各占多少 token 拼进这一次调用**」的决策过程
- 六类常见来源（路线图 3.2）：System Prompt + 对话历史 + RAG 检索片段 + 工具描述 + 工具返回结果 + 用户输入。**每一类都要争窗口里有限的位置**

#### 二、深入：预算配额 + 顺序影响

- **上下文预算管理**（本篇的核心）：窗口是硬上限（阶段一 01 篇已讲），但有效注意力更小。给每类内容分配配额，是为了**防止某一类（尤其超长检索结果、冗长工具返回）挤占其他类**
  - 配额示例（用药咨询）：System 5%、历史 30%、检索片段 40%、工具结果 15%、用户输入 10%——数字因场景而异，**关键是「先定配额、再往里装」这个动作**
  - 超配额怎么办：检索片段截断到 Top-K、工具结果精简只留结论、历史走压缩（03 篇）——**预算管理是这些下游手段的触发条件**
- **顺序影响（Lost in the Middle 的工程化）**：阶段一 01 篇用 needle-in-a-haystack 证明了「中间位置召回率低」；本阶段把它变成一条可执行的规则——**关键信息放头尾**：System 在最前（定角色与规则）、用户当前输入与最相关的检索片段靠近尾部（临门一脚时离生成最近）、历史与工具结果放中间（容忍被稀释）
- **为什么顺序和缓存要一起考虑**：稳定内容在前、易变内容在后，既利于注意力、又利于缓存命中（05 篇展开）。**顺序决策有两个维度：注意力 + 缓存，它们的方向恰好一致**
- **边界声明**：检索片段怎么分块、怎么取 Top-K → 阶段四；历史怎么压缩 → 03 篇；缓存机制本身 → 05 篇

#### 三、案例：token 占比表 + 头/中/尾顺序对照

- 项目：`labs/phase3-context/02-context-assembly/`（本阶段 `_sdk/` 的第一个模块：`assemble.ts`）
- 实验 A：上下文预算分配表——构造一次真实的用药咨询调用（System + 8 轮历史 + 3 段检索片段 + 2 个工具描述 + 1 段工具结果 + 用户输入），用 `gpt-tokenizer` 统计**每一类的 token 数与占比**，打印成表
  - **要看见**：8 轮历史 + 工具结果这两类往往悄悄吃掉一半以上的窗口——**预算失控通常不是检索片段，是历史与工具返回**
- 实验 B：顺序对照——把一条关键事实（「该药禁忌：与华法林合用会出血」）分别放进上下文的**头部（紧跟 System）/ 中间（夹在历史里）/ 尾部（紧跟用户输入）**，问同一个问题，看模型是否命中这条禁忌
  - **要看见**：头、尾命中，中间丢——与阶段一 01 篇的 needle 结论互相印证，但这次是**多来源真实上下文**，不是填充文本
- 关键结论：**组装不是「塞进去」，是「分配预算 + 排定顺序」；先定配额，再决定什么被截断**
- 脚本要求：启动打印「实验 B 3 次调用，约 ¥0.3」；`assemble.ts` 输出「预算分配表」，供 03~06 篇复用

#### 四、总结

- 本篇结论：一次调用的上下文是六类内容的配额博弈；预算管理 + 头尾顺序是两条最省成本的效果杠杆
- **里程碑 1 验收**：设计一个「System + 历史 + RAG 片段 + 工具结果」各有配额的上下文组装方案（`assemble.ts` 即该方案的代码化）
- 明确留到后面：历史太长怎么压 → 03 篇；检索片段怎么少而准 → 阶段四；配额固定了，怎么让前缀少花钱 → 05 篇

### 第 03 篇：上下文压缩：多轮对话不越聊越超预算

**副标题**：历史不是越长越好，是越「有用」越好——但「有用」要付出摘要的代价

**学习目标**：能在多轮对话里用摘要化 / 滑动窗口 / 关键信息提取三种手段控制历史长度，并说清各自的代价

**前置准备**：DeepSeek key；预计花费 ¥0.5

#### 一、概念：历史会线性膨胀，窗口是死的

- 现象：多轮对话越聊越长，到第 20 轮，历史占了 80% 的窗口，模型开始「忘掉」第 1 轮说过的重要事实——不是因为窗口不够大，是因为**历史把注意力稀释了，也把预算吃光了**
- 直觉定义：上下文压缩是「**在保留有用信息的前提下，把历史瘦身**」。三种手段：摘要化（把早期历史压成一段总结）、滑动窗口（只留最近 N 轮）、关键信息提取（只抽「过敏史、剂量」这类事实，其余丢弃）

#### 二、深入：三种手段，三种代价

- **摘要化（Summary Buffer）**：早期历史不再逐条保留，而是调用一次 LLM 生成「此前对话要点」摘要，往后只带摘要 + 最近几轮原文。代价：**多一次摘要调用**、且摘要是「有损压缩」——摘要模型可能漏掉关键事实，也可能把事实概括错
- **滑动窗口**：只保留最近 N 轮，更早的直接丢弃。代价：**早期事实必丢**（「第一轮说过过敏」到第 20 轮肯定没了）。所以滑动窗口单独用是危险的，通常要配长期记忆（04 篇）
- **关键信息提取**：用结构化输出（阶段二 04 篇的 Schema 能力）把对话里的**事实型信息**（过敏史、正在服的药、年龄）抽出来单独存，历史里只留「对话流」。代价：抽取只覆盖「你预先定义好的字段」，覆盖不到的会漏
- **三者不是互斥，是组合**：滑动窗口管「最近几轮原文」，摘要管「早期对话流」，关键信息提取管「必须精确的事实」——三种各管一段，才是生产级做法
- **压缩的触发时机**：不要每轮都压（摘要调用也花钱），而是**超预算才压**——历史 token 超过配额的 80% 时，触发一次压缩（回指 02 篇的配额）
- **边界声明**：长期记忆（关键信息提取之后存哪、怎么跨会话取）→ 04 篇；压缩与缓存的取舍 → 05 篇

#### 三、案例：20 轮对话 × 3 策略重建对比

- 项目：`labs/phase3-context/03-context-compression/`（`_sdk/` 第二个模块：`compress.ts`）
- 实验：20 轮对话，第 1 轮埋事实「我对青霉素过敏」；到第 20 轮，用三种策略重建历史后各问一次「我能不能吃阿莫西林」：
  - 策略 A：全量历史（20 轮原文全塞）
  - 策略 B：滑动窗口（只留最近 5 轮）
  - 策略 C：摘要化（前 15 轮压成摘要 + 最近 5 轮原文）
  - 记录：**输入 token 数 / 是否命中「青霉素过敏」事实**
  - **要看见**：A 最贵且可能触发窗口截断；B 最省但丢了过敏事实、给出危险回答；C 在中间——省 token 且保住关键事实（**前提是摘要没漏**，可再跑一次「摘要漏掉事实」的反面样本）
- 关键结论：**压缩的本质是「用损失换预算」，工程目标是让损失发生在「不重要的信息」上，而不是「过敏史」上**
- 脚本要求：启动打印「约 4 次调用（含 1 次摘要），约 ¥0.4」

#### 四、总结

- 本篇结论：历史膨胀是确定的，压缩是必须的；三种手段各有代价，生产级是组合使用，且「超预算才触发」
- 明确留到后面：关键信息提取出来的事实存哪、怎么跨会话 → 04 篇长期记忆；压缩省 token vs 缓存省前缀的关系 → 05 篇

### 第 04 篇：记忆系统：跨会话长期记忆

**副标题**：窗口里的历史会丢，向量库里的「事实」不会——难点不在存，在「什么该记、什么该忘」

**学习目标**：能区分短期记忆与长期记忆，跑通「写入 → 跨会话检索 → 遗忘更新」的完整链路；能说清记忆写入策略与遗忘机制

**前置准备**：本地 Ollama `qwen3-embedding:0.6b`（沿用阶段二 06 篇）；`docker compose up -d postgres`（`docker-compose.yml` 已含 `pgvector/pgvector:pg16` 服务）；labs 包新增 `pg` 依赖；预计花费 ¥0（本地 embedding + 本地库）

#### 一、概念：记忆不是「把历史存下来」，是「把事实留到下一次」

- 现象：上一轮对话告诉它「我对青霉素过敏」，关掉重开一问，它全忘了——因为**每一轮对话都是无状态的**（阶段一 00 篇的结论）
- 直觉定义：**短期记忆** = 当前窗口内的历史，会话结束就丢；**长期记忆** = 存到外部、下次会话能检索回来的「事实片段」，靠向量库 + 相似度检索实现
- 两者的分工：短期记忆管「这次对话聊到哪」，长期记忆管「这个用户是谁、有什么必须记住的事实」

#### 二、深入：写入策略 + 检索 + 遗忘

- **短期记忆的落地**：进程内 / Redis 会话（阶段二 07 篇的 `ChatMessage[]` 就是最朴素的短期记忆）
- **长期记忆的落地**：向量库存储「事实片段」，按需检索回上下文（04 篇是第一次把阶段二 06 篇的 Embedding 能力用在「记忆」这个真实场景上）
- **写入策略（本篇最难的认知）**：不是什么都记。三个问题——**什么值得记**（事实型：过敏史、正在服的药、年龄体重；不记寒暄、不记一次性问询）、**什么时候记**（在对话里识别到事实就写，而不是会话结束才批量写）、**如何避免噪音污染**（写错了、重复写了怎么办）
- **遗忘与更新（更难的认知）**：记忆会过期（「去年在吃阿司匹林」不代表现在）、会冲突（「过敏」vs「其实不过敏」）、会错（模型当时记错了）。三种处置：**过期**（加时间戳，检索时按新鲜度加权）、**冲突**（写入时先查「是否已有相似事实」，有则更新而非新增）、**纠错**（用户明确改口时覆盖旧事实）
- **与阶段四 RAG 的边界**（必须写清，防止「抢活」）：本阶段的向量库只做「**记忆**」这一个场景——存的是「关于用户的事实」，检索的是「这个用户说过什么」。RAG 存的是「药品说明书等知识文档」，检索的是「与问题相关的资料」。**同一套 pgvector，两个不同的应用场景**；阶段四的分块、混合检索、重排序等优化，本阶段都不做
- **存储决策说明**：长期记忆直接上 pgvector + Postgres（不先用 JSON 文件过渡），理由是——阶段四 RAG 本就要用 pgvector，本阶段提前打通这条链路，阶段四可以直接复用同一套向量库；`docker-compose.yml` 已有 `pgvector/pgvector:pg16` 服务，不需要新增基础设施

#### 三、案例：写入 → 跨会话检索 → 遗忘更新

- 项目：`labs/phase3-context/04-memory/`（`_sdk/` 第三个模块：`memory.ts`）
- 实验 A：写入与跨会话检索——`docker compose up -d postgres` → 建 `memories` 表（`id / content / embedding vector(1024) / user_id / created_at`）→ 会话一告诉它「我对青霉素过敏」「我今年 35 岁」，把这两条事实向量化写入 → **清空窗口历史**，会话二问「我能吃阿莫西林吗」，检索命中「青霉素过敏」并据此正确回答
  - **要看见**：窗口是空的，但答案是「对的」——记忆来自向量库，不来自窗口
- 实验 B：遗忘与更新——同一用户先记「对青霉素过敏」，再改口「其实上次是误诊，我不过敏」；写入时检索到相似旧事实，**更新而非新增**；再问一次，看它按新事实回答
  - **要看见**：如果不做「更新」，库里会有两条互相矛盾的事实，模型可能答出矛盾答案
- 关键结论：**记忆系统的难点不在「存」，在「写什么、什么时候写、写错了怎么办」；向量库只是它的存储层**
- 脚本要求：本地零成本，打印「本次写入 N 条事实，本地 embedding + pgvector ¥0」；缺 Ollama 或 Postgres 时给中文提示

#### 四、总结

- 本篇结论：短期记忆在窗口里会丢，长期记忆靠向量库跨会话留存；写入策略与遗忘更新是记忆系统真正的工程难点
- **里程碑 2 验收**：实现跨会话长期记忆，验证系统能记住上一轮会话里说过的事实（且用户改口后能正确更新）

### 第 05 篇：Prompt Caching：前缀缓存与成本

**副标题**：把不变的前缀放最前，10 轮对话的输入成本能降到 1/5 ~ 1/10——而且 DeepSeek 上你什么都不用改

**学习目标**：能解释缓存命中的原理与计费方式；能把上下文排成「缓存友好」的形状；能说清「压缩」与「缓存」的取舍与叠加

**前置准备**：DeepSeek key（**上下文硬盘缓存自动生效，无需任何代码改动**）；预计花费 ¥0.3

#### 一、概念：缓存省的是「重复前缀」的钱，不是「每次调用」的钱

- 现象：多轮对话里，System Prompt 和工具定义每轮都原样重发，每轮都按原价计费——这些不变的内容**每一轮都在重复付钱**
- 直觉定义：Prompt Caching 是「**把不变的前缀（System / 工具定义 / 长文档）在服务端缓存起来，下次请求里相同的前缀按更低的『命中价』计费**」
- 与「压缩」的关系（路线图 3.5 的取舍）：压缩省的是**每次调用的 token 数**（少塞 = 少花钱）；缓存省的是**重复前缀的钱**（同样的 token 按折扣价算）。**两者正交，可以叠加**——先把内容压短，再让短内容里的稳定前缀命中缓存

#### 二、深入：机制、排列规则、厂商差异

- **原理**：模型生成要算 KV Cache；如果新请求的前缀与某次历史请求**完全一致**，这段前缀的 KV 可以直接复用，于是这段 token 按「命中价」计费。**前缀一有不同，从那个不同点往后的 token 全部算 miss**
- **缓存友好的上下文排列（本篇的核心规则）**：**稳定内容在前、易变内容在后**。System Prompt、工具定义、few-shot 示例、长文档放最前（不变）；对话历史、用户输入往后放（每轮变）。**如果把时间戳、随机串放在最前，等于每轮前缀都不一样，缓存一次都命中不了**
- **与注意力排序的关系**：02 篇说「System 最前、用户输入靠近尾部」是注意力考量；本篇文章证明它**恰好也是缓存考量**——两个维度的方向一致，不用纠结
- **厂商机制差异（了解，实验主线只用 DeepSeek）**：
  - **DeepSeek：自动缓存**——无需任何代码，`usage` 里新增 `prompt_cache_hit_tokens`（命中）与 `prompt_cache_miss_tokens`（未命中）两个字段；命中价约为输入价的 1/10
  - **通义：显式缓存**——先调用一次「创建缓存」（写入价约为标准输入的 125%），之后命中约 10%；适合超长、高频复用前缀的场景
  - **Anthropic：prompt caching**——`cache_creation` / `cache_read` 两档计费，用 `cache_control` 标记要缓存的前缀
- **边界声明**：缓存策略与「历史压缩」的联合优化（先压短、再命中）是本阶段收尾的组合拳，但不是万能——「用户每轮都在换话题」的场景里前缀命中率天然低

#### 三、案例：10 轮对话 × 稳定前缀 vs 破坏前缀

- 项目：`labs/phase3-context/05-prompt-caching/`（`_sdk/` 第四个模块：`cost.ts`）
- 实验：同一段 10 轮对话，两个版本各跑一遍：
  - 版本 A（缓存友好）：System + 工具定义在最前，历史逐轮追加在后
  - 版本 B（破坏缓存）：每一轮都在最前面加一个随机串 / 时间戳，其余相同
  - 逐轮打印 `usage` 里的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，最后算两张成本对比表（用命中价 1/10 估算）
  - **要看见**：版本 A 从第 2 轮起 hit tokens 逐轮增长，10 轮累计输入成本降到约 1/5~1/10；版本 B 几乎全程 miss——**「前缀一变，后面全部失效」的实证**
- 关键结论：**缓存不是配置出来的，是「排」出来的——排列对了，钱就省了；排列错了，缓存形同虚设**
- 脚本要求：启动打印「20 次调用（两版本各 10 轮），约 ¥0.3」；成本表用命中价与未命中价分别标注

#### 四、总结

- 本篇结论：缓存省的是「重复前缀」的钱，命中取决于「稳定在前、易变在后」的排列；与压缩正交，可叠加
- **里程碑 3 验收**：对比开启/关闭缓存（稳定前缀 vs 破坏前缀，同一对话 10 轮）的成本差异，量化缓存收益（1/5~1/10）
- 明确留到后面：模型分级路由 + 语义缓存的更大成本优化 → 阶段九；长文档作为「稳定前缀」的进一步应用 → 06 篇

### 第 06 篇：长上下文策略：窗口够大 ≠ 全塞进去

**副标题**：整本书塞进去是三重代价——成本、延迟、注意力稀释；「定位后精读」才是正解

**学习目标**：能说清「长上下文 vs RAG」的取舍；能实现分段 Map-Reduce 摘要与「关键段落定位后精读」两种策略；知道窗口扩展技术（RoPE 外推等）是「怎么来的」即可

**前置准备**：DeepSeek key（长上下文 + 缓存命中，正是它的强项）；多份药品说明书文本（可脚本生成或从公开说明书取材）；预计花费 ¥2.5（本阶段唯一较贵的一篇——贵在长文档的 token 长度）

#### 一、概念：窗口大 ≠ 该把整本书塞进去

- 现象：模型号称 128K、200K 窗口，于是有人把几十页说明书整份塞进去问「有哪些禁忌」——答案漏了中间明确写着的一条，还多花了几倍的钱、多等了几秒
- 直觉定义：长上下文策略回答「**面对一份远超『该读的量』的长文档，怎么读**」。窗口够大是「能塞」，但「该塞」是另一回事——**成本、延迟、注意力稀释三重代价**（阶段一 01 篇已讲注意力稀释，本篇讲它如何反过来指导架构选型）

#### 二、深入：长上下文 vs RAG 的取舍 + 三种策略

- **长上下文 vs RAG 的取舍（面试高频）**：
  - 长上下文：整份文档进窗口，适合「需要全局关联、跨段推理」的任务（对比两份说明书的相互作用、总结一份长报告）；代价是成本、延迟、注意力稀释
  - RAG：先检索再精读，适合「找某一条具体信息」的任务（查「禁忌有哪些」）；代价是「检索不到就答不出」，跨段关联弱
  - **医疗说明书场景的结论**：查具体条目走 RAG（阶段四），全局对比走长上下文——**二者不是替代，是按任务选**
- **三种策略**：
  - **分段 Map-Reduce 摘要**：把长文档切成能塞进窗口的若干段，每段分别摘要，再把各段摘要汇总成一份全局摘要
  - **递归摘要**：Map-Reduce 的递归版——两两合并摘要，再合并，直到一份（适合超长文档，层级越多信息损耗越大）
  - **关键段落定位后精读**：先用「廉价手段」（关键词 / 摘要）定位到相关段落，再把这几个段落原文精读——**这是「长上下文」和「检索」思路的杂交，也是本阶段收官想建立的直觉**
- **窗口扩展技术（了解）**：RoPE 外推、位置插值（NTK、YaRN）——知道「长上下文能力是怎么来的、为什么不是免费的」即可，不碰数学（路线图原则：原理够用即止）
- **边界声明**：正式 RAG（分块、向量库、混合检索、重排序）→ 阶段四；本阶段只建立「什么时候该用长上下文、什么时候该去检索」的选型直觉

#### 三、案例：长文档 × 三种读法

- 项目：`labs/phase3-context/06-long-context/`（`_sdk/` 第五个模块：`long-doc.ts`）
- 实验：多份药品说明书拼接成一份长文档，在**中间偏后**位置埋一条唯一事实（如某药的召回批号）；三种读法各跑一次，记录**输入 token / 延迟 / 是否命中埋点**：
  - 读法 A：全塞——整份文档直接进窗口
  - 读法 B：分段 Map-Reduce 摘要——切段 → 各段摘要 → 汇总
  - 读法 C：定位后精读——先用关键词定位到相关段 → 只把这几段原文塞进去
  - **要看见**：A 最贵、延迟最高、中间埋点可能丢；B 最省但摘要可能把唯一事实概括没了；C 在召回与成本间平衡——**「先定位、再精读」是三个里的性价比之王**
- 关键结论：**窗口是能力，不是策略；策略是「用最少的 token 让最相关的原文出现在窗口里」**
- 脚本要求：启动打印「本实验约 3 次长上下文调用 + 3 次摘要调用，约 ¥2.5」；长文档脚本生成，避免侵权

#### 四、总结

- 本篇结论：长上下文与 RAG 是按任务选的两个武器，不是二选一；「定位后精读」是长文档处理的性价比之王
- 阶段三总结：到这里你已经能回答路线图阶段三的三条里程碑——
  1. 设计上下文组装方案（System + 历史 + RAG 片段 + 工具结果各有配额）→ 02 篇
  2. 跨会话长期记忆（记住上一轮说过的事实）→ 04 篇
  3. Prompt Caching 成本对比（同一对话 10 轮）→ 05 篇
- 明确留到后面：把「定位后精读」升级成真正的 RAG（分块、向量库、混合检索、重排序）→ 阶段四；把上下文管理能力装进 Agent（多步工具调用）→ 阶段五
- **成果物交付**：把本阶段六篇的 `_sdk/` 汇总成「带上下文组装 + 历史压缩 + 长期记忆 + Prompt Caching 的对话系统」，落到 `labs/phase3-context/`（不搬进 `packages/ai-sdk`——上下文层是应用侧能力，SDK 边界已在阶段二 07 篇划清）
